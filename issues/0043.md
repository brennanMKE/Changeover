> 🟢 Resolved 2026-09-15 — Each started job now gets its own `JobID`-keyed `JobLog` that outlives the next `start`, with stable row ids, timestamps and coalesced HandBrake progress, and the log area shows milestones even after the 2,000-line ring evicts them (5e8c9e2, review fix 199a5d3).

**Review (2026-09-15, claude-opus-5).** 5e8c9e2 is in scope and the buffer, store and classification are sound, but it did not fix the user-visible bug and it hid real HandBrake errors. 199a5d3 fixes four things:

1. **Evicted milestones were never displayed.** `MetadataEntryView.logArea` and `JobController.logLines` both rendered `currentLog.lines`, the capped ring. A milestone evicted from the ring survived only in `milestones`, which nothing rendered. The screen therefore still lost `── Starting`/`▶ Job` off the top of a long encode. `latestProgress` was never rendered either, so HandBrake progress, previously visible, disappeared from the log. The fix adds `JobLog.displayLines`, backed by the pure `nonisolated static mergedForDisplay(lines:milestones:latestProgress:)`. It lists the milestones older than the ring's first line, then the ring, with `latestProgress` placed by id. A milestone still in the ring shows once. The cost is O(milestones + lines), and progress placement uses a binary search. The view and `logLines` both read it.
2. **The progress rule hid glued error messages.** `isProgressOnly`'s prefix-plus-no-`] ` rule treated two real capture lines as pure progress:
   - `failure-disk-full-hb1.11.2-exit4.log`: `"Encoding: task 1 of 1, 65.53 % (… ETA 00h00m16s)ERROR: avformatMux: … No space left on device'"`
   - `failure-encode-canceled-int-hb1.11.2-exit1.log`: `"Encoding: task 1 of 1, 24.35 %Signal 2 received, terminating …"`

   Before this ticket that only kept them out of the failure tail. Once `JobLog` coalesced progress, the disk-full error went into `latestProgress` and the next percentage overwrote it. `isProgressOnly` now whole-matches HandBrakeCLI's progress shapes:
   - `Encoding: task n of m, [Searching for start time, ]pp.pp %[ (…)]`
   - `Scanning title n of m, [preview p, ]pp.pp %`
   - `Scanning title n of m...`
   - `Muxing: this may take awhile...`

   Across the stub and the five HandBrake 1.11.2 captures, the new rule differs from the old one on exactly those two lines. As a side effect, both lines now also enter the failure classifier's `LogTailBuffer`, which gives it more evidence, not less; `HandBrakeFailureClassifierTests` is unchanged and passes. `progressFraction` now returns `nil` for a non-progress line, as its doc comment already claimed.
3. **`milestones` was unbounded, and between jobs that is a real leak.** The log that stays `currentLog` after a job (or before the first job) collects every idle scan's `▶ Scanning: N%` lines and every start or eject refusal. Those are milestones, and the menu bar app stays up indefinitely. The fix adds `milestoneCapacity` (default 1,000), deliberately independent of the ring's `capacity`.
4. **The test gap the implementer found.** New `manyMilestonesAllSurviveWhenTheyOutnumberTheRingCapacity` appends 12 milestones interleaved with ordinary lines into a 5-line ring.

**Checked and fine:**

- **`LogLine.id`** is monotonic, unique and stable *within one `JobLog`*. It is never reused after eviction, and progress updates consume ids too, so id order is arrival order. It is **not** unique across jobs, because every `JobLog` starts at 0. That is harmless for today's single-log view: when `currentLog` swaps, SwiftUI just reuses rows. Across jobs, `(JobID, LogLine.id)` is the key.

- **`DiscReliabilityLog.Record.jobID`** is backward-compatible: the synthesized `Decodable` uses `decodeIfPresent` for an `Optional`, and a nil value is omitted on encode. A test now proves it.
- **Isolation.**

  - `JobLog` and `JobLogStore` are MainActor, fed from the existing `Task { @MainActor }` hops.
  - The progress `Regex` is a read-only `nonisolated(unsafe) static let`, matched from `ProcessRunner`'s handler queue and from MainActor.

## Description

Every log line from `makemkvcon` and `HandBrakeCLI` is appended to `logLines: [String]`, a `@State` array in `MetadataEntryView` that is reset to `[]` at the start of each job (`Changeover/MetadataEntryView.swift:8`, `:146`). With a queue, two jobs produce interleaved output into one array, the array grows without limit across a three-disc session, and a finished job's log is gone the moment the next one starts.

## Root cause

By the time of this pass (the `### Plan refresh (2026-09-15)` section, which superseded the original description), the log had already moved off the view and onto `JobController` (#0002) and was already capped (`defaultMaxLogLines = 2000`) — so the "unbounded array inside a view" premise was stale. Four real gaps remained, all in `JobController.swift`:

1. `logLines = []` at the top of `start(request:settings:)` destroyed the previous job's log the moment a new one started — nothing else in the app could ever read it again.
2. Rows were identified by array offset (`ForEach(Array(jobs.logLines.enumerated()), id: \.offset)`, `MetadataEntryView.swift:129`), which re-identifies every remaining row on every eviction past the cap.
3. Every line — HandBrake's several-times-a-second progress lines included — competed for the same single 2,000-line cap as the pipeline's own milestone lines (`── Starting`, `▶ Job`, `✓`/`✗` outcomes), so a long encode could push those out long before the job finished.
4. Lines carried no timestamp.

## Fix

Added `Changeover/Jobs/JobLog.swift`, two new pure/reference types:

- **`LogLine`** — `Codable`/`Sendable`/`Hashable`/`Identifiable`, with a monotonic `id` (never an array offset), a `timestamp`, `text`, and `isMilestone`.
- **`JobLog`** (`@Observable`, MainActor by default — unchanged isolation per the plan refresh) — a capped ring (`lines`, default capacity 2,000) for the lines a person reads; a `milestones` list that a line is copied into (never evicted by the `lines` cap — the whole point of this ticket; unbounded as implemented, capped separately by `milestoneCapacity` in review) when it classifies as a milestone; and `latestProgress: LogLine?`, which a progress-only line replaces instead of appending, so it never grows `lines` and can never be evicted.
- **`JobLogStore`** — a small addition beyond the ticket's original type list, added per the orchestrator's handoff ("key the log buffer by JobID... a simple bounded store"). Since #0042's `Job`/`JobSnapshot`/history hadn't landed yet (#0041 deliberately deferred them), there was nowhere yet to hang "the log lives on `Job`". `JobLogStore` is a `[JobID: JobLog]` map bounded to the most recent `maxJobs` (default 10), owned by `JobController`. `start` now asks it for a fresh `JobLog` per job instead of wiping `logLines` in place — the previous job's `JobLog`, object and all, keeps existing in the store, reachable by its own `JobID`, until `maxJobs` evicts it. This is the actual fix for gap 1, and is shaped so #0042 can lift a `JobLog` onto `Job` without redoing eviction or classification.

**Classification (`JobLog.classify`/`hasMilestonePrefix`, both `nonisolated static`, pure):**

- The pipeline's four existing prefixes — `──`, `▶`, `✓`, `✗`.
- `⚠` matched on its leading Unicode scalar (U+26A0 WARNING SIGN) so both variation-selector forms — `⚠︎` (U+FE0E, `DVDPipeline.swift`) and `⚠️` (U+FE0F, `PlexOrganizer.swift`) — count, without listing each one.
- An indented (three-space) continuation line counts as a milestone only when the *previous appended (non-progress) line* was one — one bit of state (`previousLineWasMilestone`) — covering `FailurePresenter`'s detail lines under a `✗` headline and the "…and N more" follow-ups under several other `DVDPipeline` milestones.

**Progress coalescing.** `EncodeController.isProgressOnly` was made `internal` (was `private`) rather than duplicated (the review then made it whole-match HandBrake's progress shapes, because the inherited rule hid glued error lines; see Resolution notes); `JobLog.isProgressOnly` forwards to it, so the log buffer and the failure classifier's tail can never disagree about what counts as progress. Added `EncodeController.progressFraction(fromLogLine:) -> Double?`, a pure parser for `"Encoding: task <n> of <m>, <pp.pp> %"` — the seam #0041's `JobState.progress` can use once a progress source exists; nothing consumes it yet.

**`JobController` wiring.** `currentLog: JobLog` (never `nil`, unlike `currentJobID`/`lastOutcome` — see Gotchas) replaces the private `logLines`/`maxLogLines` storage. The existing `logLines: [String]` stays as a computed back-compat property (`currentLog.lines.map(\.text)` as implemented; `currentLog.displayLines.map(\.text)` after review), so every pre-existing reader — production and test — kept working unchanged. `append(_:)` now just forwards to `currentLog.append(line)`. A new `retainedLog(forJobID:)` exposes the store for a future history view (#0042/#0048) and for the one new `JobControllerTests` case proving retention.

**View.** `MetadataEntryView.logArea` now keys its `ForEach` on `LogLine.id`, scrolling to the last row's id instead of a bare count. As implemented it read `jobs.currentLog.lines`, which never showed an evicted milestone or any progress. The review switched it to `jobs.currentLog.displayLines`.

**`DiscReliabilityLog.Record`** gained an additive `jobID: String?` (per #0041's review handoff), set from `DVDPipeline.jobID.rawValue` at the one production call site. Optional and additive: the synthesized `Decodable` treats a missing key as `nil`, so existing `disc-reliability.jsonl` lines with no `jobID` still decode.

**Decisions made (user AFK, delegated):**

- **`currentLog` is non-optional**, unlike `currentJobID`/`lastOutcome`. Refusal messages (`start`'s guards, `ejectDisc`'s `EjectPolicy` refusals) and disc-scan output can happen before any job has ever successfully started, and the old code appended all of that into the same single `logLines` array. Making `currentLog` optional would have needed a fallback buffer for exactly that traffic anyway, so `JobController.init` just builds an initial, not-yet-retained `JobLog` up front. It's discarded (never destroyed *in the ticket's sense* — it was never retained anywhere to begin with) the first time `start` actually succeeds and swaps in a store-backed log, which mirrors the old wipe-at-first-successful-start behavior for that specific pre-job traffic only.
- **`JobLogStore` was added even though the plan refresh only asked for "a controller-owned `JobLog`".** The orchestrator's handoff for this pass asked explicitly for "keyed by JobID... latest N jobs retained (a simple bounded store)". A single controller-owned `JobLog` alone cannot satisfy "the log is no longer wiped at the start of each job" for more than the current job; the store is the minimum needed to keep a *previous* job's log alive, without building any part of #0042's real history/`Job` type.
- *(Superseded in review: `milestoneCapacity`, default 1,000, independent of the ring, bounds the log that stays `currentLog` between jobs.)* **`milestones` has no separate cap** (the original plan sketch said "separately capped"). A single job's own milestone count is a few dozen at most even with #0031's per-extra loop, nowhere near the several-thousand-line `lines` cap — a second number to tune would never fire in practice. Revisit if a real job proves otherwise.
- **The "two `Job` instances interleaved" test from the original Notes was dropped**, per the plan refresh: Phase 3 went with option A (serial, disc-bound jobs — #0040), so no two jobs ever log concurrently; that test only applies to option B.

## Gotchas

- **The first falsification mutation was a false negative.** Evicting `milestones` past `capacity`, mirroring `lines`' own eviction, sounds like the obvious way to break "milestones are never evicted" — but the one test covering it only ever appends a single milestone, so a capacity-based eviction on `milestones` never triggers. The mutation that actually reproduces the historical bug is deriving `milestones` from whatever's still in `lines` after eviction, which is what the pre-#0043 code effectively did (one array, one cap, no separate retention). Worth remembering for anyone re-falsifying this later: prove the mutation actually exercises the code path the test is supposed to catch, not just that it changes behavior in the abstract.
- **`EncodeController.isProgressOnly`/`progressFraction` living in `EncodeController` rather than `JobLog`** was a deliberate call to avoid duplicating HandBrake's line-format knowledge in two places; `JobLog.isProgressOnly` is a one-line forward. If a MakeMKV-specific progress format is ever added, it should extend `EncodeController`'s rule (or a sibling), not grow a second copy inside `JobLog`.
- **No new Xcode project-file edit was needed** for `Changeover/Jobs/JobLog.swift` — the target uses a file-system-synchronized group, so the new file under `Changeover/Jobs/` was picked up automatically by both the local `xcodebuild` and the synced `gordon` build.

## Long Description

A single DVD rip emits thousands of lines — `makemkvcon` prints a progress line per chunk and `HandBrakeCLI` prints one per few frames unless muted. Both are streamed line by line into the closure (`Changeover/RipController.swift:31-41`, `Changeover/EncodeController.swift:35-45`), and the closure just appends. Three retained jobs at tens of thousands of lines each is tens of megabytes of `String` held live, rendered through a `ForEach(Array(logLines.enumerated()), id: \.offset)` (`Changeover/MetadataEntryView.swift:99`) that rebuilds the enumerated array on every append.

The fix is a per-job capped ring buffer that belongs to the `Job`, not the view. Phase 4 needs exactly this too: `RemoteControl.md:344` sketches `case logReplay([String]) // buffered backlog, on subscribe`, which is only implementable if a bounded backlog exists per job on the host.

One nuance worth keeping: not all lines are equal. The pipeline's own markers — `"── Starting: …"`, `"✓ Rip complete: …"`, `"✗ Ripping failed."` (`Changeover/DVDPipeline.swift:17`, `:32`, `:35`, `:51`, `:61`) and `PlexOrganizer`'s `"✓ Moved to: …"` (`Changeover/PlexOrganizer.swift:28`) — are the lines a human actually reads, and they must survive the ring buffer evicting ten thousand progress lines on top of them.

## Steps to reproduce

1. Rip a disc and watch the log area fill.
2. Start a second job. The log area is empty; the first job's output no longer exists anywhere.
3. Leave a long encode running and watch memory grow with no ceiling.

## Expected behavior

Each `Job` owns its own log. The log is capped so a long session cannot grow without bound, the pipeline's own milestone lines are retained even after eviction, and a finished job's log is still readable from the queue view. Lines from two concurrently running jobs never appear in the same buffer.

## Actual behavior

One shared unbounded `[String]` in a view, cleared per job. Lines from a concurrent rip and encode would interleave into it with no way to tell which job produced which line, since the callback is a bare `(String) -> Void` closing over the array (`Changeover/MetadataEntryView.swift:149-151`).

### The type

```swift
@Observable
final class JobLog {
    private(set) var lines: [LogLine] = []     // capped ring
    private(set) var milestones: [LogLine] = [] // never evicted, separately capped
    private(set) var droppedCount = 0

    let capacity: Int = 2_000

    func append(_ text: String)
    func snapshot(limit: Int? = nil) -> [String]   // for Phase 4 logReplay
}

struct LogLine: Codable, Sendable, Hashable, Identifiable {
    let id: Int             // monotonic per log, stable for ForEach
    let timestamp: Date
    let text: String
    let isMilestone: Bool
}
```

`id` is a monotonic counter rather than the array offset. The current `ForEach(Array(logLines.enumerated()), id: \.offset)` (`Changeover/MetadataEntryView.swift:99`) is already fragile, and it breaks outright once eviction shifts every offset — SwiftUI would treat the whole list as changed on every eviction.

Milestone classification: a line is a milestone if it begins with one of `──`, `▶`, `✓`, `✗`. Those prefixes are already the pipeline's own convention (`Changeover/DVDPipeline.swift:17`, `:32`, `:35`, `:51`, `:61`; `Changeover/RipController.swift:15`, `:51`, `:60`; `Changeover/EncodeController.swift:16`, `:52`, `:61`; `Changeover/PlexOrganizer.swift:28`, `:30`). Do not sniff for MakeMKV or HandBrake message text — that is a parser, and it belongs to Phase 2's `DiscScanner` work, not here.

Eviction: when `lines.count == capacity`, drop from the front and increment `droppedCount`. A `RangeReplaceableCollection.removeFirst()` on an `Array` is O(n); with 2,000 elements and a line rate in the low hundreds per second that is fine, and the alternative — a real circular buffer with a head index — complicates `ForEach` identity for no measured gain. Revisit only if profiling says so, and say so in `## Gotchas` if you do.

### Isolation

`JobLog` is MainActor by default and stays that way. `append` is only ever called from MainActor because both controllers already hop before invoking the callback (`Changeover/RipController.swift:38`, `Changeover/EncodeController.swift:42`). Do not mark `JobLog` `nonisolated` or make it an `actor` to "make it safe from the process handler" — that would be solving a problem the existing hop already solved, and it would force the call site into an `await` inside a `readabilityHandler`.

The routing change that makes concurrent jobs work: today the closure is built in the view and closes over view state (`Changeover/MetadataEntryView.swift:149-151`). After this ticket the scheduler builds it per job — `{ @MainActor line in job.log.append(line) }` — capturing the `Job`, so two simultaneously running jobs write to two different buffers with no ambiguity and no shared array.

### Risks

- **Log rate driving MainActor.** Every line is a separate `Task { @MainActor in log(trimmed) }` hop (`Changeover/RipController.swift:38`), one per line, and a `readabilityHandler` chunk can contain dozens. With a rip and an encode running concurrently that doubles. If the UI becomes unresponsive during a concurrent rip+encode, the fix is to batch inside the handler — hop once per chunk with `[String]` rather than once per line — and that is worth doing pre-emptively here since this ticket is already in both files.
- **`droppedCount` must be surfaced.** A log view that silently starts in the middle looks like data loss. [#0048](0048.md) renders "… 14,332 earlier lines dropped" at the top.
