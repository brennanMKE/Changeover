# 0043 — Log lines go into an unbounded array inside a view and are destroyed at the start of the next job

| | |
|---|---|
| **Status** | open |
| **Phase** | 3 — Unattended multi-disc |
| **Module** | JobLog / JobQueue |
| **Platform** | macOS |
| **First seen** | 2026-09-11 |

## Description

Every log line from `makemkvcon` and `HandBrakeCLI` is appended to `logLines: [String]`, a `@State` array in `MetadataEntryView` that is reset to `[]` at the start of each job (`Changeover/MetadataEntryView.swift:8`, `:146`). With a queue, two jobs produce interleaved output into one array, the array grows without limit across a three-disc session, and a finished job's log is gone the moment the next one starts.

## Long Description

A single DVD rip emits thousands of lines — `makemkvcon` prints a progress line per chunk and `HandBrakeCLI` prints one per few frames unless muted. Both are streamed line by line into the closure (`Changeover/RipController.swift:31-41`, `Changeover/EncodeController.swift:35-45`), and the closure just appends. Three retained jobs at tens of thousands of lines each is tens of megabytes of `String` held live, rendered through a `ForEach(Array(logLines.enumerated()), id: \.offset)` (`Changeover/MetadataEntryView.swift:99`) that rebuilds the enumerated array on every append.

The fix is a per-job capped ring buffer that belongs to the `Job`, not the view. Phase 4 needs exactly this too: `RemoteControl.md:344` sketches `case logReplay([String]) // buffered backlog, on subscribe`, which is only implementable if a bounded backlog exists per job on the host.

One nuance worth keeping: not all lines are equal. The pipeline's own markers — `"── Starting: …"`, `"✓ Rip complete: …"`, `"✗ Ripping failed."` (`Changeover/DVDPipeline.swift:17`, `:32`, `:35`, `:51`, `:61`) and `PlexOrganizer`'s `"✓ Moved to: …"` (`Changeover/PlexOrganizer.swift:28`) — are the lines a human actually reads, and they must survive the ring buffer evicting ten thousand progress lines on top of them.

## Steps to reproduce

1. Rip a disc and watch the log area fill.
2. Start a second job. The log area is empty; the first job's output no longer exists anywhere.
3. Leave a long encode running and watch memory grow with no ceiling.

## Expected behavior

Each `Job` owns its own log. The log is capped so a long session cannot grow without bound, the pipeline's own milestone lines are retained even after eviction, and a finished job's log is still readable from the queue view. Lines from two concurrently running jobs never appear in the same buffer.

## Actual behavior

One shared unbounded `[String]` in a view, cleared per job. Lines from a concurrent rip and encode would interleave into it with no way to tell which job produced which line, since the callback is a bare `(String) -> Void` closing over the array (`Changeover/MetadataEntryView.swift:149-151`).

### The type

```swift
@Observable
final class JobLog {
    private(set) var lines: [LogLine] = []     // capped ring
    private(set) var milestones: [LogLine] = [] // never evicted, separately capped
    private(set) var droppedCount = 0

    let capacity: Int = 2_000

    func append(_ text: String)
    func snapshot(limit: Int? = nil) -> [String]   // for Phase 4 logReplay
}

struct LogLine: Codable, Sendable, Hashable, Identifiable {
    let id: Int             // monotonic per log, stable for ForEach
    let timestamp: Date
    let text: String
    let isMilestone: Bool
}
```

`id` is a monotonic counter rather than the array offset. The current `ForEach(Array(logLines.enumerated()), id: \.offset)` (`Changeover/MetadataEntryView.swift:99`) is already fragile, and it breaks outright once eviction shifts every offset — SwiftUI would treat the whole list as changed on every eviction.

Milestone classification: a line is a milestone if it begins with one of `──`, `▶`, `✓`, `✗`. Those prefixes are already the pipeline's own convention (`Changeover/DVDPipeline.swift:17`, `:32`, `:35`, `:51`, `:61`; `Changeover/RipController.swift:15`, `:51`, `:60`; `Changeover/EncodeController.swift:16`, `:52`, `:61`; `Changeover/PlexOrganizer.swift:28`, `:30`). Do not sniff for MakeMKV or HandBrake message text — that is a parser, and it belongs to Phase 2's `DiscScanner` work, not here.

Eviction: when `lines.count == capacity`, drop from the front and increment `droppedCount`. A `RangeReplaceableCollection.removeFirst()` on an `Array` is O(n); with 2,000 elements and a line rate in the low hundreds per second that is fine, and the alternative — a real circular buffer with a head index — complicates `ForEach` identity for no measured gain. Revisit only if profiling says so, and say so in `## Gotchas` if you do.

### Isolation

`JobLog` is MainActor by default and stays that way. `append` is only ever called from MainActor because both controllers already hop before invoking the callback (`Changeover/RipController.swift:38`, `Changeover/EncodeController.swift:42`). Do not mark `JobLog` `nonisolated` or make it an `actor` to "make it safe from the process handler" — that would be solving a problem the existing hop already solved, and it would force the call site into an `await` inside a `readabilityHandler`.

The routing change that makes concurrent jobs work: today the closure is built in the view and closes over view state (`Changeover/MetadataEntryView.swift:149-151`). After this ticket the scheduler builds it per job — `{ @MainActor line in job.log.append(line) }` — capturing the `Job`, so two simultaneously running jobs write to two different buffers with no ambiguity and no shared array.

### Risks

- **Log rate driving MainActor.** Every line is a separate `Task { @MainActor in log(trimmed) }` hop (`Changeover/RipController.swift:38`), one per line, and a `readabilityHandler` chunk can contain dozens. With a rip and an encode running concurrently that doubles. If the UI becomes unresponsive during a concurrent rip+encode, the fix is to batch inside the handler — hop once per chunk with `[String]` rather than once per line — and that is worth doing pre-emptively here since this ticket is already in both files.
- **`droppedCount` must be surfaced.** A log view that silently starts in the middle looks like data loss. [#0048](0048.md) renders "… 14,332 earlier lines dropped" at the top.
- **Codable `LogLine` for the wire.** Keep it `Codable` now; Phase 4's `logReplay` should ship `[LogLine]`, not `[String]`, so the client can show timestamps and milestones. Flag that as a correction to the sketch at `RemoteControl.md:344`.

**Replacement.** The `JobLog`/`LogLine` shape above stands, with these changes:

- **Don't reuse or rename `LogTailBuffer`** (`JobOutcome.swift:146`). It is a lock-guarded, off-actor tail for the failure classifier, a different job.
- **Milestone prefixes, from today's code:**
  - `──`, `▶`, `✓`, `✗`;
  - `⚠︎` (`DVDPipeline.swift:137`, `:139`, `:458`);
  - `⚠️` (`PlexOrganizer.swift:137`).

  Match on the leading `⚠` scalar so both variation-selector forms hit. `FailurePresenter`'s detail lines are indented three spaces and follow a `✗` headline (`DVDPipeline.swift:114-120`). A three-space line counts as a milestone only when the previous appended line was one: one bit of state in `append`, tested.
- **Recommended: coalesce progress instead of appending it.**
  - Make `EncodeController.isProgressOnly` (`:229-233`) internal.
  - Add a pure `nonisolated static func progressFraction(fromLogLine:) -> Double?` for `Encoding: task 1 of 1, 45.12 %`.
  - Have `JobLog` keep only `latestProgress: LogLine?` for those lines.

  This frees the 2,000-line ring for lines a person reads, and gives #0041's `JobState.progress` a source. Note the progress line can arrive glued to a timestamped log line (`Fixtures/handbrake/main-feature-dragon-tattoo.log` has exactly one such line). Those must still be appended, which is `isProgressOnly`'s existing rule.
- **Ownership and routing.**
  - The log lives on `Job` (#0041).
  - `JobController.start` builds the closure `{ line in job.log.append(line) }` (#0042's `JobContext.log`).
  - If this lands before #0042, first swap `JobController.logLines`' storage for a controller-owned `JobLog`, then move it onto `Job`.
- **Isolation is unchanged: MainActor.** Lines arrive through `Task { @MainActor in log(line) }` from `EncodeController.encode` (`:124`, `:163`, `:170`), `MakeMKVRipper` and `DiscScanner.scan` (`:102`). `PlexOrganizer.move` awaits `log` directly.
  - Per-line unstructured `Task`s are not guaranteed to reach MainActor in emission order, so `LogLine.id` records arrival order.
  - Batching per chunk inside `ProcessRunner` would fix ordering and hop cost, but that file is heavily reviewed (#0009).
  - Unlike the original plan, **do not batch pre-emptively**: only one process runs at a time under option A. Batch only if a real log shows reordering or the UI stutters.
- **View.** `MetadataEntryView.logArea` (`:124-149`) switches to `ForEach(log.lines)` keyed on `LogLine.id`, and scrolls to `lines.last?.id`. The full per-job log UI is #0048's.

## Notes

**Verification.** A ring buffer is pure logic — no disc, no subprocess — so the `Issues.md` manual caveat does not apply and this must be unit-tested. `ChangeoverTests/JobLogTests.swift` must cover:

- appending `capacity` lines keeps all of them and `droppedCount == 0`;
- appending `capacity + n` keeps exactly `capacity`, the retained window is the **last** `capacity` lines in order, and `droppedCount == n`;
- `LogLine.id` is strictly increasing and is never reused after eviction — assert the first retained id equals `n` after `n` evictions;
- every one of the four milestone prefixes classifies as a milestone, an ordinary progress line does not, and a milestone appended before `capacity * 2` ordinary lines is still present in `milestones` afterwards;
- `snapshot(limit:)` returns at most `limit` lines, most recent last;
- `LogLine` round-trips through JSON;
- two `Job` instances appending concurrently-produced lines keep them separate — construct two jobs, interleave appends, assert each buffer contains only its own lines.

The one thing tests cannot prove is that MainActor stays responsive under a real two-process line rate. That is manual: run a rip and an encode at the same time, scroll the queue view, and note in `## Verification` which disc was used and whether the UI stayed smooth.
