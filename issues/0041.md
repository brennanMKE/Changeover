## Description

There is no `Job` type at all — a job is an implicit thing that exists for the duration of one `DVDPipeline.run()` call and is described only by a boolean (`Changeover/MetadataEntryView.swift:7`). Before a queue can exist, a job needs a stable `JobID`, an explicit stage enum with validated transitions, and a `Codable` snapshot that Phase 4 can put on the wire.

## Root cause

Two independent gaps, both from before the code that would need them existed:

- **Two unrelated job ids.** `JobController.start` minted one string
  (`Self.makeJobID()`) for `currentJobID` and the notification identifier;
  `DVDPipeline.run()` independently minted a *second*, unrelated string for
  its working directory and its own `▶ Job` log line. Nothing tied the two
  together — they only looked similar because both called the same
  `yyyyMMdd-HHmmss-XXXX`-shaped helper.
- **No phase state machine.** "What stage is a job in" was inferable only
  from which line of `DVDPipeline.run()` was executing, and a failure was a
  log line plus an early `return` with no residue anywhere else in the app.
  There was nothing to validate a transition against, and nothing for a
  future caller (a queue view, a history store) to read.

## Fix

Per the `### Plan refresh (2026-09-15)` section below (which supersedes the
original plan — `JobStage`/`JobFailure` already exist with other, wire-format
meanings since #0007, and the rip stage the original plan's stages describe
was removed by #0014) and this pass's own scope decisions, recorded here:

**New types, `Changeover/Jobs/`:**

- `JobID.swift` — a validated `String` wrapper in the existing
  `job-yyyyMMdd-HHmmss-XXXX` shape (not a `UUID` — that would have been a
  *third* shape), gated on `WorkingFiles.isJobID` in both
  `init?(rawValue:)` and JSON decoding, so `WorkingFiles`'s deletion guards
  keep protecting every `removeItem` unchanged. `JobController.makeJobID()`
  now forwards to `JobID.make(date:).rawValue`.
- `JobPhase.swift` — `starting`/`encoding`/`fallback`/`organizing`/
  `succeeded`/`failed`/`cancelled`, with an explicit
  `allowedTransitions: [JobPhase: Set<JobPhase>]` table (never a `switch`
  with `default:`, which would silently accept an edge to a case added
  later with no entry) — pinned by `JobPhaseTests
  .everyCaseHasATransitionTableEntry`, which walks `JobPhase.allCases`.
  `organizing` has no outgoing `cancelled` edge: the move into Plex is a
  `FileManager` operation over in milliseconds, and interrupting it halfway
  could leave a half-placed file in the library.
- `JobState.swift` — a pure `nonisolated` value type: `phase`, `progress`
  (always `nil` today — no progress parser exists for either CLI tool
  yet), and `outcome: JobOutcome?` (the pre-existing, untouched wire type).
  `advancing(to:)` moves between non-terminal phases; `finishing(with:)`
  maps a `JobOutcome` onto `.succeeded`/`.failed`/`.cancelled` and
  validates the mapped target against the *same* transition table — so a
  `.cancelled`-reasoned failure arriving while `organizing` is rejected
  outright, not silently reinterpreted as a plain `.failed`. Both return
  `nil` (never crash) on an illegal edge, structurally enforcing
  `outcome != nil ⇔ phase.isTerminal`: a terminal phase is only ever
  reachable through `finishing(with:)`.

**Id unification.** `DVDPipeline` now takes a caller-supplied
`jobID: JobID` (defaulted to `JobID.make()` so the ~25 existing test
construction sites compile unchanged) instead of minting its own; its
internal `let jobID = JobController.makeJobID()` is gone.
`JobController.Runner` gained `JobID` as a 7th parameter; `start(request:
settings:)` mints exactly one `JobID`, stores its `.rawValue` in
`currentJobID` (kept a plain `String` — every existing reader is
unaffected), threads it into the runner, and passes `jobID.rawValue` to
`JobNotifier.notify`. The same value now names the working directory, the
`▶ Job` log line, the notification identifier and (via `runFallback`) the
fallback's rip job directory.

**`DVDPipeline` reports phase changes.** A new defaulted
`reportPhase: @MainActor (JobPhase) -> Void = { _ in }` property, called at
the three points `run()` actually crosses a phase boundary: before the
primary encode (`.encoding`), before the MakeMKV fallback (`.fallback`),
and before the move into Plex (`.organizing`) — traced against every
`return await finish(...)` site in `run()` to confirm each one lands on a
phase whose mapped terminal target is legal (e.g. a preflight failure
returns while still `.starting`, and `.starting → .failed` is legal).
Terminal phases are never reported directly; `JobController.finish` derives
those from the returned `JobOutcome` via `JobState.finishing(with:)`.
`Runner` gained the phase-report closure as an 8th parameter, appended
after the existing 6 (never inserted in the middle) so every existing fake
`Runner` closure only needed two trailing wildcards added, never a
reordering of an existing named binding.

`JobController.pipelineRunner` stays a plain, context-free `static let`
(no `self` capture) — both new parameters are threaded straight through to
`DVDPipeline`, exactly as `log` already was — so `init` never has to reason
about ordering a self-capturing closure against Swift's two-phase
initialization.

**`JobController` wiring.** A new `private(set) var currentJobState:
JobState?`, mirroring `currentJobID`/`lastOutcome`: `nil` only before the
first job of the app's lifetime, left at its terminal value after a job
finishes (never reset to `nil`). `start` sets it to `.initial` right after
minting the id (alongside `currentJobID`/`isRunning`, unaffected by and not
affecting `sleepAssertion.begin()`'s position, which is unchanged from
#0047 — still after every guard). A new private `applyPhase(_:)`, bound to
the `Runner`'s phase-report closure, validates each report against
`JobState.advancing(to:)`; an invalid or out-of-order report is logged
(`"⚠︎ Ignored invalid phase transition …"`) and dropped. `finish(_:)` — the
single terminal transition, where `sleepAssertion.end()` unconditionally
still lives, unchanged from #0047 — applies `JobState.finishing(with:)`
*silently* (see Gotchas for why this one isn't logged) alongside it.

**Mechanical test update.** Every existing 6-parameter fake `Runner`
closure — 29 call sites across `JobControllerTests`, `PowerAssertionTests`
and `JobControllerEjectTests` — gained two trailing wildcard parameters
for the new `JobID`/phase-report arguments. Applied with a small Python
script matching `runner: { … in`, verified to have touched exactly the 29
`runner:` sites and none of the unrelated `scanRunner:` fakes (different
typealias, untouched). Purely mechanical — no behavioral change to any of
those tests.

**Decisions made (user AFK, delegated):**

- **Job/JobSnapshot are not built here.** The refresh's `@Observable Job`
  class (holding `metadata`/`disc`/`state`) and `JobSnapshot` (the
  `Codable` wire projection) are `JobQueue`/history-shaped — #0042, per
  #0040's own recommended order, is where "`JobController` holds `current`
  plus history" and "`DVDPipeline` starts reporting its phases" both live.
  Building them now, unused, would be exactly the kind of half-wired,
  premature surface the original ticket's own "Risks" section warns
  against ("don't add the queue here"). What *is* built — `JobID`,
  `JobPhase`, `JobState`, and `DVDPipeline`'s `reportPhase` hook reporting
  into a flat `JobController.currentJobState` — is the exact foundation
  #0042 needs to build `Job`/`JobSnapshot` on top of without redoing any of
  the validation logic.
- **`Runner`'s signature was widened rather than left alone.** The
  alternative — capturing a self-referencing phase-report closure inside
  `JobController.pipelineRunner` at `init` time — runs into Swift's
  two-phase initialization (`self` can't be captured, even weakly, until
  every stored property has a value, and `runner` is one of them). Widening
  `Runner` and passing both new arguments at call time (the same pattern
  `log` already uses) sidesteps that entirely, at the mechanical cost of
  touching 29 existing fakes.
- **`finish`'s outcome-to-phase reconciliation is silent, not logged** —
  see Gotchas.

## Gotchas

- **`finish`'s outcome-to-phase reconciliation had to become silent.**
  *(Superseded by the review, 5ff3c7a: the fakes now report phases through
  `fakeSuccess`, and `finish` logs a mismatch again. See Resolution notes.)*
  The first version logged `"⚠︎ Ignored a terminal phase report that
  doesn't fit …"` whenever `JobState.finishing(with:)` returned `nil`. That
  broke `JobControllerTests`/`PowerAssertionTests`/`JobControllerEjectTests`
  — nearly every existing fake `Runner` returns `.succeeded(...)` directly
  without ever calling the new phase-report closure, which leaves
  `currentJobState` at `.starting`, and `.starting → .succeeded` is
  (correctly) illegal — only `.organizing` may finish successfully. Logging
  that on every such fake flooded `logLines` and broke several tests'
  exact-content assertions. A real production mismatch is currently
  impossible (every `return await finish(...)` site in `DVDPipeline.run()`
  was traced and lands on a phase whose mapped terminal target is legal),
  so the reconciliation is applied silently: `currentJobState` still
  updates correctly for every real case, and a hypothetical future
  DVDPipeline bug that broke this invariant would leave `currentJobState`
  stale rather than crash or spam the log — the same "log and drop"
  philosophy as `applyPhase`, just without the log line for this
  particular, currently-unreachable-in-production path. `applyPhase`
  itself (the mid-job, explicit report path) still logs every rejection,
  since a report there is always a deliberate signal from `DVDPipeline`,
  never a fake silently doing nothing.
- **Widening `Runner` was the higher-risk-looking option that turned out
  cheaper than the alternative.** A self-capturing `pipelineRunner` avoids
  touching any existing fake, but hits Swift's two-phase-init rule the
  moment it tries to capture `self` while `runner` (a `let`) is itself
  still being assigned in `init`. Appending both new parameters at the end
  of `Runner`'s tuple (never inserting them in the middle) meant every one
  of the 29 existing fakes needed only `, _, _` appended before their `in`
  — no reordering of any existing named binding (`request`, `selection`,
  `extras`, `disc`, `log`) was needed anywhere.
- **`FailureReason.cancelled` already existed** (#0009), so `JobState
  .finishing(with:)`'s cancelled-reason mapping needed no new wire case —
  confirmed by reading `JobOutcome.swift` before writing anything, per the
  plan refresh's warning that the original ticket's `JobFailure` enum
  sketch was already redundant with `FailureReason`.

## Long Description

This is the foundation ticket for Phase 3 and it deliberately ships no behaviour change. It adds types.

Two separate representations are needed and conflating them is the mistake to avoid:

- **`Job`** — an `@Observable final class`, host-only, reference semantics. It is what SwiftUI rows bind to, so that updating one job's progress invalidates one row rather than the whole list. Reference types are required here: an array of `@Observable` structs does not exist, and putting mutable job state in a value type inside `JobQueue.jobs` means every progress tick invalidates every view reading the array.
- **`JobSnapshot`** — a `Codable`, `Sendable`, `Hashable` struct projected from a `Job`. This is the protocol surface. It never gains an `@Observable` macro and never gains a closure or a `Task` handle, because those cannot cross the wire.

The stage enum is the part that earns unit tests. Right now "what stage is the job in" is inferable only from which line of `DVDPipeline.run()` is executing (`Changeover/DVDPipeline.swift:16-62`), and failure is a log line plus an early `return` (`:32-34`, `:47-50`) that leaves no residue anywhere.

## Steps to reproduce

1. Open `Changeover/DVDPipeline.swift` and try to answer "is this job ripping or encoding right now" from outside the pipeline.
2. Open `Changeover/MetadataEntryView.swift:142-155` and try to name the job that `startRipping()` just began.
3. Look for anywhere in the codebase that could reject an illegal transition such as encoding a job that already failed.

## Expected behavior

A job is a first-class value with a stable identity: `JobID` (a typed wrapper, `Codable` + `Hashable` + `Sendable`), a `JobStage` enum covering every stage the pipeline actually has, a `JobFailure` describing *why* a job is in `.failed`, and a `JobState` that bundles stage, progress and failure with an enforced invariant. Illegal transitions are rejected, not silently applied.

## Actual behavior

None of these types exist. The only observable job state in the app is `isProcessing: Bool` and an array of log strings, both `@State` inside a view, and both discarded when the window closes.

### Types

```swift
struct JobID: Hashable, Codable, Sendable, CustomStringConvertible {
    let rawValue: UUID
    init() { rawValue = UUID() }
    var description: String { String(rawValue.uuidString.prefix(8)) }
}
```

A typed wrapper, not a bare `UUID`. Phase 4 will carry several kinds of id (job, peer, disc) and a bare `UUID` in the protocol means nothing stops a peer id being passed where a job id belongs.

```swift
enum JobStage: String, Codable, Sendable, CaseIterable {
    case queued          // accepted, waiting for the drive lane
    case ripping         // makemkvcon running; the disc must stay in the drive
    case awaitingEncode  // rip done, disc ejected, waiting for the encode lane
    case encoding        // HandBrakeCLI running
    case organizing      // moving into the Plex folder structure
    case done
    case failed
    case cancelled
}
```

`awaitingEncode` is the stage that makes Phase 3 possible and it is exactly the stage the current code has no room for: `DVDPipeline.run()` goes from `RipController.rip` returning (`Changeover/DVDPipeline.swift:27-35`) straight into `EncodeController.encode` (`:41-46`) with no point at which the job could wait.

Legal transitions — this table is the specification the tests assert against:

| From | To |
|---|---|
| `queued` | `ripping`, `cancelled`, `failed` |
| `ripping` | `awaitingEncode`, `failed`, `cancelled` |
| `awaitingEncode` | `encoding`, `cancelled`, `failed` |
| `encoding` | `organizing`, `failed`, `cancelled` |
| `organizing` | `done`, `failed` |
| `done`, `failed`, `cancelled` | — terminal, no outgoing edges |

Note `organizing` cannot be cancelled: it is a `FileManager.moveItem` (`Changeover/PlexOrganizer.swift:27`) that is over in milliseconds, and cancelling halfway would leave a half-placed file in the Plex library.

```swift
enum JobFailure: Codable, Sendable, Hashable, Error {
```

### Risks

- **Transition validation must be total, not `default:`-driven.** A `switch` on `(from, to)` with a `default: return false` silently rejects a stage added later. Use `CaseIterable` plus an explicit `allowedTransitions: [JobStage: Set<JobStage>]` and a test that walks `JobStage.allCases` and fails if any case is missing a key.
- **`Codable` stability.** `JobStage` is a `String` raw-value enum precisely so a Phase 4 client on an older build decodes `"encoding"` rather than an integer whose meaning shifted when a case was inserted. Do not convert it to `Int` raw values.
- **Don't add the queue here.** The temptation is to give `Job` a `next` pointer or a position. Ordering belongs to [#0042](0042.md); a job that knows its own position cannot be reordered without mutating it.
