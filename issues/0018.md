## Description

`EncodeController` passes no `--encoder` and no `--encoder-preset` (`EncodeController.swift:25-33`), so HandBrakeCLI silently picks x264 and `medium` for every disc this app has ever encoded. Neither choice was ever made — they are defaults that arrived by omission. A measurement run on 2026-09-12 compared seven encoder/preset/RF combinations on the same source segment and **x265 at RF 23, preset `slow`, wins**: 30% smaller than today's output at a *higher* VMAF score. Adopt it, and make both flags explicit named constants in `Config` so the next person can see what the app is doing without reading HandBrake's own defaults.

## Root cause

Not a defect — a decision that had never been made explicit. `EncodeController.arguments` never emitted `--encoder` or `--encoder-preset`, so HandBrakeCLI's own defaults (x264, `medium`) silently stood in for that decision on every encode this app has ever run. #0014 deliberately left this alone pending "a separate experiment"; this ticket is that experiment's result landing.

## Fix

Followed the `## Plan` as written, with no deviation:

- Added three `nonisolated static let` constants to `Config` (`Changeover/Config.swift`): `videoEncoder = "x265"`, `videoQuality = "23"` (was `"21"`), `encoderPreset = "slow"`. `videoQuality`'s doc comment was **rewritten**, not appended to — it now says a smaller RF number means better quality and a bigger file, that x264 and x265 do not share an RF scale, and that x265 RF 23 looks roughly like x264's old RF 21. `videoEncoder`'s comment names the codec change (HEVC) and points at this issue's measurement; `encoderPreset`'s comment says presets trade encode time, not quality, and that `slower` was measured and rejected. `audioEncoder` is untouched.
- Added `--encoder Config.videoEncoder` and `--encoder-preset Config.encoderPreset` to `EncodeController.arguments(source:title:output:)`, adjacent to `--quality`, so the three video decisions read as a group. `--quality` needed no code change beyond `Config.videoQuality`'s new value.
- Updated the one stale line in `CLAUDE.md`'s Architecture section to name the current three encoding constants instead of "`videoQuality` RF21, `audioEncoder`".
- Extended #0014's `qualityAndAudioEncoderComeFromConfig` (rather than duplicating it) to also assert `--encoder`/`--encoder-preset` by reference to `Config`, and added `encoderFlagsAppearExactlyOnce` to guard against a duplicated flag if this ticket and #0014 ever land out of order. The two existing exact-array tests (`argumentsForMainFeature`, `argumentsForExplicitTitleIndex`) were updated to include the two new flags in the expected vector.

## Long Description

Today `Config` carries two encoding constants (`Config.swift:8`, `:11`):

```swift
nonisolated static let videoQuality = "21"
nonisolated static let audioEncoder = "copy:aac,copy:ac3"
```

and the argument vector uses them as `--quality 21` and `--aencoder copy:aac,copy:ac3`. There is no `--encoder` and no `--encoder-preset` anywhere in the file. HandBrakeCLI's own defaults fill the gap — **x264** and preset **`medium`** — which means two of the four decisions that determine what every output file looks like are invisible in this codebase. [#0014](0014.md)'s revised plan noticed this and deliberately left it alone ("**Encoder settings are being decided elsewhere.** A separate experiment is choosing `--encoder-preset` and possibly x265 over x264. **Do not bake any encoder tuning into this ticket.**"). **This ticket is that decision landing.**

### The experiment

Run on `joe` (Apple M1 mini, 8 GB) on 2026-09-12. Source: *The Girl With The Dragon Tattoo*, title 1, a **120-second segment starting 30 minutes in**, video only (`-a none`) so audio encoding did not pollute the size or the timing. VMAF was computed against a **lossless x264 encode of the same segment** as the reference.

| Setting | Size (bytes) | vs baseline | VMAF | Speed (fps) |
|---|---|---|---|---|
| x264 medium RF21 *(current default)* | 7,819,193 | — | 81.698 | 521 |
| x264 slow RF21 | 7,427,096 | −5.0% | 81.767 | 371 |
| x264 slower RF21 | 7,514,717 | −3.9% | 81.867 | 239 |
| x265 medium RF21 | 6,622,062 | −15.3% | 81.663 | 207 |
| x265 medium RF23 | 4,865,790 | −37.8% | 80.846 | 240 |
| **x265 slow RF23 (chosen)** | 5,460,455 | **−30.2%** | **81.768** | 90 |
| x265 slower RF24 | 4,738,005 | −39.4% | 81.565 | 22 |

### Why x265 slow RF23 and not x265 slower RF24

`slower`/RF24 is another 9% smaller and still scores well — but it runs at **22 fps**. On a 98-minute feature that is roughly **7.5 hours** of encoding, against about **1h49** for `slow`/RF23. [#0040](0040.md)'s unattended multi-disc throughput cannot absorb a 7.5-hour per-disc encode; the queue stops being a queue. `slow` at RF 23 is the point on this curve where the size saving is nearly all collected and the wall clock is still within a single overnight run for several discs.

The other rejected rows, briefly: x264 `slow`/`slower` buy 4–5% for 30–55% more time — not worth changing the encoder family for. x265 `medium` RF23 is faster than `slow` RF23 (240 fps vs 90) and smaller, but it is the **only row in the table that scores below the current baseline** on VMAF (80.846 vs 81.698). The whole argument for this change is "smaller *and* not worse", and `medium` RF23 gives that up.

x265 RF23 scores **above** the current x264 RF21 baseline (81.768 vs 81.698) while producing a file 30% smaller. That is the headline: this is not a quality-for-size trade, it is a straight win on both axes, paid for in encode time (521 fps → 90 fps, roughly 5.8× slower).

### Caveats — read these before treating the table as settled

These are recorded honestly because the table is persuasive and the evidence behind it is thinner than it looks.

1. **x264 and x265 RF scales are not comparable.** An RF number means something different to each encoder; x265 RF 23 is approximately x264 RF 21 perceptually. **That offset is the entire reason the chosen RF went up rather than down.** Anyone reading "we moved from RF 21 to RF 23" as "we lowered the quality target" has misread it. Say so in the constant's doc comment, because this is the single most likely misunderstanding of this change.
2. **The absolute VMAF numbers are low and should be ignored.** Everything lands near 81, not near 95, for three compounding reasons: the reference is a lossless encode of *already-compressed MPEG-2* DVD video, it was scored at **712×472**, and the VMAF model is tuned for 1080p. **Only the relative comparison between rows is valid.** Do not quote 81.768 anywhere as a quality figure for the pipeline's output.
3. **This is one 2-minute segment of one film.** Grain and motion respond very differently to x265 — a heavily grained catalogue title, or a dark, low-motion film, may not sit where *Dragon Tattoo* sits. A second sample from a visibly different source would strengthen this materially and is cheap.
4. **HEVC changes the playback compatibility surface.** See the dedicated section below; this is the one caveat that can turn the change into a net loss.

### The compatibility risk — this is the part that can go wrong

x264 produces H.264; x265 produces **HEVC**. That is a different codec on the wire to every Plex client, not a tuning change.

Apple TV 4K direct-plays HEVC. Older Plex clients — older Apple TV hardware, smart-TV apps, browsers, anything on the network that is not the newest box — may not, and Plex's response to a client that cannot direct-play is to **transcode on the server**. A transcode is not a visible failure; it is CPU burned on the Plex host on *every single playback*, silently, forever. Trading 30% of disk for a permanent per-playback transcode is a bad trade, and it would be invisible until someone looks at the Plex dashboard.

This is not hypothetical for this setup. `/Volumes/Media/Plex` already contains `check_mp4_compatibility.sh` and `diagnosing_mp_4_files_for_plex_apple_tv.md` — **someone already wrote a compatibility checker and a diagnosis document for this exact library**, which means this class of problem has cost time here before. [#0017](0017.md) exists for the same reason and its residual question is literally "direct play or transcode?".

**Treat this as a precondition of the switch, not a follow-up.** Verify HEVC output against the real clients this library is watched from — before the default changes, or in the same sitting.

## Plan

### 1. `Config` — three explicit constants

All `nonisolated`, per `CLAUDE.md` (anything the nonisolated controllers touch must itself be nonisolated, as the existing statics already are). Keep them as `String` to match `videoQuality`'s existing shape and to go straight into the argument array without formatting.

- **`videoEncoder`** = `"x265"` — the value for `--encoder`. Doc comment: what it is, that it produces HEVC, and a pointer to this issue for the measurement.
- **`videoQuality`** = `"23"` — changed from `"21"`. Doc comment **must** carry the scale warning: lower is better quality and a bigger file, *and* x264/x265 RF scales are not comparable — x265 RF 23 ≈ x264 RF 21. The existing comment's "19 = high quality, 21 = balanced, 23 = smaller file" is written for x264 and is now actively misleading; rewrite it, don't append to it.
- **`encoderPreset`** = `"slow"` — the value for `--encoder-preset`. Doc comment: presets trade encode time, not quality; `slower` was measured and rejected at 22 fps.

Leave `audioEncoder` untouched.

### 2. The argument vector

Two entries, in the same style as the existing ones:

```
--encoder         <Config.videoEncoder>
--encoder-preset  <Config.encoderPreset>
```

`--quality` already exists and needs no change beyond `Config.videoQuality`'s new value. Place the encoder flags adjacent to `--quality` so the three video decisions read as a group.

If [#0014](0014.md) has landed, this goes in `EncodeController.arguments(source:title:output:)`. If not, it goes in the literal array at `EncodeController.swift:25-33` and #0014 carries it forward — flag the coupling in the commit message either way.

### 3. Tests

Swift Testing (`import Testing`, `@Test`, `#expect`), per `CLAUDE.md`. These run with no disc and no HandBrakeCLI:

1. `--encoder` is present and its value is `Config.videoEncoder` **by reference**.
2. `--encoder-preset` is present and its value is `Config.encoderPreset` by reference.
3. `--quality` carries `Config.videoQuality` by reference (extend #0014's planned assertion rather than duplicating it).
4. Neither flag appears more than once — a duplicated `--encoder` is the likely merge artefact if this and #0014 land out of order.

Referencing the constants rather than asserting the literals `"x265"` / `"slow"` is deliberate: the test's job is that the vector cannot diverge from `Config`, not that `Config` holds a particular string. The decision lives in the constant and its doc comment.

### 4. Manual verification — what actually has to happen on hardware

State all of this explicitly in `## Verification`, naming the disc and the client:

1. **One full feature encoded end to end with the shipped settings.** Record wall clock and output size, and compare against a known-good x264 file from the existing library. The expectation is roughly 1h49 and roughly 30% smaller; a wild divergence means the flags are not reaching HandBrake.
2. **Play it.** Not on a Mac only — see the risk below.
3. **Plex direct play vs transcode**, on the Apple TV client, watching the Plex dashboard during playback. Run `/Volumes/Media/Plex/check_mp4_compatibility.sh` against the output first and read `diagnosing_mp_4_files_for_plex_apple_tv.md` alongside it; do not re-derive what those already encode.
4. **A second, visibly different source** — ideally something grainy — to address caveat 3. Even a single extra 2-minute segment run through the same comparison is worth more than another opinion.

### 5. Risks

- **HEVC forces a server-side transcode on some client.** The one risk that can make this change a net loss, and it fails silently. Verification step 3 is not optional. If an important client transcodes HEVC, the correct outcome is to **not adopt x265** and instead take x264 `slow` RF21 from the table (−5.0%, VMAF 81.767, 371 fps) — a much smaller win but zero compatibility exposure. Record that as the fallback so it does not have to be rediscovered.
- **The RF change will be misread as a quality reduction.** 21 → 23 looks like a downgrade to anyone who does not know the scales differ. The doc comment is the mitigation and it is load-bearing; write it for a reader who has never heard of RF.
- **Encode time increases 5.8×.** Foreseen and accepted, but it changes what "the app is running" feels like — a job that used to finish inside half an hour now runs most of two hours, with no cancel ([#0001](0001.md) G7, `JobController.swift:18-23`). Do not discover this during a demo.
- **One film, one 2-minute segment, one machine.** The table is a real measurement but it is a narrow one. Treat "30% smaller at equal quality" as an expectation to check on the first full feature, not a guarantee.
- **Do not tune further in this ticket.** `--encoder-tune`, `--encoder-profile`, `--encoder-level`, `-x`/`--encopts` are all out of scope. Three decisions, measured, shipped; anything else is a new experiment with no evidence behind it.

### 6. Explicitly out of scope

Audio settings of any kind (settled, unchanged); filter decisions ([#0016](0016.md)); subtitle flags ([#0014](0014.md) §5, [#0027](0027.md), [#0029](0029.md)); exposing any of this in the UI ([#0112](0112.md), Phase 6); re-encoding the existing library.

## Correction — encode times in the evidence table were overstated about 4.2× — 2026-09-12

The time-per-film figures quoted with the table (≈1h49 for `slow` RF23 and
≈7.5 hours for `slower` RF24 on a 98-minute feature) were miscalculated. A
98-minute feature is about 141,000 frames at 23.976 fps, so the measured speeds
give:

| Setting | Stated | Correct (98-minute feature) |
|---|---|---|
| x264 `medium` RF21 | ~19 min | ~4.5 min |
| x265 `slow` RF23 | ~1h49 | ~26 min |
| x265 `slower` RF24 | ~7h30 | ~1h47 |

The full-film run above confirms the arithmetic: 227,491 frames ÷ 94.5 fps ≈ 40 min,
matching the measured 40 m 06 s.
