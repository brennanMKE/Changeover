## Description

`DVDPipeline.run()` goes rip → encode → move in one straight-line `async` function (`Changeover/DVDPipeline.swift:16-62`) with no seam between the stages, so the optical drive sits idle for the whole encode. This ticket splits the pipeline at that seam and adds a two-lane scheduler: a drive lane with capacity 1 because there is one drive, and an encode lane that runs concurrently with it.

## Long Description

The asymmetry is the design. One optical drive means one rip — `makemkvcon mkv disc:0 …` (`Changeover/RipController.swift:19-24`) addresses a physical drive index, and two of them at once is not a policy choice, it is impossible. Encoding has no such constraint; `HandBrakeCLI` is a CPU job on a file that is already on the SSD.

So the lanes are not the same kind of thing and should not be implemented as one generic `maxConcurrency` knob:

| Lane | Capacity | Nature of the limit |
|---|---|---|
| Drive — rip (and, from [#0045](0045.md), scan and eject) | 1 | Physical. Never configurable. |
| Encode — encode, organize, cleanup | 1 | Policy. A second concurrent HandBrake finishes nothing sooner on a shared core count and competes with the concurrent rip for SSD writes. Tunable if measurement later says otherwise. |

Steady state is therefore **two external processes**: job *n* encoding while job *n+1* rips. That is exactly the Phase 3 demo (`Roadmap.md:136-141`).

A second, subtler point about queue depth: the drive lane's queue is inherently shallow, because a job in `queued` or `ripping` is bound to a physical disc that is sitting in the drive. You cannot stack three rips and walk away — the disc for job 2 cannot be inserted until job 1's disc comes out. The encode lane's queue is the one that actually grows. Getting this right is what [#0045](0045.md) is for; this ticket just has to make sure a job can *sit* in `awaitingEncode` rather than holding the drive.

## Steps to reproduce

1. Insert a disc, select a movie, press **Start Ripping**.
2. Watch the rip finish and the encode begin.
3. Observe the optical drive for the duration of the encode.

## Expected behavior

The moment the rip finishes, the drive is free and the job moves to `awaitingEncode`, then to `encoding` when the encode lane is free. A second job can be ripping while the first is encoding. Two rips never overlap. Every stage transition is driven by a scheduler that owns the lane accounting, not by control flow inside one function.

## Actual behavior

`DVDPipeline.run()` awaits `RipController.rip` (`:27-31`), then immediately awaits `EncodeController.encode` (`:41-46`), then calls `PlexOrganizer.move` (`:54-59`) and returns. There is no point in that function where another job could be scheduled onto the drive, and nothing tracks how many rips or encodes are running because at most one thing is ever running.

### Splitting the pipeline

```swift
struct DVDPipeline {
    let job: Job
    let settings: AppSettings

    func runRipStage()     async -> Result<URL, JobFailure>   // returns the ripped .mkv
    func runPostRipStage(mkv: URL) async -> Result<Void, JobFailure>  // encode + organize + clean
}
```

`runRipStage` is lines 20-35 of the current file; `runPostRipStage` is lines 38-61. The `Result` return replaces the current pattern of logging a message and returning early (`:32-34`, `:47-50`), which leaves no residue for the queue to record. `DVDPipeline` stays a plain `struct` and stays MainActor by default — `Plan.md`'s convention table names it explicitly and forbids making it an `actor`.

The path capture at `:20-24` stays exactly as it is: read `AppSettings` on MainActor, pass plain `String`s into the `nonisolated` controllers. That is the pattern that keeps `RipController` and `EncodeController` free of any reference to observable state, and it must survive this refactor untouched.

### The scheduler

```swift
@Observable
final class JobScheduler {
    private weak var queue: JobQueue?
    private var ripTask: Task<Void, Never>?
    private var encodeTask: Task<Void, Never>?

    static let maxConcurrentRips = 1      // physical: one optical drive
    var maxConcurrentEncodes = 1          // policy: see Long Description

    func pump()   // synchronous. Never async. Never awaits.
}
```

`pump()`:

```
if ripTask == nil, let next = queue.jobs.first(where: { $0.state.stage == .queued }) {
    next.transition(to: .ripping)
    ripTask = Task { [weak self] in
        defer { self?.ripTask = nil; self?.pump() }
        await self?.runRip(next)
    }
}
if encodeTask == nil, let next = queue.jobs.first(where: { $0.state.stage == .awaitingEncode }) {
    next.transition(to: .encoding)
    encodeTask = Task { [weak self] in
        defer { self?.encodeTask = nil; self?.pump() }
        await self?.runPostRip(next)
    }
}
```

Three properties of this shape are load-bearing and none of them is incidental:

1. **`pump()` is synchronous.** Under `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` every method here is MainActor-isolated, which means every `await` inside a MainActor method is a re-entrancy point — another event (a disc mount, a button press, another job finishing) can run between the suspension and the resumption and observe half-updated queue state. By keeping `pump()` free of `await`, the entire lane-accounting decision is a single atomic MainActor turn. All awaiting happens inside the per-job `Task`, whose body is also MainActor-isolated (a `Task {}` created in a MainActor context inherits that isolation) and which touches queue state only at well-defined points before and after the one `await`.

2. **The lane token is the `Task?` property itself**, not a counter. A counter can drift; a `Task?` set to `nil` in a `defer` cannot leak on an early return, a thrown error, or a cancellation. This is the mechanism by which [#0046](0046.md) guarantees a failed job does not wedge the lane.

3. **Selection is `first(where: stage == …)`, not `jobs.first`.** A terminal job at the head of the array must be skipped, not block the queue. This is the head-of-line blocking bug, and it is trivially easy to reintroduce by "simplifying" to `jobs.first`.

`runRip` / `runPostRip` are thin: transition the job, build the per-job log closure `{ @MainActor line in job.log.append(line) }` from [#0043](0043.md), call the matching `DVDPipeline` stage, and transition to `awaitingEncode` / `organizing` / `done` or to `failed` with the returned `JobFailure`.

MainActor stays free during the actual work because both controllers are already `nonisolated static func … async` (`Changeover/RipController.swift:9`, `Changeover/EncodeController.swift:9`) and run on the cooperative pool. The scheduler awaits them from MainActor; the resumption lands back on MainActor and mutates queue state there. There is no shared mutable state crossing an isolation boundary anywhere in this design — which is why there is no lock and why it must not become an `actor`.

### Testability seam

The scheduler must not construct `DVDPipeline` directly, or nothing about it can be tested without a disc. Inject:

```swift
protocol StageRunner: Sendable {
    func rip(_ job: Job, settings: AppSettings) async -> Result<URL, JobFailure>
    func postRip(_ job: Job, mkv: URL, settings: AppSettings) async -> Result<Void, JobFailure>
}
```

The production conformance wraps `DVDPipeline`. `StageRunnerStub` in the test target returns canned results after an awaitable gate the test controls, which is what makes "assert two rips never overlap" an actual assertion rather than a hope.

### Risks

- **Per-job working directories are a hard prerequisite.** With one rip and one encode running concurrently, `RipController.largestMKV(in:)` (`Changeover/RipController.swift:66-77`) scanning a shared `workingRipPath` (`Changeover/AppSettings.swift:27`) would pick up the other job's file. Phase 1 ([#0001](0001.md)) fixes this; if it has not landed, this ticket must not be started.
- **Concurrent disk write pressure.** A rip writing an `.mkv` while an encode reads another `.mkv` and writes an `.mp4`, all on one external SSD, is three streams. If throughput turns out worse than serial, the correct response is to lower `maxConcurrentEncodes` behaviour, not to serialize the lanes — measure before changing the model, and record the numbers in `## Verification`.
- **`weak self` in the Task.** The scheduler is owned by the queue which is owned by `AppDelegate` (`Changeover/AppDelegate.swift:8`), so it outlives every job in practice. Use `weak` anyway; a strong capture in a long-lived `Task` makes the retain cycle invisible.
- **Do not add a stage timeout in this ticket.** A hung `makemkvcon` is real but the mitigation is user-driven cancel ([#0046](0046.md)), not a guess at how long a rip should take.

### Plan refresh (2026-09-15)

**The premise is obsolete.** Every load-bearing statement here is about MakeMKV:

- `makemkvcon mkv disc:0` — `RipController.swift` was deleted by #0014;
- "HandBrakeCLI is a CPU job on a file that is already on the SSD";
- `largestMKV(in:)` and a shared `workingRipPath`.

Today `DVDPipeline.run()` encodes straight from the disc (`DVDPipeline.swift:318-325`), so `runRipStage`/`runPostRipStage` have no rip to split at. The only intermediate `.mkv` belongs to #0015's fallback, which runs inside the same job while the disc is still in the drive. "Two external processes from two different jobs" can't happen with one drive. It would not speed anything up either: x265 `slow` is CPU-bound, and the drive already outpaces it.

**Under #0040's option A (recommended): wontfix.** The user decides. What survives lives elsewhere:

- **Phase reporting out of `DVDPipeline`** moves to #0042.
- **"The slot is released on every path" is already true.** `JobController.start`'s `Task` always calls `finish` after the non-throwing runner returns (`JobController.swift:113-125`). #0046 adds the cancel path.
- **Lane tokens and head-of-line selection** have nothing left to test.

**Under option B: rewrite as "stage the chosen title off the disc, then encode from the staged copy".** This is a sketch, gated on an experiment.

1. **Experiment first** — needs discs on joe, manual, no code. Pick a decrypting copier and measure it. Candidates:
   - `MakeMKVRipper.rip` of one title into `Working/ripping/<jobID>/`. It already exists for #0015, but it puts MakeMKV back on the happy path, and key expiry returns as the headline failure.
   - `dvdbackup -t <n>`. A new brew dependency, using libdvdcss, with the same raw-device fallback concern as `MakeMKVReplacement-Results.md` §5.
   - A plain copy of the title's VOBs. Unverified, and likely scrambled on CSS discs.

   For each, record:
   - minutes per GB (expect about 3 at 5.6 MB/s);
   - whether HandBrake's `--title` numbering survives on the staged copy;
   - CSS behaviour on Dragon Tattoo and on one disc that hits the libdvdcss fallback.
2. **Then build.** The original scheduler design is still sound for this shape:
   - `JobPhase` gains `.queued`, `.staging` and `.awaitingEncode`;
   - `JobController` gains `pending: [Job]`;
   - a MainActor `JobScheduler` has a synchronous `pump()` and two `Task?` lane tokens;
   - selection uses `first(where:)` on phase.

   The test seam and its stub:

   ```swift
   protocol StageRunner {
       func stage(_ job: JobContext, settings: AppSettings) async -> Result<StagedSource, JobFailure>
       func encodeAndMove(_ job: JobContext, source: StagedSource, settings: AppSettings) async -> JobOutcome
   }
   ```

   - **Eject** moves to the end of staging.
   - **`Preflight.minimumFreeBytes`** (2 GB) must scale with the staged bytes of every pending job.
   - **`FallbackPolicy.discStillPresent`** (`DVDPipeline.swift:345-349`) stops making sense once the disc is gone during the encode. The fallback would have to move into staging.
3. **State the payoff plainly.** Wall clock is about C + 3E against 3E: no faster. The gain is swap cadence only.

**Unit versus disc.**

- **Under A:** nothing to test here.
- **Under B:**
  - lane accounting is unit-testable against the `StageRunner` stub, using this plan's original test list minus the MakeMKV wording;
  - the copier experiment and the demo need discs.

## Notes

**Verification.** The lane accounting is the single most testable thing in this app and must be covered by real Swift Testing cases against `StageRunnerStub` — no disc, no subprocess. `ChangeoverTests/JobSchedulerTests.swift` must cover:

- enqueueing three jobs starts exactly one rip; the other two stay `queued`;
- **two rips never overlap** — the stub records enter/exit timestamps per lane and the test asserts the rip intervals are disjoint across all three jobs;
- a rip completing moves its job to `awaitingEncode` and immediately starts the *next* queued rip, while the first job's encode starts in parallel — assert an interval where job 1 is `encoding` and job 2 is `ripping` simultaneously, which is the Phase 3 demo expressed as a test;
- `maxConcurrentEncodes == 1` is honoured: with two jobs in `awaitingEncode`, only one enters `encoding`;
- `pump()` is idempotent — calling it ten times in a row with a busy lane starts nothing extra;
- a terminal job at the head of `jobs` does not prevent a later `queued` job from starting;
- lane tokens are released on the failure path as well as the success path — stub a failing rip and assert the next queued job still starts (this overlaps [#0046](0046.md) deliberately; both tickets should assert it);
- enqueueing a job *while* a rip is in flight does not corrupt state — drive it through the stub's gate so the enqueue lands mid-`await`.

Manual verification is still required for the real thing and must say so plainly: two discs back to back, naming both, confirming from `Activity Monitor` that `makemkvcon` and `HandBrakeCLI` are running simultaneously and belong to different jobs, and noting elapsed wall-clock time against two serial jobs.
