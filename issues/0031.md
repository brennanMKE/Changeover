# 0031 — Extras have nowhere to go, so ripping them would pollute the Plex Movies library

| | |
|---|---|
| **Status** | open |
| **Module** | DiscSelection / PlexOrganizer / RipController |
| **Platform** | macOS |
| **First seen** | 2026-09-11 |

## Description

Only movies belong in the Plex library. Extras — featurettes, deleted scenes,
behind-the-scenes pieces — are worth keeping and cheap to rip from a disc that is
already spinning, but they must land **outside** the Plex roots. Plex is pointed at
`Movies` and `TV Shows`, so a new derived path such as `<root>/Clips` is invisible
to it. Nothing in the app expresses that distinction today, and
`PlexOrganizer.move(encodedFile:metadata:plexMoviesPath:log:)`
(`Changeover/PlexOrganizer.swift:8-13`) takes the destination as a bare `String`,
which means an extra can be routed into `Movies/` by passing the wrong argument.

## Long Description

The disc-selection experiment (`DiscSelection.md`) made this ticket necessary by
making it cheap. One scan now yields a confident feature identification
([#0025](0025.md)) *and* a complete, classified list of everything else on the disc.
The rip is already happening; the disc is already spinning; the marginal cost of a
few extra titles is disk space and a few minutes.

### What extras actually cost

Measured from the fixtures, at the default `--minlength` (which is where a human
would look — the `min0` captures are full of 5-second stubs nobody wants):

| disc | feature | extras | overhead | extras kept |
|---|---|---|---|---|
| The Girl With The Dragon Tattoo | 7.43 GB | 0.03 GB | **0.4%** | 4 |
| Hornets' Nest | 6.10 GB | 0.85 GB | **13.9%** | 3 |
| Hanna | 6.80 GB | 1.40 GB | **20.7%** | 7 |
| The Girl in the Spider's Web | 5.85 GB | 1.74 GB | **29.7%** | 4 |
| Super Troopers | 5.38 GB | 1.72 GB | **32.0%** | 8 |
| Weird Science | 6.30 GB | 2.29 GB | **36.3%** | 10 |
| Super Troopers 2 | 5.45 GB | 2.82 GB | **51.8%** | 6 |

The commonly quoted "13–29%" understates the tail. The real range across the corpus
is **0.4% to 51.8%**, and the worst case is a disc with a 39-minute
behind-the-scenes documentary (`super-troopers-2-min0.txt` title 30, 1.4 GB on its
own). Extras are cheap *on average* and occasionally cost half again as much as the
movie. That argues for extras being **opt-in per disc**, visible in the UI with a
running size total, rather than a global "always rip extras" setting the user sets
once and forgets.

### Why the destination must be a type, not a string

This is the substance of the ticket. `PlexOrganizer.move` currently takes
`plexMoviesPath: String` and does `createDirectory` + `moveItem` into it
(`Changeover/PlexOrganizer.swift:16-27`). Adding a second call site that passes a
different string is the obvious implementation and the wrong one: the two calls are
then distinguished only by which variable the caller happened to pass, and the
failure mode — an extra filed as a movie, with a `Title (Year) {tmdb-ID}` folder
and a `.mp4` Plex will happily index — is silent and only visible in Plex.

Make it impossible by construction:

```swift
nonisolated enum Destination {
    case feature      // <root>/Movies/<Title (Year) {tmdb-ID}>/<Title (Year).mp4>
    case extra        // <root>/Clips/<Title (Year) {tmdb-ID}>/<extra name>.<ext>
}
```

The organizer takes a `Destination` and an `AppSettings`-derived root, and *it*
computes the path. A caller cannot supply a path, so a caller cannot supply the
wrong one. The Plex naming convention (`Plan.md`, `Movies.txt`) applies to
`.feature` only; `.extra` is deliberately *not* Plex-shaped, because looking like a
Plex movie is the thing being avoided.

Keeping the extras grouped under the same `Title (Year) {tmdb-ID}` folder name is
worth doing anyway — it makes them findable, and it is what [#0120](0120.md)'s clip
library will want to walk.

### Open question: do extras need encoding at all?

**Genuinely unresolved — do not invent an answer.** Two defensible positions:

- **Keep the ripped MKV.** Extras are an archive, not a playback target. Skipping
  HandBrake saves the encode time entirely (which is most of the wall clock), keeps
  the source lossless, and avoids [#0029](0029.md)'s audio- and subtitle-selection
  problems on titles nobody curated. Costs disk: roughly 2× the encoded size.
- **Encode like the feature.** Consistent, smaller, directly playable, and if
  [#0120](0120.md) ends up sourcing montage clips from extras it will want a format
  something can actually decode on a Raspberry Pi.

The answer probably depends on what Phase 7 decides it needs, which is exactly the
kind of question [#0120](0120.md) says should not be pre-answered. Until then,
**write the destination logic so the file extension is not hard-coded** —
`MovieMetadata.fileName` hard-codes `.mp4` (`Changeover/MovieMetadata.swift:22-24`)
and `.extra` must not inherit that assumption.

## Expected behavior

A single scan produces one feature and a list of extras. The feature is encoded and
moved to `<root>/Movies/…` exactly as today. Any extras the user opted into are
ripped in the same session and land under a separate derived root — `<root>/Clips`
— which Plex does not index. The destination is chosen by a type, not a path, so
there is no code path that can place an extra in `Movies/`.

## Actual behavior

`RipController.rip` rips everything with `"all"`
(`Changeover/RipController.swift:19-24`), `largestMKV(in:)` (`:66-77`) picks one file
by size, and the rest are left in the working directory. `PlexOrganizer.move`
(`Changeover/PlexOrganizer.swift:8-32`) knows only one destination and takes it as a
`String`. `AppSettings` derives `plexMoviesPath`, `plexTVPath`, `workingRipPath` and
`workingEncodePath` from `plexMediaRoot` (`Changeover/AppSettings.swift:20-30`) —
there is no `Clips` path and no notion of a non-Plex destination.

## Notes

Mostly unit-testable, and the important part entirely so:

- **Destination path derivation** — assert that `.feature` produces
  `<root>/Movies/Blade Runner (1982) {tmdb-78}/Blade Runner (1982).mp4` and that
  `.extra` produces a path under `<root>/Clips` that does **not** begin with
  `<root>/Movies`. A test asserting "no destination derivation for `.extra` ever
  yields a path inside `plexMoviesPath`" is the one that encodes the whole point of
  the ticket.
- **Extras classification** — over the fixtures, assert the extras count and total
  size per disc against the table above.
- The `AppSettings` derivation of `clipsPath`, alongside the existing derived paths.

Needs a disc: that a multi-title rip actually produces N files with the right
durations, and that nothing appears in Plex that should not. Say which disc in
`## Verification`, and check Plex's library view — not just the filesystem — because
"invisible to Plex" is the actual claim being made.

**Do not start this before [#0028](0028.md).** Extras are ripped by the same
function, at the same `--minlength`, from the same scan; building a second rip path
while the first is still being rewritten would produce two of them.
