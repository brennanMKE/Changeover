## Description

Every rip goes through `makemkvcon` (`RipController.swift:23-29`), and MakeMKV's beta key expires roughly every two months. If it ever expires without a replacement being published, Changeover stops working entirely — a single point of failure with a third-party clock attached to it. MakeMKV should become an **optional fallback**: HandBrake is tried first, `makemkvcon` is used only if it is present and HandBrake failed, and every fallback is logged.

### 1. Blocking: the reader/termination race in `runMakeMKV` (`MakeMKVRipper.swift:444-457`)

**What the flake actually was.** The xcresult bundles on gordon
(`~/Library/Developer/Xcode/DerivedData/Changeover-*/Logs/Test/`) record it
exactly. `Test-Changeover-2026.09.12_19-07-49` (full suite, 118 tests, 117
passed) failed **one** test, `fallbackEncodeFailureIsReportedAndNeverLoops`,
with five expectations:

```
:786 (fallbackStage → .rip) == .encode
:787 (fallbackReason → .noTitlesProduced) == .toolExited(code: 5)
:792 (Self.argvLines(at: handbrakeArgvLog).count → 1) == 2
:794 (mkvArgv.count → 1) == 2
:795 (mkvArgv.filter { $0.contains(" mkv ") }.count → 0) == 1
```

So `makemkvcon info` ran once and exited 0, `mkv` never ran, and the ripper
concluded the transcript held no titles. Free space is not the cause (gordon
reports 59 GB `volumeAvailableCapacityForImportantUsage` against the 8.5 GB
the dragon-tattoo fixture needs) and the sidecar `.conf` was written
synchronously before launch.

**Cause.** `readabilityHandler` runs on FileHandle's private queue;
`terminationHandler` runs on another thread. Setting `readabilityHandler = nil`
does not wait for an in-flight invocation. If the handler has already drained
the pipe with `availableData` but is still splitting lines and appending to
`LineAccumulator` when the exit is noticed, the termination handler's
`readDataToEndOfFile()` returns EOF at once, `flush()` returns nothing, and
`continuation.resume(returning: (status, accumulator.snapshot()))` fires with
an empty or partial transcript. `EncodeController` (`:99-135`) has the same
shape, but there the transcript is only a log tail; here it is control flow.

**Reproduced.** A 30 ms `usleep` inserted between `fh.availableData` and
`handle(data)` in the readability handler — nothing else changed — produced the
identical five-expectation signature in the no-loop test, plus:

```
✘ pipelineFallsBackAndSucceedsAgainstDragonTattooFixture   :512 expected success
✘ fallbackNeverPicksAStaleOrForeignMKV                    :587 expected success
✘ fallbackFailsWithUnknownWhenMKVWritesMoreThanOneFile    :694 expected .unknown
✘ fallbackFailsWithActivationExpiredAndNeverRunsMKV       :739 (fallbackReason → .toolExited(code: 253)) == .activationExpired
✘ Test run with 41 tests in 1 suite failed … with 9 issues.
```

The last line matters most: `MSG:5021` never reached `scanMessageCodes`, so an
expired key is reported as a plain tool exit — the one classification this
ticket owns. The same signature also appears in the implementer's own #0003
falsification bundle (`…_19-05-03`, see §4a below), so it occurred naturally
twice in nine runs, both times while other suites were spawning processes.

**Production impact.** Real `info` transcripts are 12–112 KB in the fixture
corpus, arrive in several chunks, and `makemkvcon` exits right after its last
write. On a disc HandBrake has already failed on, the fallback would say
"found no usable titles" and stop; with an expired key it would say
`toolExited(code: 253)`. Both are wrong answers to the question this ticket
exists to answer.

**Required fix.** Resume exactly once, only after **both** the reader has seen
EOF and the process has terminated. One reader, not two: let the readability
handler treat empty `availableData` as EOF, record it under a lock, and have
whichever of {EOF, termination} arrives second do the flush and the resume.
Drop the termination-side `readDataToEndOfFile()`. Do **not** move all reading
to after termination — a transcript larger than the pipe buffer (64 KB;
`super-troopers-2-min0.txt` is 112 KB) would deadlock. Keep the single-resume
and resume-after-exit properties the plan's §2 requires.

While there: `scanMessageCodes` and `ripMessageCodes` are captured `var`s
mutated from the handler threads. `SWIFT_VERSION = 5.0` is why that compiles
without a diagnostic. `LineAccumulator` already keeps the whole transcript, so
compute the codes from the returned `lines` after the process ends and delete
the shared mutable state. Add a test that pins the transcript: run `info`
through the stub N times (20 is plenty; the stub is `cat`, so it costs
milliseconds) and assert the returned line count equals the fixture's
non-empty line count every time — `runMakeMKV` can be `internal` for that.

## Root cause

`DVDPipeline.run()` had no fallback path at all after #0014 removed the rip
stage: a HandBrake failure was unconditionally terminal, and `makemkvcon`
was referenced nowhere in the pipeline (`AppSettings.makemkvconPath` was
stored and persisted but never read). An expired MakeMKV key was therefore
irrelevant, but so was a perfectly valid one — any disc HandBrake failed on
failed outright, with no attempt to recover it through the tool that could.

## Fix

Followed the revised `## Plan` below closely; see it for the full design.
Summary of what landed:

- **`FallbackPolicy`** (`Changeover/FallbackPolicy.swift`) — a pure,
  exhaustive `switch` (no `default`) over `FailureReason` at the `.encode`
  stage, deciding `.notEligible` / `.unavailable(makemkvconPath:)` /
  `.attempt`. Disc-shaped reasons: `.toolExited`, `.discUnreadable`,
  `.noTitlesProduced`, `.unknown`.
- **`MakeMKVRipper`** (`Changeover/MakeMKVRipper.swift`) — a fresh
  `nonisolated enum`, structured like `EncodeController`, that scans once
  (`-r --cache=1 info`), picks the longest title, ships free-space and
  provenance guards, rips exactly one title (`-r mkv <source> <index>
  <dir>`, never `all`, never `--minlength`), and succeeds only when the
  fresh per-job directory it created (which must not already exist) holds
  exactly one non-empty `.mkv`. Device resolution goes through `statfs`
  (`f_mntfromname`) rather than `disc:0`. Does **not** reuse or restore
  `RipController`/`largestMKV(in:)` — see `## Gotchas` for the falsification
  proof.
- **`JobFailure.fallback: FallbackAttempt?`** (`Changeover/JobOutcome.swift`)
  — additive, optional, synthesized `Codable`; round-trips both directions
  with a payload that predates this field.
- **`DVDPipeline.run()`** (`Changeover/DVDPipeline.swift`) — sequences
  primary encode → (on a disc-shaped failure) `FallbackPolicy.decide` →
  optional rip + second HandBrake pass over the `.mkv` → cleanup of the job
  directory (on any rip failure, and unconditionally after the second
  encode returns) → move. Only the primary failure is ever handed to
  `FallbackPolicy`; the fallback's own result never re-enters it.
- **`DiscReliabilityLog`** (`Changeover/DiscReliabilityLog.swift`) — appends
  one JSON line per finished job (success included) to
  `~/Library/Logs/Changeover/disc-reliability.jsonl`; a write failure only
  logs a warning. `DVDPipeline.reliabilityLogURL` is a defaulted `var` so
  tests redirect it.
- **`SettingsView`** — text-only: HandBrakeCLI listed first, `makemkvcon`
  captioned optional, the path-preview row renamed "Fallback rip".
- **Stub harness** — `ChangeoverTests/Fixtures/stub-makemkvcon.sh` (new) and
  `stub-HandBrakeCLI.sh` (extended), both controlled by a sidecar
  `"$0.conf"` file rather than environment variables, so the new suite runs
  concurrently with `EncodeControllerTests`' process-wide `STUB_EXIT`
  without racing it.

No divergence from the plan's constraints: `EncodeController.swift`,
`Config.swift`, `EncodeControllerTests.swift` and `JobController.Runner`
are all untouched; no new `FailureReason`/`JobStage` case was added.

One deliberate gap from the plan's §5: `DiscReliabilityLog.Record
.makemkvVersion` exists in the schema but is always written `nil`. Capturing
`MSG:1005`'s version string would have required widening
`MakeMKVRipper.rip`'s return type beyond the signature the plan specifies
(`Result<URL, JobFailure>`), which the plan does not authorize. Noted in
`## Gotchas` rather than done silently.

### Re-pass 2026-09-12 (commit `3d3bc7c`), addressing the bounce above

Fixed exactly the four numbered items in `## Review notes`, and the §5 nit.
Nothing else in `e0a96f2` — the policy table, argument vectors, wire format,
provenance, or `EncodeController`/`Config`/`LSDVDIdentity` — was touched.

- **The reader/termination race (`MakeMKVRipper.runMakeMKV`).** There is now
  exactly one reader. `readabilityHandler` treats empty `availableData` as
  EOF and records "reader done" through a new lock-protected
  `RunCompletionGate`; `terminationHandler` no longer touches the pipe at
  all — it only records "process done" on the same gate. Whichever signal
  arrives **second** flushes the line splitter's trailing carry-over and
  resumes the continuation, exactly once. The old termination-side
  `readDataToEndOfFile()` is gone, so a transcript larger than the pipe's
  ~64KB buffer (`super-troopers-2-min0.txt`, 112KB) still drains
  incrementally rather than deadlocking (#0013's fix, preserved). Also
  removed `scanMessageCodes`/`ripMessageCodes`, the `var`s the handler
  thread was mutating (silently legal under `SWIFT_VERSION = 5.0`); message
  codes are now computed by a new pure `messageCodes(in:)` from the returned
  transcript after the process ends. Added a defensive watchdog
  (`hangTimeout`, default 4 hours) that kills a child that never terminates,
  and a `readerDelay` test seam (a no-op in production, `@escaping () ->
  Void`) so the exact race the reviewer reproduced — a delay between
  `fh.availableData` and processing it — can be reproduced deterministically
  in a test. `runMakeMKV` is `internal` now (was `private`) so tests can
  drive it directly, per the review's suggestion.
- **Regression tests for the race**, all in `MakeMKVFallbackTests.swift`:
  `runMakeMKVSurvivesAReaderTerminationRaceAndKeepsTheFinalMSGLine` (the
  reviewer's exact reproduction — a 30ms `readerDelay` against the
  key-expired fixture, asserting the final `MSG:5021` line and the resulting
  `.activationExpired` classification survive), `runMakeMKVAlwaysReturns
  TheFullTranscriptAcrossRepeatedRuns` (20 runs against the dragon-tattoo
  fixture, pinning the exact non-empty line count every time), and
  `runMakeMKVDrainsATranscriptLargerThanThePipeBufferEvenWithADelayedReader`
  (the 112KB fixture combined with the delay — proves neither truncation nor
  the #0013 deadlock).
- **`pipelineSucceedsWithHandBrakeAloneAndProbesMakeMKVNever`** now writes
  its own HandBrake `.conf` (`EXIT_DIR_INPUT=0`) instead of relying on the
  process-wide `STUB_EXIT` path it silently shared with
  `EncodeControllerTests`, and gives the makemkvcon stub an `ARGV_LOG` so
  `#expect(!fileExists(makemkvArgvLog))` can actually fail if the policy
  ever regresses.
- **`EncodeControllerTests`'s two `DVDPipeline` end-to-end tests** now set
  `pipeline.reliabilityLogURL` to a temp file, same shape
  `MakeMKVFallbackTests` already used. The §5-deferred constraint ("this is
  #0018's file") no longer applies — #0018 landed at `dd01020`, before
  `e0a96f2`.
- **§5 nit, `DVDPipeline.runFallback`.** Cleanup is skipped when the rip
  failed with `.destinationUnwritable` — the one case where the rip created

  the pipeline never deletes something it didn't create, and the "Could not
  clean up" log line is no longer spurious in that case. New test:

## Long Description

This is `MakeMKVReplacement-Path.md` §1 and step 5 of its §3, and the framing there is the point: *"The fix is not to prove HandBrake is perfect and then delete MakeMKV. It is to stop requiring MakeMKV. After step 4, a dead key means 'one fallback is unavailable' rather than 'the app is broken.'"*

### Why demotion rather than deletion

`-Path.md` §1 gives three reasons, in order of weight, and they are worth restating in full because "just delete it" is the obvious next thought:

1. **The evidence base is one disc.** Fargo ripped end to end, correctly (`-Results.md` §1). That proves the path works; it does not prove it works on 33 discs — and one of them, *The IT Crowd*, already reports malformed IFO data that MakeMKV handled gracefully.
2. **The sweep that was supposed to settle this cannot be run.** `MakeMKVReplacement-Findings.md` §6 step 4 says to run the encode across "all 33 discs in `/Volumes/Media/Media/Movies`" — but that directory holds finished `.mp4` files. `-Results.md` §8 searched the whole volume and found no `VIDEO_TS` directory and no ISO images. The sweep means physically feeding 33 DVDs through the drive at ~20 minutes each: about 11 hours of manual swapping, before anything can ship.
3. **libdvdcss is running on a fallback path.** `-Results.md` §5: it could not open `/dev/disk6` and recovered through the mounted filesystem, retrieving all 17 CSS keys. It worked, instantly, but that is not the path it intended to take, and it is the most plausible future cause of "works in MakeMKV, fails in HandBrake."

Demoting rather than removing gets the entire benefit immediately, costs one `if` statement, and converts the 11-hour sweep from a blocking gate into data that accumulates naturally as discs get ripped.

It is also strictly better than the alternative that was considered and rejected. `-Findings.md` §8's option B' keeps MakeMKV on the **rip** path and uses HandBrake only for scanning — which leaves the expiring key on the critical path for every single disc, precisely the thing being fixed. Demotion inverts it.

### What actually has to change

Less than the framing suggests, because one of the five bullets in `-Path.md` step 5 is already true:

- **`AppSettings.isConfigured` stops depending on `makemkvconPath`.** *Already the case.* `isConfigured` is `!plexMediaRoot.isEmpty && !tmdbAPIKey.isEmpty` (`AppSettings.swift:33`) and has never tested either CLI path. The gap is not in `isConfigured` — it is that `DVDPipeline` invokes `makemkvcon` unconditionally, so the dependency is *de facto* required at run time without ever being declared. Fixing the run-time path is the work; `isConfigured` needs no edit.
- **`makemkvconPath` stays in Settings, clearly labelled optional.** It is stored and persisted today (`AppSettings.swift:14`, `:40`, `:52`) with a plausible-looking Homebrew default that may point at nothing. `SettingsView` should show it as optional, alongside whatever per-tool state [#0008](0008.md)'s preflight produces.
- **HandBrake is tried first.** That is [#0014](0014.md). This ticket is the `else`.
- **Fall back only if `makemkvcon` is present.** If HandBrake fails and the binary is there, run the old path and say so in the log. If it is absent, report a specific failure naming the disc — not a generic tool-missing error.
- **Log every fallback.** This is the part that is easy to skip and is the whole long-term point: that log *is* the disc-reliability data set §1 says to gather incrementally, and it is what eventually justifies removing MakeMKV outright. A fallback that happens silently teaches nothing.

## Steps to reproduce

1. Let the MakeMKV beta key expire, or set the system clock past its expiry.
2. Insert any disc, search, select, Start Ripping.
3. `makemkvcon` prints its activation error and exits non-zero; every rip fails.
4. Nothing in the app can proceed, even though HandBrakeCLI on the same machine can read the same disc unaided.

## Expected behavior

A disc HandBrake can handle never touches `makemkvcon`, so the key is irrelevant to it. A disc HandBrake fails on falls back to `makemkvcon` **if it is installed**, with a log line naming the disc and the HandBrake failure that triggered the fallback. With `makemkvcon` absent, the job fails with a message naming the disc and the reason, not a missing-tool error. An expired key degrades one fallback; it does not stop the app.

## Actual behavior

`makemkvcon` is on the critical path for every disc. Its absence or an expired key fails every job, and the failure surfaces as `"✗ makemkvcon exited with status 1"` ([#0009](0009.md)).

## Notes

Fully testable without a disc, and it should be: the fallback decision is a pure function over (HandBrake result, `makemkvcon` path exists). Test the four combinations — HandBrake succeeds (no fallback, no `makemkvcon` probe at all), HandBrake fails with `makemkvcon` present (fallback runs, log line emitted), HandBrake fails with `makemkvcon` absent (specific failure naming the disc), and that the fallback's own failure does not mask the original HandBrake failure in the reported reason.

**Not every HandBrake failure should trigger a fallback.** A missing HandBrakeCLI binary, an unwritable output path or a cancelled job are not disc problems, and retrying them through MakeMKV wastes 40 minutes to fail the same way. Gate the fallback on the `FailureReason` cases that plausibly mean "this disc defeated HandBrake" — `.discUnreadable`, `.toolExited`, `.noTitlesProduced` — and let [#0009](0009.md)'s classifier make that determination rather than duplicating string matching here.

`FailureReason.activationExpired` already exists in the vocabulary from [#0007](0007.md) with the comment `// MakeMKV key — see #0009`. It keeps its meaning; it just stops being fatal.

### 1. The trigger: `FallbackPolicy`, which #0015 carries now

**Decision: #0015 owns a small, pure policy over `FailureReason`, and does not
wait for #0009.** #0009 owns turning tool output into reasons; this ticket owns
deciding what to do with a reason. With that split, neither ticket duplicates
the other's work. **Departure 1** (§11).

The reasons:

1. **#0014 already shipped without #0009, and the app works.** G3 made #0009 a
   prerequisite because #0014 and #0015 had to land together. They didn't, and
   nothing broke, so waiting only prolongs "an expired key is irrelevant, but a
   HandBrake-hostile disc fails outright".
2. **The predicate is over the enum, not over strings.** No log matching lives
   here, so nothing is duplicated when #0009 lands. When #0009 starts turning
   some `.toolExited` into `.diskFull`, the policy excludes those automatically.
3. **Use an exhaustive `switch` with no `default`.** Any case #0009 or #0008 adds
   later won't compile until someone decides whether it is disc-shaped. That is
   the handshake between the two tickets, and the compiler enforces it.
4. **Shipping first costs little.** Until #0009 lands, `.toolExited` covers a few
   non-disc failures: disk full mid-encode, a bad argument vector (a Changeover
   bug), or HandBrake killed by a signal. Each costs at most one wasted fallback
   attempt, bounded and logged (§5). And the reliability log is exactly the data
   #0009 needs to tell them apart.

New file `Changeover/FallbackPolicy.swift`:

```swift
nonisolated enum FallbackDecision: Equatable, Sendable {
    case notEligible                        // not a disc problem, or the disc is gone
    case unavailable(makemkvconPath: String) // disc-shaped, but no makemkvcon to fall back to
    case attempt
}

enum FallbackPolicy {
    /// Pure. Exhaustive switch, no `default`.
    nonisolated static func isDiscShaped(_ failure: JobFailure) -> Bool

    /// Probes are closures so a test can prove they are NOT called when the
    /// failure is not disc-shaped — same pattern as
    /// `OpticalDiscClassifier.evaluateAppearance` (`DiscInsertion.swift:131-152`).
    nonisolated static func decide(
        primary:          JobFailure,
        makemkvconPath:   String,
        isExecutable:     (String) -> Bool,
        discStillPresent: () -> Bool
    ) -> FallbackDecision
}
```

`isDiscShaped` returns `false` unless `failure.stage == .encode`. At `.encode`:

| Reason | Disc-shaped? | Why |
|---|---|---|
| `.toolExited` | **yes** | The only disc-failure signal that exists today. Over-inclusive until #0009 lands (see above). |
| `.discUnreadable` | **yes** | The case the fallback exists for. #0009 produces it, for example from the libdvdcss raw-device fallback. |
| `.noTitlesProduced` | **yes** | HandBrake found nothing to encode on this disc. |
| `.unknown` | **yes** | #0009's "unmatched non-zero exit" is today's `.toolExited`. Excluding it would make #0009 *shrink* fallback coverage. |
| `.toolMissing`, `.toolLaunchFailed` | no | A HandBrake installation problem, not a disc problem. MakeMKV's output would be encoded by the same broken HandBrake anyway. |
| `.destinationUnwritable`, `.diskFull` | no | The rip writes to the same volume, so it would fail the same way, only slower. |
| `.cancelled` | no | The user asked for this. |
| `.activationExpired` | no | Not a HandBrake reason. |

`decide` checks in this order, and each probe is skipped once a decision is made:
1. `isDiscShaped` false → `.notEligible`.
2. `discStillPresent()` false → `.notEligible`. The pipeline supplies
   `FileManager.fileExists(atPath: disc/VIDEO_TS)`. A tray popped mid-encode is
   not something MakeMKV can fix. It is [#0013](0013.md)'s territory.
3. `makemkvconPath` empty or `isExecutable(path)` false → `.unavailable`.
4. Otherwise → `.attempt`.

The filing Notes described four combinations. Each one is now a test in §8.

```swift
        discMountPath:  String,     // DVDPipeline.disc.path
        jobDirectory:   String,     // <workingRipPath>/<job id>; must not exist yet
        makemkvconPath: String,
        log:            @escaping @MainActor (String) -> Void

    // Pure, unit-tested:
    nonisolated static func sourceSpecifier(mountedFrom device: String) -> String?
    nonisolated static func infoArguments(source: String) -> [String]
    nonisolated static func ripArguments(source: String, titleIndex: Int, outputDirectory: String) -> [String]
    nonisolated static func titles(fromInfoOutput lines: [String]) -> [RippableTitle]
    nonisolated static func chooseTitle(_ titles: [RippableTitle]) -> RippableTitle?
    nonisolated static func failureReason(exitStatus: Int32, messageCodes: Set<Int>) -> FailureReason
    nonisolated static func removeJobDirectory(_ path: String, under root: String) -> Bool
}
```

`rip` runs in this order:

**a. Create the job directory fresh.** This is the provenance.
`createDirectory(atPath: workingRipPath, withIntermediateDirectories: true)`,
then `createDirectory(atPath: jobDirectory, withIntermediateDirectories: false)`.
The second call *throws if the directory already exists*, so a leftover
directory can never be adopted. Either failure →
`JobFailure(stage: .rip, reason: .destinationUnwritable(path:))`. As in #0014
G2, this happens before any process launches, so it is testable with no binary.

The pipeline makes the job directory name with `JobController.makeJobID()`
(`JobController.swift:138-143`, already `job-yyyyMMdd-HHmmss-XXXX`). It is called
on MainActor in the prologue and passed in as a string. That shape is also what
#0004's sweep will match (§6). Do **not** widen `JobController.Runner` to thread
`currentJobID` through. #0014 §4 rejected that, and a fresh id works just as
well. Log the id so the two can be correlated.

**b. Resolve the device.** `statfs(discMountPath)` → `f_mntfromname`, such as
`/dev/disk6`. Then `sourceSpecifier(mountedFrom:)` → `"dev:/dev/rdisk6"`, which
is the raw-device form MakeMKV reports in its own `DRV:` line
(`Fixtures/makemkvcon/dragon-tattoo-min0.txt:5`,
`…,"/dev/rdisk6"`). Anything not shaped `/dev/disk…` returns `nil`, which fails with
`.unknown("could not resolve a device for <mount>")`. Doing this inside the ripper
keeps `Runner` and `DVDPipeline`'s inputs unchanged. The old code's `disc:0`
means "whichever drive MakeMKV enumerates first", which is wrong once there is
more than one drive. **Unverified:** that `dev:` accepts this form is joe item 1
(§8). If joe says no, the escape hatch is `disc:0`, a one-line change in
`sourceSpecifier`.

**c. Scan once and choose one title.**
`infoArguments` = `["-r", "--cache=1", "info", source]`. That is the
`*-mindefault.txt` capture form from `Tools/capture-disc.sh:47`, so the fixtures
match production. **Do not pass `--minlength` to either command.** MakeMKV
assigns title indices *after* the minimum-length filter
(`Tools/capture-disc.sh:11-14`), so an index taken from one threshold and ripped
at another selects the wrong title and still exits 0. Collect the whole of
stdout, then parse. After the process ends, set `readabilityHandler = nil` in
`terminationHandler`, then append `readDataToEndOfFile()` before splitting into
lines. Otherwise a chunk boundary or a late final chunk can split or drop a
`TINFO` record ([#0021](0021.md) §3, [#0024](0024.md)).

- Non-zero exit → `failureReason(exitStatus:messageCodes:)`: `MSG` code
  **5021** present → `.activationExpired`, otherwise `.toolExited(code:)`.
  This matches the **numeric code**, not the English text, and is backed by
  `keyexpired-v1.18.3-exit253.txt`. It is the same rule as `0024.md` Plan step 4.
  It is the only classification this ticket does. Everything else is #0009's.
- Exit 0 → `titles(fromInfoOutput:)` → `chooseTitle`: **longest
  `durationSeconds`, ties to the lowest index.** Titles without attribute 9 are
  skipped. No title → `.noTitlesProduced`, and `mkv` never runs.
- Log one line:
  `"▶ MakeMKV: <n> titles; ripping title <i> (<h:mm:ss>, <size>)"`.

Longest-duration is chosen from scan metadata *before* ripping one title. It is
not #0028's rip-everything-then-guess-by-size. It is still a heuristic, and it
picks *The IT Crowd*'s Play All; see Risks. HandBrake's
`Found main feature title N` can't be reused here, because HandBrake numbers
titles differently from MakeMKV and may not have got that far before failing.

**d. Guard free space. This is a "should", and it is cheap.** If attribute 11
is present and `volumeAvailableCapacityForImportantUsage` of `workingRipPath`
is below `sizeBytes + 1 GiB`, fail `.diskFull` at `.rip` without writing
anything. The rip lands on the same volume as the Plex library. An unknown
capacity counts as a pass, matching #0008's rule.

**e. Rip exactly one title.**
`ripArguments` = `["-r", "mkv", source, String(index), jobDirectory]`. There is
**never** an `all`, and no `--cache=1`, which would starve the rip. Stream
output through a carry-over line buffer, because robot mode corrupts records
split across `availableData` chunks. Log each `MSG` line's message text (4th
field) and ignore `PRGV`/`PRGC`/`PRGT` lines; structured progress is
`-Path.md` step 6 and not this ticket. Append raw `MSG` lines to the
`LogTailBuffer` so #0009 has verbatim text. Also capture `MSG:1005`'s parameter
(`"MakeMKV v1.18.4 darwin(arm64-release)"`) for §5. On a non-zero exit, use the
same `failureReason` mapping.

**f. Select the output by provenance.** On exit 0, list `jobDirectory` itself.
Look at nothing else, and don't recurse. Collect entries whose extension is
`mkv` (case-insensitive) and whose size is > 0:
- **exactly one** → `.success(url)`. If its name differs from the title's
  attribute-27 hint, log `⚠︎` with both names and still succeed. Attribute 27 is
  *not* unique across scans and its prefix varies by disc (`0021.md` §2,
  `0028.md` "`makemkvcon` does not name the file the same way"), so it can't be
  the locator. The fresh directory makes the name irrelevant.
- **zero** → `.noTitlesProduced`.
- **more than one** → `.unknown("makemkvcon wrote <n> files for one title: …")`.
  Never choose among them.

**Robot-mode parsing: keep it minimal and fixture-backed.** One private line
splitter handles `PREFIX:` split on the *first* colon only, because durations
contain colons. It handles quoted fields containing commas
(`the-girl-in-the-spider-s-web-*.txt`, attribute 27) and backslash-escaped `\"`
inside quotes (the `MSG:2010` line, `dragon-tattoo-min0.txt:3`). Treat a doubled
`""` tolerantly, and never crash on either. The reader needs only
`TINFO:title,id,code,"value"` for ids **9, 11, 27**, plus the `MSG` code (first
field) and, for 1005, its first parameter. Ignore every other line. Do not build
[#0022](0022.md)'s `DiscInfo` models or [#0023](0023.md)'s scanner here. Those
are Phase 2 and move to HandBrake JSON. **Departure 2.**

### 3. The outcome shape: one additive field, no new case

The pipeline must report the original HandBrake failure without masking it
(filing Notes). It must also tell apart "fallback ran and failed" from "no
fallback available", because #0001 §7 acceptance item 6 needs a message for each,
and [#0006](0006.md)/#0009 build messages from the outcome, not the log.

Add to `JobOutcome.swift`:

```swift
/// What the MakeMKV fallback did after a disc-shaped HandBrake failure (#0015).
nonisolated enum FallbackAttempt: Codable, Sendable, Equatable {
    /// makemkvcon was not present/executable — nothing was tried.
    case unavailable(makemkvconPath: String)
    /// The fallback ran and failed. `stage` is `.rip` or `.encode` (the second
    /// HandBrake pass over the ripped file).
    case failed(stage: JobStage, reason: FailureReason, logTail: [String])
}
```

and to `JobFailure` (`JobOutcome.swift:67-77`): `let fallback: FallbackAttempt?`,
with the initializer gaining `fallback: FallbackAttempt? = nil`. Existing call
sites and tests compile unchanged.

**Why this and not a `FailureReason` case.** A new `FailureReason` case such as
`.fallbackFailed(…)` would break an older decoder, which throws on an unknown
case key (#0007 review, `0007.md:77`). It would also swap the top-level reason
for a wrapper, which is the masking the Notes forbid. An optional *struct field*
is wire-compatible in both directions with synthesized `Codable`. An older
decoder ignores the extra key, and a newer decoder reads a missing key as `nil`
through `decodeIfPresent`. **Keep the synthesized conformance; do not hand-write
`init(from:)`.** Test both directions (§8). `FallbackAttempt` does not embed
`JobFailure`, because a struct can't contain itself. [#0060](0060.md) inherits
one note: future cases on `FallbackAttempt` have the same unknown-case problem as
`FailureReason`.

**Not changed:** `JobOutcome.succeeded(destination:)` does not gain a
"produced by" value. Adding an associated value changes that case's encoding
and breaks older decoders. The phase demo needs "the log shows which path
produced the file", and §5 provides that. If #0006 wants it in the
notification, #0006/#0060 decide the wire shape then.

### 4. `DVDPipeline.run()`: sequencing

Only the primary result is ever handed to the policy. The fallback's own result
never goes back in, so a second fallback cannot happen.

```
prologue (MainActor): discPath, handbrakePath, makemkvconPath,
                      workingEncodePath, workingRipPath, plexMoviesPath   // extend :31-35
mp4Path = workingEncodePath/metadata.fileName                              // unchanged

primary = EncodeController.encode(source: discPath, title: .mainFeature, output: mp4Path, …)
.success(url)  → mp4URL = url; producedBy = .handbrake
.failure(f)    → decision = FallbackPolicy.decide(primary: f, makemkvconPath:,
                     isExecutable: FileManager.default.isExecutableFile(atPath:),
                     discStillPresent: { fileExists(discPath/VIDEO_TS) })
   .notEligible → log "✗ Encoding failed. Aborting."           → .failed(f)
   .unavailable → log FALLBACK UNAVAILABLE line (§5)            → .failed(f + fallback: .unavailable(path))
   .attempt     → log FALLBACK line (§5)
                  jobDir = workingRipPath/JobController.makeJobID()
                  rip = MakeMKVRipper.rip(discMountPath:, jobDirectory: jobDir, makemkvconPath:, log:)
                  .failure(r) → cleanup(jobDir)                 → .failed(f + fallback: .failed(stage: .rip, reason: r.reason, logTail: r.logTail))
                  .success(mkv) →
                      second = EncodeController.encode(source: mkv.path, title: .index(1), output: mp4Path, …)
                      cleanup(jobDir)          // before inspecting `second`, whatever its result
                      .failure(e) →                             → .failed(f + fallback: .failed(stage: .encode, reason: e.reason, logTail: e.logTail))
                      .success(url) → mp4URL = url; producedBy = .makemkvFallback

move (unchanged, :64-75) → .failed(organizeFailure) | .succeeded(destination)
log "✓ Produced by: HandBrake, direct from disc" | "✓ Produced by: MakeMKV fallback, then HandBrake"
append reliability record (§5), then return
```

Outcomes. The top-level `stage`/`reason` are always the primary HandBrake
failure's when the encode stage failed:

| Case | `JobOutcome` | `makemkvcon` probed? |
|---|---|---|
| HandBrake succeeds | `.succeeded(destination)` | **no**, never touched |
| HandBrake fails, not disc-shaped (e.g. `.toolMissing`) | `.failed(stage: .encode, reason: <hb>, fallback: nil)` | no |
| Disc-shaped, disc no longer mounted | same as above; the log says why | no |
| Disc-shaped, `makemkvcon` absent | `.failed(stage: .encode, reason: <hb>, fallback: .unavailable(path))` | existence check only |
| Fallback rip fails (key expired, no titles, …) | `.failed(stage: .encode, reason: <hb>, fallback: .failed(stage: .rip, …))` | yes |
| Fallback encode fails | `.failed(stage: .encode, reason: <hb>, fallback: .failed(stage: .encode, …))` | yes |
| Fallback succeeds, organize fails | `.failed(<PlexOrganizer's .organize failure>)`, unchanged | yes |
| Fallback succeeds | `.succeeded(destination)` | yes |

This is where `JobStage.rip` and `.noTitlesProduced` become reachable again,
*inside* `FallbackAttempt`. #0014 §8 anticipated this. The top-level stage stays
`.encode`, so the reason and the stage it came from always match.

The fallback encode writes to the same `mp4Path`, overwriting any partial file
the failed primary left. Keep `titleSelection` as its own named `let` (`:42`),
and write the fallback's `.index(1)` literally at its call site with a comment:
"a MakeMKV `.mkv` contains exactly one title". Name the `producedBy` enum
something private to the pipeline. It is not part of `JobOutcome`.

### 5. Logging every fallback, which is the reliability data set

**Two channels.**

*In the job log (UI).* One stable prefix, easy to grep:

*On disk, outliving the session.* The Path document's point is that this log
*is* the data set, and an in-memory log capped at 2000 lines
(`JobController.swift:36`) doesn't qualify. New file
`Changeover/DiscReliabilityLog.swift`, with a `nonisolated static func append(_:to:)`

Make every `return` in `run()` pass through one private `finish(…)` helper,
so no path skips the record.

### 6. The intermediate `.mkv`: who deletes it, and when

**Decision: the pipeline deletes the fallback's job directory as soon as the
fallback's second HandBrake run returns, whatever its result. It also deletes it
when the rip itself fails.** It is gone before `PlexOrganizer.move` runs.

- It is several GB (7,426,183,168 bytes for *Dragon Tattoo* title 0,
  attribute 11) on the library volume.
- The `.mkv` can be re-created: on any failure the disc stays in the drive
  ([#0005](0005.md) ejects on success only).
- Deleting after a *failed* fallback encode throws away evidence. The
  reliability record and the log tail keep the part that matters. Keeping 7 GB
  per failed disc is the worse trade for [#0040](0040.md)'s unattended queue.
- It is safe to delete. `EncodeController` resumes only from
  `terminationHandler` (`EncodeController.swift:123-136`), so HandBrake has
  exited and released the file.

`removeJobDirectory(_:under:)` follows #0004's safety rules (`0004.md` § Plan,
"Safety rules"). It removes only if `root` is non-empty, `path`'s standardized
parent equals `root` standardized, and the last component starts with `job-`.
It never removes `root` itself. It returns `false` and the pipeline logs `⚠︎`,
never failing the job. It never touches `workingEncodePath` or anything under
`plexMoviesPath`.

**How this interacts with #0004.** #0015 cleans up only the one directory it
created, synchronously, inside `run()`, before the move. So #0004's fixed order,
move → cleanup → eject → notify, is unaffected, and `Working/ripping` is
already empty at #0004's cleanup step. What #0015 leaves for #0004's re-scope:
- a job directory stranded by a quit or crash *during* a fallback rip or
  encode. The launch sweep should match `job-*` direct children of
  `workingRipPath`, which is why §2a uses `makeJobID()`.
- the partial `.mp4` a failed job leaves in `workingEncodePath`. That is
  unchanged by this ticket and was already #0004's residual.

This ticket does not edit `0004.md`. Record the first bullet in #0004's re-scope
when that ticket is next touched.

### 9. Risks

- **Resurrecting #0003.** The one way "closed by construction" turns out false.
  Mitigated by the fresh directory that must not already exist (§2a), selection
  within that directory only (§2f), no size/mtime/position logic anywhere, test 13,
  and the reviewer grep in §2. **Do not** adopt [#0028](0028.md)'s plan steps
  "fall back to the newest `.mkv` … with an `mtime` after the rip started" or
  `AVAsset.load(.duration)`. The first is a discovery heuristic. The second
  assumes AVFoundation reads MKV, which is not established on macOS.
- **Fallback loops.** Only the primary failure is handed to `FallbackPolicy`;
  the fallback branch never calls it. Tests 12 and 17 count invocations.
- **Over-eligible `.toolExited` until #0009 lands.** Disk full mid-encode, a bad
  argument vector, or a signal each wastes one fallback attempt. §2d stops the
  worst of these, the library volume filling up, before any bytes are written.
  The JSONL log makes the rest visible.
- **Wall clock.** A HandBrake failure late in a full x265 `slow` encode, then a
  rip, then a second full encode, with no way to stop it (G7, no `cancel()`,
  `JobController.swift:18-22`). Accepted; one attempt only.
- **Longest-duration title choice is a heuristic** that picks Play All on
  *The IT Crowd* and has no post-rip duration check. That is acceptable only
  because this path is a fallback. Phase 2 ([#0025](0025.md), [#0032](0032.md))
  owns correctness here too.
- **Device resolution and `mkv` output shapes are unverified** until joe items 1–3.
  Each has a one-line escape hatch.
- **An expired key.** When `makemkvcon` is present but its key has expired, the
  fallback fails fast with `.activationExpired`. That is the intended
  "degrades one fallback", not a hang: robot mode doesn't prompt, and the
  fixture exits 253.
- **Unmount mid-fallback.** The rip or the second encode fails and is reported
  as a fallback failure. Not handled further; #0013 territory.
- **Keep the path small.** Resist growing a progress parser, multi-title
  ripping, language selection or a `DiscInfo` model here (the filing plan's
  warning still stands). Phase 2 builds those over HandBrake JSON, and this
  ripper stays deliberately unglamorous until MakeMKV is removed.
