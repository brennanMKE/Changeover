# 0085 — iPad runs the iPhone layout instead of a split view

| | |
|---|---|
| **Status** | open |
| **Phase** | 5 — iPhone and iPad clients |
| **Module** | RemoteClient |
| **Platform** | iPadOS |
| **First seen** | 2026-09-11 |

## Description

With `TARGETED_DEVICE_FAMILY = "1,2"` the iPad runs the same build as the
iPhone, which means it runs the compact single-column layout on an 11-inch
screen. The title picker in particular is the screen that most wants the extra
width, and it gets none of it.

## Long Description

`RemoteControl.md` "Client platforms" describes iPadOS as "same as iOS with a
wider split layout — good for the title picker", and the roadmap's Phase 5 demo
ends by showing the iPad specifically to demonstrate that wider layout. Without
it the iPad is a large iPhone and the demo's second half has nothing to show.

The substance is a `NavigationSplitView`: disc titles or search results in a
sidebar, the detail — poster confirmation, title detail with streams, or the
running job's log — in the content column. That inverts the compact flow built
in [#0083](0083.md) and [#0084](0084.md), where those are pushed destinations.

Two complications make this more than a container swap.

**Stage Manager and Split View mean an iPad is often compact.** An iPad in a
narrow multitasking slot reports `.compact` horizontal size class, and the
window can resize while the app is running. Branching on `UIDevice` idiom would
be wrong; branching on size class handles it, but only if the branch is a
container choice rather than a fork in the content.

**State has to survive the transition.** If the user has typed a query, selected
a movie, and expanded the title list, resizing the window must not discard any
of that. That constrains where the state lives: it must be owned above the
branch, not inside either arm of it.

## Steps to reproduce

1. Complete [#0083](0083.md) and [#0084](0084.md).
2. Run the client on an iPad or iPad simulator in full screen.
3. Compare with the same build on an iPhone.
4. Drag the app into a narrow Stage Manager window while a search is in progress.

## Expected behavior

Full-screen iPad shows a two-column split: list on the left, detail on the
right. Narrowing the window to a compact width falls back to the pushed-stack
layout without losing the query, the selected movie or the title selection.
Widening restores the split.

## Actual behavior

The iPad shows the iPhone layout at iPad size — one column, pushed navigation,
large amounts of unused horizontal space — and the title picker, the screen that
most benefits from width, shows one title at a time with its streams behind a
further push.

## Notes

Landscape matters more here than on a phone. `INFOPLIST_KEY_UISupportedInterfaceOrientations`
for the iPad family should allow both landscape orientations plus portrait;
[#0081](0081.md) sets it, but this ticket is where a wrong value shows up.

An iPad in this workflow is plausibly on a stand with a keyboard, which makes
the `.keyboardShortcut(.defaultAction)` on the search button
(`Changeover/MetadataEntryView.swift:38`) meaningful again — it is dead weight
on a phone but useful here. Keep it in the regular-width branch.

Do not build a separate iPad target. One target, one codebase, size-class
branching. A second target would double the surface for every subsequent change
and there is nothing about iPad that needs different code, only different
arrangement.

## Plan

### 1. One branch point, as high as possible

Introduce a single root view that reads `@Environment(\.horizontalSizeClass)`
and chooses between a `NavigationSplitView` (regular) and a `NavigationStack`
(compact). Everything below that point — rows, detail screens, the log pane, the
stream selection screen — is shared verbatim between the two arms. If a view
below the branch needs to know the size class, that is a signal the branch is in
the wrong place.

Size class is `nil` on macOS, so treat `nil` as regular. That gives the macOS
client the split layout for free and makes this ticket's work reusable by
[#0060](0060.md)'s Mac client rather than parallel to it.

### 2. State lives above the branch

The view models and selection state must be owned by the root view, not by
either arm:

- `MovieSearchViewModel` — `@MainActor @Observable`
  (`Changeover/TMDB/MovieSearchViewModel.swift:4–6`), owned with `@State` at the
  root and passed down as a parameter. Not `@StateObject`; that modifier does
  not apply to `@Observable` types and is banned in this codebase.
- The title/stream selection state from [#0084](0084.md) — same treatment.
- The selected-movie id and selected-title id, which become the
  `NavigationSplitView` sidebar selection in the regular arm and the
  `NavigationStack` path in the compact arm.

Because both arms read the same `@State`-owned objects, a live resize between
Stage Manager sizes re-renders into the other container with the query, results
and selections intact. That is the whole reason to hoist the state, and it is
worth testing explicitly rather than assuming.

Note that `MetadataEntryView` currently keeps its selection as a local
`@State private var selectedID: Int?` (`Changeover/MetadataEntryView.swift:6`)
mirrored into the view model by `.onChange` (`:23–25`). That mirroring should
not survive into the client — hold the selection in one place, in the observable
selection state, and let both arms bind to it.

### 3. Column layout

`NavigationSplitView(columnVisibility:)` with two columns:

- **Sidebar** — context-dependent: the TMDB results list when choosing a movie,
  the disc title list when choosing what to rip. A two-column split with a
  switching sidebar is simpler and truer to the task than a three-column split;
  the flow has two steps, not three.
- **Detail** — poster and folder-name preview when a movie is selected (the
  preview block currently at `MetadataEntryView.swift:73–89`), title detail with
  audio and subtitle language toggles when a title is selected, and the log pane
  once a job is running.

Set `.navigationSplitViewStyle(.balanced)` and a sidebar
`.navigationSplitViewColumnWidth(min:ideal:max:)` so the poster list gets a
usable but not dominant column.

The title detail is where the width pays off: on iPad, duration, chapters, size
**and** the full audio/subtitle stream list fit on one screen, so the separate
language destination that [#0084](0084.md) needs on a phone becomes an inline
section here. Same views, different arrangement — the language section is a view
that is pushed on compact and inlined on regular.

### 4. Ordering

Build the regular arm against the iPad simulator in full screen first, then test
the resize behavior, then confirm the compact arm is untouched. Resize is the
part that breaks; do not leave it to the end.

### 5. Risks

- **Selection semantics differ between the two containers.** A
  `NavigationSplitView` sidebar drives a selection binding; a `NavigationStack`
  drives a path. Unifying them on one piece of state is the crux of this ticket
  and the most likely source of "tapping does nothing" bugs. Get it working on
  the search list before building the title picker arm.
- **Resize during a live job.** The log pane is streaming while the window
  changes size. Confirm the `ScrollViewReader` auto-scroll
  (`MetadataEntryView.swift:96`, `:110–114`) survives the container change and
  does not jump to the top.
- **Regression on iPhone.** Every change here can break [#0083](0083.md). Build
  and run both after each step.

### 6. Verification

- iPad simulator, full screen: split layout renders, sidebar selection drives
  the detail column, both orientations work.
- iPad simulator, Stage Manager and Split View: narrow the window mid-search and
  confirm the layout falls back and the query, results and selection survive.
  Widen and confirm it restores. This is simulator-provable and is the single
  most valuable check in the ticket.
- iPhone simulator: confirm no regression to the compact layout.
- macOS client: confirm the `nil` size class takes the regular branch and the
  Mac client gets the split layout rather than a stack.
- **Device-bound:** the roadmap's demo — the same build driving a real rip from a
  real iPad against the real mini. A simulator cannot prove Bonjour discovery to
  the host. Report that portion as manual.
