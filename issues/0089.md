# 0089 — iOS Local Network permission is neither requested nor recoverable when denied

| | |
|---|---|
| **Status** | open |
| **Phase** | 5 — iPhone and iPad clients |
| **Module** | RemoteClient / Pairing |
| **Platform** | iOS · iPadOS |
| **First seen** | 2026-09-11 |

## Description

Bonjour discovery on iOS requires Local Network permission, and the prompt is
stricter and more visible than on macOS. Without the Info.plist keys, discovery
returns nothing; with them but a denial, discovery also returns nothing — and
there is no API to detect the denial or re-prompt, so the app silently appears
broken.

## Long Description

`RemoteControl.md` notes that all clients need `NSLocalNetworkUsageDescription`
and `NSBonjourServices`, and that macOS 15+ and iOS both prompt on first run. It
treats the host's prompt on a headless mini as the interesting case. On iOS the
client's own prompt is at least as interesting, for a reason that does not apply
to macOS: **the failure mode of a denial is indistinguishable from the failure
mode of no host being present.**

Concretely, if the user taps "Don't Allow":

- `NWBrowser` / `NetworkBrowser` returns no results. It does not error.
- There is no public API that reports Local Network authorization status.
- The prompt cannot be shown again. The only route is Settings → Privacy &
  Security → Local Network, or Settings → Changeover Remote.
- Deleting and reinstalling the app does **not** reliably reset it.

So the app shows "No Mac found", the user checks that the mini is running, checks
the Wi-Fi, and concludes the app is broken. This is the single most likely
first-run failure for the iOS client, and it is entirely preventable with
framing that happens before the prompt rather than after.

There is a second, quieter trap: `GENERATE_INFOPLIST_FILE = YES` is set on this
project (`Changeover.xcodeproj/project.pbxproj:404`, `:433`) and `Plan.md`
records that there is no separate Info.plist file. Every key must therefore be
set as an `INFOPLIST_KEY_*` build setting — and `NSBonjourServices` is an array,
which is awkward to express that way. Getting it silently wrong produces exactly
the same symptom as a denial: an empty browser with no error.

## Steps to reproduce

1. Complete [#0081](0081.md) so the iOS client runs on a device.
2. Install on an iPhone that has never run the app.
3. Launch it. Observe whether a Local Network prompt appears at all.
4. If it appears, tap "Don't Allow".
5. Try to find the host.

## Expected behavior

Before the system prompt, the app explains in its own words why it needs to find
devices on the local network — that Changeover talks directly to the Mac in the
house and never sends anything over the internet. The prompt then appears, and on
allow, the host is discovered. On deny, the app says clearly what happened, that
iOS will not ask again, and offers a button that opens Settings to the right
place.

## Actual behavior

No `NSLocalNetworkUsageDescription` or `NSBonjourServices` is configured, so no
prompt appears and discovery silently returns nothing. Once those are added, a
denial produces the same silent empty result as a missing host, with no
explanation and no route to recovery.

## Notes

Write the usage-description string deliberately. It is displayed verbatim inside
the system prompt and it is the only chance to earn the allow. "Changeover Remote
finds your Mac on your home Wi-Fi to control disc ripping. Nothing is sent over
the internet." is the shape — specific, names the Mac, and preempts the obvious
worry. A generic "This app uses the local network" measurably increases denials.

`NSBonjourServices` must list `_changeover._tcp` exactly as the host advertises
it. A mismatch — including a missing `_tcp` suffix or a typo — produces a browser
that finds nothing with no error, which is the same symptom as everything else in
this ticket. Check it against the host's listener registration from Phase 4
rather than against the documentation.

The host's own first-run prompt on a headless mini is a real setup step that
`RemoteControl.md` flags for the README. That belongs to Phase 4 and Phase 6, not
here — but it is worth confirming it was actually documented, because a host that
was never granted Local Network access looks identical, from the phone, to a
client that was denied.

## Plan

### 1. Get the Info.plist keys right, and verify them in the built product

On the iOS client target, set as build settings (there is no Info.plist file in
this project — `GENERATE_INFOPLIST_FILE = YES` at
`Changeover.xcodeproj/project.pbxproj:404`, `:433`):

- `INFOPLIST_KEY_NSLocalNetworkUsageDescription` — the string from Notes.
- `NSBonjourServices` — an array containing `_changeover._tcp`. Because this is
  an array, the `INFOPLIST_KEY_*` route is awkward; the reliable alternative is
  an `INFOPLIST_FILE` partial or an Info.plist preprocessing step for this target
  only. Whichever route is chosen, **verify it landed** by reading the key back
  out of the built app bundle rather than trusting the build settings editor.

Set the same keys on the macOS client target if Phase 4 did not — macOS 15+
prompts too, and the MacBook Air client has the same failure mode in a quieter
form.

### 2. Pre-prompt, in the app's own words, before the system prompt

Show an explanatory screen first, at the point the user has expressed intent —
tapping "Find my Mac" or equivalent — not at launch. One short paragraph, one
button. Only when that button is tapped does the app start the browser, which is
what actually triggers the system prompt.

This costs one screen and is the highest-leverage part of the ticket: the system
prompt cannot be re-shown, so the pre-prompt is the only chance to explain before
the irreversible decision.

### 3. Infer denial, because it cannot be queried

There is no authorization-status API. The workable heuristic:

- Start the browser and start a timer.
- If no endpoint appears within a few seconds **and** the device is on Wi-Fi
  (confirmed via the path monitor from [#0087](0087.md)), treat it as *possibly
  denied* rather than *no host*.
- Present a message that covers both honestly: the Mac may not be running
  Changeover, or Local Network access may have been denied — with a button to
  open Settings and a button to retry.

Do not claim a denial with certainty. The heuristic cannot distinguish the two
and a confident wrong message ("You denied permission") when the mini is simply
asleep is worse than an honest ambiguous one.

The path-monitor check is what keeps this from firing on cellular or Airplane
Mode, where the correct message is entirely different.

### 4. The Settings route

`UIApplication.openSettingsURLString` opens the app's own Settings page, which is
where the Local Network toggle lives — that is the correct destination and it
works. Do not attempt to deep-link into Privacy & Security; those URLs are not
supported API and break between releases.

After returning from Settings, the app is foregrounded and `scenePhase` goes
`.active`. Hook that to automatically retry discovery, so a user who flips the
toggle sees it work immediately rather than having to find the retry button.
That reuses [#0087](0087.md)'s foreground reconnect path and should not be a
second mechanism.

### 5. Ordering and risks

Do step 1 and verify the keys in the built bundle **before** anything else. Every
other symptom in this ticket is indistinguishable from a wrong `NSBonjourServices`
value, so an unverified plist makes the rest of the work undebuggable.

- **Risk: burning the prompt during development.** Once denied on a test device,
  it stays denied, and reinstalling does not reliably reset it. Reset via
  Settings → General → Transfer or Reset iPhone → Reset → Reset Location &
  Privacy, and expect to do it repeatedly. Plan for a second test device.
- **Risk: the simulator lies.** The iOS simulator does not enforce Local Network
  permission the way a device does. Anything that works only in the simulator
  proves nothing here.
- **Risk: service-type mismatch** with the host silently produces the same empty
  result. Confirm against the running host with `dns-sd -B _changeover._tcp` from
  a Mac on the same network before blaming the client.

### 6. Verification

- **Buildable/inspectable:** read `NSLocalNetworkUsageDescription` and
  `NSBonjourServices` back out of the built `.app` bundle's `Info.plist` and
  confirm both the string and the exact service type. Cheap, automatable, and it
  catches the most common failure.
- **Simulator:** the pre-prompt screen, the ambiguous-failure message, and the
  Settings button's navigation. The permission enforcement itself cannot be
  tested here and must not be claimed as tested.
- **Device-bound, and the entire point of the ticket:** on a device that has
  never run the app — allow, and confirm discovery finds the host; then reset
  privacy, reinstall, deny, and confirm the app explains itself and offers the
  Settings route; then flip the toggle in Settings and confirm discovery
  automatically retries on return. Also confirm behavior on cellular with Wi-Fi
  off, which must produce a different message than a denial.
- The `## Verification` section must state which device was used and that the
  privacy reset was performed, since a device that was allowed once cannot
  re-test the denial path.
