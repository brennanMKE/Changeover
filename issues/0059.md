1. **Argument vectors line up in every combination.** Checked by hand against
   the code, not only the tests: `.sourceDefault` → `--aencoder av_aac
   --mixdown stereo --ab 160` and no `--audio`; `.tracks([1])` → `--audio 1`
   with one entry in each of the other three; `.tracks([1,4])` → `1,4` /
   `av_aac,av_aac` / `stereo,stereo` / `160,160`; `keepOriginal: true` →
   `1,1` / `av_aac,copy:ac3` and `1,1,4,4` / `av_aac,copy:ac3,av_aac,copy:ac3`
   with matching `--mixdown`/`--ab`; `.tracks([])`/`.tracks([0])` (with
   `keepOriginal` either way) fall back to `.sourceDefault`, never `--audio
   none`. `.languages` is untouched and still unused in production. The four
   lists are built in one loop that appends to all four together, so they
   cannot drift; `audioAencoderMixdownAndAbListsAlwaysMatchInLength` asserts
   it across four shapes × both `keepOriginal` values with
   `omittingEmptySubsequences: false`, and the shape assertions use literal
   `"av_aac"`/`"stereo"`/`"160"` rather than echoing `Config`, so they are not
   tautological.
2. **Reusing the AAC mixdown/bitrate at a `copy:ac3` position is low risk,
   and the shape stands.** HandBrake ignores mixdown, bitrate, samplerate and
   DRC for a passthru track; and in the one case where it does *not* ignore
   them — a source that isn't AC3, where `copy:ac3` falls back to the
   fallback encoder (AAC for an MP4 mux) — `stereo`/`160` are precisely the
   values that path should use, so the failure mode is a duplicate AAC stereo
   track, not a wrong one. Every alternative shape is worse: an undocumented
   placeholder (`auto`) is a guess, and a short list re-exercises HandBrake's
   "reuse the last entry" behaviour that #0029 deliberately designed out. It
   is opt-in and off by default, so nothing ships on it either way. The
   `ffprobe` check on joe still settles it.
3. **Per-track passthru instead of first-track-only is justified.** #0017's
   constraint is that the output direct-plays on the Apple TV, and #0029's
   "first track only" existed because only the first track carried the AAC
   compatibility copy. That reason is gone: every selected track now carries
   a real AAC stereo encode, so per-track passthru cannot make a track *less*
   compatible than the first-track-only layout did. Stream order is
   AAC(t1), AC3(t1), AAC(t2), AC3(t2) — the first stream is still AAC stereo,
   which is what #0058's "some players pick the first track" question wants,
   and pairing each track with its own original is better for player track
   naming than grouping all the AACs first. The shipping default (passthru
   off) is a single AAC stereo track — strictly more compatible than the
   layout #0017 verified.
4. **The second-language risk was real in one case, and is fixed (5d9d11d).**
   On an *untagged* title the implementer reworded the caption to say only
   the first track starts selected and to tick more — honest, and the picker
   lists every track as a plain checkbox at natural height (`TrackSelectionView`
   `.audioSection`, unscrolled since #0140), so the others are obviously
   available. The *tagged* case had no such wording: with the default
   preference `["eng", "spa"]` on a disc carrying both, the old rule selected
   both, the new one selects English, and `notice` returned `nil` — nothing on
   screen. That is the one way this default can drop a genuine second
   language rather than a duplicate mix, and it is an ordinary Region 1 disc

## Description

The user reported the ripped files feel very large. Measured on the two films ripped on joe on 2026-09-16:

| | Oppenheimer (3:00:22) | Hornet's Nest (2:27:02) |
|---|---|---|
| File | 1.82 GB | 1.67 GB |
| Video (x265, RF 23, preset slow) | ~314 kbps → 0.42 GB | ~611 kbps → 0.68 GB |
| Audio (AC3 copied from the disc) | 1,024 kbps → **1.39 GB (76%)** | 896 kbps → **0.99 GB (59%)** |

The video encode is already frugal. **Audio is the majority of both files**, because every selected track is copied at the disc's own bitrate (448 kbps for 5.1), and #0027's preselection keeps every matching track — two 448 kbps tracks on an untagged disc, three tracks on Oppenheimer.

Separately, `Config`'s encoder settings (x265, RF 23, preset slow) have never been measured against quality on this project's own material. RF 23 at DVD resolution is conservative; nobody has data either way.

## Expected behavior

Defaults chosen from measurement: a quality target and an audio policy that a person picked after seeing size against a quality metric on real DVD material, with the numbers written down.

## Plan

**Experiment (joe).** `/Volumes/Media/test-fixtures/dragon-tattoo` is a full `VIDEO_TS` copy on local disk, so this needs no disc and no drive time.

1. Encode the same chapter range at RF 23, 24 and 25 (x265, preset slow, audio disabled) plus a near-transparent RF 10 reference.
2. Score each against the reference with `ffmpeg -lavfi libvmaf` (joe's ffmpeg has libvmaf). Note the caveat: the reference is itself an encode, so the scores measure quantization loss relative to a near-transparent copy, not absolute fidelity — fine for choosing between RF values.
3. Tabulate size and VMAF (mean and 1% low) per RF.
4. Compute audio sizes for the candidate policies: copy AC3 448k; AAC 5.1 at 256k; AAC stereo at 160k; AC3 5.1 plus AAC stereo; one track versus all tracks.

**Decisions to take from it.**

- The default RF, with its measured cost in size and VMAF.
- Whether a second matching-language track is kept by default (Hornet's Nest's two untagged 448k tracks are probably the same audio in two mixes).
- Whether 5.1 is transcoded to AAC or passed through — passthru is lossless and Apple TV plays it; AAC 5.1 at 256k saves ~43% per track.
- Whether the audio policy belongs in Settings rather than `Config` — [#0112](0112.md) already covers exposing encoder settings, and this is the evidence that issue needs.

**Out of scope here:** the missing AAC compatibility track is [#0058](0058.md); fix that first or the audio arms measure a layout that isn't shipping.

## Decision (user, 2026-09-16) — settings confirmed on a real conversion

Measured, then confirmed by watching the result. **These are the settings to use for conversions.**

| Setting | Value | Evidence |
|---|---|---|
| Video encoder | x265, preset `slow` | unchanged |
| Quality | **RF 23** | RF 24 saves 12% and RF 25 saves 23% of the *video* bitrate, which is only ~100 MB on a feature, while costing VMAF (95.07 → 94.60 → 94.05 mean, 90.11 → 87.97 at the 1% low). Not worth it: video was never the problem. |
| Deinterlace | `--comb-detect --decomb` | a 1985 telecined transfer came out correct at 23.976 fps; see #0016 for driving this from the scan rather than always-on |
| Audio | **one AAC stereo track at 160 kbps** (`--aencoder av_aac --mixdown stereo --ab 160`) | matches the user's three known-good library files (161–165 kbps AAC stereo, 0.47–0.74 GB per film); replaces copying every selected AC3 track at 448 kbps |
| Extra tracks | not kept by default | copying every matching track is what made the two new rips 59–76% audio |

**The conversion that settled it.** `Weird Science (1985)` was a raw MakeMKV rip (MPEG-2 + AC3 5.1 + DTS 5.1, 8.42 Mbps, 5.51 GB). Re-encoded with the settings above: **0.59 GB, 897 kbps total (video 726 kbps, audio 164 kbps), full 1:33:38** — a 9.3x reduction. The user watched it and approved; the original `.mkv` has been deleted.

For comparison, the library files this was tuned against: The Fifth Element 815 kbps / 0.72 GB, Tombstone 816 kbps / 0.74 GB, Massive Talent 627 kbps / 0.47 GB — all HandBrake 1.10.2, H.264 ~640 kbps video, one AAC stereo ~165 kbps.

### What this means for the app

- `Config`'s encoder constants keep `x265` / `slow` / RF 23.
- `EncodeController`'s audio arguments change from "copy every selected track" to "encode the primary selection as AAC stereo at 160 kbps". This supersedes the earlier orchestrator decision that the first track gets an AAC copy *alongside* AC3 passthru (#0027, #0029), and it subsumes #0058 — there is no `copy:aac` entry left to fall back to AC3.
- AC3 5.1 passthru becomes an opt-in, not the default. Whether that lives in Settings is #0112's question; this issue is the evidence for it.
- #0027's preselection should follow: pick one track, not every match. The untagged-disc rule (keep both when nothing is tagged) needs re-examining against this — two 448 kbps untagged tracks became two copies on Hornet's Nest.

## Root cause

`EncodeController.audioArguments(_:)`'s `.tracks` case copied every selected
track at the disc's own AC3 bitrate (a `copy:aac,copy:ac3` compatibility pair
on the first track, `copy:ac3` on the rest) — and `.tracks([])`/`.sourceDefault`
fell back to that same `copy:aac,copy:ac3` string. Nobody had measured the
encoder settings or the audio policy against the user's own library, which
runs one AAC stereo track at ~160 kbps per film. `AudioTrackOptions
.preselection` compounded it: on an untagged disc it selected *every*
non-commentary track, so a disc with two untagged 448 kbps tracks (Hornet's
Nest) copied both at full bitrate.

## Fix

Implements the "What this means for the app" list above.

- **`EncodeController.AudioSelection.tracks` gained `keepOriginal: Bool =
  false`.** Every selected track now gets one AAC-stereo entry
  (`Config.audioAACEncoder`/`.audioAACMixdown`/`.audioAACBitrateKbps` =
  `av_aac`/`stereo`/`160`) — not just an AAC copy on the first track. When
  `keepOriginal` is true (opt-in), each selected track *additionally* gets a
  `Config.audioPassthroughEncoder` (`copy:ac3`) entry right after its AAC
  entry — the AAC-plus-AC3 layout #0017 verified direct-plays on Apple TV,
  now applied per selected track rather than only the first (there is no
  longer a reason to single out the first track: every track already carries
  a real AAC encode, not a passthru gambling on the source codec).
  `--audio`/`--aencoder`/`--mixdown`/`--ab` are always the same length;
  `--mixdown`/`--ab` repeat the AAC values at a `copy:ac3` position rather
  than inventing an undocumented placeholder, since HandBrake ignores those
  settings for a copy track — flagged as unverified pending the manual
  `ffprobe` check below. `.tracks([])`/`.tracks([0])` still fall back to
  `.sourceDefault`, never `--audio none`.
- **`.sourceDefault`'s vector changed too** (no `--audio`, `--aencoder
  av_aac --mixdown stereo --ab 160`), because `Config.audioEncoder` no longer
  exists as `copy:aac,copy:ac3` — there is **no `copy:aac` anywhere** in the
  codebase now, closing off the exact fallback #0058 found. `.phase1` and the
  MakeMKV fallback's `fallbackAudio` (always `.sourceDefault`, per #0027's
  review) inherit the new AAC-stereo default for free.
- **`AppSettings.keepOriginalAudioTrack: Bool = false`** (new, persisted,
  normalized the same way as other settings) is the opt-in switch, with a
  "Keep the original 5.1 track (larger files)" toggle in `SettingsView`'s new
  "Audio" group. Captured as a plain `Bool` on MainActor and passed into
  `EncodeSelection.make(request:disc:keepOriginalAudioTrack:)` — the same
  MainActor-to-`nonisolated` pattern `DVDPipeline` already uses for path
  strings (`CLAUDE.md`) — rather than handing the `nonisolated` `make` an
  `AppSettings` reference. `JobController.start(request:settings:)` is the
  one call site that reads it.
- **`AudioTrackOptions.preselection` now selects exactly one track by
  default**, on both tagged and untagged titles — the first non-commentary
  match (or the first non-commentary option when nothing matches, or the
  first option at all when every option is commentary; never `[]` for a
  title that has audio, unchanged). Previously it selected *every* matching
  track. Decision, per this issue's own instruction to re-examine the
  untagged rule: Hornet's Nest's two untagged 448 kbps tracks became two
  near-gigabyte copies under the old rule, and identical-looking untagged
  tracks are far more often a duplicate mix (commentary-free vs. not,
  stereo-downmix-of-the-5.1, a mastering variant) than a second language —
  the Swedish-original-plus-English-dub scenario #0027 built the "keep
  everything untagged" rule against is real but rarer, and now that a second
  *ticked* track only costs ~160 kbps of AAC instead of ~448 kbps of AC3, the
  user can cheaply add it by hand when a disc actually needs it. The picker
  still shows every option (`AudioTrackOptions.options` is unchanged — no
  merging, no hiding); only the default checkbox state changed.
  `AudioTrackOptions.notice`'s untagged-disc message was reworded to match
  ("so only the first track starts selected. Tick more if this disc carries
  more than one language.").
- **`Config`** dropped `audioCompatibilityEncoders`/`audioEncoder` (the old
  `copy:aac,copy:ac3` pair) and added `audioAACEncoder`/`audioAACMixdown`/
  `audioAACBitrateKbps`; `audioPassthroughEncoder` (`copy:ac3`) is unchanged
  and now used only for the opt-in passthru entries.
- **Video/deinterlace untouched**, per this issue's own decision table and
  instruction to check #0016 before touching it: `Config.videoEncoder`/
  `.videoQuality`/`.encoderPreset` are still `x265`/`23`/`slow`.
  `DeinterlaceFilter.decomb.arguments` is still `["--decomb"]` only —
  `Changeover/DeinterlaceDecision.swift` has no `--comb-detect` flag and
  #0016's landed resolution (commit `a7f675f`) never added one either. The
  Weird Science conversion that used `--comb-detect --decomb` (see the
  Decision section above) was run outside the app, by hand, against a raw
  MakeMKV rip — not through `EncodeController`. Since #0016 owns driving
  deinterlace from the scan and its resolution doesn't include
  `--comb-detect`, this issue leaves it alone rather than adding the flag
  unilaterally; worth a look on its own ticket if the user wants it.
- **`.languages` (the #0015 MakeMKV-fallback path) is untouched.** It's
  unused in production (`EncodeSelection.fallbackAudio` is always
  `.sourceDefault`, per #0027's review) and out of this issue's stated scope.
- **Unrelated fallout, fixed because it broke:** `Preflight
  .requiredHelpTokens()` derives its required-flags list directly from
  `EncodeController.arguments(...)` (by design — "derived from the code, not
  hand-listed"), so once `.sourceDefault` started emitting `--mixdown`/`--ab`,
  HandBrakeCLI's `--help` output is now required to list them too. Updated
  `PreflightTests.goodHelpLines()` and `Fixtures/stub-interleaved-help.sh` to
  include `--mixdown`/`--ab` lines — both are real HandBrakeCLI flags present
  in the actual `help-hb1.11.2-exit0.txt` capture, so this doesn't relax the
  check, it just catches the shared test fixtures up to it.

- **Review fix (5d9d11d).** `AudioTrackOptions.notice` now names a preferred
  language that is present on a non-commentary track but not selected
  ("`fra` is also on this title and one of your preferred languages, but only
  one track starts selected — tick it to keep it too"), and clears once the
  user ticks it. The untagged caption already said this; the tagged case —
  a disc carrying both of the default `["eng", "spa"]` preferences — said
  nothing at all, which is the one shape where the new one-track default
  drops a real second language rather than a duplicate mix. Keyed on
  *language*, not track, so two English tracks (5.1 + stereo downmix) stay
  quiet. Two stale doc comments corrected in the same commit: `isUntagged`
  still claimed an untagged title keeps every non-commentary track, and
  `toggling` still claimed only the first selected track gets an AAC copy.

**Positional-list discipline**, per this issue's instruction: `--audio`,
`--aencoder`, `--mixdown` and `--ab` are always built as four equal-length
comma lists in `audioArguments(_:)`'s `.tracks` branch — asserted directly in
`audioAencoderMixdownAndAbListsAlwaysMatchInLength`, across four track-count
shapes and both values of `keepOriginal`.

## Gotchas

- **`Preflight.requiredHelpTokens()` derives its list from
  `EncodeController.arguments(...)`**, so any future change to the default
  audio vector automatically changes what a real HandBrakeCLI install is
  required to support — a good property, but it means a vector change like
  this one always needs a pass over the shared "compatible help" test
  fixtures (`goodHelpLines()`, `stub-interleaved-help.sh`), not just the
  `EncodeController`/`AudioTrackOptions` tests. `synthetic-help-no-encoder.txt`
  and `stub-HandBrakeCLI.sh`'s own fallback help text already had real
  `--mixdown`/`--ab` lines (they're closer to the real H1 capture) and needed
  no change.
- **The `--mixdown`/`--ab` values repeated at a `copy:ac3` position are a
  documented assumption, not a verified one.** HandBrakeCLI's own `--help`
  doesn't list an `auto` mixdown, and nothing in this repo's fixtures shows
  what HandBrake actually does with `--mixdown`/`--ab` on a track whose
  `--aencoder` entry is `copy:ac3`. Reusing the AAC values avoids inventing
  an undocumented placeholder; the manual `ffprobe` check above is what
  actually settles it, and only matters when `keepOriginalAudioTrack` is on.
  **Review assessment (2026-09-17):** low risk, and the shape stands.
  HandBrake ignores mixdown/bitrate/samplerate/DRC for a passthru track, and
  in the one case where it does not — a source that isn't AC3, where
  `copy:ac3` falls back to the mux's default encoder (AAC for MP4) —
  `stereo`/`160` are exactly the values that path should use, so the worst
  outcome is a duplicate AAC stereo track, never a wrong one. Nothing ships
  on it either way: passthru is off by default.
- **`EncodeSelection.make`'s new `keepOriginalAudioTrack` parameter is
  defaulted to `false`**, so `EncodeSelectionTests`'s and
  `JobControllerTests`'s pre-existing calls to `EncodeSelection.make(request:
  disc:)` (no third argument) keep compiling and stay correct — they exercise
  the `AppSettings()` default, which is also `false`. Nothing in
  `JobControllerTests.swift` needed to change.
- **`#0112`** (exposing encoder settings/`Config` review) and **`#0027`/`#0029`**
  (the superseded "first track only" AAC-copy decision, and the
  `AudioTrackOptions`/`EncodeSelection` types this issue builds on) are worth
  the reviewer's attention for consistency, but weren't touched here per this
  issue's own scope.
