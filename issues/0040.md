| | |

## Description

Changeover can only ever have one job in flight, so the machine sits idle whenever the human is not standing at it. Phase 3 replaces the single current job with an ordered **queue of jobs carrying stable `JobID`s**, splits the pipeline into a drive lane (one rip at a time, forced by there being one optical drive) and an encode lane that overlaps the next rip, and keeps the Mac awake while anything is running.

## Long Description

Phase 3 is the last phase before the wire protocol is designed, and it is scheduled there deliberately: the queue is **protocol-visible**. `RemoteControl.md` leaves "Job queue?" as open question 1 (`RemoteControl.md:523`) and the sketched protocol at `RemoteControl.md:331-347` assumes a single job — `case state(JobState)`, `case log(String)`, `case cancel` with no job identity anywhere. Once a queue exists, every one of those needs a `JobID`. Settling that now costs a type; retrofitting it after Phase 4 ships means a protocol version break across three client platforms.

The physical loop sets the shape of the concurrency model, and it is not symmetric:

| Lane | Capacity | Why |
|---|---|---|
| Drive lane — scan, rip, eject | **1, and not negotiable** | There is one optical drive holding one disc. `makemkvcon mkv disc:0 …` (`Changeover/RipController.swift:21`) reads that drive. |
| Encode lane — encode, organize, clean up | **1 by policy, tunable** | `HandBrakeCLI` saturates every core (`Changeover/EncodeController.swift:20-28`). Two encodes at once finish no sooner and fight the concurrent rip for SSD write bandwidth. |

So the steady state is **at most two external processes: one rip and one encode, from two different jobs**. That is the whole point of the phase — job *n* encodes while job *n+1* rips.

One consequence falls out of this that the roadmap does not state, and it is load-bearing: **the disc must be ejected at the end of the rip stage, not at the end of the job.** Phase 1 adds auto-eject "on completion" (`Roadmap.md:80`). If completion means after the encode and the move, then the disc stays in the drive for the entire encode and the user physically cannot insert the next disc — the Phase 3 demo is impossible. `#0045` moves the eject point.

## Steps to reproduce

1. Insert a DVD, search TMDB, select the movie, press **Start Ripping**.
2. Wait for the rip to finish and the encode to begin.
3. Try to set up the second disc while the first is still encoding.

## Expected behavior

The disc ejects as soon as its rip finishes. The user inserts disc two, it is scanned and set up, and pressing Start puts job two into the drive lane while job one is still encoding. A queue view shows job one `encoding` and job two `ripping`. Three discs go through back to back with no interaction beyond swapping and selecting, none of them stalls if one fails, and the mini does not fall asleep partway through.

## Actual behavior

There is no queue at all. Pipeline state lives in `MetadataEntryView` as `@State` — `isProcessing` and `logLines` (`Changeover/MetadataEntryView.swift:7-8`) — and `startRipping()` (`Changeover/MetadataEntryView.swift:142-155`) runs one `DVDPipeline` straight through rip → encode → move (`Changeover/DVDPipeline.swift:16-62`) with no seam between stages. The Start button is simply disabled for the duration (`Changeover/MetadataEntryView.swift:129`). The disc stays in the drive for the whole job, a second disc has nowhere to go, and nothing stops the machine idling to sleep mid-encode.

### Concurrency model, stated once

Everything in this app is `@MainActor` by default (`SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`, `Plan.md` "MainActor default isolation"). The queue does **not** become an `actor` — the convention table is explicit that the `actor` keyword is not used for types with no reason to leave the main actor. Instead:

- `JobQueue` is an `@Observable` `final class`, MainActor-isolated for free. Every mutation of queue state happens on MainActor, so there are no locks and no data races by construction.
- The long-running work is already `nonisolated static` (`Changeover/RipController.swift:9`, `Changeover/EncodeController.swift:9`) and runs on the cooperative pool, so awaiting it from MainActor frees MainActor for the duration.
- Log lines already hop back to MainActor inside the process handlers (`Changeover/RipController.swift:38`, `:51`; `Changeover/EncodeController.swift:42`, `:52`), so the log callback stays a plain `@MainActor (String) -> Void`.
- The scheduler's `pump()` is **synchronous**. It inspects state and launches Tasks; it never awaits. All awaiting happens inside a per-job Task that mutates state on MainActor and then calls `pump()` again. This removes the re-entrancy window that would otherwise exist at every `await` inside a MainActor method.

### Phase exit criteria

- Three discs processed in one sitting with no interaction beyond swapping and selecting. The second disc is set up while the first is encoding.
- At no point are two rips running; at no point is an encode blocking a rip that could have started.
- A job that fails at any stage becomes terminal and every job behind it still runs.
- `pmset -g assertions` shows a `PreventUserIdleSystemSleep` assertion held by Changeover for the whole run and released when the queue drains.
- The queue view shows what happened in what order, with each job's own log retrievable after the job finished.
- `JobID` is `Codable`, `Hashable` and `Sendable`, and there is a `Codable` snapshot value type distinct from the `@Observable` reference type — so Phase 4 can put jobs on the wire without touching the host's observation model.

### Plan refresh (2026-09-15)

Checked against `bb38aee` plus the uncommitted working tree. Phase 1's children are all resolved or closed; #0001 itself stays open until the two-disc demo on joe. From Phase 2, #0022–#0024 are resolved, #0025 is in progress, and #0026/#0027/#0029–#0033 are open.

**The central premise is obsolete.** The two lanes came from the MakeMKV pipeline: the drive lane ripped, and the encode lane ran HandBrake on a file already on the SSD. Since #0014 there is no rip stage. `DVDPipeline.run()` points `EncodeController.encode(source: discPath, …)` at the disc's mount root (`DVDPipeline.swift:318-325`), so the disc is the encode's input for its whole length: about 40 min for a feature at x265 `slow` (#0018). The drive lane and the encode lane are now the same lane. That has three consequences:

- **#0045's "eject at end of rip" has no rip to end.** Ejecting before the encode returns kills the encode.
- **#0044's "job *n* encodes while job *n+1* rips" cannot happen with one drive.** Job *n+1* cannot even exist until disc *n* is out, because `JobController.start` refuses to start without a mounted disc (`JobController.swift:100-103`).
- **A second concurrent encode would not help.** The encoder is the bottleneck, not the drive. Joe's USB 2.0 drive reads about 5.6 MB/s, which already outpaces x265 `slow` at about 70 fps.

**User decision D1 — what Phase 3 builds.**

- **Option A (recommended): serial, disc-bound jobs.** One job at a time, because the job's input is the disc. Phase 3 then delivers:
  - job identity and a session history;
  - per-job logs;
  - a real cancel;
  - idle-sleep prevention;
  - a fresh selection for every new disc;
  - a manual Eject;
  - a history view.

  Demo: *"Three discs back to back. Each one ejects and notifies; swap when notified. The history view shows three rows, each with its own log, and the mini never slept."* Swaps come about one feature-encode apart.
- **Option B: stage, then encode.** A drive-bound stage copies the selected title to local storage with a decrypting copier and ejects. The encode then runs from the copy in a second lane.
  - **It is not faster.** With copy time C (a 6–7 GB title at 5.6 MB/s is about 18–21 min) and encode time E, three discs take about **C + 3E**, against **3E** for option A. The only gain is swap cadence: all three swaps happen in the first ~3C (about an hour) instead of across ~3E (about two hours).
  - **It puts a copier back on the happy path.** Either MakeMKV, which #0014 and #0020 removed, or a new `dvdbackup` dependency. A plain file copy of CSS-protected VOBs is unverified and likely unusable.
  - **It needs working space and new policy.** About 7 GB per staged job, so `Preflight`'s 2 GB floor would have to scale. #0015's fallback also changes meaning, since the disc is gone during the encode.
  - **It needs a disc experiment before any code** (see #0044's refresh).

## Notes

**Verification.** This phase is the one genuinely testable part of the app. `Issues.md` warns that a green build is not verification for anything in the rip path, and that stands — but the queue's *state machine, ordering, lane accounting and failure isolation contain no disc and no subprocess* and belong in `ChangeoverTests` (which is currently a single empty `@Test func example()` stub in `ChangeoverTests/ChangeoverTests.swift`). Each child names the specific tests it owes. The rule for this phase: if a behaviour can be expressed as "given this queue, this event, expect this queue", it must have a Swift Testing case; only the parts that actually touch `makemkvcon`, `HandBrakeCLI`, the drive or the power assertion get a manual verification note naming the disc used.

**Roadmap corrections carried by this phase.** The Phase 3 roadmap section (`Roadmap.md:132-158`) is right about the concurrency limits but omits two things that the demo cannot work without: the eject point has to move to end-of-rip (`#0045`), and a queued rip is bound to a *specific physical disc* that can be removed out from under it (`#0045` again). It also does not mention per-job log retention, which is what makes "the queue view shows what happened in what order" more than a list of status pills (`#0043`).

### Gaps across issues

Two are defects and are filed:

- **[#0051](0051.md)** — a running scan cannot be cancelled and Eject refuses
  during it (#0045 review, by design), so a disc whose scan hangs holds the
  drive for up to `DiscScanner.scanWatchdog`'s 15 minutes with Start, Rescan
  and Eject all unavailable. #0046 built the cancellable `ProcessRunner`,
  `DiscScanner.Failure.cancelled` and the "The scan was cancelled." message,
  and left `startScan`'s `Task` untracked (`JobController.swift:813`). Also
  lets two scans of one disc run at once. Small, and the one UX dead end a
  user can hit without doing anything wrong.
- **[#0052](0052.md)** — `removeDisc()` clears the disc and selections but
  never tells `current` its disc is gone. A pulled disc ends the job as
  "disc unreadable" or, if the read blocks, as the 30-minute silence
  watchdog, with no log line, a notification blaming the disc, and a
  `DiscReliabilityLog` record against the disc. #0045's plan refresh
  specified the milestone line; the re-scope dropped it. #0046's manual
  check 3 will hit this on joe.

Recorded, not filed — none blocks the demo:

- **Sleep between jobs.** The assertion is per job, so a swap that takes
  longer than the idle timer lets the mini sleep, and a disc insertion does
  not wake it. Correct by decision; the demo must either keep the timer
  above the swap cadence or accept waking the mini by hand. Phase 4's "stay
  discoverable" setting (#0047's note) is the real answer.
- **History is in memory only.** A relaunch empties it. Fine for "the
  session's jobs"; #0060's `subscribe` will reply with whatever survives,
  so persistence is a Phase 4 question, not a Phase 3 one.
- **The instant after an automatic eject.** The end-of-job eject does not
  set `isEjecting` (the manual one does), so between `finish` and
  DiskArbitration's removal Start is briefly live against an ejected disc
  with the finished job's selection still held. A click there fails
  preflight on the same movie: no data loss. The #0045 review saw and
  accepted it.
- **`startScan` ignores `isRunning`.** A disc inserted while a job is still
  dying (after a pull) is scanned beside the encode, and the metadata window
  comes forward. Harmless, and Start is refused while running.
- **No Cancel in the metadata window.** Cancel lives in the status menu and
  the history window (#0046/#0048 decided one entry point was enough).
- **Fail-open defaults.** `JobPresentation.retryDecision` and
  `StartGate.canStart` default `discUnavailable` to `false` (#0049's
  gotcha); both real call sites pass it. A future caller that forgets fails
  open.
- **Reliability records need filtering.** A user cancel is `outcome:
  "failed"` with `decision: "cancelled"` (#0046); #0052 adds
  `"discRemoved"`. Any count of disc failures must exclude both.
- **#0050** is test hygiene in flight (pipeline tests reach the real
  `DiscEjector` on temp paths). Not a phase gate; it should land before the
  next full run is trusted as "never touches a drive".
- **Stale prose, no code effect:** this ticket's Description, Long
  Description and Notes, #0044's whole Description, and the Roadmap's Phase 3
  Work list and demo text all describe two lanes and a MakeMKV rip. Under A
  the Roadmap's demo line "set it up **while the first is still encoding**"
  should become "when it ejects, insert the second and set it up; the
  machine is never idle while a disc is in it". Suggest the Roadmap edit
  once D1 is confirmed.

**Contradictions checked, none found.** The decisions that interact are
consistent and each is pinned: Eject refuses while running (#0045) and the
#0047 handoff's "an Eject that ends a job must go through `finish`" — met by
not building that path; the flow is Cancel, then Eject, and
`ejectDiscRefusesWhileAJobIsRunning` plus `releaseOnCancel…` cover both
halves. SIGKILL after 10 s (#0046) against the refresh's "never SIGKILL" —
overridden with the reason recorded (a SIGTERM leaves an equally partial
file, and every cancelled job's directory is removed). No `ejecting` phase
(#0041) against the partial eject (#0049) — the eject is the tail of
`organizing`/`extras`, cannot be cancelled, and reports through
`JobContext.eject`; a cancel during extras still ejects and ends `succeeded`,
and its notification is the success one, so "the disc is still in the drive"
is only ever said for a cancel during the feature. Retry replays the recorded
`RipRequest` including `extraTitleIndices` (#0048 review; `RipRequest.swift`),
never the live selection. A cancelled last job reads as idle in the popover
and still posts a notification (#0048/#0046) — two surfaces, one rule.

### Is the demo achievable under A as built?

**Yes.** Every step below has code behind it and a test named above, except

#### Demo script for joe

Preparation:

1. Build from HEAD (after #0050 if it has landed; it is test-only either
   way) on the development Mac, copy to joe's `/Applications`, `xattr -cr
   /Applications/Changeover.app`, launch once. Settings configured (TMDB
   key, `HandBrakeCLI` path, Plex media root). Use a **scratch Plex root**
   for the whole session unless the three movies are known not to be in the
   library: Retry and the failure paths below replace files by design
   (#0012).
2. Record joe's idle-sleep setting (`pmset -g | grep ' sleep'`) and set it to
   ten minutes for the session (`sudo pmset -a sleep 10`). Confirm
   `pmset -g assertions | grep -i changeover` prints nothing while idle
   (#0047 check 1).
3. Open **History…** from the status menu: an empty list. Leave it open
   beside the metadata window. Note the outline `opticaldisc` glyph in the
   menu bar.
4. Have three discs: Hanna (or any known-good feature), a second feature to
   cancel and retry, and a third. Hornets' Nest or Fargo are fine for the
   third; Brooklyn Nine-Nine is not (it refuses at the Phase 2 gate, which
   is not what this demo is about).

Disc 1 — the happy path:

5. Insert. The metadata window comes forward, scans, and shows the
   confirmation row. Search, pick the movie, keep the default audio, tick
   no extras (they add encode time; one extra on disc 3 is enough), Start.
6. Within a minute: `pmset -g assertions | grep -i changeover` shows
   `PreventUserIdleSystemSleep` with `Changeover: encoding <Title (Year)>`
   (#0047 check 2). The menu bar glyph is filled (#0048 check 6). The
   popover reads "Encoding <Title>" with an active dot. The history row
   reads "Encoding", indeterminate, with a running elapsed time.
7. Walk away for longer than the ten-minute idle timer. Touch nothing. Come
   back: the job is still running and `log show --predicate 'eventMessage
   CONTAINS "Entering Sleep"' --last 1h` shows no sleep (#0047 check 4,
   first half). This is R3.
8. Close the history window and reopen it: the same job is selected and its
   log is intact (#0048 check 5). Scroll the log to the top: `── Starting`,
   `▶ Job`, the preflight lines and a single live progress row are there,
   with a "… N earlier lines dropped" marker if the ring filled (#0043's
   owed check).
9. When it ends: `✓ Output: runs …` (#0037), the move, `✓ Disc ejected —
   safe to insert the next one`, the tray opens, the notification arrives.
   `pmset -g assertions | grep -i changeover` prints nothing again (#0047
   check 3). Click the notification: History opens on that row (#0048
   check 4). The row shows the elapsed total and a green tone; the popover
   dot is green and reads idle.

Disc 2 — cancel, then retry:

10. Insert. The search is empty and nothing is selected (#0034; A2). Scan,
    pick, Start.
11. Two minutes in, status menu → **Cancel Job**. The popover closes and an
    alert comes to the front. Press Return ("Keep Going"): the job keeps
    encoding (#0048 check 2). Cancel Job again → **Cancel Job**. Watch the
    row, the popover and the menu row read "Cancelling…", then "Cancelled"
    (#0046's "Cancelling…" bridge).
12. Then check, in this order (#0046 check 1): `pgrep HandBrakeCLI` is empty
    within a couple of seconds, ten at most; `Working/encoding/<jobID>` is
    gone; the disc is still mounted; the job log has no `FALLBACK` line;
    the notification reads "<Title> was cancelled"; `pmset` shows no
    assertion; `tail -1 ~/Library/Logs/Changeover/disc-reliability.jsonl`
    has `"decision":"cancelled"`. The popover dot is green (cancel is not a
    failure; #0048 check 7, second half).
13. In the metadata window, pick a *different* title (any short one). Then
    History → the cancelled row → **Retry**. A new row starts. Its log's
    `--title n` line names the *original* title, not the one just picked
    (#0048 check 3, second bullet). Let it run to the end: eject,
    notification, four checks from step 9 again.

Disc 3 — the third feature, one extra, and the failed-job path:

14. Before inserting: set the Plex media root to a path that cannot be
    written (a read-only folder), so the move fails. Insert, pick, tick one
    extra, Start. The encode runs to the end and the move fails
    `destinationUnwritable`: the row is red with the reason, the popover dot
    is red and reads "Last job failed — …" (#0048 check 7, first half), the
    notification says what went wrong, and **the disc stays in the drive**
    (#0005 leaves a failed job mounted).
15. Fix the media root. History → **Retry**: enabled, tooltip empty. The
    replay carries the same title, tracks *and* the ticked extra; it encodes
    again (the feature, then the extra under `Clips/`), moves, ejects,
    notifies. Alternatively, to save an encode, skip Retry here: eject the
    disc from the status menu instead (#0045 check 2: **Eject Disc** after a
    failed job opens the tray) and re-insert it — it is detected as a new
    insertion and scanned (#0045 check 5) — then Retry is disabled until the
    scan completes and enabled after it, and swapping a *different* disc in
    disables it with "a different disc is in the drive" (#0048 check 3,
    third bullet).
16. History now shows, oldest first: disc 1 succeeded, disc 2 cancelled,
    disc 2 retry succeeded, disc 3 failed, disc 3 retry succeeded. Each row
    opens its own log (A5; #0048 check 1). Take the screenshot for
    `issues/0048/`. **Clear History**: the list empties and "No Job
    Selected" does not appear (#0048 check 4, last clause).
17. Verify on disk: three movie folders under `Movies/`, one clip under
    `Clips/`, `ffprobe` durations within seconds of each scan, nothing left
    under `Working/`. `log show … "Entering Sleep" --last 6h` shows no
    sleep during any job. Restore the idle-sleep setting, or leave the app
    idle past ten minutes and confirm the mini sleeps normally (#0047 check
    4, second half).

Failure paths, any disc, a few minutes each (steps 18–20 need a scratch
root; nothing in them writes to Plex):

18. **Eject while idle and while busy.** With a scanned disc idle, Eject Disc
    opens the tray and logs "Disc ejected." (#0045 check 1). Re-insert. In a
    shell, `cd /Volumes/<disc>`; Eject Disc logs the busy message and the
    disc stays usable; `cd ~`; Eject works (#0045 check 4). During a scan,
    the Eject row is disabled with the mid-scan tooltip (#0045 check 3) —
    this is #0051's dead end; note how long the scan takes on this drive.
19. **Pull the disc mid-encode** (#0046 check 3, #0052). Start a job, press
    the drive's eject button a minute in. Record: whether the tray opens at
    all while mounted; what the job log says (today: nothing about the
    removal); how long until the job ends and with which headline; whether
    Cancel shortens it. Then the next Start is accepted (#0046 check 5).
    This is the one check expected to look wrong today; its findings go on
    #0052.
20. **Partial eject** (#0049, best effort). If the drive lets the tray be
    held shut, Eject Disc with it held: the log reads "The disc was
    unmounted but not ejected …", Start and Rescan are disabled with that
    reason as their tooltip, Retry in History is disabled with the same, and
    Eject Disc stays enabled. Release and Eject again: the tray opens and
    the refusals clear. If the tray cannot be held, mount the disc again
    from Disk Utility after an unmount: the log reads "Disc remounted at …"
    and Start works from the new path. During an ordinary session, "Disc
    remounted" never appears (#0049's four checks).

Optional, separate session: cancel during a MakeMKV fallback rip (#0046
check 2; needs `makemkvcon` and an induced HandBrake failure), cancel during
an extra (#0046 check 4), and Phase 2's owed disc checks (#0020's list).
