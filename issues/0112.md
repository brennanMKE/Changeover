# 0112 — Encoder, quality and preset are hardcoded in `Config` with no way to change them and no in-app explanation of what the numbers mean

| | |
|---|---|

| **Module** | SettingsView / AppSettings / Config |
| **Platform** | macOS |
| **First seen** | 2026-09-12 |

## Description

The three settings that decide what every output file looks like — video encoder, quality (RF) and encoder preset — are compile-time constants in `Config.swift`. A user who wants smaller files, or better quality, or faster encodes has no way to ask for any of them short of editing Swift and rebuilding. Expose all three in Settings, persisted in `AppSettings` alongside the existing paths, with [#0018](0018.md)'s measured values as the defaults. **The hard part is not the controls — it is the explanation.** RF is not a size, it is not a percentage, and the scale means something different for x264 and x265; the user did not know what RF meant before running the [#0018](0018.md) experiment, and asked explicitly for "a reference to help them choose". Three unexplained numbers on a settings screen are worse than no controls at all.

## Long Description

`AppSettings` (`AppSettings.swift`) is `@Observable` and `UserDefaults`-backed, and today holds four stored values — `plexMediaRoot`, `makemkvconPath`, `handbrakePath`, `tmdbAPIKey` — plus derived paths. `SettingsView` renders them in three `GroupBox`es: Plex Media Root, CLI Tools, TMDB. The encoding settings appear nowhere, because they live in `Config` (`Config.swift`) as `nonisolated static let` constants baked into the binary.

That was the right call while the values were being decided. [#0018](0018.md) decides them — x265, RF 23, preset `slow`, measured against four alternatives — and `CLAUDE.md` already records the direction of travel: *"All path config moved to `AppSettings`."* Encoding config is the remainder.

### Why this is a Phase 6 ticket and not a Phase 1 one

Phase 1 is "trustworthy single-disc rip" and its job is to make the pipeline produce a correct file with settings the *developer* trusts. Adding user-facing knobs there would be adding surface area to something still being stabilised, and the values were not decided until [#0018](0018.md).

Phase 6 is "ship to other people", and it already owns the entire settings-and-onboarding surface:

- [#0104](0104.md) — first launch dumps the user into a bare Settings window with no guidance. **This is the same defect, one screen over.** A new encoding section added without guidance makes #0104's problem larger, not smaller; whatever explanatory pattern #0104 establishes (inline help text, a checklist, a first-run walkthrough) is the pattern this section should use. **Settle #0104's approach first, then build on it.**
- [#0105](0105.md) — a missing CLI tool is discovered at rip time instead of setup time. Same instinct: tell the user at the point of decision, not at the point of failure.
- [#0111](0111.md) — the TMDB key moved from build config into in-app settings with first-run onboarding. **This is the exact same migration this ticket performs, for a different value**: something that used to be a compile-time constant becomes a user-visible, persisted setting with an explanation of where it comes from. Follow whatever shape #0111 lands on, including where the explanatory text sits and how it reads.

Filing this in Phase 1 would mean three separate tickets in two phases all inventing their own way to explain a settings field to a stranger.

### What the guidance has to actually convey

The user's request was for "a reference to help them choose" — not a tooltip with the flag name in it. Before the [#0018](0018.md) experiment they did not know what RF meant, and they are the person who *built this app*. Anyone who installs it knows less. At minimum the in-app text must get across:

1. **RF is a quality target, not a size target.** You do not ask for a 4 GB file; you ask for a quality level and the encoder produces whatever size that takes. The same RF produces different sizes for different films — a grainy, high-motion film will be much larger than a clean, static one at identical settings. This is the single most counter-intuitive fact about the whole screen and it should be the first thing the section says.
2. **Lower RF = better quality = bigger file.** The direction is backwards from every other "quality" slider a person has used, where higher is better. Say it in words, not just by implication.
3. **The x264 and x265 RF scales are not the same** — roughly two points apart, x265 RF 23 ≈ x264 RF 21. Which means **changing the encoder without changing the RF silently changes the quality**. If the UI lets both be set independently, this is the mistake it will produce, and the guidance is the only thing standing in the way. Consider whether the UI should actively help here rather than only warn — see the Plan.
4. **Presets cost time, not quality.** A slower preset spends more CPU finding a better encode at the *same* RF; it does not make the picture worse or better in any simple sense, it makes the file a bit smaller for the same quality and takes much longer. `slower` was measured at 22 fps — around 7.5 hours for a feature — which is exactly the kind of thing a user will select without realising and then assume the app has hung.

And the guidance should be **consequential, not numeric**. "RF 23" means nothing. "About 1.2 GB and around 1h50 for a typical film" means something. Whether that is shown as a live estimate that updates with the controls or as a static table of three or four example configurations is a design call, but the practical consequence — approximate file size per film and approximate encode time per film — is the thing a non-expert actually reasons with. [#0018](0018.md)'s table is the raw material: it has size, quality and speed for seven configurations already.

## Steps to reproduce

1. Open Settings. There are three sections: Plex Media Root, CLI Tools, Movie Database (TMDB). Nothing about video encoding.
2. Decide you want smaller files, or faster encodes, or better quality.
3. There is no way to ask for any of it. `Config.swift` has to be edited and the app rebuilt.
4. Now imagine step 2 for someone who installed the app from a DMG ([#0102](0102.md)) and has no Xcode.

## Expected behavior

Settings has an encoding section. The user can choose the video encoder, the quality target and the encoder preset; the choices persist across launches; and **the screen explains what each one does in terms a person who has never encoded video can act on** — including the practical consequence of a change, not only its name.

The defaults are [#0018](0018.md)'s measured values (x265, RF 23, `slow`), so a user who never opens the section gets the same output the app would have produced anyway.

## Actual behavior

All three values are `nonisolated static let` constants in `Config.swift`, unreachable from the UI. `AppSettings` stores four unrelated values and knows nothing about encoding. Changing any of them requires a source edit and a rebuild.

## Notes

**The design tension worth deciding before writing any UI:** too many knobs invites misconfiguration. A user who sets RF 30 because "higher must be better" will produce visibly bad files, will not connect the setting to the result weeks later, and will blame the app. The same user who sets preset `veryslow` will conclude the app has hung. Every one of those is a support conversation, and the app ships to people who cannot read the source to work out what happened.

The countermeasure worth considering is **named presets over raw numbers** — a small set like "Smaller file" / "Balanced" / "Best quality", each a bundle of encoder + RF + preset chosen from [#0018](0018.md)'s measurements, each labelled with its practical consequence ("about 1.2 GB, ~1h50 per film"). The raw encoder/RF/preset controls then live behind a disclosure triangle for the person who actually wants them, where the guidance can be denser and more technical because the audience is self-selected. That also resolves guidance point 3 structurally: a named preset always pairs a matched encoder and RF, so the "changed the encoder, forgot the RF" mistake cannot happen at the top level.

This is a recommendation, not a decision — but the ticket should not be implemented as three bare controls with a help string, and the choice should be made deliberately and written down.

**Do not make the values so free-form that the app cannot be reasoned about.** Encoder should be a fixed choice (x265 / x264), not a text field: HandBrake accepts a long list of encoder strings, most of which make no sense here, and a typo becomes a runtime failure minutes into a job. Same for preset — HandBrake's preset names are a known enumeration. RF is the only one that is genuinely a number, and it should be bounded.

**`Config` does not necessarily disappear.** Its constants are a sensible place to keep the *default* values that `AppSettings` falls back to, exactly as `AppSettings.handbrakePath` has a hardcoded default today. Whether the encoding constants move out of `Config` entirely or remain as the default source is an implementation call; what matters is that `EncodeController` reads the effective values from the same place the user's choice lands.

**Conventions that apply** (`CLAUDE.md`, binding): `@Observable` via `import Observation` — never `ObservableObject`, `@Published`, `@StateObject` or `@ObservedObject`. `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`, so `AppSettings` and the view need no annotation; anything `EncodeController` reads must be `nonisolated`, which is why `Config`'s statics already are. The established pattern for getting settings into the nonisolated controllers is [#0014](0014.md)'s: **capture the values off `settings` while on MainActor in `DVDPipeline.run()` and pass them as plain parameters** into the encode call. Do not hand `AppSettings` itself to `EncodeController`.

**Persistence follows the existing shape exactly**: a stored property with a default, a `Keys` entry, a read in `init()` guarded by `!v.isEmpty`, and a write in `persist()` (`AppSettings.swift`). Note that the existing `init()` pattern treats empty string as "unset" — for a numeric RF value, decide explicitly what an absent or malformed stored value does rather than inheriting that idiom by accident.

**What is testable here without a disc:** that a persisted setting round-trips through `UserDefaults`; that the effective values reaching the argument vector are the user's and not `Config`'s once a choice has been made; that an out-of-range or malformed stored RF falls back to the default rather than reaching HandBrake; and — if named presets are adopted — that each preset maps to the intended encoder/RF/preset triple. All of that is real unit-test territory per the caveat in `issues/Issues.md`. What is *not* testable is whether the guidance actually helps anyone, which is a matter of putting it in front of someone who has not read this ticket.

## Plan

### 1. Decide the control shape first

Before any code: named presets with a disclosure for raw controls, or three raw controls with help text? See `## Notes`. This decision determines everything below and should be settled with the user, alongside [#0104](0104.md)'s onboarding approach, not discovered while implementing.

If named presets win, define them from [#0018](0018.md)'s table — each a (encoder, RF, preset) triple with a measured size and speed behind it, so the label's promise is backed by a number someone actually recorded.

### 2. `AppSettings` — three new stored values

Following the existing pattern exactly (`AppSettings.swift`): stored property with default, `Keys` entry, read in `init()`, write in `persist()`. Defaults are [#0018](0018.md)'s values. Decide deliberately how a missing or malformed stored value behaves — the existing `!v.isEmpty` idiom is written for path strings and does not transfer cleanly to a bounded number.

Keep the properties simple and `Sendable`-friendly; they are captured on MainActor and passed into a nonisolated function.

### 3. `SettingsView` — a fourth `GroupBox`

A "Video Encoding" section beside the three existing ones, in the same visual idiom (`GroupBox`, `.padding(6)`, caption-styled explanatory text — the TMDB section's help paragraph is the closest existing model). Controls should be constrained: a `Picker` for encoder, a `Picker` or stepper-bounded field for RF, a `Picker` for preset. Not free text.

Note the window is `.frame(width: 460)` and already fairly tall; a section carrying real explanatory text may push the layout past comfortable. If so, that is a signal for the disclosure approach rather than for shorter text — do not solve it by cutting the guidance down to a tooltip.

### 4. Thread the values through to the encode

`DVDPipeline.run()` captures them off `settings` on MainActor with the other path strings and passes them into `EncodeController.encode`, which builds the argument vector from its parameters. Do not read `AppSettings` from inside the nonisolated controller, and do not reach for a global.

Whether `Config`'s constants remain as the default source or are removed is an implementation call (see `## Notes`); either way there must be exactly one place the effective value comes from.

### 5. Write the guidance

This is the deliverable, not the trimming. It has to cover the four points in `## Long Description` — RF is a quality target not a size target; lower RF means better and bigger; x264 and x265 scales differ by about two points; slower presets cost time rather than quality — and it should land the practical consequence (approximate size and encode time per film) rather than only the raw numbers.

Write it for someone who has never encoded video, and have someone who has not read this ticket read it back. If they cannot say which way to move RF to get a smaller file, it is not finished.

### 6. Risks

- **Guidance written by someone who already knows the answer.** The single most likely failure: text that is accurate, complete, and useless to the person it is for. The remedy is a reader who does not already know, not another editing pass.
- **The controls ship and the guidance ships as a tooltip.** Layout pressure in a 460pt window makes this the path of least resistance. The explanation is the point of the ticket; if it does not fit, change the layout.
- **A user sets RF 30 and blames the app.** Named presets and bounded controls are the structural mitigation; a warning string is not. Decide in step 1.
- **Encoder and RF changed independently.** Switching encoder without adjusting RF silently changes quality by about two points of scale. Named presets prevent it by construction; raw controls must at minimum surface it at the moment of change.
- **Scope creep into filters and audio.** Deinterlace/detelecine is [#0016](0016.md) and it argues *against* a user-facing override. Audio is settled ([#0018](0018.md), [#0029](0029.md)). A "Video Encoding" section is not an invitation to expose the whole argument vector.
- **Overlap with [#0104](0104.md) and [#0111](0111.md).** All three touch the same window and the same "explain this field to a stranger" problem. Settle ownership before starting, exactly as [#0100](0100.md) already advises for #0104/#0106/#0111.
