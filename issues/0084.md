# 0084 — Disc title picker is too dense to use on a phone

| | |
|---|---|
| **Status** | open |
| **Module** | TitlePicker / RemoteClient |
| **Platform** | iOS · iPadOS |
| **First seen** | 2026-09-11 |

## Description

Phase 2's title picker shows every title on the disc with duration, chapter
count and size, plus per-stream audio and subtitle language selection. That is a
wide, multi-column, checkbox-dense table designed for a Mac window, and it does
not fit a phone at any reasonable font size.

## Long Description

This is the densest screen in the product. Per `Roadmap.md` Phase 2 and the
`DiscInfo` / `DiscTitle` / `DiscStream` model sketched in `RemoteControl.md`,
each title carries an index, a `Duration`, a `chapterCount`, a `sizeBytes` and an
array of streams each with a type, a language and a codec — and the user is
selecting a title *and* a set of audio languages *and* a set of subtitle
languages. A DVD with bonus features routinely has a dozen-plus titles.

On macOS that is a table with columns. On a 393pt-wide phone there is no honest
way to show four numeric columns and a set of checkboxes at once. Shrinking the
font is not a fix; the whole point of this screen is a judgement call made from
across the room.

The saving grace is that `RemoteControl.md` already specifies a default that
makes the common case a single tap: longest title is the main feature,
everything under roughly five minutes is ignored, and `DiscTitle.suggestedRole`
carries that decision from the host. **The compact design should optimize for
confirming the default, not for browsing the table.** The full table is the
escape hatch, not the main path.

There is also a timing constraint specific to this screen. `makemkvcon info` on
a DVD takes tens of seconds (`RemoteControl.md`, "Risks and gotchas"), and the
user is walking back to the couch while it runs. The phone will frequently be
opened *during* the scan, so a scanning state is not an edge case here — it is
the first thing the screen shows.

## Steps to reproduce

1. Complete Phase 2 ([#0020](0020.md)) so a title picker exists, and
   [#0082](0082.md) so it compiles for iOS.
2. Insert a disc with bonus features at the host.
3. Open the client on an iPhone and navigate to the title list.

## Expected behavior

The phone shows a scanning state while the host scans, then the main feature
already selected with its duration and size, confirmable with one tap. Titles
that were ignored by the heuristic are available behind a disclosure. Audio and
subtitle language selection is reachable but does not compete for space with the
title list.

## Actual behavior

The Phase 2 picker renders its macOS column layout at phone width — columns
collide or truncate, per-stream checkboxes are below a usable tap target, and
there is no compact path that distinguishes "confirm the obvious default" from
"inspect all fourteen titles".

## Notes

This ticket is dependent on Phase 2 in a way the others are not. If Phase 2's
picker has not shipped, this cannot be worked — and if Phase 2's picker was
built as a `Table` with `TableColumn`, this ticket gets larger, because `Table`
degrades to a single-column list on compact iOS and the column content would
have to be rebuilt anyway.

Worth raising with Phase 2 before it is implemented: if the picker's row content
is factored as a view that takes a `DiscTitle` and a size class, rather than as
`TableColumn` definitions, this ticket becomes a layout pass instead of a
rewrite. That is a cheap request to make early and expensive to retrofit.

`RemoteControl.md` open question 4 — whether extras should be ripped at all by
default, and whether they go to a separate `Extras/` folder — is not settled.
The compact UI should not bake in an answer; a multi-select title list covers
both outcomes.

## Plan

### 1. Three states, and the first one is not the list

The compact screen is a small state machine driven by Phase 4's `JobState` and
`RemoteEvent.discInfo`:

1. **No disc** — "Insert a disc at the Mac mini."
2. **Scanning** — a progress state naming what is happening ("Reading disc — this
   takes about a minute"). Not a spinner over an empty list. `RemoteControl.md`
   calls out explicitly that an empty title list during a scan reads as a
   failure.
3. **Scanned** — the picker below.

Scan failure (expired MakeMKV key, unreadable disc) must render as its own
message, per Phase 2's exit criteria, not as state 1 or an empty state 3.

### 2. Lead with the recommendation, not the table

Top of the scanned state: a single prominent card for the title whose
`suggestedRole` is `.mainFeature` — poster-adjacent in visual weight — showing
formatted duration, chapter count and size, with the primary action right there.
That is the one-tap path and it should be the whole screen for the common case.

Below it, a disclosure row: "14 other titles" expanding into the full list.
Inside, rows are `DiscTitle` summaries, each a `NavigationLink` to a detail
screen, with a multi-select affordance for choosing extras.

Format the numbers for a phone, not a spreadsheet: `Duration` through
`Duration.UnitsFormatStyle` (`1:52:13`), size through
`Measurement<UnitInformationStorage>` or `ByteCountFormatStyle` (`6.2 GB`).
Chapter count as "24 chapters", not a bare integer in a column. A single
secondary line reading `1:52:13 · 24 chapters · 6.2 GB` replaces three columns
and stays legible at large Dynamic Type.

### 3. Language selection is a separate step, not inline checkboxes

Per-stream selection is the part that genuinely cannot be compact. Move it to
its own destination, reached from the title detail screen, and collapse it from
"a checkbox per stream" to "a toggle per language" wherever the disc has one
stream per language — which is the normal case.

The known real-world requirement from `mac_plex_dvd_workflow.md` is "keep
English and Spanish, drop the rest", so the screen should make that a two-tap
operation: a short list of audio languages with toggles, a short list of
subtitle languages with toggles, defaults preselected. Show the codec only when
a language has more than one stream and the choice actually matters.

The selection has to serialize into Phase 4's `RipRequest` —
`titleIndices: [Int]`, `audioLanguages: [String]`, `subtitleLanguages: [String]`
— so the client's selection state should be modeled on those three fields
directly rather than as a parallel structure that needs mapping.

### 4. State ownership

The selection lives in an `@Observable` type owned by the picker screen with
`@State`, holding exactly the three `RipRequest` fields plus the received
`DiscInfo`. Child screens receive it as a plain parameter and use `@Bindable`
for toggle bindings. No `@ObservableObject`, no `@StateObject`. The type is
`@MainActor` by default under the project's
`SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` setting
(`Changeover.xcodeproj/project.pbxproj:416`, `:445`) and should not be written
as an `actor` — it is pure UI state.

Incoming `RemoteEvent.discInfo` must not silently discard a selection in
progress. If a rescan arrives while the user is mid-selection, reset to the new
defaults and say so; do not merge.

### 5. Ordering and risks

Build state 2 (scanning) before state 3 (the list). It is smaller, it is what
the user sees first in practice, and it is the state most likely to be skipped
and then discovered missing on a real disc.

- **Risk: Phase 2 built a `Table`.** Check before estimating. `Table` collapses
  to one column in compact width and the column content would need rebuilding.
- **Risk: discs with many near-identical titles.** Some DVDs expose a dozen
  titles within seconds of each other in length. The recommendation card is
  actively misleading there. Detect the case (several titles within, say, 10% of
  the longest) and open on the list instead of the card.
- **Risk: the compact and regular pickers diverge.** Share the row and detail
  views; branch only the container. See [#0085](0085.md).

### 6. Verification

Honest split:

- **Unit-testable, and should be:** duration/size/chapter formatting, the
  "several near-identical titles" detection, the mapping from selection state to
  `RipRequest`, and the reset-on-rescan behavior. These are pure functions over
  `DiscInfo` and deserve real tests per the project's verification caveat.
- **Simulator-verifiable:** every layout state, by feeding a fixture `DiscInfo`
  decoded from a captured JSON payload. Capture one real `DiscInfo` from a real
  scan during Phase 2 and commit it as a fixture — it makes this ticket testable
  without a disc and is worth the five minutes.
- **Device- and disc-bound:** that the title list matches what MakeMKV.app shows
  for the same physical disc, and that a rip started from the phone produces the
  chosen title with the chosen languages. This needs a real iPhone, the real
  mini, and a real disc with bonus features. There is no substitute and the
  `## Verification` section must say so plainly.
