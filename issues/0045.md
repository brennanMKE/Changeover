# 0045 — The disc stays in the drive for the whole job, so the next disc cannot be scanned or queued

| | |
|---|---|
| **Status** | open |
| **Phase** | 3 — Unattended multi-disc |
| **Module** | DiscSession / DVDMonitor |
| **Platform** | macOS |
| **First seen** | 2026-09-11 |

## Description

The disc is only needed during the rip, but Phase 1 ejects it "on completion" (`Roadmap.md:80`) — after the encode and the move. That keeps the tray occupied for the longest stage of the job, which makes the Phase 3 demo physically impossible: there is nowhere to put disc two while disc one is encoding. The eject point moves to the end of the rip stage, and the app gains a `DiscSession` concept so a new disc can be scanned and set up while earlier jobs are still running.

## Long Description

Three separate problems are bundled here because they are one problem in practice — "the app conflates the disc with the job".

**Eject timing.** With [#0044](0044.md)'s lanes in place, a job leaves the drive lane at `awaitingEncode`. That is the correct eject point. Any later and the drive lane is free but the tray is not, which is the same stall with extra steps.

**The disc has no identity.** `DVDMonitor.onDVDInserted` is `(() -> Void)?` (`Changeover/DVDMonitor.swift:4`) — it fires with no payload at all. `volumeMounted` has the volume URL in hand (`:18`) and the `VIDEO_TS` check (`:21-22`) but throws the URL away before calling back (`:24-26`). There is also no `didUnmountNotification` observer, so the app cannot tell that the disc it is about to rip was pulled out. In a single-job world that did not matter; with a queue it is a correctness bug — a job can sit in `queued` while the user, impatient, swaps the disc, and the scheduler will then rip the wrong movie under the previous movie's metadata, into the previous movie's Plex folder. That is the same class of defect as the stale-`.mkv` bug Phase 1 fixes (`Roadmap.md:35-38`), arriving by a different route.

**The metadata window is reused across discs.** `showMetadataEntry()` reuses the existing window if it is visible (`Changeover/AppDelegate.swift:72-76`), and `MetadataEntryView` keeps `vm.selectedMovie` and `selectedID` as long-lived state (`Changeover/MetadataEntryView.swift:5-6`). Insert a second disc while that window is open with a stale selection and pressing Start rips the new disc as the old movie.

## Steps to reproduce

1. Insert disc one, select the movie, press Start.
2. Wait for the rip to finish and the encode to begin.
3. Try to insert disc two.
4. Separately: with the metadata window open and a movie already selected from a previous disc, insert a new disc and press Start without changing the selection.

## Expected behavior

At step 3 the tray is already open — the disc ejected the instant its rip finished. Inserting disc two starts a fresh `DiscSession`: the metadata window resets to an empty search bound to the new disc, Phase 2 scans it, and pressing Start enqueues a second job that enters the drive lane while job one is still encoding. At step 4 the stale selection is gone, because the session it belonged to ended when its disc was ejected.

## Actual behavior

At step 3 the disc from job one is still in the drive and there is no eject control short of the Finder. At step 4 the previous selection is still highlighted and Start is live; the app will rip the newly inserted disc and file it under the previous movie's `Title (Year) {tmdb-ID}` folder (`Changeover/MovieMetadata.swift` naming, applied at `Changeover/PlexOrganizer.swift:16-19`).

## Plan

### Files added

- `Changeover/Jobs/DiscSession.swift`
- `ChangeoverTests/DiscSessionTests.swift`

### Files changed

- `Changeover/DVDMonitor.swift` — carry the volume identity through, and observe unmounts.
- `Changeover/Jobs/JobScheduler.swift` — eject at the end of the rip stage; verify disc identity before starting a rip.
- `Changeover/AppDelegate.swift` — own the current `DiscSession`; drive the metadata window from it (`:60-93`).
- `Changeover/MetadataEntryView.swift` — reset on session change.

### `DVDMonitor` changes

```swift
struct DiscToken: Hashable, Codable, Sendable {
    let volumeURL: URL
    let volumeName: String
    let mountedAt: Date
}

var onDiscInserted: ((DiscToken) -> Void)?
var onDiscRemoved:  ((DiscToken) -> Void)?
```

`volumeMounted` already has everything needed at `Changeover/DVDMonitor.swift:18` — pass it through instead of discarding it. Add a second `@objc nonisolated func volumeUnmounted(_:)` observing `NSWorkspace.didUnmountNotification`, matching the existing registration at `:7-12` and the existing `Task { @MainActor [weak self] in … }` hop at `:24-26`. Both selectors stay `nonisolated` — `Plan.md`'s convention table calls this out specifically, because `NSWorkspace` calls them on an arbitrary thread.

`mountedAt` is part of the identity on purpose. Optical media frequently has no `volumeUUIDStringKey`, and two discs from a box set can share a volume name. Mount time disambiguates a remount of the same title, which is the case that matters: same name, different physical disc, and the app must treat it as new.

### `DiscSession`

```swift
@Observable
final class DiscSession: Identifiable {
    let id = UUID()
    let token: DiscToken
    var discInfo: DiscInfo?        // from Phase 2's DiscScanner
    var state: SessionState        // .scanning | .ready | .scanFailed(JobFailure) | .committed(JobID) | .ended
}
```

One session per physical insertion. It ends when its disc unmounts. `AppDelegate` holds `var currentSession: DiscSession?` and injects it alongside `settings` and `jobQueue` with the same `.environment(…)` pattern already used at `Changeover/AppDelegate.swift:43` and `:87`.

`MetadataEntryView` gets `.id(session.id)` on its root, which is the cheapest correct reset: SwiftUI tears down and rebuilds the subtree when the identity changes, so `vm`, `selectedID` and the search text all reset with no manual clearing code. Manual clearing is the tempting alternative and it is the one that will miss a field.

Committing: pressing Start creates the `Job`, enqueues it, and sets `session.state = .committed(jobID)`. The session's job binding is one-way and final — a session commits at most once, and a second Start on a committed session is rejected rather than enqueuing a duplicate.

### Eject at end of rip

In [#0044](0044.md)'s `runRip`, after the rip result comes back and before the transition to `awaitingEncode`:

- Use `NSWorkspace.shared.unmountAndEjectDevice(at:)`, not a shell-out to `drutil eject`. It takes the volume URL the `DiscToken` already carries, returns a real error, and does not depend on a binary path the way `makemkvconPath` and `handbrakePath` do (`Changeover/AppSettings.swift:14-15`). If Phase 1 shipped `drutil`, replace it here and note the swap.
- Eject **after** the `makemkvcon` process has terminated. `RipController`'s continuation resumes from `terminationHandler` (`Changeover/RipController.swift:44-54`), so awaiting `rip(...)` already guarantees that. Ejecting while the process holds the device fails with a busy error.
- An eject failure is **not** a job failure. The rip succeeded; the file is on disk. Log it as a milestone, leave the job continuing into `awaitingEncode`, and surface "Disc could not be ejected" in the queue view ([#0048](0048.md)) with a manual **Eject** button. Failing an otherwise-successful job because a tray stuck would be a bad trade.
- On a failed rip, eject too. The disc is no longer useful in the drive and leaving it there blocks the next one.

### Disc identity check before ripping

`makemkvcon` addresses `disc:0` (`Changeover/RipController.swift:21`) — a drive index, not a volume. So before transitioning a job to `.ripping`, the scheduler asserts that the volume named by the job's `DiscToken` is still mounted. If it is not, fail the job with `JobFailure.discRemoved` ([#0041](0041.md)) rather than ripping whatever happens to be in the drive. Where Phase 2's `DiscScanner` has parsed a `DRV:` line (`RemoteControl.md:238`), cross-check the disc name too.

Also handle the live case: if `onDiscRemoved` fires for the token of the currently `.ripping` job, fail that job `.discRemoved` immediately rather than waiting for `makemkvcon` to report an I/O error minutes later.

### Risks

- **`disc:0` is assumed everywhere.** A Mac with an internal drive *and* a USB drive breaks the volume-to-drive mapping this ticket relies on. Out of scope for Phase 3 — note it, and let Phase 2's `DRV:` parsing be the eventual fix.
- **Auto-mount races the scan.** macOS mounts the volume before the disc is fully spun up and readable; a `makemkvcon info` fired at mount time can fail spuriously. Phase 2 owns scan retry, but the session state machine has to tolerate `scanFailed` and offer a rescan rather than treating it as terminal.
- **Do not eject on `awaitingEncode` in the state machine itself.** Put the eject in the scheduler's rip-stage epilogue. Hanging a side effect off a state transition makes the transition untestable and means a replayed or restored state would try to eject a drive.

## Notes

**Verification.** The session state machine and the identity check are testable without hardware and must be: `ChangeoverTests/DiscSessionTests.swift` covers a session ending on unmount of its own token and *not* on unmount of a different one; a second Start on a `.committed` session being rejected; and — driven through [#0044](0044.md)'s `StageRunnerStub` — a job whose `DiscToken` unmounts before its rip starts failing `.discRemoved` with no process launched, plus a `.ripping` job failing `.discRemoved` when its token unmounts mid-rip.

Everything physical is manual and must say so plainly in `## Verification`, naming both discs used: the tray opening the moment the rip finishes while the encode continues; a second disc being inserted, scanned and started while the first job is still `encoding`; the metadata window showing an empty search for the new disc rather than the previous selection; and pulling a disc mid-rip to confirm the job fails as `discRemoved` rather than hanging.
