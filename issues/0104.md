# 0104 — First launch dumps the user into a bare Settings window with no guidance

| | |
|---|---|
| **Status** | open |
| **Phase** | 6 — Ship to other people |
| **Module** | Onboarding / AppDelegate |
| **Platform** | macOS |
| **First seen** | 2026-09-11 |

## Description

On first launch Changeover opens the Settings window and stops (`Changeover/AppDelegate.swift:23-25`). The user is shown four fields — a folder picker, two filesystem paths, and a `SecureField` — with no ordering, no indication of which are already satisfied, and no explanation of where any of the values come from. Nothing tells them that two of those paths point at binaries that may not exist on their machine.

## Long Description

`AppSettings.isConfigured` (`Changeover/AppSettings.swift:33`) is:

```swift
var isConfigured: Bool { !plexMediaRoot.isEmpty && !tmdbAPIKey.isEmpty }
```

Two of the five real prerequisites are not represented at all. `makemkvconPath`
and `handbrakePath` default to hardcoded Apple-Silicon Homebrew paths
(`:14-15`) that are never checked for existence, so `isConfigured` returns
`true` — and `StatusMenuView` shows a green dot and "Idle — insert a DVD to
begin" (`Changeover/StatusMenuView.swift:16-18`) — on a machine where neither
tool is installed. The TMDB key is likewise "configured" as soon as it is
non-empty, whether or not it works ([#0106](0106.md)).

`SettingsView` (`Changeover/SettingsView.swift:7-73`) is a settings panel, not an
onboarding flow: three `GroupBox`es in arbitrary order, each showing current
values, with a single "Save" that persists everything and closes the window
(`:64-67`). It is the right UI for *changing* a setting later. It is the wrong UI
for someone who has never seen the app and does not know what a TMDB key is.

This matters more than the usual polish argument because of
`RemoteControl.md:86`: **"Not a single-user app."** The design intent is that
anyone managing a DVD collection into Plex can use this. Every default in
`AppSettings` currently encodes the author's machine.

## Steps to reproduce

1. On a Mac with no prior Changeover install, delete any existing defaults:
   `defaults delete co.sstools.Changeover`
2. Launch Changeover.
3. Try to determine, from the UI alone, what you need to do next.

## Expected behavior

A first-run flow that presents the prerequisites **in order**, each with its own
explicit state (satisfied / missing / unknown / checking), what it is for, and
how to satisfy it. The user works down the list; the flow does not declare the
app ready until every item is genuinely satisfied. The menu bar status reflects
the same truth.

## Actual behavior

The Settings window appears. Three group boxes, four controls, no order, no
explanation beyond one caption about TMDB (`Changeover/SettingsView.swift:54`).
Two fields are pre-filled with paths that may be wrong and are never validated.
Closing the window leaves the app claiming to be ready.

## Plan

This is the spine of Phase 6's onboarding half; [#0105](0105.md),
[#0106](0106.md) and [#0107](0107.md) each fill in one row of the checklist this
ticket builds. Land this first so those have somewhere to plug into.

**1. Model the prerequisites explicitly.** New file
`Changeover/Onboarding/SetupRequirement.swift` (a new subdirectory under
`Changeover/` is fine and auto-compiles — the target uses
`PBXFileSystemSynchronizedRootGroup`, per `Plan.md`'s notes on the Xcode 26.2
project). Sketch:

```swift
enum RequirementState: Equatable {
    case unknown, checking, satisfied(detail: String), missing(reason: String), notApplicable(reason: String)
}
```

`notApplicable` exists for the Local Network row — see the scoping note below.
Keep it a plain `enum` / `struct`; per `Plan.md` "Swift conventions", the project
is `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` and nothing here needs to leave
the main actor.

**2. Add `@Observable final class SetupChecklist`** (`Changeover/Onboarding/SetupChecklist.swift`),
owned by `AppDelegate` alongside `settings` (`Changeover/AppDelegate.swift:8`)
so the menu bar, the onboarding window and the Settings window all read one
source of truth. `@Observable` from the `Observation` module — never
`ObservableObject` (`Plan.md`, "Swift conventions"). It holds the ordered
requirement list and a `recheck()` that re-evaluates every row.

Order, matching `Roadmap.md:235-236`:

| # | Requirement | How it is checked | Ticket |
|---|---|---|---|
| 1 | `makemkvcon` | binary exists and is executable at the configured path; probe for version | [#0105](0105.md) |
| 2 | `HandBrakeCLI` | same | [#0105](0105.md) |
| 3 | TMDB API key | live validation call against TMDB | [#0106](0106.md) |
| 4 | Plex media root | folder chosen, exists, and is **writable** | this ticket |
| 5 | Local Network access | *deferred — see scoping note* | [#0060](0060.md) |
| 6 | Launch at login | `SMAppService.mainApp.status` | [#0107](0107.md) |

**3. Redefine `isConfigured` in terms of the checklist.** Replace
`Changeover/AppSettings.swift:33` with a derivation from `SetupChecklist` —
ready only when rows 1–4 are `satisfied` (rows 5 and 6 are advisory, not
blocking; the app is perfectly usable at the machine without a login item or
Local Network access). Everything that reads `isConfigured` follows:
`AppDelegate.swift:23`, `StatusMenuView.swift:16-18`, `StatusMenuView.swift:37`.

**4. Add row 4's missing check.** The Plex root is currently only tested for
non-emptiness. `PlexOrganizer` will fail at the end of a long job if the
destination is unwritable. Check `FileManager.default.isWritableFile(atPath:)` on
`plexMediaRoot`, and create `Movies` / `Working/ripping` / `Working/encoding`
(`Changeover/AppSettings.swift:21-30`) if absent rather than making the user run
the `mkdir -p` block from `README.md:53-58`. An external volume that is not
mounted is a distinct state from a path that was never chosen — report it as
such.

**5. Build `OnboardingView`** (`Changeover/Onboarding/OnboardingView.swift`): the
ordered list, one row per requirement, each with title, one-sentence purpose,
current state with an icon, and an action button whose label depends on state
("Detect", "Choose…", "Get a key", "Recheck"). Add
`AppDelegate.showOnboarding()` next to `showSettings()`
(`Changeover/AppDelegate.swift:97-121`), following the same window pattern, and
change the first-launch branch at `:23-25` to call it instead of
`showSettings()`. Keep `SettingsView` as-is for later edits — do not try to make
one view serve both jobs. Add an "Open Setup…" row to `StatusMenuView` so the
flow is reachable again after it is dismissed.

**6. `@Bindable` for bindings** from the `@Observable` settings passed into
subviews (`Plan.md`, "Swift conventions"); `SettingsView` already does this at
`:5`.

**Risks.** (a) Scope creep into a multi-step wizard with Back/Next — resist it;
a checklist the user can work in any order but that *presents* in order is
cheaper and more honest, because real users arrive with some rows already
satisfied. (b) Re-checking on every keystroke will hammer the TMDB endpoint —
[#0106](0106.md) owns that debouncing. (c) `isConfigured` currently gates
`StatusMenuView`'s "Open…" row (`:37`); tightening it means an existing user who
has MakeMKV installed somewhere unusual could suddenly find the app "not
configured". Re-detect on first run after upgrade rather than just failing the row.

**Scoping note — Local Network access (row 5).** The roadmap demo
(`Roadmap.md:236`) lists "granting Local Network access" as a Phase 6 onboarding
step, but **Changeover has nothing to grant it for yet**. The permission prompt
is triggered by opening a listener or browsing Bonjour, which arrives with the
Phase 4 `RemoteServer`; `NSLocalNetworkUsageDescription` and `NSBonjourServices`
are Phase 4 deliverables (`RemoteControl.md:435-438`, `:504`). Implement row 5
as `notApplicable(reason: "Remote control is not enabled in this version")` with
the plumbing in place, and let [#0060](0060.md) light it up. The real problem
`RemoteControl.md:447` names — that the prompt must be accepted *at* a headless
mini, where nobody is sitting — is a Phase 4 problem that this checklist is the
right place to surface when it exists.

## Notes

**Testing this honestly requires a genuinely fresh environment**, because the
bug is about the state of a user who has never run the app. Two options:

```bash
# Cheapest: a brand-new user account on the same Mac.
#   System Settings → Users & Groups → Add Account, log in as that user, launch
#   Changeover from /Applications. No Homebrew on PATH surprises, no UserDefaults,
#   no prior TMDB key. Adequate for this ticket (it is NOT adequate for
#   Gatekeeper — see #0103).

# Or reset the current account's state (destructive — note the key first):
defaults read co.sstools.Changeover          # save this output
defaults delete co.sstools.Changeover
```

Do **not** test this by reasoning about the code path. The whole defect is that
the author cannot see the problem from their own machine, and neither can an
agent reading `AppSettings.swift`.

**What automated tests can cover:** `SetupChecklist`'s state transitions and the
new `isConfigured` derivation are pure logic over injectable inputs and should
have real unit tests in `ChangeoverTests` — `issues/Issues.md` explicitly names
"path derivation" and "state machines" as the parts where "tests must actually
run" applies literally. Inject the filesystem probe and the TMDB probe so the
tests do not touch the network or `/opt/homebrew`.
