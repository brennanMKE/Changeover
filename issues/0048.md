# 0048 — There is no way to see what jobs exist, what they are doing, or what happened to the ones that finished

| | |
|---|---|
| **Status** | open |
| **Phase** | 3 — Unattended multi-disc |
| **Module** | QueueView / StatusMenuView |
| **Platform** | macOS |
| **First seen** | 2026-09-11 |

## Description

The only progress surface in the app is a 130-point scrolling log pane inside the metadata window (`Changeover/MetadataEntryView.swift:93-119`), and the menu bar popover says a hardcoded "Idle — insert a DVD to begin" whether or not anything is running (`Changeover/StatusMenuView.swift:18`). With a queue there is no way to see the two concurrent jobs, their order, their outcomes, or a finished job's log.

## Long Description

The Phase 3 demo ends with "the queue view shows what happened in what order" (`Roadmap.md:141`), which is the acceptance criterion for this ticket. The view is genuinely the proof of the phase: two rows, one `encoding` and one `ripping`, at the same moment, is the only way to see that [#0044](0044.md)'s lanes work.

Three surfaces change:

- A new **queue window** — the list of jobs with stage, progress and elapsed time, a detail pane for the selected job's log, and per-job Cancel and Retry.
- The **menu bar popover**, which currently hardcodes an idle string and gates its Open… row on `settings.isConfigured` (`Changeover/StatusMenuView.swift:16-18`, `:37`). It becomes a live summary and gains a Queue… row.
- The **metadata window**, which sheds its log pane and its `isProcessing` gating. Pressing Start hands the job to the queue and the window's job is done.

## Steps to reproduce

1. Start a job and close the metadata window.
2. Look for progress anywhere in the app.
3. Start a second job, then try to see both.
4. After a job finishes, try to read its log.

## Expected behavior

A queue window lists every job oldest-first with its stage, its own progress, and elapsed time, updating live. Two concurrent jobs show as two rows in different stages. Selecting a row shows that job's log, including for jobs that finished earlier in the session, with a note when earlier lines were dropped. Failed jobs show the actual reason and a Retry; running jobs show Cancel. The menu bar popover summarises the queue at a glance and opens the window.

## Actual behavior

Closing the metadata window takes the only progress display with it. The log array is `@State` in that view (`Changeover/MetadataEntryView.swift:8`) and is cleared at the start of every job (`:146`), so nothing survives. The popover shows "Idle — insert a DVD to begin" during an active rip. There is no cancel, no retry, and no per-job anything, because there are no jobs as such.

### The view

```swift
struct QueueView: View {
    @Environment(JobQueue.self) private var queue
    @State private var selection: JobID?
    var body: some View { /* List(queue.jobs, selection: $selection) + detail */ }
}
```

`@Environment(JobQueue.self)`, matching how `AppSettings` is read today (`Changeover/MetadataEntryView.swift:4`, `Changeover/StatusMenuView.swift:5`). The view model, if one is needed at all, is owned with `@State` — never `@StateObject`, never `ObservableObject`; `Plan.md`'s conventions are binding and the whole project already follows them.

`AppDelegate` gains `queueWindow` alongside `metadataWindow` and `settingsWindow` (`Changeover/AppDelegate.swift:13-14`) and a `showQueue()` copying the shape of `showMetadataEntry()` (`:69-93`) — reuse if visible, `NSHostingView`, `isReleasedWhenClosed = false`, `.environment(settings)` plus `.environment(jobQueue)`. A wider default than the metadata window's 480×580; roughly 720×520 for a list-plus-detail layout.

### Row identity and observation

`List(queue.jobs, selection: $selection)` works because `Job` is `Identifiable` on `JobID` ([#0041](0041.md)), which is stable across pruning — unlike the array-offset identity the log pane uses today (`Changeover/MetadataEntryView.swift:99`), which shifts under eviction.

The observation shape matters for a view updating under a two-process line rate. `Job` is an `@Observable` class, so a row reading `job.state` re-renders when *that* job changes and the list does not. Preserve that: pass the `Job` into `JobRow` and read its properties inside the row body. Reading `job.state` in `QueueView.body` to build the rows would make every progress tick on either job invalidate the whole list — the exact thing the reference-type choice in [#0041](0041.md) was made to avoid.

### The log pane

`JobLogView` renders `job.log.lines` from [#0043](0043.md), keyed on `LogLine.id` — the monotonic counter, not the offset. When `job.log.droppedCount > 0`, a header row reads "… 14,332 earlier lines dropped". Keep the autoscroll behaviour from the existing pane (`Changeover/MetadataEntryView.swift:110-114`) but pin it only when the user is already at the bottom; yanking the view down while someone is reading a failure ten thousand lines back is worse than no autoscroll. Milestone lines render in the primary colour, ordinary lines secondary, so the shape of a job is legible from a scrollbar's distance.

### Stage presentation

| Stage | Indicator |
|---|---|
| `queued` | grey dot, "Waiting for the drive" |
| `ripping` | blue, determinate bar when progress is known, indeterminate when `nil` |
| `awaitingEncode` | grey, "Waiting to encode" |
| `encoding` | purple, same progress rule |
| `organizing` | purple, indeterminate |
| `done` | green check, elapsed total |
| `failed` | red, `JobFailure.localizedDescription` plus its `recoverySuggestion` |
| `cancelled` | grey |

`JobState.progress` is `Optional` by design ([#0041](0041.md)); the view must render the `nil` case as indeterminate rather than a stuck 0%.

### Menu bar summary

`StatusMenuView`'s status line (`:16-21`) becomes derived: "Idle — insert a DVD to begin" only when `!queue.hasActiveJobs`; otherwise the live shape, e.g. "Ripping *Fargo* · Encoding *Tombstone*". Add a **Queue…** `MenuRow` (the component at `:61-97`) between Open… and Settings…, showing an active-job count. The status item's symbol (`Changeover/AppDelegate.swift:33`) switches from `opticaldisc` to a filled or badged variant while jobs are active, so the menu bar itself says whether the machine is busy.

### Risks

- **Log rendering under two concurrent processes.** The existing pane rebuilds `Array(logLines.enumerated())` on every append (`Changeover/MetadataEntryView.swift:99`). With two jobs producing lines, rendering the selected job's log must be a `LazyVStack`/`List` over an identified collection with no per-frame array transformation. If it still stutters, the fix is the batching noted in [#0043](0043.md), not a smaller cap.
- **Do not gate the queue window on `settings.isConfigured`.** The Open… row is gated that way today (`Changeover/StatusMenuView.swift:37`) and it is right for starting work — but a user whose settings broke mid-session still needs to see why their jobs failed.
- **Retry semantics.** Retry on a failed job should enqueue a **new** `Job` with a new `JobID` carrying the same `RipRequest`, not resurrect the old one — the transition table forbids leaving a terminal stage ([#0041](0041.md)), and the failed job is the history record. A retry of a job that failed during rip additionally requires its disc to be back in the drive, so it must check the `DiscToken` ([#0045](0045.md)) and explain itself rather than failing instantly with `discRemoved`.
- **Window lifetime.** `isReleasedWhenClosed = false` as the other two windows do (`Changeover/AppDelegate.swift:89`, `:117`); with `LSUIElement = YES` there is no Dock icon to reopen from, so a released window is a window the user cannot get back.

```swift
nonisolated struct JobPresentation: Equatable, Sendable {
    enum Tone: Equatable, Sendable { case neutral, active, warning, success, failure }
    enum ProgressMode: Equatable, Sendable { case none, indeterminate, determinate(Double) }
    let label: String
    let tone: Tone
    let progress: ProgressMode
    let detail: [String]                     // FailurePresenter.message(for:) headline + details
    static func make(for snapshot: JobSnapshot) -> JobPresentation
    static func menuSummary(current: JobSnapshot?, lastFinished: JobSnapshot?, isConfigured: Bool) -> String
    static func canRetry(_ job: JobSnapshot, isRunning: Bool, insertedDiscID: String?, jobDiscID: String?) -> Bool
    static func statusSymbolName(isRunning: Bool) -> String
}
```

- **It takes `JobSnapshot`, not `Job`.** That makes it testable off MainActor, and it's what the Phase 4 remote view will render, which satisfies this plan's own rule that anything read from `Job` must exist on `JobSnapshot`. The view maps `Tone` to colours.
- **Phases:**

  | Phase | Tone | Label | Progress |
  |---|---|---|---|
  | `starting` | neutral | "Checking setup" | — |
  | `encoding` | active | — | determinate when #0043's progress is known, otherwise indeterminate |
  | `fallback` | warning | "Retrying with MakeMKV" | — |
  | `organizing` | active | "Moving into Plex" | indeterminate |
  | `succeeded` | success | elapsed time | — |
  | `failed` | failure | `FailurePresenter` text | — |
  | `cancelled` | neutral | — | — |
- **Retry** is enabled only when:
  - the job ended failed or cancelled;
  - no job is running;
  - both disc ids are non-nil and equal.

  Failures don't eject, so the disc is usually still in. Retry starts a **new** `Job` with the old metadata.

## Notes

**Verification.** This is the one Phase 3 ticket that is mostly *not* unit-testable, and the `Issues.md` caveat applies squarely: a green build proves nothing about a view. What can be tested without a disc is the presentation logic, and it should be extracted to be testable rather than buried in `body` — a pure `JobPresentation` (stage label, colour, progress mode, failure text) with cases over every `JobStage` and every `JobFailure`, plus the menu bar summary string for zero, one and two active jobs. Those go in `ChangeoverTests`.

Everything else is manual and must say so, naming the discs used: two concurrent jobs visible as two rows in different stages at the same moment (this is the phase's proof, and a screenshot belongs in `issues/0048/`); selecting a finished job and reading its log; a failed job showing a specific reason and a working Retry; Cancel on a running job actually stopping it; the menu bar summary and status symbol tracking the queue; and the window surviving being closed and reopened mid-job with state intact.
