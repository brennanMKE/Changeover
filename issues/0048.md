## Description

The only progress surface in the app is a 130-point scrolling log pane inside the metadata window (`Changeover/MetadataEntryView.swift:93-119`), and the menu bar popover says a hardcoded "Idle — insert a DVD to begin" whether or not anything is running (`Changeover/StatusMenuView.swift:18`). With a queue there is no way to see the two concurrent jobs, their order, their outcomes, or a finished job's log.

## Resolution notes

> 🟢 Resolved 2026-09-15 — A history window now lists the session's jobs with their own logs, failure reasons, a confirmed Cancel and a Retry that replays the job's own recorded request on its own disc, and the menu bar summary, dot and glyph track the running job (265f0f7, review fix 4c78ea1).

**Review (2026-09-15, claude-opus-5).** 265f0f7 is in scope and its pure presentation layer is sound. Two things were wrong, and 4c78ea1 fixes them:

1. **Retry could file the wrong title under the job's movie name.** It rebuilt a `RipRequest` from the job's metadata plus `JobController`'s *live* title/audio/extras selection.
   - **A disc swap was already safe.** The metadata carries `selectionDisc`, and `start`'s #0034 `sameDisc` check refuses metadata bound to another disc. "Disc B encoded under movie A" could not happen.
   - **The same disc was not.** The user can change the selection after a failure, with no swap or rescan. Two examples: a title picked for a second movie on a double-feature disc, or a re-inserted disc's fresh preselection. Retry then encoded that title under the failed job's name, and `PlexOrganizer.move` replaces an existing copy on purpose (#0012). The draft's "nothing clears the selection when a job finishes" was true but beside the point.
   - **A disc with no identity could never be retried.** `canRetry` compared raw `discID`s, even though `start` accepts the same insertion.
   - **Fix:** `Job.request` records the `RipRequest` `start` accepted. `JobController.retry(id:settings:)` replays it behind `JobPresentation.retryDecision`, which replaces `canRetry`. It allows a retry only for a failed or cancelled job with a recorded request, with nothing running or ejecting, the job's own disc in the drive (by `SelectionReset.sameDisc`, `start`'s rule) and a completed scan. Every refusal carries a reason, which is logged and used as the disabled button's tooltip. `start` still re-checks the disc binding and that the title and tracks resolve against the held scan.
2. **Cancel's confirmation was a SwiftUI `.confirmationDialog` inside the `.transient` `NSPopover`.** A dialog taking focus can close a transient popover and orphan the dialog, so neither button fires.
   - **Fix:** `AppDelegate.requestCancel(jobID:)` closes the popover, then asks through an injectable `confirmCancel` seam. In production that is an app-modal `NSAlert`: "Keep Going" is the default (Return) button and "Cancel Job" is marked destructive.
   - It never asks about a cancel `CancelPolicy` refuses (no job, a stale id, `organizing`) or one already accepted. After a yes, `jobs.cancel(id:)` re-checks, so a job that reached `organizing` or finished while the alert was up is refused and logged.
   - The history window uses the same path instead of its own `.alert`.
   - "Cancelling…" moved from the history view's `@State` to `JobController.cancellingJobID`, set by an accepted cancel and cleared in `finish`. A cancel from either surface now shows in the menu row, the menu summary and the history window.

Smaller fixes in 4c78ea1:

- A notification for a job pruned from history selected an id no row had, which left "No Job Selected". `JobPresentation.historySelection` falls back to the existing selection, else the newest row. It is also re-applied when the rows change (Clear History, pruning).

## Root cause

By the time of this pass (`### Plan refresh (2026-09-15)` below, which
supersedes the original "QueueView with two lanes" design once #0040 settled
on option A — one job at a time), most of the pieces this ticket needs
already existed: `JobController.current`/`history` (#0042), a per-job `JobLog`
with `displayLines` (#0043), the validated `JobPhase`/`JobState` machine
(#0041), and real Cancel/Eject actions (#0046/#0045). What was actually
missing was narrower than the filing's premise:

- **No view read any of it.** `JobController.history` had no reader anywhere
  in the app — a finished job's log and outcome were reachable in code but
  invisible on screen the moment the next job started.
- **The popover's summary and status glyph were both static strings/images**,
  never touching `current`/`history` beyond the one `statusDescription`
  string `StatusMenuView` already read — there was no shared, tested layer
  deciding "what does this phase look like" that a view (or a future Phase 4
  client rendering the same `JobSnapshot`) could reuse.
- **A notification click always opened the metadata window**, even though
  the job it was about was almost always already finished and had nothing
  left to show there.
- **Cancel had no confirmation step**, per the #0046 review's own handoff
  note, and no "Cancelling…" state to bridge SIGKILL's escalation window.

**Retry** (as corrected in review, 4c78ea1): `Job.request` records the
`RipRequest` `start` accepted, and `JobController.retry(id:settings:)`

## Gotchas

- **`"opticaldisc.fill"` could not be confirmed to exist** without running
  the app (no compile-time validation of `NSImage(systemSymbolName:)`
  strings, and this subagent never launches the built app). `updateStatus
  Symbol()` is written defensively — it falls back to the known-good
  "opticaldisc" name if the filled variant returns `nil` — but whether the

- **The Cancel confirmation must never be hosted in the popover.**
  `StatusMenuView` lives in a `.transient` `NSPopover`, which a dialog taking
  focus can close, orphaning the dialog. Fixed in review: the popover closes
  first and `AppDelegate` runs an app-modal `NSAlert`. Still to be checked on
  screen (see Resolution notes).
- **`Job` is not `Identifiable`.** Rather than add that conformance (a
  behavior-neutral but still real change to a type several other tickets
  depend on), `JobHistoryView`'s `List` uses the explicit
  `List(rows, id: \.id, selection:)` form.
- **`JobState.progress` has no public mutator outside `Codable` decoding** —
  `JobPresentationTests`' determinate-progress fixture builds a `JobState`
  through `JSONDecoder` rather than any production code path, since
  `advancing(to:)` always resets `progress` to `nil` (#0041: no progress
  parser exists yet). Noted in the test file itself so a future reader
  doesn't mistake it for a real `DVDPipeline` code path.

## Long Description

The Phase 3 demo ends with "the queue view shows what happened in what order" (`Roadmap.md:141`), which is the acceptance criterion for this ticket. The view is genuinely the proof of the phase: two rows, one `encoding` and one `ripping`, at the same moment, is the only way to see that [#0044](0044.md)'s lanes work.

Three surfaces change:

- A new **queue window** — the list of jobs with stage, progress and elapsed time, a detail pane for the selected job's log, and per-job Cancel and Retry.
- The **menu bar popover**, which currently hardcodes an idle string and gates its Open… row on `settings.isConfigured` (`Changeover/StatusMenuView.swift:16-18`, `:37`). It becomes a live summary and gains a Queue… row.
- The **metadata window**, which sheds its log pane and its `isProcessing` gating. Pressing Start hands the job to the queue and the window's job is done.

## Steps to reproduce

1. Start a job and close the metadata window.
2. Look for progress anywhere in the app.
3. Start a second job, then try to see both.
4. After a job finishes, try to read its log.

## Expected behavior

A queue window lists every job oldest-first with its stage, its own progress, and elapsed time, updating live. Two concurrent jobs show as two rows in different stages. Selecting a row shows that job's log, including for jobs that finished earlier in the session, with a note when earlier lines were dropped. Failed jobs show the actual reason and a Retry; running jobs show Cancel. The menu bar popover summarises the queue at a glance and opens the window.

## Actual behavior

Closing the metadata window takes the only progress display with it. The log array is `@State` in that view (`Changeover/MetadataEntryView.swift:8`) and is cleared at the start of every job (`:146`), so nothing survives. The popover shows "Idle — insert a DVD to begin" during an active rip. There is no cancel, no retry, and no per-job anything, because there are no jobs as such.

### The view

```swift
struct QueueView: View {
    @Environment(JobQueue.self) private var queue
    @State private var selection: JobID?
    var body: some View { /* List(queue.jobs, selection: $selection) + detail */ }
}
```

`@Environment(JobQueue.self)`, matching how `AppSettings` is read today (`Changeover/MetadataEntryView.swift:4`, `Changeover/StatusMenuView.swift:5`). The view model, if one is needed at all, is owned with `@State` — never `@StateObject`, never `ObservableObject`; `Plan.md`'s conventions are binding and the whole project already follows them.

`AppDelegate` gains `queueWindow` alongside `metadataWindow` and `settingsWindow` (`Changeover/AppDelegate.swift:13-14`) and a `showQueue()` copying the shape of `showMetadataEntry()` (`:69-93`) — reuse if visible, `NSHostingView`, `isReleasedWhenClosed = false`, `.environment(settings)` plus `.environment(jobQueue)`. A wider default than the metadata window's 480×580; roughly 720×520 for a list-plus-detail layout.

### Row identity and observation

`List(queue.jobs, selection: $selection)` works because `Job` is `Identifiable` on `JobID` ([#0041](0041.md)), which is stable across pruning — unlike the array-offset identity the log pane uses today (`Changeover/MetadataEntryView.swift:99`), which shifts under eviction.

The observation shape matters for a view updating under a two-process line rate. `Job` is an `@Observable` class, so a row reading `job.state` re-renders when *that* job changes and the list does not. Preserve that: pass the `Job` into `JobRow` and read its properties inside the row body. Reading `job.state` in `QueueView.body` to build the rows would make every progress tick on either job invalidate the whole list — the exact thing the reference-type choice in [#0041](0041.md) was made to avoid.

### The log pane

`JobLogView` renders `job.log.lines` from [#0043](0043.md), keyed on `LogLine.id` — the monotonic counter, not the offset. When `job.log.droppedCount > 0`, a header row reads "… 14,332 earlier lines dropped". Keep the autoscroll behaviour from the existing pane (`Changeover/MetadataEntryView.swift:110-114`) but pin it only when the user is already at the bottom; yanking the view down while someone is reading a failure ten thousand lines back is worse than no autoscroll. Milestone lines render in the primary colour, ordinary lines secondary, so the shape of a job is legible from a scrollbar's distance.

### Risks

- **Log rendering under two concurrent processes.** The existing pane rebuilds `Array(logLines.enumerated())` on every append (`Changeover/MetadataEntryView.swift:99`). With two jobs producing lines, rendering the selected job's log must be a `LazyVStack`/`List` over an identified collection with no per-frame array transformation. If it still stutters, the fix is the batching noted in [#0043](0043.md), not a smaller cap.
- **Do not gate the queue window on `settings.isConfigured`.** The Open… row is gated that way today (`Changeover/StatusMenuView.swift:37`) and it is right for starting work — but a user whose settings broke mid-session still needs to see why their jobs failed.
- **Retry semantics.** Retry on a failed job should enqueue a **new** `Job` with a new `JobID` carrying the same `RipRequest`, not resurrect the old one — the transition table forbids leaving a terminal stage ([#0041](0041.md)), and the failed job is the history record. A retry of a job that failed during rip additionally requires its disc to be back in the drive, so it must check the `DiscToken` ([#0045](0045.md)) and explain itself rather than failing instantly with `discRemoved`.
- **Window lifetime.** `isReleasedWhenClosed = false` as the other two windows do (`Changeover/AppDelegate.swift:89`, `:117`); with `LSUIElement = YES` there is no Dock icon to reopen from, so a released window is a window the user cannot get back.
