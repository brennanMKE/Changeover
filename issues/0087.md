# 0087 — iOS client loses its connection when backgrounded and never re-syncs

| | |
|---|---|
| **Status** | open |
| **Phase** | 5 — iPhone and iPad clients |
| **Module** | RemoteClient |
| **Platform** | iOS · iPadOS |
| **First seen** | 2026-09-11 |

## Description

On iOS the app gets suspended, the TCP connection to the host dies, and nothing
brings it back. Reopening the app shows stale state — a progress bar frozen
where it was when the phone went in a pocket — with no indication that the client
lost touch with reality.

## Long Description

This is the single largest behavioral difference between the macOS client from
Phase 4 and the iOS client, and it is materially harder than it sounds.

A Mac client's connection survives almost everything short of sleep. An iOS app
is suspended within seconds of leaving the foreground; sockets are torn down,
timers stop, and `async` sequences awaiting `connection.messages` simply never
resume. On return to foreground the app finds a dead connection and, worse, an
`@Observable` client object still holding the last `JobState` it saw — which the
UI renders confidently and incorrectly.

The workflow makes this the normal case, not an edge case. `RemoteControl.md`'s
intended loop has the user walk to the mini, insert a disc, and walk back — with
the phone in a pocket for that entire interval. Then the encode runs for tens of
minutes. The app is going to be suspended during every single job.

Phase 4 already defines the recovery mechanism: the `subscribe` → `state` +
`discInfo` + `logReplay` handshake, which `RemoteControl.md` describes as making
recovery clean. What is missing on iOS is everything around it — knowing when to
re-subscribe, what to do with the stale state in the meantime, how to avoid
reconnect storms, and how to handle the case where the job finished while the app
was dead.

The Wi-Fi story compounds it. A phone on a couch roams between bands, drops to
cellular when Wi-Fi is weak, and rejoins. Each transition kills the connection
independently of app lifecycle.

## Steps to reproduce

1. Complete [#0081](0081.md) and have Phase 4's transport working.
2. Start a rip from the iPhone and watch the log stream.
3. Background the app and lock the phone.
4. Wait five minutes.
5. Unlock and reopen the app.

## Expected behavior

The client immediately shows that it is reconnecting rather than presenting stale
data as current. It re-establishes the connection, re-subscribes, receives the
current `JobState`, the current `DiscInfo` and the log backlog, and the UI
catches up within a second or two. If the job finished while the app was
suspended, the completion is shown on foreground.

## Actual behavior

The connection was torn down at suspension and is not re-established. The UI
shows the last `JobState` received before backgrounding — a progress figure that
has not moved — with no staleness indicator. Commands sent from this state fail
silently or are written to a dead socket.

## Notes

The stale-state problem is worse than the disconnection problem. A client that
obviously says "disconnected" is annoying; a client that silently shows a frozen
progress bar and accepts a Start tap that goes nowhere is a bug that costs the
user a disc.

Wi-Fi transitions and app lifecycle are two independent causes of the same
symptom and must both be handled. Testing only the lifecycle case leaves the more
common one — a phone roaming on a home network — uncovered.

This ticket is likely to surface gaps in Phase 4's protocol. If `subscribe` does
not return enough to fully reconstruct the UI, or if there is no way to ask "is
this the same job I was watching", that is a `ChangeoverProtocol` change and
should go back to [#0060](0060.md) rather than being worked around in the client.
Start this ticket early in the phase for that reason.

## Plan

### 1. Model the connection as explicit state, not as a socket that happens to exist

Phase 4's client object mirrors host events into `@Observable` properties. Add a
connection phase alongside them, as a real enum:

`.idle` → `.discovering` → `.connecting` → `.subscribing` → `.connected` →
`.reconnecting(attempt:)` → `.failed(reason)`

Everything in the UI reads from this. There is no view that renders job state
without also knowing the connection phase, because rendering a `JobState`
without knowing whether it is current is the defect in Actual behavior.

The client object is `@Observable`, owned at the app root with `@State`, and
`@MainActor` by default under the project's
`SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` setting
(`Changeover.xcodeproj/project.pbxproj:416`, `:445`). Do not write it as an
`actor` — `Plan.md`'s convention table is explicit that types with no reason to
leave the main actor stay on it, and the receive loop can be a `Task` that hops
back with `Task { @MainActor in ... }`, exactly as the existing log callbacks do
(`Changeover/DVDPipeline.swift`, `Changeover/RipController.swift`).

### 2. Mark received state with when it was received

Give the mirrored `JobState` a received-at timestamp. On foreground, before the
re-subscribe completes, the UI renders the last known state **visibly dimmed and
labelled** ("as of 4 minutes ago — reconnecting"). That is a small amount of code
and it is the difference between a client that is merely disconnected and one
that lies.

Clear it — do not keep showing it — if reconnection fails outright.

### 3. Drive the lifecycle off `scenePhase` and a path monitor

Two independent triggers:

- `@Environment(\.scenePhase)`: on `.background`, stop the receive loop
  deliberately and mark the connection stale rather than letting it die
  unobserved. On `.active`, always attempt reconnect-and-resubscribe — do not try
  to determine whether the existing connection is still good. Probing a possibly
  dead socket is slower and less reliable than reconnecting.
- `NWPathMonitor` (or the equivalent on Phase 4's transport abstraction): a
  path change to unsatisfied tears down; a change back to satisfied triggers a
  reconnect. This covers the Wi-Fi roaming case that `scenePhase` never sees.

Both funnel into one `reconnect()` entry point that is idempotent — concurrent
calls from both triggers are the normal case, and a second call while one is in
flight must be a no-op, not a second connection.

### 4. Backoff, and a bound on it

Exponential backoff with jitter, capped — roughly 0.5s, 1s, 2s, 4s, 8s, then
every 15s. Reset the counter on a successful subscribe. Without a cap and jitter,
a host that is genuinely down produces a battery-draining tight loop, and two
clients reconnecting in lockstep hammer the listener.

Suspend retries entirely while in `.background`; there is no point burning the
background window on connection attempts when [#0086](0086.md) may need it.

### 5. Re-subscribe and reconcile, including the job that finished while dead

On reconnect, send `subscribe` and handle the reply:

- `RemoteEvent.state(JobState)` — replace wholesale. Never merge; the host is the
  single source of truth per `RemoteControl.md`'s architecture.
- `RemoteEvent.discInfo(DiscInfo)` — replace. If the disc changed while the app
  was suspended, any in-flight title selection from [#0084](0084.md) is invalid
  and must be discarded with a visible explanation, not silently reset.
- `RemoteEvent.logReplay([String])` — replace the buffer, then resume appending
  from `RemoteEvent.log`. Do not append the replay to what is already there or
  the log doubles on every reconnect.

The case that needs specific handling: **the job the user was watching finished
while the app was suspended.** The client must recognize that the job id it was
tracking is now terminal and surface the completion on foreground, which is the
fallback path for [#0086](0086.md)'s undeliverable notification. This requires
stable job IDs from Phase 3 ([#0040](0040.md)) — without them, "is this the same
job" is unanswerable.

### 6. Commands sent from a stale client must fail loudly

Any `RemoteCommand` issued while not `.connected` is rejected locally with a
visible message. Do not queue commands for later delivery — a `startRip` that
fires three minutes late, against a disc that has since been swapped, is the
worst possible outcome and is exactly what naive offline queuing produces.

`RemoteControl.md` already specifies that the host rejects commands invalid for
the current state with a reason; the client should render that rejection rather
than assuming its own optimistic outcome.

### 7. Ordering

Connection phase enum and stale marking first — they are small and they make
every subsequent behavior observable while developing. Then `scenePhase`
handling, then `NWPathMonitor`, then reconcile, then command rejection. Do not
start with backoff tuning; it is the least important part and the most tempting
to fiddle with.

### 8. Risks

- **Protocol gaps in Phase 4.** Most likely: no job id in `JobState`, or
  `logReplay` with no bound so a long encode's backlog is enormous. Both are
  [#0060](0060.md) changes. Check the protocol before writing client code.
- **Log replay size.** `RemoteControl.md` specifies a capped ring buffer on the
  host. Confirm the cap is small enough that a replay over Wi-Fi on a reconnect
  loop is not seconds of transfer each time.
- **Reconnect storms across multiple clients.** Jitter matters; without it, a
  Mac and a phone reconnecting after a host restart sync up.
- **Testing this properly is slow.** Each real test is a multi-minute wait. Build
  a debug affordance to force a disconnect so the reconnect path can be exercised
  in seconds; without it, this ticket will be under-tested.

### 9. Verification

Split honestly:

- **Unit-testable, and the bulk of the correctness:** the connection phase state
  machine, backoff sequence and cap, idempotent `reconnect()`, the reconcile
  logic for `state` / `discInfo` / `logReplay` (especially that replay replaces
  rather than appends), discarding a stale title selection, and rejecting
  commands when not connected. All of this is pure logic over Phase 4's protocol
  types and should have real tests — this is precisely where the project's
  verification caveat says "tests must actually run" applies literally.
- **Simulator-verifiable:** `scenePhase` transitions, the stale-state UI, and the
  debug forced-disconnect path.
- **Device- and host-bound, non-negotiable:** the actual acceptance test is a
  real iPhone against the real mini — start a rip, pocket the phone for ten
  minutes, reopen, and confirm the client catches up within a second or two with
  a correct log and correct progress. Then: kill the app entirely mid-job and
  relaunch. Then: toggle Airplane Mode mid-job. Then: restart the host mid-job.
  A simulator reproduces none of these faithfully. The `## Verification` section
  must list each of these four as a manual device run with what was observed.
