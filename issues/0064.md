# 0064 — Transport security mechanism is undecided between TLS-PSK and identity pinning

| | |
|---|---|
| **Status** | open |
| **Phase** | 4 — Remote control from a Mac |
| **Module** | Transport / Pairing |
| **Platform** | All |
| **First seen** | 2026-09-11 |

## Description

`RemoteControl.md` leaves the transport security mechanism as "decide during implementation", with two options that have materially different consequences: TLS-PSK from the shared pairing key is simple but is **TLS 1.2 only** on Apple platforms, while a self-signed host identity with client-side fingerprint pinning keeps TLS 1.3 at the cost of more code. This must be decided, written down and implemented before either pairing mode can produce a usable connection.

## Long Description

This is the decision every other security ticket in the phase hangs off. Pairing
([#0065](0065.md), [#0066](0066.md)) produces key material; the peer registry
([#0067](0067.md)) stores it; the server ([#0068](0068.md)) gates accept on it. What
*form* that key material takes — a pre-shared secret versus a pinned certificate
fingerprint plus a client identity — is decided here, and getting it wrong means
redoing all four.

**Option A — TLS-PSK from the shared key.** The pairing key is the PSK; the identity
hint carries the peer ID. Very little code. The caveat is not cosmetic: **PSK on
Apple platforms is TLS 1.2 only** — TLS 1.3 PSK is not supported by
`Network`/`Security` (Apple Developer Forums thread 688508) — so the TLS options
must pin `min = max = .TLSv12` explicitly. If the version is not pinned and the
handshake negotiates 1.3, the PSK path fails in a way that reads as a connection
error rather than a configuration error. Shipping a TLS-1.2-only product surface in
2026 is also a thing to be able to justify out loud, and the justification here is
reasonable — it is a LAN-local link between two devices that have already
authenticated each other out of band — but it should be a recorded decision, not an
accident.

**Option B — self-signed identity plus fingerprint pinning.** The host generates a
P-256 identity on first launch and stores it in the Keychain; the client records the
SHA-256 fingerprint of the host certificate at pairing time and refuses anything
else thereafter. Keeps TLS 1.3. Requires writing `sec_protocol_options_set_verify_block`
(or the Swift `TLS` equivalent), generating a self-signed cert, and — importantly —
solving *client* authentication separately, since pinning only authenticates the
host to the client, not the client to the host. Mutual authentication needs either
client certificates issued at pairing or an in-band authentication message after the
TLS handshake, signed with the pairing key.

There is a third option worth naming rather than discovering halfway through:
**TLS 1.3 with server identity pinning, plus an in-band mutual-auth challenge over
the encrypted channel** using the pairing key (host sends a nonce, client returns
HMAC(pairingKey, nonce ‖ transcript-binding value), host verifies and vice versa).
This keeps TLS 1.3, avoids issuing client certificates, reuses the same symmetric
key both pairing modes already produce, and makes the capability lookup in
[#0067](0067.md) fall out naturally because the peer ID is carried in the challenge
response. It is more code than Option A and less than full mutual TLS.

## Steps to reproduce

1. Read the "Transport security" section of `RemoteControl.md`.
2. Try to write the `TLS()` configuration block shown in the protocol sketch.
3. Observe that neither the key material format nor the TLS version is determined.

## Expected behavior

One mechanism is chosen, the reasoning is recorded, and `BonjourAdvertiser` /
`BonjourDiscoverer` from [#0062](0062.md) configure TLS accordingly — with the
version explicitly pinned if PSK is chosen, and with a verify block that actually
rejects a mismatched fingerprint if pinning is chosen.

## Actual behavior

Undecided. The sketch shows a bare `TLS()` with no parameters, which would give an
unauthenticated or system-trust-store TLS session — neither of which authenticates
anything on a LAN with self-signed or absent certificates.

## Plan

**Step 1 — establish the facts against the SDK, the same way [#0063](0063.md) does.**
Confirm in the installed SDK what the structured-concurrency `TLS` type actually
exposes before choosing:

```bash
SDK=$(xcrun --sdk macosx --show-sdk-path)
grep -rn "struct TLS\|psk\|preSharedKey\|verifyBlock\|minVersion\|maxVersion" \
  "$SDK/System/Library/Frameworks/Network.framework/Modules/Network.swiftmodule/"*.swiftinterface
```

If the new `TLS` type does not surface PSK or a verify block, the options must be
reached through `NWProtocolTLS.Options` / `sec_protocol_options_*`, which is a point
in favour of the approach that needs fewer knobs. Record what is found; do not
assume the modern wrapper exposes everything the C API does.

**Step 2 — write the decision down before writing code.** Add
`Docs/TransportSecurity.md` to the package from [#0062](0062.md) recording: the
option chosen, what authenticates the host to the client, what authenticates the
client to the host, which TLS version is negotiated, where key material lives, and
what happens on mismatch. A future reader must be able to answer "what stops an
unpaired Mac on this network from starting a rip?" from that one file.

**Step 3 — recommendation, to be confirmed or overridden by the spike.** Prefer the
third option: **TLS 1.3 with host identity pinning plus an in-band mutual
authentication challenge keyed on the pairing secret.** Reasons specific to this
project:

- It does not strand the product on TLS 1.2 for the life of the app.
- It keeps a single symmetric pairing key as the only secret, which both
  [#0065](0065.md) and [#0066](0066.md) already produce, and avoids a second
  credential type (client certs) with its own lifecycle and revocation story.
- The challenge response is the natural place to carry the peer ID that
  [#0067](0067.md) needs for the capability lookup, so authorization is not a
  separate round trip.
- It is testable: the challenge/response is pure computation over `CryptoKit` and
  can be unit-tested against the in-memory transport from [#0062](0062.md) with no
  TLS at all.

If the spike shows the verify-block path is not reachable from the modern API and
falling back to `NWProtocolTLS.Options` is disproportionate, take Option A — but
then pin `min = max = .TLSv12` in code with a comment citing the PSK limitation, and
say so in `Docs/TransportSecurity.md` so nobody later "modernizes" the version pin
and breaks the handshake.

**Step 4 — implementation.** Whatever is chosen:

- Key material never touches `UserDefaults`. Note that `AppSettings.persist()`
  (`Changeover/AppSettings.swift:48-54`) already writes the TMDB API key to
  `UserDefaults` in plaintext at `:53`; that is a pre-existing weakness, and it is
  the pattern that must **not** be copied for pairing keys. Pairing secrets go in
  the Keychain via [#0067](0067.md).
- Use `CryptoKit` (`SymmetricKey`, `HKDF`, `HMAC<SHA256>`) rather than hand-rolled
  key handling.
- Compare all authentication tags in constant time. `CryptoKit`'s
  `HMAC.isValidAuthenticationCode(_:authenticating:using:)` does this; `==` on
  `Data` does not.
- The failure path must be a clean, logged rejection with a distinct reason
  (`RejectionReason.notPaired`, `.authenticationFailed`, `.wireVersionMismatch`)
  from [#0061](0061.md) — not a dropped connection. A client that cannot tell
  "wrong key" from "host went away" cannot show a useful error, and will retry
  forever ([#0072](0072.md)).
- Rate-limit authentication failures per source address so a hostile LAN peer
  cannot grind the challenge.

**Ordering.** Do this early — it is cheap to decide and expensive to change. It
blocks the useful parts of [#0065](0065.md), [#0066](0066.md), [#0067](0067.md) and
[#0068](0068.md), all of which can be scaffolded in parallel but not finished.

### Plan refresh (2026-09-15)

**Facts established from the SDK. Step 1 is done.**

- The modern `TLS` builder (`Network.swiftmodule/arm64e-apple-macos.swiftinterface`,
  `public struct TLS`) exposes:
  - `localIdentity(sec_identity_t)`
  - `certificateValidator(@Sendable (sec_protocol_metadata_t, sec_trust_t) async -> Bool)`
  - `peerAuthentication(.none/.optional/.required)`
  - `version(min:max:)`
  - `cipherSuites`, `applicationProtocols`, `ticketsEnabled`, `earlyDataEnabled`

  It has **no PSK**.
- PSK exists only in the C API, `sec_protocol_options_add_pre_shared_key`
  (`Security.framework/Headers/SecProtocolOptions.h:373`). It is reachable through
  `NWProtocolTLS.Options`, meaning the legacy parameters path.
  `NWParametersBuilder.parameters(initialParameters:)` might carry it into the
  modern stack, but that is unverified. Apple's PSK support is TLS 1.2 only.
  **Option A is therefore rejected.**
- Also present:
  - `sec_protocol_metadata_create_secret`, a TLS keying-material exporter
    (`SecProtocolMetadata.h:387`), usable for channel binding.
  - `sec_protocol_metadata_access_peer_certificate_chain` (`:206`).
  - `SecIdentityCreateWithCertificate` (`SecIdentity.h:82`, macOS).
  - `sec_identity_create` (`SecProtocolTypes.h:221`).
- **No public Security API builds a self-signed X.509 certificate.** One must be
  generated some other way (decision D-E in [#0060](0060.md)).
- `RemoteControl.md` chose "server identity pinning + in-band
  `HMAC(pairingKey, nonce ‖ SHA-256(server cert))`". That keeps a **shared
  symmetric key** as the client credential. In Mode A every device on the Apple ID
  holds the same key, so no per-device revocation is possible, and the peer ID
  becomes whatever the client claims.

**Recommendation for decision D-A: mutual TLS 1.3 with per-install self-signed
P-256 identities, pinned by SHA-256 of the SubjectPublicKeyInfo.**

This supersedes Step 3's "third option". There is no post-handshake HMAC challenge
and no symmetric link key.

- **Identity.**
  - Each install creates one long-term P-256 key plus a self-signed certificate:
    the host when remote control is first enabled, a client at first launch.
  - The private key is a non-exportable Keychain key.
  - Accessibility must allow a **locked, headless mini** to keep serving after
    reboot. `…WhenUnlocked…` would stop the listener whenever the screen locks, so
    use `AfterFirstUnlockThisDeviceOnly`. S2 must confirm how that maps onto the
    macOS file-based vs data-protection keychain for an unsandboxed, automatically
    signed build.
  - The certificate comes from `apple/swift-certificates` (recommended) or
    `/usr/bin/openssl` + `SecPKCS12Import`. Never hand-assembled DER.
- **Host TLS:**
  - `localIdentity(hostIdentity)`
  - `peerAuthentication(.required)`
  - `version(min: .TLSv13)`
  - A `certificateValidator` that accepts any **structurally valid self-signed
    P-256 leaf**, computes `CertificateFingerprint`, and hands it to the channel as
    `PeerIdentity` ([#0062](0062.md)).

  Authorization happens *after* the handshake, in [#0068](0068.md). An unknown
  fingerprint gets a `notPaired` refusal and is closed. Rejecting inside the
  validator would give the client an opaque TLS alert instead of a reason
  ([#0072](0072.md) needs terminal reasons).
- **Client TLS:**
  - `localIdentity(clientIdentity)`
  - `version(min: .TLSv13)`
  - A `certificateValidator` that returns true **only** when the server leaf's
    fingerprint equals the pinned host fingerprint.
  - During pairing, the validator instead checks the pairing code's commitment
    ([#0066](0066.md)).
  - A mismatch after pairing is the terminal state "host identity changed — pair
    again", and is never silently re-pinned.
- **What stops an unpaired Mac from starting a rip:** its fingerprint is not in
  `PeerRegistry` ([#0067](0067.md)), so every command, including `subscribe`, is
  refused with `notPaired`, and it never receives `HostState`. Record this sentence
  in `Docs/TransportSecurity.md`.
- **Revocation** removes a fingerprint. Live connections close with `revoked`.
  "Reset all pairings" also regenerates the host identity.
- **Rate limiting.** A pure `AttemptLimiter` keyed by remote address, with an
  injected clock, covering failed authorizations and pairing attempts.
- **Carried forward:**
  - Key material never goes in `UserDefaults`. `AppSettings.persist()` writes the
    TMDB key at `AppSettings.swift:86`; the Plan's `:48-54`/`:53` references are
    stale.
  - Constant-time `HMAC.isValidAuthenticationCode` wherever a secret-derived tag is
    checked (pairing).
- **Unsafe variants to refuse in review:**
  - A bare `TLS()`.
  - `certificateValidator { _, _ in true }` on the client.
  - Any PIN-derived PSK.
  - A peer ID taken from a message field.
  - A "LAN only" plaintext mode.

**Where the code lives**

- `ChangeoverTransport/Security/`:
  - `CertificateFingerprint.make(spkiDER:)` and `.make(certificateDER:)` (pure).
  - `PinPolicy.evaluate(presented:pinned:mode:) -> PinDecision` (pure).
  - `protocol DeviceIdentityStore` (`loadOrCreate() throws -> DeviceIdentity`).
- The Keychain-backed implementation goes in the app target or transport target
  after S2.
- `TLSStack.host(identity:)` / `.client(identity:pin:)` builders (Part B, after S2).

**Spike S2** (one Mac, cameron or gordon, **loopback only**; not in the routine
suite). A throwaway scratchpad executable that:

1. Creates a host and a client identity (via D-E's mechanism) and imports them into
   the Keychain.
2. Runs a `NetworkListener` on `127.0.0.1` with the host stack and a
   `NetworkConnection` with the client stack.
3. Confirms the **server-side** `certificateValidator` receives the client leaf and
   can compute its fingerprint.
4. Confirms a client with a wrong pin fails with a distinguishable error, and a
   server that refuses leaves a client error distinguishable from a network error.
5. Confirms `sec_protocol_metadata_create_secret` can be obtained on both ends for
   channel binding (needed by [#0066](0066.md)). If not, record that and fall back
   to binding both fingerprints plus nonces.
6. Records the Keychain prompts seen on a re-signed Debug build, and whether
   loopback triggers the Local Network or firewall prompt. The expectation is
   neither; confirm it.

Results go into `Docs/TransportSecurity.md`.

**Unit tests** (in `ChangeoverTests` via `./run-remote-tests.sh gordon`; no TLS
and no sockets):

- Fingerprints of fixture certificate DER files, as golden values.
- The `PinPolicy` table: pinned match, mismatch, pairing-mode commitment, unpinned
  outside pairing.
- An unknown fingerprint maps to `notPaired` over `InMemoryTransport`.
- `AttemptLimiter` windows on an injected clock.

**Needs two real Macs:**

- The TLS 1.3 handshake over Wi-Fi.
- The negative test: replace the client identity on the MacBook and confirm the
  host refuses with `notPaired`, not a hang.
- A host identity reset shows the client's terminal "host identity changed" state.

## Notes

**Unit-testable without hardware:** key derivation, the challenge/response
construction and verification, constant-time comparison behaviour, the rejection
reason produced for each failure class, and the rate limiter. Run these against the
`InMemoryTransport` from [#0062](0062.md).

**Requires two real machines:** that the chosen TLS configuration actually completes
a handshake over the wire, and — critically — that a peer holding the *wrong* key is
refused. The negative test matters more than the positive one and is easy to skip:
pair machine A, then edit the stored key on machine A and confirm the host rejects
it with `.authenticationFailed` rather than connecting.

**A note on threat model, since it is not written down anywhere yet.** The realistic
attacker is another device on the same home LAN — a guest's laptop, an IoT device, a
compromised browser on the same subnet. The asset is write access to the Plex media
library and the ability to spawn `makemkvcon` / `HandBrakeCLI` processes on an
**unsandboxed** host (`ENABLE_APP_SANDBOX = NO`, `project.pbxproj:402` and `:431`).
That is a meaningfully higher-value target than "someone watches a rip log", and it
is the reason this ticket exists separately rather than being a line in
[#0068](0068.md).

## Decision (user, 2026-09-15)

> **Mutual TLS 1.3 with pinned self-signed keys**, each Mac's key pinned by fingerprint after pairing. TLS pre-shared keys are rejected (legacy TLS 1.2 API only).
