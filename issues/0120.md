## Description

Umbrella for Phase 7 — define short clips from movies in the library and play them as scheduled, looping montages on displays around the living space. **This phase is deliberately not broken down yet**: its design is still open and depends on conventions that Phases 1–3 will settle.

## Long Description

Montages are a *second product built on the same media repository* as the DVD ripping workflow, not a feature of the ripper. The ripping pipeline already produces what a montage system needs — a local library of owned video files with structured metadata (title, year, TMDB ID) at predictable paths.

Two pieces of planned work feed it directly:

- **Disc title selection** ([#0020](0020.md)) exposes every title on a disc, not just the main feature. Bonus features, alternate scenes and menu loops become available as clip sources. [#0031](0031.md) goes further and actually puts them on disk: extras rip to `<root>/Clips`, grouped by `Title (Year) {tmdb-ID}` and deliberately outside the Plex roots so Plex does not index them. That is a clip source library arriving as a side effect of ripping, at predictable paths, for 0.4–52% extra disk per disc (measured — see that ticket). It leaves `Montages.md` question 5 ("does this need discs at all?") untouched; it just makes the disc-sourced half exist.
- **The remote client codebase** ([#0060](0060.md), [#0080](0080.md)) is already a "browse the library, make a selection, send it to the host" app. A clip editor is the same shape.

The full design sketch, open questions and playback-target analysis live in `Montages.md`. That document — not this ticket — is the working reference.

## Why this is not broken down yet

`Roadmap.md` defers Phase 7 planning until Phases 1–3 have settled the library and repository conventions it builds on. Breaking it into child tickets now would encode guesses about storage layout, job model and library structure that the earlier phases are still deciding.

Several first-order design questions are genuinely unresolved, and the answers change the shape of every child ticket:

1. **Virtual clips, rendered clips, or both?** Virtual clips (source file + in/out points) are ideal for editing and useless for distribution — a Raspberry Pi cannot evaluate an `AVComposition`. Rendered clips plus a manifest are the common denominator every playback target can consume.
2. **Does v1 need a custom player at all?** Rendering each montage as a single long `.mp4` into a Plex "Montages" library needs no playback client whatsoever — Plex already streams to Apple TV and browsers. Far less code, far less flexible. This is probably the right v1 and would collapse most of the phase.
3. **How are clips marked?** Scrubbing to find the right 20 seconds is the actual work. A good in/out-point UI with keyboard shortcuts and thumbnail scrubbing is the difference between this being fun and being a chore — **this is the make-or-break piece**, and if it is unpleasant the feature dies regardless of how good the playback is.
4. **Audio.** Original audio across a montage is a jarring cut every 20 seconds. Music bed with clips muted? Per-clip choice? This affects rendering.
5. **Does this need discs at all?** Clips could be marked from any file in the Plex library regardless of provenance, which argues for a library-oriented tool rather than a disc-oriented one.

## Expected behavior

Per `Roadmap.md`, the Phase 7 demo is:

> Mark five clips from movies in the library. Build a montage from them. Put it on a display on a loop. Change the active montage from a phone and watch the display switch.

## Actual behavior

No clip model, no marking UI, no playback. Nothing implemented.

## Notes

**Next action for this ticket is not implementation — it is planning.** Once Phase 3 ([#0040](0040.md)) is complete, re-read `Montages.md` against whatever the library and job conventions actually became, resolve at least questions 1–3 above, and then break this umbrella into child tickets in the 0121–0139 block.

Longer-term playback targets under consideration, in rough order of likelihood: a Mac driving a display, an Apple TV (tvOS) app, Raspberry Pi–driven displays, and a plain browser. All except the Mac need rendered clips served over HTTP — and `RemoteControl.md` independently contemplates an HTTP surface as a web fallback. If both land they should share one server rather than standing up two.

On distribution: a montage feature that exports clips from commercial films is a redistribution surface in a way that a personal Plex library is not. Keeping everything local by default — no sharing, no upload, no cloud — is both the simpler design and the safer one.
