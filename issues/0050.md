1. **The guard is complete.** Production has exactly two defaults that reach `DiscEjector.eject`: `DVDPipeline.eject` and `JobController.defaultEjector`. Both now go through `defaultEject`. `pipelineRunner` passes `context.eject`, which `start` binds to the controller's `ejector`. The automatic end-of-job eject, the manual Eject row (`ejectDisc`) and a `JobController` built with no `ejector:` therefore all end at the guarded default. `AppDelegate` never calls `DiscEjector` directly. All 47 test `DVDPipeline(` sites set `eject`: 46 use `fakeEject` and one uses its own scripted fake. No test uses a default-ejector `JobController` in a way that reaches the ejector. The only test that calls `ejectDisc` without injecting one (`JobControllerHistoryTests.betweenJobTrafficAfterAFinishedJobNeverLandsInItsRetainedLog`) first removes the disc, so `EjectPolicy` refuses before the ejector runs, and the guard would catch it anyway. The only remaining direct `eject` calls are the deliberate ones in `DiscEjectorIntegrationTests`, plus `defaultEjectCallsThroughWhenNotUnderATestHost`, which uses a never-mounted `/Volumes/…` path. A separate "no real ejector reachable" helper isn't warranted.
2. **Correction to the draft and to Expected behavior: a forgotten fake is visible, but it does not fail the test.** The guard returns `.failed("real ejector called from tests")`. `DVDPipeline.run()` logs it as `⚠︎ real ejector called from tests` in the job log, and the job still ends `.succeeded`, by #0005's design that a failed eject never fails a job. A future test that omits the fake gets a clearly labeled refusal in its log and no system call, but it passes unless it asserts on eject log lines. That is enough to close the hole. Routing tests through a pipeline factory was judged not worth the churn, since every current site is covered.
3. **Production safety.** `XCTestConfigurationFilePath` is set only by XCTest. The shipped app already relies on the same key in `LoginItemPolicy` (#0019) and `JobNotifier`. Outside a test host, `defaultEject` calls `eject(volumeURL:onBegin:)` with the same arguments as before, so the real eject path is unchanged.
4. **`DiscEjectorIntegrationTests` are safe on gordon.** They eject only a 10 MB HFS+ image each test creates with `hdiutil create` and attaches with `-nobrowse` at `/Volumes/ChangeoverEjectorTest<4 random digits>`, or a `/Volumes/…` path that was never mounted. They never address an optical drive. One theoretical edge, noted and not changed: if a volume with the same random name were already mounted, `hdiutil` would mount the image under a suffixed name, and the test would eject the pre-existing volume. The name makes that practically impossible.

## Description

Found in the #0049 review. `DVDPipeline`'s injectable `eject` defaults to the real `DiscEjector`, and existing pipeline tests (for example the extras, fallback and cancellation suites) construct pipelines without overriding it. A successful test job therefore runs a real DiskArbitration unmount/eject request against a temp directory path on the test host. Today that fails harmlessly, because a temp path is not a disc. But it breaks the project rule that tests never touch real drives. On a test host with a disc in its drive, a path that resolves to the wrong volume could eject or unmount something real, and it adds real system calls and latency to unit tests.

## Root cause

`DVDPipeline.eject` and `JobController`'s `Ejector` both defaulted straight
to `DiscEjector.eject(volumeURL:)` — the real `DASessionCreate` /
`DADiskUnmount` / `DADiskEject` path. Roughly 47 existing `DVDPipeline(...)`
construction sites across `DVDPipelineCancellationTests`,
`EncodeControllerTests`, `ExtrasPipelineTests`, `JobStateMachineTests`,
`MakeMKVFallbackTests`, `OutputDurationCheckTests` and `PreflightTests`
never overrode it, and a large fraction of those tests drive a `run()` all
the way to `.succeeded` — the only outcome that reaches the end-of-job
eject step (#0005). Every one of those runs therefore issued a real
`DiskArbitration` unmount/eject request against a temp-directory path.
Harmless today only because a temp directory never resolves to a real
volume (`DADiskCreateFromVolumePath` returns nothing and `classify` maps
that to `.failed`) — but nothing stopped it from resolving to something
real on a test host with a disc actually mounted, and there was no signal
at all if a future test accidentally did reach a real volume path.

## Fix

Two layers, matching the plan:

1. **A guard on the default ejector, not on `eject` itself.**
   `DiscEjector` gains a pure predicate,
   `isTestHost(environment: [String: String]) -> Bool`, checking
   `XCTestConfigurationFilePath` — the exact same key and reasoning
   `LoginItemPolicy.shouldRegister` (#0019) uses for the identical
   app-hosted-test-launch problem. A new
   `defaultEject(volumeURL:environment:onBegin:)` calls it: under a test
   host it returns `.failed(message: "real ejector called from tests")`
   without ever calling `eject(volumeURL:onBegin:)`; otherwise it calls
   straight through. `DVDPipeline.eject`'s default value and
   `JobController.defaultEjector` now both route through `defaultEject`
   instead of `eject` directly.

   **Deliberate deviation from a literal reading of the plan:** the plan
   says "the real `DiscEjector` refuses under a test host." The guard does
   *not* live inside `eject(volumeURL:onBegin:)` itself, because
   `DiscEjectorIntegrationTests` calls that function directly, under the
   same test-host environment, against a disk image it creates and attaches
   itself (the sanctioned, deliberate exception the file's own doc comment
   describes). A guard inside `eject` would have refused that real,
   intentional `DiskArbitration` coverage too — there is no way for `eject`
   to tell "the integration test's own direct, sanctioned call" apart from
   "a pipeline test that forgot to inject a fake and fell through to the
   production default" purely from the process environment, since both run
   under the identical XCTest environment. Guarding only the *default* (the
   thing `DVDPipeline`/`JobController` fall back to when nothing is
   injected) closes the actual hole while leaving the integration test's
   direct call untouched. Verified: with the guard in place, both
   `DiscEjectorIntegrationTests` tests and the four new `DiscEjectorTests`
   guard tests pass in the same run.

2. **Every pipeline-construction test site injects a fake.** All ~46 sites
   across the seven files above now do
   `pipeline.eject = PipelineTestSupport.fakeEject` (or `secondPipeline...`)
   right after constructing the `DVDPipeline` — a new no-op constant in
   `ChangeoverTests/FakeRunnerSupport.swift` that returns `.ejected`
   unconditionally. One `ExtrasPipelineTests` site already injected its own
   scripted fake (`theEndOfJobEjectGoesThroughTheInjectedEjectorAndAPartialEjectIsLogged`)
   and was left as-is. This means these tests no longer rely on the guard
   as their only line of defense — the guard is now purely the safety net
   for a *future* omission, exactly as the plan intends.

   `JobControllerEjectTests`' private `FakeEjector` (records calls, returns
   a scripted `DiscEjector.Outcome`) moved to `FakeRunnerSupport.swift` as
   the shared `RecordingEjector`, so any test that specifically cares about
   the ejected URL or a particular outcome (busy/failed/unmounted-but-not-
   ejected) has one shared implementation instead of a private copy.

   Mechanically: since `DVDPipeline.eject` is a `var` on the struct and
   every one of the ~47 sites already binds `var pipeline = DVDPipeline(...)`
   (never `let`), the fake could be assigned as a post-construction
   mutation rather than threading a new named argument through every
   multi-line initializer call — smaller, more mechanical, and
   easier-to-review diff than editing every argument list.

## Gotchas

- **The mechanical edit relied on every site using `var pipeline = DVDPipeline(...)`.** All ~47 sites already declared the binding as `var`, not `let` — apparently for other reasons (several mutate `pipeline.reliabilityLogURL` the same way) — which is what made the post-construction-assignment approach possible without touching any initializer argument list. If a future site ever used `let`, the same pattern would need a small tweak (change `let` to `var`) rather than a bare insertion.
- **`defaultEject`'s `environment` parameter defaults to `ProcessInfo.processInfo.environment`,** matching `LoginItemPolicy.shouldRegister`'s own default-free design closely but not identically — `LoginItemPolicy` takes `environment` with no default and always requires the caller to pass it explicitly, while `defaultEject` defaults it so `DVDPipeline`'s and `JobController`'s call sites don't have to know about `ProcessInfo` at all. Tests can still inject an explicit environment for the pure-predicate style, or rely on running under the real test host, as demonstrated by the two different guard tests.
- **`DiscEjectorIntegrationTests` was not touched.** It calls `DiscEjector.eject(volumeURL:onBegin:)` directly, never `defaultEject`, so it was never at risk from this change — confirmed by it still passing in the same full-suite run.

## Expected behavior

No unit test can reach the real `DiscEjector`, `diskutil` or DiskArbitration. Tests use a fake ejector by default, and a test that forgets to inject one fails loudly instead of silently calling the real one.

## Plan

- Find every test path that builds `DVDPipeline`/`JobController` with the default ejector (grep the test target for `DVDPipeline(` and `JobController(` without an `eject`/ejector argument).
- Route them through a test-support factory in `ChangeoverTests/FakeRunnerSupport.swift` (or a new `PipelineTestSupport.swift`) that injects a recording fake ejector.
- Add a guard: when running under XCTest, the real `DiscEjector` refuses (logs and returns `.failed("real ejector called from tests")`), using the same test-host detection #0019 uses for login items, and a test asserts the guard. That turns any future omission into a visible failure instead of a real system call.
- Verify with the full suite on gordon, and falsify by removing the fake from one test to confirm the guard trips.
