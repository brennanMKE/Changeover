# 0050 — Pipeline unit tests call the real DiscEjector on temp paths through a production default

| | |
|---|---|
| **Status** | open |
| **Phase** | 3 — Unattended multi-disc |
| **Module** | DVDPipeline / DiscEjector / ChangeoverTests |
| **Platform** | macOS |
| **First seen** | 2026-09-15 |

## Description

Found in the #0049 review. `DVDPipeline`'s injectable `eject` defaults to the real `DiscEjector`, and existing pipeline tests (for example the extras, fallback and cancellation suites) construct pipelines without overriding it. A successful test job therefore runs a real DiskArbitration unmount/eject request against a temp directory path on the test host. Today that fails harmlessly, because a temp path is not a disc. But it breaks the project rule that tests never touch real drives. On a test host with a disc in its drive, a path that resolves to the wrong volume could eject or unmount something real, and it adds real system calls and latency to unit tests.

## Expected behavior

No unit test can reach the real `DiscEjector`, `diskutil` or DiskArbitration. Tests use a fake ejector by default, and a test that forgets to inject one fails loudly instead of silently calling the real one.

## Plan

- Find every test path that builds `DVDPipeline`/`JobController` with the default ejector (grep the test target for `DVDPipeline(` and `JobController(` without an `eject`/ejector argument).
- Route them through a test-support factory in `ChangeoverTests/FakeRunnerSupport.swift` (or a new `PipelineTestSupport.swift`) that injects a recording fake ejector.
- Add a guard: when running under XCTest, the real `DiscEjector` refuses (logs and returns `.failed("real ejector called from tests")`), using the same test-host detection #0019 uses for login items, and a test asserts the guard. That turns any future omission into a visible failure instead of a real system call.
- Verify with the full suite on gordon, and falsify by removing the fake from one test to confirm the guard trips.
