# 0026 — The metadata window shows no disc titles, so there is nothing to choose from

| | |
|---|---|
| **Status** | open |
| **Phase** | 2 — Choose what gets ripped |
| **Module** | MetadataEntryView / DiscTitleListView |
| **Platform** | macOS |
| **First seen** | 2026-09-11 |

## Description

`MetadataEntryView` is a TMDB search window and nothing else — search bar, results
list, folder-name preview, log, `Start Ripping`
(`Changeover/MetadataEntryView.swift:11-26`). It never shows what is actually on the
disc, so the user cannot see fourteen titles, cannot tell which is the movie, and
cannot choose.

## Long Description

This is the ticket the Phase 2 demo is made of: *"The app lists every title with its
duration, chapter count and size, with the main feature already selected by the
length heuristic"* (`Roadmap.md` lines 101–103).

**The experiment shrank it.** `DiscSelection.md` established that on 8 of 9 discs
exactly one title runs 45 minutes or longer *and is the movie*, so the common case
is not a picker at all — it is a **confirmation row**: "Main feature: title 3 · 1:50:45 · 21 chapters ·
6.3 GB", with a way to disagree. The full sortable table is still built, but it
stops being the default view and becomes four other things:

1. **The 2+ fallback.** When [#0025](0025.md) returns `.ambiguous`, the user picks
   between candidates. Untested — no captured disc produced this case.
2. **The 0-title fallback.** When nothing clears 45 minutes, the picker is the only
   thing on screen, with an explicit "this disc did not identify itself" message.
3. **The TV-disc refusal.** When [#0025](0025.md)'s Play All guard fires, there is
   a long title *and it must not be offered as the preselection*. Brooklyn
   Nine-Nine's Play All title is 2:53:18 with 33 chapters and 6.9 GB — it looks
   more like a feature than any real feature in the corpus — so this state is
   defined by what it refuses to do.
4. **The extras opt-in.** [#0031](0031.md) rips extras to a separate destination
   outside the Plex roots. Choosing which extras is a multi-select over the same
   table, off by default.

Designing the table first and the confirmation row second would be backwards. The
row is what the user sees on almost every disc; the table is the escape hatch.

It carries the phase's second exit criterion too, which is a UI requirement as much
as a scanner one: *"Scan failure … is reported as itself, not as an empty title
list"* (`Roadmap.md` lines 127–128). An empty `List` and a failed scan render
identically unless the view has an explicit state for each. The scanner
([#0024](0024.md)) produces the distinction; this view has to honour it.

The window is also too small and too rigid for the content. It is fixed at 480 points
wide (`Changeover/MetadataEntryView.swift:22`) inside a 480×580 window
(`Changeover/AppDelegate.swift:78-83`) whose style mask is `[.titled, .closable]`
(`:80`) — not resizable. A title row carrying index, duration, chapter count and
size, stacked above a poster list and a log area, does not fit.

## Steps to reproduce

1. Insert a DVD with bonus features.
2. Search for the movie and select the correct poster.
3. Look for any indication of what is on the disc.

## Expected behavior

While the scan runs, the window shows a scanning state. When it completes:

- **One candidate** with no Play All cluster (the case on all seven movie discs) — a single confirmation
  row naming the detected feature with its duration, chapter count and size, and a
  disclosure that expands the full title table for anyone who disagrees.
- **Two or more candidates** — the table, limited to the candidates, with the one
  closest to the TMDB runtime ([#0032](0032.md)) preselected and the runtime
  comparison shown so the preselection is legible rather than magic.
- **Zero candidates** — the full table with nothing preselected and a plain
  statement that no title looks like a feature, naming the likely reasons (a TV
  disc with no Play All title, or a feature under 45 minutes).
- **A Play All title detected** — the full table, **nothing preselected**, and a
  message that says what was found rather than what was rejected: "This looks like a
  TV season disc — 8 titles of about 21 minutes that together match the length of
  title 12." Name the cluster. Ripping is still possible if the user insists, but
  nothing on screen should suggest the long title is a movie, and the folder preview
  (`Changeover/MetadataEntryView.swift:73-89`) showing a Plex *Movies* path for a
  season of television is exactly what this state exists to prevent.

If the scan fails, the window shows the failure and offers a rescan. `Start Ripping`
is enabled only once a feature title is settled.

## Actual behavior

No disc information appears anywhere. `Start Ripping`
(`Changeover/MetadataEntryView.swift:126-130`) is enabled as soon as a TMDB result is
picked (`:129`) and launches a full-disc rip.

## Notes

**Verification is mostly manual and should say so.** The Phase 2 exit criterion
"title list matches what MakeMKV.app shows for the same disc" is checked by putting
the two windows side by side with a real disc — name the disc in `## Verification`.
What *can* be automated: a SwiftUI preview per state, and — more usefully — unit
tests over whatever view-model logic ends up here, in particular the derived
"selected title indices" and the enablement rule for the start button. Keep that
logic out of the `View` struct so it can be tested.

Every state should have a `#Preview`, and the fixtures make that cheap: build the
`DiscInfo` by parsing a checked-in capture rather than hand-writing one.
`hanna-mindefault.txt` gives the one-candidate case with a non-zero index,
`hornets-nest-min0.txt` gives a disc with no language tags anywhere (which the
stream summary column must not render as blank or crash on), and
`the-girl-in-the-spider-s-web-min0.txt` gives 26 titles of which 20 are five seconds
long — the case the "show N short titles" disclosure exists for.

`brooklyn-nine-nine-min0.txt` gives the Play All state, and it is the preview worth
looking at hardest: the state's whole job is to *not* look like a confident answer
when the underlying disc looks maximally confident.

**Only the 2+-candidate preview cannot be built from a fixture**, because no
captured disc produces that case. Hand-build that one `DiscInfo` and say so in the
preview's name, so nobody mistakes it for observed data.

### State ownership — the convention that decides the shape

`Plan.md` is explicit: `@Observable`, never `ObservableObject`; view models owned
with `@State`; `@Bindable` to make bindings from an `@Observable` passed as a
parameter. Phase 1 ([#0001](0001.md)) moves `isProcessing` and `logLines`
(`Changeover/MetadataEntryView.swift:7-8`) onto an `@Observable JobController` owned
by `AppDelegate`. Disc state belongs there too, for the same reason: closing the
window must not discard a scan, and Phase 4 has to serve it to a remote client.

So:

- `JobController` gains `discInfo: DiscInfo?`, `scanState: ScanState` and
  `selectedTitleIndices: Set<Int>`.
- `MetadataEntryView` reaches it through `@Environment(JobController.self)` — the
  same mechanism `AppSettings` already uses (`Changeover/MetadataEntryView.swift:4`,
  injected at `AppDelegate.swift:43,87`).
- `DiscTitleListView` takes the controller as a parameter and uses `@Bindable` to
  bind the selection. It does **not** own any of this in `@State`.

If [#0001](0001.md) has not landed, still do not put `discInfo` in this view's
`@State` — put it in a small `@Observable DiscSelectionModel` owned by
`AppDelegate` and let Phase 1 fold it in. The failure mode being avoided is exactly
the one `RemoteControl.md` lines 310–318 describes.

`ScanState` should be a plain enum — `.idle`, `.scanning`, `.scanned(DiscInfo)`,
`.failed(DiscScanError)` — so the view's `switch` is exhaustive and adding a state
later is a compile error rather than a blank pane.

The *presentation* mode is a second, separate enum derived from
`DiscTitleHeuristic.Outcome` ([#0025](0025.md)) — `.confirmed(index:)`,
`.ambiguous(candidates:)`, `.playAll(index:episodes:)`, `.unidentified` — so that
the "which layout" decision is exhaustive too and cannot silently default to the
picker, and so that the TV case cannot be dropped into the confirmed branch by
accident.
Do not fold it into `ScanState`; a scan succeeding and a disc identifying itself are
different facts.

### Layout

Insert a titles section into the body (`Changeover/MetadataEntryView.swift:12-21`)
between `folderPreview` (`:73-89`) and `logArea` (`:93-119`). The window then reads
top to bottom as: which movie is this → which title on the disc → which tracks →
what is happening → start. That ordering matches the decision sequence in
`RemoteControl.md` lines 36–39 and is worth preserving for the remote clients that
will reuse it.

**In the confirmed case that section is one row, not a list.** That changes the
window-size arithmetic below considerably: a confirmation row plus the track
selection from [#0027](0027.md) fits without a second scrolling list, and the table
only needs room when it is disclosed. Size the window for the confirmed case and let
it grow when the table opens, rather than reserving list-sized space that almost
every disc leaves empty.

Resize the window: widen the content frame from 480 to ~620
(`Changeover/MetadataEntryView.swift:22`), grow the window to roughly 620×760
(`Changeover/AppDelegate.swift:79`) and add `.resizable` to the style mask (`:80`).
Set a `minSize` so the two lists cannot be crushed. Consider replacing the fixed
`.frame(width:)` with `.frame(minWidth:idealWidth:)` so the resize is actually
useful — a fixed-width frame inside a resizable window is a familiar disappointment.

The results list is `minHeight: 220` (`:68`); the title list needs comparable room.
Two stacked lists plus a 130-point log (`:109`) is a tall window. A `VSplitView`, or
collapsing the TMDB results once a movie is chosen, are both reasonable — prefer
collapsing, since the poster list has served its purpose by then and the title list
is what the user is now looking at.

### The confirmation row

The primary control. One line, plus a disclosure:

> **Main feature** — Title 3 · 1:50:45 · 21 chapters · 6.3 GB   *(Not this one?)*

Name the *title index* explicitly, because it is the number that gets ripped and
because it is not always 0 — it is 3 on Hanna and 9 on Hornets' Nest in the `min0`
captures. Showing it makes a mis-selection visible before forty minutes of ripping
rather than after.

"Not this one?" expands the full table below, with the detected title selected. That
is the same table the 2+ and 0-candidate modes show expanded by default.

### The table

One row per title. Columns: index, duration (`H:MM:SS` from `durationSeconds`),
chapter count, size (`ByteCountFormatter`, or `.formatted(.byteCount(style: .file))`),
and a compact stream summary — "2 audio (eng, spa) · 3 subs". Use a monospaced digit
font for the numeric columns so they align; the folder preview already uses
`.system(.caption, design: .monospaced)` (`:79,82`) for the same reason.

The stream summary must survive a title with **no language attribute on any
stream** — every stream on Hornets' Nest
(`ChangeoverTests/Fixtures/makemkvcon/hornets-nest-min0.txt`) lacks attribute 3
entirely. "2 audio · 1 sub" with no parenthetical is the right rendering; an empty
parenthetical or "(nil)" is not.

Badge the heuristic's answer rather than hiding it: a "Main feature" label on the
`.mainFeature` row makes the demo's point out loud. Show short titles, but
de-emphasized and collapsed behind a "Show N short titles" disclosure — hiding them
entirely would break the exit criterion "title list matches what MakeMKV.app shows",
and Spider's Web has twenty five-second titles to hide.

Selection: `List(selection:)` as the results list already does (`:63-66`). The
feature is a single selection; bind to `Set<Int>` anyway, because the extras opt-in
([#0031](0031.md)) is genuinely multi-select over the same rows. Keep the feature
selection and the extras selection as **two separate properties**, not one set with
a role lookup — the destination they imply is different
(`Movies/` versus `Clips/`) and conflating them is exactly the mistake
[#0031](0031.md) types its way out of.

Sortable by duration, chapters and size — `Roadmap.md` line 118 asks for it and
`Table` gives it nearly free on macOS. `Table` is the better fit here than `List`
for a genuinely columnar view; weigh it against reuse in the compact iPhone layout
of Phase 5 ([#0080](0080.md)), where `Table` does not translate. Either is
defensible; make the call explicitly and note it.

### States

Render `scanState` exhaustively:

- `.scanning` — `ProgressView` with a real label, plus the reassurance that this
  takes tens of seconds (`RemoteControl.md` line 450). Reuse the placement of the
  existing `statusRow` spinner (`:45-58`).
- `.failed(error)` — `error.errorDescription` in red, matching the existing error
  treatment (`:51-56`), with a **Rescan** button. This is the exit criterion; a
  blank list here is a bug.
- `.scanned(disc)` where `disc.titles` is empty — a distinct "this disc has no
  titles" message, not the same view as a failure and not an empty list either.
- `.idle` — nothing, as today.

Then render the presentation mode exhaustively within `.scanned`:

- `.confirmed(index)` — the confirmation row, table collapsed.
- `.ambiguous(candidates)` — the table showing the candidates, closest-runtime
  preselected, with the comparison visible. If [#0032](0032.md) has not landed or
  its fetch failed, show the candidates with **nothing preselected** rather than
  guessing; say that the runtime was unavailable.
- `.playAll(index, episodes)` — the full table, nothing preselected, and the
  episode cluster named. Do **not** badge the long title "Main feature".
- `.unidentified` — the full table, nothing preselected, and one sentence of
  explanation.

**A successful scan can still carry a warning.** [#0024](0024.md) surfaces read
errors from `MSG:4004` on a scan that exited 0 — 28 of them on Hornets' Nest. Render
that as a non-blocking caution near the title list ("28 read errors during scan —
the rip may be incomplete"), not as a failure and not silently. It is the only
warning the user gets before a rip that may produce a corrupt file.

### Start button

Tighten the enablement rule at `:129`. Today:
`vm.selectedMovie == nil || isProcessing`. It must also require a scanned disc and a
settled feature title — which in `.confirmed` is automatic and in the other two
modes requires an explicit pick. Put the rule on the controller as a computed
`canStart` so it is testable and so Phase 4 can reject an invalid `startRip` command
with the same predicate (`RemoteControl.md` lines 456–458).

Selected extras do **not** gate the button; zero extras is the default and a valid
job.
