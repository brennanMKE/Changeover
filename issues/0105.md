# 0105 — A missing CLI tool is discovered at rip time instead of at setup time

| | |
|---|---|
| **Status** | open |
| **Module** | Onboarding / AppSettings |
| **Platform** | macOS |
| **First seen** | 2026-09-11 |

## Description

`makemkvconPath` and `handbrakePath` default to hardcoded Apple-Silicon Homebrew paths (`Changeover/AppSettings.swift:14-15`) and are never checked for existence. On a Mac without MakeMKV installed the app reports itself ready, accepts a disc, accepts a TMDB selection, and only fails when `Process.run()` throws — logging "✗ Failed to launch makemkvcon" into a scrolling log area (`Changeover/RipController.swift:58-61`) that the user has to be watching to notice.

## Long Description

The whole detection story today is `SettingsView.detect(binding:)`
(`Changeover/SettingsView.swift:118-127`):

```swift
let candidates = [
    "/opt/homebrew/bin/\(name)",
    "/usr/local/bin/\(name)",
]
if let found = candidates.first(where: { FileManager.default.fileExists(atPath: $0) }) {
    binding.wrappedValue = found
}
```

Three problems. It only runs when the user presses a "Detect" button they have no
reason to press. It silently does nothing when neither candidate exists — no
error, the stale wrong path stays in the field. And `fileExists` is a weak
check: a path can exist and not be executable, or be a HandBrake *app* bundle
rather than the CLI (`README.md:29` and `MacApp.md:47-48` both warn that
`brew install --cask handbrake` gives the GUI and no `HandBrakeCLI` — a real,
common mistake).

Meanwhile `AppSettings.isConfigured` (`:33`) ignores the CLI paths entirely, so
`StatusMenuView` shows a green dot and "Idle — insert a DVD to begin"
(`:16-18`) regardless.

The cost of the late failure is what makes this worth a ticket rather than a
nicety: with HandBrake missing rather than MakeMKV, the rip completes first. The
user loses the full duration of a DVD rip before the app tells them they are
missing a program they could have installed in thirty seconds.

`Roadmap.md:245-246` names this directly: *"Graceful degradation when a CLI tool
is missing — explain and link, don't fail at rip time."*

## Steps to reproduce

1. On a Mac with neither MakeMKV nor HandBrake installed (or:
   `sudo mv /opt/homebrew/bin/makemkvcon /opt/homebrew/bin/makemkvcon.bak`).
2. Launch Changeover, set a Plex root and a TMDB key.
3. Note the menu bar popover: green dot, "Idle — insert a DVD to begin".
4. Insert a disc, search a title, select a result, press **Start Ripping**.

## Expected behavior

Step 3 shows the tool as missing, with what it is, where to get it, and the exact
`brew` command. **Start Ripping** is not reachable in a state where it is certain
to fail. If the tool is present but at a non-default location, it is found
automatically without the user pressing anything.

## Actual behavior

Step 3 shows the app as ready. Step 4 runs the pipeline, which logs
`✗ Failed to launch makemkvcon: <NSError description>` and
`✗ Ripping failed. Aborting.` (`Changeover/RipController.swift:60`,
`Changeover/DVDPipeline.swift:32`) into the log pane, leaving the user to
interpret a Cocoa error string.

## Plan

Depends on [#0104](0104.md) for the `SetupChecklist` / `RequirementState` model —
this ticket implements rows 1 and 2 of it.

**1. Write a real probe, not an existence check.** New
`Changeover/Onboarding/CLIToolProbe.swift`:

- Search a candidate list in order, and make it wider than the current two:
  `/opt/homebrew/bin` (Apple Silicon), `/usr/local/bin` (Intel / older
  installs), `/usr/bin`, and for MakeMKV the in-bundle path
  `/Applications/MakeMKV.app/Contents/MacOS/makemkvcon` — MakeMKV is distributed
  as a cask, and a user who installed the app without the CLI on `PATH` has the
  binary right there. Also honor an explicit user-entered path first.
- Check `isExecutableFile(atPath:)`, not `fileExists(atPath:)`.
- **Probe for a version.** Run the binary with a cheap flag and capture the
  first line — this is what distinguishes "a file exists here" from "this is the
  tool I think it is", and it catches the HandBrake-cask mistake where
  `HandBrakeCLI` is absent but something else answers to the name. Note that
  `makemkvcon` has no `--version`; `makemkvcon -r info` or bare `makemkvcon`
  prints a banner including the version — determine the cheapest invocation
  empirically against a real install and write down which one in the resolution,
  because it is not documented anywhere obvious.
- Keep the probe `nonisolated` and `async` (it launches a `Process`), matching
  the pattern `RipController`/`EncodeController` already use
  (`Changeover/RipController.swift:9-13`) — `Plan.md`'s isolation table is
  explicit that only things that genuinely must leave MainActor get
  `nonisolated`, and a subprocess launch qualifies.

**2. Run detection automatically.** At app launch and whenever the setup window
opens, not only on a button press. Persist what was found via
`AppSettings.persist()` (`:48-54`) so the probe cost is paid once.

**3. Give the missing state real content.** `RequirementState.missing(reason:)`
for these rows needs, in the UI:

- What the tool does in one sentence ("MakeMKV reads the disc and produces an
  MKV file").
- The install command, copyable: `brew install --cask makemkv` /
  `brew install handbrake`. Include the warning from `README.md:29` /
  `MacApp.md:47-48` that the **formula**, not the cask, is what provides
  `HandBrakeCLI`.
- A link out — `https://www.makemkv.com` / `https://handbrake.fr` — since a user
  with no Homebrew at all needs the installer, not a `brew` line.
- A "Choose…" escape hatch (`NSOpenPanel`, like `choosePlexRoot()` at
  `Changeover/SettingsView.swift:105-116`) for an install in a location nothing
  predicts.
- A "Recheck" button, because the user will go install the tool and come back.

**4. Fix the silent-failure bug in the existing Detect button.**
`Changeover/SettingsView.swift:124-126` does nothing at all when no candidate is
found. Whatever else changes, that button must report failure.

**5. Gate the pipeline.** With `isConfigured` derived from the checklist
([#0104](0104.md) step 3), the menu bar "Open…" row
(`Changeover/StatusMenuView.swift:37`) and the "Start Ripping" button
(`Changeover/MetadataEntryView.swift:126-130`) both become unreachable while a
tool is missing. Prefer disabling with a visible reason over disabling silently —
a greyed-out button with no explanation is its own bug.

**Risks.** (a) Launching an unknown binary to probe it is a (mild) trust
decision; only probe paths the user chose or that are on the known list, never
something scraped from the environment. (b) MakeMKV's licence key expires
periodically, which surfaces as a *scan* failure, not a missing-binary failure
(`RemoteControl.md`, "Risks and gotchas"; `Roadmap.md:82`). A version probe
succeeding does not mean MakeMKV will rip. Do not let this ticket's green
checkmark imply that — [#0001](0001.md) owns the expired-key error. (c) The
version probe adds launch latency; run it off the main actor and show
`.checking` rather than blocking the window.

## Notes

**The real verification for this cannot happen on the author's machine**, where
both tools are installed at the default paths. Options:

```bash
# Simulate the missing tool without uninstalling anything:
sudo mv /opt/homebrew/bin/makemkvcon /opt/homebrew/bin/makemkvcon.away
# ... run the app, confirm the row reports missing with install guidance ...
sudo mv /opt/homebrew/bin/makemkvcon.away /opt/homebrew/bin/makemkvcon
# ... confirm Recheck flips the row to satisfied ...
```

The Intel-path case (`/usr/local/bin`) and the no-Homebrew case are only
testable on the clean machine from [#0103](0103.md) — a Mac with no Homebrew is
the exact environment this ticket exists for. Fold it into that trip.

**Automated tests are genuinely possible here and should exist.** Inject the
filesystem and process-launch dependencies so `CLIToolProbe`'s candidate ordering
and its executable-vs-exists logic are unit-testable in `ChangeoverTests` without
a real binary. `issues/Issues.md` warns that a green build is not verification
for anything in the rip path — this ticket is *adjacent* to the rip path but its
core logic is pure, so the caveat does not excuse skipping tests here.
