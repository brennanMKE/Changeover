## Description

Every real disc that goes through joe is evidence, and today it is thrown away. Three captures exist (`dragon-tattoo`, `oppenheimer`, `tv-season-playall`), each grabbed by hand during a debugging session, with no consistent naming, no metadata about which disc or drive produced them, and no test that walks the whole set. The TV capture that proved the Play All guard on real data is not asserted by any test at all.

The user's ask (2026-09-16): keep a record of every disc, so the corpus drives automated regression tests on gordon (or in a VM on cameron) and a change that breaks disc selection fails immediately.

## Resolution notes

> 🟢 Resolved 2026-09-16 — four real discs now live in `ChangeoverTests/Fixtures/discs/<slug>/{scan.json,disc.json}`, each with a human-reviewed manifest that one parameterized `DiscCorpusTests` sweep asserts against the real parser, heuristic, audio-dedup and subtitle-grouping code, and `Tools/capture-disc.sh` adds the next disc in one step.

**Review, 2026-09-16 (Opus).** Approved. - `hornets-nest`: `MainFeature: -1`, 11 titles, title 11 = 8,813 s (2:26:53) / 16 chapters, and **every** `LanguageCode` on **every** audio stream of **every** title is literally `"und"` → both of title 11's AC3 5.1 streams normalize to `nil` and so never enter the merge map, giving exactly 2 audio options. The manifest's `outcome: "none"` / `outcomeIndex: null` is right for the *current* `classify` (the guard is `mainFeatureIndex != 0`, which `-1` passes, followed by a title lookup that `-1` cannot satisfy) — an honest record of today's behaviour, with the gap itself filed as [#0056](0056.md) rather than papered over.
- `tv-season-playall`: `MainFeature: 14`, 32 titles, title 14 = 10,413 s / 33 chapters, cluster 15–22 (1368, 1257, 1301, 1292, 1298, 1300, 1301, 1298) = **10,415 s**, a 2 s / 0.02% error against the 2% tolerance. Title 4 (268 s) and title 23 (378 s) both stay out of the cluster — the first below the 300 s pool floor, the second 70% away from the seed — so the eight-title answer is not an artefact of a loose filter.

**The `reviewed` gate holds, with one hole closed.** `#expect(manifest.reviewed, …)` fails a case by name, and `corpusHasAtLeastTheThreeFoundingDiscs` stops an empty `discSlugs()` from passing vacuously. But `discSlugs()` requires *both* files, so a **new** disc that lost its `disc.json` would have dropped out silently — the founding-discs test only pins the original three. `65a1694` adds `everyCapturedDiscDirectoryIsACompleteCorpusDisc`, which names the offending directories; falsified on gordon with a stub `zz-falsify/scan.json` (`Expectation failed: (missing → ["zz-falsify"]).isEmpty → false`), stub then removed. The same commit repoints `HandBrakeScanParser`'s doc comment at `Fixtures/discs/dragon-tattoo/scan.json`, the last live reference to the old `Fixtures/handbrake-scan/` path outside historical issue files.

**Also checked.** The `PBXFileSystemSynchronizedBuildFileExceptionSet` touches only the `ChangeoverTests` root group and lists only the ten disc-fixture files; no app-target file is excluded, no signing/entitlement/sandbox setting is touched, and the fixtures were never *meant* to be bundled (every reader resolves `#filePath`), which the green run on gordon confirms end to end. The eight migrated test files are path-string and doc-comment edits only — no assertion changed, no `#expect` weakened — and #0039's merged-capture negative fixture still runs as `HandBrakeScanParserTests.oppenheimerMergedCaptureFailsToDecodeAndIsFlaggedCorrupted` against `discs/oppenheimer/scan.merged.txt`, still asserting `titleSetCorrupted`, no titles, no `mainFeatureIndex`. `Tools/capture-disc.sh` was read, **never run** (the user had a disc in joe's drive): stdout and stderr go to separate remote files on every invocation, everything local is written under `ChangeoverTests/Fixtures/discs/<slug>/` plus a trapped `mktemp -d`, an unmounted disc exits 1 with a message, and all four of its reported fixes are really in place (`isinstance(main_feature, int) and main_feature > 0` before the feature lookup; `MainFeature` null *or* `<= 0` → `outcome: "none"`, `outcomeIndex: null`; version from the scan's own `VersionString`; `DISC_ID_NOTE` explaining a null `discId`). The CLAUDE.md change is purely additive — nothing was removed, and the new sentence tightens rather than loosens ("Don't run this against real hardware on your own initiative"), despite the commit message calling it a softening.

**What a human still owes.** Every `disc.json` here says `reviewed: true`, which is a claim about a *person* having looked. Two independent programmatic derivations agree, which is strong evidence the numbers are not typos — but no human eyeballed whether title 11 really is the Hornets' Nest feature, whether `tv-season-playall` really is the disc #0025 describes, or whether `dragon-tattoo`/`oppenheimer`'s three audio options and five/six subtitle groups match what the discs actually offer on a TV. **Every disc added from here on needs that human pass before `reviewed` is flipped** — that is the whole point of the flag, and a test cannot supply it.

**Smaller things left alone** (worth a follow-up only if they bite): `handbrakeVersion` is `"HandBrake 1.11.2"` on the script-written manifest and `"1.11.2"` on the three migrated ones — inconsistent, but nothing asserts it; the script interpolates `$VOLUME`, `$DRIVE_MODEL` and lsdvd's stderr into `disc.json` unescaped, so an exotic volume name or error text could emit invalid JSON (which fails loudly at review time, not silently); an explicit `slug` argument is not sanitized the way a derived one is; a non-zero `SCAN_STATUS` is printed but does not abort, so a failed scan can still write a `titleCount: 0` manifest (caught by `reviewed: false`); and `~/changeover-fixtures/` is left behind on joe. `tv-season-playall`'s `volumeName` is a recorded placeholder, which its own `notes` say plainly and which no assertion depends on.

## Root cause

Nothing wrong to fix — this is new infrastructure, not a bug. The three existing captures (`dragon-tattoo`, `oppenheimer`, `tv-season-playall`) each landed as a side effect of a different ticket (#0023/#0025/#0027/#0033's fixture, #0039's stdout/stderr splice, #0025's real-disc Play All confirmation), with no shared layout, no recorded expectations, and — for the TV capture specifically — no test at all. A regression in `HandBrakeScanParser`, `DiscTitleHeuristic`, `AudioTrackOptions` or `SubtitleGrouping` could break real-disc behavior while every synthetic-fixture test kept passing.

## Fix

Followed the seven-step Plan; one deliberate deviation and one mid-flight addition, both recorded below.

- **Step 1 (capture tool).** Rewrote `Tools/capture-disc.sh` in place rather than adding a new script — the old script captured `makemkvcon` output, which is off the pipeline's path (`CLAUDE.md`: "MakeMKV is no longer on the pipeline's path"), so nothing depended on its exact shape surviving. It runs `HandBrakeCLI -i <mount> --scan --title 0 --min-duration 1 --json` with stdout/stderr captured on **separate** remote redirects (`>scan.json 2>scan.stderr.txt`) — never a single merged stream, which is the exact corruption #0039 documents. Every remote step is its own trivial `ssh` call (no nested quoting, no remote `$(...)` embedded inside a locally double-quoted string) — line counts, exit status, and all JSON parsing happen locally after `scp` brings the files home. `disc.json` is written with what the script can safely compute (title count, `MainFeature`, the feature title's raw duration/chapters, HandBrake's version — read from the scan's own `Version:`/`VersionString` block, not a separate `--version` call) and `reviewed: false` for everything it can't (whether the disc is Play All, and the two deduplicated counts from `AudioTrackOptions`/`SubtitleGrouping`, which the script deliberately does not reimplement).
- **Step 2 (manifest).** `disc.json`'s `expect` object carries `titleCount`, `mainFeatureIndex`, `outcome` (`single`/`playAll`/`none`/`noTitles`, mirroring `DiscTitleHeuristic.Outcome`), `outcomeIndex`, `outcomeEpisodes`, `featureDurationSeconds`, `featureChapterCount`, `audioTrackCount`, `subtitleGroupCount`. **Addition beyond the Plan:** a top-level `reviewed: Bool`. The Plan says the manifest is "reviewed by a human once — the file is the recorded truth", but says nothing about enforcing that a review happened; `DiscCorpusTests` now refuses (`#expect(manifest.reviewed, …)`) any disc whose manifest hasn't been flipped to `true`, so a capture nobody looked at can never silently pin a wrong behaviour by decoding successfully with plausible-looking defaults.
- **Step 3 (corpus test).** `ChangeoverTests/DiscCorpusTests.swift`: `discMatchesItsRecordedExpectations(slug:)` is `@Test(arguments: DiscCorpusTests.discSlugs())`, where `discSlugs()` enumerates `Fixtures/discs/*/` for directories holding both `scan.json` and `disc.json`. It asserts the manifest's own `slug` field, `reviewed`, `!titleSetCorrupted`, title count, `MainFeature`, the `DiscTitleHeuristic.classify` outcome (including the `.playAll` episode cluster), and — only when `outcomeIndex` resolves to a real title — feature duration, chapter count, `AudioTrackOptions.options(for:).count`, and `SubtitleGrouping.groups(for:).count`. A companion `corpusHasAtLeastTheThreeFoundingDiscs` sanity test guards against `discSlugs()` silently returning an empty list (a broken path would otherwise leave the parameterized test vacuously green with zero cases). **Added in review (`65a1694`):** `everyCapturedDiscDirectoryIsACompleteCorpusDisc` closes the other half of that hole — `discSlugs()` needs *both* files, so a disc directory missing its `disc.json` would have dropped out of the sweep silently, and the founding-discs test only pins the original three by name.
- **Step 4 (migration).** Moved (`git mv`) the three existing captures into `Fixtures/discs/<slug>/scan.json`, updating every test file that referenced the old `Fixtures/handbrake-scan/…` paths (`AudioTrackOptionsTests`, `DiscScannerTests`, `DiscTitleHeuristicTests`, `EncodeSelectionTests`, `ExtrasPlanTests`, `HandBrakeScanParserTests`, `MakeMKVFallbackTests`, `SubtitleGroupingTests` — path strings only, no assertions changed). `oppenheimer/scan.merged.txt` (the deliberate stdout+stderr negative fixture for #0039) moved alongside `oppenheimer/scan.json` but carries no `disc.json` of its own, so `discSlugs()` never sweeps it; it stays covered by its own `HandBrakeScanParserTests` case.
- **Step 5 (TV pin).** Added `DiscTitleHeuristicTests.classifiesTheRealTVSeasonCaptureAsPlayAll`: asserts `MainFeature: 14`, 32 titles, title 14 at 10,413 s / 33 chapters, the episode cluster `15...22` summing to 10,415 s (0.02% error, inside the 2% guard tolerance), `classify` returning `.playAll`, and `applyingSuggestedRoles` never marking anything `.mainFeature`. This is also asserted generically through the corpus sweep (`tv-season-playall`'s `disc.json`), but the Plan asked for it "specifically" — the dedicated test is the one that reads like the issue's own numbers rather than a generic manifest field.
- **Step 6 (size).** `scan.json` sizes: dragon-tattoo 42 KB, oppenheimer 58 KB, tv-season-playall 231 KB, hornets-nest 133 KB — all inside the 40–240 KB range the Plan describes as fine to commit. No VOB/rip data anywhere.
- **Step 7 (docs).** Added "Capturing a real disc into the test corpus (#0055)" to `CLAUDE.md`, after "Setup required before building".

**Values derivation (Plan step 2's "then reviewed by a human once").** Rather than eyeballing the JSON, I compiled `HandBrakeScanParser.swift`, `DiscInfo.swift`, `DiscTitleHeuristic.swift`, `AudioTrackOptions.swift`, `SubtitleGrouping.swift` and `LanguageCode.swift` standalone with `swiftc` (outside Xcode — these five files have no UIKit/AppKit/SwiftUI/Observation imports and are all `nonisolated`, so they build as a plain command-line tool) and ran them directly against each committed `scan.json`, printing exactly what the corpus test itself computes. That is the "human review" for all four discs' `expect` blocks — not a guess, a second, independent execution of the same pure functions the test calls, outside the test framework.

**Mid-flight addition: the `hornets-nest` disc.** While this ticket was in progress the user captured *The Girl Who Kicked The Hornets' Nest* on joe with the new script — the first real use of it outside my own testing. That run found and fixed four bugs in `Tools/capture-disc.sh` (see `## Gotchas`) and produced a fourth corpus disc: HandBrake reports `MainFeature: -1` on it (no main feature named at all), which `classify` correctly falls through to `.none` for (no title has a negative index, so the lookup simply fails) — `disc.json` records `outcome: "none"`, `outcomeIndex: null`, so the corpus sweep's feature-specific assertions never fire for it. Every audio stream on every title on this disc is untagged, which is exactly the disc #0027's "never merge untagged tracks" rule exists for, so title 11 (the real movie, 2:26:53 / 16 chapters, confirmed by inspection) is pinned directly in a new test, `AudioTrackOptionsTests.realHornetsNestFeatureTitleKeepsBothUntaggedAudioTracksSeparate`, rather than through the generic sweep. The gap this disc exposes — `DiscTitleHeuristic.classify` has no fallback when `MainFeature` is absent — is deliberately **not** fixed here; it is filed as [#0056](0056.md), which this ticket's fixture directly supplies as evidence.

**Xcode gotcha, fixed as part of Step 1/3.** `ChangeoverTests`' `PBXFileSystemSynchronizedRootGroup` flattens Copy Bundle Resources by basename, so `scan.json`/`disc.json` repeated across `Fixtures/discs/<slug>/` subdirectories collided at build time ("Multiple commands produce … disc.json"). Added a `PBXFileSystemSynchronizedBuildFileExceptionSet` excluding every disc fixture file from `ChangeoverTests`' target membership — safe because every fixture-reading test resolves its path via `#filePath` (the source tree), never the app bundle, so nothing needs these files copied into `Contents/Resources` at all. A directory-level exception (`"Fixtures/discs"`) did **not** work in this Xcode version — verified by trying it and getting the same collision — so the exception set lists files individually; `Tools/capture-disc.sh`'s closing instructions now tell the reviewer to add a new disc's files there too.

## Gotchas

- **The Xcode synchronized-group collision** (see `## Fix`) only shows up once a second disc shares a basename with a first — it would not have been caught by building before the migration step, only after. A directory-level `membershipExceptions` entry (`"Fixtures/discs"`) silently does *not* exclude the subtree in this Xcode version (26.2, `objectVersion = 77`); only exact per-file relative paths work. Any new disc capture must add its files to that same exception set by hand — `Tools/capture-disc.sh`'s closing output says so.
- **`Tools/capture-disc.sh` had four real bugs**, all found by the user's own `hornets-nest` capture rather than by me (I never ran the script against hardware, per `CLAUDE.md`): (1) a negative `MainFeature` (`-1`) was copied straight into `outcomeIndex` instead of being treated the same as absent/zero — `outcome` stayed `"single"` with a nonsensical `outcomeIndex: -1`; (2) `HandBrakeCLI --version`'s first line on this build is a hardening-flags banner (`"[…] Compile-time hardening features are enabled"`), not the version — switched to parsing the scan's own `Version:`/`VersionString` block instead, which also removed a whole remote round trip; (3) a bare `discId: null` when `lsdvd` can't identify a disc looked identical to "nobody tried" — `DISC_ID_NOTE` now records *why* (lsdvd's stderr, an empty json with no `discid` field, or no output at all) in the manifest's `notes`; (4) `featureDurationSeconds`/`featureChapterCount` extraction was never actually broken (independently re-verified against Oppenheimer's real `MainFeature: 7` — 10,811 s / 21 chapters, matching #0039's documented numbers exactly), but the guard is now explicit (`isinstance(main_feature, int) and main_feature > 0`) rather than relying on "no title has a negative index" as an accidental safety net.
- **`issues/0056.md` was filed by a parallel process while this ticket was open**, and its first commit (`685c9d3`) happened to include my then-uncommitted rename of the three migrated fixture files (a `git mv` I'd run but not yet committed) — a snapshot of shared working-tree state landing under an unrelated commit message rather than anything I did. No content was lost; this ticket's commit (`69b7def`) contains everything else. Worth knowing if `git log --follow` on those three `scan.json` files looks like it skips a step.
- **`swiftc`-compiling app source files standalone outside Xcode worked cleanly** for the five files this ticket needed (see `## Fix`), because they're already disciplined to be `nonisolated` with no UI imports (per `CLAUDE.md`'s MainActor-by-default rule) — a nice confirmation that the architecture note in `CLAUDE.md` about these types being "pure value transforms" isn't just aspirational.

## Expected behavior

- Scanning a disc on joe produces a committed capture plus its metadata in one step, with a predictable name.
- One test walks the whole corpus and asserts each capture's recorded expectations, so adding a disc adds coverage without writing a new test.
- A regression in the parser, the heuristic, the Play All guard, subtitle grouping or audio options fails on gordon against real disc data, not just synthetic data.

## Plan

**1. Capture tool.** A small script (`Tools/capture-disc.sh`, run on joe) that, for the mounted disc:
- runs `HandBrakeCLI -i <mount> --scan --title 0 --min-duration 1 --json`, keeping **stdout and stderr in separate files** (#0039 — a merged capture is a corrupt capture);
- records `lsdvd`'s disc id when available, the volume name, the drive model, the HandBrake version, and the date;
- writes `ChangeoverTests/Fixtures/discs/<slug>/scan.json`, `scan.stderr.txt` and `disc.json`.

**2. Manifest with expectations.** `disc.json` carries what the corpus test asserts: title count, `MainFeature`, expected `DiscTitleHeuristic` outcome (`single(index:)` / `playAll(index:episodes:)` / `noTitles`), the feature's duration, chapter count, audio-track count and subtitle-group count. Written by the capture tool from the scan, then reviewed by a human once — the file is the recorded truth, so a wrong value pins a wrong behaviour.

**3. Corpus test.** `DiscCorpusTests` enumerates `Fixtures/discs/*/`, parses each `scan.json` with `HandBrakeScanParser`, and asserts every field in its `disc.json`, including running `DiscTitleHeuristic.classify`, `SubtitleGrouping.groups(for:)` and `AudioTrackOptions.options(for:)`. One test function, parameterized over the corpus, so a new disc needs no new code.

**4. Migrate the three existing captures** into the new layout, including the merged Oppenheimer capture as a deliberate negative fixture for #0039 (its own test, not part of the corpus sweep).

**5. Pin the TV capture specifically** (the user's immediate ask): assert `MainFeature: 14`, the eight-title cluster 15–22, the 10,415 s sum against title 14's 10,413 s, and that `classify` returns `.playAll`.

**6. Size discipline.** A scan JSON is 40–240 KB, which is fine to commit. Never commit VOB data or anything ripped from a disc — captures are metadata only.

**7. Document it** in `CLAUDE.md` or `Tools/README.md`: how to capture a disc on joe, and that every disc that goes through the app should be captured before it leaves the drive.
