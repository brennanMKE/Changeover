# 0046 — A failed or hung job leaves nothing to recover from and can hold a lane forever

| | |
|---|---|
| **Status** | open |
| **Phase** | 3 — Unattended multi-disc |
| **Module** | JobScheduler / RipController / EncodeController |
| **Platform** | macOS |
| **First seen** | 2026-09-11 |

## Description

Today a failure is a log line and an early `return` (`Changeover/DVDPipeline.swift:32-34`, `:47-50`) — nothing records that the job failed and nothing needs to, because there is no queue behind it. With a queue, a failure that does not release its lane token stalls every job behind it, and a hung `makemkvcon` can only be resolved by quitting the app because `Task.cancel()` does not kill a `Process`.

## Long Description

"A failed job does not stall the queue behind it" is a Phase 3 exit criterion (`Roadmap.md:156`). There are exactly four ways a queue stalls, and each needs its own defence:

1. **Lane token leak.** The rip or encode `Task` exits without clearing `ripTask` / `encodeTask`. [#0044](0044.md)'s `defer` handles the ordinary paths; this ticket proves it holds on the failure, cancellation and thrown-error paths too.
2. **Head-of-line blocking.** The scheduler picks `jobs.first` instead of `first(where: stage == .queued)`. Also [#0044](0044.md)'s design, also asserted here.
3. **A job stuck in a non-terminal stage forever.** A `makemkvcon` that hangs on a scratched disc never terminates, so `terminationHandler` (`Changeover/RipController.swift:44`) never fires, the continuation never resumes, and the lane is held indefinitely. The answer is a user-driven cancel that actually kills the process.
4. **Cancellation that does not cancel.** Both controllers use `withCheckedContinuation` (`Changeover/RipController.swift:14`, `Changeover/EncodeController.swift:15`) with no cancellation handling at all. `Task.cancel()` on the scheduler's task sets a flag nobody reads; `makemkvcon` keeps running, the continuation is still outstanding, and the job is now "cancelled" in the UI while a subprocess quietly continues writing to the working directory.

Point 4 is the substantive code change in this ticket and it has a sharp edge: `withCheckedContinuation` traps at runtime if resumed twice. A cancellation handler that resumes, racing a `terminationHandler` that also resumes, is a crash, not a bug report.

## Steps to reproduce

1. Start a rip against a disc that `makemkvcon` cannot read. Watch it log a non-zero exit status (`Changeover/RipController.swift:51`) and then nothing.
2. Try to cancel a running rip from anywhere in the UI.
3. Inspect the app afterwards for any record that the job failed and why.

## Expected behavior

A failing stage puts its job into `.failed` with a specific `JobFailure`, releases its lane token, and the scheduler immediately starts the next eligible job. A running job can be cancelled from the queue view; the underlying `makemkvcon` or `HandBrakeCLI` process is terminated, the partial output in that job's working directory is cleaned up, the job becomes `.cancelled`, and the lane is released. A cancel while a job is `queued` never launches a process at all.

## Actual behavior

`DVDPipeline.run()` logs `"✗ Ripping failed. Aborting."` and returns (`:32-34`); `MetadataEntryView` sets `isProcessing = false` (`:153`) and that is the entire failure handling in the app. There is no cancel affordance anywhere — no button, no method, no `Task` handle retained (`:148-154` discards it). A hung rip is unrecoverable without quitting.

### Cancellable processes

Both controllers get the same treatment. Sketch for `RipController.rip`:

```swift
let box = ProcessBox()                        // holds the Process, plus a resumed flag
return await withTaskCancellationHandler {
    await withCheckedContinuation { continuation in
        box.adopt(continuation)               // stores it; resume goes through the box
        // … existing setup, Changeover/RipController.swift:17-62, unchanged …
    }
} onCancel: {
    box.terminate()                           // process.terminate(); SIGTERM
}
```

`ProcessBox` is a small `final class` with an `NSLock` guarding a `resumed: Bool` and the `Process?`. **Every** resume — the success path (`:48`), the non-zero-exit path (`:52`), the launch-failure path (`:61`) and the new cancellation path — goes through `box.resumeOnce(_:)`, which resumes only if `resumed` is still false. This is the double-resume defence, and it is why the flag needs a lock: `terminationHandler` runs on a background thread while the cancellation handler runs on whichever thread cancelled.

`ProcessBox` is the one genuinely `nonisolated` addition in this ticket. It is `nonisolated` because `withTaskCancellationHandler`'s `onCancel` is a `@Sendable` closure that can run on any thread — this is the "explicit `nonisolated` only where a type genuinely must leave the main actor" case that `Plan.md` allows, and the justification belongs in a comment next to it so the next reader does not "clean it up".

`process.terminate()` sends `SIGTERM`. `makemkvcon` and `HandBrakeCLI` both handle it and exit; neither leaves the drive wedged. Do not escalate to `SIGKILL` on a timer — a `SIGKILL`ed `HandBrakeCLI` can leave a partial `.mp4` that a later run mistakes for finished output. Partial-file cleanup is explicit instead: on cancel or failure, delete the job's working directory (per-job, from [#0001](0001.md)), which removes any partial `.mkv` or `.mp4` in one step.

### Failure classification

`RipController` currently logs a bare exit status (`:51`). Map the actual failure to a `JobFailure` case ([#0041](0041.md)) instead:

- launch failure with `NSFileNoSuchFileError` for `makemkvconPath` / `handbrakePath` → `.toolMissing(path:)`;
- `makemkvcon` output containing the expired-key message → `.makemkvKeyExpired` (a recurring real-world failure, `RemoteControl.md:459-461`);
- `ENOSPC` / no-space text, or a destination that fails a writability probe → `.diskFull` / `.destinationUnwritable(path:)`;
- anything else → `.processExited(stage:status:)`.

Phase 1 ([#0001](0001.md)) does the detection work; this ticket's contribution is attaching the result to the job and releasing the lane, rather than printing it.

### Scheduler cancel

```swift
func cancel(id: JobID) {
    guard let job = queue?.job(id: id) else { return }
    switch job.state.stage {
    case .queued:                         job.transition(to: .cancelled); pump()
    case .ripping:    ripTask?.cancel()   // defer in the Task clears the token and pumps
    case .awaitingEncode:                 job.transition(to: .cancelled); pump()
    case .encoding:   encodeTask?.cancel()
    case .organizing: break               // FileManager.moveItem; too short to interrupt safely
    case .done, .failed, .cancelled: break
    }
}
```

The `.ripping` and `.encoding` cases must check that the task in that lane actually belongs to the job being cancelled — store the owning `JobID` next to each `Task` handle. Cancelling job 3 must never kill job 2's encode, and after [#0044](0044.md) the two lanes hold different jobs by design, so this is not hypothetical.

A cancelled rip still ejects the disc, for the same reason a failed one does ([#0045](0045.md)).

### Risks

- **Double resume traps.** This is the one thing in this ticket that turns a bug into a crash. The `resumeOnce` discipline is not optional and deserves a comment saying why.
- **`terminate()` on an already-exited process.** `Process.terminate()` on a process that has already reported termination raises an Objective-C exception on some paths. Guard on `isRunning` inside the lock and treat the race as benign.
- **Cancellation propagates into child tasks.** The per-line log hops are `Task { @MainActor in log(trimmed) }` (`Changeover/RipController.swift:38`) — unstructured, so they are not cancelled with the parent, which is correct here: the last few lines before termination are exactly the ones worth reading.
- **Don't make cancel a state the UI can spam.** Two cancels in flight for the same job must be idempotent; the transition table ([#0041](0041.md)) already rejects the second, so route every cancel through `transition(to:)` rather than assigning stage directly.

**Replacement.**

- **Changed:**
  - `ProcessRunner.swift`, `HandBrakeFailureClassifier.swift`;
  - `MakeMKVRipper.swift` — a cancelled termination maps to `.cancelled`;
  - `DiscScanner.swift` — its scanner-local `Failure` gains `.cancelled`, which is not wire format;

- **Tests:** extend `ProcessRunnerTests`, `HandBrakeFailureClassifierTests` and `JobControllerTests`; add `ChangeoverTests/JobCancellationTests.swift`.

1. **`ProcessRunner.run` becomes cancellable.**
   - Wrap the existing `withCheckedContinuation` in `withTaskCancellationHandler`.
   - `onCancel` runs on an arbitrary thread and calls `cancel()` on a new `nonisolated final class RunCancellation: @unchecked Sendable`. That class holds `cancelled: Bool` and `process: Process?` behind an `NSLock`. It is justified in a comment as the one genuinely off-actor type here.
   - `cancel()` sets the flag and, if a process is attached and `isRunning`, calls `terminate()`. That sends SIGTERM:
     - not SIGINT, because C5 showed SIGINT muxes a partial file;
     - not SIGKILL.
   - Attach `process` before `process.run()`. Immediately after a successful `run()`, re-check the flag and terminate. This closes the cancel-before-launch race.
   - If the flag is already set before launch, don't launch at all. Resume through the same single path with a cancelled `Termination`.
   - **The cancel handler never resumes the continuation.** Resumption stays exclusively with `RunCompletionGate`, whose inputs are `markProcessDone` from `terminationHandler` and `markReaderDone` at EOF. So there is still exactly one resume by construction, simpler than the original `resumeOnce` design.
   - Add `var cancelled: Bool = false` to `ProcessRunner.Termination`. It's internal and not wire format; the default keeps existing memberwise call sites compiling. ## Notes

**Verification.** The isolation properties are testable without a disc against [#0044](0044.md)'s `StageRunnerStub`, and must be. `ChangeoverTests/JobFailureIsolationTests.swift` covers:

- three jobs queued, the first fails its rip → the second starts ripping and all three reach terminal states, none stuck in a non-terminal stage;
- a job failing during **encode** does not block the encode lane for the job behind it;
- a failure on every non-terminal stage releases the correct lane token — parameterise over `JobStage` so a stage added later fails the test rather than silently skipping;
- a job that fails while another is `ripping` does not disturb the running one;
- cancelling a `queued` job never invokes the stub's rip at all;
- cancelling a `ripping` job transitions it to `.cancelled`, releases the drive lane and starts the next job;
- cancelling job C never cancels the concurrently running job B;
- a second `cancel(id:)` on an already-cancelled job is a no-op.

For `ProcessBox` specifically, a standalone test that launches `/bin/sleep 30`, cancels it, and asserts the call returns promptly with a single resume and the process no longer running — that exercises the real cancellation path with no MakeMKV dependency and no disc, and it is the cheapest possible guard against the double-resume trap.

Manual, and it must be labelled manual: a deliberately unreadable or damaged disc, named in `## Verification`, confirming the job shows a specific failure reason rather than a generic one and that a following queued job runs; and cancelling a real rip mid-flight, confirming in `Activity Monitor` that `makemkvcon` is gone and that the job's working directory is empty afterwards.
