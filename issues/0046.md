## Description

Today a failure is a log line and an early `return` (`Changeover/DVDPipeline.swift:32-34`, `:47-50`) — nothing records that the job failed and nothing needs to, because there is no queue behind it. With a queue, a failure that does not release its lane token stalls every job behind it, and a hung `makemkvcon` can only be resolved by quitting the app because `Task.cancel()` does not kill a `Process`.

## Resolution notes

> 🟢 Resolved 2026-09-15 — A running job can now be cancelled from the status menu. `JobController.cancel(id:)` cancels the job's `Task`, `ProcessRunner` stops the child with SIGTERM and then SIGKILL after 10 s (a watchdog stop escalates the same way), and the job ends `cancelled` through `finish`, with no MakeMKV fallback and its working directory removed (dc74d7d, review fix f9b9755).

**Review (2026-09-15, claude-opus-5).** dc74d7d is in scope. The refresh reduced this ticket to a user cancel, and the rest of the title's promise was already met elsewhere:
- **Hangs** are bounded by #0009's watchdogs: HandBrake 30 min of silence, MakeMKV 4 h absolute, scan 15 min.
- **Failures** are recorded in #0041/#0042's job state and history, with #0009's classification.
- **Stale working directories** are swept by #0004 at the start of every job (not at launch). The refresh accepted that.
- **Lane tokens** don't exist under #0040's option A.

The cancel plumbing is sound:
- `onCancel` never resumes the continuation, and `RunCompletionGate` stays the single resume path, including the pre-launch `forceExpire`.
- The classifier, `MakeMKVRipper` (scan and rip) and `DiscScanner` all check `cancelled` before any timeout or exit-code classification.
- `FallbackPolicy` rules `.cancelled` ineligible.
- `finish` runs for every cancel, so the job reaches history and the sleep assertion is released.

Three things were wrong, and f9b9755 fixes them:

1. **SIGTERM only, with no escalation. A cancel could hang forever.** A child that caught or ignored SIGTERM never exited. `terminationHandler` never fired, and the gate arms its grace only from `markProcessDone`, so the job sat in `encoding` with Cancel pressed until the child ended on its own. #0009's watchdogs had the same hole, because they also only called `terminate()`. `RunCancellation.stop(_:)` now sends SIGTERM and then, if the child is still running after `killGrace` (10 s), SIGKILL. The cancel and both watchdogs use it.
   - A disarm in `terminationHandler` keeps the kill from ever reaching a reused pid.
   - **Why this overrides the refresh's "never SIGKILL":** its reason was that a killed HandBrakeCLI leaves a partial `.mp4` a later run mistakes for finished output. That doesn't apply here. SIGTERM already leaves an equally partial file (C5), and every cancelled or timed-out job's directory is removed by `WorkingFiles.disposition`. SIGINT is still never sent.
   - **Remaining bound:** a child blocked in uninterruptible disc I/O takes neither signal until the kernel's read returns, so that case is bounded only by the drive's own I/O timeout. See the manual check below.
2. **A cancel during #0037's duration check ended `failed` with a misleading reason.** A cancel landing as HandBrakeCLI exits 0 makes `AVURLAsset.load` throw, and the check reports "duration could not be read". That `.unknown` is disc-shaped. Boundary 2 only guarded `.attempt`, so two cases slipped through, each ending `.failed`:
   - with no makemkvcon installed (MakeMKV is optional), `.unavailable`;
   - with the disc gone, `.notEligible`.

   The notification said "Something went wrong: …" in both. Boundary 2 now runs before `FallbackPolicy.decide`, and the same check runs after the fallback's own duration check.
3. **The cancel notification read as a failure and could name the wrong tool.** The title was "Changeover couldn't finish …". The body was "HandBrakeCLI was stopped before it finished.", even when makemkvcon was the process running, because a fallback cancel reports the primary `.encode` stage. The log detail also said "The MakeMKV fallback was tried and also failed". Now:
   - title: "<Title (Year)> was cancelled";
   - body: nothing new was filed in Plex, and the disc is still in the drive;
   - headline: "The job was cancelled before it finished.";
   - fallback detail: "The job was cancelled while the MakeMKV fallback was running."

**Checked and fine:**

- **Edges.**
  - A cancel in `organizing` is refused (`CancelPolicy`).
  - A wrong or stale id, or no current job, is refused and logged.
  - A second Cancel is harmless: `Task.cancel()` is idempotent, and so is `stop` (one escalation).
  - During `extras`, the in-flight extra's partial is removed, the rest are skipped with one log line, and the job ends `succeeded`. That path had no test; f9b9755 adds one.
- **Races.**
  - A cancel as the process exits normally either reads `cancelled` in `terminationHandler` (the job ends cancelled and the file is discarded, which is what the user asked for) or misses it and is caught by boundary 3 before the move.
  - A cancel accepted during the `advanceMarker(.encoded)` await between boundary 3 and `reportPhase(.organizing)` is not acted on. The move runs, any extras are skipped, and the job ends `succeeded`. That is benign, but the UI must not promise "cancelled" before the outcome (see #0048).
  - Pre-launch and mid-launch cancels are covered by `run`'s two re-checks.
  - No continuation-leak warnings.
- **Lifetimes.** The cycle `process → terminationHandler → RunCancellation → process/escalation` is broken by `processExited()` and by `onReady` clearing `terminationHandler`.

## Root cause

Per the `### Plan refresh (2026-09-15)` section below (which supersedes the
original report — there is no queue, no `RipController`, and no
lane-token/head-of-line-blocking problem under #0040's option A; see the
refresh for the full accounting), what actually remained was narrower than
the filing: **`JobController` had no way to stop an in-flight job.** Every
process ran through the shared `ProcessRunner.run`, whose
`withCheckedContinuation` had no cancellation handling at all — the
`Runner`'s `Task` could be cancelled, but nothing downstream ever looked at
`Task.isCancelled`, so the child `HandBrakeCLI`/`makemkvcon` process kept
running regardless. `JobController` said so explicitly in its own header
comment ("There is intentionally no `cancel()`").

A second, sharper problem surfaced in the refresh, found by reading Joe's
capture C5 (`HandBrakeFailureClassifier.swift:201-213`,
`Fixtures/handbrake/failure-encode-canceled-term-hb1.11.2-exit143.log`):
`SIGTERM` kills HandBrakeCLI with **no output at all**. An unclassified
`exit 143` is `.toolExited`, which `FallbackPolicy.isDiscShaped` already
treats as disc-shaped — so naively wiring `Task.cancel()` through to
`Process.terminate()` would have made a plain user cancel look exactly
like a bad disc and trigger the MakeMKV fallback.

## Fix

**`ProcessRunner.swift`.** `run(...)` is now wrapped in
`withTaskCancellationHandler`. A new `nonisolated final class
RunCancellation: @unchecked Sendable` (the one genuinely off-actor type
this ticket adds, mirroring `RunCompletionGate`/`WatchdogState`) holds the
cancellation flag and the attached `Process` behind an `NSLock`.
`onCancel` — which Swift may invoke on an arbitrary thread, possibly
concurrently with `run`'s own setup — only records the flag and, if a
process is already attached and running, sends `SIGTERM` (never `SIGINT`,
per C5; never `SIGKILL`, so a partial `.mp4` is never mistaken for
finished output). **It never resumes the continuation itself** —
resumption stays exclusively with `RunCompletionGate`
(`markProcessDone`/`markReaderDone`), so there is still exactly one resume
by construction. `run` itself handles the two edges `onCancel` can't:
cancelled-before-launch (skip `process.run()` entirely and resolve through
`gate.forceExpire(with:)` — the same single resume path) and
cancelled-during-launch (re-check right after `process.run()` returns and
terminate if the flag raced in). `ProcessRunner.Termination` gained `var
cancelled: Bool = false`, read in `terminationHandler` and carried through
`armGrace`'s synthetic termination.

**`HandBrakeFailureClassifier.classify`** gained a Tier −1 check —
`if input.termination.cancelled { return .cancelled }` — before the
existing timeout tier and before any exit-code/text classification, so a
`SIGTERM`-with-no-output cancel can never be read as a disc failure.
Pinned against the real exit-143 fixture.

**`MakeMKVRipper.runMakeMKV`** now returns `cancelled` alongside
`exitStatus`/`lines`; `rip(...)` checks it at both the `info` scan and the
`mkv` rip step, before computing `failureReason(exitStatus:messageCodes:)`,
and returns `.rip`-stage `.cancelled` directly rather than letting a
cancelled exit code fall through to the generic classifier. **`DiscScanner
.Failure`** gained a `.cancelled` case for the same reason (structural
symmetry with the shared `ProcessRunner`) even though nothing in this pass
wires a cancel button to a running scan — `JobController.startScan` still
launches its own untracked `Task`, unchanged; see Gotchas.

**`DVDPipeline.run()`** checks `Task.isCancelled` at three boundaries —
the gaps between subprocess calls, where nothing is suspended inside
`ProcessRunner.run` for its own cancellation handling to catch: before
creating the job's encode directory, before attempting the MakeMKV
fallback (belt and suspenders with `MakeMKVRipper.rip`'s own check — this
is what stops a cancel that arrives after `FallbackPolicy` already decided
`.attempt` from ever creating a rip job directory), and after a successful
encode but before the Plex move. Each reports `JobFailure(stage: .encode,
reason: .cancelled)`, the same shape a directory-creation failure at the
first boundary already used, so `WorkingFiles.disposition`'s existing
`.encode`-stage rule (`.removeJobDirectory`) disposes of the job's working
directory with no new disposal logic. **Never checked inside
`PlexOrganizer.move`** — #0012's stage-then-replace must finish once
started, which is exactly why `organizing` has no outgoing `cancelled`
edge in #0041's transition table.

The **extras loop** (`for item in extras.items`) is now a labeled
`extrasLoop:` loop. It checks `Task.isCancelled` before starting each
extra and stops (logging one line, not one per remaining extra) rather
than continuing; the currently-running extra's own `EncodeController
.encode` call reports `.cancelled` through the classifier once its process
is actually killed, and that specific case also stops the loop instead of
falling through to the next extra. Per the orchestrator's decision on the
#0046 handoff: the feature is already filed in Plex, so the job still ends
`.succeeded` — `extras → succeeded` was already a legal edge in #0041's
`JobPhase.allowedTransitions` (added by the #0041 review for the ordinary
all-extras-succeeded case), so no new transition-table edge was needed;
there remains no `extras → cancelled` edge.

**`DVDPipeline.runFallback`**'s two failure branches (a cancelled rip, a
cancelled fallback re-encode) now check whether the underlying failure's
`reason == .cancelled` and, if so, return a *combined* `JobFailure` whose
**top-level** `reason` is `.cancelled` — not masked behind
`primaryFailure.reason` the way every other fallback failure is. This
matters structurally: `JobState.finishing(with:)` reads the top-level
`JobOutcome`'s failure reason to pick the terminal `JobPhase`
(`terminalPhase(for:)`), so without this a cancel that landed while the
fallback was already running would have terminated the job `.failed`
instead of `.cancelled`. The `.fallback` field still carries the real
stage/reason detail for the log and the reliability record.

**`JobController.cancel(id: JobID) -> Bool`** is the new public entry
point (status-menu action). It delegates the decision to a new pure
`Changeover/Jobs/CancelPolicy.swift` (mirroring `EjectPolicy`'s shape):
refuses — logging a line, never touching `task` — unless `id` matches
`current.id` and the phase is neither `.organizing` nor terminal. On
`.cancel` it only calls `task?.cancel()`; it does **not** touch
`current`/`history`/`sleepAssertion` itself. The job ends exactly the way
every job does, through the existing `finish(_:)`, once the runner's
`await` actually returns a `.cancelled`-reasoned outcome — so history,
the unconditional `sleepAssertion.end()`, and `JobNotifier.notify` (which
already fires for every `JobOutcome`, unconditionally, after `finish`) are
all untouched by this ticket and correctly cover the cancel case for
free. A repeated cancel on a still-running job is harmless (`Task.cancel()`
is idempotent); a repeated cancel after the job has finished is refused,
not silently ignored (`current` is `nil` by then). `StatusMenuView` gained
a "Cancel Job" row, gated by the same `CancelPolicy.decide` the controller
re-checks, following `EjectPolicy`'s existing pattern exactly. The stale
"there is intentionally no `cancel()`" paragraph in `JobController`'s
header comment is replaced.

**Decisions made (user AFK, delegated):**

- **The known gap from the #0045 review — an unmount that succeeds with an
  eject that fails leaves a dead mount path live — is not fixed here.**
  It needs its own small design (whether `ejectDisc()`'s failure path
  should now clear `insertedDisc` itself, now that a real cancel exists to
  interrupt whatever else might be touching the disc) and this pass's
  scope was already large. Recorded precisely below for a follow-up rather
  than folded in as an afterthought.
- **No metadata-window Cancel affordance was added**, only the status-menu
  row. The issue's scope says "a UI action in the status menu and/or the
  metadata window" — one satisfies it, and `MetadataEntryView` already
  reads `jobs`/`jobs.currentJobState` from the environment, so adding a
  second entry point there is a small, low-risk follow-up if wanted.
- **`DiscScanner.Failure.cancelled` is added but not reachable in
  production.** `JobController.startScan` launches its own untracked
  `Task` (unchanged, and explicitly documented as such in its own doc
  comment); `cancel(id:)` only ever cancels the current *job*'s `Task`.
  Added for structural symmetry with the shared `ProcessRunner` and so a
  future scan-cancel ticket doesn't have to revisit this file, not because
  anything in this pass exercises it.
- **No `MakeMKVRipper`-specific cancellation test was written.** Direct
  cancellation of `MakeMKVRipper.rip(...)` is awkward to test in isolation
  (its `discMountPath` goes through `statfs`, not a stub-friendly seam),
  and the plan's own Tests section doesn't list one. The behaviour is
  covered indirectly: `ProcessRunnerTests` proves `ProcessRunner` sets
  `cancelled` correctly (what `runMakeMKV` forwards verbatim), and the
  `DVDPipelineCancellationTests`/falsification below proves the
  boundary-2 check keeps a cancel from ever reaching `MakeMKVRipper` in
  the first place. The falsification that disabled *both* guards together
  (see `## Verification`) did exercise `MakeMKVRipper`'s own cancelled
  check indirectly — it correctly reported `.cancelled` for the rip that
  did start — which is the closest this pass comes to a direct proof.

## Long Description

"A failed job does not stall the queue behind it" is a Phase 3 exit criterion (`Roadmap.md:156`). There are exactly four ways a queue stalls, and each needs its own defence:

1. **Lane token leak.** The rip or encode `Task` exits without clearing `ripTask` / `encodeTask`. [#0044](0044.md)'s `defer` handles the ordinary paths; this ticket proves it holds on the failure, cancellation and thrown-error paths too.
2. **Head-of-line blocking.** The scheduler picks `jobs.first` instead of `first(where: stage == .queued)`. Also [#0044](0044.md)'s design, also asserted here.
3. **A job stuck in a non-terminal stage forever.** A `makemkvcon` that hangs on a scratched disc never terminates, so `terminationHandler` (`Changeover/RipController.swift:44`) never fires, the continuation never resumes, and the lane is held indefinitely. The answer is a user-driven cancel that actually kills the process.
4. **Cancellation that does not cancel.** Both controllers use `withCheckedContinuation` (`Changeover/RipController.swift:14`, `Changeover/EncodeController.swift:15`) with no cancellation handling at all. `Task.cancel()` on the scheduler's task sets a flag nobody reads; `makemkvcon` keeps running, the continuation is still outstanding, and the job is now "cancelled" in the UI while a subprocess quietly continues writing to the working directory.

Point 4 is the substantive code change in this ticket and it has a sharp edge: `withCheckedContinuation` traps at runtime if resumed twice. A cancellation handler that resumes, racing a `terminationHandler` that also resumes, is a crash, not a bug report.

## Steps to reproduce

1. Start a rip against a disc that `makemkvcon` cannot read. Watch it log a non-zero exit status (`Changeover/RipController.swift:51`) and then nothing.
2. Try to cancel a running rip from anywhere in the UI.
3. Inspect the app afterwards for any record that the job failed and why.

## Expected behavior

A failing stage puts its job into `.failed` with a specific `JobFailure`, releases its lane token, and the scheduler immediately starts the next eligible job. A running job can be cancelled from the queue view; the underlying `makemkvcon` or `HandBrakeCLI` process is terminated, the partial output in that job's working directory is cleaned up, the job becomes `.cancelled`, and the lane is released. A cancel while a job is `queued` never launches a process at all.

## Actual behavior

`DVDPipeline.run()` logs `"✗ Ripping failed. Aborting."` and returns (`:32-34`); `MetadataEntryView` sets `isProcessing = false` (`:153`) and that is the entire failure handling in the app. There is no cancel affordance anywhere — no button, no method, no `Task` handle retained (`:148-154` discards it). A hung rip is unrecoverable without quitting.

### Cancellable processes

Both controllers get the same treatment. Sketch for `RipController.rip`:

```swift
let box = ProcessBox()                        // holds the Process, plus a resumed flag
return await withTaskCancellationHandler {
    await withCheckedContinuation { continuation in
        box.adopt(continuation)               // stores it; resume goes through the box
        // … existing setup, Changeover/RipController.swift:17-62, unchanged …
    }
} onCancel: {
    box.terminate()                           // process.terminate(); SIGTERM
}
```

`ProcessBox` is a small `final class` with an `NSLock` guarding a `resumed: Bool` and the `Process?`. **Every** resume — the success path (`:48`), the non-zero-exit path (`:52`), the launch-failure path (`:61`) and the new cancellation path — goes through `box.resumeOnce(_:)`, which resumes only if `resumed` is still false. This is the double-resume defence, and it is why the flag needs a lock: `terminationHandler` runs on a background thread while the cancellation handler runs on whichever thread cancelled.

`ProcessBox` is the one genuinely `nonisolated` addition in this ticket. It is `nonisolated` because `withTaskCancellationHandler`'s `onCancel` is a `@Sendable` closure that can run on any thread — this is the "explicit `nonisolated` only where a type genuinely must leave the main actor" case that `Plan.md` allows, and the justification belongs in a comment next to it so the next reader does not "clean it up".

`process.terminate()` sends `SIGTERM`. `makemkvcon` and `HandBrakeCLI` both handle it and exit; neither leaves the drive wedged. Do not escalate to `SIGKILL` on a timer — a `SIGKILL`ed `HandBrakeCLI` can leave a partial `.mp4` that a later run mistakes for finished output. Partial-file cleanup is explicit instead: on cancel or failure, delete the job's working directory (per-job, from [#0001](0001.md)), which removes any partial `.mkv` or `.mp4` in one step.

### Failure classification

`RipController` currently logs a bare exit status (`:51`). Map the actual failure to a `JobFailure` case ([#0041](0041.md)) instead:

- launch failure with `NSFileNoSuchFileError` for `makemkvconPath` / `handbrakePath` → `.toolMissing(path:)`;
- `makemkvcon` output containing the expired-key message → `.makemkvKeyExpired` (a recurring real-world failure, `RemoteControl.md:459-461`);
- `ENOSPC` / no-space text, or a destination that fails a writability probe → `.diskFull` / `.destinationUnwritable(path:)`;
- anything else → `.processExited(stage:status:)`.

Phase 1 ([#0001](0001.md)) does the detection work; this ticket's contribution is attaching the result to the job and releasing the lane, rather than printing it.

### Scheduler cancel

```swift
func cancel(id: JobID) {
    guard let job = queue?.job(id: id) else { return }
    switch job.state.stage {
    case .queued:                         job.transition(to: .cancelled); pump()
    case .ripping:    ripTask?.cancel()   // defer in the Task clears the token and pumps
    case .awaitingEncode:                 job.transition(to: .cancelled); pump()
    case .encoding:   encodeTask?.cancel()
    case .organizing: break               // FileManager.moveItem; too short to interrupt safely
    case .done, .failed, .cancelled: break
    }
}
```

The `.ripping` and `.encoding` cases must check that the task in that lane actually belongs to the job being cancelled — store the owning `JobID` next to each `Task` handle. Cancelling job 3 must never kill job 2's encode, and after [#0044](0044.md) the two lanes hold different jobs by design, so this is not hypothetical.

A cancelled rip still ejects the disc, for the same reason a failed one does ([#0045](0045.md)).

### Risks

- **Double resume traps.** This is the one thing in this ticket that turns a bug into a crash. The `resumeOnce` discipline is not optional and deserves a comment saying why.
- **`terminate()` on an already-exited process.** `Process.terminate()` on a process that has already reported termination raises an Objective-C exception on some paths. Guard on `isRunning` inside the lock and treat the race as benign.
- **Cancellation propagates into child tasks.** The per-line log hops are `Task { @MainActor in log(trimmed) }` (`Changeover/RipController.swift:38`) — unstructured, so they are not cancelled with the parent, which is correct here: the last few lines before termination are exactly the ones worth reading.
- **Don't make cancel a state the UI can spam.** Two cancels in flight for the same job must be idempotent; the transition table ([#0041](0041.md)) already rejects the second, so route every cancel through `transition(to:)` rather than assigning stage directly.
