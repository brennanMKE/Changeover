# 0008 — Nothing is checked before a rip starts, so a misconfigured setup fails minutes in

| | |
|---|---|
| **Status** | open |
| **Module** | Preflight / DVDPipeline / SettingsView |
| **Platform** | macOS |
| **First seen** | 2026-09-11 |

## Description

Start Ripping launches `makemkvcon` with whatever string is in `settings.makemkvconPath` (`DVDPipeline.swift:20`, `:27-30`) and a missing binary is only discovered when `process.run()` throws (`RipController.swift:56-62`). A wrong `HandBrakeCLI` path is not discovered until after the rip — 40 minutes later. Destination writability and free disk space are never checked at all.

## Long Description

`AppSettings.isConfigured` (`AppSettings.swift:33`) only tests that `plexMediaRoot` and `tmdbAPIKey` are non-empty. It says nothing about whether the two CLI tools exist, whether the Plex Movies folder can be written to, or whether there is room on the volume for an 8 GB rip plus a 2 GB encode.

`SettingsView.detect(binding:)` (`SettingsView.swift:118-127`) probes `/opt/homebrew/bin` and `/usr/local/bin` and, when neither exists, **silently does nothing** — the user clicks "Detect", sees no change, and has no way to tell whether the current path is valid. The defaults at `AppSettings.swift:14-15` are plausible-looking Homebrew paths that may point at nothing.

The cost of failing late is asymmetric: a bad `makemkvcon` path fails immediately and is merely annoying; a bad `HandBrakeCLI` path costs a full rip, and with [#0004](0004.md)'s cleanup gated on success, strands the `.mkv` too.

## Steps to reproduce

1. Open Settings and change the HandBrakeCLI path to `/opt/homebrew/bin/HandBrakeCLI-typo`. Save.
2. Insert a disc, search, select a movie, Start Ripping.
3. The rip runs to completion — tens of minutes.
4. Only then does the log print `"✗ Failed to launch HandBrakeCLI: …"` followed by `"✗ Encoding failed. Aborting."`
5. The intermediate `.mkv` is stranded and the disc is still in the drive.

## Expected behavior

The job refuses to start and names the exact problem before the disc is touched: which tool is missing, which path is unwritable, how much space is free versus needed. Settings shows a live valid/invalid state next to each path rather than a Detect button that quietly fails.

## Actual behavior

No checks run at any point. Problems surface as a launch failure at whichever stage happens to hit them first, expressed as `error.localizedDescription` from `Process.run()`.

## Notes

Almost entirely unit-testable and needs no disc — the checks are pure functions over a path snapshot. Write and run real tests: a nonexistent tool path, a path that exists but is not executable, a destination directory with write permission removed, a free-space figure below threshold. The negative cases matter as much as the positive ones.

Manual verification is limited to confirming the Start Ripping button disables with the right message and that Settings shows the per-tool state — the app must be run, but a physical disc is not required. Say so in `## Verification`.

## Plan

### New file: `Changeover/Preflight.swift`

```swift
struct PreflightInput: Sendable {        // plain snapshot, not AppSettings
    let makemkvconPath: String
    let handbrakePath: String
    let plexMoviesPath: String
    let workingRipPath: String
    let workingEncodePath: String
}

enum Preflight {
    nonisolated static func check(_ input: PreflightInput) -> [JobFailure]
}
```

Take a **snapshot value**, not the `@Observable AppSettings` object. `AppSettings` is MainActor-isolated under `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`, and `DVDPipeline.run()` already establishes exactly this pattern — it copies the five path strings on MainActor before entering nonisolated code (`DVDPipeline.swift:19-24`). Follow it. `Preflight.check` is `nonisolated` because it does file I/O and must be callable from tests without a MainActor hop.

### Checks

1. **`makemkvconPath` and `handbrakePath`** — `FileManager.isExecutableFile(atPath:)`, not just `fileExists`. A path pointing at a directory or a non-executable file must fail. → `.toolMissing(path:)` at `JobStage.preflight`.
2. **Plex Movies destination** — exists or can be created, and is writable. `isWritableFile(atPath:)` disagrees with ACLs on network shares and some external volumes; prefer an actual probe — create a uniquely named temp file under the destination and delete it. → `.destinationUnwritable(path:)`.
3. **Working roots** — same probe, since [#0003](0003.md) will create per-job children under them.
4. **Free space** — `URL.resourceValues(forKeys: [.volumeAvailableCapacityForImportantUsageKey])` on the volume holding `plexMediaRoot`. Compare against a named constant. → `.diskFull`.

### Where it runs

- From `JobController.start` ([#0002](0002.md)) **before** creating the `Task`. A non-empty result means the job never starts and the outcome is `.failed` with `stage == .preflight`.
- Additionally as a live state in the UI: `MetadataEntryView.actionBar` (`MetadataEntryView.swift:123-133`) disables Start Ripping with the reason visible, rather than letting the user press a button that will refuse.
- And in `SettingsView`: replace the silent `detect(binding:)` behavior (lines 118-127) with a per-tool indicator — valid / not found / not executable — next to each `cliRow` (lines 92-101). When Detect finds nothing, say so instead of doing nothing. `SettingsView` already uses `@Bindable var settings` (line 5), which is the right shape; keep it.

### Risks

- **The free-space threshold is a guess.** Without title sizes there is no honest number. Phase 2's `DiscScanner` ([#0020](0020.md)) provides real sizes; until then use a conservative named constant (a DVD main feature is 4-8 GB, plus the encode) and treat an *unknown* capacity as a pass, not a failure — failing a job because a network volume did not report capacity would be worse than the bug being fixed.
- **Do not fold preflight into `isConfigured`** (`AppSettings.swift:33`). That property answers "has the user ever set this up" and drives first-launch behavior (`AppDelegate.swift:23-25`) and the popover's status dot (`StatusMenuView.swift:16-20`). Preflight is a per-job question and re-running filesystem probes on every SwiftUI body evaluation would be a performance bug.
- **Probing by writing a temp file has a cost** on a spun-down external drive. Run the checks once per job start, not per view update; cache the result on `JobController`.
- Do not extend preflight into TMDB key validation here — `Roadmap.md` places "verify the TMDB key at entry" in Phase 6 ([#0100](0100.md)).
