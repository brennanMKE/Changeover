# 0008 — Nothing is checked before a rip starts, so a misconfigured setup fails minutes in

| | |
|---|---|
| **Status** | open |
| **Phase** | 1 — Trustworthy single-disc rip |
| **Module** | Preflight / DVDPipeline / SettingsView |
| **Platform** | macOS |
| **First seen** | 2026-09-11 |

## Description

Start Ripping launches `makemkvcon` with whatever string is in `settings.makemkvconPath` (`DVDPipeline.swift:20`, `:27-30`) and a missing binary is only discovered when `process.run()` throws (`RipController.swift:56-62`). A wrong `HandBrakeCLI` path is not discovered until after the rip — 40 minutes later. Destination writability and free disk space are never checked at all.

## Long Description

`AppSettings.isConfigured` (`AppSettings.swift:33`) only tests that `plexMediaRoot` and `tmdbAPIKey` are non-empty. It says nothing about whether the two CLI tools exist, whether the Plex Movies folder can be written to, or whether there is room on the volume for an 8 GB rip plus a 2 GB encode.

`SettingsView.detect(binding:)` (`SettingsView.swift:118-127`) probes `/opt/homebrew/bin` and `/usr/local/bin` and, when neither exists, **silently does nothing** — the user clicks "Detect", sees no change, and has no way to tell whether the current path is valid. The defaults at `AppSettings.swift:14-15` are plausible-looking Homebrew paths that may point at nothing.

The cost of failing late is asymmetric: a bad `makemkvcon` path fails immediately and is merely annoying; a bad `HandBrakeCLI` path costs a full rip, and with [#0004](0004.md)'s cleanup gated on success, strands the `.mkv` too.

## Steps to reproduce

1. Open Settings and change the HandBrakeCLI path to `/opt/homebrew/bin/HandBrakeCLI-typo`. Save.
2. Insert a disc, search, select a movie, Start Ripping.
3. The rip runs to completion — tens of minutes.
4. Only then does the log print `"✗ Failed to launch HandBrakeCLI: …"` followed by `"✗ Encoding failed. Aborting."`
5. The intermediate `.mkv` is stranded and the disc is still in the drive.

## Expected behavior

The job refuses to start and names the exact problem before the disc is touched: which tool is missing, which path is unwritable, how much space is free versus needed. Settings shows a live valid/invalid state next to each path rather than a Detect button that quietly fails.

## Actual behavior

No checks run at any point. Problems surface as a launch failure at whichever stage happens to hit them first, expressed as `error.localizedDescription` from `Process.run()`.

## Notes

Almost entirely unit-testable and needs no disc — the checks are pure functions over a path snapshot. Write and run real tests: a nonexistent tool path, a path that exists but is not executable, a destination directory with write permission removed, a free-space figure below threshold. The negative cases matter as much as the positive ones.

Manual verification is limited to confirming the Start Ripping button disables with the right message and that Settings shows the per-tool state — the app must be run, but a physical disc is not required. Say so in `## Verification`.

### 0. Where things stand

- **HandBrakeCLI is the whole job.** `DVDPipeline.run()` (`DVDPipeline.swift:56`)
  calls `EncodeController.encode` straight on the disc (`:109`). `makemkvcon`
  runs only inside `runFallback` (`:214`), after `FallbackPolicy.decide`
  (`FallbackPolicy.swift:76`) returns `.attempt`.
- **Two checks already exist, in `JobController.start`** (`JobController.swift:94-119`):
  it refuses while a job is running, and it refuses with no disc mounted
  (`:100-103`, pinned by `JobControllerTests.startRefusesWithNoDiscMounted`,
  `:313`). Both are synchronous and in memory. They stay where they are.
- **Nothing checks the HandBrake path before launch.** A bad path surfaces as
  `.toolMissing` or `.toolLaunchFailed` from `FailureReason.launchFailure`
  (`JobOutcome.swift:56-60`), at `.encode`, a second or two into the job. That
  failure is not disc-shaped, so no fallback runs. **So the filing's
  "40 minutes wasted" case is already gone.** What remains is:
  1. A HandBrake that launches but can't run Changeover's vector: no x265, or a
     renamed flag. Today that is `.toolExited`, which *is* disc-shaped
     (`FallbackPolicy.swift:35`), so the job runs a 5–8 GB MakeMKV rip and a
     second encode that fails the same way. #0009 fixes this only if its
     `unrecognizedOption`/`invalidEncoder` rows ship, and they ship only if
     real captures confirm them (0009 §2.3).
  2. A destination or free-space problem that surfaces as a bare reason, with
     nothing that tells the user which path or how much space.
  3. Settings says nothing about whether any path is valid.
- **Directories are created at the moment of use.** `EncodeController.encode`
  creates the output's parent (`EncodeController.swift:146-158`, #0014 G2).
  `PlexOrganizer.move` creates `Movies/<folder>` (`PlexOrganizer.swift`,
  `createDirectory` at the top of `move`). `MakeMKVRipper.rip` creates
  `workingRipPath` and the job directory (`MakeMKVRipper.swift:56-69`). Preflight
  adds a probe; it does not replace any of these ([#0003](0003.md) note, #0001
  review O4).
- **Free space is already guarded on one path.** `MakeMKVRipper.rip` refuses
  below `title size + 1 GiB` using the real title size (`:117-124`). The
  guard comment says "an unknown capacity counts as a pass, matching #0008's
  rule". Keep that rule.
- **`AppSettings.isConfigured`** (`AppSettings.swift:35`) is
  `!plexMediaRoot.isEmpty && !tmdbAPIKey.isEmpty`. It never touched a CLI path.
  It drives the first-launch Settings window (`AppDelegate.swift:30`), the
  "Open…" row's `.disabled` and the popover's dot and text
  (`StatusMenuView.swift`, `statusText`/`statusColor`).
- **`SettingsView.detect(binding:)`** (`SettingsView.swift:122-131`) has two
  bugs, one of them not in any earlier document:
  1. When no candidate exists it does nothing, as filed.
  2. **New finding:** it searches for
     `binding.wrappedValue.lastPathComponent`, not the tool's name. With an
     **empty field** that name is `""`, the candidate `"/opt/homebrew/bin/"` is a
     directory, `fileExists` is `true`, and Detect writes the *directory* into the
     path. With a typo'd path it searches for the typo.
- **`FileManager.isExecutableFile(atPath:)` returns `true` for a directory**
  that has its search bit set. That includes an `.app` bundle such as
  `/Applications/HandBrake.app`, which is the GUI-cask mistake #0105 describes.
  The filing plan's "use `isExecutableFile`, not `fileExists`" is therefore not
  enough on its own (§2, P1). `DVDPipeline`'s `isExecutable` closure for the
  fallback (`DVDPipeline.swift:129`) has the same gap.
- **`lsdvd`** is looked up at `LSDVDIdentity.defaultCandidatePaths`
  (`LSDVDIdentity.swift:18`) during disc insertion. It plays no part in a job.

### 2. The checks, in order

The core is new file `Changeover/Preflight.swift`: `nonisolated` and `async`,
with every side effect behind a probe closure so the decision logic is
unit-tested with fakes. The same pattern as `FallbackPolicy.decide`'s
closures, and as `OpticalDiscClassifier.evaluateAppearance`.

**All blocking checks are evaluated, except those that depend on an earlier
failure.** The report carries every blocker in order, and the job fails with the
**first**. That way a user with two problems learns both at once instead of
fixing one and starting the disc again. The checks that are skipped:
- P2 is skipped unless P1 passed, because there is nothing to launch.
- P4–P6 are skipped when P3 fails, so nothing is created under a root that
  isn't there.

| # | Check | How | Result |
|---|---|---|---|
| — | *(existing, `JobController.start`)* no job running; a disc is mounted | in memory | refuse, log line (unchanged) |
| **P1** | `handbrakePath` is a runnable file | `probes.fileKind(path)`: `.missing` / `.directory` / `.file(executable:)`, using `fileExists(atPath:isDirectory:)` plus `isExecutableFile`. It follows symlinks, so Homebrew's `/opt/homebrew/bin/HandBrakeCLI` link resolves. | empty, missing, directory or not executable → **block** `.toolMissing(path:)`. A path whose standardized, symlink-resolved form contains `.app/Contents/` → **block** `.toolIncompatible(detail:)` (see below); P2 is not launched, which also avoids opening a GUI app. |
| **P2** | this HandBrakeCLI accepts the vector | `HandBrakeCLI --help`, time-boxed to 5 s; see §4 | `.incompatible(missing:)` → **block** `.toolIncompatible(detail:)`, only while `Preflight.capabilityCheckBlocks` is `true` (§4.3); otherwise warn. `.unrecognised` / timed out → **warn** `.handbrakeUnverified`. Launch threw → **block** `.launchFailure(toolPath:error:)`, the same mapping the encode would produce. |
| **P3** | `plexMediaRoot` exists and is a directory | `probes.fileKind` | no → **block** `.destinationUnwritable(path: plexMediaRoot)`. **Never create the root.** An unmounted `/Volumes/MediaSSD/…` must fail here, with the "is the drive connected" wording, not get recreated on the boot disk. |
| **P4** | `plexMoviesPath` can be created and written | `probes.probeWritable(path)`: `createDirectory(withIntermediateDirectories: true)`, then create a uniquely named `.changeover-preflight-<UUID>` file with `Data().write(to:options: .withoutOverwriting)`, then remove it. This is an actual write, not `isWritableFile`, which disagrees with ACLs and some external or network volumes (filing plan). | failure → **block** `.destinationUnwritable(path: plexMoviesPath)`. If only the removal fails, pass and log `⚠︎`. |
| **P5** | `workingEncodePath` can be created and written | same probe | failure → **block** `.destinationUnwritable(path: workingEncodePath)` |
| **P6** | free space | `probes.availableCapacity(path)`: `volumeAvailableCapacityForImportantUsageKey`, the same read as `MakeMKVRipper.availableCapacity` (`:407-411`), at **both** `workingEncodePath` and `plexMoviesPath` (PlexOrganizer stages on the destination's volume; on one volume that is simply two equal reads) | any value `< Preflight.minimumFreeBytes` (2 GiB) → **block** `.diskFull`. `nil` → pass and **warn** `.capacityUnknown(path:)`. |
| **P7** | `makemkvconPath` | `probes.fileKind`, **never launched** | not a runnable file, or empty → **warn** `.fallbackUnavailable(makemkvconPath:)`. **Never a blocker in any state.** |
| **P8** | room for a fallback rip | only when P7 found a runnable `makemkvcon`, and P6 read a value | `< Preflight.fallbackComfortBytes` (10 GiB) → **warn** `.fallbackMayLackSpace(availableBytes:)` |

`lsdvd` is **not** in the job preflight, because a job never uses it. It appears
in Settings only, as information (§6.2).

**`workingRipPath` is deliberately not probed.** It is fallback-only
(`AppSettings.swift:26-29`). Blocking a HandBrake job on it would make the
optional tool a blocker. #0015 already reports it inside `FallbackAttempt`
when it matters, and `MakeMKVFallbackTests` has a test that plants a plain file
at `Working/ripping` (`MakeMKVFallbackTests.swift:556-558`) and expects the
primary encode to run. That test must keep passing unmodified.

**Why P4/P5 may create folders.** Creation at the moment of use (#0003, #0014
G2) is moved a second earlier, under a root P3 has proved exists. Both folders
would be created by this job anyway. The probe file is a dotfile (Plex ignores
dotfiles) and lives for milliseconds.

#### Types

```swift
nonisolated struct PreflightInput: Sendable, Equatable {   // plain snapshot, captured on MainActor
    let handbrakePath:     String
    let makemkvconPath:    String
    let plexMediaRoot:     String
    let plexMoviesPath:    String
    let workingEncodePath: String
}

nonisolated enum FileKind: Sendable, Equatable { case missing, directory, file(executable: Bool) }

nonisolated enum ToolState: Sendable, Equatable {
    case ready
    case notSet
    case notFound(path: String)
    case notExecutable(path: String)       // a directory, or no x bit
    case insideAppBundle(path: String)     // HandBrake only
    case incompatible(missing: [String])   // HandBrake only
    case unverified(String)                // HandBrake only: probe inconclusive
    case launchFailed(String)              // HandBrake only
}

nonisolated enum PreflightWarning: Sendable, Equatable {
    case handbrakeUnverified(String)
    case fallbackUnavailable(makemkvconPath: String)
    case fallbackMayLackSpace(availableBytes: Int64)
    case capacityUnknown(path: String)
    case probeFileNotRemoved(path: String)
}

nonisolated struct PreflightReport: Sendable, Equatable {
    let blockers:   [FailureReason]        // ordered P1…P6; empty = go
    let warnings:   [PreflightWarning]
    let handbrake:  ToolState
    let makemkvcon: ToolState
    var failure: JobFailure? { blockers.first.map { JobFailure(stage: .preflight, reason: $0) } }
}

nonisolated struct PreflightProbes: Sendable {
    var fileKind:          @Sendable (String) -> FileKind
    var handbrakeHelp:     @Sendable (String) async -> HelpProbe   // .lines([String]) | .timedOut | .launchFailed(String)
    var probeWritable:     @Sendable (String) -> WriteProbe        // .writable | .writableProbeNotRemoved | .unwritable
    var availableCapacity: @Sendable (String) -> Int64?
    static let live: PreflightProbes
}

enum Preflight {
    nonisolated static let minimumFreeBytes:      Int64 = 2 * 1024 * 1024 * 1024
    nonisolated static let fallbackComfortBytes:  Int64 = 10 * 1024 * 1024 * 1024
    nonisolated static let helpTimeout:           TimeInterval = 5
    nonisolated static let capabilityCheckBlocks: Bool = true   // §4.3

    nonisolated static func check(_ input: PreflightInput, probes: PreflightProbes = .live) async -> PreflightReport
    nonisolated static func handbrakeState(path: String, probes: PreflightProbes = .live) async -> ToolState  // P1+P2; Settings uses it
    nonisolated static func optionalToolState(path: String, probes: PreflightProbes = .live) -> ToolState    // P7; never launches
    nonisolated static func requiredHelpTokens() -> [String]                                               // §4.1
    nonisolated static func capability(helpLines: [String]) -> HelpVerdict                                 // §4.2, pure
}
```

`ToolState` → blocker mapping, for HandBrake only:
- `notSet` → `.toolMissing(path: "")`
- `notFound(p)` → `.toolMissing(path: p)`
- `notExecutable(p)` → `.toolMissing(path: p)`. The case's doc comment already
  says "not present (or not executable)".
- `insideAppBundle(p)` → `.toolIncompatible(detail: "\(p) is inside an app bundle")`
- `incompatible(m)` → `.toolIncompatible(detail: m.joined(separator: ", "))`
- `launchFailed(msg)` → `.toolLaunchFailed(msg)`
- `unverified` → no blocker; add a warning
- `ready` → nothing

Put `ToolLocator` (§6.1) in the same file.

### 3. Where it runs, and what it costs

**Decision: the first step of `DVDPipeline.run()`, right after the
`── Starting:` log line and the MainActor prologue (`DVDPipeline.swift:57-67`).
Add `plexMediaRoot` to the prologue.**

```swift
let report = await Preflight.check(PreflightInput(…captured strings…))
for warning in report.warnings { log(FailurePresenter.line(for: warning)) }
if let failure = report.failure {
    for extra in report.blockers.dropFirst() {
        log("✗ Also: " + FailurePresenter.headline(for: extra, stage: .preflight))
    }
    return finish(.failed(failure))      // #0009's finish(_:) logs headline + details
}
log("✓ Preflight passed")
```

Why here and not in `JobController.start`:

1. **The check is async.** P2 launches a process, and P4/P5 write to disk. A
   spun-down external drive can take seconds to answer. `start` is synchronous,
   runs on MainActor and returns a `Bool`, so running the checks there either
   blocks the UI or changes `start`'s contract.
2. **The failure becomes a `JobOutcome`.** Through `finish(_:)` a preflight
   failure gets #0009's presenter lines in the log, `JobController.lastOutcome`
   (so #0009's `failureBanner` shows it with no extra wiring), a reliability
   record, and later #0006's notification. A refusal from `start` produces only
   a log line.
3. **`JobController.Runner` does not change**, so the twelve `JobControllerTests`
   stay untouched. They construct `AppSettings()`, whose real
   `/opt/homebrew/bin/HandBrakeCLI` does not exist on gordon. Checking
   `handbrakePath` inside `start` would break every one of them.
4. **The disc is still untouched.** Nothing has launched HandBrake yet.

Accepted cost: `isRunning` is `true` for the second preflight takes, and "Start
Ripping" is disabled for that time.

**The reliability record.** A preflight failure passes through `finish(_:)`,
which keeps #0015's invariant that no `return` in `run()` skips the record. The
record has `primary: {stage: "preflight", …}`, `decision: null`,
`producedBy: null`. A reliability analysis filters on `primary.stage`. Say so in
`DiscReliabilityLog.Record`'s doc comment.

**The fallback can never run.** Preflight returns before
`EncodeController.encode`, and `FallbackPolicy.decide` is never called.
`FallbackPolicy.isDiscShaped` also rejects any stage other than `.encode`
(`FallbackPolicy.swift:30`), already pinned at `.preflight` by #0015's test 1
(`MakeMKVFallbackTests.swift:106`).

**Cost.** Three `stat`s, two tiny write-and-delete probes, two capacity reads,
and one `HandBrakeCLI --help`. The help call is one process launch that prints
roughly 10–20 KB and exits without scanning anything. Budget under 1 s on a local
SSD. There is no automated timing assertion. Record the observed time in
`## Verification` if a manual run happens. **Nothing is cached.** A capability
cache keyed on path and mtime would save about 100 ms a job and add an
invalidation problem after `brew upgrade handbrake`.

**Also in `DVDPipeline`** (small, while here): change the fallback's
`isExecutable:` closure (`DVDPipeline.swift:129`) to
`{ Preflight.optionalToolState(path: $0) == .ready }`. A directory in
`makemkvconPath` then yields `.unavailable` instead of `.attempt` followed by a
launch failure inside the fallback. `FallbackPolicy` itself does not change.

**`isConfigured` does not change.** It is evaluated in SwiftUI bodies
(`StatusMenuView.statusText`/`statusColor`), where a `stat`, let alone a process
launch, has no place. It answers "has the user set this up", which drives first
launch. #0104 step 3 and #0105 step 5 plan to derive it from a Phase 6 setup
checklist; that is their decision to make, built on `Preflight.handbrakeState`
(§10). The filing plan and the re-triage both said to keep it, and this plan
agrees.

**`MetadataEntryView` does not change** beyond #0009's banner. The filing plan
wanted Start Ripping disabled live with a reason. A truthful live state needs
the async probe and would run every time the metadata window opens. The banner
shows the same message a second after pressing the button. See §11.

### 4. The HandBrake capability check (P2)

#### 4.1 What is required, and where it comes from

`requiredHelpTokens()` is **derived from the code, never listed by hand**:

```swift
let vectors = [EncodeController.arguments(source: "/x", title: .mainFeature, output: "/x.mp4"),
               EncodeController.arguments(source: "/x", title: .index(1),    output: "/x.mp4")]
// every element with the "--" prefix, de-duplicated in first-seen order,
// then Config.videoEncoder
```

Today that is `--input --main-feature --title --output --format --encoder
--encoder-preset --quality --aencoder --markers` plus `Config.videoEncoder`. When
a later ticket adds a flag to `arguments`, preflight checks it with no edit here.
Values other than the encoder (`slow`, `av_mp4`, `copy:aac,copy:ac3`) are
**not** checked:
- Presets are listed per encoder by `--encoder-preset-list`, not in `--help`.
- `slow` is too generic a token to prove anything.
- A second invocation doubles the cost for a case #0009's runtime classifier
  covers.

#### 4.2 Why `--help`, and how it is parsed

- **Not `--version`.** #0009 §7 suggested "a `HandBrakeCLI --version` probe".
  A version number doesn't say whether this build has x265 or accepts a flag.
  Turning it into a check needs a minimum-version table, which is the "too strict"
  risk in its purest form: every HandBrake release Changeover hasn't met would be
  a guess. `--help` answers the actual question directly. HandBrakeCLI's help lists
  every long option, and under `--encoder` it lists the video encoders **this
  build** provides, generated at run time. **That last claim comes from reading
  HandBrake's source and is unconfirmed on 1.11.2. Capture H1 confirms or kills
  it (§8).**
- **Run it through #0009's `ProcessRunner.run`** with
  `watchdog: .absolute(Preflight.helpTimeout)`. Collect lines in `onLine`, capped at
  2,000. stdout and stderr share one pipe, as in the app. **Ignore the exit
  status**, because whether `--help` exits 0 is unconfirmed (H1). `.success`
  with `timedOut` → `.timedOut`. `.failure(error)` → `.launchFailed`.
- **`capability(helpLines:)` is pure:**
  1. Tokenize every line on whitespace. Trim each token's trailing `,`, `;` and
     `:`. **Match whole tokens only.** So `x264/x265` does not count as `x265`,
     and `--encoder` is not satisfied by `--encoder-preset`.
  2. **Recognition gate.** The text is HandBrakeCLI help only if the tokens
     include both `--input` and `--output`, and at least 20 distinct `--`
     tokens. If not → `.unrecognised`. That covers a wrapper that swallows
     `--help`, a crash banner, the stub's two progress lines, empty output, or
     some other program at that path.
  3. If recognised: required tokens that are absent → `.incompatible(missing:)`
     in `requiredHelpTokens()` order. None absent → `.compatible`.
- **A missing x265 only blocks because the text is recognisably HandBrake's
  help.** An unrecognisable text never proves anything is absent.

#### 4.3 The asymmetry rule, applied to preflight

Preflight's expensive error is the reverse of #0009's. A wrong `.incompatible`
verdict **blocks every job on every disc** until the parser is fixed. A wrong
`.unrecognised` verdict costs what happens today: the encode runs, and #0009
classifies whatever goes wrong. So:

- `Preflight.capabilityCheckBlocks` ships `true` **only if** capture H1 exists as
  a fixture and test 6 passes. Test 6 requires two things of that real capture:
  it parses `.compatible` against the current vector, and removing the `x265`
  line or the `--encoder-preset` line from it makes it `.incompatible`.
- **If H1 can't be captured**, ship `capabilityCheckBlocks = false`. An
  `.incompatible` verdict then becomes the warning
  `.handbrakeUnverified("HandBrakeCLI's help doesn't list …")`, and
  `## Verification` says so. P1, P3–P8 and the app-bundle rule don't depend on
  H1 and block regardless.
- **No version check exists anywhere**, so no HandBrake release can trip one.

#### 4.4 How this avoids a pointless fallback

A HandBrakeCLI without x265, or one that renamed `--encoder-preset`, fails the job
at `.preflight` in about a second. Neither HandBrake nor MakeMKV touches the disc.
Without preflight, the same install fails at `.encode`. If #0009's
`unrecognizedOption`/`invalidEncoder` rows didn't ship (0009 §2.3: they ship only
with a capture), that failure is `.toolExited`, which is disc-shaped, so a
several-GB MakeMKV rip and a second doomed encode follow **on every disc**. The
two checks are complementary. Preflight knows what the help text promises;
#0009 knows what HandBrake actually said. Neither replaces the other.

### 5. The failure and how `FailurePresenter` words it

**No new `FailureReason` case.** Every blocker maps to an existing case or to
#0009's `.toolIncompatible(detail:)`:

| Blocker | Reason (stage `.preflight`) |
|---|---|
| P1 missing, not executable, or unset | `.toolMissing(path:)` |
| P1 app bundle, P2 incompatible | `.toolIncompatible(detail:)` |
| P2 launch threw | `.toolLaunchFailed(String)` |
| P3, P4, P5 | `.destinationUnwritable(path:)` |
| P6 | `.diskFull` |

Considered and rejected:
- **Giving `.diskFull` associated values** for the free and required bytes.
  Changing the case's payload is a wire change for #0060, and the log line

### 9. Risks

- **Preflight as a false blocker.** This is the risk that matters, and each
  check is shaped against it:
  - **Capability:** the recognition gate, blocking only on recognised text, no
    version check, and `capabilityCheckBlocks` gated on a real capture (§4.3).
    HandBrake reformatting its help degrades to a warning, which is today's
    behaviour.
  - **Unmounted volume:** P3 blocks, and should. The encode would fail at
    `createDirectory` a second later anyway. The wording says "is the drive
    connected".
  - **Slow or spun-down volume:** P4/P5 wait for the disk. They are nonisolated,
    so the UI isn't blocked, and the encode would wait for the same spin-up. There
    is no timeout, because a probe that times out on a slow but healthy drive
    would be the false blocker.
  - **Network volume that hangs:** the job sits at "── Starting" with no cancel
    (#0001 G7), exactly as the encode would. Recorded, not fixed.
  - **Capacity unknown** (some network and FUSE volumes): pass with a warning.
- **The 2 GiB threshold** blocks a short film that would have fitted in 1.5 GB.
  It is chosen as follows:
  - #0018 measured 991 MB for a 2 h 38 m feature at x265 RF 23, and 1,163 MB at
    x264.
  - 687 MB of that is passthrough audio, and audio scales with runtime, so a
    3½-hour feature lands around 1.3–1.5 GB.
  - 2 GiB covers that. It also stays clear of #0009's runtime rule (`.diskFull`
    below 256 MB after a non-zero exit), which catches a disk that fills
    *during* an encode. The two numbers answer different questions and don't
    conflict.
  - The fallback's 5–8 GB is **not** in the blocking threshold. That would make
    the optional tool a blocker. It's the P8 warning instead, and
    `MakeMKVRipper.rip` still refuses with the real title size (`:117-124`).
  - `volumeAvailableCapacityForImportantUsage` counts purgeable space, which
    reduces false blocks on an APFS boot volume.
- **Side effects in a "check".** P4/P5 create two folders under an existing root,
  and a crash between creating and deleting the probe file leaves a dotfile.
  Accepted, and bounded by §2.
- **TOCTOU.** Preflight passes, then the drive is unplugged or fills. #0009
  classifies it at run time. Preflight never claims a job *will* succeed.
- **Launching an arbitrary executable.** P2 runs whatever the user put in
  `handbrakePath` with `--help`, and the encode would run it anyway. The app-bundle
  rule stops a GUI app opening. #0105's risk (a) is covered by never probing
  anything outside the user's configured path and the fixed candidates.
- **Test-machine dependence.** Stub pipeline tests now need 2 GiB free (§8).
  Test 13 and the heredoc keep the stub in step with `arguments`.
- **Settings spawns processes while typing.** Mitigated by the 400 ms debounce
  and task cancellation. At worst there are a few short-lived `--help` processes.
- **#0006 may notify on a preflight failure** the user is sitting in front of.
  Note it in `## Fix` for #0006's implementer. Don't edit `0006.md`.

- **`handbrakePath` becomes a hard precondition.** Missing or non-executable means
  the job cannot start, with a message naming the path.
- **`makemkvconPath` becomes an optional probe.** Report its state — present,
  absent, not executable — as information, never as a blocker. A machine with no
  MakeMKV installed is a fully supported configuration ([#0015](0015.md)), and
  preflight must say so neutrally rather than flagging a problem.
- **`SettingsView` should show the two differently.** One required with a validity
  state, one optional with a "fallback ripper, not required" affordance. The Detect
  button that silently does nothing (`SettingsView.swift:118-127`) is wrong for
  both.
- **`lsdvd` is a third, weaker case if [#0013](0013.md) adopts it for disc
  identity.** Optional enrichment, never a dependency (`-Results.md` §4). Probe it,
  report it, never block on it.
- **The free-space threshold gets better, not worse.** Without an intermediate
  `.mkv` the job needs room for one `.mp4`, not for 5–8 GB plus the encode. The
  note above about treating an unknown capacity as a pass still stands.

Unchanged and still correct: **do not fold preflight into `isConfigured`**
(`AppSettings.swift:33`). Worth noting explicitly since `-Path.md` §3 step 5 lists
*"`AppSettings.isConfigured` stops depending on `makemkvconPath`"* as work to do —
it already does not depend on it and never has. The dependency that needs removing
is the run-time one in the pipeline, not one in this property. See
