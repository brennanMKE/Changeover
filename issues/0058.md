# 0058 — The AAC stereo compatibility track is never produced: `copy:aac` silently falls back to AC3

| | |
|---|---|

| **Phase** | 3 — Unattended multi-disc |
| **Module** | EncodeController |
| **Platform** | macOS |

| **Closed** | 2026-09-25 |

## Description

Measured on the two films ripped on joe on 2026-09-16. #0029's decision was that the first selected audio track gets an extra **AAC stereo** copy for compatibility, alongside the original AC3 — the layout #0017 verified direct-plays on the Apple TV. That layout is not what ships.

`EncodeController` emits `--aencoder copy:aac,copy:ac3,…`. In HandBrake, `copy:aac` means *pass through only if the source is already AAC*; DVD audio is AC3, so it falls back to the fallback encoder, which is AC3. The result:

| File | Source audio | Output audio |
|---|---|---|
| Oppenheimer (2023) | AC3 5.1 448k (eng), AC3 5.1 384k (spa), AC3 2.0 192k (eng) | AC3 5.1 448k, AC3 5.1 384k, AC3 2.0 192k — **no AAC** |
| The Girl Who Kicked the Hornet's Nest (2009) | AC3 5.1 448k (und) ×2 | AC3 5.1 448k ×2 — **no AAC** |

Every output track is a byte copy of a source track. The compatibility track that the whole "first track only" decision was about does not exist, and nothing noticed because the argument vector is asserted in tests against the *intended* string, never against what HandBrake actually produces.

## Resolution notes

> 🟢 Resolved 2026-09-25 — The `copy:aac` entry is gone. `Config.audioAACEncoder
> = "av_aac"` with `audioAACMixdown = "stereo"` and `audioAACBitrateKbps = "160"`
> is what `EncodeController.audioArguments` now emits, so the default output
> carries a real AAC stereo track that is encoded rather than passed through and
> cannot fall back to AC3 (2b2b34a).

## Verification

Re-checked 2026-09-25 against `HEAD` = 97a226f.

- `Changeover/Config.swift:47-49` — `audioAACEncoder = "av_aac"`,
  `audioAACMixdown = "stereo"`, `audioAACBitrateKbps = "160"`. The doc comment at
  `:39-41` names this issue and states the rule: "**No `copy:aac` anywhere** —
  that silently fell back to AC3 if the source wasn't already AAC (#0058), which
  DVD audio never is."
- `EncodeController.audioArguments(_:)` emits those three as parallel
  `--aencoder` / `--mixdown` / `--ab` lists, entry for entry with `--audio`, for
  both `.sourceDefault` and `.tracks` — the positional-list discipline the Plan
  asked for.
- `grep -rn 'copy:aac' Changeover/` returns **two comment lines and no code**:
  `EncodeController.swift:37` describing the old behaviour, and the `Config.swift`
  rule above. Remaining hits elsewhere in the tree are stale reference docs
  (`MacApp.md`, `MakeMKVReplacement-*.md`, `Plan.md`), HandBrake's own `--help`
  text inside test fixtures, and archived scan logs — no shipping path.
- `Config.audioPassthroughEncoder = "copy:ac3"` survives and is used by the
  `.languages` selection and by `keepOriginal` in `.tracks`. That is deliberate
  and is #0059's decision (passthru on request, not by default), not a residue of
  this bug: `copy:ac3` on AC3 source is a genuine passthrough, unlike `copy:aac`.

Both branches of this ticket's "Expected behavior" are satisfied — the first
selected track produces a real AAC stereo track, *and* the code no longer claims
a passthrough it cannot perform.

**What is not verified here, and is owed elsewhere.** The lesson this issue
teaches — assert HandBrake's *output* streams with `ffprobe`, not the argument
vector — is still an owed manual check, and it is carried on
[#0059](0059.md)'s resolution notes rather than here. The same applies to
re-confirming the new single-AAC layout direct-plays on the Apple TV the way
[#0017](0017.md) did. Neither can run on gordon and neither is this ticket's
defect; resolving this one on the argument vector is sound precisely because the
defect *was* in the argument vector.

## Expected behavior

The first selected track produces a real AAC stereo track (as well as the original AC3), or the code stops claiming it does.

## Plan

- Use an explicit encoder for the compatibility track rather than relying on passthru: `--aencoder av_aac` (with `--mixdown stereo` and a sensible bitrate, e.g. `--ab 160`) for the first entry, keeping `copy:ac3` for the original. Confirm HandBrake's `--audio-fallback` default is not silently in play anywhere else.
- Positional list discipline still applies: `--audio`, `--aencoder`, `--mixdown` and `--ab` are parallel lists, so adding per-entry mixdown/bitrate means every list must line up entry for entry.
- Assert the *output*, not just the argument vector: extend the disc-corpus idea with a tiny end-to-end check on joe (encode a chapter, `ffprobe` the result, assert the stream layout). Record it as a manual step if it can't run on gordon.
- Re-verify the layout on the Apple TV the way #0017 did, since the output layout is changing.
- Decide whether the stereo track should be first (some players pick the first track) or after the AC3.

## Superseded in practice by #0059 (2026-09-17)

**The `copy:aac` code path this issue is about no longer exists**: #0059's commit `2b2b34a` replaced it with an explicit `av_aac` stereo encode, so there is nothing left to fall back to AC3. What remains open here is the lesson, not the bug — assert HandBrake's *output* streams, not just the argument vector — and that is carried as an owed manual `ffprobe` check in #0059's Resolution notes.

Status left `open` for the user to close or mark won't-fix; nothing here needs implementing.

## Superseded in part (2026-09-16)

#0059's measured decision replaces the AAC-alongside-AC3 layout with **one AAC stereo track at 160 kbps and no passthru by default**, so the `copy:aac` entry disappears rather than being fixed. What survives from this issue: assert the *output* streams, not just the argument vector — that is how this went unnoticed — and re-verify the new layout on the Apple TV the way #0017 did.
