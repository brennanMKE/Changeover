# 0023 — Nothing parses makemkvcon robot-mode output into structured data

| | |
|---|---|
| **Status** | open |
| **Phase** | 2 — Choose what gets ripped |
| **Module** | DiscScanner |
| **Platform** | macOS |
| **First seen** | 2026-09-11 |

## Description

`makemkvcon -r info disc:0` emits `DRV`, `TCOUNT`, `CINFO`, `TINFO`, `SINFO` and
`MSG` lines describing every title and stream on a disc. Changeover reads none of
it — the only `makemkvcon` output handling in the app appends raw lines to a log
array (`Changeover/RipController.swift:31-41`). A parser turning those lines into
`DiscInfo` is the piece everything else in Phase 2 sits on.

## Long Description

This ticket is deliberately scoped to a **pure function**: bytes in, `DiscInfo` out,
no `Process`, no file system, no main actor. Running the tool is
[#0024](0024.md)'s job. Splitting them this way is what makes the risky half
testable without a disc in the drive — and the fixtures now exist:
`ChangeoverTests/Fixtures/makemkvcon/`, 13 files, 14,175 lines, 7 discs. **That
folder is this ticket's test corpus**, and it is the only way any of this gets real
test coverage given the verification caveat in `issues/Issues.md`.

`DiscSelection.md` and [#0021](0021.md) carry the verified line shapes and the
verified attribute table. Both are authoritative over documentation:

```
DRV:index,visible,enabled,flags,drive name,disc name,device path
TCOUNT:count
CINFO:id,code,value
TINFO:title,id,code,value
SINFO:title,stream,id,code,value
MSG:code,flags,paramCount,message,format,params…
```

**`usage.txt` is wrong about MakeMKV's own output and must not be cited for these
shapes.** It documents `TINFO:id,code,value` and `TCOUT:count`; real output is
`TINFO:title,id,code,value` and `TCOUNT:`. The sketch in `RemoteControl.md` lines
235–241 repeats the same `id,code,value` mistake. Both would produce a parser that
reads the title index as the attribute id on every single line. Check the fixtures.

Robot-mode output is deceptively CSV-shaped and there are four specific ways a
naive parser goes wrong, all of which the fixtures demonstrate concretely:

1. **Field counts differ per line type.** `TINFO` is `title,id,code,value` (four
   fields) and `SINFO` is `title,stream,id,code,value` (five). `CINFO` really is
   three.
2. **Values are quoted and can contain commas.** `split(separator: ",")` breaks on
   a real fixture, not a hypothetical one:
   `TINFO:0,27,0,"Girl in the Spider's Web, The-B1_t00.mkv"` in
   `the-girl-in-the-spider-s-web-min0.txt` — the disc name is comma-inverted and it
   ends up inside the output filename *and* inside attribute 30. An apostrophe is in
   there too and is not special.
3. **Values contain colons.** Duration is `"1:55:11"` and frame rate is
   `"29.97 (30000/1001)"`, so the prefix split must be on the **first** colon only.
4. **Attributes arrive as a flat stream, not as grouped records.** Every `TINFO`
   line carries one attribute of one title; the title is assembled by accumulating
   them, and they are not guaranteed to be contiguous or ordered.

## Expected behavior

A `nonisolated` parser that takes the complete stdout of a `makemkvcon -r info` run
and returns a `DiscInfo` with one `DiscTitle` per title index, each with correct
duration, chapter count, size bytes, output file name, stream list and stream flags,
plus the `MSG` lines carried out **with their parameters intact** for
[#0024](0024.md) to classify and for [#0028](0028.md) to read the effective
`--minlength` out of `MSG:3025`.

## Actual behavior

No parser exists. `makemkvcon` output is treated as opaque log text: trimmed,
non-empty lines are appended to `logLines` for display
(`Changeover/RipController.swift:35-40`, `Changeover/MetadataEntryView.swift:149-151`).

### Shape

```swift
nonisolated enum MakeMKVRobotParser {
    struct Output {
        var disc: DiscInfo
        var messages: [RobotMessage]     // every MSG line, in order
        var titleCountReported: Int?     // TCOUT, for cross-checking
    }

    static func parse(_ text: String) -> Output
}

nonisolated struct RobotMessage {
    var code: Int
    var flags: Int
    var text: String
    var format: String
    var parameters: [String]
}
```

`nonisolated` is required, not stylistic: the project sets
`SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`
(`Changeover.xcodeproj/project.pbxproj:416,445`), and [#0024](0024.md) calls this
from a `nonisolated static` context for the same reason
`RipController.rip` is `nonisolated` (`Changeover/RipController.swift:9`) — a DVD
scan takes tens of seconds (`RemoteControl.md` line 450) and must not run on the
main actor.

`parse` returns rather than throws. A disc with zero titles is a legitimate parse
producing an empty `DiscInfo`; whether that is an *error* is a policy question
[#0024](0024.md) answers with the `MSG` lines and the exit status in hand. Keeping
policy out of the parser is what lets the parser's tests be about bytes.

### Approach

**Tokenizer first, semantics second.** Write a quote-aware field splitter before
anything else:

```swift
static func fields(in line: String) -> [String]
```

Walk the line character by character. Outside quotes, a comma ends a field. Inside
quotes, it does not. Handle the escape convention that [#0021](0021.md) confirms
(doubled `""` versus backslash) — do not guess; read it out of the fixtures. Strip
the surrounding quotes from the returned values. Test this function directly and
separately from the line parsing; it is where the subtle bugs live.

**Then a line-type switch.** Split on the first `:` only, since a value may contain
one (`"1:47:21"` does). Dispatch on the prefix:

| Prefix | Fields | Use |
|---|---|---|
| `DRV` | `index,visible,enabled,flags,driveName,discName,deviceName` | `DiscInfo.driveName`, fallback `volumeName` |
| `TCOUT` | `count` | `titleCountReported` |
| `CINFO` | `id,code,value` | disc attributes → `volumeName` (attribute 32) |
| `TINFO` | `title,id,code,value` | per-title attributes |
| `SINFO` | `title,stream,id,code,value` | per-stream attributes |
| `MSG` | `code,flags,count,message,format,params…` | `messages` |
| `PRGV`/`PRGC`/`PRGT` | progress | ignore in the parser; [#0024](0024.md) may use them for a progress indicator |

Anything unrecognized is skipped silently, not treated as an error — MakeMKV adds
line types between versions.

**Accumulate into dictionaries, materialize at the end.** Build
`[Int: [Int: String]]` for titles (title index → attribute id → value) and
`[Int: [Int: [Int: String]]]` for streams, then produce sorted `[DiscTitle]` in a
final pass. This is what makes out-of-order and non-contiguous attributes a
non-issue, and it means an unexpected extra attribute costs nothing.

**Value conversion.** Duration arrives as `"H:MM:SS"` (and may be `"MM:SS"` on short
titles — check the fixtures). Parse by splitting on `:` and folding, not with
`DateFormatter`, which is locale-sensitive and slow. `DiskSizeBytes` (attribute 11)
is a plain integer string and is the size to trust; `DiskSize` (attribute 10) is a
human string like `"4.3 GB"` and must never be parsed for a number. A missing or
unparseable value yields a zero/`nil` field and is recorded — never a crash and
never a discarded title.

**Classify streams from the codec id, not the type string.** Attribute 1 (Type)
yields `"Video"` / `"Audio"` / `"Subtitles"` — localized display strings that change
with the user's language. Attribute 5 (CodecId) yields stable identifiers. Map on
the first character of the codec id (`V_`, `A_`, `S_`) with a fallback to the
attribute-1 string only when the codec id is missing, and default to
`DiscStream.Kind.unknown` rather than guessing. This is a real correctness point,
not pedantry: the heuristic in [#0025](0025.md) and the language list in
[#0027](0027.md) both depend on stream kind being right, and a mini running a
non-English system locale would otherwise silently classify everything as unknown.

**Document the attribute table in the file.** Put the confirmed table from
[#0021](0021.md) in a doc comment above a `private enum Attribute { static let
duration = 9 ... }` block, so the magic numbers appear exactly once and the evidence
for them sits next to them. Do not scatter literal `9` and `27` through the switch.

## Re-triage

**2026-09-11 — rewrite against HandBrake `--json`, not `makemkvcon` robot-mode
output.** Per `MakeMKVReplacement-Path.md` §4 and §3 step 1. The ticket stays
`open` and stays the piece everything else in Phase 2 sits on; the input format
changes completely.

`-Path.md` §6 calls this out as the time-sensitive item: [#0021](0021.md) and this
ticket *"are both about a parser that should no longer be built."* Do not implement
the `TINFO`/`SINFO` line parser described in the `## Plan` above.

The new input is:

```bash
HandBrakeCLI -i <VIDEO_TS path> --scan --title 0 --min-duration 1 --json
```

**`--title 0` is mandatory.** Without it HandBrake scans only title 1, returns
valid JSON, and is silently incomplete — visible in the log as
`hb_scan: path=…, title_index=1`. The symptom is a scan returning exactly one title
on a disc that should have several, and it is what produced the incorrect
mid-session conclusion corrected in `MakeMKVReplacement-Results.md` §2. With the
flag, Fargo returns `MainFeature: 1` and 8 titles.

**The output is not a single JSON document**, and it is messier than expected.
`MakeMKVReplacement-Results.md` §10 records what actually arrives on stdout, in
order, with `2>/dev/null` already applied: a `Version:` block, roughly 25
`Progress:` blocks, and libdvdnav log lines interleaved among them —

```
libdvdnav: vm: dvd_read_name failed
libdvdnav: DVD disk reports itself with Region mask 0x00fe0000. Regions: 01
```

— all of it *before* `JSON Title Set:`. A parser that splits on a known set of
labels will break. It must tolerate arbitrary non-JSON lines anywhere in the stream
and locate the `JSON Title Set:` section specifically.

**What carries over from this ticket unchanged:**

- The scoping to a **pure function** — bytes in, `DiscInfo` out, no `Process`, no
  file system, no main actor. Running the tool is still [#0024](0024.md)'s job, and
  that split is still what makes the risky half testable without a disc.
- The fixture discipline. `ChangeoverTests/Fixtures/makemkvcon/` stops being this
  ticket's corpus; capture real `--scan --json` output into a sibling folder and
  test against that instead. The existing MakeMKV fixtures stay checked in — they
  are still the corpus for the [#0015](0015.md) fallback path, and they remain the
  record of what those discs contain.
- The general lesson that a tool's own documentation can be wrong about its own
  output. It was true of `usage.txt`'s `TCOUT`/`TINFO` field counts and it is true
  of the assumption that `--json` emits JSON.

**What is deleted:** the `DRV`/`TCOUNT`/`CINFO`/`TINFO`/`SINFO`/`MSG` line shapes,
the four naive-parser failure modes specific to robot-mode CSV, and the attribute
table doc comment. The `MSG` codes that [#0024](0024.md) uses for error
classification are a separate matter — see that ticket's re-triage.

One new requirement from [#0033](0033.md): do not fold HandBrake's parenthetical
variant into the language string. `lang=English (Wide Screen)` is a language, a
role, and a variant in one field, and all three must come out separately.
