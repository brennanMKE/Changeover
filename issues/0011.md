# 0011 — showSettings() rebuilds a closed Settings window, leaking an NSWindow and NSHostingView on every reopen

| | |
|---|---|
| **Status** | open |
| **Phase** | 1 — Trustworthy single-disc rip |
| **Module** | AppDelegate |
| **Platform** | macOS |
| **First seen** | 2026-09-11 |

## Description

`AppDelegate.showSettings()` guards window reuse with `if let w = settingsWindow, w.isVisible` (`AppDelegate.swift:112`) — the exact condition [#0002](0002.md) removed from `showMetadataEntry()`. Because `window.isReleasedWhenClosed = false` (`AppDelegate.swift:129`) keeps the closed window alive, every close-and-reopen builds a fresh `NSWindow` plus a fresh `NSHostingView`, assigns it over `settingsWindow`, and strands the previous pair with nothing releasing them.

## Long Description

The two methods are now asymmetric in the same file. `showMetadataEntry()` reads:

```swift
if let w = metadataWindow {
    w.makeKeyAndOrderFront(nil)
    NSApp.activate(ignoringOtherApps: true)
    return
}
```

(`AppDelegate.swift:84-88`), with a comment explaining that `isReleasedWhenClosed = false` is precisely why the `isVisible` test was wrong. `showSettings()` twenty-five lines later still reads `if let w = settingsWindow, w.isVisible` (`AppDelegate.swift:112`).

The consequence is narrower than #0002's — no job state hangs off the Settings window, so nothing is *orphaned* — but it is not nothing:

- **Leak per reopen.** The old `NSWindow`, its `NSHostingView`, and the SwiftUI view tree underneath stay alive because `isReleasedWhenClosed = false` suppressed the release and the only strong reference (`settingsWindow`) was overwritten. Settings gets opened on every first launch when `!settings.isConfigured` (`AppDelegate.swift:28-30`) and again whenever a path needs fixing, so the count is small but unbounded.
- **State is silently discarded.** `SettingsView(settings: settings)` (`AppDelegate.swift:127`) is rebuilt, so any `@State` local to it — an in-flight text edit, a validation result, a Detect probe — is reset by a close/reopen rather than restored. Today that is invisible; it stops being invisible as soon as [#0008](0008.md) puts per-tool live validity state in that view.
- **Window position resets.** The rebuilt window is `center()`ed rather than restored where the user left it.

This was found by the phase-3 reviewer on [#0002](0002.md), which checked and confirmed that no existing issue covers it: [#0066](0066.md), [#0074](0074.md) and [#0104](0104.md) each mention `showSettings()` for unrelated reasons.

## Steps to reproduce

1. Launch the app. Open Settings from the menu bar popover.
2. Close the Settings window with its close button.
3. Open Settings again — a new window is created, centred rather than restored to where you left it.
4. In a debugger, or with an added `deinit`/`print` on the window, observe the first window object is still alive and is no longer referenced by `settingsWindow`.

## Expected behavior

`showSettings()` reuses `settingsWindow` whenever the object exists, not only while it is visible — identical in shape to `showMetadataEntry()` after #0002. Reopening brings the same window forward with its position and its view state intact, and no object is stranded.

## Actual behavior

A closed Settings window fails the `w.isVisible` test, falls through to the construction path, and is replaced by a new `NSWindow` + `NSHostingView`. The previous pair is never released.

## Notes

This is a one-line fix — delete `, w.isVisible` from `AppDelegate.swift:112` — plus one test. The test belongs in `ChangeoverTests/MetadataWindowReuseTests.swift`, in the shape the three existing cases already use: construct a fresh `AppDelegate()` rather than touching `AppDelegate.shared`, call `showSettings()`, `#require` the window, close it, call `showSettings()` again, and assert `second === first` by identity. Identity is the assertion that matters — "a window exists" passes today.

`settingsWindow` is currently `private var` (`AppDelegate.swift:19`). It needs the same treatment `metadataWindow` got: `private(set) var`, with the comment already on `metadataWindow` (`AppDelegate.swift:16-17`) explaining why the access level is relaxed for the test. Do not make it fully settable.

Verification here is a real unit test that genuinely runs — no disc, no CLI tools, nothing manual beyond confirming the window still opens. This is one of the few tickets in Phase 1 where "tests must actually run" applies literally.

## Plan

### `Changeover/AppDelegate.swift`

- Line 112: `if let w = settingsWindow, w.isVisible {` → `if let w = settingsWindow {`. Carry over the explanatory comment from `showMetadataEntry()` (lines 80-83), trimmed to the part that applies: `isReleasedWhenClosed = false` keeps the object alive across a close, so existence — not visibility — is the right test.
- Line 19: `private var settingsWindow: NSWindow?` → `private(set) var settingsWindow: NSWindow?` so the test can assert identity. Note in a comment that the relaxation exists for the test, matching lines 16-17.

### `ChangeoverTests/MetadataWindowReuseTests.swift`

Add one `@Test func closingAndReopeningReusesTheSameSettingsWindow()` beside the three existing cases. Keep the `defer { delegate.settingsWindow?.close() }` discipline the file already uses — these tests run inside the host app, so a leaked visible window affects later tests.

Assert, in order: a window was created; `isReleasedWhenClosed == false`; it is not visible after `close()`; the second `showSettings()` yields `second === first`; and `second.contentView === first.contentView`, which is the assertion that actually catches a rebuilt `NSHostingView`.

### Risks

- **`showSettings()` is called from `applicationDidFinishLaunching`** when `!settings.isConfigured` (`AppDelegate.swift:28-30`). A fresh `AppDelegate()` in a test does not run that, so the test controls its own window lifecycle — but do not add a test that calls `applicationDidFinishLaunching`, which would install a status item and a `DVDMonitor` into the test host.
- **Do not "fix" this by setting `isReleasedWhenClosed = true`.** That would trade the leak for a dangling `settingsWindow` reference and a crash on the next reopen, and it would diverge from the metadata window's behavior.
- Scope: do not take on Settings-window content, validation, or the Detect button here. Those are [#0008](0008.md).
