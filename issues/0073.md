# 0073 — There is no Changeover Remote app, and the UI it needs is locked inside the host target

| | |
|---|---|
| **Status** | open |
| **Phase** | 4 — Remote control from a Mac |
| **Module** | ChangeoverRemote / ChangeoverUI |
| **Platform** | macOS |
| **First seen** | 2026-09-11 |

## Description

The search-and-select UI the remote needs already exists, but it lives in the host app target and is wired directly to the local pipeline: `MetadataEntryView.startRipping()` constructs a `DVDPipeline` and runs it in-process (`Changeover/MetadataEntryView.swift:142-155`). Phase 4 needs a `Changeover Remote` macOS app plus a shared UI layer both apps consume, so the poster list, the Phase 2 title picker and the log view exist once rather than twice.

## Long Description

`RemoteControl.md` makes the sharing possible by a deliberate design choice: TMDB
search runs **client-side**, so the client does its own searching and sends only the
chosen result. That means `MovieSearchViewModel`
(`Changeover/TMDB/MovieSearchViewModel.swift:4-6`), `TMDBClient`
(`Changeover/TMDB/TMDBClient.swift:3-8`) and the poster row
(`MetadataEntryView.swift:160-201`) are identical on both sides — no host round trip,
no protocol surface for search.

What is *not* identical is where the Start button goes. In the host it runs
`DVDPipeline` locally; in the client it sends `RemoteCommand.startRip`. That single
difference is the seam, and getting it in the right place determines whether this is
a shared view with an injected action or two views that drift apart within a month.

This ticket also has to close `RemoteControl.md` open question 2 — "One app or two?"
— because it cannot be built without an answer.

**Recommendation: two apps, one shared UI package.** The host is `LSUIElement = YES`
(`project.pbxproj:406`, `:435`), unsandboxed, registers a login item
(`Changeover/AppDelegate.swift:125-129`) and has no Dock presence. The remote wants
to be an ordinary windowed app the user opens, quits, and has in the Dock. Forcing
both into one bundle means a runtime mode switch controlling `LSUIElement`, login
item registration, DVD monitoring and the menu bar — and `LSUIElement` is not
switchable at runtime in any clean way. Two targets sharing a UI package keeps each
app's Info.plist, entitlements and lifecycle honest. The cost is a second bundle ID
and a second signing/notarization lane in Phase 6 ([#0100](0100.md)), which is real
but small and mostly automated by the `mac-release` skill.

## Steps to reproduce

1. Look for an app to run on the MacBook Air.
2. Try to reuse `MetadataEntryView` from a second target.

## Expected behavior

A `Changeover Remote` app target that launches, discovers the host, pairs, and
presents the same search / poster / title-picker / log UI as the host — with Start
sending a command instead of running a pipeline. One definition of each view,
consumed by both apps.

## Actual behavior

No remote target exists, and `MetadataEntryView` cannot be reused as-is: it owns
local pipeline state (`MetadataEntryView.swift:7-8`), reads `AppSettings` from the
environment (`:4`) for a TMDB key that on the client comes from the client's own
settings (`:139`), and calls `DVDPipeline` directly (`:149-152`).

## Plan

**Step 1 — extract `ChangeoverUI`.** A new target in the `ChangeoverProtocol`
package (or a sibling package). Move in, unchanged where possible:

- `TMDBClient`, `TMDBModels`, `MovieSearchViewModel` from `Changeover/TMDB/`.
  `MovieSearchViewModel` is already `@MainActor @Observable`
  (`MovieSearchViewModel.swift:4-6`) — correct per `Plan.md`. Because the package
  does not inherit `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`
  (`project.pbxproj:416`, `:445`), the explicit `@MainActor` there must stay and
  `TMDBClient`'s `nonisolated init` (`TMDBClient.swift:6`) needs re-checking against
  package-default isolation. Expect a small round of isolation annotations that were
  previously free.
- The poster row (`MetadataEntryView.swift:160-201`), the results list (`:62-69`),
  the folder-name preview (`:73-89`) and the log view (`:93-119`), each as its own
  public view. They are already cleanly separated as computed properties, so this is
  mostly moving code and adding `public`.
- The Phase 2 title/track picker from [#0020](0020.md) — coordinate so it is authored
  in this package rather than in the app and moved later.

Note the app target uses `PBXFileSystemSynchronizedRootGroup`, so **deleting files
from `Changeover/` removes them from the build automatically** and no `.pbxproj`
surgery is needed on the removal side.

**Step 2 — inject the seam.** `MetadataEntryView` becomes a shared view whose
dependencies are passed in:

```swift
public struct MetadataEntryView: View {
    let apiKey: String
    let disc: DiscInfo?
    let jobs: [JobState]
    let log: [String]
    let canStart: Bool                       // capability + state, from [#0070]
    let onStart: (RipRequest) -> Void
    let onCancel: () -> Void
    let onEject: () -> Void
}
```

The host passes closures that call `JobController`; the client passes closures that
call `RemoteSession.send(_:)`. Views own view models with `@State`
(`MetadataEntryView.swift:5` already does this correctly) and use `@Bindable` for
bindings from `@Observable` objects passed in — never `@StateObject`/`@ObservedObject`.

`canStart` being passed in rather than computed is deliberate: the host and client
compute it differently (local state vs. host-reported state plus capability) and the
view should not know which it is looking at.

**Step 3 — the remote target.** Add `Changeover Remote` to `Changeover.xcodeproj`.
macOS 26.2 deployment target to match (`project.pbxproj:328`, `:386`). Bundle ID
`co.sstools.ChangeoverRemote`. **Not** `LSUIElement` — a normal windowed app with a
`WindowGroup`, not the `Settings` scene + `NSApplicationDelegateAdaptor` shape the
host uses (`Changeover/ChangeoverApp.swift`). No `DVDMonitor`, no `DVDPipeline`, no
`RipController`/`EncodeController`/`PlexOrganizer`, no login item. Links
`ChangeoverProtocol`, `ChangeoverUI` and `RemoteClient`.

Set `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` on the new target to match the host
(`project.pbxproj:416`, `:445`) so the two apps read the same way.

Enable the App Sandbox on the remote — it does not shell out to anything and does not
need filesystem access, so it should not carry the host's `ENABLE_APP_SANDBOX = NO`
(`project.pbxproj:402`). Add the outgoing-network entitlement, and the iCloud KVS
entitlement if [#0065](0065.md) survives its spike. A sandboxed client is also the
configuration [#0080](0080.md) will need on iOS anyway.

**Step 4 — client settings.** The remote needs its **own** `AppSettings` equivalent,
much smaller: a TMDB API key and the last-used host ID. It must **not** reuse
`AppSettings` (`Changeover/AppSettings.swift`) — `plexMediaRoot`, `makemkvconPath`
and `handbrakePath` (`:13-15`) are host concepts and `isConfigured` (`:33`) means
something different on a client. Two small types beat one type with half its fields
unused, and it keeps the remote from ever looking like it can change host paths (see
[#0070](0070.md), which rules settings mutation out of the protocol).

**Step 5 — host regression pass.** After the extraction, the host app must behave
exactly as before: `AppDelegate.showMetadataEntry()`
(`Changeover/AppDelegate.swift:69-93`) constructs the shared view with local
closures, and the environment injection at `:87` still supplies `AppSettings`. Any
visible change in the host UI means the extraction changed behaviour, not just
location.

**Ordering.** Last substantial ticket in the phase. Depends on [#0071](0071.md) for
the session it binds to and [#0020](0020.md) for the title picker.

### Plan refresh (2026-09-15)

**What is stale**

- **`MetadataEntryView` no longer runs `DVDPipeline`.**
  - `startRipping()` (`MetadataEntryView.swift:325`) builds a `RipRequest` and calls
    `jobs.start(request:settings:)`.
  - The view reads `@Environment(AppSettings.self)` (`:4`) and
    `@Environment(JobController.self)` (`:7`), and owns `@State vm =
    MovieSearchViewModel()` (`:10`).
  - The computed-view references are stale. They are now: `resultsList` `:117`,
    `folderPreview` `:129`, `titlesSection` `:190`, `trackSelectionSection` `:204`,
    `failureBanner` `:220`, `logArea` `:254`, `actionBar` `:284`, `MovieRow` `:340`,
    `posterThumb` `:359`.
- **The Phase 2 picker was built in the app target, bound to `JobController`**, not
  authored in a package:
  - `DiscTitleListView` (`@Bindable var jobs: JobController`, `:26`)
  - `TrackSelectionView` (`@Bindable var jobs`, `:19`)
  - `JobHistoryView` (`@Environment(JobController.self)`, `:15`)
  - `JobLogView`

  None can be reused by a client as-is. Adding `public` and moving files is not
  enough.
- **The `TMDB` references are stale.** `MovieSearchViewModel` is
  `@MainActor @Observable` (`MovieSearchViewModel.swift:16`) with debounce, sort
  and runtime lookup. `TMDBClient` has `nonisolated init(transport:)`
  (`TMDBClient.swift:28`). Tests exist: `MovieSearchDebounceTests`,
  `MovieSearchSortTests`, `MovieSearchViewModelRuntimeTests`.
- **The references `AppDelegate.swift:69-93`/`:87`/`:125-129` are stale:**
  - `showMetadataEntry()` is now `:126-159`.
  - The environment injection is `:153`.
  - `registerLoginItem()` is `:320-334`.
- **Entitlement correction.** A sandboxed client that only browses and connects
  needs `com.apple.security.network.client`, which also covers TMDB poster fetches.
  It does not advertise, so it does not need `network.server`.
- **Phase 6 tooling now exists** (`release.sh`, `verify-dmg.sh`), and it has to
  learn about a second bundle.

- (b) Create the target now.
- (c) One app with a host/client mode. Reject, for the reasons in the Long

**Replacement plan (when D-D allows)**

1. **Selection seam first.** In `ChangeoverUI`, define a `DiscSelection`
   `@Observable` protocol-like surface: `scan: ScanStatus`, `selectedTitleIndex`,
   `selectedAudioTrackNumbers`, `selectedExtraTitleIndices`,
   `mismatchAcknowledgement`, plus the actions `selectTitle`, `toggleExtra`,
   `acknowledgeMismatch`, `rescan`, `cancelScan`. There are two implementations:
   - **Host:** a thin adapter over `JobController`, delegating to the existing
     methods, so host behaviour doesn't change.
   - **Client:** local state plus `RemoteSession`, rebuilt when `HostState.scan`
     changes.

   `DiscTitleListView`/`TrackSelectionView` then take that surface instead of
   `JobController`. Do this as a host-only refactor with the suite green before any
   client code exists.
2. **`ChangeoverUI` package target:**
   - SwiftUI only, no AppKit, iOS-ready.
   - `.defaultIsolation(MainActor.self)` if accepted, else explicit `@MainActor`.
   - Move in `TMDBClient`, `TMDBModels`, `MovieSearchViewModel`, `MovieRow`, the
     picker views and `JobLogView` (fed `[LogDisplayRow]`).
   - `JobHistoryView` renders `JobPresentation` from snapshots.
   - Recheck `TMDBClient`'s `nonisolated init` under package isolation.
3. **Action seam:** `MetadataEntryView` gets `onStart(RipRequest,
   MismatchAcknowledgement?)`, `onCancel(JobID)`, `onRetry(JobID)`, `onEject()` and
   a `StartGateDecision` passed in.
   - The host passes closures into `JobController` / `AppDelegate.requestCancel`.
   - The client passes closures into `RemoteSession.send`.
4. **The target itself:**
   - Bundle ID `co.sstools.ChangeoverRemote`, macOS 26.2.
   - `WindowGroup`, not `LSUIElement`.
   - `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`.
   - App Sandbox **on**, with `network.client`.
   - The Info.plist keys from [#0074](0074.md).
   - Links `ChangeoverProtocol`, `ChangeoverTransport`, `ChangeoverRemoteClient`,
     `ChangeoverUI`.
   - Small client settings: TMDB key (Keychain preferred) and paired hosts. It
     never reuses `AppSettings`.
5. **UI-test rule.**
   - **No UI test target for the remote**, and its scheme's Test action must not
     include one. Never add remote UI tests to the `Changeover` scheme.
   - Logic stays in package targets verified through `ChangeoverTests` with
     `./run-remote-tests.sh gordon`.
   - Any UI verification is recorded as manual or unverified. It only runs in the
     Tart VM via `./run-ui-tests-vm.sh` with user approval.

**Tests** (in `ChangeoverTests` via `./run-remote-tests.sh gordon`):

- The host `DiscSelection` adapter delegates correctly, and the existing
  `DiscTitleListView`-related controller tests still pass.
- The client adapter builds a `RipRequest` with `selectionDisc` from `HostState`.
- `StartGateDecision` is not `.allow` for an observe-only capability.
- The existing `MovieSearch*` tests keep passing after the move.

Layout is covered by SwiftUI previews per state, not tests.

## Notes

**Unit-testable:** `MovieSearchViewModel` search and error mapping — it is already
injectable via `init(client:)` (`MovieSearchViewModel.swift:15-17`), so a fake
`TMDBClient` gives real tests with no network. Also `MovieMetadata.folderName` /
`fileName` after the move ([#0061](0061.md) covers this) and that `canStart` is
false for an observe-only capability.

**Not meaningfully unit-testable:** the layout itself. Use SwiftUI previews for both
the host and client configurations of each shared view — a preview per state (no
results, results, mid-rip, failed, observe-only) is the practical regression suite
for this ticket, and it costs minutes.

**Requires two real machines:** the actual demo — search, confirm, pick titles, start,
watch the log, see the eject. That is the phase's exit criterion and it is manual by
nature; record it as manual with the disc used.

**Watch for:** `AsyncImage` poster loading on the client
(`MetadataEntryView.swift:180-198`) hits TMDB directly from the laptop, which is
correct and intended — but it means the client needs general outgoing network access,
not just Local Network. Both entitlements are required on a sandboxed client, and
only one of them is obvious.

**Phase 6 consequence to flag now:** two apps means two signing, notarization and
DMG lanes in [#0100](0100.md), and a decision about whether they ship in one DMG or
two. Better to know that while scoping Phase 6 than to discover it during a release.
