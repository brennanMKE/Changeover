# 0003 — RipController picks the largest .mkv in a shared folder, so a stale file can be encoded as the current movie

| | |
|---|---|
| **Status** | open |
| **Module** | RipController / DVDPipeline / AppSettings |
| **Platform** | macOS |
| **First seen** | 2026-09-11 |

## Description

Every rip writes into the same directory and then picks the largest `.mkv` in it (`RipController.swift:47`, `largestMKV(in:)` at lines 66-77). A leftover file from a previous disc that happens to be bigger than the current one is selected, encoded, and filed into Plex under the current movie's name. The working directories are also never created by the app, so a fresh install fails at the first rip unless the user made them by hand.

## Long Description

`DVDPipeline.run()` passes `settings.workingRipPath` as `outputDir` (`DVDPipeline.swift:21` and `:29`), and that path is a fixed derivation — `"\(plexMediaRoot)/Working/ripping"` (`AppSettings.swift:27`) — identical for every job. After `makemkvcon` exits 0, `largestMKV` enumerates the whole directory with no notion of which files this run produced. Combined with [#0004](0004.md) (nothing is ever cleaned up), the directory accumulates one `.mkv` per disc and the selection becomes "the largest movie ever ripped on this machine".

Two secondary failures live in the same code:

- **`makemkvcon` exiting 0 having produced nothing** still returns a stale path rather than an error. There is no check that anything was written.
- **Nothing creates the working directories.** `AppSettings` only derives strings (lines 27 and 30); no `createDirectory` call exists anywhere in `Changeover/`. `Plan.md` "Prerequisites" instructs the user to `mkdir -p` the four folders manually. If `Working/ripping` is missing, `makemkvcon` fails and the log shows a bare exit status ([#0009](0009.md)).

## Steps to reproduce

1. Rip a long film (disc A) — say a 7 GB main title. Because of [#0004](0004.md) its `.mkv` stays in `<plexMediaRoot>/Working/ripping`.
2. Insert a shorter film (disc B) whose main title is ~4 GB.
3. Search for B, select it, Start Ripping. Let the rip finish.
4. Watch the log line `"✓ Rip complete: …"` — it names disc A's file.
5. The encode runs on A's file and `PlexOrganizer` files it as `B (Year) {tmdb-B}/B (Year).mp4`.

## Expected behavior

A rip only ever considers files that this rip produced. A run that produces no titles fails with "makemkvcon produced no titles" rather than silently reusing an old file. Working directories are created by the app on demand.

## Actual behavior

`largestMKV(in:)` returns whichever `.mkv` in the shared folder is biggest regardless of provenance or timestamp, and `RipController.rip` returns it as this job's output. On a machine where the working folders were never created by hand, `makemkvcon` fails and the reason is not reported.

## Notes

The directory derivation, the "empty directory means no titles" path, and the directory-creation behavior are all straightforwardly unit-testable against a temp directory — write real tests and run them.

The defect itself, reproduced faithfully, needs two physical discs of different lengths. It can be simulated without hardware by pointing `makemkvconPath` at a script that writes a small file into the output directory; that proves the isolation logic but not the integration. Say which was done in `## Verification`.

This is the single defect the Phase 1 demo is built to expose — see the "do it a second time with a different disc" line in [#0001](0001.md).

## Plan

### Per-job working directories

Introduce a small value type, `Changeover/JobWorkspace.swift`:

```swift
struct JobWorkspace {
    let jobID: String
    let ripDirectory: URL
    let encodeDirectory: URL
}
```

with a failable/throwing factory that takes the two root paths from `AppSettings` plus a job id and returns the derived `URL`s. Keep it a plain `struct` — MainActor by default, no `actor` (`Plan.md` conventions). Mark the derivation `nonisolated` so `RipController` and `EncodeController`, which are `nonisolated static` (`RipController.swift:9`, `EncodeController.swift:9`), can use it without hopping.

Job id: use the `currentJobID` from `JobController` ([#0002](0002.md)) — a UUID string, or an ISO-8601 timestamp plus a short random suffix. **Do not put the movie title in the path.** Titles legitimately contain `:`, `/` and `?` (`Plan.md` names `Planes, Trains and Automobiles`), and the folder name is a machine detail, not a user-facing one.

Build paths with `URL(fileURLWithPath:).appendingPathComponent(...)`, not string interpolation. `AppSettings`'s derived paths (lines 21-30) currently use `"\(plexMediaRoot)/Movies"` interpolation; that is tolerable for a root the user picked with `NSOpenPanel`, but do not extend the pattern.

### Directory creation

In `DVDPipeline.run()`, before step 1 (`DVDPipeline.swift:26`), create both directories with `FileManager.createDirectory(at:withIntermediateDirectories: true)`. A creation failure is a job failure with a message naming the path — map it onto [#0007](0007.md)'s `FailureReason.destinationUnwritable`. This is also the fix for the "the app assumes you ran `mkdir -p`" gap in `Plan.md`'s prerequisites. Note the overlap with [#0008](0008.md): preflight checks writability *before* the disc is touched; this creates the directory at the moment of use. Both are wanted; do not collapse them.

### `Changeover/RipController.swift`

- `rip(makemkvconPath:outputDir:log:)` (line 9) takes the per-job rip directory as `outputDir`. The `process.arguments` array (lines 19-24) is otherwise unchanged — still `mkv disc:0 all <dir>` for Phase 1; title selection is Phase 2 ([#0020](0020.md)).
- Replace `largestMKV(in:)` (lines 66-77). Because the directory is created empty per job, enumerating it after termination yields only this job's output — but make the intent explicit: return an error, not `nil`, when the directory contains no `.mkv`, and keep the "largest" heuristic only as a tiebreak among *this job's* files (a full-disc rip legitimately emits one file per title).
- `largestMKV` currently compares sizes with `(try? fm.attributesOfItem(atPath:)[.size] as? Int) ?? 0` (lines 73-74) — that double-optional is fragile and yields 0 on any error, which makes `max` arbitrary. Use `URLResourceValues.fileSize` via `URL(fileURLWithPath:).resourceValues(forKeys: [.fileSizeKey])` while touching this code.
- Keep the function `nonisolated static`. Do not convert `RipController` to an `actor`.

### `Changeover/DVDPipeline.swift`

- Capture the workspace alongside the other paths in the MainActor prologue (lines 19-24) — that prologue exists precisely so nonisolated calls receive plain values, and the workspace must follow the same discipline.
- Point the encode output (lines 38-39) at `workspace.encodeDirectory` rather than `settings.workingEncodePath`.

### Risks

- **Orphan directories.** A job that fails between creating the directory and finishing leaves it behind. Retention and sweeping belong to [#0004](0004.md); this ticket must not delete anything, or the two tickets will fight over the policy.
- **Path length and volume semantics.** `plexMediaRoot` is typically an external SSD (`/Volumes/MediaSSD/Plex Media`). An unmounted volume mid-job turns directory creation into a confusing failure; report the path in the message.
- **Do not change the shape of `AppSettings.workingRipPath` / `workingEncodePath`** (lines 27, 30). They stay as the roots; the per-job directory is a child of each. `SettingsView.pathPreviewRow` displays both (lines 28-29) and should keep showing the roots.
