## Description

Found by the Phase 3 review. Inserting a disc starts a `HandBrakeCLI --scan` through `JobController.startScan`, which launches an untracked `Task` (`Changeover/JobController.swift:813`) — its own doc comment says "nothing tracks or cancels an in-flight scan `Task`". The only bound on that scan is `DiscScanner.scanWatchdog = .absolute(15 * 60)` (`Changeover/DiscScanner.swift:77`). While it runs, `scanState == .scanning`, and #0045's review made `EjectPolicy` refuse an eject for exactly that reason: the scan can't be cancelled, so ejecting under it either fails as busy or leaves a dead mount path. Start is disabled until the scan finishes, and Rescan is only offered on a failed scan.

So a disc whose scan hangs — a scratched disc, a malformed IFO like *The IT Crowd* (#0024), a drive that spins up badly — puts the app in a state where **Start, Rescan and Eject are all unavailable for up to fifteen minutes**, and the only thing the user can do is wait or quit. In an unattended session that is the disc that stops the run. #0046 built every piece the fix needs and left the scan untracked on purpose: `ProcessRunner.run` is cancellable (SIGTERM, then SIGKILL after 10 s), `DiscScanner.Failure.cancelled` exists, and `DiscTitleListView.message(for:)` already renders "The scan was cancelled." — all noted there as "not reachable today (no scan-cancel UI exists yet)".

A smaller consequence of the same gap: `startScan` can be called again while a scan is running (it bumps `scanGeneration` and discards the older result), which leaves two `HandBrakeCLI --scan` processes reading the same disc at once.

## Resolution notes

> 🟢 Resolved 2026-09-15 — A running scan can now be stopped from the metadata window's "Cancel Scan" or from the status menu's "Eject Disc", which cancels the scan, waits for its `HandBrakeCLI` to exit, then ejects; a cancelled scan shows "The scan was cancelled." with Rescan (992e796, review fix 6fde067).

**Review (2026-09-15, claude-opus-5).** 992e796 was in scope. Its scan tracking, `cancelScan()`, cancel-on-rescan/removal/insertion and generation handling were right. Two things were wrong, and 6fde067 fixes them:

1. **"Eject Disc" was still disabled during a scan, so the cancel-then-eject path couldn't be reached from the app.** `StatusMenuView` disabled the row whenever `ejectDecision != .eject`, and `EjectPolicy.decide` still returned `.refuse(scanningReason)` mid-scan, with the old "wait for the scan to finish" tooltip. Only the unit tests, which call `ejectDisc()` directly, reached the new branch. That is the unattended case this issue exists for.
2. **The branch was keyed on the reason string.** `reason == EjectPolicy.scanningReason` would have silently turned cancel-then-eject back into a refusal if the message were ever reworded.

The fix:
- `EjectPolicy.Decision` gains `.cancelScanThenEject`, returned only when a scan is the sole blocker. No disc, a running job and an eject in flight still refuse first, so a scan alongside a dying job is never cancelled for an eject that can't proceed. The menu row is enabled for it, with the tooltip "Stop the disc scan, then unmount and eject the disc.", and `canEjectManually` counts it as allowed. `scanningReason` is gone.
- `ejectDisc()` switches on the case. It holds `isEjecting` while it awaits the scan `Task`, so a second Eject, a Start or a Rescan can't slip in. Before this, a Rescan landing between the cancelled scan settling and the eject resuming would have started a new scan under the eject. If a removal or insertion lands during the wait, nothing is ejected ("The disc was removed or replaced while its scan was stopping — nothing was ejected."). A scan still running after the wait refuses with `scanStillRunningReason`; with a real scan `Task` that can't happen.
- The `DiscScannerTests` real-cancel test no longer leaves its 30 s stub running if launch detection fails.

**Checked and fine:**
- **Ordering.** `await inFlightScan?.value` is a real wait on the scan process. The scan `Task` returns only after `ProcessRunner.run` resumes, and `RunCompletionGate` resumes only after `terminationHandler` (`markProcessDone`) and reader EOF. So the eject waits out a child that ignores SIGTERM, up to the 10 s SIGKILL escalation. The new `ejectDiscMidScanWaitsForTheScanProcessToExitBeforeEjecting` runs a real process through `DiscScanner.scan`: a script that catches SIGTERM, keeps running for 2 s, then writes a marker and exits. At the moment the ejector is called, the marker exists, `kill(pid, 0)` fails, and at least 1.5 s have passed.
- **Cancelled display.** `.failure(.cancelled)` lands as `.failed(.cancelled)`: "The scan was cancelled." with Rescan. `DiscReliabilityLog` is written only from `DVDPipeline`, never from a scan, so a cancelled scan is never recorded as a disc failure.
- **Stale results.** The generation token discards a superseded scan's late outcome, and `applyScanOutcome` clears `scanTask` only for the landing generation.
- **Edges.**
  - Removal and insertion mid-scan cancel the scan's `Task`; tests use witness flags.
  - Start is impossible while a scan is being cancelled: `start` and `StartGate` need `.scanned`, and `isEjecting` is now held during an eject's wait.
  - A second Cancel is harmless, because `Task.cancel()` is idempotent. So is Cancel then Eject: the eject's own cancel is a no-op and it still awaits the same `Task`.
- **Stub fixture.** `SLEEP_SECONDS` under `--scan` affects only the new test. The other users (`DVDPipelineCancellationTests`, `ProcessRunnerTests`) run encode invocations, and the pipeline never runs `--scan`.
- **Leaks.** No leaked processes and no continuation-leak lines.

## Root cause

Nothing held a reference to the scan's own `Task`. `startScan` launched
`Task { [weak self] in … }` and threw the handle away
(`Changeover/JobController.swift:816`, pre-fix), so there was nothing to
call `.cancel()` on — `scanGeneration` only discarded a superseded scan's
*result*, it never stopped the underlying `HandBrakeCLI --scan` process.
#0046 had already built every piece cancellation needs one layer down
(`ProcessRunner`'s `withTaskCancellationHandler`, SIGTERM→SIGKILL escalation,
`DiscScanner.Failure.cancelled`) but explicitly left the scan side
unwired, noting in its own Gotchas that nothing reached it yet. `EjectPolicy`
correctly refused an eject while `scanState == .scanning` (#0045 review) —
because ejecting mid-scan without a cancel would either fail as busy or
unmount the volume out from under the scan and leave a dead mount path
(#0049's failure mode) — but with no way to end the scan, that refusal was
permanent for up to `DiscScanner.scanWatchdog`'s 15 minutes.

## Fix

**Track the scan.** `JobController` gained `private var scanTask:
Task<Void, Never>?`, set by `startScan` right before launching and cleared
by `applyScanOutcome` — but only when the outcome is for the generation
actually landing, guarded by the same `generation == scanGeneration` check
that already discards a superseded result, so a late (superseded) scan's
own cleanup can never clear the handle to the *newer* scan that replaced it.

**`cancelScan()`.** Cancels `scanTask` (a no-op, returning `false`, when
nothing is running). `task.cancel()` reaches `ProcessRunner.run`'s
`withTaskCancellationHandler` exactly the way `JobController.cancel(id:)`
already does for a running job — real SIGTERM, escalating to SIGKILL after
the grace period — and `DiscScanner.scan` already mapped a cancelled
termination to `.failure(.cancelled)` (#0046). `applyScanOutcome` applies
that for the current generation as `scanState = .failed(.cancelled)` with no
special-casing needed: it's just another `DiscScanner.Failure`, and
`DiscTitleListView` already rendered `.cancelled` as "The scan was
cancelled." with Rescan offered — that path just wasn't reachable before.

**`startScan` cancels any prior scan first.** A Rescan, or a second
`startScan` call while one is already running, now calls `scanTask?.cancel()`
before bumping `scanGeneration` and launching the new one — closing the
"two `HandBrakeCLI --scan` processes on the same disc" gap the Description
calls out, not just discarding the stale result the way the generation token
alone already did.

**`removeDisc()` cancels a scan in flight.** A disc pulled or ejected while
scanning now stops the process, not just the eventual (now-irrelevant)
result — proven with a real cancellation-aware fake, not just the generation
check (see Verification). `insertDisc()` gets the same effect for free,
since it already calls `startScan`, which now cancels first.

**Eject during a scan.** Per the Plan's "do both" recommendation (chosen as
the least-surprising UX: unattended, Eject is the action that actually
matters — a user watching the metadata window has "Cancel Scan" too, but
someone walking away and coming back to a stuck drive only has Eject):

- `ejectDisc()` re-checks `EjectPolicy.decide`'s refusal reason. When it is
  *exactly* `EjectPolicy.scanningReason` (not the job-running or
  already-ejecting refusals, which are left alone), it logs "Cancelling the
  scan to eject…", calls `cancelScan()`, `await`s the scan `Task`'s own
  value so the process has actually stopped, then re-decides and proceeds.
  `EjectPolicy` itself stays pure and still refuses outright on its own —
  it has no way to cancel anything — the caller is what turns "refuse" into
  "cancel, then eject".
- `DiscTitleListView`'s scanning state also gained a "Cancel Scan" link
  button, calling `jobs.cancelScan()` directly, for the case where the user
  is at the metadata window and just wants the scan to stop without also
  ejecting.

**Decisions made (user AFK, delegated), per the task brief:**

- **Did both** — the tracked-scan-Task/`cancelScan()`/Eject-cancels-then-
  ejects core, *and* a "Cancel Scan" button — rather than picking one, since
  the Plan already recommended both and reasoned why.
- **Eject's cancel-then-retry is keyed to the exact refusal reason
  (`EjectPolicy.scanningReason`), not `scanState` directly.** `EjectPolicy
  .decide`'s guard order checks `isRunning` before `isScanning`, so if a job
  happens to be running *and* a scan is also in flight (`startScan` doesn't
  gate on `isRunning`, per its own doc comment — a disc inserted while a
  prior job is still dying), `.decide` already refuses for the job-running
  reason. Cancelling an unrelated scan in that case would help nothing and
  silently kill a scan the eject can't proceed with anyway — checking the
  precise reason string means the cancel-then-retry path only ever fires
  when a scan is genuinely the *only* thing blocking the eject.
- **No new observable "cancelling" state for the UI** (nothing mirroring
  `cancellingJobID`). A scan's cancellation is quick enough (`ProcessRunner`'s
  10 s SIGTERM grace, versus a job's potentially much longer encode) that
  the existing `.scanning` → `.failed(.cancelled)` transition was judged
  sufficient without a dedicated "Cancelling scan…" label; `ejectDisc()`'s
  one added log line covers the eject case.

## Gotchas

- **The stub script change is shared infrastructure.** `stub-HandBrakeCLI.sh`
  is used by many suites; `SLEEP_SECONDS` under `--scan` is opt-in (empty by
  default, same as the encode branch always was) so every existing
  `SCAN_FIXTURE`/`SCAN_EXIT`-driven test is unaffected — confirmed by the
  full 782-test run.
- **`ejectDiscRefusesWhileTheDiscIsBeingScanned`** (an existing #0045-review
  test that sets `scanState = .scanning` directly, with no real `scanTask`)
  still passes unchanged, but now takes the cancel-then-retry branch as a
  no-op: `cancelScan()` finds `scanTask == nil` and returns `false`,
  `scanState` never resolves, and the eject still refuses — it now also logs
  "Cancelling the scan to eject…" before the refusal, which the test's
  `.contains` assertions don't notice. This is a test-only artifact (hand-set
  `scanState` with no matching `scanTask`); in production the two are always
  set together by `startScan`.
- **No `.ambiguous`/queue-of-scans complexity was added.** One
  `scanTask`/one `scanGeneration` was already the right shape for "one scan
  in flight at a time"; cancellation slots into the existing generation
  bookkeeping rather than needing its own.

## Steps to reproduce

1. Insert a disc that scans slowly, or stub `HandBrakeCLI` with a scan that sleeps.
2. While the metadata window shows the scanning state, open the status menu: "Eject Disc" is disabled with the mid-scan tooltip.
3. Try to stop the scan from anywhere in the app.

## Expected behavior

A running scan can be stopped: an explicit "Cancel Scan" action, and "Eject Disc" during a scan cancels the scan first and then ejects. A cancelled scan ends promptly (`ProcessRunner`'s SIGTERM→SIGKILL path), is shown as "The scan was cancelled." with Rescan offered, and never applies a stale result. Starting a new scan cancels the one in flight instead of running beside it.

## Actual behavior

The scan runs to completion or to the 15-minute watchdog. Eject, Start and Rescan are all unavailable for the duration. Nothing in the app can shorten it.

## Plan

- **Track the scan.** `JobController` keeps `scanTask: Task<Void, Never>?` beside `scanGeneration`. `startScan` cancels any previous `scanTask` before launching (one scan process per disc at a time), and `applyScanOutcome` clears the handle when the matching generation lands.
- **`cancelScan()`.** Cancels `scanTask`. Cancellation reaches `ProcessRunner.run` the way #0046's job cancel does, and `DiscScanner.scan` already maps a cancelled termination to `.failure(.cancelled)`. `applyScanOutcome` applies it for the current generation as `scanState = .failed(.cancelled)`, so the existing "The scan was cancelled." message and Rescan button render; an outcome for an older generation is discarded as today.
- **Eject during a scan.** Keep `EjectPolicy` pure. In `ejectDisc()`, when the decision is the mid-scan refusal, call `cancelScan()`, `await scanTask?.value`, then re-run `EjectPolicy.decide` and proceed. Log one line ("Cancelling the scan to eject…"). Alternatively surface a "Cancel Scan" button in `DiscTitleListView`'s scanning state and leave Eject as it is; the review recommends doing both, since the eject is the case that matters unattended.
- **Tests** (`JobControllerScanTests`, gated `scanRunner`, no disc, through `./run-remote-tests.sh gordon`): `cancelScan` ends the scan as `.failed(.cancelled)` and a following `startScan` is accepted; `ejectDisc` mid-scan cancels the scan, waits, and then calls the fake ejector once; a second `startScan` while scanning cancels the first and only the second outcome is applied; a cancelled scan's late outcome for an older generation is discarded. `EjectPolicyTests` unchanged unless the policy gains a case.
- **Manual on joe:** insert a disc, click "Eject Disc" during the scan — the tray opens within a few seconds, the log shows the cancel, and re-inserting the disc scans it normally.
