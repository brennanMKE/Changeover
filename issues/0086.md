# 0086 — No local notification on iOS when a job finishes and the disc ejects

| | |
|---|---|
| **Status** | open |
| **Module** | Notifications / RemoteClient |
| **Platform** | iOS · iPadOS |
| **First seen** | 2026-09-11 |

## Description

The iOS client has no notification of any kind, so the user has to keep the app
open and watch it to know when a disc is done. That defeats the purpose of the
couch case — the whole point is to put the phone down between discs.

## Long Description

`RemoteControl.md` frames the intended loop as seven steps, and step 6 is "disc
auto-ejects; client notifies 'done, next disc'". It then says outright that
auto-eject and the completion notification "are not enhancements — they are what
closes this loop". Without the notification the user is polling a screen, which
is not meaningfully better than watching the mini.

Phase 1 adds a completion notification via `UNUserNotificationCenter` on the
**host** (`Roadmap.md` Phase 1 work list, `Plan.md` 11.5). That does not help
here for two reasons: the notification fires on the mini, which is in another
room and probably headless; and iOS has its own authorization flow, its own
delegate requirements for foreground presentation, and its own constraints on
delivery while the app is suspended. Sharing the `UNUserNotificationCenter` API
name is the only thing the two have in common.

The delivery problem is the hard part and it is inseparable from
[#0087](0087.md). A local notification has to be scheduled by code running on the
phone, but the phone's app gets suspended shortly after backgrounding and the
socket dies with it — so at the moment the job actually finishes, there may be no
process alive to schedule anything. "Local notification on job completion" is
therefore not a one-line `UNNotificationRequest`; it is a question about what
wakes the client.

## Steps to reproduce

1. Complete [#0081](0081.md) so the iOS client runs.
2. Start a rip from the iPhone.
3. Press the home gesture to background the app, lock the phone, and wait for
   the job to finish.

## Expected behavior

A notification arrives saying the movie is done and the disc has ejected — "Done
— next disc" — with the app backgrounded and the screen locked. Tapping it opens
the client on the finished job. With the app in the foreground, the completion is
shown in-app rather than as a redundant banner.

## Actual behavior

Nothing arrives. The app was suspended shortly after backgrounding, its
connection to the host was torn down, and no notification was ever requested. The
user discovers the job finished by unlocking the phone and reopening the app.

## Notes

Do not ask for notification authorization at launch. A permission prompt before
the user has done anything is the classic way to get a permanent denial, and a
denied notification permission cannot be re-requested — only routed to Settings.
Ask at the moment the first rip is started, when the value is self-evident.

The notification content should carry the movie title, because by the time it
arrives the user may not remember which disc was running:
"Blade Runner (1982) — done. Next disc." `MovieMetadata.folderName` /
`.fileName` (`Changeover/MovieMetadata.swift:17–24`) already produce display
strings, and Phase 4's `RemoteEvent.finished(folderName:)` carries the folder
name to the client.

Failure deserves a notification too, and a different one. A rip that failed
because the MakeMKV key expired is exactly the case where the user is sitting on
the couch assuming it worked. `RemoteControl.md` calls MakeMKV key expiry out
specifically as a recurring real-world failure that must be reported as itself.

## Plan

### 1. Settle the delivery mechanism before writing any UI

There are three candidate mechanisms and they are not equally good. Decide this
first, because everything else follows from it.

**A. Schedule on receipt, while in the foreground or shortly after backgrounding.**
Works only if the app is still alive when `finished` arrives. For a short encode
where the user never leaves the app, fine. For anything longer, the app is
suspended and this delivers nothing. Necessary but not sufficient.

**B. Keep the connection alive briefly in the background, schedule from there.**
A `URLSessionTask`-style background allowance or a short `beginBackgroundTask`
window buys seconds to minutes, not the duration of an encode. Useful as a
bridge — it covers the case where the job finishes just after the user puts the
phone down — but it is not a general answer.

**C. Push from the host.** The host knows when the job finishes and is never
suspended. But push means APNs, an entitlement, and a server-side token flow;
`Roadmap.md` lists CloudKit and push under "things deliberately not in this
roadmap" and `RemoteControl.md` rejects them for adding multi-second latency and
breaking the multi-Apple-ID case. Do not reach for this without escalating — it
is a roadmap change, not an implementation detail.

**Recommended path: A + B, with the gap acknowledged.** Schedule on receipt when
alive; take a background task to extend the window when the app backgrounds
mid-job; and on foreground, [#0087](0087.md)'s re-sync detects that the job
finished while the app was suspended and shows it in-app immediately. What the
user loses is the *proactive* notification for a long encode, which is real and
should be stated in the ticket's resolution rather than papered over.

There is a fourth option worth evaluating cheaply first: schedule a **time-based
local notification in advance**, when the rip starts, using the host's estimate
of completion, then cancel or reschedule it when the real `finished` arrives.
This delivers with the app fully suspended because the scheduling already
happened. The cost is accuracy — it needs an estimate from the host, and a
notification that fires early is worse than one that fires late. Evaluate it
against how well Phase 3's queue can estimate duration; if the estimate is within
a couple of minutes, this is the best answer available without push.

### 2. Authorization, requested at the right moment

Request `.alert`, `.sound` and `.badge` via
`UNUserNotificationCenter.current().requestAuthorization` at first rip start, not
at launch. Handle all three outcomes explicitly:

- **Granted** — proceed.
- **Denied** — do not nag, do not retry. Show a one-line inline explanation on
  the job screen with a link to `UIApplication.openSettingsURLString`, the same
  pattern [#0089](0089.md) uses for Local Network.
- **Not determined / provisional** — consider `.provisional` authorization as a
  softer first ask; it delivers quietly to Notification Center without a prompt
  and the user can promote it. For an app whose notifications are genuinely
  wanted, provisional is a good fit and avoids burning the one-shot prompt.

Check `notificationSettings()` on each foreground rather than caching the result
— the user can change it in Settings while the app is suspended.

### 3. Foreground presentation

Set a `UNUserNotificationCenterDelegate` and implement
`userNotificationCenter(_:willPresent:)`. With the app foregrounded and the job
screen visible, suppress the banner and let the UI show completion — a banner
covering the screen that already says "done" is noise. If the app is foregrounded
but on another screen, present it.

The delegate is a `nonisolated` callback surface. Under this project's
`SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`
(`Changeover.xcodeproj/project.pbxproj:416`, `:445`) the conformance methods
need explicit `nonisolated` and should hop back with `Task { @MainActor in ... }`
— the same pattern `DVDMonitor.volumeMounted` uses for its `@objc` callback
(`Changeover/DVDMonitor.swift`) and that `Plan.md`'s isolation table documents.
Do not make the notification coordinator an `actor`; it has no reason to leave
the main actor.

### 4. Content and actions

Three categories, with distinct content:

- **Completed** — title from `RemoteEvent.finished(folderName:)`, body "Done —
  next disc." Add a notification action to eject if the host has not already, so
  the user can start the errand from the lock screen.
- **Failed** — names the actual failure (expired MakeMKV key, disk full,
  destination unwritable), matching Phase 1's requirement that every failure
  mode produce a message naming the real problem. A generic "job failed" is a
  defect here.
- **Queue drained** (Phase 3) — if a queue finished rather than a single job,
  say so. Coordinate with [#0040](0040.md) rather than inventing a second
  completion concept.

Tapping a notification deep-links to the relevant job. Carry the job id from
Phase 3's stable job IDs in `userInfo` so the target is unambiguous when a queue
is running.

### 5. Risks

- **The suspended-app gap is real and may not be closable** without push. Say so
  explicitly in the resolution rather than shipping something that works in
  testing (short jobs, app in foreground) and fails in use (long encode, phone in
  a pocket).
- **Duplicate notifications** when [#0087](0087.md)'s reconnect replays state
  and the client re-derives "finished" from a `JobState` it already notified
  about. De-duplicate on job id, and make the notification request identifier the
  job id so a re-request replaces rather than duplicates.
- **Badge counts** drift if the app is killed. Either maintain them properly
  against the queue or do not request `.badge` at all.

### 6. Verification

- **Simulator:** authorization prompt appears at first rip start and not at
  launch; a notification scheduled from a debug action is delivered and presented
  correctly in foreground and background; denial shows the Settings link. All
  provable in a simulator with no host.
- **Unit-testable:** the mapping from `JobState` / `RemoteEvent` to notification
  content, the de-duplication by job id, and the failure-reason text. Worth real
  tests — this is exactly the kind of pure logic the project's verification
  caveat says should be tested.
- **Device- and host-bound, and not optional:** a real rip started from a real
  iPhone, the phone locked and pocketed, and the notification observed arriving.
  A simulator cannot reproduce real app suspension timing. This is the ticket's
  actual acceptance test and the `## Verification` section must report it as a
  manual device run, naming the disc used and the elapsed time.
