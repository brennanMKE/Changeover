## Root cause

No code ever ran a scan: inserting a disc went straight to the TMDB search
window, and the first touch of the drive was the full encode. The filed plan
targeted `makemkvcon info` with MSG-code classification; the Re-triage
redirected the tool to HandBrake and rebuilt the failure model — exit status
decides, and the text explains — because successful scans carry scary lines
and a text-matching classifier fails real discs.

## Fix

`499b253` — new `Changeover/DiscScanner.swift`:

- Runs the re-triaged command (`--scan --title 0 --min-duration 1 --json`;
  `--title 0` mandatory — without it the scan succeeds with silently
  incomplete JSON) through the shared `ProcessRunner`, whose line splitting
  and drain-before-resume behaviour this ticket's Notes documented as the
  latent bug to not inherit — already fixed there (#0009).
- **The exit status decides.** Non-zero → `.failure(.toolExited(code:))`
  whatever the output says; a launch failure classifies `.toolMissing` vs
  `.launchFailure` by the same rule `FailureReason.launchFailure` uses.
- **The one exit-0 failure:** the `JSON Title Set:` section never arrived —
  the incomplete scan that reports success — checked explicitly, never
  inferred from an empty title list. A disc that genuinely has no titles
  parses to an empty `DiscInfo` and stays a success.
- **Warnings, not verdicts, from text:** only the two signatures observed on
  hardware (libdvdcss raw-device fallback; non-fatal subtitle decode errors)
  produce warnings, deduplicated with counts, attached to a success and
  never failing one. No branch invented for unobserved failures (malformed
  IFO data stays uncaptured — swap the disc in first).
- **Progress:** `"Progress": <fraction>` lines log at 25% crossings
  (`▶ Scanning: 50%`) for #0026's scanning state.
- **Scanner-local `Failure` enum** deliberately — adding a `JobStage.scan`
  case would be a wire change (#0007's review); mapping onto the pipeline's
  `JobFailure` (e.g. for #0015's fallback decision) is the call site's job.
- `parseTitleSet` (from #0023) now brace-matches the JSON document, so a
  straggler diagnostics line after the payload — possible now that
  `ProcessRunner` merges stderr into the same stream — cannot corrupt the
  parse.
- `@concurrent` like `Preflight.check`/`PlexOrganizer.move`: a scan takes
  tens of seconds and must not hold the main actor.

**Deviation from the Plan:** the Plan's verification examples used the
makemkvcon fixtures (`keyexpired…exit253` → `.keyExpired`); the Re-triage
deleted MSG handling and the MakeMKV key-expiry failure mode along with it —
HandBrake has no key to expire. The equivalent regression tests exist
against the re-triaged model: real fixture + exit 0 → success; real fixture +
exit 3 → failure whatever the text says; exit 0 + noise-only → `.jsonMissing`.

## Gotchas

- `ProcessRunner` merges stdout and stderr onto one pipe: the JSON and the
  libdvdread/libdvdcss chatter arrive interleaved on one line stream. The
  parser's marker-plus-brace-matching survives this; anything that parses
  "everything after the marker" would not.
- A scanning HandBrake is silent for long stretches (progress arrives in
  bursts), so an inactivity watchdog would kill healthy scans — the scanner
  uses an absolute 15-minute ceiling instead.
- The fixture is stdout-only (`2>/dev/null` at capture time), so the
  end-to-end warning tests use synthetic lines for the two stderr
  signatures; a fuller capture with stderr included would let those be
  tested against real text.

## Description

Changeover never runs `makemkvcon info`. Inserting a disc goes straight to the TMDB
search window (`Changeover/DVDMonitor.swift:15-27` →
`Changeover/AppDelegate.swift:60-65`), and the first time the app touches the drive
is the full-disc rip. A `DiscScanner` has to run the scan, stream its progress, and
— the part that is easy to get wrong — tell an expired MakeMKV key apart from a
disc that genuinely has nothing on it.

## Long Description

The Phase 2 exit criterion is specific: *"Scan failure (expired key, unreadable
disc) is reported as itself, not as an empty title list"* (`Roadmap.md` lines
127–128). That is not a nicety. MakeMKV's free key expires roughly monthly and has
to be refreshed by hand; `RemoteControl.md` line 459 flags it as a recurring
real-world failure, and `MacApp.md` §10 notes it too. An expired key that surfaces
as "this disc has no titles" sends the user looking at the disc instead of at
MakeMKV, and the scan is the first place it can be caught — the current code only
finds out at rip time, tens of minutes later.

### Exit status decides; MSG codes explain

The experiment (`DiscSelection.md`) disproved the approach this ticket was filed
with. It planned to classify failures by matching text in the output. **Two real
discs would be wrongly failed by that.**

`dragon-tattoo-min0.txt` — a scan that exited 0 and ended with
`MSG:5011,0,0,"Operation successfully completed"` — contains:

```
MSG:2003,0,3,"Error 'Scsi error - ILLEGAL REQUEST:READ OF SCRAMBLED SECTOR WITHOUT
AUTHENTICATION' occurred while reading '…' at offset '1048576'"
```

`hornets-nest-min0.txt`, also exit 0 and also `MSG:5011`, contains **28** of:

```
MSG:4004,0,2,"The source file '/VIDEO_TS/VTS_01_1.VOB' is corrupt or invalid at
offset 12288, attempting to work around"
```

Both discs scanned successfully and produced usable title lists. A classifier that
greps for `"Error"`, `"corrupt"` or `"invalid"` fails both. **The exit status is the
verdict; the `MSG` codes are the explanation.**

The corollary matters too: a *successful* scan carrying `MSG:4004` should surface a
**warning** — "28 read errors during scan; the rip may be incomplete" — because the
resulting rip may be silently corrupt and this is the only moment the user is told
before committing forty minutes. That is a warning attached to a success, not a
third outcome. [#0026](0026.md) renders it.

### MakeMKV already solves problems this ticket was going to re-solve

- **`MSG:3025` carries the effective minimum length as a parameter.** Its trailing
  fields are `"1","23","120"` — title, actual length, threshold. The app can *read*
  the threshold MakeMKV applied and assert it matches what was asked for, rather
  than assuming. Given that a threshold mismatch silently renumbers the titles
  ([#0028](0028.md)), that assertion is worth making.
- **`MSG:3026` and `MSG:3027` are MakeMKV's own decoy detection.** 3026 is
  `"Title #3 declared length is 0:00:00 while its real length is 0:00:00 - assuming
  fake title"`; 3027 is `"Title #03 in VTS 1 is equal to title #02 and was
  skipped"`. Both appear in the corpus (3026 on Super Troopers and Super Troopers 2,
  3027 on four discs). The fake-title and duplicate-title filtering is upstream and
  free — log these, do not reimplement them.
- **`MSG:3038`** (`"Cells 20-20 were removed from title end"`) fires on four discs
  and explains small duration discrepancies. Relevant to [#0028](0028.md)'s
  duration tolerance; harmless here.

### A latent bug in the existing subprocess plumbing

This ticket must not inherit it. `RipController`'s `readabilityHandler`
(`Changeover/RipController.swift:31-41`) does:

```swift
let data = handle.availableData
guard !data.isEmpty, let text = String(data: data, encoding: .utf8) else { return }
for line in text.components(separatedBy: .newlines) { … }
```

There is no carry-over buffer, so a line straddling two reads is split into two
fragments and both are logged. For a scrolling log that is cosmetic. For a parser it
silently drops and corrupts records. `String(data:encoding:.utf8)` also returns
`nil` for a chunk that ends mid-multi-byte-sequence, discarding the whole read.

## Steps to reproduce

1. Let the MakeMKV licence key expire (or set `makemkvconPath` in Settings to a path
   that does not exist).
2. Insert a DVD.
3. Search a title, select a poster, click `Start Ripping`.

## Expected behavior

The scan runs on insertion at an explicit `--minlength`, the UI shows a scanning
state while it does, and a failure names itself: "MakeMKV key has expired — refresh
it in MakeMKV.app", "no disc in the drive", "makemkvcon not found at
/opt/homebrew/bin/makemkvcon". A scan that succeeds *with* read errors succeeds, and
says how many.

## Actual behavior

No scan happens at all. With an expired key the rip proceeds, `makemkvcon` exits
non-zero, and the user sees `✗ makemkvcon exited with status N`
(`Changeover/RipController.swift:50-51`) followed by `✗ Ripping failed. Aborting.`
(`Changeover/DVDPipeline.swift:32`) — after having waited for a rip that was never
going to happen.

## Notes

**Split verification honestly.** Error *classification* is a pure function over
`MSG` lines plus an exit status, so it is unit-testable against the fixtures in
`ChangeoverTests/Fixtures/makemkvcon/` with no drive. The three tests that matter
most:

- `keyexpired-v1.18.3-exit253.txt` + exit **253** → `.keyExpired`. It carries
  `MSG:5021` and no `TCOUNT` line at all.
- `dragon-tattoo-min0.txt` + exit 0 → **success**, despite `MSG:2003`.
- `hornets-nest-min0.txt` + exit 0 → **success with a warning naming 28 read
  errors**, despite `MSG:4004` × 28.

The last two are the regression tests for the text-matching mistake; write them even
though they assert a non-failure.

The line-buffering fix is testable by feeding a `DiscScanner` line accumulator a
byte stream deliberately chopped mid-line and mid-UTF-8-sequence. Everything
involving an actual `Process` needs the mini and a disc, and `## Verification` must
say which disc and which failure was provoked.

**The fixture corpus is thin on failures — one run, one exit status.** Two cheap
captures are still missing and should be taken when next at the drive: an empty
drive (`makemkvcon -r info disc:0` with no disc, two seconds) and a current-version
key expiry. Until then, `.noDisc` is classified from reasoning rather than from
evidence, and the ticket should say so rather than implying otherwise.

## Plan

### Files

New: `Changeover/DiscScanner.swift`, `Changeover/DiscScanError.swift` (or one file;
prefer one, it is small).
Changed: `Changeover/DVDMonitor.swift` — surface the mounted volume URL so the
scanner is not guessing which drive.

### Shape

Mirror `RipController` exactly. It is the established pattern in this codebase and
diverging costs more than it gains:

```swift
nonisolated enum DiscScanner {
    static func scan(
        makemkvconPath: String,
        discIndex: Int = 0,
        minLengthSeconds: Int,
        log: @escaping @MainActor (String) -> Void
    ) async -> Result<DiscInfo, DiscScanError>
}
```

`nonisolated static`, matching `Changeover/RipController.swift:9-13` and
`Changeover/EncodeController.swift:9-14`. This is one of the places
`Plan.md`'s convention genuinely requires the annotation rather than merely
permitting it — the scan blocks for tens of seconds (`RemoteControl.md` line 450)
and `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` would otherwise pin it to the main
actor. Do **not** make this an `actor`; `Plan.md` is explicit that the `actor`
keyword is not used for types with no custom isolation needs.

The `log` closure keeps the `@escaping @MainActor (String) -> Void` signature used
throughout, so `JobController` can pass the same closure it passes to
`DVDPipeline` (`Changeover/DVDPipeline.swift:12`).

### Command

```
makemkvcon -r --cache=1 --noscan --minlength=<n> info disc:<index>
```

`--minlength` is load-bearing and turned out to be more so than this ticket assumed.
MakeMKV's default is 120 seconds — read straight out of `MSG:3025`'s third
parameter in `hanna-mindefault.txt` — so `info` hides short titles unless asked.
Worse, **MakeMKV renumbers the titles after applying the filter**, so the threshold
decides not only what is listed but what each index *means*: Hornets' Nest's movie
is title 9 at `--minlength=0` and title 3 at the default. [#0028](0028.md) has the
full worked example.

Three rules:

1. **Always pass an explicit value.** Never inherit the default on either the scan
   or the rip. The app must know the number it ran at.
2. **Pass a low one (0 or 30)** and let Changeover do its own filtering, so the
   app's thresholds are the only thresholds and a 90-second extra remains
   selectable.
3. **Pass the same value to the rip**, carried in `RipRequest`
   ([#0027](0027.md)) rather than re-read from `AppSettings`, so a settings change
   between scan and rip cannot desynchronize them.

Store it in `AppSettings` as `scanMinLengthSeconds` next to the existing string
settings (`Changeover/AppSettings.swift:13-16`), with a matching `Keys` entry
(`:58-63`) and a line in `persist()` (`:48-54`). Note **0 is a legitimate value**,
so load it with `object(forKey:) as? Int`, not `integer(forKey:)`.

Optionally assert the threshold: if any `MSG:3025` appears, its third parameter is
the threshold MakeMKV actually applied. Log a mismatch loudly.

`--noscan` skips enumerating other drives and shaves seconds off. The captures were
taken with it and the `DRV` lines are present — `DRV:0` names the drive, the volume
label and the device path, with `DRV:1` through `DRV:15` as empty placeholders — so
it does not suppress what the scanner needs.

### Process plumbing — the part to get right

Copy the `Process` + `Pipe` + `withCheckedContinuation` skeleton from
`Changeover/RipController.swift:14-63`, with three deliberate changes:

1. **Accumulate stdout into a `Data` buffer rather than logging chunks.** Append
   each `availableData` read to a buffer held by the continuation scope. Extract
   complete lines only up to the last `\n` in the buffer, keep the remainder for the
   next read, and decode line-by-line. This fixes both the split-line and the
   split-multi-byte problems described above. The complete accumulated text is what
   gets handed to `MakeMKVRobotParser.parse` in the termination handler.
2. **Separate stdout from stderr.** `RipController` merges them onto one pipe
   (`Changeover/RipController.swift:27-28`). That is fine for a log and wrong here —
   stderr text interleaved mid-line into stdout would corrupt the record stream.
   Give each its own `Pipe`, parse stdout, keep stderr for the error message.
3. **Log selectively.** Do not echo every `TINFO` line into the user-visible log; a
   disc produces hundreds. Log the `MSG` lines (which are the human-readable ones),
   and drive a progress indication from `PRGV` if [#0021](0021.md) confirms its
   shape. Keep dispatching through `Task { @MainActor in log(line) }` as the
   existing handlers do (`Changeover/RipController.swift:38`) — the handler runs on a
   background thread.

Add a timeout. A scan that hangs on an unreadable disc currently has no ceiling; a
few minutes with `Task.sleep` racing the continuation, terminating the process and
returning `.timedOut`, is enough. Make the task cancellable too, since Phase 3
([#0040](0040.md)) will want to abandon a scan when the user ejects.

### Error classification

```swift
nonisolated enum DiscScanError: Error, LocalizedError {
    case makemkvconNotFound(path: String)
    case launchFailed(String)
    case keyExpired
    case noDisc
    case discUnreadable
    case noTitles
    case timedOut
    case failed(status: Int32, message: String)
}
```

Give each a real `errorDescription`, following the pattern already set by
`TMDBError` (`Changeover/TMDB/TMDBModels.swift:41-56`), whose messages name the
actual problem and the actual fix ("Get a free API key from themoviedb.org and enter
it in Settings"). `.keyExpired` should say to refresh the key in MakeMKV.app.

Classify in this order, and write the order down in a comment because it is the
substance of the exit criterion. **The ordering principle is the finding: exit
status decides whether it failed; `MSG` codes decide what to call the failure.**

1. `FileManager.fileExists` on `makemkvconPath` *before* launching →
   `.makemkvconNotFound`. This is a cheap check that turns a confusing launch error
   into a precise one, and the path is user-editable in Settings
   (`Changeover/SettingsView.swift`) so it is a realistic failure.
2. `process.run()` throwing → `.launchFailed`.
3. **Exit status 0 → not a failure.** Stop here. Do not inspect the messages for
   error-shaped text; `MSG:2003` and `MSG:4004` both occur on successful scans.
   Emit a warning (not an error) if `MSG:4004` is present, carrying the count.
4. Non-zero exit, `MSG:5021` present → `.keyExpired`. Match the **numeric code**;
   the English text is not stable across versions. The captured case is exit 253 on
   v1.18.3.
5. Non-zero exit, `MSG` codes indicating no disc / open tray → `.noDisc`. **No
   fixture exists for this yet** — implement it from the code MakeMKV emits when
   the capture is taken, and until then do not pretend the branch is verified.
6. Non-zero exit with none of the above → `.failed(status:message:)`, carrying the
   last few `MSG` lines so the user sees something specific.
7. Exit 0 with zero titles → `.noTitles`. This is now a narrow branch — it cannot
   absorb cases 4–6, because those all exit non-zero — and it is still worth a
   dedicated test.

`.discUnreadable` deserves a second look before it is implemented. On the evidence,
an unreadable disc is not a distinct *outcome*: Hornets' Nest is physically damaged
and scans fine. Either drop the case or define it as "non-zero exit with `MSG:4004`
present", and say which.

The classification function should take `[RobotMessage]` and an `Int32` and return
`DiscScanError?`, so it is testable without a `Process` — and a second function
should take the same inputs and return `[DiscScanWarning]`, so the read-error
warning has somewhere to live that is not the error type.

### Wiring

`DVDMonitor` (`Changeover/DVDMonitor.swift:3-27`) currently discards the volume URL
after checking for `VIDEO_TS` (`:21-22`). Change `onDVDInserted` to
`onDVDInserted: ((URL) -> Void)?` and pass it through — the scanner does not need it
today (`disc:0` is fine for a single-drive mini) but the volume name is a useful
fallback for `DiscInfo.volumeName` and Phase 3 will want to know which disc mounted.
Keep `volumeMounted` `nonisolated` and keep the hop to the main actor at
`:24-26`; it is an `@objc` selector called by `NSWorkspace` on an arbitrary thread
and that annotation is correct.

`AppDelegate.startDVDMonitor` (`:60-65`) should hand the event to Phase 1's
`JobController` ([#0001](0001.md)) rather than calling `showMetadataEntry()`
directly, so the scan starts immediately on insertion and runs while the user is
still choosing a poster — or, in Phase 4, still walking back to the couch. If
[#0001](0001.md) has not landed, start the scan from `AppDelegate` and leave a
`// TODO: move to JobController` — do not put the scan state in
`MetadataEntryView`'s `@State`, which is precisely what Phase 1 is removing.

## Re-triage

**2026-09-11 — rewrite against HandBrake; the failure modes are different.** Per
`MakeMKVReplacement-Path.md` §4. The ticket stays `open` and its core requirement
is unchanged: **a failed scan and a disc with no titles must not look identical.**
What changes is the tool being run and the material available to explain a failure
with.

The command becomes
`HandBrakeCLI -i <VIDEO_TS path> --scan --title 0 --min-duration 1 --json`, with
`--title 0` mandatory (see [#0023](0023.md)'s re-triage — without it the scan
succeeds, returns valid JSON, and is silently incomplete, which is precisely the
"looks like success" failure this ticket exists to prevent).

**The error-classification section needs rebuilding.** It is written around
MakeMKV's `MSG` codes, and this ticket's own argument — *"MakeMKV already solves
problems this ticket was going to re-solve"* — was that those codes explain a
failure that the exit status merely reports. HandBrake has no equivalent. Exit
status still decides; what explains it is different material, and the specific
failure modes observed on hardware are these:

- **libdvdcss cannot open the raw device and falls back.**
  `MakeMKVReplacement-Results.md` §5 is the one real reliability concern in the
  whole exercise: `libdvdread: Could not open /dev/disk6 with libdvdcss` →
  `Attempting to retrieve all CSS keys` → 17 keys, every one at `Elapsed time 0`,
  then `Found 4 VTS's`. It succeeded, instantly, but it is running the path
  libdvdread itself describes as slow and last-resort, and a disc where the
  fallback does not hold *"would fail, and the failure would be a CSS error rather
  than an obvious one."* This is the signature most worth recognizing and reporting
  as itself.
- **Subtitle decode errors that are not fatal.** `ERROR: unable to decode subtitle
  with 2019 bytes.` appeared on the very first disc tested and the encode completed
  anyway. A classifier that treats any line containing `ERROR` as a failure will be
  wrong on disc one.
- **An incomplete scan that reports success.** Covered above; worth an explicit
  sanity check rather than only a parse.
- **Malformed IFO data.** *The IT Crowd* disc reports it and MakeMKV handled it
  gracefully; HandBrake's behavior is **untested**
  (`MakeMKVReplacement-Results.md` §11). Do not write a classifier branch for it
  from imagination — swap the disc in and capture what actually happens.

**The exit-status-decides principle survives and is still right.** So does the
latent subprocess-plumbing bug documented in this ticket; it is a `Process`
concern, not a MakeMKV one, and it applies to a HandBrake scan identically.

Relationship to [#0015](0015.md): a scan failure is one of the signals that should
trigger the MakeMKV fallback, so the classification this ticket produces feeds that
decision. Not every failure qualifies — see [#0015](0015.md)'s plan.
