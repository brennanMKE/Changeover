# 0012 — PlexOrganizer deletes the existing library file before the replacement is verified, so a failed re-rip destroys the copy you had

|---|---|

## Description

`PlexOrganizer.move` removes an existing destination file before moving the new one into place:

```swift
if fm.fileExists(atPath: destPath) {
    try fm.removeItem(atPath: destPath)
}
try fm.moveItem(atPath: encodedFile, toPath: destPath)
```

(`PlexOrganizer.swift:29-32`). Re-ripping a movie that is already in the library therefore destroys the copy you had **before** the replacement is known to be good. This is data loss, not a bug with a workaround — the deleted file is gone from a Plex library, not recoverable from a working folder.

### What fails review

`FileManager.replaceItemAt(_:withItemAt:)` requires both items on the **same volume**. Probed on this machine with a throwaway APFS disk image (`hdiutil create -size 32m -fs APFS`, attach, run `replaceItemAt(dest, withItemAt: encoded)` for each arrangement, detach):

| Case | Result | Destination afterwards | Encoded file |
|---|---|---|---|
| same volume, no existing destination | OK | new bytes | moved |
| same volume, destination exists | OK | new bytes | moved |
| same volume, destination exists, source folder locked | throws 513 `NSFileWriteNoPermissionError` | **original intact** | still in source |
| **cross-volume, no existing destination** | **throws 512 `NSFileWriteUnknownError`** | absent | still in source |
| cross-volume, destination exists | throws 512 | original intact | still in source |
| cross-volume, destination exists, source locked | throws 512 | original intact | still in source |
| cross-volume, source on the image, destination local | throws 512 | original intact | still in source |

Three consequences:

1. **Regression.** Before `9e3ef5a`, `moveItem` copied across volumes and every configuration worked (destructively). After it, a working-encode folder and a Movies folder on different volumes fail **every** job at the organize stage — including the first rip of a movie with nothing at the destination. It is latent today only because `AppSettings` derives both from `plexMediaRoot`; it goes live the moment `<root>/Movies` is a separate mount point or a symlink, or Phase 3 puts the encode folder on the internal SSD — which [#0040](0040.md) already discusses as the way to stop the encode fighting the rip for SSD bandwidth. The plan's `### Risks` said exactly this: *"Cross-volume `replaceItemAt` is not atomic. Detect the same-volume case and treat the cross-volume case as a plain sequence with an explicit backup."*
2. **The failure is opaque.** Error 512 maps to `.unknown("The file … couldn't be saved in the folder …")` — no path, no hint that a volume boundary is the cause.
3. **`## Gotchas` bullet three is false** — *"`replaceItemAt`'s internal temp file lands on the destination's volume before the atomic rename, so even a cross-volume replace never risks the original … confirmed by reasoning about the primitive's documented behavior."* It never gets that far. That sentence would send the next person, adding a working-directory setting, in exactly the wrong direction. Correct it.

Also worth noting, non-blocking: the source-locked failure is surfaced as `.destinationUnwritable(path: <Movies folder>)`, naming a folder that is in fact writable. The test does not assert the reason (correctly), and the mis-mapping is the same class the #0007 review already handed to [#0009](0009.md); leave it there.

### What the next pass must do

- **Stage on the destination volume before the swap.** The API is built for this: `fm.url(for: .itemReplacementDirectory, in: .userDomainMask, appropriateFor: destURL, create: true)` returns a temporary directory on `destURL`'s volume, outside `Movies/`. `moveItem` the encoded file there — a rename on the same volume, a copy-then-delete across volumes, and Foundation keeps the source if the copy fails — then `replaceItemAt(destURL, withItemAt: staged)`. If anything throws after staging, move the staged file back to `encodedURL` (or, failing that, log where it is) so the encoded file is never lost. Detecting same-volume via `URLResourceKey.volumeIdentifierKey` and keeping the current single call for that case is an acceptable alternative shape; the cross-volume branch still needs the staged copy either way.
- The requirements, stated as properties: cross-volume works; a pre-existing library file survives every failure path; the encoded file is never lost; nothing is ever left inside `Movies/`. Keep `nonisolated static` and `throws(JobFailure) -> URL`.
- **Tests.** All four `move` tests must still pass unchanged. A unit test cannot fabricate a second volume, so verify the cross-volume branch with the same `hdiutil` probe described above and record it in `## Verification` as manual, naming the arrangement exercised. If a seam is added to force the staged path, add a test that the original survives a failure injected after staging.
- **Correct `## Gotchas`** so the record is true.

## Root cause

`PlexOrganizer.move` called `removeItem` on the destination unconditionally, then `moveItem` the new encode into place, with no protection against a failure in the gap between the two calls. `removeItem` succeeding is not evidence that `moveItem` will also succeed — a cross-volume move, a permission change, or a full disk between the two calls left the library missing a file with nothing having replaced it, and the job reported only a generic organize failure with no indication the original was gone.

## Fix

Replaced the manual `removeItem` + `moveItem` sequence with `FileManager.replaceItemAt(_:withItemAt:)`. This primitive stages the incoming file and performs the destructive swap over the destination only once that staging has fully succeeded — if anything throws before that (permissions, disk full, an unplugged volume), the pre-existing destination file, if any, is left exactly as it was. When nothing exists at the destination yet, the same call degrades to a plain move, so the no-collision path is unchanged.

This is a smaller diff than the plan's suggested manual "temp name in destination folder, then rename or `replaceItemAt`" dance — empirically, `replaceItemAt` already handles the case where nothing exists at the destination (verified with a standalone Swift script before writing the fix), so the extra `fileExists` branch and manual temp-file bookkeeping the plan describes were unnecessary. `FileManager` owns temp-file placement and cleanup internally on both the success and failure paths, so there's no leftover dotfile for Plex to scan.

Deliberately **not** in scope for this pass: the plan's "decision to make deliberately" (refuse silently-destructive overwrites vs. overwrite vs. backup) and the `AppSettings`-gated unattended-overwrite flag it floats for Phase 3. The issue's own Scope note restricts this ticket to `PlexOrganizer` and explicitly excludes `AppSettings`, so implementing a user-facing "refuse by default with an explicit path forward" would require UI/settings work outside that boundary. What's landed here removes the actual data-loss window unconditionally, which is the load-bearing part of the bug; the overwrite-policy UX is a reasonable follow-up ticket rather than part of this fix.

No new `FailureReason` case was added. The failure this fix's tests exercise (permission denied on the swap) already maps to the existing `.destinationUnwritable` case via `reason(for:destination:)`, confirmed empirically to be `NSFileWriteNoPermissionError` (code 513) for both `moveItem` and `replaceItemAt` failures — same vocabulary, same mapping.

## Gotchas

- `FileManager.replaceItemAt` is undocumented-but-verified (via a throwaway Swift script, not just API docs recollection) to fall back to a plain move when nothing exists at the destination yet — this let the implementation stay a single call instead of the plan's two-branch `fileExists` dance, without losing any of the safety guarantee.
- The first attempt at the regression test used the wrong permission target (destination folder) and gave a false sense of coverage — it passed both before and after the fix, because `removeItem` and `moveItem`/`replaceItemAt` fail for the *same* reason when the destination directory itself is unwritable. The falsification step in this workflow is exactly what caught this; the corrected test locks the *source* folder instead, which is the only way to make `removeItem` succeed while the replacement step still fails.
- Cross-volume behavior: `replaceItemAt`'s internal temp file lands on the destination's volume before the atomic rename, so even a cross-volume replace never risks the original — the non-atomic part (copying new content across volumes) happens entirely before the destructive swap. Not separately unit-tested here (no way to fabricate a second real volume in CI), but confirmed by reasoning about the primitive's documented behavior and the permission-failure experiments above, which show the original surviving in every failure path exercised.

## Long Description

The delete-then-move ordering is unsafe in three separate ways, and they compound.

**1. The window between the two calls is unprotected.** `removeItem` succeeds, then `moveItem` throws — a cross-volume move that fails partway, a full destination volume, a permissions change, an unmounted `plexMediaRoot`. The catch block (`PlexOrganizer.swift:33-37`) logs and throws a `JobFailure`, correctly, but by then the old file is already gone. The job reports failure and the library is worse off than if the job had never run.

**2. The new file is never verified to be better — or even valid.** The pipeline treats HandBrake exit 0 as success (`EncodeController.swift:58-68`), and `MakeMKVReplacement-Results.md` §11 records the reason that is not enough: *"A corrupt rip still produces a file, so spot-check playback, not exit codes."* A disc with bad sectors can produce an exit-0 encode of a truncated or artefacted title. Today that file silently replaces a known-good one.

**3. The trigger is ordinary, not exotic.** The destination is fully determined by TMDB metadata — `Movies/Title (Year) {tmdb-ID}/Title (Year).mp4` — so *any* second rip of the same movie collides by construction. Re-ripping to get a better encode, re-ripping after fixing settings, and re-ripping because the first attempt looked wrong are all normal things to do, and each one is a one-way door. `Movies.txt` shows a library of 33 titles already on disk; every one of them is a live target.

The collision is also more likely than it looks under [#0003](0003.md): a stale-file mix-up files movie A's content under movie B's name, and the natural corrective action is to re-rip B — which then deletes the one copy of B, if B had ever been ripped correctly.

## Steps to reproduce

1. Rip a movie end to end so `Movies/Title (Year) {tmdb-ID}/Title (Year).mp4` exists and plays.
2. Make the destination folder unwritable after the encode starts — `chmod a-w` the movie folder, or unmount `plexMediaRoot` mid-encode. (Any `moveItem` failure will do; this is the cheapest to stage.)
3. Rip the same movie again. Search the same TMDB entry so the destination path is identical.
4. `removeItem` deletes the existing file, `moveItem` throws, the log prints `"✗ ERROR moving file: …"` and the job returns `.failed(.organize, .destinationUnwritable(...))`.
5. The library file is gone. The encoded replacement is still sitting in the working encode folder, unnamed and unfiled.

## Expected behavior

The existing library file survives until the replacement is in place. Concretely: move the new file to a temporary name in the destination folder, confirm it landed, then swap — and only then remove the old file, or keep it as a `.previous` sidecar for the user to delete. A failure at any step leaves the library exactly as it was.

Better still, refuse silently-destructive overwrites outright: a destination that already exists is a decision, not a detail. Either report it as a distinct outcome the user can act on, or write beside it, but do not delete first and hope.

## Actual behavior

`removeItem` runs unconditionally whenever the destination exists, before `moveItem` is attempted and with no verification of the incoming file beyond the encoder's exit status. A failure after the delete leaves the library missing a movie and the job reporting a generic organize failure.

## Notes

`FileManager` has a primitive for exactly this: `replaceItemAt(_:withItemAt:backupItemName:options:)`, which performs the swap atomically where the filesystem supports it and can retain a backup. It is a better fit than hand-rolling delete-then-move, and it removes the window entirely on a same-volume move. Note that a cross-volume replacement is *not* atomic — `plexMediaRoot` is typically an external SSD while the working folders may or may not be on the same volume (`AppSettings.swift:27,30` derive both from the same root today, but the user can repoint them).

Entirely unit-testable with no disc: `JobOutcomeTests` already exercises `PlexOrganizer.move` against a temp directory with `chmod 0o500` (see [#0007](0007.md)'s `moveThrowsWhenDestinationIsUnwritable`). The regression test is the same shape — pre-create a destination file with known bytes, make the move fail, assert the original bytes are still there afterwards. Write it and run it; that test fails today.

A new `FailureReason` case may be wanted for "destination already exists and was not replaced". [#0007](0007.md) owns the vocabulary and [#0009](0009.md) owns turning it into text; add the case there rather than inventing a string here.

## Plan

### `Changeover/PlexOrganizer.swift`

Replace lines 29-32. The shape:

1. Move `encodedFile` into the destination folder under a temporary name in the same directory (same volume as `destPath`, which matters for atomicity).
2. If nothing exists at `destPath`, rename the temporary into place and return.
3. If something does exist, use `fm.replaceItemAt(destURL, withItemAt: tempURL, backupItemName: …, options: [])` and let `FileManager` own the swap. Keep or discard the backup per the decision below.
4. On any throw, clean up the temporary file and leave the original untouched, then throw the `JobFailure` as today.

Keep `move` `nonisolated static` and keep its `throws(JobFailure) -> URL` signature (`PlexOrganizer.swift:13-18`) — the typed-throws discipline from [#0007](0007.md)'s gotchas applies, and widening it to `any Error` will break callers.

### The decision to make deliberately

Overwrite silently, refuse, or keep a backup? Recommend **refuse by default** with an explicit user-visible path forward, because a Plex library is not a scratch directory and the current behavior is silent. If the pipeline must be able to overwrite unattended (Phase 3 wants that), gate it on an `AppSettings` flag and still write the replacement beside the original first. Do not make the unattended queue's convenience the default for a single interactive rip.

### Risks

- **Do not verify by size.** [#0028](0028.md) already documents why file size is not evidence about content; the same argument applies to "the new file is bigger so it must be fine."
- **Cross-volume `replaceItemAt` is not atomic.** Detect the same-volume case and treat the cross-volume case as a plain sequence with an explicit backup, rather than assuming the API's guarantee holds everywhere.
- **Leftover temporaries in the Plex Movies folder are worse than leftovers in a working folder** — Plex will try to scan them. Use a name Plex ignores (a leading dot) and delete it on every failure path.
