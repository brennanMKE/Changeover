# 0232 — `status` shows the previous disc's job against a newly inserted disc

| | |
|---|---|
| **Status** | resolved |
| **Phase** | 4 — Agentic control |
| **Module** | ChangeoverBridge / BridgeStatusReader / JobController |
| **Platform** | macOS |
| **First seen** | 2026-10-07 |
| **Closed** | 2026-10-08 |

## Description

After one disc is imported and ejected and a new disc is inserted,
`changeoverctl status` still shows the **previous** disc's job block beside the
new disc's name. Observed with PITCH_BLACK in the drive and Pacific Rim:
Uprising's job id, film and 17 extras still listed next to it.

The disc half of the projection updates on insertion; the job half keeps
reporting the last job the app ran.

## Why this matters

The two halves of one `status` response disagree about which disc they describe,
and nothing in the output says so. An agent reading it sees a disc with a
completed job already attached and can reasonably conclude this disc has been
imported — the opposite of the truth. The #0196 acting verbs are gated on
`status` being an accurate picture of the present, so this undermines the whole
agentic flow rather than being a cosmetic wart.

## Fix

**Cleared, not tagged** — the user's call, and the better one: *"once a disc is
ejected the state should essentially be cleared except for history. We should
not be holding onto previous disc state."*

Tagging would leave the stale block on screen and ask every reader to notice a
field saying to disregard it. Clearing says the only true thing, which is that
nothing is happening with the disc in the drive. Nothing is lost either —
`report` reads `jobs.history` directly, and a finished job belongs there.

A job now records the insertion it was started for (`Job.discInsertionID`,
stamped in `JobController.start`), and `BridgeStatusReader.jobStatus` returns
`nil` for a finished job whose insertion is not the one in the drive.

Keyed on the **insertion**, never the volume path: a path is equal across two
visits of the same disc, so it cannot tell "still here" from "taken out and put
back" — and a disc put back in is a new visit whose old job is just as stale as
another disc's. This is the same key #0196's `import` already refuses on, and
the one #0152 introduced so one physical insertion stays one insertion.

A job with no recorded insertion predates the field and belongs to nothing, so
it clears with the disc rather than lingering. The safe direction, since the
harm here is a stale block being believed.

## Files changed

- `Changeover/StaleJobRule.swift` (new) — the decision as a plain value, so it
  is readable and testable without a `JobController`
- `Changeover/Jobs/Job.swift` — `discInsertionID`
- `Changeover/JobController.swift` — stamps it at start
- `Changeover/BridgeStatusReader.swift` — applies the rule
- `ChangeoverTests/StaleJobStatusTests.swift` (new)

## Relation

The familiar shape: #0211 resolved the disc at point of use and #0214 then had
to fix `discStatus`, which still reported the value decided at classification.
This is the same class of fault one level up — a rule that is right in the app
and a projection that reports an older state. Keyed on `insertionID`, which
#0152 introduced precisely so one physical insertion stays one insertion.

Related to #0231: both are `status`/`library` projections misreporting state
that the app itself has correct.
