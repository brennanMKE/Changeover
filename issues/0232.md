# 0232 — `status` shows the previous disc's job against a newly inserted disc

| | |
|---|---|
| **Status** | open |
| **Phase** | 4 — Agentic control |
| **Module** | ChangeoverBridge / BridgeStatusReader / JobController |
| **Platform** | macOS |
| **First seen** | 2026-10-07 |

## Description

After one disc is imported and ejected and a new disc is inserted,
`changeoverctl status` still shows the **previous** disc's job block beside the
new disc's name. Observed with PITCH_BLACK in the drive and Pacific Rim:
Uprising's job id, film and 17 extras still listed next to it.

The disc half of the projection updates on insertion; the job half keeps
reporting the last job the app ran.

## Why this matters

The two halves of one `status` response disagree about which disc they describe,
and nothing in the output says so. An agent reading it sees a disc with a
completed job already attached and can reasonably conclude this disc has been
imported — the opposite of the truth. The #0196 acting verbs are gated on
`status` being an accurate picture of the present, so this undermines the whole
agentic flow rather than being a cosmetic wart.

## Suggested fix

Either clear the job block when the insertion id changes, or tag it with the
insertion it belongs to so a reader can see it is stale. Tagging is probably
better than clearing: "the last job on this machine was X, for a different
disc" is useful information, and silently emptying the block loses it.

Whichever is chosen, the job block and the disc block must agree about which
insertion they describe, and that agreement should be the thing that is tested.

## Relation

The familiar shape: #0211 resolved the disc at point of use and #0214 then had
to fix `discStatus`, which still reported the value decided at classification.
This is the same class of fault one level up — a rule that is right in the app
and a projection that reports an older state. Keyed on `insertionID`, which
#0152 introduced precisely so one physical insertion stays one insertion.

Related to #0231: both are `status`/`library` projections misreporting state
that the app itself has correct.
