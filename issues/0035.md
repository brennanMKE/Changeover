## Description

Since #0026 the user can choose which title to encode, and `JobController.start` passes HandBrake `.index(n)`. When the direct HandBrake encode fails and the #0015 MakeMKV fallback runs, `MakeMKVRipper.rip()` takes no title argument and still picks the longest title, then encodes the one-title `.mkv` with `.index(1)`. A title picked by hand (a Play All override, an unidentified disc, or "Not this one?") is silently replaced by the longest title, which gets filed under the chosen movie's name. On a TV-season disc, the longest title is exactly the Play All title that #0025 refuses to call a movie.

Found during the #0026 review, which added a comment at the call site. Nobody has reproduced it with a disc, because the fallback only runs after a HandBrake failure.

   MakeMKV drops title #03 as "equal to #02". A HandBrake pick of either
   8:21 title matches the single survivor, which MakeMKV has judged to

   Titles HandBrake lists but makemkvcon filters out (under 120 s) find no

3. **The `.single` regression is accepted: refusal, with no tiebreak.**
   Take a disc where makemkvcon lists two titles within 1% of the feature,
   such as seamless-branching language or credit variants. The old code
   ripped the longest, and the new code refuses.

   That is the right product behaviour. The ticket says never guess. Both
   candidates are the same length to within the tools' own measurement
   error, so "longest" picks a variant, not the one HandBrake was told to
   encode. A narrower tiebreak isn't safe either: "the unique title within
   2 s wins" fails on the Dragon Tattoo evidence, where the true match is
   7 s off, and could pick a neighbouring variant instead.

   The cost is small: this path runs only after HandBrake has already
   failed. The refusal names every candidate with its duration in the log,
   and the original HandBrake failure stays the headline.

   The same logic refuses 2 of 6 *The IT Crowd* episode picks
   (23:34 and 23:44 are 10 s apart, inside 14 s). That is also accepted.

## Root cause

`MakeMKVRipper.rip()` never received any information about which title
HandBrake had been told to encode — only `discMountPath` and
`jobDirectory`. It always ran `chooseTitle(allTitles)` (longest duration,
ties to lowest index) after its own `info` scan, regardless of what the
user had picked. `DVDPipeline.runFallback` had a comment acknowledging
this (a HandBrake title index isn't a makemkvcon index, so nothing was
passed across) but never supplied the one thing the two tools *do* share:
duration.

Separately, per the #0031 review/handoff, extras were still sent to
HandBrake after a MakeMKV-fallback feature succeeded, even though that
HandBrake had just failed on this same disc and would likely fail the
same way on the extras too — `DVDPipeline.run()`'s extras loop had no
`producedBy` check at all.

## Fix

- Added `EncodeSelection.featureDurationSeconds: Int?` — the chosen
  title's duration from HandBrake's own scan (`DiscTitle.durationSeconds`),
  set by `EncodeSelection.make(request:disc:)` alongside the title index,
  and `nil` only for `.phase1`/`.mainFeature` (no scan ever happened, e.g.
  in the ~25 pre-existing test construction sites).
- Added `MakeMKVRipper.matchTitle(_:toDurationSeconds:)`, a pure function:
  matches makemkvcon's `info`-scan titles against a target duration within
  `max(2, target / 100)` seconds (2s or ~1%, whichever is larger — absorbs
  each tool's own rounding). Returns the single title inside that
  tolerance, or `nil` — never a guess — when zero or more than one title
  qualifies.
- `MakeMKVRipper.rip(...)` gained a `targetDurationSeconds: Int? = nil`
  parameter. When set, it uses `matchTitle` instead of `chooseTitle` and,
  on no unique match, refuses with `JobFailure(stage: .rip, reason:
  .unknown(...))` and a log line naming the target duration and every
  candidate title — never falling through to "pick the longest" as a
  silent recovery. When `nil` (no title was ever explicitly chosen), it
  keeps the pre-#0035 `chooseTitle` behaviour byte for byte, so `.phase1`
  and the many existing test call sites are unaffected.
- `DVDPipeline.runFallback` threads `selection.featureDurationSeconds`
  through as `targetDurationSeconds`; the doc comment that used to justify
  "keeps choosing its longest title" was rewritten to describe the fix.
- Distinguished "no titles at all" (`.noTitlesProduced`, pre-existing)
  from "titles exist but none/more than one matched" (`.unknown(...)`,
  new) so the failure reason explains which happened. (Review, 7035d96:
  the `.unknown` detail string was reworded into a sentence for
  `FailurePresenter`; see Resolution notes §5.)
- Decided **not** to add a new `FailureReason` case for the
  no-unique-match refusal — `.unknown(String)` already exists for
  "anomalies Changeover observes itself" (`FallbackPolicy`'s own doc
  comment), and the "wrote more than one `.mkv` file" case right next to
  it in the same function already sets this precedent.
- Extras-on-fallback (#0031 handoff, orchestrator decision, implemented
  here since it shares this ticket's `DVDPipeline.run()` surface):
  `run()`'s extras block now checks `producedBy == .makemkvFallback`
  first. On the fallback path, extras are skipped entirely, one log line
  explains why (naming #0035), and the feature's own outcome — already
  `.succeeded` by the time extras are considered — is untouched. Off the
  fallback path, behaviour is unchanged.
- The fallback audio question from the #0027/#0031 handoffs was already
  resolved before this ticket started: `fallbackAudio` stays
  `.sourceDefault` (`EncodeSelection.make`), unchanged here.
- No new `RippableTitle`/`FailureReason` fields; no changes to
  `FallbackPolicy` (eligibility for attempting the fallback at all is
  orthogonal to which title gets ripped once it does).

## Gotchas

- `dragon-tattoo-min0.txt`'s five titles (9471s, 14s, 9s, 15s, 28s) are
  close enough together that a target of 15s matches *two* titles (14s
  and 15s, both within the 2s floor tolerance) — useful for the ambiguous
  case, but it meant the "non-longest, unique" test had to target 28s
  instead of 15s to get a clean single match.
- The `if producedBy == .makemkvFallback` extras-skip check reuses the
  same condition as the pre-existing "Produced by: …" log line a few
  lines above it in `run()` — two separate `if` statements, not a shared
  `let`, since the first only ever logs and the second changes control
  flow; grep for the line number, not just the text, when touching either
  one (the falsification above had to target line 466, not the first
  match at line 446).

## Expected behavior

The fallback rips the title the user chose, or it refuses to run and says why. It never substitutes a different title.

## Plan

- Pass the chosen title into the fallback as a duration (seconds from the HandBrake scan), not an index. HandBrake and MakeMKV number titles differently and can't be mapped index to index.
- The fallback picks the makemkvcon title whose duration matches within a small tolerance (for example ±2 s, or 1%), using the robot-mode parser/model already present. Put that match in a pure, unit-tested function. If there is no unique match, refuse the fallback with a clear `JobFailure`, never guess.
- Keep today's behaviour when the job used the heuristic's `.single` answer and durations agree.
- Unit-test the matcher and the refusal. A real fallback run needs a disc and an induced HandBrake failure, so that stays manually unverified.
