# 0070 — The host has no validation or arbitration layer, so a remote command is executed as sent

| | |
|---|---|
| **Status** | open |
| **Phase** | 4 — Remote control from a Mac |
| **Module** | RemoteServer / ChangeoverProtocol |
| **Platform** | macOS |
| **First seen** | 2026-09-11 |

## Description

Nothing sits between a decoded `RemoteCommand` and the `JobController`. Two clients could start two rips at once, an observe-only peer could send `startRip`, and — most seriously — a `RipRequest` whose `MovieMetadata.title` contains `../` or a leading `/` would make the host write outside the Plex library, because the destination folder is built by string interpolation from client-supplied text.

## Long Description

Three separate problems share one fix — a single validation and arbitration layer
every command passes through before it reaches `JobController`.

**1. Path traversal into the media volume.** `MovieMetadata.folderName` is
`"\(title) (\(year)) {tmdb-\(tmdbID)}"` (`Changeover/MovieMetadata.swift:17-19`) and
`PlexOrganizer` joins it onto `AppSettings.plexMoviesPath`
(`Changeover/AppSettings.swift:21`). Today `title` always comes from a TMDB API
response via `MovieMetadata(from:)` (`MovieMetadata.swift:10-14`), so it is
trustworthy by construction. **Phase 4 breaks that assumption**: the title arrives
inside a `RipRequest` over the network, and `RemoteControl.md` explicitly routes
TMDB search to the client so only the chosen result is sent. A title of
`../../../../Users/brennan/Library/LaunchAgents/x` produces a real path outside the
library, on a host that is **unsandboxed** (`ENABLE_APP_SANDBOX = NO`,
`project.pbxproj:402`, `:431`) and therefore has the filesystem privileges of the
logged-in user. `RemoteControl.md` does not mention this anywhere; it is the most
concrete security consequence of the whole phase and it is currently unowned.

The same applies to `fileName` (`MovieMetadata.swift:22-24`), to `titleIndices`
passed to `makemkvcon` as process arguments, and to language codes if they are ever
interpolated into a HandBrake argument string.

**2. Capability enforcement.** [#0067](0067.md) defines `Capability.permits(_:)`.
Somebody has to call it, on every command, and return a reason when it says no.

**3. Multi-client arbitration.** `RemoteControl.md`: "Two connected clients must not
start two rips. The `JobController` is the serialization point; commands invalid for
the current state are rejected with a reason." The Phase 4 exit criterion is "two
connected clients cannot start conflicting jobs." Rejection with a *reason* is the
requirement — a silently ignored command is indistinguishable from a dropped packet
and will be retried.

There is also a scoping decision to close here. `RemoteControl.md` open question 3
asks how much of Settings the remote should expose, noting that editing the Plex
root remotely "expands the trust surface." It does — a remote that can set
`plexMediaRoot` (`AppSettings.swift:13`) or `makemkvconPath` (`:14`) can redirect
every future write or **choose which binary the host executes**, which turns a
media-library write into arbitrary code execution. The answer for v1 is no: there is
no settings-mutating command in the protocol, and that absence should be recorded as
a deliberate decision rather than an oversight, because the next person to add a
command will not know.

## Steps to reproduce

1. Two clients connect to the host; both press Start on different movies.
2. Separately, a client paired with observe-only capability sends `startRip`.
3. Separately, a client sends a `RipRequest` with
   `metadata.title = "../../../Shared/evil"`.

## Expected behavior

The second Start is rejected with a reason the client can display ("A rip is already
running"). The observe-only peer is rejected with `.notPermitted`. The traversing
title is rejected with `.invalidRequest` and never reaches `PlexOrganizer`, with the
attempt logged on the host.

## Actual behavior

There is no layer to do any of it. Written the obvious way, all three commands would
be executed: two concurrent rips, an unauthorized rip, and a write outside the media
library.

## Plan

**One chokepoint.** Add `CommandValidator` in the app target. `RemoteServer`
([#0068](0068.md)) calls it for every decoded command and never calls `JobController`
directly:

```swift
enum CommandDecision {
    case allow(ValidatedCommand)
    case reject(RejectionReason)
}

func validate(_ command: RemoteCommand,
              from peer: PairedPeer,
              given state: [JobState]) -> CommandDecision
```

Returning a distinct `ValidatedCommand` type — not the original `RemoteCommand` — is
what makes the check unforgettable: `JobController`'s remote entry point accepts only
`ValidatedCommand`, so bypassing the validator is a compile error rather than a code
review question.

**Layer 1 — authorization.** `peer.capability.permits(command)` from
[#0067](0067.md). Exhaustive `switch`, no `default`.

**Layer 2 — request sanitization. This is the layer that does not exist in any
design document and must not be skipped.** Put it in the package from
[#0061](0061.md) so client and host share one definition and the client can
pre-validate and show the error before sending:

```swift
extension MovieMetadata {
    func validated() throws -> MovieMetadata
}
```

Rules:

- `title`: reject if it is empty, contains `/`, `\`, a null byte, any control
  character, or a path component equal to `.` or `..`; reject a leading `.`; cap at
  a sane length (say 200 characters). Prefer **rejecting** over sanitizing —
  silently rewriting a title produces a folder Plex will not match, which is a
  confusing bug, whereas a rejection is a clear message.
- `year`: exactly four digits, or the literal `—` that `TMDBMovie.yearText` produces
  when `releaseDate` is missing (`Changeover/TMDB/TMDBModels.swift:33-36`).
- `tmdbID`: digits only. It is `String` today (`MovieMetadata.swift:8`) purely
  because it is interpolated; validate it as an integer.
- `titleIndices`: non-empty, each `>= 0`, below a ceiling, count below
  `ProtocolLimits`, no duplicates. These become `makemkvcon` arguments
  (`Changeover/RipController.swift:19-24`, where `"all"` is the literal today).
- `audioLanguages` / `subtitleLanguages`: match `^[a-z]{3}$`, matching the `["eng",
  "spa"]` form in `RemoteControl.md`.

**Belt and braces at the filesystem boundary.** Independently of the validator, make
`PlexOrganizer.move(...)` resolve its destination and assert it is still inside
`plexMoviesPath` before writing — compare
`URL(fileURLWithPath:).standardizedFileURL.path` prefixes, not raw strings. Two
independent checks is the right amount for a write into someone's media library, and
the second one keeps the guarantee if a future non-remote caller skips the validator.
`Process` argument arrays already avoid shell injection (`RipController.swift:19-24`
passes an array, never a shell string) — keep it that way; never move to
`/bin/sh -c`.

**Layer 3 — state validity.** A table, not scattered `if`s:

| Command | Allowed when |
|---|---|
| `subscribe`, `ping` | always |
| `rescanDisc` | disc present, no scan in flight, no rip in flight on that disc |
| `startRip` | disc present and scanned; per [#0040](0040.md), queueing is allowed but a second *rip* is not |
| `cancel(jobID)` | that job exists and is not already terminal |
| `eject` | no job actively reading the disc |

Rejections carry `RejectionReason` with enough context to render: `.busy(jobID:)`,
`.noDisc`, `.notScanned`, `.notPermitted`, `.invalidRequest(field:)`,
`.unknownJob`. A bare boolean is not enough — the client needs to say *why*.

**No settings mutation.** Do not add `setPlexRoot`, `setToolPath` or similar to
`RemoteCommand`. Record the reason in `Docs/Protocol.md`: a remote that can set
`makemkvconPath` chooses which binary an unsandboxed host executes.

**Client-side mirror.** The client uses the same `validated()` and the same
capability from the package to disable buttons before a command is sent. Host-side
enforcement remains authoritative — client-side checks are UX, never security.

## Notes

**Almost entirely unit-testable, and this is the highest-value test file in the
phase.** No network, no disc, no second machine:

- A traversal corpus against `MovieMetadata.validated()`: `../`, `..\\`, `/etc`,
  `a/b`, `.`, `..`, leading `.`, embedded `\0`, embedded newline, 10 KB title,
  empty title, and — as negative controls — real titles that must still pass:
  `Planes, Trains and Automobiles`, `WALL·E`, `Amélie`, `8½`, `Seven (Se7en)`. The
  negative controls matter as much as the attacks; an over-aggressive filter that
  rejects `WALL·E` is a bug users will hit and attackers will not.
- `PlexOrganizer` containment: assert a destination outside `plexMoviesPath` is
  refused even when handed an unvalidated metadata value directly.
- The full command × capability × state matrix, asserting the exact
  `RejectionReason` for each cell.
- Two-client arbitration against the `InMemoryTransport` from [#0062](0062.md): two
  simulated peers both send `startRip`; assert exactly one reaches `JobController`
  and the other receives `.busy`.

**Requires two real machines:** only the human-visible half — that the losing
client's UI shows a sensible message rather than a spinner that never resolves.

**Flagging this as a gap in the design docs, not just a ticket.** Neither
`Roadmap.md` nor `RemoteControl.md` mentions input validation or path traversal.
The Phase 4 exit criteria cover *unpaired* devices but say nothing about what a
*paired* device is allowed to send. Pairing is not a substitute for validation: a
paired device can be compromised, buggy, or an older client with a bug. This ticket
should be treated as blocking the phase's exit criteria, not as hardening to be
deferred.
