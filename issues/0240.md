## Description

#0236 gave a failed job its position, HandBrake's own words and the classifier's
matched line — and none of it could be read back for the two failures that
prompted it. `jobs.history` is **launch-scoped**, and installing the build that
carried the diagnostics restarted the app that held them.

That is not an unlucky ordering. An install is exactly what happens between a
failure and someone asking about it, so the launch history is the wrong place
for the only copy.

Three faults, all found by the agent session driving joe:

1. **The evidence does not survive a restart.** `report --job <id>` for either
   Lady in the Water failure returned the generic report.
2. **An unmatched `--job` was silently ignored** and the whole-disc report
   printed as though it had matched. My own fault, introduced the same day:
   #0236 says in as many words that quietly widening a narrowed question is how
   an agent reads another job's failure as its own, and then shipped a renderer
   that did exactly that.
3. **The persisted log did not report its job id**, so even the surviving rows
   could not be tied back to a `--job` query.

## Fix

The reliability log already survives restarts, so the evidence goes there:
`failedAtPercent`, `failureEvidence` and `failureLogTail` are written with the
row in `DVDPipeline`, and `report` reads them back. All three are `var` with a
`nil` default so the append-only file's existing lines decode unchanged — there
is a test for exactly that.

The position needed somewhere to come from. The job's own progress is cleared on
every phase edge, so by the time a failure is recorded the number is gone;
`DVDPipeline.FurthestProgress` is a small reference box (the pipeline is a
struct by design and the progress closures escape) holding the high-water mark,
shared with the fallback encode so a fallback failure reports where the
*fallback* got to.

`--job` for an unknown id now refuses with exit 4 and names the id, with a hint
saying the history is per launch and plain `report` still shows the persisted
log. And `jobID` — which the log has carried since #0043 and never reported — is
in the rendering.

## Gotchas

The job id was already persisted. Only the projection was missing, which makes
this the sixth instance of that shape in this project after #0203, #0208,
#0213, #0214 and #0236. The pattern is worth naming: when a fact exists in the
app and an agent cannot see it, look for the projection before adding storage.
