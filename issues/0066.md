# 0066 — PIN pairing has no design that resists offline guessing of a six-digit code

| | |
|---|---|
| **Status** | open |
| **Phase** | 4 — Remote control from a Mac |
| **Module** | Pairing |
| **Platform** | All |
| **First seen** | 2026-09-11 |

## Description

Mode B pairing — the host shows a six-digit code, the user types it on the client, "both derive a shared key" — is the only path that works for a household on several Apple IDs or a user with no iCloud, so it is not optional. But a key derived directly from a six-digit PIN has roughly 20 bits of entropy, and anyone who captures the pairing handshake on the LAN can brute-force all 1,000,000 candidates offline in seconds. The pairing exchange needs a design that makes guessing an *online*, rate-limited, single-shot operation.

## Long Description

`RemoteControl.md` says Mode B is "necessary for households on different Apple IDs,
for users not signed into iCloud, and as the manual fallback when KVS sync is slow",
and observes that it is also the model Wi-Fi Aware enforces natively, so building it
now means the mental model already matches `WAPairedDevice` / `WASharedSecret`. All
of that is right. What it does not do is specify the exchange, and the obvious
implementation is broken.

**The naive design and why it fails.** Host shows PIN `481902`. Both sides compute
`key = HKDF(PIN, salt)`. The client connects with TLS-PSK using that key. An
attacker on the same LAN records the handshake, then tries all 10^6 PINs offline
against the recorded transcript. A modern laptop does this faster than the user
finishes typing. The attacker now holds the pairing key and, through it, write
access to the media library on an unsandboxed host.

This matters more here than in a typical "pair my headphones" case because of what
is behind the door: `RemoteControl.md` itself makes the point — "the remote can
**write into the media repository**, which is the thing actually worth protecting" —
and the host is deliberately unsandboxed (`project.pbxproj:402`, `:431`) and spawns
external processes.

**What actually fixes it.** Either make the secret big enough that offline guessing
is infeasible, or make guessing require a fresh online interaction per attempt:

- **PAKE (SPAKE2 / OPAQUE / SRP).** A password-authenticated key exchange gives a
  strong session key from a weak shared PIN, with the property that an eavesdropper
  learns nothing usable offline and each guess costs one live protocol run. This is
  the textbook-correct answer. `CryptoKit` does not ship a PAKE, so it means either
  a vetted dependency or implementing SPAKE2 over P-256 — the latter is real
  cryptographic engineering and should not be attempted casually.
- **Short-lived, single-use, rate-limited online-only pairing window.** The host
  accepts pairing attempts only while the user has the pairing sheet open, for
  ~120 seconds, for **one** successful attempt, with a hard cap of about five
  failures before the window closes and a new PIN is required. Combined with the
  channel already being TLS to a fingerprint the client pins at first sight, and
  with an out-of-band confirmation (see below), this reduces the attack to "guess
  1 in 10^6 within five tries while the user is standing there".
- **Raise the entropy.** Ten digits (~33 bits) or six base32 characters (~30 bits)
  instead of six digits costs the user two seconds of typing and removes three
  orders of magnitude from the attacker's advantage. Wi-Fi Aware uses six digits
  because the *system* enforces the rate limit; an app-level implementation does not
  get that for free and should compensate.

## Steps to reproduce

1. Two Macs in the same house, signed into different Apple IDs.
2. Try to pair the MacBook Air to the mini.

## Expected behavior

The host shows a code with an explicit expiry. The user types it on the client
within the window. The two derive a session key through an exchange that an
eavesdropper cannot resolve offline, both sides display a short confirmation
string derived from the negotiated key, and the user confirms they match. The peer
is then recorded in the host's Keychain ([#0067](0067.md)) with a capability.

## Actual behavior

No pairing exists, and the design as sketched would derive the link key directly
from the PIN, which is offline-guessable by any device on the LAN that can observe
the handshake.

## Plan

**Step 1 — pick the mechanism and write down the threat model.** Add a
`Docs/Pairing.md` stating the attacker (another device on the home LAN), the asset
(library write access plus process spawning on an unsandboxed host), and the chosen
exchange. Recommendation, in order of preference:

1. **SPAKE2 over P-256** if a vetted, auditable implementation can be vendored. It
   is the only option that is correct rather than merely adequate, and it is the
   same family of construction Wi-Fi Aware's system pairing uses, so the migration
   story in [#0062](0062.md) stays coherent.
2. If a PAKE is judged disproportionate for v1 — which is a defensible call for a
   LAN-local media tool — ship the **bounded online window** instead, and make all
   four of its properties non-negotiable: expiry, single success, failure cap, and
   out-of-band confirmation. Then raise the code to ten digits. Write in
   `Docs/Pairing.md` that this is a deliberate trade, what it does not protect
   against, and that a PAKE is the upgrade path. An honest, documented compromise is
   fine; an undocumented one is not.

Whatever is chosen, **do not invent a bespoke handshake**. If neither option above
is taken, the ticket is not done.

**Step 2 — the exchange, concretely (bounded-window variant).**

- Host, on opening the pairing sheet: generate a fresh code from
  `SystemRandomNumberGenerator` — never `Int.random(in:)` seeded loosely, never a
  timestamp — plus a 16-byte salt and a 16-byte host nonce. Start a 120-second timer.
- Client connects over the TLS channel from [#0064](0064.md), pinning the host
  certificate fingerprint on first contact, and sends
  `HMAC(HKDF(code, salt: salt, info: "changeover-pair-v1"), hostNonce ‖ clientNonce ‖ clientPeerID)`.
- Host verifies in constant time
  (`HMAC.isValidAuthenticationCode(_:authenticating:using:)`, not `==`), then derives
  the long-term link key as
  `HKDF(sharedSecret, salt: hostNonce ‖ clientNonce, info: "changeover-link-v1")`
  and returns its own tag so the client can verify the host too.
- **Both sides then display the same six-character confirmation string** derived
  from the link key (`SHA256(linkKey ‖ "confirm")`, base32, first six characters).
  The user confirms they match. This is the step that catches an active
  man-in-the-middle, and it costs one sheet and two seconds.
- On success: close the window, record the peer ([#0067](0067.md)), and invalidate
  the code. On the fifth failure: close the window and require a new code.
- The PIN itself is never stored, never logged, and never written to
  `UserDefaults`. Note that `AppSettings.persist()` writes the TMDB key in
  plaintext at `Changeover/AppSettings.swift:53`; that is the pattern to avoid, not
  to follow.

**Step 3 — host UI.** A pairing sheet presented from `SettingsView` — which is
already the credential surface (`Changeover/SettingsView.swift:46-60`) — and
reachable from `StatusMenuView` (`Changeover/StatusMenuView.swift:39-45`). Show the
code in a large monospaced font, a visible countdown, the list of currently paired
peers, and the confirmation string when a client is mid-handshake. The mini is often
driven headless, so the sheet must also be reachable over Screen Sharing without
the popover being focus-dependent — `AppDelegate.showSettings()`
(`Changeover/AppDelegate.swift:97-121`) already builds a real window, so present
from there rather than from the transient popover
(`AppDelegate.swift:45`, `.behavior = .transient`).

**Step 4 — client UI.** Six (or ten) single-character fields or one wide field with
auto-advance, the confirmation-string comparison step, and clear distinct errors for
wrong code, expired code, too many attempts, and host unreachable. Generic "pairing
failed" is the thing that makes people give up.

**Step 5 — conventions.** `PINPairingCoordinator` is a plain `@Observable final class`
owned by the view with `@State`, per `Plan.md` — never `ObservableObject`. It
inherits `@MainActor`; the crypto is fast enough not to need to leave it, and
`CryptoKit` operations here are microseconds. Do not introduce an `actor`.

### Plan refresh (2026-09-15)

**What is stale or unsafe**

- **Step 2's exchange is still offline-guessable.**
  - The client sends `HMAC(HKDF(code, salt), …)` to whatever answered its
    connection *before the host is authenticated*. On first contact there is no
    pin, only trust-on-first-use.
  - An active impersonator on the LAN (answering the Bonjour browse) receives a
    code-keyed tag. HKDF is not a slow KDF, so it can try all 10^6 (or 10^10) codes
    in seconds, then pair with the real host inside the window.
  - The confirmation string only catches this if the user compares two screens
    across the room.
  - Deriving the long-term link key from the code and nonces also means anyone who
    later cracks the code from a captured MitM transcript learns the key.
- **Option 1's "vendor SPAKE2 over P-256" has no ready source.** CryptoKit in
  `MacOSX26.5.sdk` has no PAKE: a grep of `CryptoKit.swiftmodule` for
  SPAKE/CPace/SRP/OPAQUE returns nothing, only HPKE and ML-KEM. A search of
  `swift-crypto` found no public PAKE either. Choosing a PAKE means vendoring C
  (e.g. BoringSSL's SPAKE2+) or an unaudited package.
- **Line references:**
  - The TMDB key write is `AppSettings.swift:86`.
  - The credential GroupBox is "Movie Database (TMDB)", `SettingsView.swift:81`.
  - `AppDelegate.showSettings()` is `:289-316`; the popover `.transient` is `:88`.
  - `StatusMenuView.swift:39-45` no longer describes a menu row.
- **No link key.** Under [#0064](0064.md)'s recommendation the long-term
  credentials are the two TLS identities. Pairing only has to let each side learn
  the other's fingerprint authentically.

**Recommended mechanism for decision D-B: a commitment code (online-only guessing,
no PAKE)**

1. **The host opens the window.** The user clicks "Pair a device…" in the Settings
   window (a real window, so it works over Screen Sharing on a headless mini). The
   host mints:
   - A **fresh, ephemeral P-256 pairing identity**, used only for this window.
   - A one-time 6-digit secret `s` from `SystemRandomNumberGenerator`.
   - A 120 s window with one success and at most 5 failures.

   It accepts pairing connections presenting ALPN `changeover-pair/1`.
2. **The host displays the code.** It is `C ‖ s`, where
   `C = Crockford-base32(first 50 bits of SHA-256(ephemeral SPKI))`, 10 characters,
   e.g. `7KQ4M-2XDPA · 481 902`.
3. **The client checks the commitment before sending anything.** The user types
   the code. The client's `certificateValidator` accepts only a server leaf whose
   SPKI hash matches `C`; otherwise it disconnects **without sending anything**.
   Grinding a matching key needs about 2^50 key generations inside the window's
   lifetime, and the identity is fresh per window, so nothing can be precomputed.
4. **The client proves `s`.** Over TLS 1.3 it sends
   `PairRequest{clientName, clientNonce, tag}` where:
   - `tag = HMAC-SHA256(key: SHA-256("changeover-pair-v1" ‖ s), data: "client" ‖
     ephemeralFP ‖ clientFP ‖ clientNonce ‖ hostNonce ‖ exporter)`.
   - `exporter` is `sec_protocol_metadata_create_secret` if S2 shows it is
     reachable, otherwise it is omitted. The fingerprints still bind the tag.

   Only the holder of the committed ephemeral key ever receives the tag, so an
   impersonator gets nothing to guess offline. A fake *client* gets 5 online
   guesses at 10^-6 each.
5. **The host verifies and replies.** It checks with
   `HMAC.isValidAuthenticationCode`, then replies
   `PairAccept{hostLongTermCertificateDER, hostID, hostName, hostTag}`, where
   `hostTag` is the same construction with role `"host"`.
   - It records the client fingerprint in `PeerRegistry` ([#0067](0067.md)) with
     the capability chosen on the sheet, and closes the window.
   - The client verifies `hostTag` and pins the long-term host fingerprint, which
     arrived over the committed channel.
6. **Nothing code-derived persists.** `s` is never stored, logged or written to
   `UserDefaults`.

This composes TLS 1.3, SHA-256 and HMAC from Network.framework and CryptoKit; it
invents no primitive. **It is still protocol design**, so the implementer must:

- Write `Docs/Pairing.md`: threat model, message diagram, and what is not
  protected (shoulder-surfing the code, a compromised client Mac).
- Have it independently reviewed before any code lands.

If D-B = (b) instead, keep this ticket's code UX but replace steps 3–5 with the
vendored PAKE, gated on spike S4 (RFC 9383 test vectors as unit tests on gordon).

**Concurrency and placement**

- Pure `PairingCode` (Crockford encode/decode with normalization `O→0`, `I/L→1`,
  separators ignored), `PairingCommitment`, `PairingTag` and `PairingWindow` state
  machine (injected clock) go in `ChangeoverTransport`. CryptoKit is fine there,
  including on iOS.
- The host `PINPairingCoordinator` and the client's pairing flow stay
  `@Observable final class`, MainActor (app target default / explicit in the
  package). No `actor`.

**Tests** (in `ChangeoverTests` via `./run-remote-tests.sh gordon`; no network):

- Code round-trip and typo normalization.
- The commitment accepts the matching SPKI and rejects a 1-bit change.
- A tag verifies, a 1-bit flip fails, and a swapped role fails.
- The window expires at the injected time. Five failures close it and the sixth is
  refused. Success closes it.
- A replayed `PairRequest` (same nonces) is refused.
- The secret never reaches a captured log sink.
- The full exchange over `InMemoryTransport`, with fake fingerprints and no TLS.

**Needs two real Macs:**

- Pairing across two Apple IDs with real TLS.
- The client refusing a host whose certificate doesn't match the commitment
  (simulate by typing a wrong `C`).
- The human factor: whether 120 s is enough to walk from the mini with the code.

## Notes

**Almost entirely unit-testable, and it must be.** Against the `InMemoryTransport`
from [#0062](0062.md), with no network and no second machine:

- Correct code produces matching link keys on both sides.
- Wrong code produces a rejection and *not* a key.
- The link key differs across runs with the same code (nonces are doing their job).
- The confirmation string matches on both sides for a successful run and differs if
  either nonce is tampered with.
- The window expires at the stated time and rejects afterwards.
- The sixth failed attempt closes the window; the first five do not.
- A replayed transcript does not authenticate a second time.
- Tag comparison uses the constant-time API — assert by code review, and add a test
  that a one-bit-flipped tag is rejected.

These are the single most valuable tests in Phase 4: this is the code that stands
between a guest's laptop and the user's media library, and it can be fully exercised
on one machine with no disc.

**Requires two real machines:** the end-to-end pairing across different Apple IDs,
and the human factors — whether the countdown is long enough to walk from the mini
to the couch with a code in your head. It is not; assume the user photographs the
screen or the window is generous.

**Explicitly out of scope here:** capability assignment and revocation, which is
[#0067](0067.md). This ticket hands that ticket a verified peer identity and a link
key, nothing more.
