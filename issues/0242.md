|---|---|

## Description

On WILLIS, both films were chosen by an agent through `changeoverctl select`,
and `status.film.chosenBy` and `resolvedBy` both say **`user`**. Earlier
single-film discs correctly said `agent`.

So the multi-feature selection path records the wrong chooser.

## Why it matters

`chosenBy` exists so a person can tell what the machine decided from what they
decided — it is the field behind #0195's agent banner and the reason #0208 was
filed. A value that says a human chose a film a human never saw is worse than
no value: the whole point is accountability for an automated decision, and this
quietly attributes it to the one party who was not involved.

It is also now the **seventh** bug of this family, and the third about this
exact field. #0208 fixed `chosenBy` being hardcoded to `automation` in
`job.film`; this is the mirror image on a path #0208 did not touch.

## Root cause

My guess above was wrong and worth recording as such. `IdentificationSummary
.chooser` defaults to `.automation`, not `.user`, and the per-feature path does
record a story. The default that bit is one level down:

```swift
func select(movieID: Int?, jobs: JobController, apiKey: String,
            origin: SelectionOrigin = .user, askedFor: String? = nil)
```

`.user` is the right default for the window's results row, which is what it was
written for. But `selectFeature` reaches `select` through
`applyActiveFeature` — an internal re-entry that knows nothing about who asked —
and so inherited a default meant for UI callers. An agent's pick was recorded as
a person's.

#0200 fixed precisely this on the single-film path, and its comment is still
there saying so: *"an agent's `select` arriving with the default origin made the
panel say 'You chose X' to someone who had never seen the film."* It could not
fix this path, because nothing on it took an origin at all.

## Fix

`origin` and `askedFor` are threaded through `selectFeature` and
`applyActiveFeature`, and `AgentActions.select` passes `.agent` the way the
single-film path already did.

Falsified rather than assumed: with the forwarding removed the new test fails on
exactly the assertion it exists for, and passes with it restored.

## The part not fixed

The hazard is still there for the next caller. A defaulted parameter that names
a specific actor will be inherited again by the next internal path that forwards
to `select` without thinking about it — that is now twice. Removing the default
would force all four UI call sites to say `.user` explicitly, which is more
honest but touches the window; worth doing, deliberately, rather than as part of
this.

## Relation

other way round.
