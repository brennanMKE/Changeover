## Description

Found on joe during the first real-disc run (Oppenheimer, 2026-09-16). The app scanned the disc, showed the orange warning "libdvdcss could not open the raw device and fell back to the mounted filesystem", and then said:

> This disc did not identify itself — no title looks like a feature. That can happen on a TV disc with no Play All title, or a feature under 45 minutes. Choose one below.

Below it was **nothing**: the title table was empty, so there was nothing to choose, and Start Ripping stayed disabled with no explanation.

The disc is fine. Running the app's own command from a shell on joe reports the feature correctly:

```
HandBrakeCLI -i /Volumes/OPPENHEIMER --scan --title 0 --min-duration 1 --json
→ MainFeature: 7, 8 titles; title 7 = 3:00:11, 21 chapters, 3 audio, 6 subtitles
```

So the app's scan came back with **zero titles**, and `DiscTitleHeuristic.classify` correctly returned `.none` for an empty disc. The defect is that a zero-title scan is presented as "no title looks like a feature", which is a statement about the *contents* of a disc that was in fact never read.

**Root cause, confirmed 2026-09-16 (not permissions).** `ProcessRunner.run` feeds the child's stdout **and stderr into one pipe**, so HandBrake's log lines interleave with its JSON. On this disc the splice lands inside a JSON value:

```
"KeepDuplicateTitles": falseHandBrake has exited.
,
```

`HandBrakeScanParser.parseTitleSet` brace-matches the block, `JSONSerialization` then fails, and the parser returns an empty `DiscInfo` with `mainFeatureIndex == nil`. `DiscScanner` sees exit 0 **and** the `JSON Title Set:` marker, so its "incomplete scan reports success" guard passes and the empty disc is reported as a success. `DiscTitleHeuristic.classify` then correctly returns `.none`.

Captures are committed as `ChangeoverTests/Fixtures/handbrake-scan/oppenheimer-title0-min1-merged.txt` (stdout+stderr, reproduces the failure) and `oppenheimer-title0-min1.json` (stdout only, parses to 8 titles, `MainFeature: 7`). The existing Dragon Tattoo fixture is stdout-only, which is why no test caught this.

The same interleaving can corrupt any scan; this disc just makes it likely, because retrieving CSS keys makes HandBrake chatty while the JSON is being written.

## Resolution notes

> 🟢 Resolved 2026-09-16 — `ProcessRunner` now reads stdout and stderr as
> two independent pipes with serialized callback delivery, so HandBrake's
> stderr can no longer splice into its scan JSON, and a scan that read zero
> titles is presented as exactly that rather than as a verdict on the disc.

Reviewed at `b279b85`; approved with one fix, `81e7f61`.

**What the review changed.** The two-pipe split is the right fix and its
#0009 guarantees hold (details under `## Review findings` below), but it
silently changed `ProcessRunner`'s callback contract. Foundation dispatches
the two pipes' `readabilityHandler`s on **two concurrent threads** of
`com.apple.NSFileHandle.fd_monitoring` — measured with a standalone probe,
not assumed — so `onLine`, serialized by construction while both streams
shared one pipe, was being re-entered from two threads at once.
`DiscScanner.scan` accumulates into plain local `var`s (`lines`,
`stdoutLines`, `lastLoggedPercent`) and was correctly left unchanged by
`b279b85`, because it was safe under the old contract; under the new one it
was an `Array` append raced from two threads — memory corruption, not
merely out-of-order lines, and most likely on exactly the chatty real disc
this ticket was filed against. `EncodeController` and `MakeMKVRipper`
happened to be safe only because `LogTailBuffer`/`LineAccumulator` carry
their own locks. `81e7f61` restores the contract in the one place that owns
it — a `callbackLock` held across every `onLine`/`onStdout` invocation,
including `onReady`'s leftover flush — rather than pushing a lock into each
caller.

## Root cause

`ProcessRunner.run` fed the child's stdout and stderr into **one shared
`Pipe`**. The kernel interleaves two independent write streams at the byte
level with no regard for line boundaries, so on a real disc HandBrake's
chatty stderr log text spliced into the middle of its stdout JSON payload:
`"KeepDuplicateTitles": falseHandBrake has exited.`. `HandBrakeScanParser
.parseTitleSet`'s brace-matcher still located a balanced block (the splice
doesn't touch brace counts), but `JSONSerialization` failed to decode it,
and the parser silently returned an empty `DiscInfo` with `mainFeatureIndex
== nil`. `DiscScanner` saw exit 0 plus the `JSON Title Set:` marker present
and reported success. `DiscTitleHeuristic.classify` then correctly answered
`.none` for the (spuriously) empty title list — but `.none` is worded as a
verdict about the disc's *contents* ("no title looks like a feature"), so a
scan that never actually read anything was presented as one that had looked
and found nothing, over an empty picker with Start disabled and no
explanation.

## Fix

Followed both parts of the `## Plan` below, no deviations.

**Part 1 — stop corrupting the JSON.** `ProcessRunner.run` now reads stdout
and stderr as two independent `Pipe`s, each with its own `LineSplitter` and
readability handler, so a line from one stream can never be corrupted by
bytes from the other arriving mid-write — this is structural, not
timing-dependent; see `## Gotchas`. "Reader done" now requires EOF on
**both** pipes (a new `DualReaderCompletion` helper) before
`RunCompletionGate.markReaderDone()` is ever called, so every one of
`RunCompletionGate`'s #0009-documented guarantees (self-retain, grace arms
only from `markProcessDone(_:)`, the broken `process ↔ gate` retain cycle)
is unchanged by the split. Lines from both streams still reach the shared
`onLine` callback in real arrival order — `MakeMKVRipper` and
`EncodeController` (whose progress parsing reads from this same merged
stream) needed no changes and are covered by the full suite passing
unmodified. *(Review correction: true for those two only because their
`LogTailBuffer`/`LineAccumulator` are already locked — `onLine` did become
concurrent, which is what `81e7f61` fixes; see `## Resolution notes`.)* A new `onStdout` parameter (default a no-op) additionally
reports stdout-only lines; `DiscScanner` uses it to build the text handed to
`HandBrakeScanParser.parse`, while `classify()`'s warnings and the progress
logger keep reading the merged `onLine` stream exactly as before.

As the belt-and-braces guard the Plan asked for, `HandBrakeScanParser
.Output` gained `titleSetCorrupted: Bool`: the `JSON Title Set:` marker
present but the brace-matched block failing to decode is now distinguished
from "the marker never arrived" (the pre-existing `.jsonMissing`) and from a
genuinely empty `TitleList`. `DiscScanner.Failure` gained
`.titleSetCorrupted` to surface it as its own failure — so any future
corruption source, not just this one, can never again look like an empty
disc.

**Part 2 — never present an empty scan as a judgement about the disc.**
`DiscTitleHeuristic.Outcome` gained `.noTitles`, checked in `classify(_:
mainFeatureIndex:)` **before** the existing `mainFeatureIndex` logic: a scan
that genuinely read zero titles now always classifies as `.noTitles`,
regardless of what `mainFeatureIndex` says (an empty title list with a
non-nil `mainFeatureIndex` would itself be a scan-shaped contradiction, but
the guard refuses to fall through to `.none`'s wording regardless). `.none`
now only ever fires when titles exist and none clears the bar, matching the
Plan's requirement exactly.

`DiscTitleListView` renders `.noTitles` as its own failure-shaped state —
the message, a Rescan button, no table — mirroring `.failed`'s treatment
rather than the picker. `DiscTitleFormatting.noTitlesMessage(warnings:
lastLine:)` is a new pure, tested helper: it always leads with "The scan
read no titles from this disc.", appends HandBrake's own last line when one
is known, and appends the permissions hint — worded as a possibility ("may
not have permission"), never a diagnosis — only when a warning names the
libdvdcss raw-device fallback. `DiscScanner.Result` gained `lastLine:
String?` (defaulted, so the ~30 pre-existing `Result(disc:mainFeatureIndex:
warnings:)` test construction sites compile unchanged) so the view has
something concrete to show.

`#0025`'s note that `classify` returning `.none` for an empty disc is
"correct" is superseded by this ticket: `.none` for an empty disc is exactly
the bug. `#0024`'s exit-status-decides rule is untouched — the JSON-missing
check (marker absent) and the new corrupted-block check (marker present,
undecodable) both still key off the marker/decode outcome, never off
whether the resulting title list happens to be empty.

## Gotchas

- **The `stdoutAndStderrNeverInterleaveWithinALine` test is deterministic,
  not timing-dependent, and that's the point.** The real disc's corruption
  came from HandBrake's own internal threads racing at the OS level; the
  test's shell script instead issues three sequential, ordered `printf`s
  (stdout, then stderr, then stdout) from a single process. Even so, when
  falsification A merged the two pipes back together, the exact real-disc
  corruption shape reproduced byte for byte
  (`"KeepDuplicateTitles": falseHandBrake has exited.,`) — because two
  independent `Pipe`s make interleaving *structurally impossible*
  regardless of write order or scheduling, not merely unlikely. That's a
  stronger guarantee than a timing-based repro could ever prove.
- **Falsification A's mechanics, worth recording:** pointing
  `process.standardError` at the already-open `stdoutPipe` while leaving
  `stderrPipe` constructed but never attached to the child left
  `stderrPipe`'s write end open with nothing to close it, so its reader
  never saw EOF and the call only resolved after `hardCeilingGrace`'s 10s
  default — not a bug in the fix, just a mechanical artifact of how that
  particular falsification was applied (confirmed the grace backstop from
  #0009 still does its job even here).
- `#0026`'s `DiscTitleListView` Plan text (pre-`.noTitles`) described the
  zero-candidate state as "the full table … and a plain statement that no
  title looks like a feature" — that wording is what this ticket's `.none`
  keeps; `.noTitles` is new and deliberately does not reuse it.
- The permissions hint in `noTitlesMessage` is speculative by design (the
  Notes section below is still open on whether Full Disk Access actually
  changes anything on joe) — worded as "may not have permission," never
  asserted as the cause.

## Review findings

Independent review of `b279b85`, 2026-09-16. Everything below was checked
against the diff and, where stated, re-run.

- **`ProcessRunner`'s #0009 guarantees survive the split.** `onReady` is
  still the only resume site and still captures `process` (and now both
  `Pipe`s directly), so the lifetime fix holds; `DualReaderCompletion`
  cannot resume on one EOF (it requires both) and cannot hang forever if one
  stream never EOFs, because `markProcessDone(_:)` still arms
  `hardCeilingGrace` independently — the implementer's falsification A
  accidentally exercised exactly that path. Neither readability handler
  captures `process`, so no new retain cycle. Both `handleStdout` and
  `handleStderr` call `watchdogState.recordActivity()`, so the inactivity
  watchdog still counts bytes from both streams, and the `cancel` path
  (#0046 `SIGTERM`→`SIGKILL`, `Termination.cancelled`) is untouched.
- **Ordering and line splitting.** Each stream has its own `LineSplitter`,
  so chunk-boundary carry-over is per stream and correct; stdout lines reach
  `onLine` and `onStdout` exactly once each, stderr lines only `onLine`; the
  leftover flush covers both.
- **The one defect found**, and fixed in `81e7f61`: concurrent `onLine`
  delivery. See `## Resolution notes`.
- **Callers.** `EncodeController`'s progress parsing and `MakeMKVRipper`
  still read the merged stream; `DiscScanner` parses stdout only, still
  classifies the libdvdcss warning out of the merged stream (so a
  stderr-only warning is still seen), and #0024's exit-status-decides rule
  is intact — `.jsonMissing` keys off the marker and `.titleSetCorrupted`
  off the decode, neither off an empty title list.
- **Presentation.** `.titleSetCorrupted` and `.noTitles` both render as
  failure-shaped states with a Rescan button and no table, and neither
  reuses `.none`'s wording; the permissions hint stays a possibility ("may
  not have permission"). With zero titles there is no extras summary and no
  runtime verdict, so no empty picker is reachable, and
  `JobController`'s auto-select only fires on `.single`.
- **Test honesty.** The two real Oppenheimer fixtures are genuinely
  asserted (8 titles, `MainFeature: 7`, title 7 = 3:00:11 / 21 chapters / 3

  and be flagged corrupted. `stdoutAndStderrNeverInterleaveWithinALine` is
  not a tautology — the implementer's falsification A reproduced the exact

- **Two stale comments** in `Preflight.swift` and `PreflightTests.swift`,
  which still described `ProcessRunner.run` as merging both streams onto one

- A scan that exits 0 but yields no titles is reported as what it is: "The scan read no titles from this disc", with HandBrake's own last error line, a Rescan button, and — when the warning names the libdvdcss/raw-device fallback — a hint that the app may lack permission to read the disc (Privacy & Security → Files and Folders / Full Disk Access).

## Actual behavior

Zero titles are folded into `.none` and rendered with an invitation to choose from an empty table. Start stays disabled with no reason given.

## Plan

**Part 1 — stop corrupting the JSON (the actual bug).**

- Read stdout and stderr as **separate streams** in `ProcessRunner` (its header says it wires "one pipe exactly as both current callers do"), and parse the scan's JSON from stdout only. Keep stderr for `DiscScanner.classify`'s warnings, which is where the libdvdcss line comes from, and for failure text.
- `EncodeController`'s progress parsing reads HandBrake's stderr today through the same merged stream — its behaviour must not change. Whatever shape the split takes, both callers keep working.
- Regression-test with the committed merged capture: parsing `oppenheimer-title0-min1-merged.txt` the old way fails, and the new stdout/stderr split yields 8 titles and `MainFeature: 7`. Assert the stdout-only fixture parses to the same thing.
- Consider a belt-and-braces parser guard: if the brace-matched block fails to decode, report a parse failure rather than an empty `DiscInfo`, so a corrupt scan can never again look like a disc with no titles.

**Part 2 — never present an empty scan as a judgement about the disc.**

- `DiscTitleHeuristic.Outcome` (or the view's switch over it) gains a distinct empty case, e.g. `.noTitles`, so "the scan read nothing" and "nothing looks like a feature" can never render the same way. A pure function, unit-tested with an empty `DiscInfo`.
- `DiscTitleListView` renders `.noTitles` as a failure-shaped state: the message, the scan's warnings/last stderr line, and the existing Rescan button. No table.
- Carry the tail of HandBrake's stderr (or its classified warning) on `DiscScanner.Result` so the reason can be shown. `HandBrakeFailureClassifier` may already name this case; reuse it rather than adding a second vocabulary.
- When the libdvdcss raw-device fallback warning is present **and** zero titles came back, add the permissions hint, worded as a possibility, not a diagnosis.
- Check `#0024`'s claim that a failed scan and a disc with no titles can't look identical — that exit-status rule holds, but the zero-title success path was never surfaced to the user. Update that issue's notes if needed.
- Regression-test the parser against the real capture committed here (`0039/handbrake-scan-stderr.txt` is the stderr; the JSON stdout capture should be added as a fixture under `ChangeoverTests/Fixtures/handbrake-scan/oppenheimer-title0-min1.json`) and assert it yields 8 titles and `MainFeature: 7`. That pins "the parser is not the problem".
