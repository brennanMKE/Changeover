# 0063 — The NetworkListener API for advertising a Bonjour service name and type is unverified

| | |
|---|---|
| **Status** | open |
| **Module** | Transport |
| **Platform** | macOS |
| **First seen** | 2026-09-11 |

## Description

The `RemoteControl.md` protocol sketch shows `NetworkListener { Coder(...) { TLS() } }` on the host, but never shows how that listener advertises the service **name and type** over Bonjour — because that call has not been confirmed against the SDK. The WWDC25 session covers `NetworkBrowser` on the discovery side only. This must be resolved by reading the SDK, not by guessing, before [#0062](0062.md) commits to an API shape.

## Long Description

`RemoteControl.md` states the gap explicitly:

> **Unverified:** the exact call for advertising a Bonjour service *name and type*
> on the new `NetworkListener` has not been confirmed against documentation — the
> WWDC25 session covers `NetworkBrowser` on the discovery side but not the
> listener's advertisement API. Fallback is the established
> `NWListener(service: .init(name:type:), using:)`, which definitely does it.

There are three plausible outcomes and they are not equivalent in cost:

1. `NetworkListener` has a first-class service/advertisement parameter or modifier.
   Best case: the whole transport uses the structured-concurrency API consistently.
2. `NetworkListener` can only listen on a port, and advertisement is a separate
   concern — possibly `NWListener.Service` attached some other way, possibly
   `NetServer`/`DNSSD` registration alongside.
3. Advertisement only exists on the older `NWListener`. Then the host uses
   `NWListener(service:using:)` with a callback-based accept path while the client
   keeps `NetworkBrowser`, and `BonjourAdvertiser` has to bridge the old callback
   API into the `TransportConnection` protocol from [#0062](0062.md).

Outcome 3 is the expensive one — it means one side of the transport is written in
the modern API and the other in the legacy one, with an `AsyncStream` bridge in
between. That is a real design fork, which is why this is a ticket and not a
footnote.

There is a second unverified point worth resolving in the same sitting: whether the
new API exposes **TXT record** attachment on advertisement. The handshake design in
[#0069](0069.md) would like a small TXT record carrying the wire version and a host
instance ID so a client can filter incompatible or foreign hosts before opening a
connection. If TXT records are not reachable, that filtering moves into the
handshake and the client must connect first to find out.

## Steps to reproduce

1. Open `RemoteControl.md` and read the host-side snippet under "Protocol sketch".
2. Try to write the equivalent line that makes the listener discoverable as
   `_changeover._tcp` with a human-readable instance name.
3. Search the WWDC25 "Use structured concurrency with Network framework" session
   and the `Network` framework documentation for the listener-side advertisement API.

## Expected behavior

A confirmed, cited API call — read out of the installed SDK's `.swiftinterface` and
demonstrated working — that `BonjourAdvertiser` can be built on, plus a recorded
decision on whether the modern or legacy listener is used.

## Actual behavior

The call is assumed to exist. Writing it speculatively would produce code that
either does not compile or compiles and silently never advertises, which is the
worse of the two failures because discovery failures look like network problems.

## Plan

**This is a spike, timeboxed. It produces a decision and a working minimal example,
not production code.**

**Step 1 — read the SDK, do not search the web first.** The installed SDK is
authoritative and the answer is mechanically checkable:

```bash
SDK=$(xcrun --sdk macosx --show-sdk-path)
ls "$SDK/System/Library/Frameworks/Network.framework/Modules/Network.swiftmodule/"
grep -rn "NetworkListener" \
  "$SDK/System/Library/Frameworks/Network.framework/Modules/Network.swiftmodule/"*.swiftinterface
```

Read every `NetworkListener` initializer and every nested type. Then grep the same
files for `ListenerProvider`, `BrowserProvider`, `Connectable`, `bonjour`,
`Service`, `txtRecord` and `NWTXTRecord`. The `.swiftinterface` files carry the
complete public API surface including availability and default arguments — this is
the same technique that established the Wi-Fi Aware availability situation in
`RemoteControl.md`, and it is conclusive in a way documentation is not.

**Step 2 — compile the candidate.** Write a throwaway single-file Swift program in
the scratch area (not in the repo) that constructs the listener with the candidate
advertisement call and type-checks it:

```bash
xcrun swiftc -target arm64-apple-macos26.2 -typecheck /tmp/listener-spike.swift
```

A clean type-check rules out outcome 1 being imaginary. It does not prove the
service is actually advertised.

**Step 3 — prove it advertises.** Run the spike binary and, from a second terminal
(and ideally a second machine), observe the advertisement:

```bash
dns-sd -B _changeover._tcp local.
dns-sd -L "<instance name>" _changeover._tcp local.
```

`dns-sd -B` listing the instance is the actual proof. `dns-sd -L` additionally shows
the resolved host, port and any TXT record, which answers the TXT question in the
same command. Expect the macOS Local Network prompt to appear here — that is
[#0074](0074.md), and hitting it during this spike is useful early evidence.

**Step 4 — record the decision.** Write the outcome into this ticket's `## Notes`
and into `Docs/Transport.md` in the package from [#0062](0062.md): which API is
used, the exact call, whether TXT records are available, and — if outcome 3 — what
the `NWListener` bridge looks like. Cite the `.swiftinterface` path and line so the
next person can re-verify in one command rather than re-running the whole spike.

**Step 5 — if outcome 3.** Do not try to force the modern API. Implement
`BonjourAdvertiser` over `NWListener(service:using:)` and bridge
`newConnectionHandler` into an `AsyncStream<TransportConnection>` inside the
advertiser. The client side keeps `NetworkBrowser`; there is no requirement that
both ends use the same generation of the API, and `RemoteControl.md` already names
this as the fallback that "definitely does it". Note the asymmetry prominently in
`Docs/Transport.md` so it does not read as an oversight later.

**What not to do.** Do not write `NetworkListener(service:...)` or any similar call
into `BonjourAdvertiser` on the strength of it looking plausible. Do not paste an
API shape from a blog post or a model's recollection. The whole point of this ticket
is that the project does not currently know the answer.

## Notes

**Verification is the deliverable.** This ticket is "done" when three artifacts
exist: the grep output showing the API in the installed `.swiftinterface`, a
type-check that passes, and a `dns-sd -B _changeover._tcp local.` transcript showing
the instance. Paste all three into `## Verification` when the ticket is worked. A
`## Verification` for this ticket that says only "it compiles" is a failed
verification — compiling proves nothing about whether the service is on the wire.

**Second machine not strictly required**, but preferred. `dns-sd -B` on the same
machine confirms registration with `mDNSResponder`; a second Mac on the same LAN
additionally confirms the advertisement is leaving the host, which is the thing that
actually breaks. If a second machine is available, use it — it costs nothing extra
and is the difference between "registered locally" and "discoverable".

**Related risk to note while in there:** `mDNSResponder` will silently rename a
conflicting instance (`Changeover (2)`), so the instance name is not a stable
identity. Whatever [#0069](0069.md) uses to identify the host must be a value the
app controls — a persistent host UUID in the handshake or in a TXT record — not the
Bonjour instance name.
