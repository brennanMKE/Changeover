# 0083 — TMDB search and poster list do not fit a compact-width iPhone screen

| | |
|---|---|
| **Status** | open |
| **Phase** | 5 — iPhone and iPad clients |
| **Module** | MetadataEntryView / RemoteClient |
| **Platform** | iOS |
| **First seen** | 2026-09-11 |

## Description

The search-and-select screen is built for a 480pt macOS window with a
mouse-driven `List` selection, a 40×60 poster thumbnail and a permanently
visible 130pt log pane. On a phone that is a horizontally clipped layout with
selection that does not respond to taps.

## Long Description

Three separate problems hide behind "the layout is wrong".

**Width.** `MetadataEntryView` sets `.frame(width: 480)`
(`Changeover/MetadataEntryView.swift:22`). An iPhone 15 is 393pt wide and an
iPhone SE is 375pt. [#0082](0082.md) removes that modifier, which stops the
clipping but leaves a layout that was proportioned for a desktop window.

**Selection.** The results list uses `List(vm.results, selection: $selectedID)`
with `.tag(movie.id)` (`:63–66`), and a separate `.onChange(of: selectedID)`
(`:23–25`) to mirror the id back into `vm.selectedMovie`. Single-selection
`List` bindings on iOS behave nothing like macOS: outside of edit mode or a
`NavigationSplitView` sidebar, tapping a row does not populate the selection
binding. Ported verbatim, tapping a poster on a phone does nothing and the
Start button never enables (`:129`).

**Vertical budget.** The screen stacks six regions in a fixed `VStack`
(`:12–21`): search bar, status row, results list (`minHeight: 220`, `:68`),
folder preview, log pane (`height: 130`, `:109`) and action bar. On macOS that
totals a comfortable 580pt window (`Changeover/AppDelegate.swift:79`). On a
phone, with a keyboard up, there is roughly 350pt of usable height. Something
has to give, and the right answer is not to shrink all six.

Secondary: `.keyboardShortcut(.defaultAction)` on the Search button (`:38`) is a
no-op on a phone with no hardware keyboard, so `.onSubmit` (`:34`) becomes the
only way to run a search — it needs the right keyboard return key to be legible
as "Search".

## Steps to reproduce

1. Complete [#0081](0081.md) and [#0082](0082.md).
2. Run the client in an iPhone simulator.
3. Type a movie title and submit.
4. Tap a result row.

## Expected behavior

Results fill the screen at phone width with a poster large enough to actually
recognize a film by. Tapping a row selects it visibly. The chosen movie and its
Plex folder name are confirmable, and Start is reachable with a thumb without
the log pane eating half the screen before a job has even started.

## Actual behavior

The layout is proportioned for a 480×580 desktop window, tapping a row does not
update the selection binding so Start stays disabled, and a 130pt log pane
occupies fixed vertical space.

## Notes

`AsyncImage` (`Changeover/MetadataEntryView.swift:180–198`) is already
cross-platform and needs no change beyond sizing. The placeholder branch
(`:190–196`) uses `Color(.separatorColor)`, which [#0082](0082.md) replaces.

Poster size should go up on iOS, not down. `MovieSearchViewModel.posterURL`
defaults to `w185` (`Changeover/TMDB/MovieSearchViewModel.swift:38`) and the
thumbnail renders at 40×60 (`:186`, `:199`). 40×60 is a desktop list icon; on a
Retina phone at arm's length on a couch, a poster is the fastest way to confirm
the right film and deserves the space. `w185` is still the right fetch size for
a ~60×90 render at 3x.

This ticket is where `Plan.md` 11.1 (debounced type-to-search) stops being
polish. On a phone, a separate Search button next to a text field is the
interaction users complain about. The roadmap suggests folding 11.1 into Phase 2;
if it has not landed by the time this ticket is worked, do it here.

## Plan

### 1. Put the screen inside a `NavigationStack` and make selection navigation

The cleanest fix for both the selection bug and the vertical budget is the same
one: stop treating "pick a movie" as a selection inside a list and start treating
it as a step. On iOS, wrap the search screen in a `NavigationStack` and make each
result row a `NavigationLink` to a confirm step.

That removes the dependency on `List(selection:)` behaving like macOS
(`MetadataEntryView.swift:63`) — which it does not — and it removes the need for
the `selectedID` / `onChange` mirroring at `:6` and `:23–25` on iOS. On macOS,
keep the existing selection binding; it works and it is the right idiom there.

Express this as a `compactSearchBody` / `regularSearchBody` split driven by
`@Environment(\.horizontalSizeClass)` rather than by `#if os(iOS)`, so that an
iPad in a narrow Stage Manager window gets the compact treatment too, and so
[#0085](0085.md) can reuse the regular-width branch. Size class is `nil` on
macOS, so make the `nil` case take the regular branch.

`MovieSearchViewModel` does not change. It stays a `@MainActor @Observable`
class (`Changeover/TMDB/MovieSearchViewModel.swift:4–6`) owned by the view with
`@State` (`MetadataEntryView.swift:5`). Pass it into child views as a plain `let`
and use `@Bindable` inside any child that needs a binding to `vm.query`
(`:32`) — not `@ObservedObject`, which does not apply to `@Observable` types.

### 2. Rebuild the row for a phone

In the compact branch, the row from `MovieRow` (`:160–201`) grows:

- Poster to roughly 60×90, keeping the `w185` fetch
  (`MovieSearchViewModel.swift:38`) and the existing `.scaledToFill()` /
  `.clipped()` / `RoundedRectangle` treatment (`:184–188`).
- Title stays `.headline` with `lineLimit(2)` (`:168–170`).
- The `"\(movie.yearText)  ·  tmdb-\(movie.id)"` subtitle (`:171`) keeps the
  year but should demote the TMDB id to `.caption`. On a desktop the id is a
  useful disambiguator; on a phone it is noise competing for a narrow line.
- Minimum 44pt tap target — the current `.padding(.vertical, 4)` (`:176`) plus a
  60pt poster clears that comfortably.

### 3. Give the vertical budget somewhere to go

Compact layout, top to bottom:

1. Search field as `.searchable` on the `NavigationStack`, or an inline field
   with `.submitLabel(.search)` so the return key reads correctly. Drop
   `.keyboardShortcut(.defaultAction)` (`:38`) in the compact branch — it is
   dead weight without a hardware keyboard.
2. Results list filling all remaining height. No `minHeight: 220` (`:68`).
3. Status row (`:45–58`) stays exactly as is — a `ProgressView` and an error
   `Text` both work unmodified on iOS.
4. **Folder preview and log pane move off this screen.** The folder preview
   (`:73–89`) belongs on the confirm step, next to the poster, where it is
   answering "is this the right film". The log pane (`:93–119`) belongs on a
   job-progress screen — see step 4.

Keep `.scrollDismissesKeyboard(.interactively)` on the results list so the
keyboard gets out of the way while scrolling posters.

### 4. Split the log pane out into a progress destination

Extract `LogPaneView(lines:)` as described in [#0082](0082.md) and give it its
own navigation destination on iOS rather than a fixed 130pt strip (`:109`). The
`ScrollViewReader` auto-scroll (`:96`, `:110–114`) carries over unchanged and
works correctly on iOS.

This matters more than it looks: `RemoteControl.md` notes the user is walking
back to the couch during a scan, and `makemkvcon info` takes tens of seconds. The
progress screen is what they look at when they sit down, and it should be a
screen, not a strip.

### 5. Ordering

Do step 1 first and verify selection works on a device before touching any
visual detail — if the navigation structure is wrong, every layout decision
built on it has to be redone. Steps 2–4 are independent after that.

### 6. Risks

- **`.searchable` vs. an inline field.** `.searchable` is the platform-correct
  idiom but changes where the text lives and interacts with the `NavigationStack`
  differently on iPad. If it fights [#0085](0085.md), fall back to an inline
  `TextField` with `.submitLabel(.search)`; it is the smaller change from the
  current code (`:32–34`) and does not compromise the outcome.
- **Size-class branching drifts into duplicated bodies.** Keep the row view and
  the view model shared; only the container differs. If the two branches start
  diverging in content rather than arrangement, that is the signal to stop and
  rethink.
- **macOS regression.** The host app uses this view too
  (`Changeover/AppDelegate.swift:86–88`). Every change here has to be checked
  against the host's 480×580 window.

### 7. Verification

Most of this is simulator-verifiable, which is unusual for this project and
worth exploiting:

- iPhone simulator, `xcodebuild -destination 'platform=iOS Simulator,name=iPhone 16'`
  — search, tap a result, confirm selection visibly changes and the Start
  affordance enables. TMDB is plain HTTPS, so no host is needed for this.
- Check iPhone SE (375pt) as well as a 6.7" device; the SE is where fixed
  metrics break.
- Dynamic Type at the largest accessibility size, and both orientations.
- Host app on macOS: confirm the metadata window looks and behaves as before.
  Manual, and must be reported as manual.

A unit test on `MovieSearchViewModel.search(apiKey:)` with a stubbed
`URLSession` is worth adding if Phase 4 did not already — it is one of the few
genuinely testable seams in this area, and `TMDBClient`'s injectable session
(`Changeover/TMDB/TMDBClient.swift:6`) was clearly designed for it. Layout
itself gets no automated coverage; say so plainly rather than implying a green
build proves anything.
