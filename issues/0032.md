## Description

`TMDBClient.searchMovies(query:apiKey:)` calls `/search/movie`
(`Changeover/TMDB/TMDBClient.swift:18`), and that endpoint does **not** return
`runtime` — `TMDBMovie` (`Changeover/TMDB/TMDBModels.swift`) has no such field
because there is nothing to decode it from. Every use of runtime that Phase 2 now
depends on — rejecting a wrong title, disambiguating a remake, breaking a
theatrical/extended tie — requires a second request to `/movie/{id}`.

## Root cause

`/search/movie` never returns `runtime`; nothing in the app called
`/movie/{id}`, so there was no independent signal to check a chosen title's
duration against. `TMDBMovie` and `TMDBClient` had no seam for it and no way
to test one without a real network call.

## Fix

Implemented per the `## Plan`. The one deviation is noted below: `RuntimeLookup`
is declared at file scope. The client tests cover a 404 but not a 429; both take
the same non-2xx path.

- **`TMDBClient`** gained an injectable `Transport` (`@Sendable (URLRequest)
  async throws -> (Data, URLResponse)`) seam. `searchMovies` was moved onto
  it (no behaviour change — same URL, same query items, same error mapping);
  the convenience `init(session:)` builds a transport from `URLSession.data(for:)`.
  Added `movieDetails(id:apiKey:) async throws -> TMDBMovieDetails`: an empty
  key throws `.missingAPIKey` before any transport call; a per-id
  `detailsCache` remembers successful decodes (a `nil` runtime included,
  since "TMDB has no runtime" is itself an answer); a per-id `inFlight`
  dictionary of `Task`s coalesces concurrent/rapid-reselect calls into one
  request; errors are never cached, so the next selection retries. No lock
  needed — `TMDBClient` stays MainActor by the project default, matching the
  Plan.
- **`TMDBMovieDetails`** (`TMDBModels.swift`) is a `nonisolated` `Decodable`
  struct with `runtimeMinutes: Int?`, collapsing `null`, `0`, and a missing
  key to a single "unknown" `nil`.
- **`RuntimeCrossCheck.swift`** (new) is the pure comparison: `compare`,
  integer-only as #0025's guard is — `abs(disc - expected) * 100 <=
  expected * 6 + 60 * 100` (6% tolerance for PAL's ~4% speed-up plus
  headroom, 60s slack for TMDB's whole-minute rounding — the "Decisions
  (user, 2026-09-15)" values). `evaluate` joins a disc duration with a
  `RuntimeLookup` and never returns `.consistent`/`.mismatch` without both.
  `rankedByCloseness` orders (never selects) by closeness, ties broken by
  `DiscTitle.index`, deterministic under shuffling.
- **`MovieSearchViewModel`** gained `select(movieID:apiKey:)`, driving
  `runtimeLookup` through `.loading` → a terminal state, guarding on both
  `Task` cancellation and `selectedMovie?.id` still matching before writing
  a result — a stale response from a superseded selection never overwrites
  the current one. `search(apiKey:)` cancels the in-flight lookup and resets
  to `.idle`.
- **`MetadataEntryView`**'s `.onChange(of: selectedID)` now calls
  `vm.select(movieID:apiKey:)` instead of assigning `selectedMovie` directly,
  and one caption line was added under the folder preview: "Checking TMDB
  runtime…", "TMDB runtime 1h 57m", or "Runtime cross-check will not run —
  <reason>" — the `.unavailable` case is worded so it never reads like a
  pass.

**One decision made during implementation, not spelled out in the Plan:**
`RuntimeLookup` is declared at file scope in `MovieSearchViewModel.swift`,
`nonisolated`, rather than nested inside the (MainActor) view model class.
The Plan's contingency ("If isolation gets in the way, take
`(runtimeMinutes: Int?, notRunReason:)` instead") anticipated exactly this:
a type nested in a MainActor class would itself default to MainActor
isolation under this project's `SWIFT_DEFAULT_ACTOR_ISOLATION`, which
`RuntimeCrossCheck.evaluate` (explicitly `nonisolated`) couldn't take as a
parameter without crossing actor isolation. Declaring it at file scope
avoids that without needing the tuple fallback, and keeps `evaluate`'s
signature exactly as the Plan specifies (`evaluate(discSeconds:lookup:)`).

**Not built, left for #0026 per scope:** mismatch gating before Start, and
joining `RuntimeCrossCheck.evaluate` to a scanned `DiscInfo` / `JobController`
disc state. Search ordering/debounce is #0030's file — only the transport
seam was touched there.

## Long Description

This was a line in [#0025](0025.md) until the Brooklyn Nine-Nine capture made it
load-bearing. It is its own ticket because it is a networking change with its own
failure modes, its own tests and its own caching question, and because burying a new
API call inside a heuristic ticket hides both.

### Why it matters more than "a tiebreaker"

Every other check the app makes reads the **same disc metadata**: duration, chapter
count, size, segment map. On a disc that lies consistently, they agree with each
other and are wrong together — which is precisely what
`ChangeoverTests/Fixtures/makemkvcon/brooklyn-nine-nine-min0.txt` does. Its Play All
title is the longest, the largest, and has the most chapters, and it is eight
episodes of television.

TMDB is the only **independent** source in the system. A 2:53:18 title against a
sitcom's TMDB entry is a rejection from outside the disc's own account of itself.
[#0025](0025.md)'s Play All guard catches that disc structurally; this is the check
that would catch the disc the guard misses.

### Uses, in order of value

1. **Sanity check / safety net.** Feature duration wildly inconsistent with the
   chosen movie's runtime → stop and ask. This is the Brooklyn Nine-Nine case.
2. **Remake disambiguation.** *The Girl With The Dragon Tattoo* exists as a 2009
   Swedish film (152 min) and a 2011 Fincher film (158 min).
   `dragon-tattoo-min0.txt` title 0 runs 2:37:51 — 157.9 min — which says *which
   film the disc is*. That is the same ambiguity the `{tmdb-ID}` folder convention
   exists to resolve, answered from the same signal, and getting it wrong means the
   wrong TMDB id in the Plex folder name forever.
3. **The 2+ tiebreak.** Theatrical versus extended cut is a runtime difference and
   nothing else. Untested — no captured disc produces two feature-length titles.

### The tolerance problem

**PAL transfers run about 4% fast.** A PAL DVD of a 100-minute film runs about 96
minutes, because 24 fps film is played at 25 fps. So any comparison needs a
tolerance of at least 5%, and once the tolerance is that wide the check cannot
distinguish a 155-minute cut from a 158-minute one. Consequences to write down
rather than discover:

- The check is a **safety net and a coarse selector**, never a precise one.
- Two cuts less than ~8 minutes apart are *not* separable by runtime. The 2+ case
  must still show the picker; ranking by closeness orders the rows, it does not
  decide.
- `MSG:3038` ("Cells N-N were removed from title end") fires on several discs, so
  MakeMKV's own duration is already a few seconds off the nominal runtime. That is
  noise well inside the tolerance, not something to correct for.
- Do not attempt to detect PAL and apply a 4% correction. NTSC/PAL is not reported
  in the robot output in any form the fixtures show; `SINFO` attribute 21 gives a
  frame rate (`29.97 (30000/1001)` on all seven movie discs, all NTSC), but with no
  PAL disc captured there is **no evidence** for what a PAL disc reports. Widen the
  tolerance instead, and note the open question.

## Expected behavior

Once a movie is selected from search results, the app can fetch its runtime and use
it to sanity-check the title the heuristic chose, warning clearly when they disagree
and offering the picker rather than proceeding.

## Actual behavior

There is no way to obtain a runtime. `searchMovies` returns `[TMDBMovie]` decoded
from `TMDBSearchResponse` (`Changeover/TMDB/TMDBClient.swift:35`), and `/search/movie`
omits `runtime` from every result. Nothing in the app requests `/movie/{id}`.

## Notes

Unit-testable without a network: `MovieSearchViewModel`'s initializer already takes
an injectable `TMDBClient` (`Changeover/TMDB/MovieSearchViewModel.swift:15-17`), and
the comparison itself is a pure function over two integers and a tolerance.

Cover: decoding a `/movie/{id}` payload including a `null` runtime (TMDB returns
`null` for films it has no runtime for — the check must degrade, not crash); the
comparison at exactly the tolerance boundary; a PAL-shortened runtime passing; and
the Brooklyn Nine-Nine shape (a 173-minute observed duration against a ~22-minute
TMDB runtime) failing loudly.

Needs a network, not a disc: that a real `/movie/{id}` call returns what is expected
for a known id — `tmdb-78` (Blade Runner) is the worked example already used in
`Plan.md` and `Movies.txt`.

**Decide and write down whether the fetch is eager or lazy.** Fetching on every
search result is wasteful and rate-limited; fetching only after the user picks a
poster is one extra request at a moment where a brief spinner is acceptable. Prefer
lazy. Cache by TMDB id for the session so a rescan does not re-request.

**The app must work with this unavailable.** No API key, no network, TMDB down, or a
`null` runtime are all ordinary. In every one of those cases the behaviour is
"proceed without the cross-check and say the cross-check did not run" — never block
a rip, and never silently skip the warning as though the check had passed.

### The request and the response model

`GET https://api.themoviedb.org/3/movie/{id}?api_key=<key>`. Pass the key as a
query item, the same way `searchMovies` does, and build the URL with `URLComponents`.
Do not add `append_to_response`, and do not decode anything the check does not use.

```swift
// TMDBModels.swift
nonisolated struct TMDBMovieDetails: Decodable, Equatable, Sendable {
    let id: Int
    let title: String?
    /// Minutes. TMDB sends `null` for films it has no runtime for, and `0` on
    /// some sparse entries; both mean "unknown". A missing key decodes to nil too.
    let runtime: Int?
    var runtimeMinutes: Int? { runtime.flatMap { $0 > 0 ? $0 : nil } }
}
```

Make the struct `nonisolated`, as `DiscInfo` is. The existing `TMDBMovie` and
`TMDBSearchResponse` are MainActor by default. Leave them alone, because that is
#0030's file too.

Client API:

```swift
typealias Transport = @Sendable (URLRequest) async throws -> (Data, URLResponse)

nonisolated init(session: URLSession = .shared)   // forwards to the transport init
nonisolated init(transport: @escaping Transport)
func movieDetails(id: Int, apiKey: String) async throws -> TMDBMovieDetails
```

`searchMovies` moves onto the same `transport` (`URLRequest(url:)`) with no change
in behaviour. That keeps a single network path and makes search stubbable for #0030
as well. Errors reuse `TMDBError`:
- an empty key throws `.missingAPIKey` **before** the transport is called;
- a non-2xx response throws `.badResponse(code)` (this covers 404, 401 and 429);
- undecodable JSON throws `.decodingFailed`;
- transport errors propagate as they are.

Nothing retries.

### Caching and eager vs lazy: **lazy**, cached per id for the session

Fetch only after the user selects a result, never for every search row. Eager
fetching costs N requests per keystroke once #0030's debounce lands, and it runs into
rate limits. Inside `TMDBClient`, whose MainActor isolation means no lock is needed:

- `private var detailsCache: [Int: TMDBMovieDetails]` stores successful decodes,
  **including a nil runtime**, because that is an answer. Errors are never cached,
  so the next selection retries.
- `private var inFlight: [Int: Task<TMDBMovieDetails, Error>]` coalesces select,
  deselect and reselect into one request. Check the cache, then `inFlight`, then
  create the task. Remove the `inFlight` entry on both success and failure. When a
  caller's task is cancelled, the shared unstructured task keeps running, so a quick
  reselect reuses it.

### Lookup state in the view model

```swift
enum RuntimeLookup: Equatable {
    case idle                                            // nothing selected
    case loading(movieID: Int)
    case loaded(movieID: Int, runtimeMinutes: Int)
    case unavailable(movieID: Int, reason: RuntimeCrossCheck.NotRunReason)
}
private(set) var runtimeLookup: RuntimeLookup = .idle
private var runtimeTask: Task<Void, Never>?
func select(movieID: Int?, apiKey: String)
```

- `select` sets `selectedMovie` from `results`, cancels `runtimeTask`, and moves to
  `.loading`. It then awaits `client.movieDetails`.
- Before it writes the result, it checks that the task was not cancelled and that
  `selectedMovie?.id` still matches. A stale response must never label a different
  movie.
- A nil runtime becomes `.unavailable(.noRuntimeOnTMDB)`. A missing key becomes
  `.unavailable(.missingAPIKey)`. Any thrown error becomes
  `.unavailable(.lookupFailed(message))`.
- A lookup failure **does not** set `errorMessage`. That field is the search
  banner, and a failed runtime lookup is not a failed search.
- `search(apiKey:)` also cancels `runtimeTask` and resets to `.idle` next to its
  existing `selectedMovie = nil`. Keep the edit to those lines so it merges cleanly
  with #0030's sort and debounce changes.
- `MetadataEntryView`'s `.onChange(of: selectedID)` calls
  `vm.select(movieID: id, apiKey: settings.tmdbAPIKey)`.
- Add one caption line under `folderPreview`: "Checking TMDB runtime…",
  "TMDB runtime 1h 57m", or "Runtime cross-check will not run — <reason>". This is
  the only UI in this ticket. It must never read like a pass when the check did not
  run.

### The comparison: a pure function

```swift
nonisolated enum RuntimeCrossCheck {
    static let tolerancePercent = 6     // PAL 25/24 speed-up is 4.0%, plus headroom
    static let slackSeconds = 60        // TMDB rounds to whole minutes; logos, trimmed cells

    enum NotRunReason: Equatable, Sendable {
        case missingAPIKey, pending, lookupFailed(String), noRuntimeOnTMDB, noFeatureTitle
    }
    enum Verdict: Equatable, Sendable {
        case consistent(deltaSeconds: Int)   // signed: disc minus TMDB
        case mismatch(deltaSeconds: Int)
        case notRun(NotRunReason)
    }

    static func compare(discSeconds: Int, tmdbRuntimeMinutes: Int) -> Verdict
    static func evaluate(discSeconds: Int?, lookup: RuntimeLookup) -> Verdict
    static func rankedByCloseness(_ titles: [DiscTitle], runtimeMinutes: Int) -> [DiscTitle]
}
```

- **Rule**, in integer seconds as #0025 does it: `expected = minutes * 60`, and the
  verdict is consistent iff `abs(disc - expected) * 100 <= expected * tolerancePercent
  + slackSeconds * 100`. The tolerance is symmetric. Do **not** detect PAL or apply a
  4% correction.
- **`evaluate`** maps `.idle` or `.loading` to `.notRun(.pending)`, `.unavailable` to
  its reason, and a nil `discSeconds` to `.notRun(.noFeatureTitle)`. `RuntimeLookup`
  lives in the view model, and `evaluate` only reads it. If isolation gets in the
  way, take `(runtimeMinutes: Int?, notRunReason:)` instead.
- **`rankedByCloseness`** is a stable sort by `abs(delta)`, with ties broken by
  index. It orders picker rows only and never selects.
- **Honest limits, to repeat in the doc comment:**
  - A 2:37:51 disc (9,471 s) is 351 s from the 2009 *Dragon Tattoo* (152 min, 607 s
    allowed) and 9 s from the 2011 one (158 min). **Both are consistent.**
  - So remake disambiguation shows the signed delta and never decides. Cuts less
    than about 8 minutes apart are not separable, as the Description already says.
  - An extended cut against TMDB's theatrical runtime will usually be a mismatch.
    That is intended: it asks.
- Make it `nonisolated`, as `DiscTitleHeuristic` is, so a nonisolated scan path or the
  Phase 4 package can call it.

### Who calls it and what they do with it (contract for #0025 / #0026)

Keep `DiscTitleHeuristic.classify` free of network input. The structural
classification stays pure over the disc and must work offline. #0026 joins the two
where `JobController`'s scan outcome meets `vm.runtimeLookup`:

| #0025 outcome | verdict | behaviour |
|---|---|---|
| `.single(i)` | consistent | confirmation row notes "matches TMDB (±Δ)" |
| `.single(i)` | **mismatch** | **stop and ask**: show both durations, expand the picker, and require explicit confirmation before Start. This is not a tiebreak input. |
| `.single(i)` | notRun | proceed as normal, and the row says "runtime not checked — <reason>" in a style distinct from a pass |
| `.playAll` | any | still refuse. A mismatch adds weight to the message; notRun never softens the refusal. |
| `.none` | any | picker rows ordered by `rankedByCloseness` when a runtime is known; the user still picks |

### Concurrency (`SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`)

- `TMDBClient` and `MovieSearchViewModel` stay MainActor with no new annotations.
  The cache dictionaries need no actor or lock.
- The `@Sendable` transport closure is nonisolated, so awaiting it leaves the main
  actor for the network. Decoding a small payload back on main matches what search
  already does.
- `TMDBMovieDetails` and `RuntimeCrossCheck` (with its nested enums) are explicitly
  `nonisolated` and `Sendable`.
- Don't use the `actor` keyword anywhere here.

### Testing without the real API

Inject `init(transport:)`. **Do not use a `URLProtocol` stub.** Its handler is
static, and Swift Testing runs suites in parallel in one process, so two suites that
register handlers race each other. A per-test closure has no shared state. Record
calls in a `Mutex` from `Synchronization` (macOS 15+) inside the `@Sendable` closure.
Put `@MainActor` on the client and view-model suites. Payloads are inline JSON
literals shaped after TMDB's `/movie/{id}` docs; no fixture is captured from the
live API.

- **Client:**
  - the request path is `/3/movie/78` and carries `api_key`;
  - a runtime decodes;
  - `null`, `0` and a missing `runtime` key all give `runtimeMinutes == nil`;
  - a 404 or 429 throws `.badResponse`;
  - garbage throws `.decodingFailed`;
  - an empty key throws with **0** transport calls;
  - two calls for one id make 1 transport call, and a nil runtime is cached too;
  - a failed call is not cached (the retry makes a second call);
  - concurrent calls for one id make 1 transport call.
- **`RuntimeCrossCheck`** with `expected = 6000 s`:
  - 6420 and 5580 are consistent; 6421 and 5579 are a mismatch (the boundary on
    both sides);
  - a PAL 100-minute film at 5760 s is consistent;
  - Brooklyn Nine-Nine, 10,398 s against 22 min, is a mismatch with delta +9,078;
  - Dragon Tattoo, 9,471 s, is consistent against both 152 and 158, with deltas
    +351 and −9;
  - `evaluate` maps every `RuntimeLookup` case and a nil disc duration to `notRun`,
    never to `consistent`;
  - `rankedByCloseness` is stable, and shuffled input gives the same order.
- **View model:**
  - select goes `.loading` then `.loaded`;
  - a nil runtime gives `.unavailable(.noRuntimeOnTMDB)`;
  - a transport error gives `.unavailable(.lookupFailed)`, and `errorMessage` stays
    nil;
  - reselecting before a slow stub resolves never shows the first movie's runtime;
  - `search` resets to `.idle`.

Verify with `./run-remote-tests.sh gordon` and check that the new suites appear by
name with a non-zero count. **Unverified by construction:** that a live
`/movie/78` returns a non-null runtime. The test needs a network and a key, so
record it as a manual check. Never run UI tests. No UI test is warranted.

### Out of scope

- Eager or batch detail fetches for search results.
- Disk-persisted cache.
- Retry or backoff on 429.
- PAL detection or correction.
- Choosing or switching the TMDB id automatically from runtime.
- Gating Start or rendering the verdict next to disc titles (#0026).
- Logging the verdict into the job log (#0026, when `start` gains disc state).
- Sorting and debounce (#0030).
- Changing `TMDBMovie`'s isolation.
- Phase 4 wire format for the verdict.
- Any use of genres, TV detection or other `/movie/{id}` fields.

### Decisions (user, 2026-09-15)

- **Tolerance:** 6% + 60 s, as proposed.
- **Mismatch gating:** a runtime mismatch requires explicit confirmation before Start (built in #0026), not just a warning.
