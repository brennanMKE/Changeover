# 0028 — RipController rips every title on the disc and then guesses the movie by file size

| | |
|---|---|
| **Status** | open |
| **Module** | RipController |
| **Platform** | macOS |
| **First seen** | 2026-09-11 |

## Description

`RipController.rip` passes the literal string `"all"` to `makemkvcon`
(`Changeover/RipController.swift:22`), ripping bonus features, trailers, FBI warnings
and alternate angles along with the movie, and then picks whichever resulting file is
largest (`:47`, `:66-77`). It should rip one title index — the one the user chose —
and know the output file's name in advance.

## Long Description

This is the ticket the phase is named for, and it retires two defects at once.

The first is waste: a disc with fourteen titles is ripped fourteen times over, which
is most of the elapsed time in the demo comparison `Roadmap.md` line 106 asks for.

The second is correctness. `largestMKV(in:)`
(`Changeover/RipController.swift:66-77`) does a `contentsOfDirectory` over
`settings.workingRipPath` — a single shared folder derived from the Plex root
(`Changeover/AppSettings.swift:27`) — and returns the biggest `.mkv` it finds. Nothing
scopes that listing to the current job, so a leftover file from a previous disc can
win. `Roadmap.md` lines 35–38 records this as a known defect and Phase 1
([#0001](0001.md)) mitigates it with per-job working subdirectories. This ticket
removes the root cause instead: once the title is chosen and its output file name is
known from the scan, there is no search and therefore nothing to search wrongly.

Worth noting that the two fixes are complementary, not redundant. Keep both.

## Steps to reproduce

1. Rip any disc, then start a second rip from a different disc without emptying
   `<Plex root>/Working/ripping`.
2. Observe which file HandBrake is handed.

## Expected behavior

`makemkvcon mkv disc:0 <index> <dest>` runs once for the selected title, and the
resulting `.mkv` is identified by the name the scan already reported, not by a
directory listing.

## Actual behavior

`makemkvcon mkv disc:0 all <dest>` rips everything
(`Changeover/RipController.swift:19-24`), then `largestMKV(in:)` scans the shared
working directory and returns the largest `.mkv` present — which may be from an
earlier disc.

## Notes

**Verification needs a disc and should say so.** The core claim — "a disc with bonus
features rips only the chosen title" (`Roadmap.md` line 125) — is provable only on
the mini with the demo disc. Record which disc, how many titles it has, and the
elapsed time against the previous full-disc rip of the same movie; that comparison is
the demo.

**What can be unit-tested** is the argument construction. Extract the
`makemkvcon` argument array into a pure `static func arguments(for:)` and test it:
that the title index appears where `"all"` used to, that index 0 is emitted as `"0"`
and not omitted, and that the destination is quoted/escaped correctly for a Plex root
containing spaces — `/Volumes/MediaSSD/Plex Media/...` (`AppSettings.swift:20-30`)
always contains one. `Process.arguments` does not go through a shell so no quoting is
needed, but a test pinning that expectation is cheap insurance against someone
"fixing" it later.

Also unit-test the expected-output-path derivation, including the fallback branch.

## Plan

### Files

### Signature

```swift
nonisolated static func rip(
    makemkvconPath: String,
    discIndex: Int = 0,
    title: DiscTitle,
    outputDir: String,
    minLengthSeconds: Int,
    log: @escaping @MainActor (String) -> Void
) async -> Result<String, RipError>
```

Keep `nonisolated static` — the annotation at `Changeover/RipController.swift:9` is
there for a real reason (the rip must not occupy the main actor) and the doc comment
at `:4-8` explains it correctly; preserve both.

Take the whole `DiscTitle`, not a bare `Int`. The function needs `index` for the
command line and `outputFileName` for the result, and passing them separately invites
the two to drift apart. It also makes the call site self-documenting about *which*
integer is meant — a live risk, given that `TMDBMovie.id`
(`Changeover/TMDB/TMDBModels.swift:21`) is also an `Int` travelling through the same
window.

Returning `Result` rather than `String?` mirrors [#0024](0024.md) and lets the
expired-key case surface as itself here too, rather than as
`✗ makemkvcon exited with status N` (`:50-51`). Reuse `DiscScanError`'s
classification helper if the `MSG` codes turn out to be shared — [#0021](0021.md)
will show whether they are.

### Arguments

```swift
["mkv", "disc:\(discIndex)", String(title.index), outputDir,
 "--minlength=\(minLengthSeconds)", "-r", "--progress=-same"]
```

Replacing `"all"` at `:22`. Two details:

- **Index 0 is a real index.** Any `if index > 0` guard, or any use of a
  non-`Optional` sentinel like `-1`, will eventually rip the whole disc when the main
  feature is title 0 — which is the common case. Pass it unconditionally.
- **`--minlength` must match the scan.** `makemkvcon` applies its own minimum title
  length at rip time as well as at scan time. If the scan used a lower threshold than
  the rip, a short title the user deliberately selected will be silently skipped and
  the rip will produce nothing while exiting 0. Thread the same
  `AppSettings.scanMinLengthSeconds` from [#0024](0024.md) into both.

Whether to add `-r` to the rip is a judgement call: robot mode gives parseable
`PRGV` progress lines (useful for a real progress bar, and for Phase 4's log stream)
but makes the human-readable log worse, and the log area
(`Changeover/MetadataEntryView.swift:93-119`) is what the user currently watches.
Decide explicitly; if `-r` is adopted, apply the same buffered line-accumulation fix
[#0024](0024.md) makes, because the handler at `:31-41` splits chunks with no
carry-over and will corrupt records.

### The return path — deleting `largestMKV`

Delete `largestMKV(in:)` (`:66-77`) outright. Replace it with:

1. Expected path = `outputDir/title.outputFileName`, from attribute 27 confirmed in
   [#0021](0021.md).
2. On exit 0, `FileManager.fileExists` at that path → return it.
3. If it is missing, **do not fall back to a size comparison.** Fall back to the
   newest `.mkv` in `outputDir` with an `mtime` after the rip started, log loudly
   that the expected name did not appear, and include both names in the message. A
   quiet fallback to the old behaviour would resurrect the exact defect this ticket
   exists to remove, and the loud version gives [#0021](0021.md) a feedback channel if
   attribute 27 turns out to be wrong on some disc type.
4. If neither, return `.failure` — never `nil`-as-success.

Confirm during [#0021](0021.md) whether `makemkvcon` names the file identically when
ripping a single title versus `all`. If it renames (`title_t00.mkv` versus
`<volume>_t00.mkv`, say), the expected-name derivation has to account for it, and the
mtime fallback is what catches the discrepancy in the meantime.

### Caller

`DVDPipeline.run()` (`Changeover/DVDPipeline.swift:16-62`) captures its paths on the
main actor before entering nonisolated code (`:19-24`) — preserve that pattern and
add the title and min-length to what it captures. Its `guard let mkvPath = await
RipController.rip(...) else` (`:27-34`) becomes a `switch` on the `Result` so the
failure message is the specific one rather than `✗ Ripping failed. Aborting.` (`:32`).

### Multiple titles

`makemkvcon mkv` takes one title id or `all`, not a list. If `RipRequest.titleIndices`
holds more than one, that means N sequential invocations and N outputs — and the
pipeline downstream (`DVDPipeline.swift:38-59`) assumes exactly one file becoming one
Plex movie. Phase 2 should rip exactly one title and treat multi-select as a UI
affordance that is not yet honoured, or reject it at the start button. Extras are an
open question (`RemoteControl.md` lines 534–536: a separate `Extras/` destination per
Plex convention) and belong to a later phase. Say which choice was made in `## Fix`
rather than leaving a half-working path.
