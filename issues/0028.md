# 0028 — RipController rips every title on the disc and then guesses the movie by file size

| | |
|---|---|
| **Status** | open |
| **Module** | RipController |
| **Platform** | macOS |
| **First seen** | 2026-09-11 |

## Description

`RipController.rip` passes the literal string `"all"` to `makemkvcon`
(`Changeover/RipController.swift:22`), ripping bonus features, trailers, FBI warnings
and alternate angles along with the movie, and then picks whichever resulting file is
largest (`:47`, `:66-77`). It should rip one title index — the one the user chose —
and know the output file's name in advance.

## Long Description

This is the ticket the phase is named for, and it retires two defects at once — but
the experiment in `DiscSelection.md` disproved the replacement this ticket was
originally written around, so read the "verify by duration" section before anything
else.

The first is waste: a disc with fourteen titles is ripped fourteen times over, which
is most of the elapsed time in the demo comparison `Roadmap.md` line 106 asks for.

The second is correctness. `largestMKV(in:)`
(`Changeover/RipController.swift:66-77`) does a `contentsOfDirectory` over
`settings.workingRipPath` — a single shared folder derived from the Plex root
(`Changeover/AppSettings.swift:27`) — and returns the biggest `.mkv` it finds. Nothing
scopes that listing to the current job, so a leftover file from a previous disc can
win. `Roadmap.md` lines 35–38 records this as a known defect and Phase 1
([#0001](0001.md)) mitigates it with per-job working subdirectories. This ticket
removes the root cause instead: once the title is chosen and its output file name is
known from the scan, there is no search and therefore nothing to search wrongly.

Worth noting that the two fixes are complementary, not redundant. Keep both.

### The filename check is defeated — verify by duration

This ticket planned to verify a rip by checking that the file named by attribute 27
appeared on disk. **That check does not work**, because MakeMKV assigns title
indices *after* applying the minimum-length filter, and the output filename is
derived from the post-filter index. The same disc at two thresholds produces the
same filename for two entirely different titles:

```
hanna-min0.txt         TINFO:1,27,0,"D1_t01.mkv"   TINFO:1,9,0,"0:00:13"   12,242,944 bytes
hanna-mindefault.txt   TINFO:1,27,0,"D1_t01.mkv"   TINFO:1,9,0,"1:50:45"   6,795,724,800 bytes
```

**Identical output filename, same disc, 555× size difference.** One is a 13-second
clip; the other is the movie. A rip that produced the wrong one would pass a
filename check, and `makemkvcon` exits 0 either way.

The destructive direction was demonstrated on Hornets' Nest: the movie is title
**9** in the `--minlength=0` scan and title **3** in the default scan. Scan at the
default, let the user pick index 3, then rip at `--minlength=0`, and index 3 is
`0:01:32` of something else
(`hornets-nest-min0.txt`: `TINFO:3,9,0,"0:01:32"`). Exit status 0, a file on disk,
the wrong movie.

Two rules follow, and neither is optional:

1. **Pass one explicit `--minlength` to both the scan and the rip.** Never inherit
   MakeMKV's default on either side. The value travels in `RipRequest`
   ([#0027](0027.md)) so the rip cannot be run against a threshold the scan did not
   use.
2. **Never mix indices from two scans.** A title index is only meaningful paired
   with the threshold that produced it. If the threshold changes, rescan.

And the verification itself becomes: **check the duration of the ripped file**, not
its name. `ffprobe` (or `AVAsset.load(.duration)`, which needs no extra binary)
against `DiscTitle.durationSeconds` with a few seconds of tolerance. That check
would have caught every failure mode above; the filename check catches none of them.

Note also that attribute 27 is not the shape the old plan assumed. It is
`<letter><digit>_t<NN>.mkv` (`B1_t00.mkv`), sometimes prefixed with the disc name
(`Girl in the Spider's Web, The-B1_t00.mkv`), and whether the prefix appears varies
by disc. It is still worth using as the *expected* name — it just cannot be the
proof.

### MakeMKV reports the effective threshold, so read it

`MSG:3025` carries the threshold as a parameter rather than only in prose:

```
MSG:3025,16777216,3,"Title #1 has length of 23 seconds which is less than minimum
title length of 120 seconds and was therefore skipped","Title #%1 has length of %2
seconds which is less than minimum title length of %3 seconds and was therefore
skipped","1","23","120"
```

The trailing `"1","23","120"` are title, actual length, and **effective minimum**.
The app can assert that the threshold MakeMKV actually applied is the one it asked
for, rather than assuming. Cheap, and it turns a silent index shift into a logged
mismatch.

## Steps to reproduce

1. Rip any disc, then start a second rip from a different disc without emptying
   `<Plex root>/Working/ripping`.
2. Observe which file HandBrake is handed.

## Expected behavior

`makemkvcon mkv disc:0 <index> <dest>` runs once for the selected title, at the same
explicit `--minlength` the scan used, and the resulting `.mkv` is confirmed to be
the right title by comparing its **duration** against the scanned
`DiscTitle.durationSeconds` — not by a directory listing and not by its filename.

## Actual behavior

`makemkvcon mkv disc:0 all <dest>` rips everything
(`Changeover/RipController.swift:19-24`), then `largestMKV(in:)` scans the shared
working directory and returns the largest `.mkv` present — which may be from an
earlier disc.

## Notes

**Verification needs a disc and should say so.** The core claim — "a disc with bonus
features rips only the chosen title" (`Roadmap.md` line 125) — is provable only on
the mini with the demo disc. Record which disc, how many titles it has, and the
elapsed time against the previous full-disc rip of the same movie; that comparison is
the demo.

**What can be unit-tested** is the argument construction. Extract the
`makemkvcon` argument array into a pure `static func arguments(for:)` and test it:
that the title index appears where `"all"` used to, that index 0 is emitted as `"0"`
and not omitted, that `--minlength` is always present with the value from the
request, and that the destination is quoted/escaped correctly for a Plex root
containing spaces — `/Volumes/MediaSSD/Plex Media/...` (`AppSettings.swift:20-30`)
always contains one. `Process.arguments` does not go through a shell so no quoting is
needed, but a test pinning that expectation is cheap insurance against someone
"fixing" it later.

Also unit-testable: the duration check itself as a pure comparison
(expected seconds, observed seconds, tolerance → pass/fail), and the
threshold-mismatch detector over parsed `MSG:3025` parameters.

**The filename-collision case has a fixture-backed test that needs no disc.** Parse
`hanna-min0.txt` and `hanna-mindefault.txt`, assert both produce a title 1 whose
`outputFileName` is `D1_t01.mkv`, and assert their durations differ by more than two
orders of magnitude. That test is the executable form of why the verification
changed, and it should be written even though it tests the parser more than the
ripper.

### Signature

```swift
nonisolated static func rip(
    makemkvconPath: String,
    discIndex: Int = 0,
    title: DiscTitle,
    outputDir: String,
    minLengthSeconds: Int,     // MUST equal the scan's; see #0027's RipRequest
    log: @escaping @MainActor (String) -> Void
) async -> Result<String, RipError>
```

Keep `nonisolated static` — the annotation at `Changeover/RipController.swift:9` is
there for a real reason (the rip must not occupy the main actor) and the doc comment
at `:4-8` explains it correctly; preserve both.

Take the whole `DiscTitle`, not a bare `Int`. The function needs `index` for the
command line and `outputFileName` for the result, and passing them separately invites
the two to drift apart. It also makes the call site self-documenting about *which*
integer is meant — a live risk, given that `TMDBMovie.id`
(`Changeover/TMDB/TMDBModels.swift:21`) is also an `Int` travelling through the same
window.

Returning `Result` rather than `String?` mirrors [#0024](0024.md) and lets the
expired-key case surface as itself here too, rather than as
`✗ makemkvcon exited with status N` (`:50-51`). Reuse `DiscScanError`'s
classification helper if the `MSG` codes turn out to be shared — [#0021](0021.md)
will show whether they are.

### Arguments

```swift
["mkv", "disc:\(discIndex)", String(title.index), outputDir,
 "--minlength=\(minLengthSeconds)", "-r", "--progress=-same"]
```

Replacing `"all"` at `:22`. Two details:

- **Index 0 is a real index.** Any `if index > 0` guard, or any use of a
  non-`Optional` sentinel like `-1`, will eventually rip the whole disc when the main
  feature is title 0 — which is the common case. Pass it unconditionally.
- **`--minlength` must match the scan, and must always be explicit.** This is the
  single most important line in the ticket. `makemkvcon` applies its minimum title
  length at rip time as well as at scan time, and it **renumbers the titles** after
  applying it. A rip at a different threshold than the scan does not fail — it rips
  a *different title* and exits 0. Hornets' Nest is the worked example: the movie is
  index 9 at `--minlength=0` and index 3 at the default. Thread the value out of
  `RipRequest` ([#0027](0027.md)), not out of `AppSettings` directly, so a settings
  change mid-job cannot desynchronize the two calls.
- **Never omit it.** Inheriting MakeMKV's default on either side means the app does
  not know what threshold it ran at, and `MSG:3025`'s third parameter is the only
  way to find out after the fact.

Whether to add `-r` to the rip is a judgement call: robot mode gives parseable
`PRGV` progress lines (useful for a real progress bar, and for Phase 4's log stream)
but makes the human-readable log worse, and the log area
(`Changeover/MetadataEntryView.swift:93-119`) is what the user currently watches.
Decide explicitly; if `-r` is adopted, apply the same buffered line-accumulation fix
[#0024](0024.md) makes, because the handler at `:31-41` splits chunks with no
carry-over and will corrupt records.

### The return path — deleting `largestMKV`, and verifying by duration

Delete `largestMKV(in:)` (`:66-77`) outright. Replace it with:

1. Expected path = `outputDir/title.outputFileName`, from attribute 27. Use it to
   *locate* the file.
2. On exit 0, `FileManager.fileExists` at that path. If it is missing, fall back to
   the newest `.mkv` in `outputDir` with an `mtime` after the rip started, and log
   loudly that the expected name did not appear, including both names. **Never** a
   size comparison — that resurrects the defect this ticket exists to remove.
3. **Then verify the file's duration.** Read it (`AVAsset.load(.duration)` avoids
   adding an `ffprobe` dependency) and compare against `title.durationSeconds`.
   Outside tolerance → `.failure`, with both durations in the message. This is the
   check that catches a threshold mismatch, a stale index, or a rip that silently
   produced a different title; the filename check catches none of them because
   `D1_t01.mkv` is a valid name for two different titles on the same disc.
4. A few seconds of tolerance is enough for a same-threshold rip — MakeMKV's
   `MSG:3038` ("Cells N-N were removed from title end") shows it does trim, and it
   fires on four of the seven discs. Do not make the tolerance a percentage; a
   percentage of 2:37:51 is minutes.
5. If the file is absent or the duration is wrong, return `.failure` — never
   `nil`-as-success.

`makemkvcon` does **not** name the file the same way across discs: `B1_t00.mkv` on
some, `Girl in the Spider's Web, The-B1_t00.mkv` on others. Whatever derivation is
written must tolerate both, which is a second reason the name is a hint and the
duration is the proof.

### Caller

`DVDPipeline.run()` (`Changeover/DVDPipeline.swift:16-62`) captures its paths on the
main actor before entering nonisolated code (`:19-24`) — preserve that pattern and
add the title and min-length to what it captures. Its `guard let mkvPath = await
RipController.rip(...) else` (`:27-34`) becomes a `switch` on the `Result` so the
failure message is the specific one rather than `✗ Ripping failed. Aborting.` (`:32`).

### Multiple titles

`makemkvcon mkv` takes one title id or `all`, not a list, so N titles means N
sequential invocations and N outputs. `RipRequest` ([#0027](0027.md)) now separates
`featureTitleIndex` from `extraTitleIndices` precisely so this function never has to
guess what a given index is for.

**This ticket rips the feature only.** One invocation, one output, one Plex movie —
the pipeline downstream (`DVDPipeline.swift:38-59`) assumes that and should keep
assuming it here. Extras are [#0031](0031.md): the same `rip` call, a different
destination, and a destination type that makes routing an extra into `Movies/`
impossible rather than merely discouraged. Do not add a second output path to this
ticket; do not leave a half-honoured multi-select.

The important sequencing note: all of those invocations must share the one
`--minlength` from the request, and must use indices from the one scan that produced
it.
