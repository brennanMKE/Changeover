# 0065 — Zero-config pairing over iCloud KVS is unproven in an unsandboxed app

| | |
|---|---|
| **Status** | open |
| **Module** | Pairing |
| **Platform** | macOS |
| **First seen** | 2026-09-11 |

## Description

Mode A pairing — the host writes a random 32-byte key to `NSUbiquitousKeyValueStore` and clients on the same Apple ID read it with no user interaction — is the zero-config default in `RemoteControl.md`. It requires the iCloud key-value entitlement, and **Changeover is deliberately unsandboxed** (`ENABLE_APP_SANDBOX = NO`, `Changeover.xcodeproj/project.pbxproj:402`), which is the one configuration where iCloud container provisioning is least certain. That has to be proven before Mode A is built on.

## Long Description

Mode A is genuinely the right default when it works: no PIN, no UI, no
passphrase plumbing. The host generates the key once, stores it in the Keychain as
the authoritative copy, and mirrors it into `NSUbiquitousKeyValueStore`; a client
signed into the same Apple ID finds it and pairs silently.

Two things make it a ticket rather than a paragraph:

**The sandbox question.** iCloud entitlements on macOS are historically tied to the
App Sandbox — the ubiquity container is provisioned through the sandbox's container
machinery. Changeover cannot enable the sandbox: it shells out to `makemkvcon` and
`HandBrakeCLI` at absolute paths the user chooses (`AppSettings.makemkvconPath`,
`Changeover/AppSettings.swift:14-15`) and writes into an arbitrary external volume
(`plexMediaRoot`, `:13`). `ENABLE_APP_SANDBOX = NO` is set for both Debug and
Release (`project.pbxproj:402`, `:431`) for exactly that reason. Whether
`com.apple.developer.ubiquity-kvstore-identifier` functions without it is not
something to assume in either direction — `RemoteControl.md` does not mention the
interaction at all, and if the answer is "no", Mode A is not merely inconvenient,
it is impossible, and [#0066](0066.md) becomes the *only* pairing path.

**What it actually grants.** A key in KVS is readable by this app on every device
signed into that Apple ID. Mode A therefore means "any device on my Apple ID can
write to my media library" — which is probably the user's intent, but it is a
policy, and it should be stated in the UI rather than inferred. It also means the
key's blast radius is the Apple ID, so it must be rotatable ([#0067](0067.md)).

## Steps to reproduce

1. Sit at the MacBook Air, signed into the same Apple ID as the mini.
2. Expect the client to discover the host and pair without being asked anything.

## Expected behavior

The host generates a 32-byte key on first launch, keeps the authoritative copy in
its Keychain, mirrors it to KVS, and a same-Apple-ID client pairs silently. If
iCloud is unavailable, not signed in, or KVS has not synced, the UI says so plainly
and offers PIN pairing ([#0066](0066.md)) instead of hanging.

## Actual behavior

No pairing of any kind exists, and it is not established that an unsandboxed
Developer ID build can provision a ubiquity KVS container at all.

## Plan

**Step 1 — settle the sandbox question first. This is the whole risk of the ticket
and it is cheap to answer.** In a scratch branch (no commit):

- Add the `com.apple.developer.ubiquity-kvstore-identifier` entitlement to a
  `Changeover.entitlements` file and wire `CODE_SIGN_ENTITLEMENTS` in the target.
  Note that the project has no entitlements file today — `grep ENTITLEMENTS
  Changeover.xcodeproj/project.pbxproj` returns nothing.
- Enable the iCloud capability with key-value storage for the App ID
  `co.sstools.Changeover` (`project.pbxproj:412`, `:441`) in the developer account.
- Leave `ENABLE_APP_SANDBOX = NO`.
- Build, sign with the Developer ID identity, run, and call
  `NSUbiquitousKeyValueStore.default.synchronize()`, then write and read a value.
  Log the result and watch for the container-provisioning failure in Console.

The outcome is binary and determines everything below. **Record it in this ticket
before writing the pairing service.** If KVS does not provision without the
sandbox, close this ticket `wontfix` with the evidence, mark Mode A unavailable on
macOS in `Docs/Pairing.md`, and re-scope [#0066](0066.md) as the sole pairing path
with a correspondingly better UX. Do not attempt to split the host into a sandboxed
helper to obtain the entitlement — that is a disproportionate amount of XPC
machinery for a convenience feature.

**Step 2 — the pairing service, if step 1 passes.** Add a `PairingService` to the
app target (not the package — it is platform-specific and touches iCloud and the
Keychain differently per platform):

- `func hostKey() throws -> SymmetricKey` — reads the Keychain, generating and
  storing a fresh `SymmetricKey(size: .bits256)` on first call. The Keychain is the
  source of truth; KVS is a mirror, never the authority. A key that exists only in
  KVS must never be trusted by the host, because KVS is writable by any copy of the
  app on the account and a host that adopts a key it did not generate can be steered.
- `func publishToKVS()` on the host — writes the key and a generation counter.
- `func adoptFromKVS() -> SymmetricKey?` on the client — reads, validates length,
  stores in the client's own Keychain, and stops consulting KVS thereafter.
- Observe `NSUbiquitousKeyValueStore.didChangeExternallyNotification` so a client
  that launches before the key syncs picks it up without a relaunch.

**Step 3 — the honest failure UI.** KVS sync latency is unpredictable — this is the
same property that disqualified the iCloud Drive job-drop option in
`RemoteControl.md`. The client must not present an indefinite spinner. Show
"Looking for Changeover on your iCloud account…" with a visible **Pair with a code
instead** button from the first second, not after a timeout. Distinguish four
states in the UI: iCloud unavailable, not signed in, signed in but no key yet,
and paired. `FileManager.default.ubiquityIdentityToken` is the cheap check for the
first two.

**Step 4 — convention compliance.** `PairingService` is a plain `final class`, and
if any of it is observed by a view it uses `@Observable` from `Observation` — never
`ObservableObject`/`@Published`/`@StateObject`, per `Plan.md`. It gets `@MainActor`
for free from `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` (`project.pbxproj:416`),
which is correct here: KVS notifications arrive on the main thread and the Keychain
calls are fast. Do not make it an `actor`. Views own view models with `@State`;
pass the service via `.environment(...)` alongside `AppSettings`, the way
`AppDelegate` already injects settings (`Changeover/AppDelegate.swift:43`, `:87`).

**Where the host surfaces it.** `StatusMenuView` currently shows a configured/
unconfigured dot (`Changeover/StatusMenuView.swift:14-21`). Add a pairing row there
and a pairing section in `SettingsView`, which is where the user already manages
credentials (`Changeover/SettingsView.swift:46-60`).

## Notes

**The step-1 spike is the verification that matters, and it cannot be faked.** It
needs a signed build with a real entitlement against a real Apple ID. A simulator
or an unsigned debug build proves nothing about entitlement provisioning. The
`## Verification` for this ticket must state which build was signed with which
identity and what Console showed.

**Unit-testable without iCloud:** key generation and length, Keychain round trip
(against a test keychain, not the login keychain), the rule that a KVS-sourced key
is never adopted by the host, and the four-state UI logic driven by an injected
fake. Inject the KVS dependency behind a small protocol so the tests never touch
`NSUbiquitousKeyValueStore`.

**Requires two real machines on one Apple ID:** the actual silent pairing, and the
sync-latency behaviour that the fallback UI exists to cover.

**Security note to carry into the UI copy:** Mode A grants library write access to
every device on the Apple ID that runs this app. That is defensible as a default but
must be stated where the user turns it on, and it must be revocable per peer via
[#0067](0067.md) — rotating the KVS key has to invalidate previously adopted peers,
which is why the generation counter in step 2 exists.
