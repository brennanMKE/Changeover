# 0047 — Nothing stops the Mac idling to sleep in the middle of a rip or an encode

| | |
|---|---|
| **Status** | open |
| **Phase** | 3 — Unattended multi-disc |
| **Module** | PowerManagement |
| **Platform** | macOS |
| **First seen** | 2026-09-11 |

## Description

Changeover takes no power assertion of any kind, so a headless Mac mini on default energy settings can idle-sleep partway through a job that has no keyboard or mouse activity to keep it awake for a hour or more. The app must hold a `ProcessInfo.beginActivity` assertion while any job is active and release it the moment the queue drains.

## Long Description

This is only a Phase 3 problem in degree, but the degree is what matters: a single supervised rip finishes while someone is nearby, whereas the Phase 3 demo is explicitly "sit down" and "no interaction beyond swapping and selecting" (`Roadmap.md:139-155`) across three discs. That is the scenario where the machine goes to sleep.

The stakes are higher than a paused encode. `HandBrakeCLI` resumes after a sleep, but a `makemkvcon` rip across a disc that spun down can fail outright, and the working directory then holds a truncated `.mkv`. The Phase 1 defect where a leftover `.mkv` is picked up as the current movie (`Roadmap.md:35-38`) is fixed by per-job directories, but a truncated file inside the *correct* job's directory still encodes into a half-length movie that lands in Plex looking finished.

There is also a Phase 4 dependency worth stating now rather than rediscovering: "Sleep kills discovery. If the mini sleeps, Bonjour advertisement stops" (`RemoteControl.md:444-446`). This ticket's assertion is scoped to active jobs, which is right for Phase 3 but will not be enough for Phase 4 — a client that wants to browse the host while it is idle needs a separate, user-controlled "stay discoverable" setting. Do not widen the scope here to pre-empt that; note it and let Phase 4 own it.

## Steps to reproduce

1. On a Mac with **Energy Saver** set to sleep after a short idle period, start a rip.
2. Do not touch the keyboard or mouse.
3. Run `pmset -g assertions` and look for an assertion owned by Changeover.

## Expected behavior

`pmset -g assertions` shows a `PreventUserIdleSystemSleep` assertion held by Changeover with a readable reason string for as long as any job is not in a terminal stage, and the assertion is gone within a moment of the last job finishing. The machine does not idle-sleep mid-job. Display sleep is unaffected — a headless mini has no display worth keeping lit, and holding the display awake would be a rude and pointless power cost.

## Actual behavior

No assertion is taken. `Changeover/AppDelegate.swift` sets up the status item, popover, DVD monitor and login item (`:16-26`) and never touches `ProcessInfo`. The only thing keeping the machine awake during a long job is whatever the user happens to be doing at the keyboard.

## Plan

### Files added

- `Changeover/PowerAssertion.swift`
- `ChangeoverTests/PowerAssertionTests.swift`

### Files changed

- `Changeover/Jobs/JobQueue.swift` — own a `PowerAssertion` and drive it from `hasActiveJobs`.

### The type

```swift
@Observable
final class PowerAssertion {
    private var token: (any NSObjectProtocol)?
    private(set) var isHeld = false

    func begin(reason: String)
    func end()
}
```

`begin` is a no-op when `token != nil` and `end` is a no-op when it is `nil`, so the calls are idempotent and a caller cannot leak or double-release by calling twice.

```swift
token = ProcessInfo.processInfo.beginActivity(
    options: [.userInitiated, .idleSystemSleepDisabled],
    reason: reason
)
```

Option choices, each deliberate:

- `.idleSystemSleepDisabled` — the actual requirement. Prevents idle system sleep only.
- `.userInitiated` — marks the work as user-initiated so App Nap does not throttle the app. A background menu bar app with no visible window (`LSUIElement = YES`) is a prime App Nap candidate, and a throttled app reads its subprocess pipes more slowly.
- **Not** `.idleDisplaySleepDisabled` — keeping a display awake for a headless rip is pure waste.
- **Not** `.automaticTerminationDisabled` — irrelevant; the app is not automatically terminable with a status item.

`beginActivity` returns a token whose *lifetime* is the assertion. Storing it in a `let` that goes out of scope ends the assertion immediately, which is the classic way this API silently does nothing. Hold it in a stored property, and `endActivity(_:)` explicitly rather than relying on deallocation.

### Driving it from the queue

`JobQueue.hasActiveJobs` from [#0042](0042.md) is the trigger. Rather than calling `begin`/`end` from a dozen scheduler paths — every one of which is a chance to leak the token on an error path — derive it in one place:

- After every mutation that could change activity (enqueue, any `transition(to:)` observed by the queue, pruning), call a single private `syncPowerAssertion()` that does `hasActiveJobs ? assertion.begin(reason:) : assertion.end()`.
- The reason string should name the work: `"Changeover: 2 jobs (ripping, encoding)"`. It is what appears in `pmset -g assertions`, which makes it the one piece of user-facing diagnostics this ticket produces. Recompute it on change.

The whole thing is MainActor-isolated by the module default. `ProcessInfo.beginActivity` is thread-safe, but there is no reason to reach for that — every call site is a queue mutation, which is already MainActor. No `actor`, no `nonisolated`, no lock.

### Risks

- **The assertion outliving the queue.** If the app quits mid-job the process dies and the assertion goes with it, which is fine. The real leak is a job reaching a terminal stage without `syncPowerAssertion()` being called — the mini then never sleeps again until the app is quit, and nobody notices for weeks. This is exactly why the sync is derived from one observed predicate rather than sprinkled through the scheduler. Add a `deinit` that calls `end()` as a backstop.
- **`hasActiveJobs` must actually invalidate.** `jobs` is an array of `@Observable` reference types, so mutating `job.state` does not invalidate readers of the array itself. `hasActiveJobs` reads job state inside a computed property, which does establish the dependency — but this must be **verified, not assumed**, and [#0042](0042.md) owes the `withObservationTracking` test that proves it. If that invalidation does not fire, this ticket's `end()` never runs.
- **What `beginActivity` does not do.** It does not prevent sleep when a lid is closed, when the user explicitly chooses Sleep, or on a low-battery shutdown. On a mains-powered mini none of those apply; if Changeover is ever run on a laptop this becomes a documentation item, not a code one.
- **Do not use `IOPMAssertionCreateWithName` directly.** `beginActivity` is the supported Foundation wrapper and it is the one Apple's own guidance points at. Reaching for the IOKit call adds a manual release path with the same leak risk and no benefit.

### Plan refresh (2026-09-15)

**Checked: still essentially current.** The `beginActivity` options, holding the token in a stored property, `pmset` as the proof, and not reaching for IOKit all stand. Small corrections:

- **Driver.**
  - `JobQueue.hasActiveJobs` becomes `JobController.isRunning`, which exists today (`JobController.swift:41`).
  - `isRunning` has exactly two mutation points, both on MainActor: set in `start` (`:105`) and cleared in `finish` (`:131-135`).
  - Call `begin` in `start` right before the `Task` launches, and `end` in `finish`. `finish` is the only exit from that `Task`, so there is no leak path and no observation-derived sync is needed.
  - **This ticket doesn't have to wait for #0041/#0042** and can land first. After #0042, the calls move with the `current` assignment.
- **Files.** The changed file is `JobController.swift`, not `Jobs/JobQueue.swift`. `AppDelegate`'s launch method is now `:24-40`, not `:16-26`.
- **Test seam:**

  ```swift
  protocol SleepAssertion: AnyObject {       // MainActor by default
      var isHeld: Bool { get }
      func begin(reason: String)             // idempotent
      func end()                             // idempotent
  }
  final class ProcessInfoSleepAssertion: SleepAssertion { … }   // [.userInitiated, .idleSystemSleepDisabled]
  ```

  `JobController.init(maxLogLines:runner:sleepAssertion: SleepAssertion = ProcessInfoSleepAssertion())`. Controller tests inject a recording fake. The real type's idempotence is tested directly; a real assertion taken in the test host is released immediately and is harmless. `@Observable` is unnecessary.
- **Drop the `deinit` backstop.** Under default MainActor isolation, a `deinit` can't call `end()` without isolated-deinit machinery. The controller lives as long as the app, and process exit releases the assertion anyway.
- **Reason string (option A):** `"Changeover: encoding <Title (Year)>"`. The multi-job form returns only under #0040's option B.
- **Stakes paragraph.** The truncated `makemkvcon` `.mkv` is now a HandBrake read from a disc that spun down mid-encode. The classifier and watchdog are likelier to fail that job than to ship a half-length movie, but a sleep still costs the whole job. MakeMKV is exposed only through the #0015 fallback.
- **Worth knowing, no change needed.** The inactivity watchdog uses `DispatchTime` uptime (`ProcessRunner.swift:528-548`), which doesn't advance during system sleep. A sleep alone won't trip the 30-minute hang detector.
- **Not covered, and acceptable:** a disc scan that runs outside a job. `DiscScanner` isn't wired in yet, and a scan takes about a minute.

**Tests** — no disc, run through `./run-remote-tests.sh gordon`, stub `Runner` with a gate:

- the assertion is held while the stub job runs;
- it is released after success, after a failure, and after a cancel (the last once #0046 lands);
- `begin` is never called when `start` refuses (already running, or no disc);
- the reason string names the job.

**Manual on joe, unchanged:** the `pmset -g assertions` and `log show` checks above, during a real job.

## Notes

**Verification.** The token bookkeeping is unit-testable without any hardware: `ChangeoverTests/PowerAssertionTests.swift` asserts that `begin` sets `isHeld`, that a second `begin` does not create a second token, that `end` clears it, that a second `end` is harmless, and — driven through a `JobQueue` populated by hand — that `hasActiveJobs` going true takes the assertion and going false releases it, including the case where the last job ends by **failing** rather than succeeding, and the case where a job is pruned.

Whether the Mac actually stays awake is not unit-testable and must be labelled manual in `## Verification`. The specific check:

```bash
pmset -g assertions | grep -i changeover
```

Run it with the queue idle (expect nothing), during a job (expect `PreventUserIdleSystemSleep` with the reason string naming the job count), and after the queue drains (expect nothing again). The end-to-end proof is the Phase 3 exit criterion itself: set the idle sleep timer short, run a three-disc session, and confirm from the system log (`log show --predicate 'eventMessage CONTAINS "Entering Sleep"' --last 2h`) that no sleep occurred while jobs were running and that the machine sleeps normally afterwards.
