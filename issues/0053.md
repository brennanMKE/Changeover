## Description

Found during the first real-disc run on joe (2026-09-16), twice. `Start Ripping` is bound to `StartGate.canStart(...)`, which returns a bare `Bool` (`Changeover/MetadataEntryView.swift:287-300`). When it returns false the button is simply greyed, with no tooltip, no caption and nothing in the log. The user's reasonable reading is "the button is broken".

There are at least eight distinct reasons the gate can refuse: no movie selected, a job already running, no disc, the disc unavailable after a partial eject (#0049), the scan not finished, no title selected, no audio track selected (#0027), a runtime lookup still loading, and an unacknowledged runtime mismatch (#0032). Every one of them is actionable by the user, and none of them is shown.

Note the id: the Phase 2 block (0020–0039) is full, so this takes the next free id in the Phase 3 block, per `issues/Issues.md`'s numbering rule. It is a Phase 2 defect by subject.

## Resolution notes

> 🟢 Resolved 2026-09-16 — A disabled Start button now states its reason, from a pure `StartGate.decide` returning a typed `StartDecision` with one case per refusal, shown as the button's tooltip and as a caption beside it, and reused for `JobController.start`'s matching log lines (b45403d, review fix a170acf).

**Review (2026-09-16, claude-opus-5).** b45403d was in scope and correct in structure: `decide` is the only decision, `canStart` is exactly `decide(...) == .ready` with its signature and truth table unchanged, `StartDecision` is file-scope, `nonisolated` and `String`-`Codable` as #0070 needs, and no guard in `start` was weakened or reordered — the four rewritten guards still refuse the same inputs, still `return false`, and the four `reason!` force-unwraps are all on non-`.ready` cases, which is the only case with a `nil` reason. The reused log lines read correctly, and `JobControllerEjectTests`' byte-exact assertion on the partial-eject sentence still passes.

One reachable state was wrong and two captions used our words instead of the window's. a170acf fixes all three:

1. **A zero-title scan told the user to "Pick a title." with no picker on screen.** #0039's zero-title case is a *successful* scan carrying an empty title list, so it lands in `decide`'s `.scanned` branch, fails the title lookup and returned `.noTitleSelected` — while `DiscTitleListView.noTitlesView` renders exactly that state as a failure: the scan's own message, a Rescan button, and deliberately no table. The caption named a control that isn't there. New `StartDecision.noTitlesOnDisc`, checked at the top of the `.scanned` branch: "The scan read no titles from this disc — rescan before starting." `canStart`'s truth table is unchanged (that state refused before and refuses now).
2. **`.runtimeLookupLoading` said "Waiting on the TMDB runtime lookup."** "Runtime lookup" is our name for the type, not the screen's: `MetadataEntryView`'s own caption for the same state says "Checking TMDB runtime…". Now "Checking the TMDB runtime — this finishes on its own."
3. **`.runtimeMismatchUnconfirmed` said "Confirm the runtime mismatch."** The only control that confirms it is #0032's **Rip anyway** button under the mismatch line; a user reading the caption would hunt for a Confirm button. Now "Confirm the runtime mismatch with Rip anyway.", with a test pinning that the caption names that button.

**Ordering, checked state by state.** The chain is defensible everywhere it is reachable:

- *No disc + no movie* → "No disc is mounted — insert a DVD before starting." Right: the movie search is useless without a disc to rip.
- *A Play All disc* → nothing is preselected (#0026), so the caption is "Pick a title.", and `DiscTitleListView` has just said "Ripping is still possible by picking a title below". The two agree, and the table is on screen. Correct.
- *Mismatch unconfirmed with a stale acknowledgement for another movie* → `isAcknowledged` requires the ack to name both the title index and the movie the lookup is for, so a stale ack does not count and the caption asks for confirmation again. Correct, and this is #0032's stop-and-ask intent.
- *The screenshot case* (scan done, title picked, tracks ticked, no movie chosen) → "Choose a movie.", as the Plan required, pinned by `theScreenshotCaseSaysChooseAMovie`.
- *Scan failed + no movie* → "Choose a movie.", not "rescan". Considered and kept: the scan failure is already on screen in red with its own Rescan button beside it, the caption is not the only channel, and choosing the movie is work the user must do on this disc regardless. Hoisting `.scanFailed` above the movie check would split the `scanState` checks across the movie check for a state whose remedy is already the loudest thing in the window.

**Tests.** 20 new cases in b45403d — one per `StartDecision` case, the screenshot scenario, the adjacent ordering pairs, and the `canStart ≡ decide == .ready` sweep — are behavioural, not a restatement: the implementer's falsification (swapping the guard order on gordon's copy only) failed exactly the two priority tests that rule covers and nothing else. a170acf adds 4 more, including the one adjacent pair that was missing (a missing audio pick outranks a still-loading lookup, which b45403d's mismatch test skipped by using a `.loaded` lookup).

**On-screen check owed on joe** (not done here — the user is mid-encode, and no subagent touches joe): the caption and tooltip rendering for each decision in the running app, and specifically that the screenshot's own disc shows "Choose a movie" beside the greyed button. Worth watching for one layout detail: the caption is a plain `Text` in the action bar's `HStack`, so the longest sentence (the partial-eject one, ~100 characters) may truncate in a narrow window — the full text is still in the tooltip, but it may want a `lineLimit(2)` once it has been seen on screen.

## Expected behavior

When Start is disabled, the user can tell why without guessing: a help tooltip on the button, and ideally a short caption beside it naming the next action ("Choose a movie", "Pick a title", "Keep at least one audio track", "Confirm the runtime mismatch", "Waiting for the scan").

## Actual behavior

The button is greyed with no explanation anywhere in the window.

## Plan

- Replace `StartGate.canStart` with (or add alongside it) `StartGate.decide(...) -> StartDecision`, a pure enum: `.ready` plus one case per refusal, each carrying a short user-facing sentence. `canStart` becomes `decide(...) == .ready` so existing call sites and tests keep working.
- `MetadataEntryView` shows the reason as `.help(...)` on the button and as a caption next to it. Keep the view thin; all wording comes from the pure type, and is unit-tested case by case.
- Order the checks so the message names the *first* thing the user should do, not an arbitrary one. The screenshot case ("scan done, title picked, tracks ticked, no movie chosen") must say "Choose a movie".
- Reuse the same decision for `JobController.start`'s refusal log lines where the wording matches, so the button and the log can't disagree.
- Phase 4 note: #0070 already plans to gate remote Start on `StartGate`; a typed decision is what it needs to send back to a client, so keep it `Codable`-friendly and free of AppKit.

## Root cause

`StartGate.canStart` (`Changeover/StartGate.swift`, from #0026) collapsed nine independent refusal reasons — a running job, no disc, a disc unmounted-but-not-ejected (#0049), the scan not finished, no title selected, no movie selected, no audio track kept (#0027), a still-loading TMDB runtime lookup (#0032), and an unconfirmed runtime mismatch (#0032) — into a single `Bool`. `MetadataEntryView.actionBar` bound `.disabled(...)` directly to that `Bool` with a fixed `.help(...)` string ("Encode the selected title into the Plex library.") that never changed to reflect *why* the button was disabled. There was nowhere for the reason to go once it collapsed to `false`.

## Fix

Added `StartDecision` (`Changeover/StartGate.swift`), a `String, Equatable, Sendable, Codable` enum at file scope (matching the `ScanState`/`RuntimeLookup` convention already established for types a `nonisolated` decision function takes as a plain value) with one case per refusal plus `.ready`, and a `reason: String?` computed property giving each non-ready case a short, user-facing sentence naming the next action (`.ready` has none; a review pass added an eleventh case, `.noTitlesOnDisc`, in a170acf). `StartGate.decide(...)` replaces `canStart`'s body with the same guard chain, now returning the specific `StartDecision` instead of `false`. `canStart` is now exactly `decide(...) == .ready`, with its original signature and default-parameter kept, so every existing call site and test compiles and passes unchanged — the underlying truth table is unaffected by check order, only *which* reason wins when several would refuse.

**Ordering.** Per the Plan's requirement, `decide` orders environment blockers (a running job, disc state) ahead of content choices, and orders the content checks the way the window itself reads top to bottom: movie → disc title → tracks → runtime cross-check.
```
isRunning → discUnavailable → hasDisc → hasMovieSelected → scanState (in progress / failed) → zero titles on the disc → selectedTitleIndex → audio selection → runtimeLookup (loading) → runtime mismatch → .ready
```
This makes the screenshot's exact case (scan done, title picked, tracks ticked, no movie chosen) say "Choose a movie" — every check ahead of `hasMovieSelected` passes for that disc state, so it's the first (and only) one that fails.

**View.** `MetadataEntryView.actionBar` computes a `startDecision` property once (`StartGate.decide` fed from the same inputs `canStart` used before) and uses it for the button's `.disabled(startDecision != .ready)`, its `.help(startDecision.reason ?? "Encode the selected title into the Plex library.")` tooltip, and a `Text` caption shown beside the button when a reason exists. All wording lives in `StartDecision`; the view stays a thin `if let reason = ...` the same way `failureBanner` already reads `FailurePresenter`'s output.

**Reused wording in `JobController.start`.** Where `start`'s own failsafe guards refuse for exactly the same reason a `StartDecision` names — no disc, an unmounted-but-not-ejected disc, no audio track, a job already running — the guard now interpolates `StartDecision.<case>.reason!` instead of a separately hand-written literal, so the button/caption and the log line can't drift apart by an unrelated wording edit. `start`'s other guards (a movie picked for a different disc, a title/track index that no longer resolves against the currently held scan) have no `StartDecision` equivalent — they are `start`'s own point-of-harm failsafe (the #0034 pattern), not something the UI can ever observe as a distinct button state, so they keep their own wording unchanged. No guard in `start` was weakened or reordered.

**Decisions made (delegated, per the Plan's invitation to make sensible calls):**

- **`StartDecision` is a raw-`String` `Codable` enum**, not just `Equatable, Sendable`, per the Plan's #0070 note — a plain string case name is the simplest thing that crosses a JSON wire cleanly for a future remote client's Start gating.
- **Split `start`'s single "no completed disc scan" guard into two `StartDecision` cases**, `.scanInProgress` (`.idle`/`.scanning`) and `.scanFailed` (`.failed`) — a caption telling the user to wait is different advice from one telling them to rescan, even though `start`'s own failsafe treats both the same way (refuse). `start`'s own guard message is unchanged and still covers both scan states in one sentence, since splitting it there would need to be threaded through `EncodeSelection.make`'s combined title/track-mismatch message too, which is out of this ticket's scope.
- **`.noAudioTrackSelected`'s reason and `.noDisc`'s reason are the exact byte-for-byte text `start` already logged** for those cases (see Files changed) — not the shorter illustrative captions the Plan sketches ("Keep at least one audio track") — because an exact match let the log line be *derived from* the decision's wording rather than merely similar to it, which is the stronger form of "can't disagree." `.noMovieSelected` and `.noTitleSelected` use the Plan's own suggested short captions verbatim ("Choose a movie.", "Pick a title.") since `start` has no directly corresponding guard for either. (Review, a170acf: `.runtimeMismatchUnconfirmed` was the Plan's "Confirm the runtime mismatch." too, but now names the **Rip anyway** button that actually confirms it.)

## Files changed

- `Changeover/StartGate.swift` — new file-scope `StartDecision` enum (`.ready` + 11 refusal cases after a170acf) with `reason: String?`; new `StartGate.decide(...)`, the guard chain `canStart` used to run, now returning `StartDecision`; `canStart` reimplemented as `decide(...) == .ready`.
- `Changeover/JobController.swift` — `start`'s `isRunning`/`discUnavailable`/`insertedDisc`/audio-empty guards now interpolate `StartDecision.<case>.reason!` instead of a separately hand-written literal (`isRunning`'s message is reworded slightly to embed the shared sentence while still containing "already running"; `discUnavailable`/`noDisc`/`noAudioTrackSelected` are now byte-identical to their `StartDecision` case, which they already matched verbatim before this change).
- `Changeover/MetadataEntryView.swift` — new `startDecision` computed property; `actionBar` uses it for `.disabled`, `.help(...)`, and a caption `Text` shown beside the button.
- `ChangeoverTests/StartGateTests.swift` — 24 new tests (20 in b45403d, 4 in a170acf): one per `StartDecision` case, the screenshot scenario, six ordering-priority tests, and two equivalence checks (`.ready` has no reason and every other case does; `canStart` is exactly `decide(...) == .ready` over a representative sweep).

## Gotchas

- **`start`'s "no completed disc scan" guard and the `EncodeSelection.make` mismatch guard have no 1:1 `StartDecision` equivalent.** The first covers `StartDecision.scanInProgress` *and* `.scanFailed` in one message (kept as-is, unsplit, since splitting it would touch `DiscScanner`/`EncodeSelection` plumbing outside this ticket's scope); the second is `start`'s own point-of-harm failsafe for a title/track index that no longer resolves against the currently held scan — a case `StartGate.decide` doesn't model at all, because the UI-level `selectedTitleIndex`/`selectedAudioTrackNumbers` can't independently drift from the scan the way a request replayed through Retry (#0048) can. Left alone, per the Plan's "don't weaken `start`'s guards."
