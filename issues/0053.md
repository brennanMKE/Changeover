# 0053 — The Start Ripping button never says why it is disabled

| | |
|---|---|
| **Status** | open |
| **Phase** | 3 — Unattended multi-disc |
| **Module** | MetadataEntryView / StartGate |
| **Platform** | macOS |
| **First seen** | 2026-09-16 |

## Description

Found during the first real-disc run on joe (2026-09-16), twice. `Start Ripping` is bound to `StartGate.canStart(...)`, which returns a bare `Bool` (`Changeover/MetadataEntryView.swift:287-300`). When it returns false the button is simply greyed, with no tooltip, no caption and nothing in the log. The user's reasonable reading is "the button is broken".

There are at least eight distinct reasons the gate can refuse: no movie selected, a job already running, no disc, the disc unavailable after a partial eject (#0049), the scan not finished, no title selected, no audio track selected (#0027), a runtime lookup still loading, and an unacknowledged runtime mismatch (#0032). Every one of them is actionable by the user, and none of them is shown.

Note the id: the Phase 2 block (0020–0039) is full, so this takes the next free id in the Phase 3 block, per `issues/Issues.md`'s numbering rule. It is a Phase 2 defect by subject.

## Expected behavior

When Start is disabled, the user can tell why without guessing: a help tooltip on the button, and ideally a short caption beside it naming the next action ("Choose a movie", "Pick a title", "Keep at least one audio track", "Confirm the runtime mismatch", "Waiting for the scan").

## Actual behavior

The button is greyed with no explanation anywhere in the window.

## Plan

- Replace `StartGate.canStart` with (or add alongside it) `StartGate.decide(...) -> StartDecision`, a pure enum: `.ready` plus one case per refusal, each carrying a short user-facing sentence. `canStart` becomes `decide(...) == .ready` so existing call sites and tests keep working.
- `MetadataEntryView` shows the reason as `.help(...)` on the button and as a caption next to it. Keep the view thin; all wording comes from the pure type, and is unit-tested case by case.
- Order the checks so the message names the *first* thing the user should do, not an arbitrary one. The screenshot case ("scan done, title picked, tracks ticked, no movie chosen") must say "Choose a movie".
- Reuse the same decision for `JobController.start`'s refusal log lines where the wording matches, so the button and the log can't disagree.
- Phase 4 note: #0070 already plans to gate remote Start on `StartGate`; a typed decision is what it needs to send back to a client, so keep it `Codable`-friendly and free of AppKit.
