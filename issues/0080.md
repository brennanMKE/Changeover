# 0080 — Phase 5 — the remote client does not run on iPhone or iPad

| | |
|---|---|

| **Platform** | iOS · iPadOS |

## Description

Phase 4 delivers a remote client that runs only on macOS, so the disc-triage
loop still requires a laptop. Phase 5 extends that client to iPhone and iPad —
the couch case — which is the payoff for the entire remote track.

## Long Description

`RemoteControl.md` is explicit that the remote exists for the **decision steps**,
not the disc swap: which movie is this, which titles do we want, which audio and
subtitle tracks, and is it done. Those are couch activities. A Mac-only client
puts the user back at a desk, which is most of the way back to walking over to
the mini.

This umbrella covers the work to make one SwiftUI codebase run correctly on
macOS, iOS and iPadOS. The roadmap frames that as "restructure the remote client
as a multiplatform target", which understates it. The shared views are not
platform-neutral today: `MetadataEntryView` hard-codes a 480pt window width
(`Changeover/MetadataEntryView.swift:22`) and uses two AppKit-only semantic
colors (`:108`, `:191`); `SettingsView` imports AppKit directly
(`Changeover/SettingsView.swift:2`) and drives an `NSOpenPanel`
(`:105–116`) and `NSApp.keyWindow?.close()` (`:129–131`); every window in the
app is an `NSWindow` hosting an `NSHostingView`
(`Changeover/AppDelegate.swift:78–92`, `:106–120`). Porting those is real work,
not a recompile.

Beyond layout, iOS adds three problems macOS does not have: an app that gets
**suspended** (killing the socket and desynchronizing job state), a **stricter
and more visible Local Network permission prompt**, and a **separate
`UNUserNotificationCenter` authorization flow** from the one Phase 1 set up on
the host.

### Demo

> Same loop as Phase 4, done entirely on an iPhone while sitting down —
> including the notification when the disc ejects and it's time to swap.
> Then the same thing on an iPad to show the wider split layout.

## Steps to reproduce

1. Complete Phase 4 ([#0060](0060.md)): the host advertises `_changeover._tcp`
   and the macOS remote client drives a full rip.
2. Open `Changeover.xcodeproj` and look at the destination list for the remote
   client scheme.
3. Try to select an iPhone or iPad destination.

## Expected behavior

The remote client scheme offers iPhone, iPad and Mac destinations, builds for
all three, pairs with the host, and drives the full loop from a phone on the
couch — including a notification when the disc ejects with the app backgrounded.

## Actual behavior

The project targets macOS only — `SDKROOT = macosx` and
`MACOSX_DEPLOYMENT_TARGET = 26.2` at both project-level build configurations
(`Changeover.xcodeproj/project.pbxproj:328`, `:332`, `:386`, `:389`) — and the
shared views will not compile for iOS even if a destination is added, because of
the AppKit dependencies listed above.

lifecycle, notifications) are not left as a scramble at the end of the phase.

**Verification for this phase is device-bound.** A simulator cannot prove
Bonjour discovery to a physical Mac, cannot exercise real app suspension, and
does not reproduce the Local Network permission prompt faithfully. The phase is
not done until it has been run from a real iPhone and a real iPad against the
real mini. See `issues/Issues.md` "Verification caveat specific to this
project".

### Phase exit criteria

- Full loop from an iPhone, start to eject: disc appears, TMDB search, poster
  confirmed, title and tracks chosen, rip started, log streamed, disc ejects.
- Notifications arrive with the app backgrounded and with the screen locked.
- The same build runs correctly on iPad with a split layout, not a stretched
  phone layout.
- Killing the app mid-job and relaunching reconnects and re-syncs state, disc
  info and log backlog.
- An iPhone that has never paired can pair with a six-digit PIN without help.
- Denying Local Network access produces an explanation and a route to Settings,
  not a silent empty device list.

## Plan

This umbrella ships no code. It is resolved when every child is terminal.

**Ordering.** [#0081](0081.md) and [#0082](0082.md) are a pair and must land
first: the target does not compile for iOS until the AppKit audit is done, and
the audit cannot be verified until an iOS destination exists. Do [#0081](0081.md)
first with the shared views excluded from the iOS target, then [#0082](0082.md)
to bring them in.

Layout work ([#0083](0083.md), [#0084](0084.md), [#0085](0085.md)) follows and
can be parallelized, with the caveat that [#0084](0084.md) is blocked on Phase 2
([#0020](0020.md)) actually having shipped a title picker.

The two runtime tickets ([#0086](0086.md), [#0087](0087.md)) and the two
permission/pairing tickets ([#0088](0088.md), [#0089](0089.md)) depend only on
[#0081](0081.md) and on Phase 4's transport, so they can start as soon as the
target builds. Start [#0087](0087.md) early — it is the one most likely to
surface protocol gaps that have to go back to [#0060](0060.md).

**Re-audit before opening the layout tickets.** Per the umbrella pattern, once
[#0081](0081.md) and [#0082](0082.md) land, re-read [#0083](0083.md)–[#0085](0085.md).
The shape of the shims chosen in [#0082](0082.md) will change how much layout
work is actually left.

**Constraints that apply to every child.** `@Observable` only — never
`ObservableObject`, `@Published`, `@StateObject` or `@ObservedObject`. View
models are owned by views with `@State` and passed down with `@Bindable`.
`SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` must be set on every new target
(matching `Changeover.xcodeproj/project.pbxproj:416` and `:445`), so new types
are `@MainActor` for free and `nonisolated` is written only where a type
genuinely must leave the main actor.
