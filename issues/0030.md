## Description

Every TMDB search requires clicking `Search` or pressing Return
(`Changeover/MetadataEntryView.swift:34-38`), and results come back in whatever order
the API returned them (`Changeover/TMDB/MovieSearchViewModel.swift:28`) — so an exact
title match can sit below a remake or a documentary about it. `Plan.md` 11.1 and 11.7
cover both, and `Roadmap.md` line 309 folds them into Phase 2.

## Long Description

This is the one Phase 2 ticket that is not about discs. It is here because
`Roadmap.md`'s cross-cutting notes (lines 308–309) put it here:

> Debounced type-to-search and result sorting (`Plan.md` 11.1, 11.7). Polish; fold
> into Phase 2 where the search UI is already being touched.

Note that `Roadmap.md` carries this under "Things deliberately not in this roadmap"
(line 309) rather than in the Phase 2 work list (lines 108–120), so there is no
corresponding bullet up there — it is filed here so the fold-in is tracked rather
than implied.

That reasoning holds — [#0026](0026.md) and [#0027](0027.md) are both restructuring
`MetadataEntryView`, so touching the search half in the same phase avoids a second
pass over the same file. It is genuinely lower priority than the rest of the block
and contributes nothing to the phase demo; if Phase 2 runs long, this is the ticket
to drop.

Half the debounce machinery is already in place: `runSearch()` cancels the previous
task before starting a new one (`Changeover/MetadataEntryView.swift:137-140`), and
`searchTask` is held as `@State` (`:9`). What is missing is a trigger on query
change and a delay before the request goes out.

## Resolution notes

> 🟢 Resolved 2026-09-15 — Typing now searches after a 350ms debounce and results sort exact > prefix > rest, newest first, and after review only the latest search can publish and the list selection follows the view model (2333f4d, review fix ba6aa26).

**Review (2026-09-15, claude-opus-5).** 2333f4d was in scope and its sort
and debounce were right, but two things were wrong. ba6aa26 fixes them:

1. **A superseded search still published.** `search(apiKey:)` had no
   generation check. A keystroke, Return, a blank query or a disc reset
   cancels the in-flight search, and URLSession throws `URLError.cancelled`
   for a cancelled task. The old search's `catch` then blanked `results`,
   showed a red "cancelled" error, and its `defer` cleared `isLoading` under
   the newer search. After Return that error stayed on screen next to the
   new results. A late response that ignored cancellation overwrote the newer
   results. Backspacing to empty mid-flight left the spinner running and then
   showed the error. Now `search` takes a generation and publishes (results,
   error, `isLoading`) only while it is current and not cancelled.
   `cancelSearch()` (used by `runSearchNow`, `queryChanged` and
   `resetForNewDisc`) retires the generation and stops the spinner. The
   blank-query path also clears the selection, so the view model alone never
   keeps a `selectedMovie` for results it has cleared.
2. **The re-pick bug came back through the debounce window.** The view
   cleared `selectedID` on each keystroke, but `vm.selectedMovie` was
   cleared only when the debounced search fired 350ms later. A row clicked
   in that window was selected, then `search` dropped `selectedMovie` and
   left `selectedID` set. If the new results held the same id, the row
   stayed highlighted, Start stayed disabled, and clicking it fired nothing.
   The view now also sets `selectedID = nil` whenever
   `vm.selectedMovie?.id` becomes nil.

**Judged and kept.** Clearing the pick on every keystroke is acceptable. Any
new search replaces the list and `search` already cleared `selectedMovie`,
so a refinement could never keep the pick. Clearing at once just makes the
preview and Start go away while typing, not 350ms later. It doesn't touch a
running job: `jobs.start` copied its `MovieMetadata`, the #0026
`MismatchAcknowledgement` lives on `JobController` keyed by movie id, and
with no selection `SelectionReset.reconcile` returns `.keep`. `resetForNewDisc`
setting `query = ""` re-fires `onChange(of: vm.query)` into the blank path,
which is harmless. The sort is correct: stable by original index, a missing or
short `releaseDate` sorts last in its group, and case/diacritic folding comes
from `compare`/`range(of:)` options. A leading "The" is not ignored ("Matrix"
won't rank "The Matrix" as a prefix match), which is fine for now. The
`Sleeper` is a nonisolated `@Sendable` closure, and the debounce `Task`
inherits MainActor.

**Weak test fixed.** With an instant sleeper, removing the sleep from
`queryChanged` entirely still passed all four debounce tests. ba6aa26 adds
`theDebouncedSearchWaitsForTheSleeperWithTheDebounceDelay` (a gated sleeper:
no request until it returns, asked for `debounceDelay`),
`aSupersededSearchReturningLateNeverOverwritesTheNewerSearch` (late error and
late results) and
`blankingTheQueryWhileASearchIsInFlightStopsTheSpinnerAndDropsItsResponse`.
All use gates and yields, with no real waits and no network.

## Root cause

Two independent gaps in the search UI:

1. `MetadataEntryView`'s `TextField` only fired a search from `.onSubmit` or the
   `Search` button (`:70-74` before this fix) — nothing observed `vm.query` changing
   as the user typed.
2. `MovieSearchViewModel.search(apiKey:)` assigned TMDB's response straight to
   `results` with no reordering, so `/search/movie`'s raw (roughly popularity-based)
   order decided what showed up first, not title relevance.

Handoff bug found during #0026/#0034: `MetadataEntryView`'s `selectedID` (`@State`,
drives `List(selection:)`) was never cleared when a new search ran. `vm.search`
already reset `selectedMovie`/`runtimeLookup`, but `selectedID` stayed pointing at
whatever row index/id was previously selected. If the new results happened to
contain a movie with the same `id` at a different row and the user picked it again,
`selectedID`'s *value* didn't change, so `.onChange(of: selectedID)` never re-fired,
`vm.select(movieID:apiKey:)` never ran again, and `runtimeLookup`/`selectedMovie`
stayed at whatever `search()` had reset them to — `Start Ripping` stuck disabled.

## Fix

- Added `MovieSearchViewModel.queryChanged(apiKey:)` — the as-you-type entry point.
  It cancels any pending search, and for a blank/whitespace-only query clears
  `results`/`errorMessage` synchronously (no request), matching the `Search`
  button's own disabled condition instead of surfacing `TMDBError.emptyQuery` on
  every backspace to empty. Otherwise it schedules a debounced search behind a new
  injected `Sleeper` seam (`typealias Sleeper = @Sendable (Duration) async throws ->
  Void`, default `{ try await Task.sleep(for: $0) }`) with a 350ms
  `debounceDelay`, so tests can replace the real wait with an instant (or
  gated) stand-in — no real waiting, no timing flakiness.
- Added `MovieSearchViewModel.runSearchNow(apiKey:)` for the immediate Return /
  `Search`-button path. Both entry points share one internal `searchTask`, so
  whichever fires last cancels the other — the immediate path and the debounce
  can no longer race and produce two requests. (Review correction: cancelling
  alone did not stop a superseded in-flight search from publishing its error or
  results. ba6aa26 adds a generation check; see Resolution notes.)
- `resetForNewDisc()` (#0034) now also cancels `searchTask`, so a pending debounced
  search for the *previous* disc's query can't land after the reset and repopulate
  `results` for a disc that's no longer in the drive (the orchestrator's handoff
  note).
- Added `MovieSearchViewModel.sorted(_:for:)`, a `nonisolated static` pure function
  `search(apiKey:)` now runs the fetched results through before publishing them:
  exact title match (case- and diacritic-insensitive via
  `compare(_:options:[.caseInsensitive, .diacriticInsensitive])`) ranks first, then
  a prefix match (`.anchored` range search, same options), then everything else;
  within a rank, `releaseDate` year descending, with a missing/short `releaseDate`
  sorting *last* in its group (`Int.min`), never crashing and never floating to the
  top. The final tiebreaker is each element's original index, so equal
  rank+year results keep TMDB's own order (`sorted(by:)` isn't guaranteed
  stable otherwise).
- Fixed the handoff bug: both of `MetadataEntryView`'s search entry points — the
  new `.onChange(of: vm.query)` debounce trigger and `runSearch()` (Return / the
  button, now delegating to `vm.runSearchNow`) — clear `selectedID = nil` before
  triggering a search. That re-fires `.onChange(of: selectedID)` with `nil`,
  which itself calls `vm.select(movieID: nil, apiKey:)` and clears `selectionDisc`,
  so re-picking the same movie id in a fresh result set always re-runs the
  runtime lookup. `StartGate.isAcknowledged`/`MismatchAcknowledgement` were
  already keyed by `movieID` (#0026's review fix), so a stale "Rip anyway"
  acknowledgment already can't survive a movie change without further changes
  here — clearing the selection just makes sure `runtimeLookup` actually leaves
  `.loaded` for the old movie so that keying takes effect.
  (Review correction: the keystroke clear left a 350ms window where a click
  was dropped by the later `search`. ba6aa26 also syncs `selectedID` to
  `vm.selectedMovie` becoming nil.)
- Removed `MetadataEntryView`'s local `@State private var searchTask` — ownership
  of the debounce/immediate-search task moved into `MovieSearchViewModel` so the
  debounce behaviour is unit-testable directly against a stubbed `TMDBClient`,
  with no SwiftUI view instantiation needed. This is the one deviation from the
  plan's sketch (which kept `searchTask` as View `@State`); the plan's design was
  otherwise followed as written.

## Gotchas

- `nonisolated` cannot be applied to a `typealias` inside a `@MainActor` class —
  the project default-isolation build setting (`-default-isolation=MainActor`)
  still makes the alias usable from a `nonisolated` context (matches
  `TMDBClient.Transport`, which also carries no `nonisolated`); the modifier just
  has to be omitted, not added, unlike on the functions and structs elsewhere in
  this codebase.
- The debounce tests never actually wait out a delay: the injected `Sleeper`
  returns instantly, and what suppresses the first two of three rapid keystrokes
  is `searchTask?.cancel()` cancelling the still-not-yet-running prior `Task`
  before the cooperative executor gets a chance to run it — the same mechanism
  `select(movieID:apiKey:)`'s stale-response guard already relies on
  (`MovieSearchViewModelRuntimeTests`). No real timing is under test here, which
  is deliberate — real-time waits would make CI flaky depending on gordon's load.

## Steps to reproduce

1. Insert a disc (or open the metadata window from the menu bar).
2. Type a movie title. Nothing happens until Return or a click on `Search`.
3. Search for a title with a well-known remake — the exact-year match is not reliably
   first.

## Expected behavior

Typing searches on its own after a short pause, and results are ordered so the
obvious answer is at the top: exact title matches first, then by release year
descending.

## Actual behavior

Search only fires on `onSubmit` or the button (`:34`, `:36`). Results are displayed
in the order TMDB returned them, assigned straight through at
`Changeover/TMDB/MovieSearchViewModel.swift:28`.

## Plan

### Debounce (`Plan.md` 11.1)

In `Changeover/MetadataEntryView.swift`, add to the body's modifiers alongside the
existing `.onChange(of: selectedID)` (`:23-25`):

```swift
.onChange(of: vm.query) { _, _ in
    searchTask?.cancel()
    searchTask = Task {
        try? await Task.sleep(for: .milliseconds(350))
        guard !Task.isCancelled else { return }
        await vm.search(apiKey: settings.tmdbAPIKey)
    }
}
```

Reuse the existing `searchTask` `@State` (`:9`) rather than adding a second one, so
the explicit `Search` button and the debounce cancel each other correctly. Keep the
button and `onSubmit` working — `runSearch()` (`:137-140`) stays as it is and simply
becomes the zero-delay path.

Guard the empty query: `vm.search` sets `errorMessage` from
`TMDBError.emptyQuery` on a blank string, and firing that on every backspace to empty
would flash an error. Return early when the trimmed query is empty and clear
`vm.results` instead, matching the disabled condition the button already uses (`:37`).

Everything here runs on the main actor by default
(`SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`,
`Changeover.xcodeproj/project.pbxproj:416,445`) and `MovieSearchViewModel` is
explicitly `@MainActor @Observable`
(`Changeover/TMDB/MovieSearchViewModel.swift:4-6`), so no isolation annotations are
needed. `vm` is owned with `@State` (`Changeover/MetadataEntryView.swift:5`) per
`Plan.md`'s convention; do not change that to `@StateObject`.

One detail worth getting right: `vm.search` sets `selectedMovie = nil` on every call
(`MovieSearchViewModel.swift:23`). With debounce firing automatically, a stray
keystroke after the user has picked a poster would now silently clear the selection
and disable `Start Ripping` (`MetadataEntryView.swift:129`). Either skip the
auto-search once a movie is selected, or preserve the selection when the new results
still contain it.

### Sorting (`Plan.md` 11.7)

In `MovieSearchViewModel`, sort in `search(apiKey:)` before assigning `results`
(`:28`). Extract a `nonisolated static func sorted(_:for:) -> [TMDBMovie]` so it is
testable without the actor and without the client:

1. Exact title match against the trimmed query — case- and diacritic-insensitive,
   via `compare(_:options:[.caseInsensitive, .diacriticInsensitive])` — first.
2. Then prefix matches.
3. Then everything else.
4. Within each group, `yearText` descending, with `"—"` (no release date) sorting
   last.

Use a stable sort key so equal-ranked results keep TMDB's own relevance ordering
rather than being reshuffled arbitrarily — TMDB's default order is popularity-based
and is a reasonable tiebreaker, not noise to discard.
