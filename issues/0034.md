## Description

The metadata window and its `MovieSearchViewModel` live for the whole app session: `AppDelegate.showMetadataEntry()` reuses the window (`Changeover/AppDelegate.swift:96-100`), and `MetadataEntryView` owns `vm` and `selectedID` as `@State` (`Changeover/MetadataEntryView.swift:10-11`). A new disc insertion only sets `jobs.insertedDisc` and brings the window forward (`AppDelegate.swift:76-81`). Nothing clears the previous search results or selected movie. After disc A finishes and ejects, inserting disc B leaves movie A selected with Start enabled. Pressing Start encodes disc B into `Movies/A (Year) {tmdb-A}/A (Year).mp4`, and because `PlexOrganizer` replaces an existing file by design (#0012), it **overwrites the good copy of movie A in the Plex library**.

This was found by reading the code during the Phase 3 plan refresh (#0045) and has not been reproduced with discs. It fits the single-disc flow that exists today, so it is a live data-loss bug, not a Phase 3 concern.

## Resolution notes

> 🟢 Resolved 2026-09-15 — A selection is now bound to the disc it was chosen for, cleared when a different disc arrives, and `JobController.start` refuses any metadata that isn't bound to the disc in the drive.

Review (Opus) found two gaps in 48a7ba6 and fixed them in f62110a:

1. **Data loss was still reachable.** "Open…" opens the metadata window with no disc in the drive. A movie chosen there got `selectionDisc == nil`. `shouldReset` never fires for nil, and `start` skipped its check for nil. Select with no disc, insert A, Start, eject, insert B: Start filed B under A. Fix: `SelectionReset.reconcile` binds such a selection to the first disc inserted, and `start` now **refuses** metadata with no `selectionDisc` (fails closed). The optional default stays only for metadata that never reaches `start`. One test helper change covered the existing tests.
2. **Discs with no identity were locked out.** Without lsdvd, `DVDMonitor` uses the volume-name/UUID/size fallback, so most no-lsdvd users were fine. But with no volume name either, `discID` is nil, and "unknown is never a match" made `start` refuse every job, even on the disc the movie was chosen on. Fix: `DiscInsertion` carries a per-event `insertionID`. `sameDisc` matches a known identity or the same insertion event. Lookalike unidentified discs from different insertions still count as different. It also means `onChange(of: insertedDisc)` fires for every new insertion even if SwiftUI coalesces the removal while the window is closed.

The view also re-runs the decision when a job stops (`onChange(of: jobs.isRunning)`), so a swap that lands mid-job resets afterwards instead of leaving Start enabled on a selection `start` would refuse.

Checked and fine: the reset never touches `JobController` state; `resetForNewDisc` clears #0032's `runtimeLookup` (and cancels its task) through `select(movieID: nil)`; re-inserting the same disc keeps the selection; all mutation happens in `onChange` actions, not `body`; `SelectionReset` and `DiscInsertion` are `nonisolated`.

## Root cause

`AppDelegate.showMetadataEntry()` reuses the same `NSWindow` (and therefore
the same `MetadataEntryView` instance, `vm`, and `selectedID`) for the whole
app session. A new insertion only sets `jobs.insertedDisc` and brings the
window forward — nothing compared the disc the current selection was made
for against the disc now in the drive, so a stale selection from the
previous disc carried straight through to `Start`.

## Fix

Two layers, matching the `## Plan`:

1. **`SelectionReset.shouldReset(previousDisc:newDisc:isRunning:)`**
   (`Changeover/SelectionReset.swift`) is a pure, `nonisolated` decision
   function, free of SwiftUI/Observation, so it's testable with plain
   `DiscInsertion` values. It resets only when: no job is running, there was
   a prior selection, a new disc actually arrived, and that new disc is a
   *different* identity (`SelectionReset.sameDisc`, which mirrors
   `OpticalDiscClassifier`'s stance that an unresolvable/unknown `discID` on
   either side is never assumed to be a match). `MetadataEntryView` now
   tracks `selectionDisc` (the disc the current `selectedID`/`vm.selectedMovie`
   belong to) and, in a new `.onChange(of: jobs.insertedDisc)`, calls
   `vm.resetForNewDisc()` (clears query/results/error, and via
   `select(movieID: nil, ...)` also clears `selectedMovie` and #0032's
   `runtimeLookup` atomically) plus resets `selectedID`/`selectionDisc`
   whenever `shouldReset` says so.
2. **Defence in depth in `JobController.start`.** `MovieMetadata` gained an
   optional `selectionDisc: DiscInsertion?`, set by `MetadataEntryView` from
   the tracked `selectionDisc` when calling `jobs.start`. `start` refuses,
   logging a visible reason in the same shape as the existing re-entrancy
   and no-disc guards, when `metadata.selectionDisc` doesn't
   `SelectionReset.sameDisc` the current `insertedDisc`. This is the
   failsafe if the UI-level reset above somehow doesn't run.

   *Corrected in review (f62110a):* the draft let `nil` skip this check and
   treated an unknown `discID` as a mismatch. `start` now refuses `nil`,
   `sameDisc` also matches the same insertion event, and `reconcile` binds a
   selection made with no disc to the next disc inserted. See
   `## Resolution notes`.

Divergence from the plan: none of substance. The plan's example signature
(`SelectionReset.shouldReset(previousDisc:newDisc:isRunning:)`) is used
verbatim; `sameDisc` was added as a small second entry point since both the
view-level reset decision and the controller-level guard need the identical
"same disc?" test and it seemed wrong to duplicate it.

Kept small per the plan's request — no other change to `MetadataEntryView`'s
shape, leaving #0026's rework a clean base to build on.

## Steps to reproduce

1. Insert disc A, search, select movie A, Start. Let it finish and eject.
2. Insert disc B. The metadata window comes forward.
3. Observe: movie A is still selected and Start is enabled. Press Start.

## Expected behavior

A newly inserted disc (a different disc identity from the one the selection was made for) starts with no movie selected, and Start stays disabled until the user picks a movie for *this* disc. A job that is still running is never disturbed by the reset.

## Actual behavior

The previous disc's selection carries over. Start encodes the new disc under the previous movie's name and replaces that movie's library file.

## Plan

- Bind the selection to the disc it was made for. The simplest correct shape: `JobController` (or the view) records the disc identity (`DiscInsertion`'s identity, already debounced by #0013) the selection belongs to. On an insertion whose identity differs, and when no job is running, reset `MovieSearchViewModel` (query, results, `selectedMovie`) and `selectedID`. Put the "should reset?" decision behind a pure, unit-testable function (e.g. `SelectionReset.shouldReset(previousDisc:newDisc:isRunning:)`), so the rule is tested without UI.
- Defence in depth at the point of harm: `JobController.start(metadata:settings:)` refuses when the metadata was chosen for a different disc identity than `insertedDisc`. That makes the guard hold even if a UI path forgets the reset. Unit-test it through the existing `Runner` seam.
- Re-inserting the *same* disc (same identity) should keep the selection. That is a convenience, and harmless.
- Coordinate with #0026, which reshapes `MetadataEntryView` around the scan. Keep this fix small so #0026 builds on it.
- Verification: unit tests via `./run-remote-tests.sh gordon`. The UI reset itself is not UI-tested (policy). Record it as manually unverified unless it is checked in the app on joe.
