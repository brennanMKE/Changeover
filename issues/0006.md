## Description

The only completion signal is a line appended to a log view inside a window the user has usually closed and walked away from (`DVDPipeline.swift:61`). Nothing imports `UserNotifications` anywhere in `Changeover/`; `Plan.md` 11.5 is unchecked. On an `LSUIElement` app with no Dock icon, a finished job is genuinely invisible.

## Long Description

The UX flow sketched in `Plan.md` already ends with "Notification: 'Done — scan Plex'", and the Phase 1 demo in `Roadmap.md` ends with "a notification says it's done". It is the last step of the "insert a disc and walk away" loop — without it, the user has to keep coming back to the machine to see whether a 90-minute job finished, which defeats the purpose of [#0005](0005.md) as well.

The same mechanism has to carry failures. Today a job that failed at the rip stage prints `"✗ Ripping failed. Aborting."` (`DVDPipeline.swift:32`) into a log nobody is watching and then stops. The user finds out an hour later.

## Root cause

Nothing in the app ever imported `UserNotifications` or called
`UNUserNotificationCenter`. The only completion signal was the appended log
line inside `MetadataEntryView`'s window, which the user has typically
already closed by the time a 90-minute job finishes — on an `LSUIElement`
app with no Dock icon there was no other place to look.

## Fix

Followed the Plan as written, adapted for what has landed since it was
written (#0007's typed `JobOutcome`, #0009's `FailurePresenter`, #0005's
`DiscEjector`):

- **New `Changeover/JobNotifier.swift`**, a plain `enum` namespace (matching
  `EncodeController`/`PlexOrganizer`), matching the Plan's sketched shape
  with one addition:
  - `message(for metadata: MovieMetadata, outcome: JobOutcome) -> (title:
    String, body: String)` — the pure, unit-testable part. Success uses the
    raw `title`/`year` (not `folderName`'s `{tmdb-ID}` tag, which means
    nothing to a person reading a banner). Failure reuses
    `FailurePresenter.message(for:).headline` (#0009) so the banner shows
    the same actionable sentence the log already does, never a bare exit
    code or `String(describing: reason)`.
  - `requestAuthorizationIfNeeded()` / `notify(metadata:outcome:jobID:)` —
    thin wrappers over a new `JobNotificationPoster` protocol, rather than
    calling `UNUserNotificationCenter` directly. The real implementation
    (`UNNotificationCenterPoster`) wraps `requestAuthorization(options:)` and
    bridges the completion-handler-based `add(_:)` with a continuation.
    A denied/undetermined authorization degrades silently — `notify` never
    throws or blocks the pipeline.
  - Both entry points are gated on a new `isRunningUnderXCTest` check
    (`ProcessInfo.processInfo.environment["XCTestConfigurationFilePath"] !=
    nil`) so a test run can never trigger a real authorization prompt or a
    real notification, per the issue's own Notes and the hard rule in
    `CLAUDE.md`. To keep the forwarding logic itself testable despite that
    gate, the un-gated bodies are exposed separately as `authorize(poster:)`
    and `post(metadata:outcome:jobID:poster:)`; tests call those directly
    with a fake `JobNotificationPoster` and assert the gated entry points
    are no-ops under the very XCTest run exercising them.
- **`AppDelegate.swift`**: conforms to `UNUserNotificationCenterDelegate`,
  sets itself as the delegate and fires
  `Task { await JobNotifier.requestAuthorizationIfNeeded() }` in
  `applicationDidFinishLaunching`, alongside `registerLoginItem()` — not
  lazily at job completion, so the first-time permission prompt never
  appears the moment an unattended job ends.
  `userNotificationCenter(_:willPresent:)` returns `[.banner, .sound]` so
  the banner still shows while Changeover is frontmost;
  `userNotificationCenter(_:didReceive:)` calls `showMetadataEntry()` so
  clicking it opens the metadata window on the job's log (viable now that
  #0002 makes the log outlive the window).
- **`JobController.swift`**: `start(metadata:settings:)` now captures the
  job's `jobID` as a local `let` and, inside the same `Task` that already
  calls `finish(outcome)`, awaits
  `JobNotifier.notify(metadata:outcome:jobID:)` — on **both** outcomes,
  using the `metadata`/`jobID` values captured directly (not read back off
  `self`) so notification still fires even if whatever started the job has
  gone away, matching the existing "job keeps running after the starting
  scope goes away" guarantee (#0002).

**Deviation from the Plan:** the Plan says to fire the notification "From
`DVDPipeline` (or `JobController`) at the end of `run()`... after the eject
(#0005)". #0016 was concurrently editing `DVDPipeline.swift` in this same
session, so per this session's staging rules the hook was placed in
`JobController` instead, exactly as the Plan's parenthetical allows.
`DVDPipeline.run()` already performs the eject before returning its
`JobOutcome` on the success path, so "notify only after the eject" still
holds — `JobController` just reacts to the outcome `run()` already produced,
rather than sequencing the eject itself.

## Gotchas

- `UNUserNotificationCenter.add(_:)` has no `async throws` overload in the
  SDK used here — only `requestAuthorization(options:)` does. Bridged with
  `withCheckedContinuation`, swallowing the error deliberately (a failed
  notification must never fail a job).
- The XCTest gate check (`XCTestConfigurationFilePath`) is what actually
  keeps this whole feature safe to test at all — see the falsification note
  above about a concurrent session's sync clobbering the first attempt.
  Anyone re-running this falsification on a shared host like gordon should
  do the edit-and-run as tightly back-to-back as possible and verify the
  remote file still holds the mutation if the result comes back
  unexpectedly green.
- Notification *actions* ("Retry", "Open in Plex") were deliberately not
  added, per the Plan's own "Risks" section — clicking the banner just opens
  the metadata window on the job's log.

## Steps to reproduce

1. Insert a disc, start a rip, and close the Changeover window.
2. Wait for the job to finish (or fail).
3. Nothing appears — no banner, no badge, no sound, no menu bar change (the popover still reads `"Idle — insert a DVD to begin"`, `StatusMenuView.swift:18`).
4. The only way to learn the outcome is to reopen the window — which, today, also loses the log entirely ([#0002](0002.md)).

## Expected behavior

A user notification on every terminal outcome. Success: the movie title and confirmation the disc has been ejected. Failure: the actionable reason from [#0009](0009.md), not an exit code. Clicking the notification opens the metadata window with that job's log.

## Actual behavior

No notification is ever posted, and authorization has never been requested, so the app does not even appear in System Settings → Notifications.

## Notes

Delivery is manual to verify: run the app, complete a job (or a deliberately broken one), and confirm the banner appears with the app closed and with it frontmost. It does **not** require a physical disc — a stub `makemkvcon` script is enough to drive a job to a terminal state.

What should carry a real unit test is the **message construction**: a pure function from `(MovieMetadata, JobOutcome)` to `(title, body)`. Keep it separate from the `UNUserNotificationCenter` call precisely so it can be tested. Say in `## Verification` which part was automated and which was eyeballed.

## Plan

### New file: `Changeover/JobNotifier.swift`

```swift
enum JobNotifier {
    static func requestAuthorizationIfNeeded() async
    static func notify(metadata: MovieMetadata, outcome: JobOutcome) async
    nonisolated static func message(for metadata: MovieMetadata,
                                    outcome: JobOutcome) -> (title: String, body: String)
}
```

`message(for:outcome:)` is the pure, testable part — split it out deliberately. The rest is a thin wrapper over `UNUserNotificationCenter.current()`. A plain `enum` namespace matches how `RipController`, `EncodeController` and `PlexOrganizer` are already written; do not introduce an `actor` or an `@Observable` class for this.

### Authorization timing

Request authorization from `AppDelegate.applicationDidFinishLaunching` (`AppDelegate.swift:16-26`), not lazily at job completion. A first-time permission prompt that appears the moment a 90-minute job ends — when nobody is at the machine — is the worst possible time to ask. Fire it as a `Task` alongside `registerLoginItem()` (line 21).

### Foreground presentation

`UNUserNotificationCenter` suppresses banners while the app is frontmost unless the delegate says otherwise. Conform `AppDelegate` to `UNUserNotificationCenterDelegate`, set `UNUserNotificationCenter.current().delegate = self` during launch, and implement:

- `userNotificationCenter(_:willPresent:)` returning `[.banner, .sound]` so a notification shows even when Changeover happens to be active.
- `userNotificationCenter(_:didReceive:)` calling `showMetadataEntry()` (`AppDelegate.swift:69`) so clicking the banner opens the window on the job's log. This only works once [#0002](0002.md) has made the log outlive the window — otherwise the click opens an empty view.

### Where it fires

From `DVDPipeline` (or `JobController`) at the end of `run()`, on **both** outcomes, after the eject ([#0005](0005.md)). Do **not** put notification calls inside `RipController` or `EncodeController` — those are `nonisolated static` shell-out helpers and should stay free of app-level concerns.

### Risks

- **`LSUIElement` and notification delivery.** An accessory app with no Dock icon does receive user notifications, but it must be a properly bundled app with a stable bundle identifier (`co.sstools.Changeover`). Running an unsigned debug build from DerivedData is usually fine; if authorization silently fails, do not crash or block the pipeline — degrade to the log line that exists today.
- **Authorization can be denied or undecided.** `notify` must be a no-op in that case, not a `fatalError` or an unhandled throw. The job outcome does not depend on the notification succeeding.
- **`UNUserNotificationCenter.current()` traps when called from a non-bundled context** (e.g. a unit test host that is not the app). This is why `message(for:outcome:)` must be separately testable — do not write a test that touches the notification center.
- Resist adding notification *actions* ("Retry", "Open in Plex") in this ticket. That is a real design question and it is not what the Phase 1 demo needs.
