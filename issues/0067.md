# 0067 — There is no paired-peer registry, so peers cannot be limited to observing or revoked once trusted

| | |
|---|---|
| **Status** | open |
| **Phase** | 4 — Remote control from a Mac |
| **Module** | Pairing |
| **Platform** | macOS |
| **First seen** | 2026-09-11 |

## Description

`RemoteControl.md` calls for a per-peer capability field distinguishing "can start rips and write to the library" from "can watch progress only", but there is nowhere to put it: no record of who is paired, no Keychain-backed store, and no way to un-pair a device once it is trusted. Without this, pairing is permanent and every paired device is an administrator.

## Long Description

Pairing ([#0065](0065.md), [#0066](0066.md)) answers *which device*. This ticket
answers *what that device may do*, and *for how long*.

Both questions are load-bearing. The Phase 4 exit criterion in `Roadmap.md` says "an
unpaired device on the same network cannot control the host" — but it says nothing
about a device that **was** paired: a laptop that has been sold, a guest's iPad that
was paired once for a demo, a phone that was lost. With no registry there is no list
to show and nothing to remove, and the only revocation available is rotating the key
and re-pairing everything.

The capability distinction is worth more than it first looks. `RemoteEvent.log`
streams raw `makemkvcon` and `HandBrakeCLI` output — which includes absolute paths
under `AppSettings.plexMediaRoot` (`Changeover/AppSettings.swift:13`), working
directory layout, and MakeMKV registration and licence messages. An observe-only
peer is therefore not a zero-privilege peer; it learns the library layout. That is
an argument for the capability field being explicit rather than implied, and for the
log stream to be scrubbed rather than passed through verbatim.

`RemoteControl.md` also notes this matters more once montage editing lands
(`Montages.md`, Phase 7 / [#0120](0120.md)) — a second, broader write path into the
same repository. Building the capability field now, while there is exactly one
privileged command family, is far cheaper than retrofitting it when there are two.

## Steps to reproduce

1. Pair a device with the host.
2. Try to find a list of paired devices anywhere in the app.
3. Try to remove one, or to grant it watch-only access.

## Expected behavior

The host keeps a Keychain-backed registry of paired peers — stable ID, display name,
link key, capability, date paired, date last seen. Settings shows the list with a
capability control and a Remove button. Removing a peer takes effect immediately on
any live connection, not at next launch.

## Actual behavior

No registry exists. As designed in `RemoteControl.md`, a successfully paired peer
would have full control forever, with no record and no way to take it back.

## Plan

**The record.**

```swift
struct PairedPeer: Codable, Identifiable, Sendable {
    let id: UUID                 // stable peer identity, generated by the client
    var displayName: String      // "Brennan's MacBook Air"
    var capability: Capability   // .control | .observe
    let pairedAt: Date
    var lastSeenAt: Date?
    var pairingMode: PairingMode // .icloud | .pin — shown in the UI so the user knows how it got there
}

enum Capability: String, Codable, Sendable, CaseIterable {
    case control   // may startRip, cancel, eject, rescanDisc
    case observe   // may subscribe and ping only
}
```

`Capability` lives in the package from [#0061](0061.md) so the client can render a
correct UI for its own access level rather than offering buttons the host will
refuse. `PairedPeer` itself stays host-side.

**Storage.** Keychain, generic password class, one item per peer, service
`co.sstools.Changeover.peer` (matching `PRODUCT_BUNDLE_IDENTIFIER`,
`project.pbxproj:412`), account = peer UUID, value = JSON-encoded `PairedPeer` with
the link key held as a separate `kSecClassGenericPassword` item so the metadata can
be listed without pulling secrets into memory. Set
`kSecAttrAccessibleWhenUnlockedThisDeviceOnly` — the key must not ride a backup or
sync to another device. **Not `UserDefaults`**: `AppSettings.persist()` already
writes the TMDB key there in plaintext (`Changeover/AppSettings.swift:48-54`,
specifically `:53`), and that is a weakness not to propagate.

The app is unsandboxed (`project.pbxproj:402`), so Keychain access is to the login
keychain with no keychain-access-group entitlement needed — but it will produce an
authorization prompt if the app's signature changes, which it does on every
re-sign during development. Handle `errSecInteractionNotAllowed` and the user
clicking Deny as a real, reported state, not a silent empty registry: an empty
registry silently means "nobody is paired", which fails open into "nobody can
connect" (acceptable) but also makes debugging miserable.

**The store type.** `PeerRegistry`, a plain `@Observable final class` in the app
target, owned by `AppDelegate` next to `settings` (`Changeover/AppDelegate.swift:8`)
and injected with `.environment(...)` the same way settings already is
(`AppDelegate.swift:43`, `:87`). `@Observable` from `Observation`, never
`ObservableObject` — `Plan.md` is binding. It gets `@MainActor` from
`SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` (`project.pbxproj:416`), which is right:
it is read on every connection accept but those are infrequent, and making it an
`actor` would fight the observation story for the Settings list.

**Enforcement — the part that must not be skipped.** A capability field nobody
checks is worse than none, because it reads as protection. Enforcement lives in
[#0070](0070.md) but the API surface is defined here:

```swift
extension Capability {
    func permits(_ command: RemoteCommand) -> Bool
}
```

Write it as an exhaustive `switch` over `RemoteCommand` with **no `default` case**,
so adding a command to the protocol is a compile error until its authorization is
decided. That single detail is what keeps this from rotting the first time someone
adds `.setPlexRoot`.

**Revocation must be live.** `RemoteServer` ([#0068](0068.md)) holds a map from peer
ID to active connection. `PeerRegistry.remove(_:)` posts to that map and the server
closes the connection with `RejectionReason.revoked`. Revocation that only takes
effect at next launch is not revocation — the realistic case is "I need this device
off *now*".

**Also here: key rotation.** A single "Reset all pairings" action that generates a
new host key, clears the registry, and closes every connection. This is the recovery
path when something has gone wrong and the user does not know which peer to blame.
It is also what makes the Mode A generation counter from [#0065](0065.md) do
anything.

**UI.** A Paired Devices section in `SettingsView` below the existing credential
GroupBoxes (`Changeover/SettingsView.swift:36-60`): a `List` of peers with name,
capability `Picker`, last-seen date, and a Remove button, plus the Reset all
pairings action. The default capability for a newly paired peer is a product
decision — recommend `.control` for Mode A (same Apple ID, the user's own devices)
and `.control` for Mode B as well, since a household member who just typed a code at
the machine has demonstrated physical presence. Make the picker visible at pairing
time so downgrading is one click, rather than defaulting to `.observe` and having
every first pairing feel broken.

## Notes

**Fully unit-testable, no hardware:**

- `Capability.permits(_:)` for every `RemoteCommand` case, both capabilities — this
  is a small exhaustive table and it is the security boundary, so test all of it.
- `PairedPeer` encode/decode round trip.
- Registry add / list / remove / rotate against a **test keychain** created with
  `SecKeychainCreate` or, better, behind a `PeerStore` protocol with an in-memory
  implementation so tests never touch the developer's login keychain.
- That removing a peer while a connection is open produces a close with
  `.revoked` — testable against the `InMemoryTransport` from [#0062](0062.md).

**Requires two real machines:** that Keychain items survive a host restart and are
readable by the re-signed app, and that a revoked device really loses its live
connection rather than lingering until its next command.

**Gap worth flagging beyond this ticket:** the `RemoteEvent.log` stream is currently
specified as raw CLI output. Before Phase 4 ships, decide whether observe-only peers
receive it verbatim. At minimum, filter MakeMKV licence/registration lines out of
the fan-out — they are the most sensitive thing the log carries and they are also
noise. That work belongs in [#0069](0069.md), where the log buffer is built.
