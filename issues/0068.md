# 0068 — The host has no network surface, so JobController changes reach nothing outside the app

| | |
|---|---|
| **Status** | open |
| **Phase** | 4 — Remote control from a Mac |
| **Module** | RemoteServer |
| **Platform** | macOS |
| **First seen** | 2026-09-11 |

## Description

Nothing on the mini listens on the network. Phase 4 needs a `RemoteServer` that advertises `_changeover._tcp`, accepts authenticated connections, gates them on the peer registry, and fans every `JobController` change out to every connected client — while remaining the single serialization point so two clients cannot start two rips.

## Long Description

This is the ticket where the host stops being a single-process app. It sits on top
of four others: the protocol types ([#0061](0061.md)), the transport abstraction
([#0062](0062.md)), the verified advertisement API ([#0063](0063.md)), and the
authentication mechanism ([#0064](0064.md)) with its peer registry
([#0067](0067.md)).

The design constraint that shapes everything is stated in `RemoteControl.md`: **the
`JobController` is the serialization point**. `RemoteServer` must not hold job state
of its own. It translates commands into `JobController` calls and observes the
controller's state back out. Any state the server caches is state that can diverge,
and divergence between what the mini is doing and what the couch sees is the exact
failure this phase exists to prevent.

The fan-out mechanism deserves thought. `JobController` is `@Observable`
([#0001](0001.md)), which gives change notification through `withObservationTracking`
— but that API delivers *one* callback per registration and must be re-armed, and it
tells you a change happened, not what changed. For a log that appends many lines per
second during a rip, re-arming per line and re-serializing the whole state is
wasteful and will show up as main-thread churn on a machine that is simultaneously
running `makemkvcon` and `HandBrakeCLI`.

## Steps to reproduce

1. Start a rip on the mini.
2. From another machine, try to observe the job.

## Expected behavior

`RemoteServer` advertises on the LAN, authenticates and authorizes each connection,
and pushes `RemoteEvent.state`, `.discInfo`, `.log` and `.finished` to every
subscribed client as the `JobController` changes — with the host's own
`MetadataEntryView` behaving exactly as before.

## Actual behavior

There is no server. `JobController` does not exist yet either; today the pipeline's
state is `@State` inside a view (`Changeover/MetadataEntryView.swift:7-8`,
`:142-155`), which is precisely why `RemoteControl.md` calls the extraction the
prerequisite for any remote design.

## Plan

**Ownership.** `AppDelegate` owns `RemoteServer`, alongside `settings`
(`Changeover/AppDelegate.swift:8`) and the `JobController` that [#0001](0001.md)
adds. Start it in `applicationDidFinishLaunching`
(`Changeover/AppDelegate.swift:16-26`) — but **only once the host is configured and
has a host key**. Starting a listener before `settings.isConfigured`
(`Changeover/AppSettings.swift:33`) means advertising a host that cannot do anything,
and on first launch `AppDelegate` already opens Settings instead
(`AppDelegate.swift:23-25`). Gate on configured-and-paired, and restart the listener
when that becomes true rather than requiring a relaunch.

**Shape.**

```swift
final class RemoteServer {
    init(advertiser: TransportAdvertiser,
         jobController: JobController,
         registry: PeerRegistry,
         settings: AppSettings)
    func start() async
    func stop() async
    var connectedPeers: [PairedPeer] { get }   // @Observable, for the status UI
}
```

`TransportAdvertiser` is injected ([#0062](0062.md)) — the server must not import
`Network`. `connectedPeers` is what `StatusMenuView` renders
(`Changeover/StatusMenuView.swift:14-21` is where the status dot lives today; add a
"2 remotes connected" line beside it).

**Accept path, in order. Every step is a gate, and each failure is a distinct
`RejectionReason` from [#0061](0061.md), sent before closing:**

1. TLS handshake per [#0064](0064.md).
2. Wire version check — refuse with `.wireVersionMismatch` and the host's version so
   the client can tell the user to update rather than showing "connection failed".
3. Peer authentication — resolve the peer ID.
4. Registry lookup — unknown peer gets `.notPaired`. **This is the exit criterion
   "an unpaired device on the same network cannot control the host", and it is the
   one test that must never be skipped.**
5. Capability recorded on the connection for [#0070](0070.md) to consult per command.
6. `PeerRegistry` `lastSeenAt` updated.

Rate-limit steps 1–4 per source address so a hostile peer cannot spin the accept
path. Log rejections to the host's own log with the peer address — a silent
rejection is unreportable when a legitimate client will not connect.

**Fan-out.** Do not naively re-serialize full state per change. Instead:

- Give `JobController` an explicit `AsyncStream<JobEvent>` alongside its
  `@Observable` properties, published from the same mutation points. The
  `@Observable` surface serves SwiftUI; the stream serves the network. Two consumers
  with different needs, one source of truth. Coordinate this with [#0001](0001.md)
  so the stream is designed in rather than bolted on.
- `RemoteServer` consumes that stream once and pushes to all connections, rather
  than each connection observing the controller independently.
- Coalesce progress: `.ripping(progress)` and `.encoding(progress)` fire constantly.
  Throttle state pushes to ~4/second and always send the terminal state
  immediately and unthrottled. A dropped intermediate progress value is invisible; a
  dropped `.done` is a client stuck at 99%.
- Log lines are appended, not coalesced, but bound the per-connection send queue. If
  a client is slow, drop from the middle of its queue and send a
  `.log(jobID, "… <n> lines dropped …")` marker rather than growing without limit or
  blocking the rip. **A slow couch client must never be able to stall `makemkvcon`.**

**Isolation.** `RemoteServer` gets `@MainActor` from
`SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` (`project.pbxproj:416`), which is the
right default because it reads `JobController` and `PeerRegistry`, both MainActor.
Per-connection I/O state belongs in the `actor` inside the transport layer
([#0062](0062.md)), not here. Do **not** make `RemoteServer` an `actor` — `Plan.md`
is explicit that the `actor` keyword is not for types with no reason to leave
MainActor, and the connection handling that genuinely does is already encapsulated.
Follow the existing pattern for background→MainActor hops, e.g.
`RipController.swift:38` and `:51` (`Task { @MainActor in log(line) }`).

**Lifecycle.** `stop()` on `applicationWillTerminate`, closing connections cleanly so
clients distinguish "host quit" from "network dropped" — the former should not
trigger aggressive reconnect ([#0072](0072.md)).

**Ordering.** Last of the host-side infrastructure tickets. Can be scaffolded against
the `InMemoryTransport` before [#0063](0063.md) resolves.

### Plan refresh (2026-09-15)

**What is stale**

- **`JobController` exists.** It is `@Observable final class` at
  `JobController.swift:41`, owned by `AppDelegate` as `jobs` (`AppDelegate.swift:13`).
  The Actual behavior section's `MetadataEntryView.swift:7-8,:142-155` no longer
  applies.
- **The `AsyncStream<JobEvent>` fan-out was never added.** Don't add it now. The
  SDK's `Observations` (`Observation.swiftinterface`, `struct Observations`) gives a
  transaction-coalesced async sequence over `@Observable` reads, without touching
  `JobController`'s ~20 mutation points.
- **`RipController.swift:38/:51`** was deleted in #0014.
- **`AppDelegate` references:** `applicationDidFinishLaunching` is `:49-69`, the
  `isConfigured` → `showSettings()` check `:66-68`. There is no
  `applicationWillTerminate` yet; add one. The `StatusMenuView` status dot is
  `:16-19`.
- **"Queue" semantics are gone** under D1 (one job at a time). The second-Start
  arbitration is `JobController.start`'s own `isRunning` refusal.
- **Progress coalescing already partly exists.** `JobLog.latestProgress`
  (`JobLog.swift:73`) replaces itself rather than appending, and
  `JobState.progress` is always `nil` (no parser yet).
- **The accept path changes** under [#0064](0064.md): the TLS layer yields an
  authenticated `PeerIdentity`, the version check rides on `subscribe(ClientHello)`,
  and every refusal is a `RemoteEvent.commandResult(.refused)` from
  [#0061](0061.md).

**Replacement design** (app target, `Changeover/Remote/`, MainActor by default)

```swift
@Observable final class RemoteServer {
    init(listener: any TransportListener, jobs: JobController, registry: PeerRegistry,
         settings: AppSettings, identity: HostIdentityInfo /* hostID, name */,
         router: CommandRouter /* #0070 */, clock: any Clock<Duration> = ContinuousClock())
    private(set) var connections: [ConnectedPeer]       // StatusMenuView: "2 remotes connected"
    func start()                                        // spawns listener Task + fan-out Tasks
    func stop(reason: GoodbyeReason) async              // sends goodbye, closes all
    func disconnect(_ fingerprint: CertificateFingerprint, reason: RefusalCode)   // live revocation (#0067)
}
```

- **Per connection:**
  1. `registry.lookup(channel.peer)`. If nil, send `commandResult(.refused(notPaired))`
     to the first command, then `close`. No `HostState` is ever sent.
  2. Wait for `subscribe(ClientHello)`. On a version mismatch, refuse with
     `wireVersionMismatch(host:)` and close.
  3. Run [#0069](0069.md)'s handshake, then join the fan-out set with log cursors.
  4. Hand every later `CommandEnvelope` to `CommandRouter` ([#0070](0070.md)) and
     send its `commandResult`.

  The read loop is `for try await` over `channel.incoming` inside a
  `Task { @MainActor in … }`. Awaits suspend and nothing blocks the main thread.
- **State fan-out:** one `Task` iterating
  `Observations { HostStateProjector.make(jobs:, hostID:) }`.
  - `HostStateProjector` is pure. It maps `jobs.snapshots`, `current?.id`,
    `cancellingJobID`, `insertedDisc`, `isEjecting`, `discUnavailable` and
    `scanState` → `ScanStatus`.
  - Values are `Equatable`-deduped.
  - A trailing-edge throttle limits sends to at most 4/s on the injected clock,
    **except** that a value whose current job's phase turned terminal, or whose
    `scan` changed case, is sent immediately.
  - The payload stays small: ≤ `defaultHistoryLimit` 20 snapshots
    (`JobController.swift:123`) plus a `DiscInfo`.
- **Log fan-out:** `Observations` over a cheap `LogCursorKey`: current job id, the
  last `LogLine.id` of each source, `latestProgress?.id`, and the controller-log
  epoch.
  - The pure `LogFanout.delta(rows:since:)` turns `jobs.logDisplayRows`
    (`JobController.swift:180`) into `logAppend` batches of lines whose id is past
    the connection's cursor.
  - `latestProgress` goes out as `progress`, throttled to at most 4/s.
  - Each connection's `ChannelWriter`/`OutboundQueue` ([#0062](0062.md)) absorbs a
    slow client. **Nothing on MainActor ever awaits a slow socket**, so a stalled
    couch client cannot stall `JobController` or `HandBrakeCLI`.
- **Enablement and lifecycle:**
  - Start only when `settings.isConfigured` **and** a new
    `AppSettings.remoteControlEnabled` (default `false`) is on. That flag is set by
    [#0074](0074.md)'s explicit "Enable remote control" action, and starting then is
    what triggers the Local Network prompt while the user is looking.
  - Restart when either flag changes, without a relaunch.
  - `applicationWillTerminate` → `stop(reason: .hostQuitting)`.
- **`hostID`** is a UUID persisted in `UserDefaults`. It's not secret and is used
  only as a TXT hint and label.

**Isolation.** `RemoteServer`, `CommandRouter` and `PeerRegistry` are MainActor (no
`actor`). Socket I/O and queues live in `ChangeoverTransport`'s nonisolated types
and its `ChannelWriter` actor.

*Part A — implementable now over `InMemoryListener`.* Tests (`@MainActor`, in
`ChangeoverTests`, fake `Runner`/`ScanRunner`/`Ejector` from
`FakeRunnerSupport.swift`, injected clock):

- An unpaired peer is refused `notPaired` and receives no `HostState`.
- A version mismatch is refused with the host version.
- A subscribed client sees phase changes of a gated fake job, and the terminal
  state arrives immediately despite the throttle.
- 1,000 progress lines produce at most the throttle's worth of `progress` events.
- A stalled client gets the drop marker while a second client still receives

- `stop()` sends `goodbye` and closes all channels.
- `disconnect(…, .revoked)` closes only that peer.
- The existing `JobControllerTests` and `JobControllerHistoryTests` still pass
  unchanged (host UI regression guard).

## Notes

**Unit-testable against the in-memory transport, no network:** the whole accept-path
gate sequence including each rejection reason, that an unknown peer is refused,
progress coalescing (feed 1000 synthetic progress events, assert the number pushed),
the slow-client drop marker, and that `stop()` closes every connection.

**Requires two real machines:** that the service is discoverable from another Mac at
all, that the TLS handshake completes over the wire, and that log streaming keeps up
during a real `makemkvcon` rip. The last one cannot be simulated usefully — synthetic
log volume does not reproduce a real rip's burst pattern, and this is the scenario
where the "slow client stalls the rip" bug would actually appear. Verify with a real
disc and state plainly in `## Verification` that it was manual, per the caveat in
`issues/Issues.md`.

**Regression risk to watch:** `MetadataEntryView` must behave identically with the
server running. The host UI is the control case — if local ripping changes at all,
the fan-out is touching state it should only be reading.
