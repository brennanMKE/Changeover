# 0249 — `interrogate` reports films as unconfirmed that the feature match just named

| | |
|---|---|
| **Status** | resolved |
| **Phase** | 3 — Unattended multi-disc |
| **Module** | DiscFindings / DiscInterrogation / RipFlowController |
| **Platform** | macOS |
| **First seen** | 2026-10-11 |
| **Closed** | 2026-10-11 |

## Description

On both WILLIS discs, `flow.log` showed the feature match placing films and
then, about 8 seconds later, the interrogate pass reporting **every** one of
those names as unconfirmed:

```
feature match: feature 3 <- Sunset (id 38560)
feature match: feature 4 <- Hudson Hawk (id 9292)
...
interrogate unconfirmed: The menus suggest a film called "SUNSET" —
                         unconfirmed by the disc's runtimes
```

Two parts of the app appearing to disagree about one disc, in the same second.

## Root cause — and neither path was wrong

`DiscInterrogation.verify` binds claims to titles **by runtime**. A film claim
comes off a menu with **no runtime**, because menus print titles and not
lengths, so `timed` is empty and every film name returns unverified. That is
deliberate, and the function's own comment says so:

> A claim with no runtime cannot be checked this way and comes back unverified.
> That is correct and deliberate: the films question is answered by name alone,
> and names are bound to titles by TMDB runtimes in `FeatureMatching`, which
> knows things this does not.

So the logic was right. **The reporting was not.** The sentence read as a
verdict — "unconfirmed by the disc's runtimes" asserts the runtimes were
consulted and failed to confirm — when the runtimes were never consulted and
could not be. It was then printed after the question had already been answered
elsewhere.

## Fix

Two changes, both to what is said rather than what is decided:

1. **A film claim is not reported when every feature already has a film.** The
   question this path cannot answer has been answered by the path that can.
2. **The sentence says something true otherwise:** "unconfirmed here; a menu
   carries no runtime, so only a TMDB match can confirm a film's name." It keeps
   the word "unconfirmed", which #0171 requires reach the user, and drops the
   clause that blamed a check that never ran.

`unconfirmedDiscClaims` — what the window shows — applies the same suppression,
so the window and the flow log cannot say different things about one disc. That
divergence is the whole subject of this ticket and it would have been easy to
fix the log alone and recreate it one layer up.

Bonus and extra claims are untouched. Those **do** carry runtimes off the menu,
so "no title on this disc runs that long" is a real check that really failed.

## Why it mattered

Not cosmetic, for the same reason #0236 was not: this is agent-facing output
that reads as a finding. An agent seeing all three films reported unconfirmed
would reasonably doubt a correct assignment — and on this disc one of those
assignments was wrong (#0248), so a reader had no way to tell the real problem
from the noise.

## Relation

Found while looking for #0248's (E). Same family as #0246's two tolerances: two
parts of the app answering one question differently, except here the difference
was only in the telling.
