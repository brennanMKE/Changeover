# 0101 — Release build settings live in project.pbxproj and block the signing pipeline

| | |
|---|---|
| **Status** | open |
| **Module** | Release / Build |
| **Platform** | macOS |
| **First seen** | 2026-09-11 |

## Description

Every setting a release pipeline needs to own — `MARKETING_VERSION`, `CURRENT_PROJECT_VERSION`, signing, hardened runtime — is hardcoded in `Changeover.xcodeproj/project.pbxproj`, and the one `baseConfigurationReference` slot is occupied by a gitignored `Secrets.xcconfig` that no longer supplies anything. The `mac-release` preflight hard-fails on this project as it stands, so no release can be cut until the build configuration is restructured.

## Long Description

Four specific defects, all in `project.pbxproj`:

1. **`MARKETING_VERSION = 1.0` and `CURRENT_PROJECT_VERSION = 1` are set at
   target level** (`:401`, `:411` Debug; `:430`, `:440` Release). Per
   `mac-release` `references/versioning.md` ("One source of truth: the
   xcconfig"), a per-target value here *silently wins* over an xcconfig at build
   time — you bump the version, the build ignores it, and you ship the old one.
   `templates/preflight.sh` makes the mere presence of these lines a hard `[✗]`.

2. **`ENABLE_HARDENED_RUNTIME` is not set anywhere.** Notarization requires it
   (`templates/Build.xcconfig`, and `references/signing-notarization.md`, "The
   three requirements"). Xcode enables it by default for new macOS app targets,
   but it is not in the pbxproj, so it is not pinned and cannot be asserted by a
   preflight gate.

3. **`DEVELOPMENT_TEAM` is absent** — only `CODE_SIGN_STYLE = Automatic`
   (`:399`, `:428`). The release scripts read the Team ID from one place;
   there is currently no such place.

4. **`baseConfigurationReference = Secrets.xcconfig`** is wired to *both*
   project-level configurations (`:276` Debug, `:340` Release), and
   `Secrets.xcconfig` is gitignored (`.gitignore:4`). Two consequences: a fresh
   clone has no base configuration file at all, and there is no free slot for
   the `App.xcconfig` / `Build.xcconfig` the release pipeline wants to own.
   Worse, the file is now **dead weight** — commit `1c1e3d9` moved the TMDB key
   to `UserDefaults` (`Changeover/AppSettings.swift:16`, `:42`, `:53`) and
   removed `INFOPLIST_KEY_TMDB_API_KEY`, so nothing in the build reads
   `TMDB_API_KEY` any more. `grep -n INFOPLIST Changeover.xcodeproj/project.pbxproj`
   returns only `GENERATE_INFOPLIST_FILE`, `INFOPLIST_FILE` and
   `INFOPLIST_KEY_LSUIElement`.

One thing is already right: `INFOPLIST_FILE = Changeover/Info.plist` is set
(`:405`, `:434`) and the file exists (`Changeover/Info.plist`) — currently an
empty `<dict/>`. `references/versioning.md` ("Info.plist wiring") and
`references/sparkle.md` both require an explicit plist rather than a purely
synthesized one, so the hook is in place; it just has no keys in it.

## Steps to reproduce

1. `grep -n 'MARKETING_VERSION\|CURRENT_PROJECT_VERSION' Changeover.xcodeproj/project.pbxproj`
2. `grep -n 'ENABLE_HARDENED_RUNTIME\|DEVELOPMENT_TEAM' Changeover.xcodeproj/project.pbxproj`
3. `git stash list` a clean clone: `git clone` the repo into a fresh directory and open it in Xcode without creating `Secrets.xcconfig`.

## Expected behavior

Step 1 prints nothing (both values live in `App.xcconfig`). Step 2 shows
`ENABLE_HARDENED_RUNTIME = YES` and a real `DEVELOPMENT_TEAM`, both from
`Build.xcconfig`. A fresh clone opens and builds in Xcode with no missing-file
warning, because the committed xcconfigs are the base configuration.

## Actual behavior

Step 1 prints eight lines (four targets × two settings). Step 2 prints nothing.
A fresh clone points its base configuration at a file that is not in the repo.

## Plan

Order matters; do these in sequence.

**1. Settle the Sparkle question first.** [#0110](0110.md) decides whether v1
ships auto-updates. If yes, `App.xcconfig` needs `SU_FEED_URL` /
`SU_PUBLIC_ED_KEY` and `Info.plist` needs the matching `$(…)` references; if no,
both are omitted and added later. Doing this after the xcconfig lands means
touching it twice, which is fine but wasteful — so take the decision first.

**2. Create the xcconfigs.** Copy `templates/Build.xcconfig` and
`templates/App.xcconfig` from `/Users/brennan/.claude/skills/mac-release/` into a
new `Configuration/` folder at the repo root (not into `Changeover/` — that
directory is a `PBXFileSystemSynchronizedRootGroup`, so anything dropped in it is
auto-added to the compile sources phase). Adapt, preserving the templates'
comments — they encode real failures:

- `Build.xcconfig`: set `MACOSX_DEPLOYMENT_TARGET = 26.2` (matching
  `project.pbxproj:328`, `:386`), `SWIFT_VERSION = 5.0` (matching `:417`, `:446`
  — do **not** silently bump it to 6.0 as the template does; that is a separate
  change with its own risk), `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`,
  `SWIFT_APPROACHABLE_CONCURRENCY = YES`, `ENABLE_APP_SANDBOX = NO` (keep the
  template's comment explaining why, and add that Changeover's reason is the
  `makemkvcon` / `HandBrakeCLI` shell-outs), `ENABLE_HARDENED_RUNTIME = YES`,
  `CODE_SIGN_STYLE = Automatic`, `DEVELOPMENT_TEAM = <the real Team ID>`.
- `App.xcconfig`: `PRODUCT_BUNDLE_IDENTIFIER = co.sstools.Changeover`,
  `PRODUCT_NAME = Changeover`, `MARKETING_VERSION = 1.0.0` (note: SemVer, three
  components — the current `1.0` is not), `CURRENT_PROJECT_VERSION = 1`,
  `INFOPLIST_FILE = Changeover/Info.plist`,
  `ASSETCATALOG_COMPILER_APPICON_NAME[sdk=macos*] = AppIcon`.

**3. Decide what happens to `Secrets.xcconfig`.** Recommended: **retire it.** It
feeds nothing since `1c1e3d9`; keeping it costs a base-configuration slot and
perpetuates the README instructions that [#0108](0108.md) has to delete. That
means removing the `baseConfigurationReference` at `project.pbxproj:276` and
`:340` and pointing both at `Build.xcconfig` instead, deleting
`Changeover/Secrets.xcconfig.example`, and removing the `Secrets.xcconfig` line
from `.gitignore:4`. Leave `Changeover/Secrets.xcconfig` itself on disk untouched
and uncommitted — it is the user's file, it contains a real API key, and deleting
someone's secrets file is not this ticket's business. If instead the file must be
kept for some reason not visible in the repo, the alternative is
`#include? "Secrets.xcconfig"` from `Build.xcconfig` (the `?` makes it optional,
as `templates/App.xcconfig` does with `Active.xcconfig`) — but say so explicitly
in the ticket resolution, because it changes [#0108](0108.md)'s README text.

**4. Wire the configs into the project.** Set `baseConfigurationReference` for
project-level Debug and Release to `Build.xcconfig`, and for the **Changeover
target's** Debug and Release (`:396`-ish and `:425`-ish blocks) to
`App.xcconfig`, which should `#include "Build.xcconfig"`. Leave the
`ChangeoverTests` and `ChangeoverUITests` targets alone apart from deleting their
version lines (`:457`, `:460`, `:477`, `:480`, `:496`, `:498`, `:514`, `:516`) —
test bundles do not need release identity, but the preflight grep does not
distinguish targets, so those lines must go too.

**5. Delete the pbxproj overrides.** Remove `MARKETING_VERSION` and
`CURRENT_PROJECT_VERSION` from all four targets. In Xcode: target → Build
Settings → search the setting → if bold, delete it so it falls through. Then
confirm with the grep in step 1 of "Steps to reproduce" that it prints nothing.

**6. Populate `Changeover/Info.plist`.** It is currently an empty `<dict/>`. Add:

```xml
<key>CFBundleShortVersionString</key>
<string>$(MARKETING_VERSION)</string>
<key>CFBundleVersion</key>
<string>$(CURRENT_PROJECT_VERSION)</string>
```

Do **not** move `LSUIElement` out of `INFOPLIST_KEY_LSUIElement`
(`project.pbxproj:406`, `:435`) — `GENERATE_INFOPLIST_FILE = YES` merges the
synthesized keys with the explicit file, and moving it risks losing the menu-bar
behavior for no benefit. Verify after the build that both forms survived:
`/usr/libexec/PlistBuddy -c 'Print :LSUIElement' <built app>/Contents/Info.plist`.

**Risks.** (a) Editing `project.pbxproj` by hand is error-prone; make the
`baseConfigurationReference` changes in Xcode's UI where possible and diff the
result. (b) `SWIFT_VERSION = 5.0` with `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`
is the current working combination — changing either while restructuring the
configs would make a build break ambiguous. (c) If `DEVELOPMENT_TEAM` is
committed to a public repo, that is a deliberate choice (Team IDs are not secret,
but they are identifying); note the decision rather than making it silently.

## Notes

**Verification is mechanical and cheap for this ticket.**

```bash
# 1. The preflight's hard gate — must print nothing.
grep -n 'MARKETING_VERSION\|CURRENT_PROJECT_VERSION' Changeover.xcodeproj/project.pbxproj

# 2. The build still succeeds.
xcodebuild -project Changeover.xcodeproj -scheme Changeover -destination 'platform=macOS' build

# 3. The built bundle carries the versions the xcconfig declares.
APP=$(xcodebuild -project Changeover.xcodeproj -scheme Changeover -showBuildSettings \
      | awk -F' = ' '/ BUILT_PRODUCTS_DIR/{d=$2} / FULL_PRODUCT_NAME/{n=$2} END{print d"/"n}')
/usr/libexec/PlistBuddy -c 'Print :CFBundleShortVersionString' "$APP/Contents/Info.plist"  # 1.0.0
/usr/libexec/PlistBuddy -c 'Print :CFBundleVersion'            "$APP/Contents/Info.plist"  # 1
/usr/libexec/PlistBuddy -c 'Print :LSUIElement'                "$APP/Contents/Info.plist"  # true

# 4. Hardened runtime is actually on in the built binary.
codesign -d --entitlements - --verbose=2 "$APP" 2>&1 | head -20
codesign -dvvv "$APP" 2>&1 | grep -i 'flags='   # expect runtime

# 5. A fresh clone builds with no base-configuration warning.
git clone . /tmp/changeover-clean && \
  xcodebuild -project /tmp/changeover-clean/Changeover.xcodeproj -scheme Changeover \
             -destination 'platform=macOS' build 2>&1 | grep -i 'unable to open\|could not find'
```

Step 5 is the one that proves the `Secrets.xcconfig` decision actually worked;
run it from a directory the working copy does not shadow. Note that the clone
will not carry the gitignored `Secrets.xcconfig`, which is exactly the condition
being tested.

Also re-run the app once after the change and confirm the menu bar icon appears
and no Dock icon does — that is the cheapest proof `LSUIElement` survived the
`Info.plist` edit.
