# 0102 — There is no signed, notarized, stapled DMG for Changeover

| | |
|---|---|
| **Status** | open |
| **Phase** | 6 — Ship to other people |
| **Module** | Release |
| **Platform** | macOS |
| **First seen** | 2026-09-11 |

## Description

Changeover has never been signed with a Developer ID, never submitted to Apple's notary service, and has no distributable artifact of any kind. The documented install path is "build it in Xcode yourself, then run `xattr -cr`" (`README.md:74-79`, `Plan.md:301-306`) — which only works for someone with the repo, and teaches the user to disable the exact protection notarization exists to satisfy.

## Long Description

The sandbox is off (`Changeover.xcodeproj/project.pbxproj:402`, `:431`) because
`RipController` (`Changeover/RipController.swift:17-24`) and `EncodeController`
(`Changeover/EncodeController.swift:18-28`) launch `Process` against
user-specified binaries. That permanently rules out the Mac App Store, so direct
Developer ID distribution is not a preference — it is the only remaining option,
and the bar for getting it right is correspondingly higher.

The user has a paid Apple Developer account (`RemoteControl.md:84-85`), so every
prerequisite is available: a Developer ID Application certificate, and an App
Store Connect API key for `notarytool`.

This ticket adopts the `mac-release` skill's pipeline rather than writing a new
one. That skill exists precisely for this and ships seven parameterized script
templates plus reference docs distilled from a shipping app.

## Steps to reproduce

1. Build Changeover in Xcode and export/copy the `.app`.
2. Copy it to another Mac by any means that sets the quarantine attribute
   (AirDrop, a download, a mounted DMG).
3. Double-click it.

## Expected behavior

The app launches. `spctl -a -vvv` reports `accepted` with
`source=Notarized Developer ID`, and `xattr -p com.apple.quarantine` on the
installed bundle is irrelevant because the stapled ticket satisfies Gatekeeper
offline.

## Actual behavior

Gatekeeper refuses to open it ("unidentified developer" / "damaged"), and the
documented workaround is `xattr -cr /Applications/Changeover.app`
(`README.md:79`). There is no DMG to distribute in the first place.

## Plan

**Prerequisite: [#0101](0101.md) must land first.** `templates/preflight.sh`
hard-fails on any `MARKETING_VERSION =` / `CURRENT_PROJECT_VERSION =` line in
`project.pbxproj`, and there are currently eight of them. Do not start here.

Work directly from `/Users/brennan/.claude/skills/mac-release/`. The skill's
"Adapting the templates to an app" section is the procedure; do not restate it
here, follow it. Concretely, for this project:

**1. One-time account setup.** Follow `references/signing-notarization.md` —
"The Developer ID Application certificate" and "The notary keychain profile".
Use `templates/setup-notary.sh` to create the `notarytool` keychain profile from
an App Store Connect API key. **Do not touch the keychain, certificates, or
provisioning profiles from an agent session** — this step is the user's, run
interactively, per the skill's own safety note and `xcode-build`'s rules.

**2. Install tooling.** `brew install create-dmg fileicon` per the skill's
Prerequisites. `notarytool` / `stapler` / `spctl` / `xmllint` come with Xcode's
command-line tools.

**3. Copy and parameterize the scripts** into a new `scripts/` directory at the
repo root: `preflight.sh`, `release.sh`, `verify-dmg.sh`, `tag-release.sh`, and
`setup-notary.sh`. Edit only the `CONFIG` block at the top of each — app name
`Changeover`, scheme `Changeover`, project `Changeover.xcodeproj` (not a
workspace), bundle id `co.sstools.Changeover`, the Team ID and signing identity
from `Build.xcconfig`, the notary profile name, and the xcconfig path from
[#0101](0101.md). `chmod +x` all of them. **Preserve the templates' comments** —
the skill states they encode real failures (why the DMG name must equal the
volname, why the build dir is torn down, the same-day build-number trap).

**4. Delete the gates that do not apply and add the ones that do.** The
templates assume Sparkle; if [#0110](0110.md) defers it, strip the Sparkle key
gate, the appcast-consistency gate and the bump-vs-appcast gate from
`preflight.sh`, and do not copy `appcast-item.sh`, `deploy-website.sh` or
`appcast.xml`. Add Changeover-specific gates while you are in there — at
minimum, assert `ENABLE_APP_SANDBOX = NO` and `ENABLE_HARDENED_RUNTIME = YES`
survived the [#0101](0101.md) restructure, and assert `LSUIElement` is present in
the built `Info.plist` (a menu-bar app that ships with a Dock icon is a visible
regression and the synthesized-plist merge is exactly where that would break).

**5. Run preflight, then release.** `./scripts/preflight.sh` is read-only and
safe to run from a session. **`./scripts/release.sh` submits to Apple's notary
service — hand that run to the user**, per the skill's "Safety — do not notarize
or publish autonomously from an agent session." Output is
`dist/Changeover-<sha>.dmg`.

**6. Write `RELEASE.md`.** Copy `templates/RELEASE.md` to the repo root (or
`docs/`) and fill in the Changeover specifics. This is the checklist the next
release follows; without it the pipeline is one person's shell history.

**Risks.**

- **Hardened runtime vs. `Process` launches.** Changeover shells out to
  arbitrary user-specified binaries. Hardened runtime does not block spawning a
  child process, but it does block loading unsigned libraries *into Changeover's
  own address space* — which the app does not do. No entitlement should be
  needed. If notarization or runtime behavior says otherwise, the answer is a
  targeted entitlement, not turning hardened runtime off; turning it off makes
  notarization impossible.
- **`SMAppService` login-item registration** (`Changeover/AppDelegate.swift:127`)
  behaves differently for a signed app in `/Applications` than for a debug build
  run from DerivedData. That interaction is [#0107](0107.md)'s problem, but it
  will first be *observed* here — note anything you see and hand it to that
  ticket rather than fixing it inline.
- **Notarization rejections are opaque.** `references/signing-notarization.md`,
  "Reading notarization failures", covers pulling the JSON log from
  `notarytool log`. Read it before guessing.

## Notes

**This is the most verifiable ticket in Phase 6 — verify it properly.**

After `release.sh` produces a DMG, `templates/verify-dmg.sh` is the primary
check; it validates signing, notarization and stapling and simulates the
recipient's download-quarantine. Run it, and independently confirm:

```bash
# Signature is valid, sealed, and from a Developer ID.
codesign -vvv --deep --strict /Volumes/Changeover/Changeover.app
codesign -dvvv /Volumes/Changeover/Changeover.app 2>&1 | grep -i 'Authority\|flags='
#   expect: Authority=Developer ID Application: <name> (<TeamID>)
#   expect: flags=0x10000(runtime)

# Gatekeeper accepts it as notarized — this is the exit-criteria line.
spctl -a -vvv -t exec /Volumes/Changeover/Changeover.app
#   expect: accepted / source=Notarized Developer ID

# The ticket is stapled, so it works with no network.
xcrun stapler validate /Volumes/Changeover/Changeover.app
xcrun stapler validate dist/Changeover-*.dmg

# Simulate what a downloader gets.
xattr -w com.apple.quarantine "0081;00000000;Safari;" dist/Changeover-*.dmg
hdiutil attach dist/Changeover-*.dmg
```

**A green `verify-dmg.sh` on the build machine is not the whole story** — the
build machine has the signing certificate in its keychain, which can mask
problems. The clean-machine half of verification is [#0103](0103.md); do not
close this ticket on local verification alone.

`issues/Issues.md` ("Build / verify command for this project") notes that a green
`xcodebuild` is not verification for anything in the rip path. That caveat cuts
the other way here: this ticket's verification is *entirely* tooling-based and
genuinely provable, but it proves nothing about whether the app then works.
