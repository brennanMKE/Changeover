# 0081 — Remote client is a macOS-only target and must be restructured as multiplatform

| | |
|---|---|
| **Status** | open |
| **Module** | RemoteClient / Project |
| **Platform** | All |
| **First seen** | 2026-09-11 |

## Description

The `Changeover Remote` target from Phase 4 builds for macOS only, and the
project has no iOS destination at all. Before any iPhone or iPad work can start,
the client has to become a genuinely multiplatform target with shared sources in
a place both destinations can reach.

## Long Description

`Changeover.xcodeproj` is a single-platform project today:
`SDKROOT = macosx` and `MACOSX_DEPLOYMENT_TARGET = 26.2` at both project-level
build configurations (`Changeover.xcodeproj/project.pbxproj:328`, `:332`,
`:386`, `:389`), and the app target sets `INFOPLIST_KEY_LSUIElement = YES`
(`:406`, `:435`) and `ENABLE_APP_SANDBOX = NO` (`:402`, `:431`) — three settings
that are either meaningless or actively wrong on iOS.

The project uses `PBXFileSystemSynchronizedRootGroup`
(`Changeover.xcodeproj/project.pbxproj:33–49`, `objectVersion = 77` at `:6`), so
a source file's target membership follows the folder it lives in. That is
convenient for the existing single target and a trap for a multiplatform one: a
file dropped into `Changeover/` is compiled into the host app whether or not it
should be. Deciding where shared client code lives is therefore a structural
decision, not a checkbox.

The pieces that genuinely want to be shared between the host app, the macOS
client and the iOS client are `MovieSearchViewModel`
(`Changeover/TMDB/MovieSearchViewModel.swift:4–41`), `TMDBClient`
(`Changeover/TMDB/TMDBClient.swift:3–48`), `TMDBModels`, `MovieMetadata`
(`Changeover/MovieMetadata.swift:5–25`) and the search/poster UI out of
`MetadataEntryView`. All of those are already platform-neutral in substance —
`TMDBClient` is pure Foundation and `URLSession`, `MovieSearchViewModel` is a
plain `@MainActor @Observable` class — so the obstacle is packaging, not logic.

## Steps to reproduce

1. Open `Changeover.xcodeproj`.
2. Select the `Changeover Remote` scheme.
3. Open the destination picker.

## Expected behavior

The destination picker lists My Mac, iPhone simulators and devices, and iPad
simulators and devices. Building for each produces a working client app, and the
TMDB search stack is compiled from one copy of the source, not duplicated.

## Actual behavior

Only macOS destinations are offered. There is no iOS target, no iOS deployment
target, and no shared package — the TMDB sources live inside `Changeover/`, a
`PBXFileSystemSynchronizedRootGroup` bound to the macOS host app.

## Notes

`ENABLE_APP_SANDBOX = NO` exists on the host because it shells out to
`makemkvcon` and `HandBrakeCLI`. The client shells out to nothing, so it should
be sandboxed on macOS and will be sandboxed by definition on iOS. Do not copy
that setting forward.

The host app should keep `LSUIElement = YES`; the iOS client obviously cannot be
a menu bar app, and the macOS client's own window-vs-popover decision is Phase 4's
call, not this ticket's.

Verification here is honest and cheap: this is the one Phase 5 ticket that a
build machine can fully prove. `xcodebuild -showdestinations` plus a successful
build for each destination is the whole test. No device required.

## Plan

### 1. Decide the sharing mechanism — one SPM package, not folder membership

Add a local Swift package `ChangeoverUI` alongside the existing
`ChangeoverProtocol` package from Phase 4, and move these files into it:

- `Changeover/TMDB/TMDBClient.swift` — moves unchanged; it is pure Foundation
  (`:3–48`) and already has a `nonisolated init` (`:6`).
- `Changeover/TMDB/TMDBModels.swift` — moves unchanged.
- `Changeover/TMDB/MovieSearchViewModel.swift` — moves unchanged; `@MainActor
  @Observable final class` (`:4–6`) is correct on every platform. Keep the
  explicit `@MainActor` even though the package will set MainActor default
  isolation, because an explicit annotation survives a package-settings mistake.
- `Changeover/MovieMetadata.swift` — check first whether Phase 4 already moved
  this into `ChangeoverProtocol`; `RemoteControl.md` lists `MovieMetadata` among
  the shared protocol models. If it is already there, leave it there and have
  `ChangeoverUI` depend on `ChangeoverProtocol` rather than duplicating it.
- The search UI extracted from `Changeover/MetadataEntryView.swift` — see
  [#0082](0082.md) and [#0083](0083.md) for what that extraction looks like. This
  ticket only needs to create the destination, not perform the extraction.

A package is the right mechanism specifically **because** of
`PBXFileSystemSynchronizedRootGroup` (`project.pbxproj:33–49`): folder-synced
groups make per-file target membership fragile, and a package makes the sharing
boundary explicit and enforced by the compiler.

### 2. Package build settings must match the app's conventions

In `Package.swift` for `ChangeoverUI`, set `swiftSettings` to enable MainActor
default isolation so the package matches `SWIFT_DEFAULT_ACTOR_ISOLATION =
MainActor` on the app target (`project.pbxproj:416`, `:445`). If the package and
the app disagree on default isolation, every type crossing the boundary needs
annotations that the rest of the codebase does not use, and `Plan.md`'s
convention table stops describing reality. Platforms: `.macOS(.v26)`,
`.iOS(.v26)`. Do the same for `ChangeoverProtocol` if Phase 4 did not.

### 3. Make the client target multiplatform

Set the `Changeover Remote` target's `SUPPORTED_PLATFORMS` to
`macosx iphoneos iphonesimulator`, add `TARGETED_DEVICE_FAMILY = "1,2"` (iPhone
and iPad from one target — the iPad layout in [#0085](0085.md) is a size-class
adaptation, not a second target), and add `IPHONEOS_DEPLOYMENT_TARGET = 26.0`
next to the existing `MACOSX_DEPLOYMENT_TARGET = 26.2`.

Settings that must **not** be carried over from the host app target:

- `INFOPLIST_KEY_LSUIElement` (`project.pbxproj:406`, `:435`) — macOS-only.
- `ENABLE_APP_SANDBOX = NO` (`:402`, `:431`) — the client has no reason to
  disable the sandbox. Leave it enabled on macOS.

`GENERATE_INFOPLIST_FILE = YES` stays; per `Plan.md` there is no separate
Info.plist file in this project, so every Info.plist key is an
`INFOPLIST_KEY_*` build setting. The client needs at minimum:

- `INFOPLIST_KEY_NSLocalNetworkUsageDescription` and the `NSBonjourServices`
  array — see [#0089](0089.md), which owns the wording and the denial path.
- `INFOPLIST_KEY_UILaunchScreen_Generation = YES` for iOS.
- `INFOPLIST_KEY_UISupportedInterfaceOrientations` — portrait plus both
  landscapes for iPad; see [#0085](0085.md).

Bundle identifiers: `co.sstools.Changeover.Remote` for both platforms keeps
pairing records and Keychain access groups coherent across the two clients.

### 4. Stage the cutover so `main` never has a broken build

Land this ticket with the iOS destination present and the shared views **not yet**
in the iOS target — a minimal iOS entry point (`App` + a placeholder view that
shows the connection state from Phase 4's client object) is enough. That keeps
this ticket independently verifiable. [#0082](0082.md) then brings the real views
in, one file at a time, with a green build at each step.

### 5. Risks

- **The folder-synced group fights back.** Moving `Changeover/TMDB/` out from
  under a `PBXFileSystemSynchronizedRootGroup` may require an explicit membership
  exception rather than a plain file move. Verify the host app still compiles
  after the move before touching anything else.
- **Two `MovieMetadata` definitions.** If Phase 4 put it in `ChangeoverProtocol`
  and this ticket also puts it in `ChangeoverUI`, everything compiles and the
  types are silently incompatible across the wire. Check first.
- **Default-isolation mismatch** between package and app produces a wall of
  confusing `@MainActor`-inference errors. Set it before moving files, not after.

### 6. Verification

```
xcodebuild -project Changeover.xcodeproj -scheme 'Changeover Remote' -showdestinations
xcodebuild -project Changeover.xcodeproj -scheme 'Changeover Remote' -destination 'platform=macOS' build
xcodebuild -project Changeover.xcodeproj -scheme 'Changeover Remote' -destination 'generic/platform=iOS' build
xcodebuild -project Changeover.xcodeproj -scheme Changeover -destination 'platform=macOS' build
xcodebuild -project Changeover.xcodeproj -scheme Changeover -destination 'platform=macOS' test
```

The last two matter as much as the first three: moving the TMDB sources into a
package must not break the host app. Any existing `TMDBClient` /
`MovieMetadata` unit tests must still run and pass after the move — if the test
target loses sight of them, that is a real regression, not a bookkeeping detail.
