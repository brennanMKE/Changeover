## Description

Umbrella for **Phase 1 — Trustworthy single-disc rip**. The pipeline works once, on a clean machine, with the window open — but it can silently encode the wrong file on the second disc, it never cleans up after itself, it cannot eject, and it reports every failure as an exit code. This phase makes the core loop correct and self-closing before anything is built on top of it.

## Long Description

Phase 1 comes first because of the roadmap's first ordering rule: **correctness before capability**. Every later phase — title selection (Phase 2), a multi-disc queue (Phase 3), remote control (Phase 4) — either sits on top of the rip path or puts its state on the wire. Building a remote client that faithfully streams the progress of a job that produced the wrong movie is worse than not building it.

Two of the children are also structural prerequisites for later phases and are worth doing now even though they ship no user-visible behavior on their own:

- [#0002](0002.md) moves job state out of `MetadataEntryView` into an `@Observable JobController` owned by `AppDelegate`. Phase 3's queue and Phase 4's fan-out both need a job that exists outside a window.
- [#0007](0007.md) gives the pipeline a typed outcome instead of log text. Phase 4's `JobState` goes on the wire; getting the shape right here is far cheaper than reshaping it across a protocol package later.

## Demo

> Insert a DVD. Search the title, pick the poster, hit Start. Walk away. The rip runs, the encode runs, the file appears in the Plex library under the correct `Title (Year) {tmdb-ID}` folder, the disc ejects, and a notification says it's done. **Then do it a second time with a different disc** — and show that the second movie is also correct, which is the part that is broken today.

## Steps to reproduce

1. Rip disc A end to end. Confirm it lands in the Plex Movies folder.
2. Look in `<plexMediaRoot>/Working/ripping` — disc A's multi-gigabyte `.mkv` is still there.
3. Insert disc B (a shorter film than A). Search, select, Start Ripping.
4. When disc B's rip finishes, `RipController` picks the **largest** `.mkv` in that shared folder — disc A's file.
5. The Plex library now contains `B (Year) {tmdb-B}/B (Year).mp4` whose contents are movie A.

## Expected behavior

Two different discs ripped back to back both produce the correct output; the working folder is empty after each job; closing the metadata window mid-job does not orphan or duplicate the job; and every failure mode names the actual problem.

## Actual behavior

The second disc can be encoded from the first disc's leftover file ([#0003](0003.md)), the working folder grows forever ([#0004](0004.md)), the disc stays in the drive ([#0005](0005.md)), nothing tells you the job finished unless the window is open ([#0006](0006.md)), and the only failure signal is `"✗ makemkvcon exited with status 1"` ([#0009](0009.md)).

## Exit criteria

Taken verbatim from `Roadmap.md`:

- Two different discs ripped consecutively both produce correct output.
- Working folder is empty after each job.
- Killing the metadata window mid-job does not kill the job.
- Every failure mode above produces a message that names the actual problem.

## Notes

This ticket ships no code. It closes when all eight children are resolved and the two-disc demo above has been run on the mini with real discs.

Per the build/verify caveat in `issues/Issues.md`: a green `xcodebuild` proves nothing about the rip path. The parts of Phase 1 that *can* carry real unit tests are the working-directory derivation ([#0003](0003.md)), the cleanup sweep predicate ([#0004](0004.md)), the outcome types and error mapping ([#0007](0007.md)), the preflight checks ([#0008](0008.md)) and the failure classifier ([#0009](0009.md)). Eject ([#0005](0005.md)) and notification delivery ([#0006](0006.md)) are manual-only. Every child's `## Verification` must say which it was.

Swift conventions apply throughout (`Plan.md` "Swift conventions"): `@Observable` and never `ObservableObject`; view models owned with `@State`; `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` so nothing needs `@MainActor` and nothing should become an `actor` without a reason; `nonisolated` only where a type genuinely must leave the main actor, as `RipController`, `EncodeController` and `PlexOrganizer` already do.

## Plan

Sequencing matters here; the children are not independent in time even though each is independently verifiable.

1. **[#0007](0007.md) — typed outcome** first. It is the smallest change with the widest blast radius, and [#0004](0004.md), [#0005](0005.md), [#0006](0006.md) and [#0009](0009.md) all need a value that says "this job succeeded" rather than inferring it from reaching the end of `DVDPipeline.run()`.
2. **[#0002](0002.md) — `JobController`** next. It gives every subsequent ticket one place to hang job state, and it is the one refactor that touches `AppDelegate`, so doing it before the feature work avoids rebasing the feature work onto it.
3. **[#0003](0003.md) — per-job working directories**. The correctness fix the phase is named for. Depends on nothing but is cleaner once the job has an id from [#0002](0002.md).
4. **[#0004](0004.md) — cleanup**, which deletes the directories [#0003](0003.md) creates, on the success signal [#0007](0007.md) provides.
5. **[#0009](0009.md) — failure classification**, then **[#0008](0008.md) — preflight**. Both produce `FailureReason` values from [#0007](0007.md); preflight is second because it reuses the same reasons for "checked before" as the classifier produces for "discovered during".
6. **[#0005](0005.md) — eject** and **[#0006](0006.md) — notification** last. They are the visible payoff of the demo and they read the outcome everything else has been building. Their ordering inside `DVDPipeline` is fixed: move → cleanup → eject → notify, so the notification is the last thing that happens and genuinely means "the disc is out, swap it".

The main risk in the phase is **scope creep into Phase 2**. Several of these tickets brush against title selection — the empty-rip-directory case in [#0003](0003.md), the free-space threshold in [#0008](0008.md), the classifier in [#0009](0009.md) — and all three get better once `DiscScanner` exists. Resist: Phase 1 keeps ripping `all` titles. The only requirement is that the result is correct and the failure is legible.

The second risk is **calling the phase done on a single disc**. The defect this phase exists to kill only shows up on the second disc. The exit criteria are not met until two different discs have gone through consecutively on the mini.
