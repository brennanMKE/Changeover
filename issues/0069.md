# 0069 — A client that attaches mid-job has no way to catch up on state, disc info or log history

| | |
|---|---|
| **Status** | open |
| **Phase** | 4 — Remote control from a Mac |
| **Module** | RemoteServer / ChangeoverProtocol |
| **Platform** | All |
| **First seen** | 2026-09-11 |

## Description

A client that connects while a rip is already running would see only the events that happen after it attached — no current state, no disc title list, no log backlog, an empty window on a busy machine. The `subscribe` → `state` + `discInfo` + `logReplay` handshake is what makes both first connection and every reconnect identical, and it needs a bounded log ring buffer on the host to feed it.

## Long Description

`RemoteControl.md` names this as the mechanism that makes recovery clean: "clients
must survive host restarts, Wi-Fi drops, and laptop sleep. The `subscribe` →
`state` + `discInfo` + `logReplay` handshake makes recovery clean." The important
property is that **there is no separate reconnect path** — reconnecting is just
subscribing again. That is what keeps [#0072](0072.md) from becoming a second state
machine, and it only works if the handshake is genuinely complete: after it, a
freshly attached client and a client that has been attached for an hour must be
indistinguishable.

The host has no log buffer today. Log lines are accumulated in view state
(`Changeover/MetadataEntryView.swift:8`, appended at `:150`) and thrown away when
the window closes — which is also one of the defects [#0001](0001.md) fixes. The
buffer needs to be a capped ring on `JobController`, per job, because
[#0040](0040.md) introduces a queue and the demo explicitly involves three discs.

The demo for this phase ends with "quit and relaunch the client to show it
reconnects and re-syncs mid-job" — so this handshake is not infrastructure, it is
the closing beat of the demo.

## Steps to reproduce

1. Start a rip.
2. Two minutes in, launch the remote client for the first time.

## Expected behavior

The client shows the running job with its correct stage and progress, the disc's
scanned title list, and the log scrolled to the most recent lines — within a second
of connecting, without having been present when any of it happened.

## Actual behavior

No handshake exists. With a naive event-push server, the client would show an idle,
empty UI while the host is visibly mid-rip, which is worse than showing nothing
because it looks like a working connection to an idle host.

## Plan

**Host-side buffer.** Add to `JobController` ([#0001](0001.md)) a per-job capped log
ring:

```swift
struct LogRing {
    private(set) var lines: [String]
    private(set) var droppedCount: Int
    let capacity: Int          // 2000 lines
    mutating func append(_ line: String)
}
```

2000 lines is a few hundred KB and comfortably covers a full rip's interesting
output. When it wraps, `droppedCount` increments and `logReplay` carries a synthetic
leading line — `"… <n> earlier lines not retained …"` — so the client never silently
misrepresents the log as complete. The host's own `MetadataEntryView` should read
from this same ring rather than keeping its own `@State` array, so there is one log,
not two that can disagree.

**The handshake, in order.** On `RemoteCommand.subscribe`, after the accept gates in
[#0068](0068.md) pass, the server sends, on one connection, in this sequence:

1. `.state([JobState])` — the full queue, not just the current job. `RemoteControl.md`
   open question 1 asks whether a queue is needed; [#0040](0040.md) answers yes, so
   the handshake carries an array from the start.
2. `.discInfo(DiscInfo)` — only if a disc is present and scanned. If a scan is in
   flight, the state from step 1 must already be `.scanning`, because
   `makemkvcon info` on a DVD takes tens of seconds and the client must show a
   scanning state, not an empty title list. This is called out as a risk in
   `RemoteControl.md` and it is the single most likely thing to look like a bug.
3. `.logReplay(jobID, [String])` per active or recently finished job.
4. Live events from then on.

**Ordering must be guaranteed, not incidental.** Send all four from one place, in one
`Task`, before the connection joins the fan-out set — otherwise a live `.log` can
interleave ahead of the replay and the client's log ends up out of order. The
simplest correct implementation: buffer live events for that connection while the
handshake is being written, then flush. Say so in a comment; it reads as unnecessary
until the first time it is wrong.

**Idempotence.** `subscribe` must be safe to send repeatedly on a live connection —
that is how a client recovers from its own confusion without tearing down TLS. A
second `subscribe` re-sends the full handshake and the client replaces rather than
merges its state.

**Wire version.** The client sends its `WireVersion` with `subscribe`; the host
either proceeds or rejects with `.wireVersionMismatch` ([#0068](0068.md) step 2). If
[#0063](0063.md) finds TXT records are reachable, also publish the version there so a
mismatched client can be filtered before it connects; if not, this is the only place
it is checked.

**Scrub the log on the way out.** Per the concern raised in [#0067](0067.md), filter
MakeMKV licence and registration lines out of `.log` and `.logReplay` before they
leave the host. They are the most sensitive thing the stream carries and they are
noise to the client. Do the filtering at the fan-out boundary in `RemoteServer`, not
at the ring, so the host's own log view keeps the full text for troubleshooting — the
MakeMKV key expiry case in `RemoteControl.md` is a recurring real-world issue and the
local operator needs to see it verbatim.

**Client side.** `RemoteSession` ([#0071](0071.md)) applies `.state` as a wholesale
replacement, never a merge. Merging is how a reconnected client ends up displaying a
job that finished while it was asleep.

**Size.** A replay of 2000 lines as JSON is comfortably inside the 256 KiB frame
limit from [#0061](0061.md) only if lines are short; `makemkvcon` progress lines are.
Chunk `logReplay` into several messages of ~200 lines rather than one large frame, so
the limit is never the thing that breaks a reconnect.

### Plan refresh (2026-09-15)

**What is stale**

- **`LogRing` is superseded by `JobLog`** (#0043, `Jobs/JobLog.swift:46`). It
  provides:
  - A per-job cap of 2,000 (`defaultCapacity`).
  - `milestones` never evicted by that cap.
  - `latestProgress` coalesced (`:73`).
  - `droppedCount` (`:80`).
  - `LogLine` with a monotonic per-log `id` (`:13`).
  - `displayLines` merge (`:159`).
  - `snapshot(limit:) -> [String]` (`:148`). **Don't use it for the wire;** it drops
    ids, timestamps and milestone flags.

  The host UI already reads one log via `JobController.logDisplayRows`
  (`JobController.swift:180`), so "one log, not two" is done. The `MetadataEntryView`
  references (`:8`, `:150`) are stale.
- **`.state([JobState])` becomes `hostState(HostState)`**, carrying
  `JobController.snapshots` (history then current, oldest first; #0042 handoff).
- **The separate `.discInfo` event folds into `HostState.scan`**
  (`ScanStatus.scanned(disc:…)`), so scan status and title list can never disagree.
  "Scan in flight" is `ScanStatus.scanning`, not a job state.
- **`logReplay(jobID, [String])` becomes chunked `logReplay(LogChunk)`** with
  `[LogLine]`, `droppedCount` and `latestProgress` (#0043 handoff).
- **"Per active or recently finished job" becomes "the current job, or the last
  finished one, plus the controller log".** That's exactly what the host's own log
  pane shows (`logDisplayRows`). Older history logs come on demand via
  `fetchLog(JobID)` → `JobController.retainedLog(forJobID:)` (`:372`).
- **MakeMKV is fallback-only now** (#0014/#0015). The licence and registration
  scrub still applies whenever `makemkvcon` output reaches the log.

**Replacement plan**

- **The ordering guarantee comes from cursors, not buffering.** On `subscribe`,
  inside **one synchronous MainActor section** (no `await` between reads), capture:
  - `SessionInfo`
  - `HostState`
  - for each replay source, its `displayLines`, `droppedCount` and `latestProgress`
  - the last `LogLine.id` per source, as the connection's cursor

  Enqueue `session`, `hostState`, then the replay chunks (the last one has
  `isLast: true`) onto that connection's `OutboundQueue`, and mark the connection
  live with those cursors. Live deltas carry only ids past the cursor. Because ids
  are monotonic and the capture is atomic on MainActor, there can be no gap, no
  duplicate and no interleaving. That makes "buffer live events during the
  handshake" unnecessary; replace that paragraph's mechanism with this.
- **Controller-log epoch.** `JobController.start` replaces `controllerLog` with a
  fresh `JobLog`, whose ids restart at 0. Add a tiny `controllerLogEpoch: Int`
  counter to `JobController`, incremented wherever `controllerLog` is replaced.
  Key the wire source as `.controller(epoch:)`. A client seeing a new epoch replaces
  that store. This is a one-line host change plus a test.
- **Chunking.**
  - At most `ProtocolLimits.maxLogLinesPerChunk` (200) lines per chunk.
  - Lines longer than `maxLogLineBytes` (4 KiB) are truncated host-side with a `…`
    suffix.
  - A test proves the worst case (200 × 4 KiB, JSON-escaped) stays under
    `maxFrameBytes`. If it doesn't, lower the chunk size, not the frame limit.
- **Idempotent resubscribe** re-runs the whole capture. The client replaces its
  state rather than merging.
- **Scrubbing** happens at the fan-out boundary (`LogScrubber.scrub(_:)`, pure).
  - It drops MakeMKV registration/key lines for all peers.
  - For `.observe` peers it also applies [#0067](0067.md)'s path redaction.
  - The host's `JobLog` keeps the verbatim text.
- **Wire version** is checked on `subscribe(ClientHello)`, per [#0068](0068.md). The
  TXT `v=` hint from [#0063](0063.md) is only a pre-filter.

**Pure seams** (app target unless noted):

- `HandshakeBuilder.make(session:state:sources:chunkSize:) -> [RemoteEvent]`
- `LogCursor` / `LogFanout.delta`
- `LogScrubber`
- `HostStateProjector` (shared with [#0068](0068.md))
- `LogChunk` / `LogSource` (in `ChangeoverProtocol`)

**Tests** (in `ChangeoverTests` via `./run-remote-tests.sh gordon`, `@MainActor`,
`InMemoryTransport`, fake runners; no disc):

- Handshake content and order for each host situation: idle with no disc, disc
  scanning, scanned, mid-encode (gated fake runner), just finished (current `nil`,
  history non-empty), scan failed.
- Lines appended right after the capture arrive as `logAppend` with ids strictly
  greater than the cursor, with no duplicates.
- A second `subscribe` yields an identical handshake.
- The controller epoch bumps when a job starts, and the client-facing source
  changes.
- Worst-case chunk size stays under `maxFrameBytes` via `ProtocolCodec`.
- The scrubber removes key lines on the wire while `JobLog` retains them, and the
  observe peer's paths are redacted.

mid-encode) and the SIGKILL variant.

## Notes

**Fully unit-testable against the `InMemoryTransport` from [#0062](0062.md) — no
network, no disc, no second machine.** This is the ticket where that fake pays for
itself:

- `LogRing` wrap behaviour and `droppedCount` arithmetic.
- Handshake message order for: idle host, disc inserted but unscanned, scan in
  flight, mid-rip, mid-encode, just-finished.
- That a live log line produced *during* the handshake arrives after the replay, not
  interleaved into it.
- That a second `subscribe` produces a complete, identical handshake.
- That licence/registration lines are absent from fanned-out events and present in
  the host's own ring.
- That `logReplay` chunking never produces a frame over `ProtocolLimits.maxFrameSize`.

**Requires two real machines:** the demo beat itself — quit the client mid-rip,
relaunch, confirm it lands on the right stage with the right log tail. Also worth
doing the ugly version: kill the client with `SIGKILL` rather than quitting cleanly,
so the host sees an abrupt drop rather than a graceful close.
