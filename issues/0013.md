## Description

`DVDMonitor.volumeMounted` accepts any `NSWorkspace.didMountNotification` whose volume contains a `VIDEO_TS` directory (`DVDMonitor.swift:23-24`) and immediately opens the metadata window (`AppDelegate.swift:67-72`). A NAS share, a mounted DMG of a disc image, a USB drive holding an old backup, or the same disc remounting after a hiccup are all indistinguishable from a freshly inserted DVD. There is no disc identity and no debounce, so nothing can tell "a new disc" from "the disc that is already in the drive".

> 🟢 Resolved 2026-09-12 — Re-pass `6b84e91` reviewed independently: the unit suite (`-only-testing:ChangeoverTests`, never bare `test`) run seven times (76 tests; 80–81 on the three runs that carried a temporary reviewer probe, since deleted), all passing with no crash report and no leaked `ChangeoverTestDVD*` volume, and both must-fixes falsified by hand — restoring read-after-wait in `LSDVDIdentity.discID` fails `aLargeOutputStillParsesWellWithinTheTimeout` (`discID → nil` at 5.0016 s, the timeout exactly), and moving the `isGenuineOpticalMedia` guard after the closures in `evaluateAppearance` fails exactly `nonOpticalMediaNeverTriggersVideoTSStatOrDiscIDResolution` and `opticalMediaWithoutVideoTSNeverResolvesDiscID` (3 issues) and nothing else.
>
> **Gate ordering is real, not a parallel copy:** `DVDMonitor.diskAppeared` has a single classification path, `OpticalDiscClassifier.evaluateAppearance` (`DVDMonitor.swift:153`); the only other `classify(` caller is `evaluateAppearance` itself.
>
> **Drain implementation (`LSDVDIdentity.discID`)** — correct. `readabilityHandler` is cleared on all three exits (EOF branch, `run()` failure, after the wait); empty `availableData` is treated as EOF; a genuinely hung child is killed at the timeout (reviewer probe: `nil` after 1.003 s with `timeout: 1.0`, script gone afterwards); a non-zero exit returns `nil`. One theoretical gap, recorded for hardening rather than fixed: the handler is nil'd right after `waitUntilExit()` returns without a final drain, so under dispatch thread-pool starvation the last chunk could in principle be unread when the source is cancelled. Not observed: 0 wrong/`nil` results in 600 serial and 1,240 eight-way-concurrent probe calls, including a stub whose closing `"}` is the final tiny write before exit; and in every diagnosed timeout case below the accumulator already held the full output with EOF seen. If hardened later: leave the EOF branch to signal a second `DispatchGroup` and wait on it (bounded by the timeout) before reading the accumulator, rather than cancelling the source from the caller.
>
> **Pre-existing, shape-independent, note only:** under heavy concurrent spawning (8 threads × 2,400 calls) `Process.waitUntilExit()` occasionally never returns even though the child has exited and been reaped (`isRunning == false`, `kill(pid, 0) == ESRCH`) — 86 cases with the old read-after-wait shape vs 42 with the new drain per 2,400 calls; 0 in 900 serial calls. Production calls `discID` serially on the DA queue, so this is not reachable there. When it does fire, the timeout branch calls `terminate()` on an already-reaped pid and leaves a utility-queue thread parked in `waitUntilExit()` — worth a `process.isRunning` guard if `discID` is ever called concurrently.
>
> **Follow-ups (approved with these recorded; fold into the next ticket that touches these files, e.g. #0005):**
> 1. `OutputAccumulator` (`LSDVDIdentity.swift:26`) is MainActor-isolated by the project default yet is constructed and used from the nonisolated `discID` and the `@Sendable` `readabilityHandler` — the compiler reports three warnings (lines 91, 104, 127: "call to main actor-isolated initializer/instance method in a synchronous nonisolated context", "main actor-isolated property 'data' can not be referenced from a nonisolated context"). Safe today (NSLock-guarded, Swift 5 mode inserts no hop), but it is the same pattern the bounce had `Box` fixed for and it breaks CLAUDE.md's "anything they touch must also be `nonisolated`". One keyword: `private nonisolated final class OutputAccumulator`.
> 2. `Box` justification, wording only. The false "no session-invalidate call" claim was corrected as required and the ordered-release alternative is now acknowledged — but the replacement sentence ("no way to release `Box` … without either racing that in-flight callback or blocking to wait for it"; `## Gotchas` #2: "no non-blocking way to wait for it from `deinit`") is itself false and is contradicted by its own next sentence: `DASessionSetDispatchQueue(session, nil)` cancels the session's dispatch source so no further handler invocation is submitted, and a subsequent `queue.async { release }` on the serial queue runs strictly after any handler already executing — non-blocking, no race, and no self-deadlock even when `deinit` runs on `queue`. The accurate justification is the one the re-pass also gives: not adopted this pass because it changes the teardown shape and warrants the stress test, and the leak is bounded (one `Box` per app lifetime). `deinit`'s own comment (`DVDMonitor.swift:121-123`) also still says "`DiskArbitration` has no separate 'invalidate' entry point in this SDK". The `Box` itself stands as judged in the bounce: correct and bounded.
>

The debug-only Thread Performance Checker warning noted in `## Gotchas` #4 appears in the review's own logs and is cosmetic.

## Root cause

`DVDMonitor` had exactly one signal — "does a `VIDEO_TS` folder exist at this
mounted volume's root" — and no notion of disc identity or removal. Any
mounted volume satisfying that one check (a DMG, a NAS share, the same disc
remounting) was treated identically to a freshly inserted DVD.

## Fix

Replaced the `NSWorkspace.didMountNotification`/`didUnmountNotification`
observer with a `DiskArbitration` session (`DASessionCreate` +
`DASessionSetDispatchQueue`, `DARegisterDiskAppearedCallback` /
`DARegisterDiskDescriptionChangedCallback` / `DARegisterDiskDisappearedCallback`).

- **`Changeover/DiscInsertion.swift`** (new) — `DiscInsertion` (mount URL,
  BSD device node, disc id), `DiscMountDecision`, and `OpticalDiscClassifier`:
  pure, `nonisolated`, `DiskArbitration`-free decision logic. A mount is only
  accepted when `kDADiskDescriptionMediaKindKey` names a real optical media
  class (`IODVDMedia`/`IOCDMedia`/`IOBDMedia` — verified on hardware in this
  issue's Notes) *and* `kDADiskDescriptionDeviceProtocolKey` isn't `"Disk
  Image"` *and* `VIDEO_TS` exists at the mount root. Identity comes from
  `LSDVDIdentity` (below) or `OpticalDiscClassifier.fallbackDiscID` (volume
  name + UUID + size); an unresolvable identity is always treated as a new
  disc rather than silently suppressed (Plan's "Risks": a false negative is
  worse than an occasional false positive).
- **`Changeover/LSDVDIdentity.swift`** (new) — optional `lsdvd -x -Oj`
  enrichment for a stable `dvddiscid`. Not on the critical path: a missing
  binary (checked at two Homebrew paths) returns `nil` immediately without
  launching anything, and a hung/misbehaving process is time-boxed at 3s.
- **`Changeover/DVDMonitor.swift`** — rewritten around the `DiskArbitration`
  session. `onDVDInserted` widened from `(URL) -> Void` to
  `(DiscInsertion) -> Void`; new `onDVDRemoved: (() -> Void)?`, satisfying
  #0001's phase review assignment of unmount observation to this issue
  (struck from #0005's plan there). The callback methods are `nonisolated`
  per `CLAUDE.md`'s concurrency rules, matching the discipline the old
  `@objc nonisolated volumeMounted` used.
- **`Changeover/JobController.swift`** — `insertedDiscURL: URL?` widened to
  `insertedDisc: DiscInsertion?`.
- **`Changeover/AppDelegate.swift`** — `startDVDMonitor()` wires
  `onDVDRemoved` to clear `jobs.insertedDisc`, alongside the existing
  `onDVDInserted` wiring (now passing the richer value).

**Two real `DiskArbitration` bugs found and fixed via the DMG integration
test (not guessed):**

1. `description[kDADiskDescriptionVolumeUUIDKey] as? CFUUID` is flagged by
   the compiler as "conditional downcast ... will always succeed" — and it
   really does always succeed at runtime regardless of the value's actual
   type, which crashed the monitor the first time a real disk-appeared event
   ran. Fixed with a `CFGetTypeID` check before an `unsafeBitCast`.
2. The C callback context was `Unmanaged.passUnretained(self)` (then, after
   the first fix, an unretained bridging `Box`) — dangling the instant the
   owner's last strong reference went away while a callback was still in
   flight on the monitor's own dispatch queue. Reproduced twice as real
   crashes (`abort()` inside a Swift runtime `fatalError`, then
   `EXC_BAD_ACCESS`/`SIGBUS` in `swift_weakLoadStrong`) and once as a
   self-deadlock (an attempted `queue.sync` teardown in `deinit` blocking on
   the very queue already executing). Final shape: a small `Box` holding
   `weak var monitor: DVDMonitor?`, itself deliberately retained forever via
   `Unmanaged.passRetained` — cycle-free since the reference back is weak, so
   a late callback reads a zeroed weak reference and no-ops instead of
   touching freed memory. (**Corrected below** — the original justification
   here, that this SDK's `DiskArbitration` has no session-invalidate call,
   was false and was bounced by phase 3 review; see "Re-pass" below for the
   real reason `Box` stays immortal.)

**Deliberately not done**, per scope: no eject (#0005), no notifications
(#0006), no queueing or "already ripped" lookup (#0040).

### Re-pass (commit `6b84e91`, against the phase 3 bounce of `06354f3`)

Phase 3 found two defects and three smaller issues (see `## Review notes`
below, unchanged from the bounce). Fixed:

1. **`LSDVDIdentity.discID` pipe deadlock ("must fix" #1).** The previous
   shape called `outputPipe.fileHandleForReading.readDataToEndOfFile()` only
   *after* `waitUntilExit()` returned. A pipe's kernel buffer is only
   ~64KB; once `lsdvd -x -Oj` (cells/audio/subtitle tables for every title —
   realistically well over 64KB on a real feature disc) fills it, the child
   blocks in `write`, `waitUntilExit()` never returns, and the function
   returns `nil` after every single `timeout` — silently degrading the
   stable `dvddiscid` this issue exists to deliver into the weak fallback
   identity, with a 3s stall per disk event. Fixed by draining stdout
   **concurrently** with the child running: a `readabilityHandler` on the
   pipe's read end appends each chunk into a lock-protected
   `OutputAccumulator`, registered before `process.run()` so nothing is
   missed. The timeout/wait logic is otherwise unchanged (`DispatchGroup` +
   `group.wait`, `process.terminate()` on timeout). This is the same
   discipline `EncodeController.encode` already uses for `HandBrakeCLI`.
2. **`diskAppeared` did expensive work before its own media-kind gate
   ("must fix" #2).** It used to stat `VIDEO_TS` and resolve disc identity
   (spawning `lsdvd`) unconditionally, for *every* disk-appeared/
   description-changed event on the system, before `classify` ever looked at
   `mediaKind`/`protocolName`. Added
   `OpticalDiscClassifier.evaluateAppearance(mediaKind:protocolName:
   previousDiscID:resolveVideoTS:resolveDiscID:)`, which checks
   `isGenuineOpticalMedia` *first* and only calls the `resolveVideoTS`/
   `resolveDiscID` closures once that passes; `classify(...)`'s own
   signature is untouched, so every test built directly on it still stands.
   `DVDMonitor.diskAppeared` was reordered to read only the cheap
   `mediaKind`/`protocolName`/`mountURL`/`deviceNode` up front and pass the
   rest as closures.
3. **DMG integration test cleanup ordering ("should fix").** `attachVideoTSImage`
   was split into `attachImage(name:)` (create + attach only) and
   `addVideoTSFolder(at:)`. The test now registers `defer { detachAndDelete
   ... }` immediately after `attachImage` succeeds, before calling
   `addVideoTSFolder`, so a throw from `createDirectory` can no longer leak a
   mounted, undetached image.
4. **`Box` marked `nonisolated` ("should fix").** It compiled clean under
   `SWIFT_VERSION = 5.0` either way, but the class is read from
   `@convention(c)` callbacks that run off the main actor, so the annotation
   now makes that explicit per `CLAUDE.md`'s concurrency rules.
5. **Corrected the `Box` justification ("must fix" #3).** The claim in the
   code comment (and copied into `## Fix` above and `## Gotchas` below) that
   "this SDK's `DiskArbitration` has no session-invalidate call" is false —
   `DAUnregisterCallback(session, callback, context)` exists
   (`DiskArbitration.h:552`). The real reason `Box` stays immortal is
   different: a callback can already be *executing* on `queue` at the
   moment `deinit` runs, and there is no way to release `Box` — with or
   without first unregistering — from `deinit` without either racing that
   in-flight callback or blocking to wait for it, and blocking is exactly
   the self-deadlock this issue hit once already (a `queue.sync` teardown
   attempt, reverted — `## Gotchas` #2). A leak-free alternative does exist
   (`DASessionSetDispatchQueue(session, nil)`, which guarantees no *new*
   callback block is ever enqueued, followed by releasing `Box` inside a
   `queue.async` block, which — because `queue` is serial — is guaranteed to
   run only after every already-enqueued callback has finished) but was
   **not adopted** in this pass: it changes the teardown shape enough to
   warrant the same kind of dedicated stress test (hundreds of
   create-and-drop cycles under load) that found both crashes in the first
   pass, which is out of scope for this re-pass. Per phase 3's own judgement,
   the immortal `Box` is "correct and bounded" as-is, so it was kept
   unchanged; only the comment (`Changeover/DVDMonitor.swift`), this
   section, and `## Gotchas` were corrected.

Not touched: `EncodeController`, `DVDPipeline`, eject (#0005), notifications
(#0006), #0015's fallback ripper, encoder settings (#0018) — all out of
scope per the re-pass assignment.

## Gotchas

The `DiskArbitration` C-callback lifetime turned into the hardest part of
this issue, and it was only found because the DMG integration test exercises
the *real* session rather than a mock:

1. `as? CFUUID` off an `Any` "always succeeds" per the compiler's own
   diagnostic, and that's not just a false-positive warning — it really does
   always succeed at runtime, which crashed the monitor. Any future `Any` →
   CF-type cast in this file should use the `CFGetTypeID` + `unsafeBitCast`
   pattern here, not `as?`/`as!`.
2. A raw `Unmanaged.passUnretained(self)` (or, one iteration later, an
   unretained bridging `Box`) context is unsafe for any C API that can
   deliver a callback after the Swift side's last strong reference is
   dropped. This surfaced as two different crashes and a self-inflicted
   deadlock (a `queue.sync` teardown attempt in `deinit`, reverted) before
   landing on the weak-`Box`-retained-forever shape. **Corrected in the
   re-pass:** `DiskArbitration` already *has* a real unregister call
   (`DAUnregisterCallback`, `DiskArbitration.h:552`) — the line that used to
   be here ("if `DiskArbitration` gains a real invalidate call in a future
   SDK...") was factually wrong, per phase 3's review. What actually blocks
   a leak-free teardown isn't a missing API; it's that a callback can be
   executing on `queue` at the exact moment `deinit` runs, and there is no
   non-blocking way to wait for it from `deinit` — a `queue.async {
   Unmanaged<Box>.fromOpaque(context).release() }` issued after
   `DASessionSetDispatchQueue(session, nil)` would work (serial `queue`
   guarantees it runs after any callback already enqueued), but adopting it
   needs the same kind of dedicated stress test that found the two crashes
   here, which the re-pass didn't do. The immortal `Box` was judged
   "correct and bounded" by phase 3 review and was kept as-is.
3. Running the full test suite once and seeing it pass is not enough evidence
   for anything touching this session — the failure was intermittent and
   load-dependent (reliable in isolation, occasionally crashing under the
   full 58-test suite's CPU contention). The suite was run six consecutive
   times after the final fix specifically because of this — and again, six
   more times, after the re-pass's fixes (`## Verification`).
4. **New in the re-pass:** a debug-only `Thread Performance Checker` warning
   ("Thread running at User-initiated quality-of-service class waiting on a
   lower QoS thread running at Utility quality-of-service class") prints
   during `aLargeOutputStillParsesWellWithinTheTimeout`, with a backtrace
   that looks alarming out of context but is not a crash — the test still
   passes, `xcodebuild` still reports `** TEST SUCCEEDED **`, and it is
   Xcode's own debug diagnostic tooling, not a signal handler or an
   `abort()`. It comes from `LSDVDIdentity.discID`'s `group.wait(...)`
   blocking the calling (test) thread on a `.utility`-QoS background queue —
   the same pattern this function already used before this re-pass, just

### Judgement on the deliberately-retained `Box`

The design is **correct**. Because the `Box` is immortal, the context pointer
can never dangle; the `weak` load is the atomic handoff — a callback either
obtains a strong `DVDMonitor` (which then cannot deinit until the callback
returns) or reads `nil`. That closes the race rather than narrowing it. The
leak is bounded: exactly one `Box` per `DVDMonitor` (`passRetained` runs once,
in `init`), and the app creates one monitor for its lifetime.

It is **not unavoidable**, and the justification in the code comment,
`## Fix` and `## Gotchas` is inaccurate: this SDK does expose
`DAUnregisterCallback(session, callback, context)` (`DiskArbitration.h:552`).
More to the point, a leak-free teardown needs neither that nor a leak: in
`deinit`, after `DASessionSetDispatchQueue(session, nil)` (which cancels the
dispatch source, so no further handler is submitted), `queue.async {
Unmanaged<Box>.fromOpaque(context).release() }` — the serial queue guarantees
the release runs after any callback already in flight. Adopting that is
optional (the weak `Box` stays as the safety net either way); correcting the
"no session-invalidate call" claim is not.

### Must fix before re-review

1. **`LSDVDIdentity.discID` deadlocks on any `lsdvd` output larger than the

   runs only after `waitUntilExit()` returns; once `lsdvd` fills the pipe
   (~64KB) it blocks in `write`, the wait hits the timeout, the process is
   terminated and the result is `nil`. Reproduced with no hardware: a fake
   `lsdvd` shell script injected through `candidatePaths`, printing valid

   tables for every title) on a real feature disc is realistically above

## Long Description

The whole test is two lines:

```swift
let videoTS = url.appendingPathComponent("VIDEO_TS")
guard FileManager.default.fileExists(atPath: videoTS.path) else { return }
```

(`DVDMonitor.swift:23-24`). Everything downstream inherits that imprecision. `AppDelegate` records the URL as the disc to eject (`AppDelegate.swift:70`, feeding [#0005](0005.md)) and opens the search window. An eject aimed at a network share is at best a no-op and at worst unmounts something the user was using; an eject aimed at a mounted DMG dismounts it.

Three concrete false positives, all ordinary:

- **A network share.** `/Volumes/Media` on this project's own setup holds a Plex library; any volume mount with a `VIDEO_TS` folder anywhere at its root trips the monitor.
- **A mounted disc image.** Attaching a `.dmg` or `.iso` of a DVD posts `didMountNotification` exactly like a physical disc. There is no `Optical Media Type` check to separate them.
- **A remount of the disc already in the drive.** macOS remounts after a transient read error or a sleep/wake cycle. The monitor fires again, `showMetadataEntry()` brings the window forward (correct, since [#0002](0002.md)), but `jobs.insertedDiscURL` is overwritten and there is no signal that this is the same disc — nothing dedupes it.

There is also no notion of *removal*. The monitor observes `didMountNotification` and nothing else, so ejecting a disc leaves `insertedDiscURL` pointing at a path that no longer exists.

**The fix is now known, and it was verified on hardware.** `MakeMKVReplacement-Results.md` §3 records what DiskArbitration exposes for the drive on `joe`:

```
Device Node:              /dev/disk6
Device / Media Name:      PLDS DVD+-RW DS-8A8SH
Optical Media Type:       DVD-ROM
Removable Media:          Removable
Media Ejectable:          Yes
Protocol:                 USB
```

`Optical Media Type: DVD-ROM` is the field that separates a real disc from a DMG or a share — it is absent on both. `Media Ejectable` makes the eject in [#0005](0005.md) safe to attempt rather than hopeful.

For identity, `lsdvd -x -Oj` returns a stable fingerprint (`-Results.md` §4):

```
dvddiscid: ceaaceba983071d9a7e28fd6107947b7
```

That is a disc identity, which is what a debounce needs: two mounts with the same `dvddiscid` are the same disc, whatever their mount path. Neither `MakeMKVReplacement.md` nor `-Findings.md` anticipated getting this; it fell out of the lsdvd evaluation. lsdvd 0.21 is installed via `brew install lsdvd`.

This is **step 7** of `MakeMKVReplacement-Path.md` §3 and a **Phase 3 prerequisite** — an unattended multi-disc queue cannot dedupe re-mounts or recognize an already-ripped disc without a stable disc id.

## Steps to reproduce

**False positive on a disc image:**

1. Create or obtain a `.dmg`/`.iso` containing a `VIDEO_TS` folder at its root.
2. Double-click it to mount.
3. The metadata window opens as though a DVD were inserted, and `jobs.insertedDiscURL` now points at the image's mount point.

**No debounce on a remount:**

1. Insert a DVD; the window opens.
2. Eject and reinsert the same disc (or let the machine sleep and wake).
3. The monitor fires again with no indication that it is the same disc. Nothing compares it to what was already there.

## Expected behavior

The monitor reports **optical disc insert and remove events**, not volume mounts. A mount that is not `Optical Media Type: DVD-ROM` is ignored. Each disc carries a stable identity so a remount of the same disc is recognized as such and does not restart anything. Removal is observed, so `insertedDiscURL` is cleared when the tray opens.

## Actual behavior

Any mounted volume with a `VIDEO_TS` folder is treated as a newly inserted DVD. There is no media-type check, no identity, no debounce, and no removal event.

## Notes

lsdvd is an **optional enrichment, not a dependency** — `-Results.md` §4 is explicit about that, and `-Path.md` §2 keeps it optional. If lsdvd is absent, fall back to a weaker identity (volume name plus size, or the DiskArbitration media UUID) rather than failing the mount. Do not put lsdvd on the critical path.

The DiskArbitration facts above are from `diskutil` output on the actual drive; a Swift implementation uses the `DiskArbitration` framework directly (`DARegisterDiskAppearedCallback` / `DARegisterDiskDisappearedCallback`) rather than shelling out to `diskutil`. Both read the same properties.

Concurrency: `DVDMonitor.volumeMounted` is already `nonisolated` because `NSWorkspace` calls the `@objc` selector on an arbitrary thread (`DVDMonitor.swift:17`, and `CLAUDE.md`'s concurrency rules). DiskArbitration callbacks arrive on whichever run loop the session is scheduled against, so the same discipline applies — do the classification off the main actor, then `Task { @MainActor in … }` to notify, exactly as lines 26-28 do now.

Testable without a disc: the classification predicate (given a media-type string, a `VIDEO_TS` existence result and a previous disc id, should this fire?) is a pure function and should be one. The DiskArbitration plumbing itself is manual — say so in `## Verification` and name the disc used, per the verification caveat in `issues/Issues.md`.

## Plan

### `Changeover/DVDMonitor.swift`

Replace the `NSWorkspace` observer with a DiskArbitration session:

- `DASessionCreate` + `DASessionSetDispatchQueue` on a dedicated serial queue.
- `DARegisterDiskAppearedCallback` and `DARegisterDiskDisappearedCallback`.
- In the appeared callback, read `DADiskCopyDescription` and require the optical/removable media keys before doing anything else. Only then look for `VIDEO_TS` on the mount point.
- Keep `onDVDInserted: ((URL) -> Void)?` as the outward shape so `AppDelegate.startDVDMonitor` (`AppDelegate.swift:65-73`) changes minimally, but widen the payload to a small value type carrying the mount URL, the BSD device node, and the disc id when available. `AppDelegate` stores that on `JobController` instead of a bare URL.
- Add `onDVDRemoved` so `insertedDiscURL` can be cleared.

### Disc identity

Shell `lsdvd -x -Oj <mount point>` once per appeared event, parse `dvddiscid`, and treat it as the disc key. Time-box it and treat absence as "identity unknown" rather than an error — a disc with no readable id must still be rippable.

Debounce: if the incoming disc id equals the currently-tracked one and a job for it is running or finished, bring the window forward without resetting anything. This is the behavior [#0002](0002.md)'s window reuse already assumes.

### Risks

- **Do not gate the rip on the media type check being right.** A conservative classifier that ignores a real disc is a worse failure than one that occasionally offers to rip a disc image. Log what was rejected and why, so a false negative is diagnosable.
- **`VIDEO_TS` existence is still needed** — a data DVD or an audio CD is `DVD-ROM`/optical and carries no video. The media type narrows the candidates; it does not replace the content check.
- **Keep the eject decision out of this ticket.** [#0005](0005.md) owns ejecting; this ticket only supplies a URL and a device node it can trust.
- Scope: no queueing, no "already ripped this disc" library lookup. Those are [#0040](0040.md). This ticket produces the identity that makes them possible.
