## Description

Phase 2's umbrella ([#0020](0020.md)) lists **"The rip is verified by duration,
not by filename"** as an exit criterion, and nothing implements it. After the
primary encode returns, `EncodeController.encode` checks only that the output
file is non-empty (`Changeover/EncodeController.swift:276-289`); `DVDPipeline.run()`
then advances the marker to `.encoded` and moves the file into
`Movies/<Title (Year) {tmdb-ID}>/` (`Changeover/DVDPipeline.swift:417-422`). A
`.mp4` that stops twenty minutes early is filed, notified as a success, and
replaces any existing library copy through #0012's staged move.

The original motive for the criterion — MakeMKV renumbering titles across
`--minlength` values — died with the rip stage (#0014, #0028 closed by
construction). The residual risk did not: a disc with read errors can produce
a shorter file with exit 0. Hornets' Nest scans with 28 `MSG:4004` read errors
and #0024 already warns at scan time that "the rip may be incomplete", but
nothing checks afterwards whether it was. `MakeMKVReplacement-Results.md` §11
makes the same point from the other side: *"A corrupt rip still produces a
file, so spot-check playback, not exit codes."* Today that spot-check is the
user's job, after the file is already in Plex.

The one input the check needs is already carried: #0035 added
`EncodeSelection.featureDurationSeconds`, the chosen title's duration from
HandBrake's own scan, and threads it to the fallback
(`Changeover/DVDPipeline.swift:401`). It is not read on the success path.

Found by the Phase 2 phase-level review. Not reproduced on a disc; this is a
missing check, not an observed truncation.

## Resolution notes

> 🟢 Resolved 2026-09-15 — The encoded feature's duration is measured with AVFoundation and compared with the scan (tolerance `max(30 s, 2%)`) before it can be filed; a short or unmeasurable primary output counts as a disc-shaped encode failure and goes through the MakeMKV fallback once, a short fallback output fails the job, and a short extra is removed (cfe250b, review fix fd5948c).

**Review (2026-09-15, claude-opus-5).** cfe250b is in scope, and no short
file can reach `PlexOrganizer.move` on any path. One design point was wrong,
and fd5948c fixes it.

1. **Fixed: a short primary output never reached the fallback.** cfe250b ran
   the check after the primary/fallback `switch`, so a truncated exit-0
   encode failed the job outright. That shut out the ticket's own case:
   - A read-error disc is what MakeMKV's read recovery is for.
   - A manual retry only repeats HandBrake's read of the same disc. Nothing
     else in the app reaches MakeMKV.
   - `FallbackPolicy.isDiscShaped` already treats `.unknown` at `.encode` as
     disc-shaped. Its own comment names "exit 0 with no output", which is
     the same anomaly, whole rather than partial.

   fd5948c measures the primary output *before* `FallbackPolicy.decide`, and
   a short or unmeasurable result becomes the primary failure. The
   fallback's output is measured once more. If that is short too, the job
   fails, with HandBrake's short output as the headline and
   `fallback: .failed(.encode, .unknown(…))`. It never goes back through
   the policy, so nothing can loop. The `.attempt` branch already deletes
   the primary's `.mp4` before the rip. This overrides the Plan's "Out of
   scope: a fallback trigger on a short file" and its "must not trigger the
   fallback" test. The cost is one rip and one more encode, only on a disc
   whose HandBrake output was already unusable.
2. **Tolerance is sound for truncation, not for scattered skips.** Measured
   drift is 7 s on 9,478 s (Dragon Tattoo, #0035). With the 2% term, the
   tolerance is 132 s for Hanna (6,645 s) and 176 s for Hornets' Nest
   (8,807 s).
   - **Caught:** an encode that stops minutes early.
   - **Not caught:** libdvdread skipping a few seconds per bad sector. 28
     read errors may well add up to that.

   The check is a guard against lost library copies, not a playback check.
   `.long` logs `⚠︎` and continues, which is right: more of the movie is not
   data loss. It could hide a wrong-title pick, but #0025 already guards
   that. Titles under 30 s can't be meaningfully checked (the floor), which
   is fine for extras.
3. **Plan deviation (disposal) approved.** A duration failure is at the
   `.encode` stage, so `WorkingFiles.disposition` removes the job directory.
   That is correct: the short file is not the movie, the disc is still the
   source, and the library copy is untouched because the move never ran.
   The Plan's "the job directory is kept" was simply wrong. The user
   wasn't told the file was gone, though. fd5948c's sentence now reads
   "…so it was discarded, not filed. Any copy already in Plex is untouched."
   `FailurePresenter` shows it as "Something went wrong: …". With no
   makemkvcon, it adds "MakeMKV isn't installed …, so no fallback was tried".
4. **Unmeasurable output fails strictly, and the order is safe.**
   - `ProcessRunner` resumes only after the process has exited *and* the
     reader has seen EOF (#0015's `RunCompletionGate`).
   - `EncodeController.encode` returns `.success` only after that.
   - HandBrake's `av_mp4` muxer writes `moov` when it closes the file (no
     `--optimize`), so an exit-0 file is finished and closed before it is
     measured.
   - `load(.duration)` reads `mvhd` without decoding, so HEVC and AC3
     passthrough don't matter.

   fd5948c adds a test in which the *real* measurer rejects the stub's
   text-only `.mp4`. **HandBrakeCLI is not installed on cameron or gordon**,
   so no real HandBrake file has been measured (see the manual checks).
   If AVFoundation can't read one, *every* job fails. That fails safe, and
   the Plan's recorded user decision ("downgrade to a logged warning")
   covers it. `.phase1`/nil is not reachable in production. `JobController`
   builds the only `DVDPipeline` and takes `selection` only from
   `EncodeSelection.make`, which always sets `featureDurationSeconds`. No
   production site passes `measureDuration`.
5. **Extras are fine.** A short or unmeasurable extra is removed with
   `WorkingFiles.removeFile` and skipped. `succeededExtras` is not
   incremented and `destination` is never reassigned. Extras are skipped
   entirely on the fallback path (#0035).
6. **Isolation is acceptable.** `SWIFT_APPROACHABLE_CONCURRENCY = YES`
   makes `measureSeconds` and the seam `nonisolated(nonsending)`, so they
   start on the MainActor. Only the `AVURLAsset` allocation runs there.
   `load(.duration)` suspends and parses on AVFoundation's own queues, so
   there is no blocking I/O to move off the actor, unlike #0012's
   synchronous `FileManager` move.

   The `AVAssetWriter` test is deterministic: 1 s at timescale 600 is
   exact, and 0.2 s on gordon. fd5948c also makes it throw if the one frame
   isn't accepted, instead of writing an empty track.

## Root cause

Nothing between HandBrakeCLI's exit and `PlexOrganizer.move` ever compared
the encoded `.mp4`'s length to anything. `EncodeController.encode` only
checked `outputIsNonEmpty` (a non-zero byte count); `DVDPipeline.run()` then
advanced the marker straight to `.encoded` and moved the file. The MakeMKV
fallback's `#0035` fix (`featureDurationSeconds`, `MakeMKVRipper.matchTitle`)
verifies which *title* the fallback ripped by duration, but that number was
never read again after the second HandBrakeCLI pass to verify the resulting
file was *whole*. A disc read error (Hornets' Nest's 28 `MSG:4004` warnings,
#0024) can make HandBrakeCLI exit 0 having encoded only part of the title.

## Fix

New `Changeover/OutputDurationCheck.swift`, split the way the Plan asked:

- `compare(expectedSeconds:actualSeconds:) -> Verdict` is pure —
  `.consistent(deltaSeconds:)`, `.short(deltaSeconds:)`,
  `.long(deltaSeconds:)`, all carrying a signed delta (actual − expected).
  `tolerance = max(minimumToleranceSeconds, expectedSeconds *
  tolerancePercent / 100)` with `minimumToleranceSeconds = 30` and
  `tolerancePercent = 2`, exactly as the Plan specified, with the Plan's own
  evidence (Dragon Tattoo's 7s/0.07% scan-vs-rip drift, MakeMKV's `MSG:3038`
  cell trimming) recorded in the doc comments as the tolerance's
  justification. `.long` logs and continues — a file with *more* of the
  movie in it is never the data-loss risk this check exists for.
- `measureSeconds(of:) async throws -> Int` reads a local file's duration
  with `AVURLAsset(url:).load(.duration)` — no new dependency (`ffprobe`
  stays out, per the Plan and #0037's Notes) — truncated to whole seconds
  the same way HandBrake's own `Duration.Seconds` truncates.

`DVDPipeline` gained `var measureDuration: @Sendable (URL) async throws ->
Int = OutputDurationCheck.measureSeconds`, defaulted exactly like
`selection`/`extras`/`removeJobDirectory` so every existing construction
site compiles unchanged and tests can inject a fake measurer with no real
media file.

`run()` gained a local nested `checkDuration(_:expectedSeconds:label:)`
(alongside the existing nested `advanceMarker`/`logSweepReport` helpers) that
measures, compares, and logs one line naming both durations and the signed
delta — used at both call sites below.

**The feature.** Once, right after `"✓ Encode complete: …"` and *before*
`advanceMarker(.encoded)` — after the primary/fallback `switch` has already
returned, so a duration failure here structurally cannot re-enter
`FallbackPolicy` (only the primary encode's own failure ever reaches that
switch). `selection.featureDurationSeconds == nil` (only `.phase1`, i.e. no
scan ever happened) logs "Output duration not checked — no scan duration"
and proceeds — never guessing. On `.short`, or when `measureDuration` itself
throws (a file `AVFoundation` can't open is one Plex/Apple TV can't play
either — the Plan's own call, kept strict rather than downgraded to a
warning), the job fails with `JobFailure(stage: .encode, reason:
.unknown("The encoded file runs H:MM:SS but the scan said this title runs
H:MM:SS, so it was not filed"))`, using `DiscTitleFormatting.duration` for
both numbers, same as the Plan's worked example.

**Extras.** After each extra's own encode succeeds, before its move: the
same `checkDuration` against `ExtrasPlan.Item.durationSeconds`. `.short` (or
a measuring failure) removes the file with `WorkingFiles.removeFile` — the
same disposal a failed extra already got — and `continue`s the loop; the
job's own outcome is never touched, per #0031's rules.

**Deviation from the Plan's test list, recorded here as instructed:** the
Plan's Tests section says a short-feature failure leaves "the job directory
… kept". That's inconsistent with `WorkingFiles.disposition(for:
jobDirectoryCreated:)`'s existing, deliberate rule for `stage: .encode`
failures ("A partial or fallback-failed encode is unplayable and nothing in
the app can use it; the disc is still the source" → `.removeJobDirectory`) —
the same rule the Plan's own code sample invokes by using `stage: .encode`
for this failure. Kept as `.encode` (matching the Plan's explicit code and
`## Notes`'s "the same as any failed encode" framing) rather than switching
to `.organize` (which would keep it): the short file is genuinely unplayable
and the disc remains the source, so there is nothing worth preserving. The
test asserts the directory is disposed of, not kept; flagging this for
review rather than silently reconciling it.

## Gotchas

- **The extras duration check has no "no expected duration" escape hatch**
  the way the feature does — `ExtrasPlan.Item.durationSeconds` is
  non-optional (it always comes from a live scan, #0031), so every extra is
  measured every time. This is what broke the three pre-existing
  `ExtrasPipelineTests` (their stub-written placeholder isn't real media)
  until they got an injected measurer — worth knowing before adding another
  extras pipeline test without one.
- `AVAssetWriter.endSession(atSourceTime:)` is what makes
  `measureSecondsReadsARealOneSecondMP4` reliable: it pins the container's
  reported duration to exactly the given time regardless of how many frames
  were actually appended (one, here), sidestepping frame-rate arithmetic
  that would otherwise make the test's expected duration fragile.
- The Plan's Tests section text ("the job directory is kept") and its own
  code sample (`stage: .encode`) point in different directions once
  `WorkingFiles.disposition` is checked against them — see `## Fix`'s
  deviation note. Flagged, not silently resolved either way.

## Expected behavior

Before the feature is moved into the library, the app reads the encoded file's
duration and compares it with the scanned title's duration. A file that is
materially shorter than the scan said is treated as a failed encode — logged
with both durations, kept in the job directory under #0004's rules, and never
filed as the movie. A file whose duration matches (within a tolerance that
absorbs tool rounding and trimmed cells) logs the match and proceeds exactly as
today.

## Actual behavior

`HandBrakeFailureClassifier` sees `outputIsNonEmpty` and nothing about length.
Any non-empty `.mp4` from an exit-0 encode is moved into `Movies/` and reported
as `✓`.

## Notes

- The same check applies to the MakeMKV fallback path: the second encode of
  the `.mkv` produces the `.mp4` that gets filed, and
  `featureDurationSeconds` is the same number. #0035's `matchTitle` only
  verified which makemkvcon title was ripped, not that the resulting file is
  whole.
- Extras (#0031) should get the same measurement, log-only: a short extra is
  removed the way a failed extra is, and never changes the job outcome.
- Drift evidence for the tolerance: on Dragon Tattoo, HandBrake's scan says
  9,478 s and makemkvcon's rip says 9,471 s (#0035) — 7 s, about 0.07%.
  MakeMKV's `MSG:3038` ("Cells N-N were removed from title end") shows a few
  seconds of trim is normal. A truncated encode is minutes short, not
  seconds. A tolerance of `max(30 s, 2%)` separates the two by a wide margin;
  the numbers are a starting point, not tuned.
- `AVURLAsset(url:).load(.duration)` reads the `moov` atom of a local MP4 in
  milliseconds and needs no extra binary. `ffprobe` is not a dependency and
  should not become one.
- Nothing here is UI. No UI test is warranted or permitted.

### The pure seam

```swift
nonisolated enum OutputDurationCheck {
    enum Verdict: Equatable, Sendable {
        case consistent(deltaSeconds: Int)     // actual minus expected, signed
        case short(deltaSeconds: Int)          // beyond tolerance, and shorter
        case long(deltaSeconds: Int)           // beyond tolerance, and longer — log, don't fail
    }
    static let minimumToleranceSeconds = 30
    static let tolerancePercent = 2
    /// Integer arithmetic, as #0025 and #0032 do it.
    static func compare(expectedSeconds: Int, actualSeconds: Int) -> Verdict
}
```

`tolerance = max(minimumToleranceSeconds, expectedSeconds * tolerancePercent / 100)`.
Write the Dragon Tattoo 7 s drift and the `MSG:3038` trim into the doc
comment as the evidence for the floor. A `.long` file is surprising but not
a truncation — log it and proceed; do not fail a job for a file that has more
of the movie in it.

### Measuring

A second function, `nonisolated static func measureSeconds(of url: URL) async
throws -> Int`, using `AVURLAsset(url: url).load(.duration)` from
`AVFoundation`, truncated to whole seconds (HandBrake's `Duration.Seconds` is
truncated too, so the two round the same way). Keep it in the same file but
separate from `compare`, so `compare` is testable without a media file.

Give `DVDPipeline` a `var measureDuration: @Sendable (URL) async throws -> Int
= OutputDurationCheck.measureSeconds` property, defaulted like `selection`
and `extras`, so the ~25 existing construction sites are untouched and the
pipeline tests can inject a measurer without a real MP4.

### Where it runs in `run()`

After the primary encode's `.success(let url)` and after the fallback's
second-encode success — that is, once, on the `.mp4` that will be filed —
and **before** `advanceMarker(.encoded)`:

1. If `selection.featureDurationSeconds` is `nil` (the `.phase1` test
   default; production always sets it via `EncodeSelection.make`), log
   `Output duration not checked — no scan duration` and continue. Never
   guess a duration.
2. Measure. If measuring throws, treat it as a failed encode with the
   reason below — a local `.mp4` AVFoundation cannot open is not one Plex or
   the Apple TV will play either. *User decision:* if this proves flaky in
   the field, downgrade to a logged warning; start strict.
3. `.consistent` → log `✓ Output runs H:MM:SS, scan said H:MM:SS (Δ ±N s)`.
4. `.long` → log the same line with a `⚠︎` and continue.
5. `.short` → `return await finish(.failed(JobFailure(stage: .encode,
   reason: .unknown("The encoded file runs H:MM:SS but the scan said this
   title runs H:MM:SS, so it was not filed"), logTail: …)))`. Use
   `DiscTitleFormatting.duration` for both numbers. The partial stays in the
   job directory for #0004's disposal rules, the same as any failed encode;
   nothing is moved, nothing is ejected, and #0012's existing library copy is
   untouched because the move never runs.

`.unknown(String)` rather than a new `FailureReason` case, for the reason
#0035 recorded: `FailureReason` is wire format and an older decoder throws on
an unknown case key. `FailurePresenter` will render it as "Something went
wrong: <sentence>", which is why the string is a sentence.

**The failure must not trigger the MakeMKV fallback.** `FallbackPolicy` only
sees the primary encode's `JobFailure`; this check runs after that switch and
returns through `finish`, so it never reaches the policy. Assert that in a
test.

In the extras loop (`Changeover/DVDPipeline.swift:494-519`), after each
extra's encode succeeds and before its move: measure against
`ExtrasPlan.Item.durationSeconds`; on `.short` (or a measuring error) log one
line and remove the file with `WorkingFiles.removeFile`, exactly as a failed
extra is handled; the outcome is unchanged.
