# 0103 — Clean-Mac Gatekeeper install has never been verified

| | |
|---|---|
| **Status** | open |
| **Module** | Release |
| **Platform** | macOS |
| **First seen** | 2026-09-11 |

## Description

Phase 6's headline exit criterion is "clean-Mac install with no `xattr -cr` step and no Gatekeeper prompt" (`Roadmap.md:252`), and nothing currently proves it. Every check available on the build machine is contaminated by the build machine — it holds the signing certificate, has the developer tools installed, and has already trusted the app. This ticket is the acceptance test for [#0102](0102.md), run somewhere that has never seen Changeover.

## Long Description

The specific things a build machine cannot tell you:

- **Stapling actually works offline.** `spctl` on the build machine may accept a
  bundle because it can reach Apple's notary service, not because the ticket is
  stapled. The failure mode — a notarized but unstapled app that works for you
  and fails for a user on a plane — is invisible locally.
- **Quarantine is really cleared by the DMG path.** `xattr -w com.apple.quarantine`
  simulates the flag, but not the full Launch Services first-launch evaluation, and
  not a real Safari download.
- **The app runs without the developer's environment.** Changeover shells out to
  `makemkvcon` and `HandBrakeCLI` via `Process`
  (`Changeover/RipController.swift:18`, `Changeover/EncodeController.swift:19`)
  at hardcoded `/opt/homebrew/bin` defaults
  (`Changeover/AppSettings.swift:14-15`). On a machine with no Homebrew — or an
  Intel Mac where Homebrew lives at `/usr/local/bin` — those paths are wrong.
  That is [#0105](0105.md)'s bug to fix, but this is where it becomes visible.
- **`UserDefaults` is genuinely empty.** Every local run of Changeover has
  populated `plexMediaRoot`, `makemkvconPath`, `handbrakePath` and `tmdbAPIKey`
  under the `co.sstools.Changeover` domain
  (`Changeover/AppSettings.swift:58-63`). The author's Mac can no longer produce
  a true first launch without deleting them.

## Steps to reproduce

1. Take the DMG produced by [#0102](0102.md).
2. Look for any record — a log, a note, a ticket — of it being opened on a Mac
   that is not the build machine.

## Expected behavior

A documented, repeatable acceptance run exists: DMG downloaded over HTTPS onto a
clean macOS install, opened, dragged to Applications, launched, with no
Gatekeeper dialog, no right-click-Open workaround, and no Terminal command — and
the result recorded on this ticket.

## Actual behavior

No such run has happened. The only distribution instructions in the repo
(`README.md:74-79`, `Plan.md:301-306`) assume the opposite: that the user will
have to strip quarantine by hand.

## Plan

**Prerequisite: [#0102](0102.md) must produce a DMG first.** This ticket adds no
code and changes no build settings — it is a test procedure and its recorded
result.

**1. Pick a clean target.** In descending order of honesty:

- A second physical Mac that has never run Changeover. Best, and the user has a
  MacBook Air (`RemoteControl.md`, Phase 4 context) — though note that if it has
  ever run a debug build from Xcode, it is no longer clean for the
  `UserDefaults` half of the test.
- A fresh macOS VM (Virtualization.framework / Tart / UTM on Apple Silicon). Good
  for the Gatekeeper half, and resettable, which makes the test repeatable.
  Verify that the VM has *never* had the Developer ID certificate installed.
- A brand-new user account on the build Mac. Cheapest, and adequate for the
  `UserDefaults` and onboarding half, but **not** adequate for Gatekeeper — the
  signing certificate lives in the login keychain of one user but the trust
  evaluation and the `spctl` assessment database are system-wide, so a
  same-machine account can pass when a real stranger's Mac would fail. Use it for
  [#0104](0104.md), not for this.

**2. Get the DMG there the way a user would.** Not AirDrop from Finder, not a
shared folder — host it somewhere and download it with Safari, so the real
`com.apple.quarantine` attribute with a real originating-URL is set. If
[#0110](0110.md) results in hosting an appcast, the same host serves the DMG
(`references/website-deploy.md`).

**3. Run the acceptance script** and record each line's result on this ticket:

- Double-click the DMG. It mounts with no warning.
- Drag `Changeover.app` to the Applications alias in the DMG window.
- Launch from `/Applications` by double-click. **No dialog appears** — not
  "unidentified developer", not "downloaded from the internet, are you sure",
  not "damaged and should be moved to the Trash."
- The menu bar icon appears and **no Dock icon does** (`LSUIElement`, from
  `project.pbxproj:406` / the `Info.plist` work in [#0101](0101.md)).
- `spctl -a -vvv -t exec /Applications/Changeover.app` → `accepted`,
  `source=Notarized Developer ID`.
- `xcrun stapler validate /Applications/Changeover.app` → validated, **with
  Wi-Fi turned off**. This is the check that only means something off the build
  machine.
- `codesign -vvv --deep --strict /Applications/Changeover.app` → valid on disk,
  satisfies its Designated Requirement.
- `xattr -l /Applications/Changeover.app` → note whether the quarantine flag is
  present. It may legitimately still be there after a first launch; the point is
  that nothing had to be *removed* by hand.

**4. Record the negative result too.** If a dialog appears, capture it as a
screenshot into `issues/0103/` and name the exact text. "It didn't work" is not
a useful result for a Gatekeeper failure — the wording distinguishes an unsigned
app from an unnotarized one from a stapling failure, and
`references/troubleshooting.md` ("Gatekeeper / notarization") maps the wordings
to causes.

**5. Then keep going into the app.** Once past Gatekeeper, continue straight into
[#0104](0104.md)'s onboarding flow on the same clean machine and note where it
breaks. Two tickets, one trip.

**Risks.** (a) The clean machine will very likely lack MakeMKV and HandBrake
entirely — expected, and it is the real test of [#0105](0105.md), but it means a
full end-to-end rip may not be possible on the first trip. Plan for installing
them there, or accept that this ticket stops at "the app launches and asks for
what it needs." (b) A macOS VM's `spctl` behavior is close to but not identical
to bare metal; if the result is surprising, confirm on physical hardware before
concluding the pipeline is broken.

## Notes

**Verification of this ticket is the ticket.** Its `## Verification` section on
resolution must name the actual machine or VM image used, the macOS version, how
the DMG got there, and the literal output of `spctl`, `stapler validate` and
`codesign`. Per `issues/Issues.md` ("Verification caveat specific to this
project"), where a check was manual it must say so plainly — every check here is
manual, and that is fine, but it must be stated rather than implied.

Re-running this after any change to signing, the Team ID, or macOS major version
is cheap and worth it; write the procedure down in `RELEASE.md` (step 5 of the
`mac-release` pipeline, "Smoke-test on a clean Mac / fresh user account") so it
becomes part of every release rather than a one-time event.
