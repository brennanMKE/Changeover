# 0042 — The app can hold one job at a time because job state lives in a view, not in an ordered store

| | |
|---|---|
| **Status** | open |
| **Module** | JobQueue / AppDelegate |
| **Platform** | macOS |
| **First seen** | 2026-09-11 |

## Description

Phase 1's `JobController` tracks a single current job; there is nowhere to put a second one. This ticket introduces `@Observable final class JobQueue` — an ordered, MainActor-isolated store of `Job` objects owned by `AppDelegate` — with enqueue, lookup by `JobID`, ordering, and retention of finished jobs so the queue view has a history to show.

## Long Description

The distinction between this ticket and [#0044](0044.md) matters: **this one is the data structure, that one is the scheduler.** `JobQueue` here has no `Task`, launches nothing, and runs no process. It answers "what jobs exist, in what order, in what state". That separation is what makes the scheduler testable — [#0044](0044.md) can be exercised against a queue populated by hand.

`AppDelegate` is the right owner. It already owns `let settings = AppSettings()` (`Changeover/AppDelegate.swift:8`) and the `DVDMonitor` (`:12`), and injects settings into every hosting view with `.environment(settings)` (`:43`, `:87`). The queue follows the same path: `.environment(queue)`, read with `@Environment(JobQueue.self)`. It must not be owned by a view with `@State` — `Roadmap.md:41-42` names the exact bug that causes, and it is worse with a queue than with one job.

Retention is a design decision, not an afterthought. The Phase 3 demo ends with "the queue view shows what happened in what order" (`Roadmap.md:142`), which requires terminal jobs to stay in the list. They stay for the session, capped, oldest-terminal-pruned-first.

## Steps to reproduce

1. Start a rip.
2. While it runs, try to get a second job into the app in any state at all — even `queued`.
3. After a job finishes, try to find out from anywhere in the app what its outcome was.

## Expected behavior

`AppDelegate` owns a `JobQueue`. Any number of jobs can exist simultaneously, each with its own `JobID` and state. Jobs stay in the queue after they reach a terminal stage so the history is inspectable, up to a cap. Any view or, later, any remote client can ask the queue for the ordered list or for one job by id.

## Actual behavior

`MetadataEntryView` owns `isProcessing: Bool` and `logLines: [String]` as `@State` (`Changeover/MetadataEntryView.swift:7-8`); `startRipping()` clears the log and runs one pipeline (`:142-155`); the Start button is disabled while `isProcessing` is true (`:129`). There is exactly one slot, it is inside a view, and it is cleared at the start of every job so no history survives.

### The type

```swift
@Observable
final class JobQueue {
    private(set) var jobs: [Job] = []          // creation order, oldest first
    var finishedJobRetentionLimit = 50

    func enqueue(_ job: Job)
    func job(id: JobID) -> Job?
    func remove(id: JobID)                     // terminal jobs only
    func clearFinished()

    var active: [Job] { jobs.filter { !$0.state.stage.isTerminal } }
    var hasActiveJobs: Bool { !active.isEmpty }
    var snapshot: [JobSnapshot] { jobs.map(\.snapshot) }
}
```

No annotations. Under `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` this class is `@MainActor` already, which is the whole isolation story: every mutation of `jobs` happens on MainActor, so there is no lock, no `actor`, and no possibility of a torn read. `Plan.md`'s convention table is explicit that the `actor` keyword is not used for types with no reason to leave the main actor, and this type has none — it never touches a `Process`.

The one thing to be careful about is the **boundary**: the long-running work in [#0044](0044.md) runs `nonisolated` on the cooperative pool (`Changeover/RipController.swift:9`, `Changeover/EncodeController.swift:9`), and results come back across an `await`. Because the awaiting code is MainActor-isolated, the resumption lands on MainActor and the subsequent `jobs` mutation is safe. Nothing nonisolated ever holds a reference to `JobQueue` — the controllers take plain path parameters and a `@MainActor (String) -> Void` closure, and that signature must stay that way.

### Ordering and retention

- `jobs` is append-only on enqueue; the array order is creation order and never changes. Display order in [#0048](0048.md) is a sort over that, not a mutation of it.
- Pruning runs after every transition into a terminal stage: while `jobs.filter(\.state.stage.isTerminal).count > finishedJobRetentionLimit`, drop the oldest terminal job. Active jobs are never pruned regardless of count.
- `remove(id:)` refuses a non-terminal job and returns without mutating. Removing a running job would orphan its `Task` and leak its lane token — [#0046](0046.md) handles stopping a running job, and it does so by cancelling it into a terminal stage first.

### Observation correctness

`jobs` is an array of `@Observable` reference types. Two consequences that must be got right or [#0048](0048.md) will be subtly wrong:

- Mutating `job.state` does **not** invalidate readers of `queue.jobs`, because the array itself did not change. That is the desired behaviour — a row observing its own `Job` updates, the list does not. Any derived property on `JobQueue` that reads job state (`active`, `hasActiveJobs`, `snapshot`) therefore *does* re-evaluate for an observer, because reading `job.state` inside the computed property registers a dependency on that job. Verify this rather than assuming it; if `hasActiveJobs` fails to invalidate, [#0047](0047.md) will never release the power assertion.
- Do not cache counts in stored properties kept in sync by hand. A stored `runningCount` that drifts from `jobs` is the classic source of a wedged queue.

### Risks

- **Double ownership.** If Phase 1's `JobController` survives as a separate type holding a current job *and* `JobQueue` holds the same job, they will disagree. Collapse or delegate — do not run both.
- **`AppDelegate.showMetadataEntry()` reuses one window** (`Changeover/AppDelegate.swift:72-76`). With a queue, that window is per-disc, not per-job; it is [#0045](0045.md)'s problem, but do not paper over it here by keying the window off a job.

## Notes

**Verification.** No disc, no subprocess, no UI — fully unit-testable, so the `Issues.md` manual-verification caveat does not apply. `ChangeoverTests/JobQueueTests.swift` must cover:

- enqueue preserves creation order across at least three jobs, and `job(id:)` returns the right one for each;
- `job(id:)` returns `nil` for an id that was never enqueued and for one that was pruned;
- `active` and `hasActiveJobs` reflect stage changes made through `Job.transition(to:)` — including the transition from the last active job to a terminal stage flipping `hasActiveJobs` to `false`, which is the exact edge [#0047](0047.md) depends on;
- pruning drops the **oldest terminal** job when the cap is exceeded and never drops an active job, tested with a mix of active and terminal jobs past the cap;
- `remove(id:)` on a running job is a no-op and leaves the array unchanged;
- `clearFinished()` removes every terminal job and no active one;
- `snapshot` has the same count and order as `jobs` and each element's `id` matches.

One observation test is worth the trouble even though it is fiddly: register with `withObservationTracking` on `queue.hasActiveJobs`, transition the only active job to `.done`, and assert the change handler fired. That is the assertion that [#0047](0047.md) rests on, and it is cheaper to catch here than as a mini that never sleeps again.
