## Description

Phase 1's `JobController` tracks a single current job; there is nowhere to put a second one. This ticket introduces `@Observable final class JobQueue` — an ordered, MainActor-isolated store of `Job` objects owned by `AppDelegate` — with enqueue, lookup by `JobID`, ordering, and retention of finished jobs so the queue view has a history to show.

## Resolution notes

> 🟢 Resolved 2026-09-15 — `JobController` now holds `current: Job?` plus a bounded, oldest-pruned `history` of finished `Job`s, each with its own `JobLog`, validated `JobState`, recorded outcome and `Codable` `JobSnapshot`, driven through a per-job `JobContext` (73c01f0, review fix 9c465a3).

**Review (2026-09-15, claude-opus-5).** 73c01f0 is in scope and its data model is sound, but it shipped a user-visible regression. 9c465a3 fixes it:

1. **Every between-job line vanished after the app's first job.** `append` sent lines to `controllerLog` whenever `current == nil`, but the log area rendered `currentLog`, which was `(current ?? history.last)?.log ?? controllerLog`. Once one job had finished, `history.last` always won, so "No disc is mounted", the other start guards (#0026 `StartGate`, #0034 wrong disc), every #0045 eject refusal, "Disc ejected." and the next disc's scan output went to a buffer nothing rendered. The #0043 bug was fixed by hiding the lines instead of routing them. `betweenJobTrafficAfterAFinishedJobNeverLandsInItsRetainedLog` checked only the retained log, never what is shown. The fix:
   - `JobController.logDisplayRows` replaces `currentLog`. While a job runs, it is that job's log. Once idle, it is the last job's log **followed by** `controllerLog`. `logLines` mirrors it, and `MetadataEntryView.logArea` renders it.
   - Rows are `LogDisplayRow`s keyed by source + `LogLine.id`, because every `JobLog` numbers from 0 and the two merged sources would collide in a `ForEach`.
   - `controllerLog` is replaced by each successful `start`, so it holds only the gap since the last job began and never trails a later job. Pre-first-job traffic is discarded at the first `start`, as before.
   - Retained logs still hold only their own job.
2. **`finish` had slipped from "unconditional".** `sleepAssertion.end()` sat after `guard let job = current else { return }`. It was unreachable in practice, but #0047's rule is "unconditional", so it now comes before the guard. `finish` also appends to `history` before clearing `current`, the refresh's order, so an `isRunning` observer never sees the job in neither place.
3. **`JobLogStore` was dead.** Nothing in production used it after 73c01f0, and it described itself as the retention mechanism, which would mislead #0048. Deleted with `JobLogStoreTests`, and `JobLog`'s doc comments were updated.

Pruning is `removeFirst` on `history` and never calls `end`. `isRunning` is `current != nil`.

## Root cause

Phase 1's `JobController` (per #0002) tracked exactly one job as five
independent scalars — `currentJobID`, `currentJobState` (#0041),
`currentLog`/`logStore` (#0043), `currentMetadata`, `lastOutcome` — each
reset or overwritten in place at the start of the next `start()`. There was
no single `Job` object binding those facts together, and nothing kept a
finished job's *full* state (not just its `#0043` log) reachable once the
next job started. The #0043 review additionally found a live bug in that
scalar model: because `currentLog` stayed pointed at whatever job it last
named, any log line appended between jobs — a disc-scan progress line, a
refused `start`/`ejectDisc` — landed inside the *previous, already-finished*
job's retained log.

Per the 2026-09-15 plan refresh, the original plan's separate `JobQueue`
store is superseded: #0040 option A means there is never a second *active*
job (a job needs its disc in the drive), so what's actually missing is
**history** — `JobController` itself needed to hold the current job plus a
bounded list of finished ones.

- **`Changeover/Jobs/Job.swift`** (new) — `@Observable final class Job`:

    `JobState.finishing(with:)`. Records `outcome`/`endDate`

## Gotchas

- **`lastOutcome` deliberately does not read `history.last?.state.outcome`**, despite that being the plan refresh's literal sketch. Two existing #0041-era tests (`aSuccessWithNoPhaseReportsIsLoggedNotApplied`, `anInvalidMidJobReportIsLoggedAndDropped`) require `lastOutcome` to equal the runner's actual returned outcome even when the phase-report contract was broken and `state` was deliberately left non-terminal (so `state.outcome` is `nil` per `JobState`'s own invariant). `Job` therefore stores `outcome` as a separate field, set unconditionally in `finish(with:)`, independent of whether the mapped terminal phase was a legal edge. `JobController.lastOutcome` reads `Job.outcome`, not `Job.state.outcome`.
- **`fakeSuccess`'s signature changed from taking a bare `phase` closure to taking the whole `JobContext`.** The first pass (matching the plan's literal `JobContext.phase` field) compiled but produced a "converting non-Sendable function value to '@MainActor @Sendable (JobPhase) -> Void' may introduce data races" warning at every `fakeSuccess(context.phase, destination:)` call site — the same bound-method-argument pattern #0045's Gotcha already hit with `ejector.eject`. Passing the whole `context` and calling `context.phase(...)` from inside `fakeSuccess` (rather than handing the closure value itself to a caller) cleared every warning; verified with a clean `build-for-testing` before the final gordon run.
- *(Superseded in review: 9c465a3 deleted `JobLogStore` and its tests as dead code.)* **`JobLogStore` (#0043) is untouched but no longer used by `JobController`** — a job's `JobLog` now lives directly on `Job`, created once by `start` and kept alive by `history` for exactly as long as `historyLimit` allows. `JobLogStore`/`JobLogStoreTests` remain in the tree as still-valid, independently tested infrastructure; deleting it was out of scope and would have been a gratuitous diff against a type nothing else references badly.
- **No `JobControllerScanTests`/`DVDMonitorWiringTests` changes were needed** — those suites (in `JobControllerTests.swift`) never touch the `Runner` seam.

## Long Description

The distinction between this ticket and [#0044](0044.md) matters: **this one is the data structure, that one is the scheduler.** `JobQueue` here has no `Task`, launches nothing, and runs no process. It answers "what jobs exist, in what order, in what state". That separation is what makes the scheduler testable — [#0044](0044.md) can be exercised against a queue populated by hand.

`AppDelegate` is the right owner. It already owns `let settings = AppSettings()` (`Changeover/AppDelegate.swift:8`) and the `DVDMonitor` (`:12`), and injects settings into every hosting view with `.environment(settings)` (`:43`, `:87`). The queue follows the same path: `.environment(queue)`, read with `@Environment(JobQueue.self)`. It must not be owned by a view with `@State` — `Roadmap.md:41-42` names the exact bug that causes, and it is worse with a queue than with one job.

Retention is a design decision, not an afterthought. The Phase 3 demo ends with "the queue view shows what happened in what order" (`Roadmap.md:142`), which requires terminal jobs to stay in the list. They stay for the session, capped, oldest-terminal-pruned-first.

## Steps to reproduce

1. Start a rip.
2. While it runs, try to get a second job into the app in any state at all — even `queued`.
3. After a job finishes, try to find out from anywhere in the app what its outcome was.

## Expected behavior

`AppDelegate` owns a `JobQueue`. Any number of jobs can exist simultaneously, each with its own `JobID` and state. Jobs stay in the queue after they reach a terminal stage so the history is inspectable, up to a cap. Any view or, later, any remote client can ask the queue for the ordered list or for one job by id.

## Actual behavior

`MetadataEntryView` owns `isProcessing: Bool` and `logLines: [String]` as `@State` (`Changeover/MetadataEntryView.swift:7-8`); `startRipping()` clears the log and runs one pipeline (`:142-155`); the Start button is disabled while `isProcessing` is true (`:129`). There is exactly one slot, it is inside a view, and it is cleared at the start of every job so no history survives.

### The type

```swift
@Observable
final class JobQueue {
    private(set) var jobs: [Job] = []          // creation order, oldest first
    var finishedJobRetentionLimit = 50

    func enqueue(_ job: Job)
    func job(id: JobID) -> Job?
    func remove(id: JobID)                     // terminal jobs only
    func clearFinished()

    var active: [Job] { jobs.filter { !$0.state.stage.isTerminal } }
    var hasActiveJobs: Bool { !active.isEmpty }
    var snapshot: [JobSnapshot] { jobs.map(\.snapshot) }
}
```

No annotations. Under `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` this class is `@MainActor` already, which is the whole isolation story: every mutation of `jobs` happens on MainActor, so there is no lock, no `actor`, and no possibility of a torn read. `Plan.md`'s convention table is explicit that the `actor` keyword is not used for types with no reason to leave the main actor, and this type has none — it never touches a `Process`.

The one thing to be careful about is the **boundary**: the long-running work in [#0044](0044.md) runs `nonisolated` on the cooperative pool (`Changeover/RipController.swift:9`, `Changeover/EncodeController.swift:9`), and results come back across an `await`. Because the awaiting code is MainActor-isolated, the resumption lands on MainActor and the subsequent `jobs` mutation is safe. Nothing nonisolated ever holds a reference to `JobQueue` — the controllers take plain path parameters and a `@MainActor (String) -> Void` closure, and that signature must stay that way.

### Ordering and retention

- `jobs` is append-only on enqueue; the array order is creation order and never changes. Display order in [#0048](0048.md) is a sort over that, not a mutation of it.
- Pruning runs after every transition into a terminal stage: while `jobs.filter(\.state.stage.isTerminal).count > finishedJobRetentionLimit`, drop the oldest terminal job. Active jobs are never pruned regardless of count.
- `remove(id:)` refuses a non-terminal job and returns without mutating. Removing a running job would orphan its `Task` and leak its lane token — [#0046](0046.md) handles stopping a running job, and it does so by cancelling it into a terminal stage first.

### Observation correctness

`jobs` is an array of `@Observable` reference types. Two consequences that must be got right or [#0048](0048.md) will be subtly wrong:

- Mutating `job.state` does **not** invalidate readers of `queue.jobs`, because the array itself did not change. That is the desired behaviour — a row observing its own `Job` updates, the list does not. Any derived property on `JobQueue` that reads job state (`active`, `hasActiveJobs`, `snapshot`) therefore *does* re-evaluate for an observer, because reading `job.state` inside the computed property registers a dependency on that job. Verify this rather than assuming it; if `hasActiveJobs` fails to invalidate, [#0047](0047.md) will never release the power assertion.
- Do not cache counts in stored properties kept in sync by hand. A stored `runningCount` that drifts from `jobs` is the classic source of a wedged queue.

### Risks

- **Double ownership.** If Phase 1's `JobController` survives as a separate type holding a current job *and* `JobQueue` holds the same job, they will disagree. Collapse or delegate — do not run both.
- **`AppDelegate.showMetadataEntry()` reuses one window** (`Changeover/AppDelegate.swift:72-76`). With a queue, that window is per-disc, not per-job; it is [#0045](0045.md)'s problem, but do not paper over it here by keying the window off a job.

**Replacement (option A). There is no new store type; `JobController` changes.**

```swift
@Observable final class JobController {
    private(set) var current: Job?                 // #0041
    private(set) var history: [Job] = []           // terminal jobs, oldest first
    static let defaultHistoryLimit = 20
    var isRunning: Bool { current != nil }
    /// Keeps today's semantics: nil while a job runs.
    var lastOutcome: JobOutcome? { current == nil ? history.last?.state.outcome : nil }
    func job(id: JobID) -> Job?
    func clearHistory()
    var snapshots: [JobSnapshot] { get }           // history + current, oldest first
    @discardableResult func start(metadata: MovieMetadata, settings: AppSettings) -> Bool   // unchanged contract
}
```

- **`start`:**
  - keeps both refusal guards (`:95-103`);
  - creates `Job(id: .make(), metadata:, disc: insertedDisc)` and sets `current`;
  - launches the one `Task`, as today.
- **When the runner returns:**
  1. `job.finish(with: outcome)`;
  2. append the job to `history` and prune the oldest while over the limit;
  3. set `current = nil`;
  4. notify, in the existing order (`:117-124`).
- **History limit.** The limit is 20 rather than 50, because each retained job keeps its #0043 `JobLog` (up to 2,000 lines) in memory.
- **The runner seam** passes a per-job context instead of loose values:

```swift
struct JobContext {                                  // MainActor by default, like Runner
    let id: JobID
    let metadata: MovieMetadata
    let disc: URL
    let log: @MainActor (String) -> Void             // appends to job.log (#0043)
    let phase: @MainActor (JobPhase) -> Void         // job.advance(to:)
}
typealias Runner = @MainActor (JobContext, AppSettings) async -> JobOutcome
```

- **`DVDPipeline` reports its phases** through a new `phase: @MainActor (JobPhase) -> Void` property. It defaults to `{ _ in }`, so `EncodeControllerTests` and `MakeMKVFallbackTests` compile unchanged. It is called:
  - with `.encoding` just before `EncodeController.encode` (`DVDPipeline.swift:318`);
  - with `.fallback` in the `.attempt` branch (`:369`);
