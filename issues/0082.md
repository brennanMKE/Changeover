# 0082 — Shared views depend on AppKit APIs that do not exist on iOS

| | |
|---|---|
| **Status** | open |
| **Phase** | 5 — iPhone and iPad clients |
| **Module** | MetadataEntryView / RemoteClient |
| **Platform** | All |
| **First seen** | 2026-09-11 |

## Description

The views the roadmap assumes can be reused on iOS do not compile there. They
reference AppKit-only semantic colors, drive an `NSOpenPanel`, close windows
through `NSApp`, and hard-code macOS window widths. Every one of these needs a
platform-conditional replacement before the iOS target can include them.

## Long Description

`RemoteControl.md` states that `MetadataEntryView` and `MovieSearchViewModel`
"can be shared between the host app and every client nearly unchanged". That is
true of `MovieSearchViewModel` (`Changeover/TMDB/MovieSearchViewModel.swift:4–41`,
pure Observation and Foundation) and of `TMDBClient`
(`Changeover/TMDB/TMDBClient.swift:3–48`, pure `URLSession`). It is not true of
the views.

The concrete blockers, all of which are hard compile errors on iOS rather than
runtime surprises:

| Location | API | Why it fails on iOS |
|---|---|---|
| `Changeover/MetadataEntryView.swift:108` | `Color(.textBackgroundColor)` | `textBackgroundColor` is `NSColor`-only; no UIKit equivalent by that name |
| `Changeover/MetadataEntryView.swift:191` | `Color(.separatorColor)` | `NSColor.separatorColor` vs `UIColor.separator` — different spelling, so the `Color(_:)` initializer does not resolve |
| `Changeover/SettingsView.swift:2` | `import AppKit` | Module does not exist on iOS |
| `Changeover/SettingsView.swift:105–116` | `NSOpenPanel` | No equivalent; iOS uses `.fileImporter` / `UIDocumentPickerViewController`, and picking an arbitrary host filesystem path from a phone is not a meaningful operation at all |
| `Changeover/SettingsView.swift:129–131` | `NSApp.keyWindow?.close()` | No `NSApp`; dismissal is `@Environment(\.dismiss)` |
| `Changeover/StatusMenuView.swift:2, :51` | `import AppKit`, `NSApp.terminate(nil)` | No `NSApp`; iOS apps do not quit themselves |
| `Changeover/AppDelegate.swift:1, :31–37, :42, :78–92, :106–120` | `NSStatusItem`, `NSPopover`, `NSHostingController`, `NSWindow`, `NSHostingView` | Whole file is AppKit; the iOS client needs a `WindowGroup`-based entry point instead |

Two more are not compile errors but are layout defects that make the views
unusable on a phone, and they are cheapest to fix in the same pass:
`.frame(width: 480)` on `MetadataEntryView` (`:22`), `.frame(width: 460)` on
`SettingsView` (`:72`), `.frame(width: 260)` on `StatusMenuView` (`:55`), and
the fixed `.frame(height: 130)` log pane (`MetadataEntryView.swift:109`).

There is also a behavioral dependency that is easy to miss: `MetadataEntryView`
constructs and runs `DVDPipeline` directly (`:142–155`). On a client that is
wrong regardless of platform — the client must send Phase 4's
`RemoteCommand.startRip` instead. Phase 4 should have already addressed this for
the macOS client; if it has not, this ticket is where it surfaces.

## Steps to reproduce

1. Complete [#0081](0081.md) so an iOS destination exists.
2. Add `Changeover/MetadataEntryView.swift` and `Changeover/SettingsView.swift`
   to the iOS client target.
3. Build for `generic/platform=iOS`.

## Expected behavior

The shared search, poster list and log views compile and run on macOS, iOS and
iPadOS from a single copy of each source file, with platform differences
confined to a small, named set of shims.

## Actual behavior

The build fails with unresolved-type errors on `NSOpenPanel`, `NSApp` and
`import AppKit`, and with "type 'Color' has no member" style failures on
`Color(.textBackgroundColor)` and `Color(.separatorColor)`. Even with those
fixed, the views render at a fixed 480pt width on a 393pt-wide iPhone.

## Notes

Do not fix these by sprinkling `#if os(macOS)` through the view bodies. A
conditional inside a `body` is where multiplatform SwiftUI code goes to die —
it makes both platforms harder to read and neither easy to change. Push the
conditionals down into named, single-purpose shims and keep the view bodies
platform-free.

`AppSettings` (`Changeover/AppSettings.swift:13–33`) is a separate question from
the views. Its fields — `plexMediaRoot`, `makemkvconPath`, `handbrakePath` — are
host-machine paths that mean nothing on a phone. The client needs its own
settings type (host identity, pairing state, TMDB key) rather than a
platform-conditional `AppSettings`. `RemoteControl.md` open question 3 ("how
much of Settings should the remote expose?") is still open; this ticket should
not try to settle it, only avoid compiling the host's version into the client.

## Plan

### 1. Audit first, in one pass, and write the result down

Before changing anything, produce the definitive list. The table in Long
Description is the audit as of filing, but Phase 1 through Phase 4 will have
edited these files — `MetadataEntryView` in particular loses its `@State`
pipeline ownership in Phase 1. Re-run the audit:

```
grep -rn 'NSOpenPanel\|NSApp\|NSWindow\|NSImage\|NSHostingView\|NSHostingController\|NSStatusItem\|NSPopover\|NSColor\|import AppKit' \
  Changeover ChangeoverUI ChangeoverProtocol 'Changeover Remote'
grep -rn 'Color(\.' Changeover ChangeoverUI 'Changeover Remote'
grep -rn '\.frame(width:' Changeover ChangeoverUI 'Changeover Remote'
```

The `Color(.` grep is the one that catches the silent cases — `Color(.textBackgroundColor)`
and `Color(.separatorColor)` read as platform-neutral SwiftUI and are not.

### 2. Add one shim file, not conditionals in view bodies

Create `ChangeoverUI/Sources/ChangeoverUI/PlatformColor.swift` (or equivalent in
whatever package [#0081](0081.md) settled on) holding a small enum of semantic
colors used by the shared views:

- A `logBackground` replacing `Color(.textBackgroundColor)`
  (`MetadataEntryView.swift:108`) — `NSColor.textBackgroundColor` on macOS,
  `UIColor.secondarySystemBackground` on iOS.
- A `hairline` replacing `Color(.separatorColor)`
  (`MetadataEntryView.swift:191`) — `NSColor.separatorColor` on macOS,
  `UIColor.separator` on iOS.

One `#if canImport(AppKit)` / `#elseif canImport(UIKit)` block in that one file.
The call sites become `Color.logBackground` and `Color.hairline` and stop being
platform-aware. `canImport` rather than `os(macOS)` because it also does the
right thing for Catalyst and for any future destination.

### 3. Delete the fixed widths from the shared views

`MetadataEntryView.swift:22` (`.frame(width: 480)`) is the single most
consequential line in this ticket: it is what makes the view a macOS window
rather than a view. Remove it from the shared view entirely and apply a width
constraint at the **macOS call site** instead — the `NSWindow` in
`AppDelegate.showMetadataEntry()` already sets a 480×580 content rect
(`Changeover/AppDelegate.swift:78–83`), so the window is already doing the job
and the view modifier is redundant on macOS as well as harmful on iOS.

Same treatment for the log pane's `.frame(height: 130)` (`:109`) and the results
list's `.frame(minHeight: 220)` (`:68`) — those become `.frame(maxHeight:)` or
`.layoutPriority` decisions made by [#0083](0083.md), not fixed points.

Leave `StatusMenuView.swift:55` (`.frame(width: 260)`) alone: that view is a
macOS menu bar popover and is not shared. Same for `SettingsView.swift:72`
unless the client reuses the settings screen, which per Notes it should not.

### 4. Split `MetadataEntryView` along the host/client seam

The view mixes three responsibilities that need to separate anyway:

1. **Search + results + poster list** (`:30–69`, `:160–201`) — genuinely shared.
   Extract into a `MovieSearchView` in the shared package. It owns its
   `MovieSearchViewModel` with `@State` (`:5`), per the project convention — not
   `@StateObject`, which does not apply to `@Observable` types at all.
2. **Folder-name preview** (`:73–89`) — shared, and pure. It calls
   `MovieMetadata.folderName` / `.fileName`
   (`Changeover/MovieMetadata.swift:17–24`), both `nonisolated` and portable.
3. **Log pane** (`:93–119`) — shared in shape, but the log source differs: local
   `@State logLines` on the host, streamed `RemoteEvent.log` on the client.
   Extract as `LogPaneView(lines: [String])` taking the lines as a parameter so
   both callers can supply them. The `ScrollViewReader` auto-scroll at `:110–114`
   works identically on both platforms.

The action bar (`:123–133`) and `startRipping()` (`:142–155`) stay behind as
host-specific, because `startRipping()` constructs `DVDPipeline` directly
(`:149`) and that is a host-only capability.

Pass the search view model down with `@Bindable` where a child needs bindings
into it — never `@ObservedObject`, which does not exist in this codebase.

### 5. `SettingsView` is not shared — do not try

`Changeover/SettingsView.swift` should stay in the host target unchanged,
AppKit import and all. `NSOpenPanel` (`:105–116`) picks a folder **on the
machine that has the SSD attached**; there is no sensible iOS translation, and
`.fileImporter` on a phone would pick a path on the phone. The iOS client gets
its own small settings screen (host selection, pairing state, TMDB key) built in
[#0088](0088.md) and [#0089](0089.md). The only thing worth extracting is the
TMDB API key field (`:46–60`), since the client does its own TMDB search per
`RemoteControl.md`.

### 6. Ordering and risk

Bring files into the iOS target one at a time, building after each: shim file →
`MovieSearchView` → folder preview → `LogPaneView`. A single big-bang move
produces a hundred errors at once and no signal about which change caused which.

The real risk is **scope creep into layout**. This ticket's exit condition is
"compiles and runs on iOS", not "looks right on iOS". A 480pt-wide layout
squeezed onto a phone is an acceptable output of this ticket; [#0083](0083.md)
fixes it. Resist doing both at once — if this ticket bounces on review, it
should bounce for a missed AppKit dependency, not for a layout opinion.

### 7. Verification

```
xcodebuild -project Changeover.xcodeproj -scheme 'Changeover Remote' -destination 'generic/platform=iOS' build
xcodebuild -project Changeover.xcodeproj -scheme 'Changeover Remote' -destination 'platform=macOS' build
xcodebuild -project Changeover.xcodeproj -scheme Changeover -destination 'platform=macOS' build
xcodebuild -project Changeover.xcodeproj -scheme Changeover -destination 'platform=macOS' test
```

Buildability is genuinely provable here and is most of the ticket. Beyond the
build: run the client in an iPhone simulator and confirm a TMDB search returns
posters — that exercises `TMDBClient` and `AsyncImage`
(`MetadataEntryView.swift:180–198`) on iOS over plain HTTPS with no host
involved, so no device and no Mac mini are needed. Confirm the host app's
metadata window is visually unchanged after the fixed-width move; that is a
manual check and should be stated as manual.
