# 0016 — Deinterlace and detelecine are not driven by the scan, and adding --detelecine unconditionally would corrupt a soft-telecined disc

| | |
|---|---|
| **Status** | open |
| **Phase** | 1 — Trustworthy single-disc rip |
| **Module** | EncodeController / Config |
| **Platform** | macOS |
| **First seen** | 2026-09-11 |

## Description

`EncodeController` passes no `--decomb`, no `--deinterlace` and no `--detelecine` (`EncodeController.swift:25-33`), so an interlaced or hard-telecined disc is encoded with its combing intact. The naive fix — adding `--detelecine` to the argument list — is **wrong**, and provably so: *Fargo* scans as `23.976 fps, InterlaceDetected: false`, meaning it is soft telecine already resolved from the MPEG-2 pulldown flags, and a filter there would fix a problem that does not exist. The decision must be driven by the scan's `InterlaceDetected` and `FrameRate`.

## Long Description

This is step 3 of `MakeMKVReplacement-Path.md` §3, and it exists as its own ticket because both earlier documents in the series got the underlying fact wrong.

From `MakeMKVReplacement-Results.md` §6, measured on the actual disc:

> **Fargo is soft telecine, not hard.** Scan reports `23.976 fps` and `InterlaceDetected: false`; MakeMKV reported 29.97. HandBrake reads the MPEG-2 pulldown flags and resolves to native film rate. Both earlier documents describe this disc as hard-telecined — including the findings document's §5 argument against ffmpeg, which rests on that premise.

And the filter chain HandBrake actually built for the verified encode contained **no deinterlacer, correctly**:

```
+ Framerate Shaper (mode=0)
+ Crop and Scale (width=712:height=472:crop-top=0:crop-bottom=8:crop-left=8:crop-right=0)
```

The MakeMKV-reported 29.97 is the reason this is a trap rather than a footnote. Anyone reasoning from the old pipeline's numbers — or from the two earlier documents — concludes the disc is 29.97 hard telecine and reaches for `--detelecine`. Applying an inverse-telecine filter to a stream that is already at native film rate does not "fix" anything; it puts a pattern-matching filter in front of content that has no 3:2 pattern, with the risk of dropped or duplicated frames and judder that was not there before.

`-Results.md` §6 states the rule directly: *"never add `--detelecine` unconditionally."* `-Findings.md` §7 step 4 mentions driving it from `InterlaceDetected` and `FrameRate` as an aside — the results document's correction is that **the aside is the rule**.

Meanwhile the real gap is untouched: a genuinely interlaced disc (a concert film, a TV-sourced disc, anything at 29.97 with `InterlaceDetected: true`) gets no filter at all today and is encoded combed. Both halves of this ticket are the same decision, made from the same two fields.

## Steps to reproduce

**The gap:**

1. Rip an interlaced NTSC disc — 29.97 fps, genuinely interlaced rather than telecined.
2. Play the resulting `.mp4` and look at any horizontal motion.
3. Combing artefacts are present. No deinterlace filter was applied because none is ever requested.

**The trap (do not ship this):**

1. Add `--detelecine` to `process.arguments` in `EncodeController.swift`.
2. Encode Fargo, which scans as 23.976 fps with `InterlaceDetected: false`.
3. An inverse-telecine filter now runs over a stream with no telecine pattern.

## Expected behavior

The scan decides. `InterlaceDetected` and `FrameRate` from `HandBrakeCLI --scan --title 0 --min-duration 1 --json` determine whether any filter is applied and which one:

- `InterlaceDetected: false` at 23.976 → **no filter**. Soft telecine already resolved, or native progressive film.
- `InterlaceDetected: true` at 29.97 → hard telecine or true interlace. Distinguish, then apply `--detelecine` or `--decomb` accordingly.
- Anything ambiguous → prefer no filter and log the scan values, so a bad call is diagnosable from the log rather than from the output file.

## Actual behavior

No filter is ever requested. The argument vector is a fixed list (`EncodeController.swift:25-33`) with no scan input at all, and `Config` carries only `videoQuality` and `audioEncoder` — nothing about filtering.

## Notes

The decision function is a pure function of two scan fields and is exactly the kind of thing that should carry real unit tests with no disc attached: feed it `(23.976, false)`, `(29.97, true)`, `(29.97, false)`, `(25.0, true)` and assert the chosen filter. Fargo's actual values are a fixture with a documented provenance — use them.

What is **not** testable without discs: whether the classification is correct in the ambiguous middle. `-Results.md` only measured one disc. Treat any rule beyond "no filter when `InterlaceDetected` is false at film rate" as provisional and say so in `## Verification`, naming every disc actually exercised.

This ticket needs the scan to exist. Until [#0014](0014.md) and the HandBrake scanner land, there is no `InterlaceDetected` to read — which is why it is filed as its own ticket rather than folded into the argument vector rewrite. Do not implement it by shelling out to a second scan inside `EncodeController`; the scan result should be passed in, the way the title number is.

`--decomb` and `--detelecine` are not interchangeable. `--decomb` adaptively deinterlaces; `--detelecine` inverse-telecines a 3:2 pattern back to 23.976. Applying the wrong one is its own defect.

## Plan

### Where the decision lives

A small `nonisolated` pure function — given the scanned title's `FrameRate` and `InterlaceDetected`, return an enum (`none` / `decomb` / `detelecine`) — living beside `Config` or in the disc-model file, and marked `nonisolated` so `EncodeController` can call it (`CLAUDE.md`: anything the nonisolated controllers touch must itself be nonisolated, as `Config`'s statics already are).

`EncodeController.encode` takes the resulting value as a parameter, appends at most one filter flag, and does nothing else differently. Do not have the controller read a scan, a settings object, or a global.

### What to log

Log the two scan values and the chosen filter on every encode, at the point the decision is made. When a disc comes out wrong, that line is the difference between a diagnosis and a guess — and it is also how the rule gets refined as more discs go through.

### Risks

- **Do not trust MakeMKV's frame rate for this.** It reported 29.97 for a disc HandBrake correctly resolved to 23.976. If any fallback path ([#0015](0015.md)) produces an intermediate file, the interlace decision must come from HandBrake's own scan of that file, not from the disc's MakeMKV metadata.
- **`InterlaceDetected` is a heuristic over sampled frames, not a certainty.** A disc with a short interlaced intro and a progressive feature can report either. Prefer the conservative answer and keep the log line.
- **Resist adding a user-facing override in this ticket.** A Settings checkbox for "deinterlace" invites the exact unconditional application this ticket exists to prevent. If an override is genuinely wanted later, make it per-disc and make the scan's answer the default.
