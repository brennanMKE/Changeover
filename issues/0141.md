# 0141 — A finished job could not unmount the disc, and the failure is only a log line

| | |
|---|---|
| **Status** | open |
| **Phase** | 3 — Unattended multi-disc |
| **Module** | DiscEjector / DVDPipeline |
| **Platform** | macOS |
| **First seen** | 2026-09-16 |

## Description

Seen on joe (2026-09-16) at the end of the Hornet's Nest job, in the app's own log:

```
✓ Moved to: /Volumes/Media/Media/Movies/The Girl Who Kicked the Hornet's Nest (2009) {tmdb-33613}/…
✓ Produced by: HandBrake, direct from disc
⚠ Could not unmount the disc: status -119930872
— Done. Scan your Plex Movies library to pick up the new title.
```

The job succeeded and the file is correct, but the disc stayed mounted in the drive. `-119930872` is a DiskArbitration dissenter status, which normally means a process still holds the volume — a plausible culprit here is Plex or Spotlight indexing the freshly written library, or HandBrake's own file handles not yet closed.

#0049 handles "unmounted but not ejected". This is the other half: the unmount itself is refused, so the disc never ejects, and the only signal is one warning line the user has to notice.

## Triage notes (2026-09-25)

**Stays open. One of the three Expected items is met, two are partial, and the
literal line in the bug report can still be produced.** Checked against
`HEAD` = 97a226f.

**Item 1 — "retried a few times with a short backoff" — MET, and more generously
than asked.** `DiscEjector.retryDelays` (`Changeover/DiscEjector.swift:85-88`) is
`[500ms, 1s, 2s, 4s, 6s, 8s, 8s]` — about thirty seconds — consumed by
`attempting(_:retryDelays:sleep:step:)`, which retries **only** a busy answer and
treats `.failed` as a settled no. `sleep` is injected so the policy is tested at
full speed. Landed in ee65ffa ("Keep asking when the drive says the disc is
busy") and b653fc3 ("Keep asking diskutil, because a dissent is temporary"). The
doc comment even gives this ticket's own reasoning back: "The moment this runs is
when a real 'busy' is most likely — HandBrake has just closed a file it read for
forty minutes."

**Item 2 — "says so where the user will see it … and offers Eject" — PARTIAL, and
this is the genuine movement since the last sweep.** `JobNotifier` now takes
`discWasEjected: Bool?` and appends " The disc is still in the drive." to the
success banner when the eject demonstrably failed
(`JobNotifier.swift:161-163`), fed by `Job.recordEject(succeeded: outcome ==
.ejected)` at `JobController.swift:771` (commit 2df608b, "Stop the notification
claiming the disc was ejected when it was not"). That is a real, off-log,
user-visible signal and it did not exist before.

What it does **not** do is carry the *reason* or offer the action. In
`JobController`'s eject-outcome switch, `.busy` and `.failed` do exactly one thing
each — `append("⚠︎ \(message)")` (`JobController.swift:906-913`) — and
`applyAutomaticEject` is `guard case .unmountedButNotEjected` at `:935`, so
**this ticket's case sets no state at all**: no `discUnavailable`, no status-menu
text, no tooltip on the manual Eject item. The notification says the disc is still
there; nothing anywhere says why, and the Plan's "leave the manual Eject item
enabled with the reason as its tooltip" is unimplemented.

**Item 3 — "human-readable reason, not a raw negative status code" — PARTIAL, and
the reported failure is still reproducible.**
`DiscEjector.classify(status:statusString:action:)` (`:636-643`) is:

```swift
let reason = statusString ?? "status \(status)"
if status == DAReturn(kDAReturnBusy) || status == DAReturn(kDAReturnExclusiveAccess) {
    return .busy(message: "Could not \(action) the disc — it's still in use: \(reason).")
}
return .failed(message: "Could not \(action) the disc: \(reason).")
```

The Plan asks for a `kDAReturn*` → readable-text lookup with a default. There is
none: only `kDAReturnBusy` and `kDAReturnExclusiveAccess` are matched by value,
and `kDAReturnNotPermitted` appears only in comments and in one
`text.contains("\(kDAReturnNotPermitted)")` string check at `:320`. When the
dissenter supplies no status string — which is precisely the case that produced
`⚠ Could not unmount the disc: status -119930872` in this report — the raw number
still reaches the user verbatim.

**What would close this ticket.** A `kDAReturn*` lookup table so `classify` never
falls back to a bare integer, and threading `.busy`/`.failed` into the same state
`.unmountedButNotEjected` already sets, so the Eject item's tooltip and the status
menu can name the reason. The retry half is done and does not need revisiting.

**Still manually unverified**, as the Plan says: the real case needs a disc on joe
whose unmount is refused. Nothing in this sweep touched hardware.

## Expected behavior

- A failed unmount is retried a few times with a short backoff, since the usual cause is transient.
- If it still fails, the app says so where the user will see it — the completion notification or the status menu — not only in the log, and offers Eject.
- The reported reason is human-readable, not a raw negative status code.

## Plan

- Map the common DiskArbitration dissenter statuses to readable text (busy, in use by another process, not permitted) rather than printing the raw number. `kDAReturn*` codes are an enum, so this is a lookup with a default.
- Retry the unmount on a busy status, e.g. 3 attempts with a growing delay, before reporting failure. Put the retry policy in a pure, testable value.
- Reflect the outcome where it is visible: include it in the completion notification's text, and leave the manual Eject item enabled with the reason as its tooltip.
- Consider whether the disc should be marked unavailable (#0049's `discUnavailable`) — probably not, since it is still mounted and readable; record the reasoning.
- Unit-test with a fake ejector returning each status; the real case needs a disc on joe and is manually unverified.
