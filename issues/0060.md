## Description

Every step of the disc loop that needs a screen — TMDB search, poster confirmation, title and track selection, watching the rip — can only be done sitting at the Mac mini. This umbrella covers Phase 4 of `Roadmap.md`: a shared protocol package, a LAN transport with real pairing and authorization, a host-side `RemoteServer`, and a `Changeover Remote` macOS client that drives the whole loop from the MacBook Air.

## Long Description

`RemoteControl.md` makes the case precisely: inserting a disc is a fifteen-second
errand that cannot be automated away, but the *decision* steps around it are slow,
need attention, and are exactly the ones that do not need to happen next to the
drive. The product shape is a **disc triage console** — the mini owns discs, CLI
tools and the media volume; the remote owns judgement.

Phase 4 is the largest phase in the roadmap because it is the only one that adds
a second process, a wire format, a trust boundary and a second app target all at
once. It is also the phase where the app stops being single-user software: a
remote client can start rips and therefore **write into the user's media
library**, so pairing and per-peer authorization are load-bearing, not polish.

Two structural decisions from `RemoteControl.md` shape the whole phase and are
carried into individual tickets so they do not get lost:

1. **The transport is built against `Network.ListenerProvider` /
   `Network.BrowserProvider` abstractions, not against Bonjour concretely.**
   `WAPublisherListener` and `WASubscriberBrowser` conform to those same
   protocols. Wi-Fi Aware ships on macOS today but every public symbol carries
   `@available(macOS, unavailable)` (28 annotations in the `MacOSX26.5.sdk`
   module interface, enforced by the compiler). If Apple lifts that gate, adding
   Wi-Fi Aware should be a provider swap plus a pairing UI, not a rewrite.
2. **Two pairing modes ship together.** Mode A (iCloud `NSUbiquitousKeyValueStore`,
   same Apple ID, zero-config) is the pleasant default. Mode B (six-digit PIN) is
   **not optional** — this app is intended for general release, and a household on
   several Apple IDs, or a user not signed into iCloud, must still be able to pair.

This umbrella depends on all three earlier phases: [#0001](0001.md) extracts the
`@Observable JobController` that the server fans out (no remote design of any kind
is possible before that), [#0020](0020.md) produces the `DiscInfo` / `DiscTitle` /
`DiscStream` models the protocol carries, and [#0040](0040.md) introduces the
stable job IDs the protocol addresses jobs by.

## Steps to reproduce

1. Sit down on the couch with a MacBook Air on the same Wi-Fi as the Mac mini.
2. Walk over, insert a DVD into the mini, walk back.
3. Try to search TMDB, pick the poster, choose the main feature, and start the rip
   from the MacBook.

## Expected behavior

The disc appears on the MacBook with its title list already scanned. TMDB search
runs locally on the laptop; only the chosen result is sent to the mini. The rip and
encode log streams live. On completion the disc ejects across the room and the
laptop notifies. Quitting and relaunching the client reconnects and re-syncs
mid-job.

## Actual behavior

There is no network surface at all. The only way to drive the loop is Screen
Sharing into the mini, which is what this phase exists to replace.

## Plan

This umbrella is not implemented directly — it is closed when its children are. What
it owns is **sequencing**, because Phase 4's dependency graph is the deepest in the
roadmap and several tickets are cheap to start and expensive to reorder.

**Wave 0 — decisions and spikes. Start these first; they are small, they are
blocking, and two of them may change the shape of the phase.**

- [#0063](0063.md) — verify the `NetworkListener` Bonjour advertisement API against
  the installed SDK. If it comes back "legacy `NWListener` only", [#0062](0062.md)
  grows a bridge.
- [#0064](0064.md) — choose the transport security mechanism. Blocks four tickets.
- [#0065](0065.md) step 1 — prove (or disprove) that an unsandboxed Developer ID
  build can provision an iCloud KVS container. If it cannot, Mode A is dead and
  [#0066](0066.md) becomes the only pairing path, which changes its UX priority.
- [#0074](0074.md) — land the Info.plist keys before anything listens, so the rest of
  the phase is not debugged against an unknown TCC state.

**Wave 1 — foundations.** [#0061](0061.md) then [#0062](0062.md). Build the
`InMemoryTransport` fake in [#0062](0062.md) early: every ticket from here on is
unit-testable against it with no network, no second machine and no disc, and skipping
it is what would make this phase untestable.

**Wave 2 — trust.** [#0066](0066.md) and [#0065](0065.md) in parallel, then
[#0067](0067.md), which both feed.

**Wave 3 — the host.** [#0068](0068.md), then [#0069](0069.md) and [#0070](0070.md).
[#0070](0070.md) is not optional hardening — it is what stops a client-supplied movie
title from writing outside the Plex library.

**Wave 4 — the client.** [#0071](0071.md), then [#0072](0072.md) and
[#0073](0073.md).

**The hard prerequisite outside this phase** is [#0001](0001.md). Pipeline state
lives in `MetadataEntryView` as `@State` today
(`Changeover/MetadataEntryView.swift:7-8`, `:142-155`); until an `@Observable
JobController` exists and `AppDelegate` owns it, there is nothing for
[#0068](0068.md) to fan out. Two smaller couplings are worth raising with the other
phases *now* rather than discovering later:

1. [#0001](0001.md) should expose an `AsyncStream<JobEvent>` alongside its
   `@Observable` surface. SwiftUI and the network want different things from the same
   source of truth, and retrofitting the stream means touching every mutation point
   twice.
2. [#0020](0020.md) should author `DiscInfo` / `DiscTitle` / `DiscStream` **directly
   in the `ChangeoverProtocol` package**, and [#0020](0020.md)'s title picker directly
   in `ChangeoverUI`, rather than in the app target to be moved in
   [#0061](0061.md) and [#0073](0073.md).

**Convention constraints that apply to every child.** `@Observable` from
`Observation`, never `ObservableObject`/`@Published`/`@StateObject`/`@ObservedObject`;
view models owned with `@State`; `@Bindable` for bindings from `@Observable` values
passed in. One phase-specific wrinkle: `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`
(`Changeover.xcodeproj/project.pbxproj:416`, `:445`) is a **target** setting, so the
new Swift package does **not** inherit it. Wire types there must be explicitly
`Sendable`, `RemoteSession` must be explicitly `@MainActor`, and the connection-state
types are the rare legitimate use of `actor` in this project — `Plan.md` otherwise
rules it out, so every such use needs a comment saying why.

## Demo

> Insert a disc at the mini and walk across the room. On the MacBook, the disc
> appears with its title list already scanned. Search TMDB, confirm the poster,
> choose the title and tracks, hit Start. Watch the rip and encode log stream
> live. When it finishes, the disc ejects across the room and the laptop
> notifies. Then quit and relaunch the client to show it reconnects and
> re-syncs mid-job.

## Exit criteria

- Full loop driven from a second Mac with no Screen Sharing.
- Client survives host restart, Wi-Fi drop and laptop sleep, and resyncs mid-job.
- Two connected clients cannot start conflicting jobs; the loser is told why.
- An unpaired device on the same network cannot control the host, and a paired
  device can be revoked from the host without restarting it.
- A peer with observe-only capability cannot start, cancel or eject.
- A malformed or hostile `RipRequest` cannot cause a write outside
  `AppSettings.plexMoviesPath`.
- Both pairing modes work: Mode A on one Apple ID, Mode B between two Apple IDs.
- The protocol codec, pairing key derivation and command-validation state machine
  have real unit tests that run in `ChangeoverTests`.

## Notes

**Verification split for the whole phase.** Per the build/verify caveat in
`issues/Issues.md`, a green build is not verification for anything in the rip
path. For Phase 4 the split is unusually clean and every child ticket restates
its own half:

- **Unit-testable with no hardware and no second machine:** the `Codable` round
  trip and framing, unknown-case tolerance, decoder limits, PIN key derivation,
  peer-record encode/decode, capability checks, `RipRequest` path validation, the
  command-validity state machine, reconnect backoff arithmetic.
- **Requires two real machines on one LAN:** Bonjour advertisement and discovery,
  the TLS handshake, the Local Network permission prompt, reconnect after wake,
  multi-client arbitration under a real running job.

`ChangeoverTests/ChangeoverTests.swift` is the existing test target; Phase 4 is
the first phase with a large body of genuinely testable logic, so this is where
the test suite should stop being a stub.

**Out of scope for Phase 4, deliberately:** off-LAN control (no use case — the
user has to be in the house to swap discs), the HTTP + SSE web fallback, the
`changeover` CLI over a Unix socket, and Wi-Fi Aware itself (blocked on Apple;
ER FB17988268). Remote editing of Settings is also out of scope — see
[#0070](0070.md), which fixes that as a protocol-level rule rather than leaving
it as an open question.
