## Description

The file produced by the direct `VIDEO_TS` → MP4 encode has never been played in Plex. Two properties of the verified output are known problems: it carries a `bin_data` stream at index 3 — the VOBSUB track pulled in by `--subtitle scan`, and **VOBSUB in MP4 is poorly supported** — and `ffprobe` reports a container timebase of `r_frame_rate=120/1`, an artefact of VFR output. The test file exists at `/tmp/fargo-direct.mp4` on `joe`. **This gates [#0014](0014.md)**, which is the commit point of the whole MakeMKV replacement.

## Long Description

From `MakeMKVReplacement-Results.md` §6, "Two output details to check against Plex":

> - Container timebase reports `r_frame_rate=120/1` — an artifact of VFR (Framerate Shaper mode=0), not a real 120 fps. Consider whether CFR output is preferable for Plex/Apple TV.
> - A `bin_data` stream (index 3) is present — the VOBSUB track from `--subtitle scan`. **VOBSUB in MP4 is poorly supported.** Given `check_mp4_compatibility.sh` and `diagnosing_mp_4_files_for_plex_apple_tv.md` already exist in `/Volumes/Media/Plex`, this has bitten before. Verify playback before trusting the output.

That last sentence is the reason this is a ticket rather than a note. **Those two files already exist on the Plex volume.** Someone wrote a compatibility checker and a diagnosis document for MP4 files that Plex or an Apple TV client would not play — which means this class of problem has cost time on this exact setup before, and the new pipeline is producing a file with two of the known markers on it.

Neither marker is proof of a problem:

- `r_frame_rate=120/1` is a container-level artefact of variable frame rate output, not a claim that the video is 120 fps. Many players handle it. Some direct-play paths on an Apple TV do not, and fall back to transcoding — which on a Plex server is a silent performance regression rather than a visible failure, and is exactly the sort of thing a compatibility script gets written for.
- `bin_data` is how `ffprobe` describes a VOBSUB (bitmap) subtitle track muxed into MP4. MP4's subtitle support is aimed at text formats; bitmap subtitles are carried, but client support varies and Plex's handling is inconsistent. The track exists because `--subtitle scan` was passed (`EncodeController.swift:31`).

The two are linked to the same argument list, and both have a cheap way out — dropping `--subtitle scan` removes the `bin_data` stream and halves the encode's wall clock ([#0014](0014.md), `-Results.md` §6), and a CFR flag removes the `120/1` timebase. What is missing is the evidence to say whether either is actually needed.

Also worth carrying forward: the same run logged `ERROR: unable to decode subtitle with 2019 bytes.` during the subtitle scan. Non-fatal — the encode continued and completed — but it is the disc-quirk class appearing on the very first disc tested, and it originates in the same subtitle pass.

## Steps to reproduce

1. On `joe`, `ffprobe /tmp/fargo-direct.mp4` and read the stream list: stream 3 is `bin_data`; the video stream reports `r_frame_rate=120/1`.
2. Copy the file into the Plex library (or point Plex at it) and play it — on the Apple TV client specifically, not only on a desktop browser.
3. Check the Plex dashboard while it plays: is it direct play, direct stream, or transcode?
4. Enable subtitles and see whether the VOBSUB track is offered and whether it renders.

## Expected behavior

The pipeline's output direct-plays on the clients this library is actually used from, with correct chapter navigation and working subtitles — or the encode arguments are changed until it does. Whichever way it goes, the answer is recorded, because it determines the default argument vector [#0014](0014.md) ships with.

## Plan

1. **Run the existing checker first.** `/Volumes/Media/Plex/check_mp4_compatibility.sh /tmp/fargo-direct.mp4`, and read `diagnosing_mp_4_files_for_plex_apple_tv.md`. Record what it reports verbatim in this issue, including the comparison against a file from the existing library.
2. **Play it through Plex**, on the Apple TV client. Watch the Plex dashboard for direct play vs. transcode. Check chapter navigation (36 chapters were preserved) and subtitle rendering.
3. **If subtitles are the problem**, re-encode without `--subtitle scan` and re-test. This is also the [#0014](0014.md) performance decision — the flag runs a complete extra pass and was roughly half of Fargo's 21m44s.
4. **If the timebase is the problem**, re-encode with constant frame rate and re-test. Note the result against [#0016](0016.md), since both touch the filter chain.
5. **Write the conclusion into [#0014](0014.md)'s argument vector** as the shipped default, with this issue cited as the evidence. An undocumented flag choice is how the next person re-derives all of this.

### Risks

- **"It plays on my Mac" is not the test.** Desktop Plex clients transcode far more willingly than an Apple TV. Test on the client the library is actually watched from.
- **A silent transcode is the likely failure mode**, not a refusal to play. Read the dashboard; do not judge by whether a picture appears.
- **Do not fix this by dropping subtitles without checking**, and do not keep them without checking either. Both defaults have a real cost and the point of this ticket is to pay for the evidence once.

## Correction — the `bin_data` stream is the chapter track, not VOBSUB — 2026-09-12

This issue's title and description treat the `bin_data` stream as a VOBSUB
subtitle track produced by `--subtitle scan`. **It is not.** `ffprobe` reports
`codec_tag_string=text` (`0x74786574`) — a QuickTime chapter text track written
by `--markers`:

| File | Stream | Tag | Frames | Chapters |
|---|---|---|---|---|
| Fargo, existing library copy (February, old workflow) | 2 | `text` | 36 | 36 |
| Dragon Tattoo, #0014 shipped vector, no `--subtitle` flag at all | 3 | `text` | 16 | 16 |

It is the chapter markers: standard in MP4, and present in files Plex has served
for months. It is not a compatibility risk and must not be stripped — doing so
would remove chapters.

Together with the earlier finding that the VFR `120/1` timebase is also present in
the working library, **both of this issue's original concerns are resolved as
non-issues.** What remains open is Plex direct play versus transcode, which now
only matters for the HEVC output #0018 introduces — test it with an x265 file.

The misidentification originated in `MakeMKVReplacement-Results.md` §6 and spread
into this issue, #0014's plan and #0018.
