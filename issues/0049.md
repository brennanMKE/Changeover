## Description

Found in the #0045 review and deferred by #0046. `DiscEjector` unmounts and then ejects. If the unmount succeeds but the eject fails (the drive refuses, or the tray is jammed), the disc sits unmounted in the drive. DiskArbitration fires no removal, so `jobs.insertedDisc` and `scanState` still point at the old mount path. Once `isEjecting` clears on the failure, Start and Rescan come back live against a path that no longer exists. They then fail with confusing scan or encode errors instead of saying the disc is unmounted.

## Resolution notes

> 🟢 Resolved 2026-09-15 — A partial eject, whether from the manual Eject row or the #0005 automatic end-of-job eject, now marks the disc unavailable, so Start, Rescan and Retry refuse with a stated reason while Eject stays offered; a successful eject, a removal, a new insertion or an in-place remount of the same disc clears it (4db0e8d, review fix 738cfc4).

**Review (2026-09-15, claude-opus-5).** 4db0e8d was in scope, and its `combine` mapping, `discUnavailable` flag and refusals were right. Three things were wrong or missing. 738cfc4 fixes them:

1. **The automatic end-of-job eject stayed log-only.** That is the most common eject path, and a partial eject there left Start, Rescan and Retry live against the dead path: the bug this issue exists to fix. The draft said no back-channel existed, but #0042's `JobContext` is exactly that channel. `JobContext` gains `eject`, which `start` binds to the controller's own `ejector` seam. It applies the outcome through `applyAutomaticEject`, which sets `discUnavailable` on `.unmountedButNotEjected` when the mount URL matches `insertedDisc`. `DVDPipeline` gains an injectable `eject` (default: the real `DiscEjector`), and `pipelineRunner` passes `context.eject`. The pipeline no longer calls `DiscEjector` directly.
2. **A remount in place could leave the flag set.** A disc left unmounted and then remounted without leaving the drive (e.g. from Disk Utility) produces `DVDMonitor`'s `.sameDiscRemounted`, never a removal or insertion. So nothing cleared `discUnavailable`, and Start stayed refused against a live disc until the user ejected it. `DVDMonitor` now reports that case through `onDVDRemounted`, and `AppDelegate` forwards it to `JobController.discRemounted(_:)`. That method clears the flag only for the same disc by identity, takes the new mount path and keeps the original `insertionID`, so the movie selection bound to it still matches. It does nothing while the disc is available, since the same callback fires for ordinary description changes.
3. **The partial-eject message didn't say what happened.** From the manual Eject row, `combine` passed the eject step's own message through ("Could not eject the disc: …"), which doesn't say that the disc was unmounted. It now reads "The disc was unmounted but not ejected — it's still in the drive. <eject message>". Both eject paths log that as-is. The Start button also gained a tooltip naming the reason, matching Rescan.

The skipped mount-path-exists backstop stays skipped. With both eject paths and the remount path now wired, the only way left to get a dead path is an external unmount (e.g. `diskutil unmount`). A `pathExists` seam would touch every fake-path test to cover that. Filing it as a follow-up is reasonable if it ever occurs; it isn't needed here.

**Manual checks owed on joe** (a real drive and disc; a partial eject can't be simulated):

- **Manual Eject, partial.** Hold the tray closed at eject, if the drive allows it. Start (with its tooltip), Rescan (with its tooltip) and Retry in the history window must all refuse. "Eject Disc" must stay enabled, and retrying it once the drive releases must open the tray and clear the refusal.
- **Automatic end-of-job eject, partial.** Same setup at the end of a real job: the job still succeeds, its log shows the unmounted-not-ejected line, and the same three refusals follow.
- **Remount in place.** After a partial eject, mount the disc again from Disk Utility. The log shows "Disc remounted at …", the refusals clear, and Start encodes from the new mount path.
- **No false remounts.** During an ordinary session with a mounted disc, "Disc remounted" never appears in the log.

## Root cause

`DiscEjector.eject(volumeURL:)` ran the unmount and the eject as two separate calls (`DADiskUnmount`, then `DADiskEject`), classified each one with the same `classify(status:statusString:action:)`, and returned whichever ran last. A failed eject after a successful unmount therefore came back as a plain `.busy` or `.failed`. That is the same shape as an *unmount* failure, which leaves the disc mounted and untouched. Nothing distinguished "nothing happened" from "the disc is now unmounted but still in the drive".

DiskArbitration will never report that mount path as removed. Only media actually disappearing fires `DVDMonitor`'s disk-disappeared callback. An unmount alone reaches only the description-changed callback, which ignores a disc with no volume path (the mechanism the #0045 review diagnosed for the mid-scan case). `JobController.ejectDisc()` cleared `isEjecting` on every failure alike, and neither `start`, `startScan` nor `JobPresentation.retryDecision` could learn that the disc it still named was gone. The #0005 automatic eject in `DVDPipeline` had no path to controller state at all.

## Fix

**`DiscEjector.swift`.** `Outcome` gains a third case, `.unmountedButNotEjected(message:)`. A new pure `combine(unmountOutcome:ejectOutcome:)` (no DiskArbitration calls, tested directly) maps the two steps:

- **Unmount failed:** its outcome (`.busy` or `.failed`, disc still mounted) passes through unchanged.
- **Unmount succeeded, eject succeeded:** `.ejected`.
- **Unmount succeeded, eject busy or failed:** `.unmountedButNotEjected`. Its message starts "The disc was unmounted but not ejected — it's still in the drive." and then gives the eject step's own message (review fix).

`eject(volumeURL:onBegin:)` routes through `combine`.

**`JobController.swift`** gains `private(set) var discUnavailable`:

- **Set** on `.unmountedButNotEjected` from the manual `ejectDisc()`. `isEjecting` clears so Eject can be retried. It is also set from the automatic end-of-job eject via `JobContext.eject` and `applyAutomaticEject` (review fix).
- **Read** by `start` (which logs its refusal reason), by `startScan` (which refuses silently, like its other refusals) and by `retryDecision(id:)`. That last one forwards the flag into `JobPresentation.retryDecision`, whose refusal reason shows in the history window's Retry tooltip.
- **Cleared** by a later successful eject, `removeDisc()`, `insertDisc()` and `discRemounted(_:)` for the same disc (review fix).

**`JobContext` / `DVDPipeline.swift`** (review fix). `JobContext.eject` is bound in `start` to the controller's `ejector`. `DVDPipeline.eject` is injectable, defaults to the real `DiscEjector` and is passed `context.eject` by `pipelineRunner`. The pipeline logs a partial eject, and the job's outcome is unchanged: an eject failure never fails a job whose movie is already in Plex.

**`DVDMonitor.swift` / `AppDelegate.swift`** (review fix). `.sameDiscRemounted` now fires `onDVDRemounted(insertion)` when a volume path is present, and `AppDelegate` forwards it to `jobs.discRemounted(_:)`.

**`StartGate.swift` / `MetadataEntryView.swift` / `DiscTitleListView.swift`.** `canStart` takes `discUnavailable`. The Start and Rescan buttons are disabled while it is set, and their tooltips name the reason (the Start tooltip is from the review fix).

**`EjectPolicy` needed no change.** It decides from `insertedDisc`, `isRunning`, `isScanning` and `isEjecting`, none of which a partial eject leaves set. So Eject stays enabled and offers the retry (`ejectRemainsAvailableWhileDiscUnavailable`).

**Decision: no mount-path-exists backstop.** See the Resolution notes.

## Gotchas

- **Most pipeline tests still reach the real `DiscEjector`.** `DVDPipeline.eject` defaults to it, and the existing construction sites that run to success (`ExtrasPipelineTests`, `EncodeControllerTests` and others) don't inject a fake. So they call `DiscEjector.eject` on a temp-directory path. This predates #0049: 4db0e8d called `DiscEjector` directly. It is harmless in practice, since the path is not a volume and the call returns "Could not find a disk", but it breaks the "never call the real ejector from tests" rule. Now that the seam exists, a follow-up should inject a no-op `eject` at those sites.
- **`retryDecision`'s and `canStart`'s `discUnavailable` default to `false`.** A future caller that forgets to pass it fails open. Both real call sites pass it explicitly.
- **`discRemounted` relies on disc identity.** `SelectionReset.sameDisc` needs matching `discID`s, because a remount event carries a fresh `insertionID`. `DVDMonitor` only reports `.sameDiscRemounted` when the identity matched, so this holds in production.

## Expected behavior

After a partial eject, the app knows the disc is no longer mounted. Start and Rescan are refused with a clear reason, and the user is offered a retry of the eject (or a remount). No job or scan is run against the dead path.

## Plan

- Distinguish the three results in `DiscEjector`: `.ejected`, `.unmountedButNotEjected(error)` and `.failed(error)`, as a pure mapping over the unmount and eject results, with tests.
- On `.unmountedButNotEjected`, `JobController` marks the inserted disc as unmounted: clear or flag `insertedDisc`, or set a `discUnavailable` state, so `StartGate`, Rescan and `EjectPolicy` refuse with a reason and Eject offers a retry.
- Optionally, check that the mount path still exists before Start or Rescan as a cheap backstop.
- Unit-test with a fake ejector. A real jammed tray is manually unverified.
