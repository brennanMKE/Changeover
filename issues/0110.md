# 0110 — Sparkle auto-updates have no scope decision for v1

| | |
|---|---|
| **Status** | open |
| **Phase** | 6 — Ship to other people |
| **Module** | Release |
| **Platform** | macOS |
| **First seen** | 2026-09-11 |

## Description

Once a DMG ships to someone else, every future fix needs a way to reach them. Nothing in `Roadmap.md`'s Phase 6 section (`:239-248`) mentions updates at all — the phase ends at "install from a DMG" and has no answer for what happens on the second release. This ticket is the decision: Sparkle in v1, or manual re-download, with the version-numbering discipline that either choice requires.

## Long Description

This is a **decision ticket**. It may legitimately resolve as "deferred" — but it
has to be resolved before [#0101](0101.md) finishes, because the answer changes
what goes in `App.xcconfig` and `Changeover/Info.plist`, and before
[#0102](0102.md) starts, because it changes which `mac-release` templates get
copied and which preflight gates survive.

**The case for Sparkle in v1.** Changeover ships to people who are not the
author and who will never think to check for a new version. It is a menu bar
app that runs unattended on a mini — nobody is going to visit a download page.
The `mac-release` skill already covers the whole thing (`references/sparkle.md`,
`references/appcast.md`, `templates/appcast-item.sh`, `templates/appcast.xml`,
`templates/deploy-website.sh`), so the marginal cost on top of [#0102](0102.md)
is small: EdDSA keys, four `Info.plist` keys, a hosted `appcast.xml`, and an
update-check menu item.

**The case against.** It adds a hosting dependency the project does not otherwise
have (`references/website-deploy.md` — self-host, GitHub Pages, S3 or Releases,
all of which are a decision and an ongoing cost), an SPM dependency, a second
signing key to manage and never lose, and a class of failure that is
notoriously confusing to debug (`references/versioning.md`, "The drift trap:
'You're up to date' while running an old version").

**Either way, the versioning discipline is not optional.** The project currently
has `MARKETING_VERSION = 1.0` — not SemVer — and `CURRENT_PROJECT_VERSION = 1`
hardcoded in `project.pbxproj` for all four targets (`:401`, `:411`, `:430`,
`:440`), with a build number that has never moved. Two DMGs built a week apart
today are indistinguishable from the outside. [#0101](0101.md) moves these into
`App.xcconfig`; this ticket settles what the numbers should *mean*:

- `MARKETING_VERSION` — SemVer, bumped by hand once per release, the only thing
  a human edits (`references/versioning.md`, "One source of truth: the
  xcconfig").
- `CURRENT_PROJECT_VERSION` — the `YYYYMMDD` UTC build number injected at
  archive time by `release.sh` (`references/versioning.md`, "The build-number
  scheme: YYYYMMDD"). Note the **same-day collision trap** documented in that
  reference: two releases on one day produce the same build number, and Sparkle
  will not offer the second.

## Steps to reproduce

1. Imagine the DMG from [#0102](0102.md) is installed on someone else's mini.
2. Fix a bug and cut a second release.
3. Identify the mechanism by which their copy learns about it.

## Expected behavior

Either the app checks an appcast and offers the update, or the decision to make
updates manual is written down along with how users will be told (release notes,
a "check for updates" link, a README line), and the version numbers are
meaningful enough to tell two builds apart.

## Actual behavior

There is no mechanism and no decision. `MARKETING_VERSION` is `1.0` in four
places in `project.pbxproj` and the build number has never been incremented, so
the installed copy could not report what it is running even if someone asked.

## Plan

**Step 1 — Take the decision. Recommended: defer Sparkle past v1, but do the
versioning work now.**

Reasoning: Phase 6's exit criteria (`Roadmap.md:250-256`) are entirely about the
*first* install, and the audience for v1 is small and known. Adding a hosting
dependency and a second signing key before anyone is running v1 optimizes for a
problem that does not exist yet. What cannot be deferred is the numbering — if
v1 ships with `1.0`/`1` and no discipline, adding Sparkle later starts from a
fleet of indistinguishable installs, which is the worst starting position for
exactly the drift bug `references/versioning.md` warns about.

If the decision goes the other way, that is fine too — the work is well-covered
and the skill's templates make it close to mechanical. Either way **write the
decision and its reasoning into this ticket**, because the next person to open
`App.xcconfig` will otherwise re-litigate it.

**Step 2 — Do the versioning work regardless (feeds [#0101](0101.md)):**

- `MARKETING_VERSION = 1.0.0` in `App.xcconfig` — three components. Bumped by
  hand, once per release, alone in its own commit (`references/versioning.md`,
  "Per release").
- `CURRENT_PROJECT_VERSION = 1` in `App.xcconfig` for local Debug builds;
  `release.sh` overrides it at archive time with the UTC `YYYYMMDD`. Never
  bumped by hand.
- `Changeover/Info.plist` gets `CFBundleShortVersionString = $(MARKETING_VERSION)`
  and `CFBundleVersion = $(CURRENT_PROJECT_VERSION)`
  (`references/versioning.md`, "Info.plist wiring").
- Keep `release.sh`'s version-consistency gate — it fails the build if the built
  bundle's versions disagree with the xcconfig, which catches a pbxproj override
  shadowing the xcconfig before anything ships. That gate is worth having with
  or without Sparkle.
- Add a visible version somewhere in the app. `StatusMenuView`'s header
  (`Changeover/StatusMenuView.swift:11-22`) is the natural place — a small
  "1.0.0 (20260911)" under the title. Without Sparkle this is the *only* way a
  user can tell you what they are running, which makes it more important when
  updates are manual, not less.

**Step 3 — If Sparkle is in scope**, follow `references/sparkle.md` end to end;
do not improvise. The load-bearing points from it and from
`references/appcast.md`:

- `sparkle generate_keys --account Changeover` — a **per-app** account, and the
  private key lives in the keychain. Losing it means no user can ever be updated
  again; back it up deliberately.
- `SU_FEED_URL` and `SU_PUBLIC_ED_KEY` go in `App.xcconfig`, referenced as
  `$(…)` from `Changeover/Info.plist`. Note the xcconfig comment-syntax trap in
  `templates/App.xcconfig`: `//` starts a comment, so a URL has to be
  reassembled from a separate `HTTPS = https:/` variable.
- `GENERATE_INFOPLIST_FILE = YES` (`project.pbxproj:404`, `:433`) is the gotcha
  `references/sparkle.md` calls out — a synthesized plist commonly drops the
  Sparkle keys. [#0101](0101.md)'s explicit `Changeover/Info.plist` is the fix,
  but verify with PlistBuddy against the *built* bundle, not the source file.
- **Never hand-type appcast attributes.** `templates/appcast-item.sh` derives
  `sparkle:version`, `sparkle:shortVersionString`, `length` and `edSignature`
  from the DMG itself. `references/troubleshooting.md` ("Sparkle: update not
  offered") is the debugging path when it goes wrong.
- Changeover has **no Dock icon and no main menu** (`LSUIElement`,
  `project.pbxproj:406`) — so Sparkle's usual "Check for Updates…" menu item has
  nowhere to live. Add it to `StatusMenuView` alongside "Settings…"
  (`Changeover/StatusMenuView.swift:39-45`). This is a real integration detail
  the templates cannot anticipate.
- An app that updates itself while a rip is running would be a serious
  regression. Suppress or defer update installation while a job is active — a
  concern that gets sharper once Phase 3's job queue exists ([#0040](0040.md)).

**Risks.** (a) Deferring Sparkle is only safe if the versioning half is
genuinely done — a deferral that also skips step 2 is how the drift bug gets
built in. (b) Adding Sparkle later to an already-distributed app means the
existing installs cannot be auto-updated to the version that adds updating;
accept and plan for one manual re-download at that point, and say so in the
resolution. (c) The EdDSA private key is unrecoverable if lost.

## Notes

**If Sparkle is deferred**, verification for this ticket is the versioning half:

```bash
# Built bundle reports both numbers, and they match the xcconfig.
/usr/libexec/PlistBuddy -c 'Print :CFBundleShortVersionString' <app>/Contents/Info.plist
/usr/libexec/PlistBuddy -c 'Print :CFBundleVersion'            <app>/Contents/Info.plist
# The numbers are visible to a user who cannot open a terminal:
#   launch the app, open the menu bar popover, read the version in the header.
```

Plus the grep from [#0101](0101.md) confirming no version override survives in
`project.pbxproj`.

**If Sparkle ships**, verification is a genuine two-release test and cannot be
faked: cut 1.0.0, install it on the clean machine from [#0103](0103.md), cut
1.0.1, publish the appcast, and confirm the installed copy *finds, downloads,
verifies and installs* it — then confirm the relaunched app reports 1.0.1 in
both `CFBundleShortVersionString` and the UI. Checking that the appcast XML
parses is not the test; the test is an app on another machine actually updating
itself. `references/troubleshooting.md` covers what each failure mode looks like.

Note the safety rule from the `mac-release` skill: publishing an appcast and
deploying to a host **modify outside state and must not be run autonomously from
an agent session** — prepare, then hand the publish to the user.
