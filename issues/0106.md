# 0106 — The TMDB API key is only validated when a search first fails

| | |
|---|---|
| **Status** | open |
| **Module** | Onboarding / TMDB |
| **Platform** | macOS |
| **First seen** | 2026-09-11 |

## Description

Changeover accepts any non-empty string as a TMDB API key. `SettingsView`'s Save button just calls `settings.persist()` (`Changeover/SettingsView.swift:64-67`), and `isConfigured` only checks `!tmdbAPIKey.isEmpty` (`Changeover/AppSettings.swift:33`). A typo, a stale key, or a pasted key with trailing whitespace is not discovered until the user has a disc in the drive and runs a search, where it surfaces as "Server returned status 401" (`Changeover/TMDB/TMDBModels.swift:53`).

## Long Description

The path a bad key takes today:

1. `SettingsView` `SecureField` (`Changeover/SettingsView.swift:51`) binds
   straight to `settings.tmdbAPIKey`. No trimming, no check.
2. Save persists it to `UserDefaults` (`Changeover/AppSettings.swift:53`).
3. `isConfigured` goes `true`; the menu bar shows green, "Idle — insert a DVD to
   begin" (`Changeover/StatusMenuView.swift:16-18`).
4. The user inserts a disc, `MetadataEntryView` opens, they type a title and
   press Search → `runSearch()` (`Changeover/MetadataEntryView.swift:137-140`)
   → `MovieSearchViewModel.search(apiKey:)`
   (`Changeover/TMDB/MovieSearchViewModel.swift:21-34`) →
   `TMDBClient.searchMovies` throws `TMDBError.badResponse(401)`
   (`Changeover/TMDB/TMDBClient.swift:29-32`).
5. The red status row (`Changeover/MetadataEntryView.swift:51-57`) reads
   **"Server returned status 401."**

That string names neither the problem nor the fix. The one good error message in
the enum — `missingAPIKey`, "TMDB API key is not configured. Get a free API key
from themoviedb.org and enter it in Settings"
(`Changeover/TMDB/TMDBModels.swift:50`) — is only reachable when the key is
*empty* (`TMDBClient.swift:13`), which is precisely the case the UI already
prevents by other means.

There is a second, historical trap. The key moved from a build-time
`Secrets.xcconfig` value to a runtime `UserDefaults` setting in commit
`1c1e3d9`, but `README.md:61-72` still documents the xcconfig flow. A new user
following the README puts their key in a file nothing reads, launches the app,
and gets a blank field. That documentation half is [#0108](0108.md); this ticket
is the app-side half.

`Roadmap.md:247` names it: *"Verify the TMDB key at entry rather than on first
search."*

## Steps to reproduce

1. Open Settings, paste `not-a-real-key` into the TMDB API Key field, press Save.
2. Open the menu bar popover — green dot, "Idle — insert a DVD to begin".
3. Insert a disc (or use **Open…**), type a movie title, press Search.

## Expected behavior

Step 1 validates the key against TMDB before accepting it and reports the result
inline — valid, invalid, or "couldn't reach TMDB" as three distinct outcomes.
Step 2 does not claim readiness with a key that does not work.

## Actual behavior

Step 1 accepts anything non-empty. Step 2 claims ready. Step 3 shows "Server
returned status 401."

## Plan

Depends on [#0104](0104.md) for the `SetupChecklist` / `RequirementState` model —
this implements row 3.

**1. Add a validation call to `TMDBClient`**
(`Changeover/TMDB/TMDBClient.swift`). The cheapest correct probe is
`GET /3/authentication` (or `/3/configuration`) with the key as `api_key`. Return
a three-way result, not a `Bool` — "the key is wrong" and "there is no network"
must not collapse into one state, because the remedies are opposite:

```swift
enum KeyValidation: Equatable {
    case valid
    case rejected(status: Int)     // 401 → the key itself is wrong
    case unreachable(String)       // DNS/offline/timeout → say so, don't blame the key
}
```

Give it a short `URLRequest.timeoutInterval` (5–10s) so a captive portal does not
hang the setup window.

**2. Improve `TMDBError.badResponse`** (`Changeover/TMDB/TMDBModels.swift:45`,
`:53`). Special-case 401 to say the key was rejected and point at Settings, and
401-vs-404-vs-429 should read differently; 429 in particular means rate-limited,
not broken. The generic "Server returned status \(c)." stays as the fallback for
everything else. This is a small change that pays off even for users who never
see the onboarding flow.

**3. Trim on entry.** A pasted key routinely carries whitespace or a newline.
Trim in the binding or in `persist()` (`Changeover/AppSettings.swift:53`). A key
that fails only because of a trailing space is the most frustrating possible
version of this bug.

**4. Wire row 3 of the checklist.** `.checking` while the request is in flight,
`.satisfied` on `valid`, `.missing(reason:)` on `rejected`, and — deliberately —
**`.unknown` rather than `.missing` on `unreachable`**, so that being offline
during setup does not brand a perfectly good key as broken. Re-validate on
demand ("Recheck") and automatically when the key text changes, debounced;
without debouncing, typing a 32-character key fires 32 requests.

**5. Don't re-validate on every launch.** Cache the last successful validation
(a `UserDefaults` timestamp alongside the existing keys at
`Changeover/AppSettings.swift:58-63`) and treat a key validated recently as good
until it fails in real use. Validating on every cold start makes the app depend
on the network to reach an idle state, which it otherwise does not.

**6. Give the row a "Get a key" link** to
`https://www.themoviedb.org/settings/api`, the same URL the
`Secrets.xcconfig.example` comment already carries
(`Changeover/Secrets.xcconfig.example:3`). The existing caption
(`Changeover/SettingsView.swift:54`) explains what TMDB is but is not a link.

**Risks.** (a) A `SecureField` hides the key, which makes a typo invisible —
consider a reveal toggle, since a TMDB key is not a password and the user needs
to be able to check it against the one on the website. (b) Validation adds a
network dependency to the setup flow; step 4's `.unknown`-on-unreachable rule is
what keeps that from being a hard failure. (c) Do not log the key — it currently
travels as a `api_key` query parameter (`Changeover/TMDB/TMDBClient.swift:20`),
so be careful that no new error path prints the URL.

## Notes

**Verification here is mostly automatable, unusually for this project.**

- **Unit tests** in `ChangeoverTests` against a stubbed `URLSession` (the client
  already takes one by injection — `Changeover/TMDB/TMDBClient.swift:6-8`, which
  makes this straightforward): assert 200 → `.valid`, 401 → `.rejected(401)`, a
  thrown `URLError.notConnectedToInternet` → `.unreachable`, and that the
  checklist row maps `.unreachable` to `.unknown` and not `.missing`. Confirm
  the test names appear in the output and the counts increased —
  `issues/Issues.md` is explicit that a test which compiles but never ran proves
  nothing.
- **Manual, against the live API**, three runs: a real key (expect valid), the
  real key with one character changed (expect rejected, with a message naming
  the key), and the real key with Wi-Fi off (expect "couldn't reach TMDB", with
  the key **not** marked invalid). The third is the one most likely to be got
  wrong and the one least likely to be tested.
- Check the whitespace case explicitly: paste a key with a trailing newline.

Run the manual half on the clean machine from [#0103](0103.md) if convenient —
but unlike [#0105](0105.md), this ticket does not need one, because the state
being tested is a `UserDefaults` string that can be set to anything locally.
