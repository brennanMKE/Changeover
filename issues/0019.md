## Root cause

`AppDelegate.applicationDidFinishLaunching` called `registerLoginItem()`
unconditionally, and `ChangeoverTests` is app-hosted — every unit test run
launched the app and called `SMAppService.mainApp.register()`, registering
whatever DerivedData build was under test as a login item. macOS then
relaunched that dead path at every login (BTM disposition
`enabled, allowed, notified`), leaving stray instances that collide with
later test runs. There was no test-host guard and no installed-vs-ad-hoc
distinction anywhere in the registration path.

## Fix

`040d5d0` — new `Changeover/LoginItemPolicy.swift` with the pure,
`nonisolated` predicate `shouldRegister(environment:bundleURL:)`: a test host
(`XCTestConfigurationFilePath` present in the environment) never registers,
and neither does any bundle outside `/Applications/` (prefix checked at the
component boundary, so `/ApplicationsX/…` and `/tmp/Applications/…` fail).
Only an installed app registers. `AppDelegate.registerLoginItem()` guards on
it and returns without touching `SMAppService` otherwise.

**Deliberate deviation from the Plan's step 4 option:** the "have the fixed
app call `SMAppService.mainApp.unregister()` once when it detects a
non-`/Applications` build" self-heal was **not** implemented. Both builds
share the bundle identifier `co.sstools.Changeover`, so an unregister call
from a DerivedData build could strip the login item of the real
`/Applications` installation — the cure would be able to cause the same
class of problem it fixes. Existing registrations are cleaned up out of band
instead (see `## Verification`).

## Files changed

- `Changeover/LoginItemPolicy.swift` (new) — the pure
  `shouldRegister(environment:bundleURL:)` predicate.
- `Changeover/AppDelegate.swift` — `registerLoginItem()` guards on the
  policy and returns without touching `SMAppService` for test hosts and
  non-`/Applications` builds.
- `ChangeoverTests/LoginItemPolicyTests.swift` (new) — 5 tests over the

## Gotchas

- `sfltool resetbtm` cannot be run non-interactively over SSH: it demands
  the `com.apple.auth.admin` authorization right and fails with
  `errAuthorizationInteractionNotAllowed` even under `sudo -n`. Plan for a
  GUI session or System Settings when cleaning BTM state remotely.
- `sfltool dumpbtm` (read) works fine over `sudo -n` SSH; only the reset is
  interactive.
- The unregister-once self-heal idea is a trap for this app specifically:
  shared bundle identifier means any build can unregister any other build's
  login item. If self-healing is ever wanted, it needs a path check that the
  *registered* item points at the calling bundle, not just that the caller
  is ad-hoc.

## Description

`AppDelegate.applicationDidFinishLaunching` calls `registerLoginItem()` unconditionally
(`AppDelegate.swift:28`), which calls `SMAppService.mainApp.register()` (`AppDelegate.swift:145-148`).
`ChangeoverTests` is app-hosted, so **every unit test run launches the app** — and so registers the
DerivedData test build as a login item on whatever Mac runs the tests. After the next login, macOS
relaunches that build, and the stray instance collides with the next test run's own test host.

It likely left a stale Changeover build running on cameron since August 20, and a stray instance on
gordon on 2026-09-12. **Not yet proven** — see Notes. It did **not** cause #0009's hour-long hang —
see *Correction* below.

## Evidence

On gordon, 2026-09-12 (login at 20:35 after an `fdesetup authrestart`):

| pid | Started | Parent | What |
|---|---|---|---|
| 1481 | 20:35:23 | `/sbin/launchd` | `DerivedData/Changeover-…/Debug/Changeover.app` — 23 seconds after login, nothing started a test |
| 2674 | 20:55:18 | `/sbin/launchd` | the test host #0009's run launched |
| 2633 | 20:55 | sshd (the test run) | `xcodebuild … test -only-testing:ChangeoverTests`, **hung 58 minutes at 0% CPU**, no progress |

Both app instances were listed in the GUI launchd domain as `application.co.sstools.Changeover.…`.
Killing 2633, its `SWBBuildService` and both app instances cleared gordon.

On cameron, earlier the same day, a Changeover build had been running since **August 20** from a
`build/` folder that no longer existed (pid 1426, parent `launchd`). Its window popped up whenever a
`VIDEO_TS` disk image mounted, which the user saw as "UI tests popping up". Same shape: a test-launched
build relaunched by the OS long after the test.

## Steps to reproduce

1. On a clean Mac, run `ChangeoverTests` once (the test host launches `Changeover.app` from DerivedData).
2. Log out and back in, or reboot and log in.
3. Observe a `Changeover` process from DerivedData running with parent `launchd`.
4. Run `ChangeoverTests` again: expect the run to stall with a second test host alongside the stray one.

## Expected

Running tests leaves no trace in the system's login items. Only a real installed Changeover (e.g. in
`/Applications`) registers itself as a login item.

## Actual

Every test run registers the DerivedData build; the OS relaunches it at login; later test runs hang.

## Plan

1. **Skip registration under XCTest.** In `registerLoginItem()`, return early when the process is a
   test host — `ProcessInfo.processInfo.environment["XCTestConfigurationFilePath"] != nil` is the
   standard signal. Consider also skipping when the bundle is not in `/Applications`, so ad-hoc
   Debug builds never register.
2. Put the decision behind a pure, `nonisolated` predicate (`shouldRegisterLoginItem(environment:bundleURL:)`)
   so it is unit-testable without calling `SMAppService`.
3. Tests: under a test-host environment → no registration; `/Applications` bundle, no XCTest → registers;
   DerivedData path → no registration. Falsify by removing the guard.
4. **Clean up existing registrations** on gordon and cameron. There's no targeted command-line
   unregister for another app's `SMAppService` item; remove it in System Settings → General → Login
   Items & Extensions, or have the fixed app call `SMAppService.mainApp.unregister()` once when it
   detects it is a non-`/Applications` build.

Verification: unit tests on gordon only, per `CLAUDE.md`. The end-to-end check needs a login cycle on
the test Mac: run tests, log out and in, confirm no `Changeover` process appears, run tests again.

## Notes

**What is not proven.** A process launched by `launchd` right after login is also what macOS's
"Reopen windows when logging back in" produces for apps that were running at shutdown. The two are
distinguished by the Background Task Management database: `sudo sfltool dumpbtm | grep -i -A8 changeover`
on gordon, or a look at System Settings → General → Login Items & Extensions. The code path in
`AppDelegate.swift:28` and `:145-148` is certain; whether it is what relaunched pid 1481 still needs that
check.

## Correction — 2026-09-12

This issue first said the stray instance "very likely" hung #0009's verification run. **That was
wrong.** The hung run's own result bundle on gordon
(`Test-Changeover-2026.09.12_20-55-12--0700.xcresult`) contains:

```
SWIFT TASK CONTINUATION MISUSE: run(executablePath:arguments:watchdog:readerDelay:onLine:) leaked its continuation without resuming it. This may cause tasks waiting on it to remain suspended
```

That is `ProcessRunner.run`, new in #0009's commit `6143729`. A leaked continuation leaves its awaiting
task suspended forever, which matches the 58-minute hang at 0% CPU. The hang is a #0009 defect, tracked
there. The stray login-item instance was present at the same time and is still a real bug, but nothing
shows it caused that hang.
