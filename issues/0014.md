# 0014 — Remove the rip stage: EncodeController encodes straight from VIDEO_TS and RipController is deleted

| | |
|---|---|
| **Status** | open |
| **Phase** | 1 — Trustworthy single-disc rip |
| **Module** | EncodeController / RipController / DVDPipeline / AppSettings |
| **Platform** | macOS |
| **First seen** | 2026-09-11 |

## Description

The pipeline rips a disc to an intermediate `.mkv` with `makemkvcon` and then encodes that file with HandBrakeCLI. HandBrake reads DVDs directly, so the rip stage is unnecessary: `EncodeController.encode` should take a `VIDEO_TS` path plus a title number and invoke HandBrakeCLI once. `RipController` is deleted. **This is the commit point of the MakeMKV replacement** — after it lands, no disc touches `makemkvcon` on the happy path, and 5–8 GB of write-then-read per disc disappears.

## Long Description

This is step 4 of `MakeMKVReplacement-Path.md` §3, and it was proven end to end on hardware before being filed. From `MakeMKVReplacement-Results.md` §1, run on `joe` (M1 mini, macOS 26.6.2, 8 GB) on 2026-09-11 against the *Fargo* Special Edition disc:

```
HandBrakeCLI -i /Volumes/FARGO_SE__16X9 -t 1 --format av_mp4 --quality 21 \
  --aencoder "copy:aac,copy:ac3" --subtitle scan --markers -o /tmp/fargo-direct.mp4
```

`work result = 0`. 1,128,135,218 bytes (1.13 GB). h264 712×472, AAC stereo + AC3 5.1, **36 chapters preserved**, duration 1:38:08, 21m44s wall clock for a 98-minute feature. No MakeMKV, no intermediate MKV, no expiring key.

The title number comes from the scan, which was also verified (`-Results.md` §2):

```
HandBrakeCLI -i /Volumes/FARGO_SE__16X9 --scan --title 0 --min-duration 1 --json
→ MainFeature: 1   titles: 8
```

**`--title 0` is mandatory.** Without it HandBrake scans only title 1, returns valid JSON, and is silently incomplete — the symptom is a scan returning exactly one title on a disc that should have several. That single detail is called out as the most important invocation fact in the entire results document.

### What this closes by construction

Three open tickets stop describing anything real the moment there is no intermediate file:

- **[#0003](0003.md)** — `RipController` picks the largest `.mkv` in a shared folder, so a stale file can be encoded as the current movie. There is no shared rip folder and no `.mkv` to pick, correctly or otherwise. The selection code (`RipController.swift:66-77`, `largestMKV(in:)`) is deleted along with the file.
- **[#0004](0004.md)** — working folders are never cleaned, so every rip strands its intermediate `.mkv`. There is no intermediate to strand. The encode's own output still needs a home and still gets moved, but the multi-gigabyte per-disc residue is gone.
- **[#0028](0028.md)** — `RipController` rips every title on the disc and then guesses the movie by file size. There is no full-disc rip and no size-based guess; HandBrake is pointed at one title index and encodes that.

"By construction" is the load-bearing phrase. These are not fixed by better code — the code they describe ceases to exist. Each of those three should still be read before this lands, because each documents a constraint worth keeping (per-job isolation, cleanup on success only, verifying by duration rather than size).

### The `--subtitle scan` decision

`--subtitle scan` is currently passed unconditionally (`EncodeController.swift:31`). Decide it deliberately here rather than inheriting it. From `-Results.md` §6: it runs **a complete extra pass over the full title before encoding begins** — the `task 1 of 2` visible in the progress output — and accounted for **roughly half of Fargo's 21m44s**. Phase 3 ([#0040](0040.md)) wants unattended multi-disc throughput, so doubling wall clock per disc for a forced-subtitle scan is a real cost.

It is also the source of the `bin_data` VOBSUB stream that [#0017](0017.md) is about. Two reasons to revisit it, one performance and one correctness, and they point the same way.

Related, non-fatal, observed on the same run: `ERROR: unable to decode subtitle with 2019 bytes.` during the subtitle scan. The encode continued and completed.

## Steps to reproduce

Not a defect report — this is the architectural change the three documents in the `MakeMKVReplacement*` series conclude with. The behavior it replaces is reproducible as [#0003](0003.md)'s steps.

## Expected behavior

`DVDPipeline.run()` is **scan → encode → move**. The encode reads the `VIDEO_TS` path the monitor supplied and the title index the scan chose, and writes the final `.mp4` directly. `RipController.swift` no longer exists. `makemkvcon` is not invoked on any disc that HandBrake can handle.

## Actual behavior

`DVDPipeline.run()` is rip → encode → move. `makemkvcon mkv disc:0 all <dir>` (`RipController.swift:24-29`) writes every title on the disc to `<plexMediaRoot>/Working/ripping`, the largest `.mkv` is selected, and HandBrakeCLI reads that file back (`EncodeController.swift:25-33`). Every disc pays a full write-then-read of 5–8 GB and depends on a beta key with a two-month clock on it.

## Plan

### `Changeover/EncodeController.swift`

Signature becomes roughly:

```swift
nonisolated static func encode(
    videoTS:       String,
    title:         Int,
    output:        String,
    handbrakePath: String,
    log:           @escaping @MainActor (String) -> Void
) async -> Result<URL, JobFailure>
```

Keep it `nonisolated static` — this is the long-running work that must stay off the main actor, and the `Task { @MainActor in log(line) }` discipline inside the `readabilityHandler` and `terminationHandler` (`EncodeController.swift:40-51`, `:56-69`) stays exactly as it is. Keep the `LogTailBuffer` and the `Result<URL, JobFailure>` return from [#0007](0007.md); the two resume sites and their continuation discipline are unchanged.

Arguments, from the verified invocation:

```
--input <videoTS> --title <n> --format av_mp4 --quality <Config.videoQuality>
--aencoder <Config.audioEncoder> --markers --output <output>
```

`Config.videoQuality` is already RF21 and `Config.audioEncoder` already the copy list, so the constants carry over; keep them `nonisolated` (`CLAUDE.md` concurrency rules). `--subtitle scan` is the deliberate decision described above, not a line to copy across.

### `Changeover/RipController.swift`

Delete the file. Remove it from the Xcode target. Check for references in `DVDPipeline.swift`, `MetadataEntryView.swift` and the test target before deleting, not after.

### `Changeover/DVDPipeline.swift`

`run()` loses its rip stage and its `.rip` failure branch. The MainActor prologue that captures path strings off `settings` before calling into the nonisolated controllers (`DVDPipeline.swift:19-24`) stays — that pattern is why `DVDPipeline` is a plain MainActor `struct` and not an `actor`, per `CLAUDE.md`, and it now captures the `VIDEO_TS` path and title instead of `workingRipPath`.

`JobStage.rip` (`JobOutcome.swift`) becomes unreachable. **Leave the case in place** rather than removing it — [#0007](0007.md)'s review findings record that `FailureReason`/`JobStage` decoding throws on an unknown case key, so an older peer cannot decode a newer vocabulary, and Phase 4 puts these types on the wire. Removing a case is a wire-compatibility change; make it deliberately in [#0060](0060.md), not as a side effect here.

### `Changeover/AppSettings.swift`

`workingRipPath` (`AppSettings.swift:27`) loses its only consumer. Do not delete the property in this ticket — [#0015](0015.md) keeps a MakeMKV fallback that still needs somewhere to write. Update its doc comment to say it is fallback-only.

### Risks

- **The one-disc evidence base.** Fargo ripped correctly end to end; that proves the path works, not that it works on 33 discs. `-Path.md` §1 is explicit that the sweep cannot be run as specified (`/Volumes/Media/Media/Movies` holds finished `.mp4` files, not discs; the real sweep is ~11 hours of manual disc swapping). The mitigation is [#0015](0015.md)'s fallback plus logging every fallback, not delaying this.
- **libdvdcss is running on a fallback path.** `-Results.md` §5: libdvdcss could not open `/dev/disk6` and recovered by retrieving all 17 CSS keys through the mounted filesystem — instantly, but on a path libdvdread itself describes as slow and last-resort. It is the most plausible future cause of "works in MakeMKV, fails in HandBrake". Log it when it appears.
- **Bad-sector behavior is uncharacterized.** `-Results.md` §11: MakeMKV has `io_ErrorRetryCount`/`io_IgnoreReadErrors`; HandBrake's equivalent is unknown, and a corrupt rip still produces a file. Spot-check playback, not exit codes — which is also [#0012](0012.md)'s argument.
- **The IT Crowd disc is still untested** and already reports malformed IFO data that MakeMKV handled gracefully. It is the known test case for both the malformed-IFO question and R9 (Play All). Do not treat this ticket as evidence about it.
