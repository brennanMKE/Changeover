# 0088 — Six-digit PIN pairing has no iOS entry UX

| | |
|---|---|
| **Status** | open |
| **Module** | Pairing / RemoteClient |
| **Platform** | iOS · iPadOS |
| **First seen** | 2026-09-11 |

## Description

Phase 4's Mode B pairing displays a six-digit code on the host that the user
types into the client. On a Mac that is a text field; on a phone it is a distinct
interaction that needs a numeric keypad, per-digit feedback, and a sane answer
for what happens when the code expires or is mistyped.

## Long Description

`RemoteControl.md` specifies two pairing modes. Mode A — a random 32-byte key in
`NSUbiquitousKeyValueStore`, read automatically by clients on the same iCloud
account — is zero-interaction and is the default when it works. Mode B — the
host shows a six-digit code, the user enters it on the client, both derive a
shared key and the host stores the client's identity in its Keychain — exists
because the app is explicitly **not** a single-user app: households on different
Apple IDs, users not signed into iCloud at all, and the case where KVS sync is
simply slow.

For an iPhone, Mode B is not the fallback — it is frequently the first
experience, because the mini and the phone may well be on different Apple IDs
and because KVS propagation is not instant. This screen is the first thing a new
user touches, and it is the gate on writing into their media library.

The UX specifics that differ from a Mac:

- There is no hardware keyboard, so the input needs `.keyboardType(.numberPad)`
  and a visible way to dismiss it.
- The user is holding the phone in one hand, looking at a code displayed across
  the room, which argues for large per-digit boxes rather than a small text
  field.
- iOS offers one-time-code autofill semantics that make the flow much better when
  the code arrives via a channel the system can see — and much more confusing
  when it does not.
- There is no window to put a modal sheet over; the pairing flow is the app's
  entire first screen until it succeeds.

Mode A also needs iOS-specific handling. KVS requires the iCloud key-value
entitlement on the iOS target, the account can be signed out entirely, and the
KVS change notification may arrive seconds after launch — so the UI must handle
"waiting for iCloud" without either blocking on it or skipping past it too
eagerly.

## Steps to reproduce

1. Complete [#0081](0081.md) and Phase 4's pairing ([#0060](0060.md)).
2. Install the client on an iPhone signed into a different Apple ID than the
   mini — or signed out of iCloud entirely.
3. Launch it and try to pair with the host.

## Expected behavior

The client discovers the host, detects that Mode A is unavailable, and presents a
clear six-digit entry screen: large digit fields, numeric keypad up immediately,
per-digit feedback, automatic submission on the sixth digit, and an explicit
error for a wrong or expired code with the ability to retry without restarting.
Once paired, the device is remembered and the screen never appears again.

## Actual behavior

There is no iOS pairing UI at all. The Mac client's text-field entry has no
numeric keyboard, no per-digit affordance, and no phone-appropriate error or
retry handling, and the Mode A path has neither the iOS entitlement nor a
"waiting for iCloud" state.

## Notes

Pairing is a security boundary, not a convenience screen. `RemoteControl.md` is
explicit that what is worth protecting is that the remote can **write into the
media repository**, and that this expands further once montage editing lands. A
sloppy pairing screen is not a cosmetic problem.

The per-peer capability field from `RemoteControl.md` — distinguishing "can start
rips and write to the library" from "can watch progress only" — should be visible
in the iOS pairing result even if v1 always grants full capability. Showing what
was granted at pairing time costs a line and makes the field real rather than
theoretical.

The Wi-Fi Aware note in `RemoteControl.md` matters here in one specific way:
Wi-Fi Aware's native pairing is a **mandatory six-digit PIN exchange** handled by
the system through `DevicePairingView`. Building Mode B's mental model to match
means that if Apple lifts the macOS availability gate, this screen is replaced by
a system view rather than rearchitected. Keep the client's pairing state machine
independent of the entry UI so that substitution stays cheap.

The Wi-Fi Aware hardware floor — iPhone 12 and later; iPad 10th gen, iPad Air 4th
gen, iPad Pro 11" 3rd gen, iPad Pro 12.9" 5th gen, iPad mini 6th gen and later —
is irrelevant to this ticket today because macOS cannot be the peer. It only
becomes a deployment consideration if the gate lifts, and even then the iOS 26
deployment target from [#0081](0081.md) is a stricter floor than the Wi-Fi Aware
one, so no device that can run this app would be excluded.

## Plan

### 1. One first-run flow, not two screens that happen to be adjacent

Sequence, as a single state machine in an `@Observable` pairing coordinator owned
at the app root with `@State`:

1. **Local Network permission** — [#0089](0089.md) owns the prompt and the denial
   path, but it happens here, before discovery can return anything.
2. **Discovery** — browse for `_changeover._tcp`. Zero hosts is a distinct state
   from "found a host, not paired", and the messages are completely different
   ("Can't find a Mac running Changeover" vs. "Found Mac mini — enter the code").
3. **Mode A attempt** — read the shared key from `NSUbiquitousKeyValueStore`.
   Give it a short, bounded wait with a visible "checking iCloud" state, then
   fall through. Do not block indefinitely; KVS can take seconds or never arrive.
4. **Mode B entry** — the six-digit screen.
5. **Paired** — never show any of the above again unless the stored identity is
   rejected by the host.

Keep the state machine separate from the views so that a future Wi-Fi Aware
`DevicePairingView` can replace step 4 without touching steps 1–3 or 5.

### 2. The digit entry screen

- Six large digit boxes, not a single `TextField`. Implement as one hidden
  `TextField` bound to a `String` with the boxes rendering its characters — the
  standard approach, and the one that keeps paste and autofill working.
- `.keyboardType(.numberPad)`, `.textContentType(.oneTimeCode)`, and
  `@FocusState` set on appear so the keypad comes up without a tap.
- Filter input to digits and cap at six characters in the binding's setter;
  `.numberPad` still admits paste of arbitrary text.
- Auto-submit on the sixth digit. Requiring a Confirm tap after the sixth digit
  is a small, constant annoyance for no benefit.
- Show which host is being paired with — the Bonjour service name — so a user
  with two Macs is not guessing.

`.textContentType(.oneTimeCode)` is worth evaluating rather than assuming: it
enables the QuickType one-time-code bar, which is helpful if the code can reach
the phone through a system-visible channel and is dead weight otherwise. If it
produces a misleading empty suggestion bar, drop it.

### 3. Errors, expiry and retry

Three distinct failures, three distinct messages:

- **Wrong code** — clear the field, keep focus, say so. Do not navigate away.
- **Expired code** — the host's displayed code should have a lifetime; say that
  it expired and tell the user to look at the Mac for the new one. This is the
  case most likely to be diagnosed as "pairing is broken" if the message is
  generic.
- **Host unreachable mid-pairing** — a transport failure, not a credential
  failure. Route it to the reconnect handling from [#0087](0087.md) rather than
  telling the user their code was wrong.

Rate-limit attempts on the **host** side, not the client — client-side limiting
protects nothing. Six digits is a million combinations; without a host-side
limit and a code lifetime, an attacker on the LAN can brute-force write access to
the media library. If Phase 4 did not implement that, it is a [#0060](0060.md)
bug and this ticket should raise it rather than quietly shipping on top of it.

### 4. Persistence and Mode A entitlement

- Store the derived key in the iOS Keychain with
  `kSecAttrAccessibleAfterFirstUnlock` — the client needs it on a foreground
  reconnect after a suspension ([#0087](0087.md)), which can happen with the
  device locked. `WhenUnlocked` would fail exactly then.
- Add the iCloud key-value store entitlement to the iOS target for Mode A. It
  needs no CloudKit container and no push, per `RemoteControl.md`.
- Provide an explicit "Forget this Mac" action in settings. Without it, a
  mis-pairing or a host reinstall is unrecoverable short of deleting the app.

### 5. Ordering and risks

Build Mode B first and Mode A second, even though Mode A is the default when it
works. Mode B is the path that must work for everyone, it is independently
testable without matching iCloud accounts, and Mode A silently succeeding will
mask Mode B bugs during development.

- **Risk: Mode A hides Mode B.** On the developer's own devices, sharing an Apple
  ID, Mode A will always win and Mode B will never be exercised. Add a debug
  toggle to force Mode B, or test on a device signed out of iCloud.
- **Risk: re-prompting a paired client.** A connection failure must not look like
  a pairing failure. This is the most likely user-visible bug from this ticket
  and it interacts directly with [#0087](0087.md).
- **Risk: the host has no code lifetime or attempt limit.** Check before
  building. It is a Phase 4 gap, not something to work around here.

### 6. Verification

- **Unit-testable, and should be:** the pairing state machine's transitions
  (discovery → Mode A wait → Mode B → paired, and every failure edge), digit
  input filtering and the six-character cap, and the classification of a
  transport failure as not-a-credential-failure. These are pure logic and are
  where the real correctness lives.
- **Simulator-verifiable:** the digit screen's keyboard, focus, auto-submit,
  paste handling, Dynamic Type and both orientations.
- **Device- and host-bound:** an actual pairing against the real mini —
  a correct code, a wrong code, an expired code, and a second pairing attempt
  from an already-paired device. Plus the multi-Apple-ID case, which needs a
  device signed into a different iCloud account than the host, and the
  signed-out-of-iCloud case. The `## Verification` section must name which of
  these were actually run and on what hardware; the multi-account cases are the
  ones most likely to be skipped and they are the reason Mode B exists.
- **Negative test, required by Phase 4's exit criteria:** an unpaired device on
  the same network cannot control the host. Confirm from the iPhone specifically,
  not only from the Mac client.
