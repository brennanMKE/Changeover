## Description

`MovieMetadata.folderName` interpolates the TMDB title directly into a path component, so a title containing `/` — *Face/Off*, *Frost/Nixon*, *8½* variants — silently creates a nested directory instead of one Plex-matchable folder. The rip appears to succeed and the movie never shows up in Plex.

## Resolution notes

> 🟢 Resolved 2026-09-12 — Reviewed independently: 36 unit tests re-run and passed with all nine `MovieMetadataSanitizationTests` observed by name; with `pathSafe` reverted to the identity function exactly the seven substitution tests fail while `normalTitleIsUnchanged` and the 33-name round-trip still pass; the fixture was diffed against `Movies.txt` and matches it exactly minus the stray line 13; `{tmdb-ID}` never passes through the sanitizer.

## Long Description

`MovieMetadata.swift:17-19` builds `folderName` as `"\(title) (\(year)) {tmdb-\(tmdbID)}"` with no sanitization. `PlexOrganizer.move` (`PlexOrganizer.swift:16-19`) passes that straight to `NSString.appendingPathComponent`, then calls `createDirectory(atPath:withIntermediateDirectories: true)` at `:23`.

With `withIntermediateDirectories: true`, an embedded `/` is not an error — `FileManager` cheerfully creates the whole nested chain. For *Face/Off* (TMDB id 754) the result is:

```
Movies/
  Face/
    Off (1997) {tmdb-754}/
      Face/
        Off (1997).mp4        ← fileName has the same defect
```

Plex sees a folder named `Face` containing a folder named `Off (1997) {tmdb-754}`, matches neither, and the movie is absent from the library. `PlexOrganizer` logs `✓ Moved to: …` because the move genuinely succeeded — see [#0007](0007.md), which is why a wrong outcome reports as success.

The title is currently always a TMDB response value, so this is not an injection issue today — it is a correctness issue with legitimate real-world titles. That changes in Phase 4: [#0070](0070.md) covers the same code path when `MovieMetadata` arrives from a remote client, where `../..` in a title becomes a write outside the library on a host with `ENABLE_APP_SANDBOX = NO` (`project.pbxproj:402`, `:431`). **Fixing sanitization here closes the present-day bug and removes the sharpest edge of that later one.**

## Steps to reproduce

1. Insert any DVD.
2. Search TMDB for `Face/Off` and select the 1997 result (tmdb-754).
3. Start the rip and let it complete.
4. Look in the Plex Movies folder.

## Expected behavior

One folder, `Movies/Face-Off (1997) {tmdb-754}/`, containing `Face-Off (1997).mp4` — using whatever substitution the project settles on — and Plex matches it via the `{tmdb-754}` tag.

## Actual behavior

A nested `Movies/Face/Off (1997) {tmdb-754}/Face/Off (1997).mp4` chain. Plex matches nothing. The log reports success.

## Root cause

`MovieMetadata.folderName` and `MovieMetadata.fileName` (`MovieMetadata.swift:16-24`)
interpolated the raw TMDB `title` directly into what becomes a single
filesystem path component. `PlexOrganizer.move` then calls
`FileManager.createDirectory(atPath:withIntermediateDirectories: true)`
(`PlexOrganizer.swift:23`) against that string. With
`withIntermediateDirectories: true`, an embedded `/` is not an error — it
is silently treated as a path with multiple components, so `Face/Off`
creates `Movies/Face/Off (1997) {tmdb-754}/` instead of one folder. The
move genuinely succeeds (see #0007), so the log reports success even
though Plex can never match the result.

## Fix

Added a `nonisolated private static func pathSafe(_ value: String) -> String`
helper to `MovieMetadata`, applied to `title` inside both `folderName` and
`fileName` (the stored `title` property itself is left untouched, since
nothing today reads it besides these two computed properties, and a
future caller — search UI, logging — should still see the raw TMDB value).

Character decisions, following the plan's priority order:

- **`/`** — substituted with `-`, not stripped. "Face-Off" stays readable;
  "FaceOff" would not.
- **`:`** — the plan calls out deciding this explicitly rather than by
  omission. Decision made: treat it the same as `/` and substitute with
  `-`. Rationale: `:` is legal on APFS, but Finder renders it as `/` in
  the UI, producing the exact same visual/nesting confusion a real slash
  would, and it's no more welcome on the SMB/exFAT shares a Plex NAS
  setup plausibly uses. "Star Wars: Episode IV" becomes
  "Star Wars- Episode IV".
- **NUL** — stripped outright. Never meaningful in a TMDB title today;
  load-bearing once #0070 lets a remote, less-trusted client supply the
  title directly.
- **Leading `.`** — stripped, so a title can never produce a hidden
  folder/file. This runs before the empty-result fallback below, so a
  title that is only dots (e.g. a literal `".."`) collapses to an empty
  string rather than surviving as a `..` traversal component.
- **Trailing dots and spaces** — trimmed. Harmless on APFS, but broken on
  SMB/exFAT shares.
- **Empty result** — falls back to `"Untitled"` so `folderName`/`fileName`
  never degenerate to just `" (Year) {tmdb-ID}"` or `".mp4"`.

No divergence from the plan. Sanitization was applied only inside
`MovieMetadata`, not at the `PlexOrganizer` call site, per the plan's
scope note. `{tmdb-ID}` was left untouched — it's numeric and is what
Plex actually matches on. #0012 (delete-before-move) was left alone as a
separate issue.

### Review findings (phase 3)

Re-verified independently rather than from the drafted `## Verification`.

- **Independent run.** `xcodebuild … test -only-testing:ChangeoverTests` — `** TEST SUCCEEDED **`, 36 tests (the 27 that predate this ticket plus the nine in `MovieMetadataSanitizationTests`, every name observed in the output). Note the count in the draft (33) was correct at the time; #0011 and #0012 added three more before this review ran.
- **Falsified.** With `pathSafe` made the identity (`return value` inserted as its first line), the run fails exactly `slashInTitleIsSubstitutedNotStripped`, `colonInTitleIsSubstitutedExplicitly`, `nulByteIsStrippedOutright`, `leadingDotDoesNotProduceAHiddenFolder`, `wholeTitleOfDotDotFallsBackRatherThanTraversing`, `trailingSpaceInTitleIsTrimmed` and `trailingDotInTitleIsTrimmed` — seven — while `normalTitleIsUnchanged`, `sanitizingEveryKnownGoodLibraryNameIsANoOp` and every other test still pass. The fix was then restored and the tree checked against `18fbaee`.
- **The `:` decision is sound and is explicit in three places** — the doc comment on `pathSafe`, `## Fix`, and a test named for it. Plex matches on the `{tmdb-ID}` tag, so the title text is cosmetic and `Star Wars- Episode IV` costs nothing in matching. The substitution is also idempotent (the output contains no `/` or `:`), which is what makes the round-trip property hold for any name this code has ever produced.
- **`{tmdb-ID}` is untouched.** `tmdbID` is interpolated raw in `folderName` and `fileName` carries no tag; the 33-name no-op test would catch any drift.
- **Conventions hold.** `pathSafe` is `nonisolated private static`, which it must be since `folderName` / `fileName` are `nonisolated` for `PlexOrganizer`; no `actor`, no isolation annotations, nothing MainActor-bound touched.
- **Non-blocking, recorded so they are not rediscovered:** (1) the Windows-reserved set (`? * " < > | \\`) is not handled even though SMB/exFAT is the stated rationale for the trailing-dot trim — harmless on APFS, and if the library ever lives on a share the set belongs in this one function. (2) `TMDBMovie.yearText` falls back to `"—"` when TMDB has no release date, producing `Title (—) {tmdb-ID}`; same code path, different ticket. (3) `isSinglePathComponent`, the plan's "honest assertion", is exercised only by the slash test; fine, since that is the only case that can produce a second component.

## Plan

1. Add a `nonisolated` sanitizer to `MovieMetadata` — a single `pathSafe(_:)` helper applied to `title` in **both** `folderName` and `fileName`. Do not sanitize at the `PlexOrganizer` call site: the invariant belongs to the type that constructs the name, and Phase 4 will have other callers.
2. Characters to handle, in priority order:
   - `/` — the actual break. Substitute, don't strip: `Face-Off` reads correctly, `FaceOff` does not.
   - `:` — legal on APFS but rendered as `/` by Finder and a known irritant for titles like `Star Wars: Episode IV`. Decide explicitly rather than by omission.
   - Leading `.` — produces a hidden folder.
   - `..` as a whole component, and any NUL — meaningless from TMDB, load-bearing for [#0070](0070.md).
   - Trailing dots and spaces — harmless on APFS, break on SMB/exFAT shares, which is a plausible Plex setup.
3. Verify the result is a single path component. The cheap assertion is that the sanitized string contains no `/`; the honest one is that `(base as NSString).appendingPathComponent(name)` has exactly one more component than `base`.
4. Check the existing library for damage: `Movies.txt` lists 33 folders, none of which currently contain a separator, so no migration is needed — but confirm before assuming. A previously-ripped affected title would already be sitting in a nested folder.
5. Leave `{tmdb-ID}` untouched — it is numeric and is what Plex actually matches on.

Constraints: `MovieMetadata` is a plain `struct` under `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`, and `folderName` / `fileName` are already `nonisolated` because `PlexOrganizer` is `nonisolated static`. The sanitizer must be `nonisolated` too.

## Notes

**Fully unit-testable — no disc required.** This is a pure string transformation, which makes it one of the few Phase 1 items with an honest automated verification story. Cases owed: `Face/Off`, a leading dot, `..`, a trailing space, a colon title, and a normal title asserted unchanged (a sanitizer that mangles the 33 known-good names in `Movies.txt` is a regression). `ChangeoverTests` currently holds a single empty stub, so the test count moving from 1 to N is itself a signal.

Worth adding a round-trip test over every title in `Movies.txt`: sanitizing an already-correct folder name must be a no-op.
