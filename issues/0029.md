# 0029 — HandBrake keeps only the first audio track, so chosen languages never reach the MP4

| | |
|---|---|
| **Status** | open |
| **Phase** | 2 — Choose what gets ripped |
| **Module** | EncodeController |
| **Platform** | macOS |
| **First seen** | 2026-09-11 |

## Description

`EncodeController` invokes HandBrakeCLI with no audio or subtitle selection flags
(`Changeover/EncodeController.swift:20-28`). With no `--audio` or
`--audio-lang-list`, HandBrake encodes the first audio track and discards the rest —
so even once [#0027](0027.md) lets the user pick English and Spanish, the output MP4
will contain whichever single track the disc listed first.

## Long Description

Phase 2's third exit criterion is *"Selected audio languages are present in the
output and unselected ones are not"* (`Roadmap.md` line 126). Choosing them
([#0027](0027.md)) does not achieve it; this does. The two halves are split because
the picker is unit-testable and this is not — proving a track survived into an `.mp4`
means encoding a real disc and inspecting the result.

Two substantive findings came out of planning this:

**Subtitles are not symmetric with audio.** Most DVD subtitles are VOBSUB — bitmap
images — and the MP4 container does not carry bitmap subtitle tracks. HandBrake will
either drop them or burn them into the picture. So for the current output format
(`--format av_mp4`, `Changeover/EncodeController.swift:23`), "select subtitle
languages" cannot mean "get selectable subtitle tracks". `Roadmap.md` line 119 pairs
audio and subtitle selection as though they were the same job; they are not, and the
resolution has to be an explicit choice rather than a surprise in the output.

**But the blanket deferral this ticket recommended is too broad, and the fixtures
show why.** Four of the seven captured movie discs — Dragon Tattoo, Super Troopers, Super
Troopers 2 and Spider's Web — carry an `S_CC608/DVD` stream that MakeMKV converts to
**text**, not bitmap:

```
SINFO:3,1,5,0,"S_CC608/DVD"
SINFO:3,1,30,0,"CC→Text English ( Lossy conversion )"
```

(`ChangeoverTests/Fixtures/makemkvcon/dragon-tattoo-min0.txt`.) MP4 carries text
subtitle tracks perfectly well. So the honest statement is narrower than the one
this ticket was filed with:

- **Bitmap `S_VOBSUB` → genuinely blocked** in MP4. Deferral stands.
- **`S_CC608/DVD` → not blocked.** It is a closed-caption track converted to text,
  it is the *English* track on a majority of the corpus, and it is exactly the
  subtitle a Plex library wants. Whether it is worth wiring in Phase 2 is a cost
  question, not a feasibility one — and "MP4 cannot carry DVD subtitles" must stop
  being written as though it were feasibility.
- **Forced `S_VOBSUB` (attribute 22 == 4096) → blocked as a track, useful burned
  in.** Ten such streams across the corpus. This is what `--subtitle scan
  --subtitle-forced` already half-addresses.

Note the conversion is marked `( Lossy conversion )` by MakeMKV, against
`( Lossless conversion )` on every other stream. CC608 is a caption stream with
positioning and formatting that plain text discards. That is a quality caveat worth
stating in the UI, not a reason to drop it.

**`--aencoder` is a per-track list, not a global setting.** The current
`copy:aac,copy:ac3` (`:25`) supplies two entries. With one selected track the second
is unused; with three selected tracks HandBrake reuses the last entry for the
remainder. The value happens to work today only because exactly one track is ever
encoded. It will not survive the change to multiple tracks without being rethought.

## Steps to reproduce

1. Rip and encode a DVD that carries English, Spanish and French audio.
2. Inspect the finished `.mp4` in the Plex Movies folder (`ffprobe`, or the audio
   menu in a player).

## Expected behavior

The MP4 contains one audio track per selected language and no others, each tagged
with its language so Plex shows a correct audio menu. Whatever the ticket decides
about subtitles, the decision is stated in the UI at selection time rather than
discovered in the output — and a disc carrying a text-convertible `S_CC608/DVD`
track is not told that subtitles are impossible.

## Actual behavior

The MP4 contains one audio track — the disc's first, whatever language that is.
Nothing in the app expresses a preference:
`--aencoder copy:aac,copy:ac3 --subtitle scan`
(`Changeover/EncodeController.swift:24-27`) is a fixed string built from
`Config.audioEncoder` (`Changeover/Config.swift:11`).

## Notes

**This is the least automatable ticket in Phase 2 and the `## Verification` must say
so plainly.** The proof is: encode a multi-language disc, run `ffprobe` on the
resulting `.mp4`, and confirm the audio stream count and the `language` tag on each.
Record the disc and paste the relevant `ffprobe` output.

Two discs are worth naming as the verification set, because the corpus says what to
expect from them. **Hanna** has English 5.1, Spanish 5.1, French 5.1, English
stereo and an English commentary (attribute 22 == 1) on title 3 — a preference of
`["eng","spa"]` should yield the English and Spanish tracks and not the commentary.
**Hornets' Nest** has no language tags at all, so the correct outcome is *both*
audio tracks surviving; an MP4 with one track, or none, is the failure this ticket
most needs to rule out and the one `--audio-lang-list` makes easy to cause.

What *is* unit-testable, and should be extracted for exactly that reason, is the
argument construction: given a `RipRequest` with `["eng", "spa"]`, assert the
resulting `[String]` argument array. That pins the flag combination — including the
encoder-list length rule below — without needing HandBrake installed. Neither
`HandBrakeCLI` nor `makemkvcon` is present at the paths
`Changeover/AppSettings.swift:14-15` defaults to on a typical dev machine, so
anything requiring the binary runs on the mini.

### Audio

Replace `--aencoder copy:aac,copy:ac3` (`:25`) with:

```
--audio-lang-list eng,spa
--all-audio
--aencoder copy
--audio-copy-mask aac,ac3
--audio-fallback av_aac
```

- `--audio-lang-list` + `--all-audio` selects every track in the listed languages
  rather than just the first per language. A disc with both a 5.1 and a stereo
  English track will yield both; that is the right default for a Plex library, and
  the per-language track counts shown by [#0027](0027.md)'s picker tell the user to
  expect it.
- `--aencoder copy` with `--audio-copy-mask` passes AC3 and AAC through untouched and
  only re-encodes what MP4 cannot carry. `--audio-fallback av_aac` handles DVD tracks
  that are neither (DTS, LPCM). This replaces the positional
  `copy:aac,copy:ac3` list, which silently misbehaves once the track count varies —
  the real reason to change it, beyond it being wrong.
- Emit the language list from the `RipRequest`, joined with commas, lowercase ISO
  639-2 codes as MakeMKV reports them.
- **Guard the empty case.** If `audioLanguages` is empty, omit
  `--audio-lang-list` entirely rather than passing an empty value — an empty list
  plus `--all-audio` is undefined behaviour across HandBrake versions, and the
  degenerate outcome (a silent movie) is the worst possible failure here.
  [#0027](0027.md) should make it unreachable; defend anyway.

`Config.audioEncoder` (`Changeover/Config.swift:11`) becomes wrong as a single
string. Replace it with `audioCopyMask` and `audioFallbackEncoder` constants, keeping
the `nonisolated static let` form the file already uses (`:8,11`) — that annotation
is required because `EncodeController` reads them from a `nonisolated` context, as
`Plan.md`'s conventions table notes.

### Subtitles — pick one and write down why

`--subtitle scan` (`:26`) today performs a forced-subtitle scan and nothing else.
Four options now, because the CC608 finding added one that did not exist when this
ticket was filed:

1. **Drop subtitle selection from Phase 2 output and say so.** Keep
   `--subtitle scan --subtitle-forced` so foreign-dialogue forced subtitles still
   appear, do not offer a subtitle language picker, and file the rest as a follow-on.
   Cheapest, and satisfies every stated exit criterion — none of which mentions
   subtitles. **It is no longer fully honest**, because it drops a text track that
   MP4 could carry on four of seven discs.
2. **Carry the `S_CC608/DVD` text tracks and nothing else.** `--subtitle` with the
   track numbers of the CC608 streams (HandBrake numbers subtitle tracks in source
   order), no `--subtitle-burned`. MP4 accepts text subtitles, so this needs no
   container change and no `MovieMetadata.fileName` change. The cost is mapping
   MakeMKV's stream indices to HandBrake's subtitle track numbers, which is not
   one-to-one and is the actual work in this option. **Verify the mapping against a
   real encode before trusting it** — nothing in the fixtures proves it.
3. **Burn in one selected subtitle track.**
   `--subtitle <track> --subtitle-burned`. Works in MP4, but it is destructive and
   irreversible in the library, and only one can be burned. Wrong default for a Plex
   library; defensible as an explicit opt-in for a forced track.
4. **Switch the container to MKV.** `--format av_mkv` carries VOBSUB natively and
   `--subtitle-lang-list eng,spa --all-subtitles` then does what the picker implies.
   But it changes the file extension, which `MovieMetadata.fileName` hard-codes to
   `.mp4` (`Changeover/MovieMetadata.swift:22-24`) and which the Plex naming
   convention in `Plan.md` and `Movies.txt` is written around, and
   `mac_plex_dvd_workflow.md` §4.2 chose MP4 deliberately for Apple TV direct play.
   Too big a change to make as a side effect of a subtitle picker.

**Recommendation: option 1 for Phase 2, with option 2 as the immediate follow-on**,
and the picker in [#0027](0027.md) labelled honestly: forced-only for bitmap subs,
"available, not yet wired" for a CC608 text track. Option 2 is small enough that it
may be worth folding in directly if the track-number mapping turns out to be
straightforward — decide on evidence from one encode, not in advance.

File options 2 and 4 as a follow-on ticket in the Phase 2 block (next free id after
[#0032](0032.md)) before resolving this one, and link it both ways — a subtitle
story deferred in prose disappears the moment this closes. Do **not** repeat the
claim that MP4 cannot carry DVD subtitles in that ticket; say bitmap, and say which
discs have text.

#### The type

Add this to `EncodeController.swift`, next to `TitleSelection`:

```swift
nonisolated enum AudioSelection: Equatable, Sendable {
    /// No --audio; --aencoder Config.audioEncoder. Today's vector, byte for byte.
    case sourceDefault
    /// HandBrake TrackNumbers from the same scan as the title (the disc path).
    case tracks([Int])
    /// For the MakeMKV fallback's .mkv, whose track numbers differ from the disc's.
    /// Empty means every track.
    case languages([String])
}
nonisolated static func audioArguments(_ selection: AudioSelection) -> [String]
```

`arguments(source:title:output:filter:audio: AudioSelection = .sourceDefault)`
replaces its `"--aencoder", Config.audioEncoder` pair with `audioArguments(audio)`,
in the same position. `encode(… audio: AudioSelection = .sourceDefault …)` passes it
through. Every existing call site and exact-vector test stays as it is.

#### Rules for `audioArguments`

- **`.sourceDefault`** → `["--aencoder", Config.audioEncoder]`.
- **`.tracks(t)`**
  - Drop repeated and non-positive track numbers, keeping order.
  - If nothing is left, behave exactly like `.sourceDefault`. **Never emit
    `--audio none`**, because a silent movie is the worst failure available here.
  - Otherwise the first track gets the verified pair and every later track gets one
    passthrough entry:
    `["--audio", "t0,t0,t1,…", "--aencoder", "copy:aac,copy:ac3,copy:ac3,…"]`.
  - The two lists always have the same length, so HandBrake's reuse rule for a short
    encoder list is never exercised.
  - `copy:ac3` on a source that isn't AC3 falls back to HandBrake's default AAC
    encoder. `copy:aac` already depends on that same fallback today.
- **`.languages(l)`**
  - Normalize the codes and drop repeats.
  - A non-empty list →
    `["--audio-lang-list", l.joined(separator: ","), "--all-audio", "--aencoder", "copy:ac3"]`.
  - An empty list → `["--all-audio", "--aencoder", "copy:ac3"]`.
  - A positional encoder list can't be matched to an unknown number of tracks.
    Whether HandBrake reuses the last `--aencoder` entry for every matched track is
    **unverified**. It is checked on joe (see below).
- **`Config`**
  - Add `nonisolated static let audioCompatibilityEncoders = ["copy:aac", "copy:ac3"]`
    and `nonisolated static let audioPassthroughEncoder = "copy:ac3"`.
  - Define `audioEncoder` as the joined pair, so `qualityAndAudioEncoderComeFromConfig`
    still holds.

#### User decision

Which selected tracks should get the AAC stereo compatibility copy? The options are
the first selected track only, every selected track, or none. The default above is
the first track only, which keeps a one-track output identical to the file already
verified in Plex. This is a question about the user's playback devices, so the code
can't settle it.
