# 0072 — The connection will not survive a host restart, a Wi-Fi drop or the laptop sleeping

| | |
|---|---|
| **Status** | open |
| **Phase** | 4 — Remote control from a Mac |
| **Module** | RemoteClient / RemoteServer |
| **Platform** | All |
| **First seen** | 2026-09-11 |

## Description

A remote that stops working the first time the MacBook lid closes is not usable from a couch. Both ends need lifecycle handling the basic connect path does not provide: the client must re-browse and reconnect with backoff after sleep, Wi-Fi changes and host restarts, and the host must keep advertising across its own sleep/wake and network changes rather than going quietly undiscoverable.

## Long Description

This is a named Phase 4 exit criterion — "client survives host restart, Wi-Fi drop
and laptop sleep" — and it is the difference between a demo and something used
daily. The realistic sequence during the intended loop is: make selections, close
the lid, walk over, swap a disc, come back, open the lid. Every one of those is a
connection-breaking event.

`RemoteControl.md` flags the host half under risks: "**Sleep kills discovery.** If
the mini sleeps, Bonjour advertisement stops. Use `ProcessInfo.beginActivity` to
hold off idle sleep during jobs, and consider a 'stay discoverable' setting." The
`beginActivity` part is Phase 3 ([#0040](0040.md)) and covers only *during* jobs.
The gap this ticket closes is the idle host: the mini has been sitting idle for an
hour, has slept, and the client cannot find it — which reads as "the app is broken",
not "the computer is asleep".

The reason this is a modest ticket rather than a large one is [#0069](0069.md):
reconnect is not a separate code path, it is re-running `subscribe`. If this ticket
starts introducing reconnect-specific state, something has gone wrong upstream.

## Steps to reproduce

1. Connect the client to the host and start a rip.
2. Close the MacBook lid for two minutes, then open it.
3. Separately: restart Changeover on the mini while the client is connected.
4. Separately: move the MacBook from Wi-Fi to a wired dock, or switch bands.
5. Separately: leave the mini idle for an hour, then try to connect.

## Expected behavior

In every case the client reconnects on its own within a few seconds, re-runs the
handshake, and shows correct current state — including a job that finished while it
was asleep. The UI shows "Reconnecting…" while it happens, not a frozen last-known
view presented as live. The idle mini is still discoverable, or the app tells the
user plainly that the host is asleep.

## Actual behavior

Nothing exists yet. With a naive implementation each of these leaves the client
showing stale state indefinitely, or stuck in a failed state until relaunched — and
an idle mini simply disappears from the network.

## Plan

**Client — the reconnect loop.** Wrap `RemoteSession.start()` from
[#0071](0071.md):

- On any connection error or clean close, transition to `.reconnecting(attempt:)`
  and retry with exponential backoff and jitter: 0.5s, 1s, 2s, 4s, 8s, then hold at
  15s indefinitely. Jitter matters when several clients reconnect after the same
  Wi-Fi event.
- **Re-browse, do not reuse the cached endpoint.** After a host restart or a DHCP
  change the endpoint is stale. Bonjour resolution is cheap; a stale endpoint costs
  a full connect timeout per attempt.
- Reset backoff to zero on a successful handshake, not on a successful TCP connect —
  a host that accepts and then rejects on `.notPaired` must not be hammered.
- A clean close from the host (`applicationWillTerminate`, [#0068](0068.md)) sets a
  longer initial delay and a distinct UI message ("Changeover quit on the host") —
  the user quit it; do not reconnect aggressively for a minute.
- `.notPaired`, `.revoked` and `.wireVersionMismatch` are **terminal**. Stop
  retrying and say what is wrong. Retrying a revoked key forever is both useless and
  the shape of a device that has been removed but will not go away.

**Client — platform lifecycle.** On macOS, observe
`NSWorkspace.willSleepNotification` and `didWakeNotification` (the same
`NSWorkspace.shared.notificationCenter` `DVDMonitor` already uses,
`Changeover/DVDMonitor.swift:7-12`): tear down cleanly on sleep, and on wake reset
backoff and reconnect immediately rather than waiting out a timer that was frozen.
Also observe network path changes via the transport so a Wi-Fi-to-Ethernet move
triggers an immediate re-browse. Keep the sleep/wake observation in the app target,
not the package — `NSWorkspace` does not exist on iOS, and [#0080](0080.md) will
need `scenePhase` instead. Expose it as a `RemoteSession.networkConditionsChanged()`
call the platform layer invokes.

**Host — stay discoverable.** Two parts:

- Re-arm the advertisement after wake and after a network path change. Do not assume
  the listener from [#0068](0068.md) survives either. On
  `NSWorkspace.didWakeNotification`, and on a path change, stop and restart the
  advertiser. Log both — an advertisement that quietly failed to re-register is
  otherwise invisible and presents as "the client can't find the host sometimes",
  the worst class of bug to chase.
- Add a **Stay discoverable** setting in `SettingsView` (default on). When on, the
  host holds a `ProcessInfo.beginActivity(options: .idleSystemSleepDisabled,
  reason: "Changeover remote discovery")` for as long as the server is running.
  Store it on `AppSettings` next to the existing values
  (`Changeover/AppSettings.swift:13-16`) with a matching key in the `Keys` enum
  (`:58-63`) and a line in `persist()` (`:48-54`). Word the setting honestly — it
  keeps a Mac mini awake, which some users will not want, and it is useless on a
  laptop host. Note that this is *idle sleep* only: a user-initiated sleep or a
  closed lid still sleeps, and nothing in the app can prevent that. The UI must not
  imply otherwise.
- Keep the existing job-duration activity from [#0040](0040.md) separate from this
  one; they have different reasons and lifetimes, and `beginActivity` returns a token
  per assertion.

**Both ends — heartbeat.** `RemoteCommand.ping` / `RemoteEvent.pong` exist in the
protocol ([#0061](0061.md)) for this. A dropped Wi-Fi connection often does not
surface as a socket error for minutes; TCP keepalive defaults are far too slow for a
UI. Client pings every 10s and treats two missed pongs as a disconnect. The host
does the same in reverse so it can reap dead connections rather than fanning events
into sockets nobody is reading — which matters because [#0068](0068.md) bounds the
per-connection send queue, and a dead client that is never reaped just accumulates
drop markers.

**UI honesty.** While reconnecting, the client must visibly mark its data as stale.
A greyed panel with "Reconnecting — last updated 14:32" is correct; showing the last
known progress bar as though it were live is not. This is the single most important
UX detail in the ticket: a remote that lies about being connected is worse than one
that disconnects visibly.

## Notes

**Unit-testable without hardware:** backoff and jitter arithmetic (assert the
sequence and that jitter stays in bounds); that a successful *handshake* resets
backoff but a successful connect alone does not; that `.notPaired`, `.revoked` and
`.wireVersionMismatch` stop the loop; heartbeat timeout logic driven by an injected
clock; and — against the `InMemoryTransport` from [#0062](0062.md) — that a
simulated drop mid-job followed by a reconnect leaves `RemoteSession` with exactly
the post-reconnect state and no merged remnants of the pre-drop state.

**Requires two real machines, and there is no substitute.** This is the least
simulatable ticket in the phase. The manual matrix, each to be run and recorded in
`## Verification` per the caveat in `issues/Issues.md`:

1. Lid close / open, idle.
2. Lid close / open, mid-rip — must land showing the job further along.
3. Lid close for longer than a job takes — must land showing the job finished.
4. Quit and relaunch Changeover on the mini.
5. Force-quit Changeover on the mini (no clean close).
6. Toggle client Wi-Fi off and on.
7. Move the client between Wi-Fi and a wired connection.
8. Let the mini idle-sleep with Stay discoverable off, then on.

Case 3 is the one most likely to expose a merge bug in [#0071](0071.md) and case 5
the one most likely to expose a missing heartbeat.
