## Description

Rip and encode progress is held as `@State` inside `MetadataEntryView` (`isProcessing` and `logLines`, `MetadataEntryView.swift:7-8`), so nothing outside that one view can observe a job. Close the window mid-rip and reopening builds a brand-new view with an empty log and an enabled Start Ripping button — the running job becomes invisible and a second `makemkvcon` can be launched against the same drive.

## Resolution notes

> 🟢 Resolved 2026-09-11 — Reviewed independently: 24 unit tests and 4 UI tests re-run and passed, and both halves of the bug were falsified by hand — restoring the `w.isVisible` window guard breaks `closingAndReopeningReusesTheSameWindow`, and deleting the `guard !isRunning` re-entrancy check breaks `secondStartWhileRunningIsRefused` and nothing else.

## Root cause

Two defects, and the ticket is only fixed if both go. The first is where the state lived: `isProcessing` and `logLines` were `@State` on `MetadataEntryView`, so the running `Task`'s log closure wrote into one specific view instance and nothing else in the app could see that a job existed. The second is what made that fatal: `showMetadataEntry()` reused `metadataWindow` only when `w.isVisible` was true. A closed window is not visible, so the guard fell through and built a brand-new `NSWindow` + `NSHostingView`, assigning it over the old one — a fresh view with an empty log, an enabled Start Ripping button, and a fresh `MovieSearchViewModel`. The first job kept running, invisibly, and a second `makemkvcon` could be launched against the same drive and the same shared working directory.

## Fix

Added `Changeover/JobController.swift`: a plain `@Observable final class` (MainActor for free under `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`, deliberately **not** an `actor`) owned by `AppDelegate` as `let jobs` and injected into both hosted views with `.environment(_:)`. It holds `logLines`, `isRunning`, `currentMetadata`, `currentJobID`, `insertedDiscURL` and the `JobOutcome` from [#0007](0007.md) as `lastOutcome` — the `@State private var lastOutcome` that ticket parked in the view is deleted. `JobFailure` already carries its own `stage`, so the controller adds no parallel stage bookkeeping.

`start(metadata:settings:)` is `@discardableResult -> Bool`: it returns `false` and logs a visible warning when a job is already running. That is the app-level re-entrancy guard the ticket asks for — per-view `isProcessing` could never provide it, because a freshly built view starts at `false`. `append(_:)` trims `logLines` to the last 2000 entries, since the log now outlives the window and is no longer reset by view teardown.

The pipeline call sits behind an injectable `Runner` seam (`typealias Runner = @MainActor (MovieMetadata, AppSettings, @escaping @MainActor (String) -> Void) async -> JobOutcome`), defaulting to `JobController.pipelineRunner`, which is the real `DVDPipeline`. That is what makes the controller testable without `makemkvcon`, `HandBrakeCLI` or a disc.

**There is no `cancel()`.** The plan offered a choice; cancelling the Swift `Task` would not kill the child `Process`, so the UI would claim the rip had stopped while `makemkvcon` kept running. Real cancellation needs `Process.terminate()` plumbed through `RipController` / `EncodeController`, which is out of scope here, so the method is omitted entirely and the reason is recorded in the type's doc comment rather than shipped as a button that lies.

`showMetadataEntry()` now reuses `metadataWindow` whenever it is non-nil. `isReleasedWhenClosed = false` was already set, so the object survives a close and is simply re-ordered front.

Two deliberate extras, both named in the plan. `StatusMenuView` stops hardcoding `"Idle — insert a DVD to begin"` and renders `jobs.statusDescription` (`"Working on <title>…"` while running), with the status dot going blue for a running job. And `DVDMonitor.onDVDInserted` now carries the mounted volume's `URL`, which `AppDelegate` stores in `jobs.insertedDiscURL` — without that, the property the plan specifies would have been dead code for [#0005](0005.md) to discover.

Held to scope: `@State private var vm = MovieSearchViewModel()` stays on the view (its lifetime genuinely is the view's); no cleanup, eject, notification, per-job working directory, preflight or failure presentation. `JobFailure.logTail` is still read by nothing — that is [#0009](0009.md)'s input.

## Gotchas

- `@escaping` **is** accepted inside a `typealias` for a function type, and is required here: without it, the `log` parameter of the `Runner` closure is non-escaping and `pipelineRunner` cannot hand it to `DVDPipeline`, which stores it (`error: passing non-escaping parameter 'log' to function expecting an '@escaping' closure`).
- The test targets do **not** set `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` — only the app target does. Test suites touching `JobController` or `AppDelegate` therefore need an explicit `@MainActor` on the suite type. The project is on `SWIFT_VERSION = 5.0`, so getting this wrong produces warnings rather than errors, which is exactly how it would go unnoticed.
- AppKit window lifecycle is unit-testable in this project's test bundle: the tests are hosted by the app, so `AppDelegate()` can be constructed and `showMetadataEntry()` called for real. That is a far more reliable way to test window reuse than a UI test trying to click an `NSStatusItem`.
- `showSettings()` still has the identical `if let w = settingsWindow, w.isVisible` bug — a closed Settings window is rebuilt rather than reused. It was left alone as out of scope (no job state hangs off it), but it leaks an `NSWindow` per reopen and should get the same one-line fix.

## Long Description

`AppDelegate.showMetadataEntry()` (`AppDelegate.swift:69-93`) only reuses the existing window when `w.isVisible` is true. A closed window fails that test, so a fresh `NSWindow` and `NSHostingView` are built and assigned to `metadataWindow` (line 92), releasing the previous one. Meanwhile the `Task` started in `startRipping()` (`MetadataEntryView.swift:148-154`) is still alive — it captured `metadata` and `settings` and a log closure that appends to the *old* view's `logLines`. The job keeps running and keeps writing into a view nobody can see.

There is no app-level re-entrancy guard anywhere. `isProcessing` is per-view state, so a second view instance starts at `false` and the Start Ripping button (`MetadataEntryView.swift:129`) is enabled again.

This is also the structural prerequisite the roadmap calls out for Phases 3 and 4: a queue and a remote fan-out both need a job that exists independently of any window.

## Steps to reproduce

1. Insert a DVD, search for the movie, select a result, click **Start Ripping**.
2. While the rip log is streaming, close the Changeover window.
3. Open the menu bar popover and click **Open…**.
4. A window appears with an empty log area and an idle UI.
5. Search, select any movie, and click **Start Ripping** again.

## Expected behavior

One job at a time, tracked at the app level. Reopening the window reattaches to the running job and shows its accumulated log and current stage. Start Ripping is disabled while any job is running. Closing the window does not affect the job.

## Actual behavior

The reopened window shows no sign that a job is running. Start Ripping is enabled and a second `DVDPipeline` can be started concurrently against the same optical drive and the same shared working directory. The first job's log lines go to a released view.

## Notes

Partly unit-testable. With the pipeline call behind a small injectable seam, tests can assert that a second `start(...)` while running is rejected, that `logLines` accumulate and are capped, and that state survives the caller going away. Those tests are real and must be run and observed passing.

What cannot be automated: that closing and reopening the *window* reattaches correctly. That needs the app running. It does **not** need a physical disc — point `makemkvconPath` at a shell script that prints a few lines and sleeps, and the whole window-lifecycle behavior is exercisable. A real disc is still needed for a final end-to-end pass. State plainly in `## Verification` which parts were manual.

## Plan

### New file: `Changeover/JobController.swift`

```swift
@Observable
final class JobController {
    private(set) var logLines: [String] = []
    private(set) var isRunning: Bool = false
    private(set) var currentMetadata: MovieMetadata?
    private(set) var currentJobID: String?
    var insertedDiscURL: URL?          // written by the DVD monitor, read by #0005
    private var task: Task<Void, Never>?
}
```

A plain `final class` — **not** an `actor`. `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` is set on this project (`Plan.md` "MainActor default isolation"), so this type is `@MainActor` for free and needs no annotation, exactly like `DVDPipeline` (`DVDPipeline.swift:9`). `@Observable` from the Observation module, never `ObservableObject`.

Methods:

- `func start(metadata: MovieMetadata, settings: AppSettings)` — `guard !isRunning else { return }`, clear `logLines`, set `currentMetadata` and a fresh `currentJobID`, build the `DVDPipeline` with a log closure that appends to `self.logLines`, and store the `Task`. Set `isRunning = false` when the task completes.
- `func cancel()` — cancels the task. Note honestly in the code that cancelling the Swift task does **not** kill the child `Process`; a real cancel needs `Process.terminate()` plumbed through `RipController`/`EncodeController`, which is out of scope here. Either implement the plumbing or omit `cancel()` entirely rather than shipping a button that lies.
- `private func append(_ line: String)` — appends and trims to the last ~2000 lines. The log now outlives the window, so unbounded growth is a real leak; today `logLines` is reset on every `startRipping()` (`MetadataEntryView.swift:146`) and dies with the view.

### `Changeover/AppDelegate.swift`

- Add `let jobs = JobController()` beside `let settings = AppSettings()` (line 8).
- Inject it into both hosted views: `StatusMenuView().environment(settings).environment(jobs)` (line 43) and `MetadataEntryView().environment(settings).environment(jobs)` (line 87). Keep `SettingsView(settings:)` as-is — it takes `@Bindable var settings` directly (`SettingsView.swift:5`) and has no job concern.
- Fix window reuse in `showMetadataEntry()` (lines 72-76): reuse `metadataWindow` whenever it is non-nil, not only when `isVisible`. `isReleasedWhenClosed = false` is already set (line 89), so the window object survives a close and can simply be re-ordered front. This is the actual mechanism of the orphaning and must be fixed alongside the state move — otherwise the new window gets a fresh `MovieSearchViewModel` and loses the user's search results too.

### `Changeover/MetadataEntryView.swift`

- Delete `@State private var isProcessing` and `@State private var logLines` (lines 7-8).
- Add `@Environment(JobController.self) private var jobs`.
- `logArea` (lines 93-119) reads `jobs.logLines`; its guard becomes `!jobs.logLines.isEmpty || jobs.isRunning`.
- `actionBar` (lines 123-133) disables on `vm.selectedMovie == nil || jobs.isRunning`.
- `startRipping()` (lines 142-155) collapses to building `MovieMetadata` and calling `jobs.start(metadata:settings:)`.
- **Keep `@State private var vm = MovieSearchViewModel()` (line 5) as it is.** The `@State`-owned-view-model convention still applies to view models whose lifetime *is* the view's. `JobController` is the exception precisely because it must outlive the view, which is why `AppDelegate` owns it and it arrives through `@Environment`.

### Status surfacing

With job state app-level, `StatusMenuView` (`StatusMenuView.swift:16-20`) can stop hardcoding `"Idle — insert a DVD to begin"` and show the running job instead. Small, in scope, and the first visible payoff of the refactor.

### Ordering and risks

Do [#0007](0007.md) first if possible, so `JobController` is written once against the typed outcome rather than against `Void`.

Risks:

- `@Environment(JobController.self)` traps at runtime if the object was never injected. Both hosting views must be updated; a missed injection is a crash, not a warning.
- The `DVDPipeline` call is made from `JobController` now, so the log closure captures `self`. Keep the closure `@MainActor (String) -> Void` to match `DVDPipeline.log` (`DVDPipeline.swift:12`) and avoid retain-cycle noise by using an unowned or weak capture where appropriate.
- Do not move `MovieSearchViewModel` to `AppDelegate` as well. Search state is genuinely per-window and hoisting it would be scope creep into Phase 4's multi-client arbitration.
