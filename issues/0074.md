## Description

Neither app declares `NSLocalNetworkUsageDescription` or `NSBonjourServices`, so the first time `RemoteServer` starts listening macOS will either deny Local Network access outright or throw a modal prompt — on a Mac mini that is typically headless. `Changeover/Info.plist` is an empty dictionary today. Without these keys and a documented first-run procedure, discovery fails in a way that looks like a network bug.

## Root cause

`Changeover/Info.plist` was a literal empty `<dict/>`. The project merges
`GENERATE_INFOPLIST_FILE = YES` build settings over `INFOPLIST_FILE =
Changeover/Info.plist` at `project.pbxproj:404-405/:433-434`, but nothing —
neither the plist file nor an `INFOPLIST_KEY_*` build setting — supplied
`NSLocalNetworkUsageDescription` or `NSBonjourServices`. With no usage
description, macOS has no string to show in the Local Network permission
prompt (or denies outright); with no `NSBonjourServices`, `_changeover._tcp`
advertising has no declared service type. The only key set anywhere was
`INFOPLIST_KEY_LSUIElement`.

## Fix

Scoped to exactly what the 2026-09-15 plan refresh marks "pure code,
implementable now, item 1" — the Info.plist keys plus a unit test that reads
them from the built bundle. Everything else in the refresh (the
`RemoteConstants.bonjourServiceType` package constant, the
`LocalNetworkStatus.interpret(_:)` denial-inference seam, the Settings
"Enable remote control" action, `StatusMenuView` warning UI, and the README
headless procedure) is out of scope for this pass and left for the tickets
that already own them (#0061, #0063, #0068).

  keys are more reviewable in the file, and `NSBonjourServices` is an array,

  Macs, iPhones and iPads in your home can see the disc, choose what to rip,

- `NSBonjourServices`: `["_changeover._tcp"]`, matching the service type

  `Packages/` directory), and the orchestrator's scope for this pass was
  narrowed to the Info.plist keys and their test only. The new unit test

## Long Description

`RemoteControl.md` names this twice: all clients need
`NSLocalNetworkUsageDescription` and `NSBonjourServices` in Info.plist, and
separately, "for the host, that prompt appearing on a headless mini is a real setup
step to document."

The headless case is the awkward one and it is worth being concrete about why. The
prompt is a system modal that appears on the mini's own display. If the mini runs
without a monitor, the user reaches it by Screen Sharing — which works, but only if
they know to look, and only if the app is frontmost enough for the prompt to be
visible. Changeover is `LSUIElement = YES` (`project.pbxproj:406`, `:435`), so it has
no Dock icon and no menu bar presence beyond the status item; there is nothing
obvious to click to bring it forward. A denied or dismissed prompt then persists
silently, and the symptom is "the client cannot find the host", which is exactly the
symptom of a dozen unrelated network problems.

There is a second, subtler failure: the permission is tied to the app's code
signature. During development the signature changes on every build, so the prompt can
recur or the grant can silently lapse — which produces intermittent discovery
failures that look like a bug in [#0068](0068.md) or [#0072](0072.md). Knowing this
in advance saves a day.

## Steps to reproduce

1. Build and run Changeover with `RemoteServer` from [#0068](0068.md) enabled.
2. Observe the Info.plist: `Changeover/Info.plist` contains an empty `<dict/>`.
3. Try to discover the host from a second Mac.

## Expected behavior

Both apps declare a clear usage description and their Bonjour service types. The
host requests the permission at a moment the user is looking at the screen, shows its
current permission state in the UI, and the README documents the headless
first-run procedure including how to check and reset the grant.

## Actual behavior

`Changeover/Info.plist` is empty, `grep INFOPLIST_KEY Changeover.xcodeproj/project.pbxproj`
shows only `INFOPLIST_KEY_LSUIElement`, and nothing anywhere mentions Local Network.
Discovery would fail with no in-app explanation.

## Plan

**Where the keys go.** The project sets both `GENERATE_INFOPLIST_FILE = YES` and
`INFOPLIST_FILE = Changeover/Info.plist` (`project.pbxproj:404-405`, `:433-434`), so
generated keys are merged over the file on disk. Either mechanism works; **pick one
and use it consistently**, because a key set in both places with different values is
a genuinely confusing bug to find. Recommendation: put the string keys in
`Changeover/Info.plist` where they are readable and reviewable, and leave
`INFOPLIST_KEY_LSUIElement` where it is. `NSBonjourServices` is an array and is
cleaner in the plist file than as a build setting regardless.

**Host — `Changeover/Info.plist`:**

```xml
<key>NSLocalNetworkUsageDescription</key>
<string>Changeover uses your local network so Macs, iPhones and iPads in your home can see the disc, choose what to rip, and watch progress.</string>
<key>NSBonjourServices</key>
<array>
    <string>_changeover._tcp</string>
</array>
```

Write the description for the person reading the prompt, not for the reviewer. It
should answer "why does my DVD ripper want my network?" in one sentence — the
existing user-facing copy in `SettingsView` (`Changeover/SettingsView.swift:54`) is a
good model for tone.

**Remote — the same two keys** in the `Changeover Remote` target from
[#0073](0073.md). The client browses rather than advertises but needs both keys just
the same. If the remote is sandboxed as recommended in [#0073](0073.md), it also
needs `com.apple.security.network.client` and
`com.apple.security.network.server`, plus `com.apple.security.network.client` for
TMDB poster fetches (`MetadataEntryView.swift:180`) — which is a different
permission entirely and is the one people forget.

**Trigger the prompt deliberately.** Do not let the first prompt happen at a random
moment. Add an explicit "Enable remote control" action in `SettingsView` (next to the
existing credential GroupBoxes, `Changeover/SettingsView.swift:36-60`) that starts
the server and therefore triggers the prompt while the user is looking at the
Settings window — a real window created by `AppDelegate.showSettings()`
(`Changeover/AppDelegate.swift:97-121`), which will be frontmost. This is far better
than triggering it from `applicationDidFinishLaunching`
(`AppDelegate.swift:16-26`) where a headless mini may show it to nobody.

**Show the state, do not guess at it.** macOS offers no clean API to query Local
Network authorization. Infer it instead: if the advertiser starts but no client has
ever connected and browsing from the host itself finds nothing, show an actionable
warning in Settings and `StatusMenuView` (beside the existing status dot,
`Changeover/StatusMenuView.swift:14-21`) — "Remote control may be blocked. Check
System Settings › Privacy & Security › Local Network." Being explicit that this is an
inference rather than a read is better than either silence or a false claim.

**Document the headless procedure** in the README (Phase 6, [#0100](0100.md), owns
the wider setup docs; this ticket supplies the section):

1. Screen Share into the mini.
2. Open Changeover's Settings from the menu bar icon.
3. Click Enable remote control and Allow when prompted.
4. Verify in System Settings › Privacy & Security › Local Network that Changeover is
   listed and on.
5. If it is missing or off after a reinstall, reset with
   `tccutil reset ScreenCapture co.sstools.Changeover`-style handling for the Local
   Network service — **verify the exact `tccutil` service name on the target OS
   before publishing this step; the Local Network service identifier is not the same
   across releases and should not be guessed.**

**Also worth documenting:** MDM-managed Macs can pre-approve Local Network access via
a configuration profile, which is the clean answer for anyone deploying this to a
family mini they administer. Mention it; do not build it.

## Notes

**Not unit-testable at all.** TCC grants cannot be exercised from a test. The
verification is manual and must be recorded as manual per the caveat in
`issues/Issues.md`.

**The verification that actually proves something is the clean-machine one**, and it
is easy to fool yourself here because a development Mac has almost certainly already
granted the permission to a previous build. Verify by:

1. Resetting the grant (or using a Mac that has never run Changeover).
2. Launching, clicking Enable remote control, observing the prompt text — and reading
   it, since the usage description is the deliverable and a typo ships forever.
3. Confirming `dns-sd -B _changeover._tcp local.` from a second Mac sees the host.
4. Then **denying** the permission on a second reset and confirming the app says
   something useful rather than failing silently. The denial path is the one users
   will hit and the one nobody tests.

**Do this early, not last.** The prompt will first appear during the [#0063](0063.md)
spike, and every subsequent networking ticket will be debugged against whatever
permission state that left behind. Landing the plist keys before [#0068](0068.md)
removes an entire class of false leads from the rest of the phase — it is listed last
in the block only because it is the smallest, not because it should be done last.
