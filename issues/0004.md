# 0004 — Working folders are never cleaned, so every rip strands its intermediate .mkv

| | |
|---|---|
| **Status** | open |
| **Module** | DVDPipeline / PlexOrganizer |
| **Platform** | macOS |
| **First seen** | 2026-09-11 |

## Description

Nothing in the app ever deletes an intermediate file. `DVDPipeline.run()` ends with the Plex move and a log line (`DVDPipeline.swift:53-61`) and the multi-gigabyte `.mkv` stays in the ripping folder forever. This is `Plan.md` 11.6, and it is what turns [#0003](0003.md) from a latent bug into an inevitable one.

## Long Description

The encoded `.mp4` is *moved* into the library by `PlexOrganizer.move` (`PlexOrganizer.swift:27`), so the encode directory only leaks an empty folder. The `.mkv` is the real cost: a DVD main feature is 4-8 GB, and on the external SSD that holds the Plex library, a dozen ripped discs is 60-100 GB of dead weight on the same volume the library lives on.

The cleanup cannot be done blind. Today the pipeline cannot tell success from failure — `PlexOrganizer.move` catches its own error, logs it, and returns normally (`PlexOrganizer.swift:29-31`), after which the pipeline prints `"── Done. Scan your Plex Movies library…"` (line 61) whether or not anything landed. Deleting the working files on that signal would destroy the only copy of a rip whose move just failed.

## Steps to reproduce

1. Complete a full rip, encode and move for any disc.
2. Run `ls -lh "<plexMediaRoot>/Working/ripping"` — the intermediate `.mkv` is still there at full size.
3. Repeat with a second disc. Both `.mkv` files are now present; nothing ever removes either.
4. `df -h` on the volume holding `plexMediaRoot` shows the space consumed indefinitely.

## Expected behavior

After a job that fully succeeded — ripped, encoded, and moved into the Plex library — that job's working files and directories are gone and the working folder is empty. After a job that failed, the working files are **kept** so the failure can be inspected and the rip potentially salvaged. Directories older than a retention window are swept at launch so a run of failures does not fill the disk either.

## Actual behavior

Nothing is deleted, ever, under any outcome. The working folder grows by one full-size `.mkv` per disc.

## Notes

The sweep predicate — "which directories under the working roots are safe to delete, and which are too young" — is a pure function and must have real unit tests run against a temp directory, including the negative cases (a directory whose name is not job-id-shaped, a file rather than a directory, the working root itself).

That a real rip leaves an empty folder behind is manual, and needs a physical disc. Deleting several gigabytes is not a thing to verify by reasoning about the code; state in `## Verification` that the folder was inspected after an actual job.

## Plan

### Where cleanup runs

In `DVDPipeline.run()`, after `PlexOrganizer.move` **succeeds** (`DVDPipeline.swift:54-59`). With [#0007](0007.md) in place, `PlexOrganizer.move` throws rather than swallowing (`PlexOrganizer.swift:21-31`), so the success path is a real branch instead of an assumption. Cleanup runs only on `.succeeded`.

Order inside the pipeline, fixed across Phase 1: **move → cleanup → eject ([#0005](0005.md)) → notify ([#0006](0006.md))**. The notification is last so that when it arrives, everything it claims is actually true.

### What cleanup does

Add to the `JobWorkspace` type from [#0003](0003.md):

```swift
nonisolated func removeAll() throws
```

which removes `ripDirectory` and `encodeDirectory` — the per-job children, never the roots. `nonisolated` because it is pure file I/O with no need for MainActor, matching `PlexOrganizer` (`PlexOrganizer.swift:8`).

### Launch-time sweep

Add `nonisolated static func sweepStaleJobDirectories(underRoots:olderThan:)`, called from `AppDelegate.applicationDidFinishLaunching` (`AppDelegate.swift:16-26`) after the `settings.isConfigured` check — there is nothing to sweep before a root is configured, and the first-launch path already branches there (line 23).

Retention: keep something conservative (7 days) as a named constant. Failures need to survive long enough for the user to notice them.

### Safety rules — the part to get right

This code deletes multi-gigabyte files on the same volume as the user's Plex library. Non-negotiables:

- Only remove entries that are **direct children** of `workingRipPath` or `workingEncodePath` (`AppSettings.swift:27`, `:30`).
- Only remove entries whose name matches the job-id format from [#0003](0003.md). Anything else in those folders is the user's and stays.
- Never `removeItem` on `workingRipPath` or `workingEncodePath` themselves, and never on any path under `plexMoviesPath` (line 21).
- Bail out entirely if `plexMediaRoot` is empty (line 13) — the derived paths would otherwise begin with `/Working/ripping`, an absolute path at the filesystem root.
- Check the path still exists before removing; a removable volume can be unmounted mid-job. Log the failure, do not throw the job into a failed state over a cleanup problem that happened *after* the file already landed in Plex.

### Risks

- **Deleting a file still being written.** In practice safe: `EncodeController.encode` only resumes its continuation from `terminationHandler` (`EncodeController.swift:48-55`), so the child process is gone before the pipeline continues. Do not restructure that.
- **A cleanup failure must not mark a successful job failed.** The movie is in Plex; a stranded temp folder is a nuisance, and the launch sweep catches it later. Log it and keep `.succeeded`.
- Do not clean up on cancellation either — a cancelled rip may still be worth resuming manually.
