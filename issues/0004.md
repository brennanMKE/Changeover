## Root cause

Nothing in the pipeline ever deleted a working file, and the encode wrote to a
shared, flat path (`Working/encoding/<Title (Year).mp4`), so a failed job's
partial `.mp4` stayed forever and the next job for the same movie would
overwrite it — the exact collision shape #0003 fixed for rips, still open for
encodes. Two structural gaps: there was no per-job provenance for the encode
output, and there was no outcome-driven disposal — cleanup could not be gated
on the typed `JobOutcome` because `finish(_:)` was synchronous log-and-record
code with no disposal step.

## Gotchas

- **`isJobID`'s hex class is load-bearing in tests, not just code.** T10
  initially used fixture names like `job-…-gggg` — `g` is not a hex digit, so
  `isJobID` correctly rejected them and the sweep left them alone. The
  pattern is right; the fixture names were wrong. Any hand-written job-id
  fixture must use real hex (`d00d`, `c0de`, `beef`).
- **`ssh -n` eats stdin.** Falsification edits piped to `python3 -` over ssh
  silently no-oped twice because `-n` forces the remote stdin to
  `/dev/null`; the edit "landed" nothing and the grep check caught it. Drop
  `-n` when piping a script into a remote python.
- **`perl -0pi -e` interpolates `@` in patterns.** `@concurrent` in a perl
  regex is an array interpolation; escaping as `\@` through nested shell
  quoting failed repeatedly — the piped-python form is the reliable way to
  edit gordon's copy.
- The sweep's per-root guard order matters: `realpath` overlap is checked
  *before* the `lstat` symlink skip, so a root symlinked into Movies is
  refused (T12) rather than silently skipped.
- **Diff every commit against its own message before reporting done.** The
  first review bounce happened because `90f974e` was staged without
  `DVDPipeline.swift` while its message described the wiring. The test-run
  verification rule caught the test count but not the commit content — the
  reviewer's `git show` inspection is what caught it. `git status` after
  staging, and re-read the message against `git show --stat`, every time.
- `dispose` deliberately takes `jobDirectoryCreated` as a parameter instead
  of probing the filesystem: after a refused `createJobDirectory` the
  directory exists but was not created by this job, and a filesystem probe
  would authorize deleting it.

## Description

Nothing in the app ever deletes an intermediate file. `DVDPipeline.run()` ends with the Plex move and a log line (`DVDPipeline.swift:53-61`) and the multi-gigabyte `.mkv` stays in the ripping folder forever. This is `Plan.md` 11.6, and it is what turns [#0003](0003.md) from a latent bug into an inevitable one.

## Long Description

The encoded `.mp4` is *moved* into the library by `PlexOrganizer.move` (`PlexOrganizer.swift:27`), so the encode directory only leaks an empty folder. The `.mkv` is the real cost: a DVD main feature is 4-8 GB, and on the external SSD that holds the Plex library, a dozen ripped discs is 60-100 GB of dead weight on the same volume the library lives on.

The cleanup cannot be done blind. Today the pipeline cannot tell success from failure — `PlexOrganizer.move` catches its own error, logs it, and returns normally (`PlexOrganizer.swift:29-31`), after which the pipeline prints `"── Done. Scan your Plex Movies library…"` (line 61) whether or not anything landed. Deleting the working files on that signal would destroy the only copy of a rip whose move just failed.

## Steps to reproduce

1. Complete a full rip, encode and move for any disc.
2. Run `ls -lh "<plexMediaRoot>/Working/ripping"` — the intermediate `.mkv` is still there at full size.
3. Repeat with a second disc. Both `.mkv` files are now present; nothing ever removes either.
4. `df -h` on the volume holding `plexMediaRoot` shows the space consumed indefinitely.

## Expected behavior

After a job that fully succeeded — ripped, encoded, and moved into the Plex library — that job's working files and directories are gone and the working folder is empty. After a job that failed, the working files are **kept** so the failure can be inspected and the rip potentially salvaged. Directories older than a retention window are swept at launch so a run of failures does not fill the disk either.

## Actual behavior

Nothing is deleted, ever, under any outcome. The working folder grows by one full-size `.mkv` per disc.

## Notes

The sweep predicate — "which directories under the working roots are safe to delete, and which are too young" — is a pure function and must have real unit tests run against a temp directory, including the negative cases (a directory whose name is not job-id-shaped, a file rather than a directory, the working root itself).

That a real rip leaves an empty folder behind is manual, and needs a physical disc. Deleting several gigabytes is not a thing to verify by reasoning about the code; state in `## Verification` that the folder was inspected after an actual job.

## Plan (revised 2026-09-13)

> Replaces the original plan, which was written for the `.mkv` pipeline: a `JobWorkspace` from #0003 and a launch-time sweep. Git has the old text (`ee3bd81`).

### 0. Decisions at a glance

1. **Each job encodes into its own new directory:** `Working/encoding/job-<id>/Title (Year).mp4`. That stops collisions by construction.
2. **The outcome decides what happens to the working files.** A pure, exhaustive function of `JobOutcome`, called once in `finish(_:)`:
   - `.succeeded` → remove the job directory, which is now empty apart from its marker.
   - encode or fallback failure → remove.
   - **organize failure → keep.**
   - preflight → nothing was created.
3. **A marker file,** `.changeover-job`, in each encode job directory records `encoding` → `encoded` → `kept`. The sweep deletes only what the marker proves is disposable, and never an `encoded` or `kept` directory that still holds content.
4. **The stale sweep runs at the start of every job, before preflight.** It does not run at launch.
5. **The user learns about a kept file twice:** from a log line when the move fails, and from a reminder line at the start of every later job until they deal with it.

### 1. Which outcomes delete the working `.mp4`

| How the job ended | `JobOutcome` | Encode job directory | Why |
|---|---|---|---|
| Preflight blocked | `.failed(stage: .preflight)` | nothing to do | The job directory is created *after* preflight, so none exists. |
| Job directory could not be created | `.failed(stage: .encode, reason: .destinationUnwritable)` | **nothing: never touch it** | This job created nothing. It must never delete what it did not create; the same rule as `runFallback`'s `.destinationUnwritable` case (#0015). |
| HandBrake exits non-zero, is killed by the inactivity watchdog, fails to launch, or exits 0 with an empty file. The fallback is `.notEligible` or `.unavailable`. | `.failed(stage: .encode)` | **delete** | The partial file is unplayable, and nothing in the app can use it. The disc is still the source. Keeping it costs about 1 GB (#0018) and is what the next job collides with. |
| `.cancelled` (reserved: no cancel exists today, see `JobController`) | `.failed(stage: .encode, reason: .cancelled)` | **delete** | HandBrake cannot resume an encode. The old plan's "don't clean up on cancellation" was about a resumable `.mkv` and no longer applies. |
| Fallback attempted and failed (the rip or the second encode) | `.failed(stage: .encode, fallback: .failed(...))`. The top-level stage stays the primary's `.encode`. | **delete** | Same as above. The rip job directory is already removed by #0015's `runFallback`. |
| Encode succeeded (directly or through the fallback), then `PlexOrganizer.move` threw | `.failed(stage: .organize)` | **keep**, marker → `kept` | It is the **only copy** (#0012). Re-creating it means another 20–40 minute encode, and the disc may already be back on the shelf. |
| Succeeded | `.succeeded(destination:)` | **remove the directory**, but only if it holds nothing except the marker | The `.mp4` has already been moved. If anything else is still in there, keep it and log a warning: that outcome is ambiguous. |
| Crash, force-quit or power loss mid-job | no outcome | left for the sweep, which acts on the marker state | See §4. |

**Also, before the fallback rips:** on the `.attempt` branch, remove the primary encode's partial `.mp4` at `mp4Path`, with the file-level guard from §6. It is useless, because the second encode overwrites that path anyway. Removing it early frees about 1 GB before a 5–8 GB MakeMKV rip, the space #0008's P8 warns about. Refusal or failure only logs a warning.

### 2. Collisions

- **One job id.** In `run()`'s MainActor prologue, generate `let jobID = JobController.makeJobID()` once and log it (`▶ Job <id>`).
  - Use it for `Working/encoding/<jobID>/` and, on the fallback path, `Working/ripping/<jobID>/`. `runFallback` takes `jobID` as a parameter instead of calling `makeJobID()` itself, so the two directories correlate.
  - **Do not widen `JobController.Runner`** (#0014 §4, #0015 §2a).
- **The job directory is created fresh, never adopted.** Add `WorkingFiles.createJobDirectory(root:jobID:) throws -> String`, modelled on `MakeMKVRipper.rip` step (a):
  - `createDirectory(root, withIntermediateDirectories: true)`, then `createDirectory(jobDir, withIntermediateDirectories: false)`.
  - The second call throws if the directory already exists.
  - Call it after preflight passes and before `EncodeController.encode`.
  - On failure, `primaryRecord = .encode/.destinationUnwritable` and `return await finish(.failed(JobFailure(stage: .encode, reason: .destinationUnwritable(path: jobDirectory))))`, with `jobDirectoryCreated == false`.
- **The output path becomes** `mp4Path = jobDirectory/metadata.fileName`.
  - **No change to `EncodeController`:** its own `createDirectory(..., withIntermediateDirectories: true)` is a no-op on the existing directory.
  - **No change to `PlexOrganizer`:** it takes the destination file name from `metadata`, never from `encodedFile`'s path.
- **Result:** two jobs for the same movie, or a retry after an organize failure, never share a path. HandBrake can never overwrite a kept file.
- **Legacy loose files are never touched.** Earlier builds wrote `Working/encoding/Title (Year).mp4` directly. The sweep only reports them (§4).

### 3. The job marker

- **Location:** `<jobDirectory>/.changeover-job`, in encode job directories only.
  - Rip job directories need no marker: a `.mkv` is never the only copy of anything.
- **Format:** a small `Codable` JSON document, `{"state":"encoding","movie":"Blade Runner (1982) {tmdb-78}"}`.
  - The `movie` field makes the reminder line readable.
  - Written with `.atomic`.
  - **Parsing is pure:** `WorkingFiles.parseMarker(Data) -> MarkerRead`, which returns `.marker(JobMarker)` or `.unreadable`. An unknown `state` string is `.unreadable`, never a default state.
- **Transitions, all written from `run()`:**
  - `encoding`: immediately after `createJobDirectory` succeeds, before HandBrake launches.
  - `encoded`: immediately after `✓ Encode complete`, before `PlexOrganizer.move`.
  - `kept`: in the organize `catch` branch.
- **When a marker write fails, the failure must land on the safe side:**
  - Failing to write `encoding` leaves the directory with no marker. The sweep never auto-deletes a directory without a marker. Log a warning; the job continues.
  - Failing to write `encoded` or `kept`: log a warning, then **remove the marker file**. A stale `encoding` marker must never stay in front of a complete `.mp4`. A directory without a marker is kept.
  - If that removal also fails, log the job directory path in the warning. The outcome is unchanged.
  - Preflight's P5 has already proved this root writable seconds earlier, so this is a corner case. It still gets a defined answer.

### 4. The stale sweep

**When:** first thing in `DVDPipeline.run()`, after `── Starting` and **before** `Preflight.check`, so reclaimed space counts toward P6's free-space blocker. It does not run at launch:

- At login, the SMB or external volume holding `plexMediaRoot` is often not mounted yet (cameron's library is `/Volumes/Media`).
- There is nowhere at launch to show its report. `JobController` clears `logLines` at the start of each job (`logIsClearedAtTheStartOfEachJob`), so a launch report would be wiped before anyone read it.
- Leftovers only matter when the next job needs the space, which is exactly when this runs.
- Changeover is a login item that runs for weeks, so a launch-only sweep would almost never run.
- A single call site can be driven by the existing stub pipeline harness.

The in-process job cannot be in flight during the sweep: `JobController.start` refuses re-entry, and the new job directory doesn't exist yet. The age guard covers a second app instance.

**Entry point:**

```swift
@concurrent nonisolated static func sweep(_ input: SweepInput, now: Date = Date()) async -> SweepReport
```

- `SweepInput` holds `plexMediaRoot`, `workingEncodePath`, `workingRipPath`, `plexMoviesPath` and `staleAfter`.
- It is `@concurrent` for the same reason as `Preflight.check` and #0012's follow-up: directory listing and `removeItem` on an SMB volume block, and `run()` is MainActor.
- It never throws and never creates anything.

**Whole-sweep guards.** The sweep is a no-op when any of these holds, with one log line unless noted:

- `plexMediaRoot` is empty. The derived paths would begin `/Working/…`. No log line.
- A working root isn't an existing real directory, checked with `lstat`, not following symlinks. Skip that root and never create it.
- A working root's `realpath` is `/`, equals `realpath(plexMoviesPath)`, is inside it, or contains it. The whole sweep is refused.

**Per entry.** List **direct children only**, with no recursion and no symlink-following. For each child, build a plain `SweepEntry` value:

- `name`
- `kind`: `.directory`, `.symlink`, `.file` or `.other`, from `lstat`
- `marker`: `.missing`, `.unreadable` or `.marker(JobMarker)`
- `newestModification: Date?`: the newest `lstat` mtime of the directory, its marker and its direct children; `nil` if unreadable
- `hasContentBesidesMarker: Bool`

Then `WorkingFiles.sweepDecision(for: SweepEntry, in: .encode | .rip, now:, staleAfter:) -> SweepDecision` returns `.delete`, `.report(KeptReason)` or `.leave`. It is pure and exhaustive.

**Encode root:**

| Entry | Decision |
|---|---|
| Name not job-id-shaped, and it's a regular `.mp4` file | `.report(.legacyLooseFile)`, never deleted |
| Name not job-id-shaped, anything else (user files, `.changeover-preflight-*`, `.DS_Store`) | `.leave` |
| Job-shaped name, but a symlink, file or other | `.leave` |
| Job-shaped directory, marker `.missing` or `.unreadable` | `.report(.unrecognised)`. Ambiguous, so keep. |
| `encoding`, age ≥ `staleAfter` | `.delete` |
| `encoding`, age < `staleAfter`, `newestModification == nil`, or an mtime in the future | `.leave` |
| `encoded` (the app died between encode success and the move finishing) | `.report(.encodedNeverMoved)`, never deleted |
| `kept`, with content besides the marker | `.report(.keptAfterFailedMove)`, never deleted |
| `kept`, holding only the marker (the user already moved the `.mp4` out) | `.delete` |

**Rip root:**

| Entry | Decision |
|---|---|
| Job-shaped real directory, age ≥ `staleAfter` (a crash mid-fallback, or #0015's untouched `.destinationUnwritable` leftover) | `.delete` |
| Anything else | `.leave` |

**`WorkingFiles.staleAfter = 24 * 60 * 60`.** The longest realistic job is about 3 h: a 40 min encode, up to 30 min of watchdog silence, a fallback rip, and a second 40 min encode. 24 h is an eightfold margin, and a crash leftover costs at most about 1 GB (the rip's `.mkv` at most about 8 GB) for at most a day. `encoded` and `kept` never expire.

**Deletion** goes through `removeJobDirectory` (§6). It re-checks everything at delete time, because the entry was examined earlier (a time-of-check-to-time-of-use gap).

**Report and logging.** `SweepReport` holds `removed: [String]`, `kept: [(path, KeptReason, movie?)]`, `failed: [(path, message)]` and `refusal: String?`. `run()` logs:

- `✓ Removed stale working folder <path>`, one line per path.
- For each kept entry, a reminder in this form: `⚠︎ Kept from an earlier job: <path> (<movie>). The move into Plex failed. Move the .mp4 into Plex by hand, then delete the folder.`
  - `.encodedNeverMoved`, `.unrecognised` and `.legacyLooseFile` get their own wording.
- `⚠︎ Could not remove <path>: <message>`.
- The refusal, if any.
- At most 5 lines per category, then `…and N more`.

None of these can fail the job.

### 5. How the user learns a kept file exists

1. **At the failure.** In the organize `catch` branch, after writing `kept` and before `return await finish(...)`:
   - If the file exists at `mp4Path`, log `⚠︎ The encoded file was kept at <mp4Path>. Move it into "<plexMoviesPath>/<folderName>/" by hand, or delete <jobDirectory> to discard it.`
   - If it doesn't, log that it is not in the working folder and to see the line above. `PlexOrganizer` already logs `…it remains at <stagedURL>` when its restore fails.
2. **At every later job.** The sweep's reminder (§4), until the user moves or deletes the file.
3. **Out of scope here.**
   - No new field on `JobFailure` or `JobOutcome`. That is a wire-shape decision, the precedent from #0015 §3.
   - #0006's notification can word the `.organize` failure to say the file was kept.
   - A Settings or popover surface is not in this ticket.

### 6. Safety guards

**Every deletion goes through one function:**

```swift
nonisolated static func removeJobDirectory(_ path: String, under root: String, forbidding moviesPath: String = "") -> RemovalResult
// RemovalResult: .removed | .refused(RefusalReason) | .failed(String)
```

**Checks, in order:**

1. `root` and `path` are non-empty and absolute.
2. **No `.` or `..` component in the raw `path`.** Reject it before any normalisation; never "fix" it.
3. `lstat(path)` is a **directory**. A symlink is refused, never followed: a symlink named `job-…` pointing into `Movies` must survive, and so must its target. A regular file is refused. A missing path gives `.refused(.missing)`, for a volume unmounted mid-job, and logs quietly.
4. **Canonical containment.** `realpath(3)` of `path`'s parent must equal `realpath(root)` exactly: a direct child only.
   - Use Darwin `realpath`, not `NSString.resolvingSymlinksInPath`. That API strips `/private` only when the result exists, and every test temp directory lives under `/var → /private/var`.
5. `realpath(root)` is not `/`. It is not equal to, inside, or containing `realpath(moviesPath)`. If `moviesPath` doesn't exist, compare standardised strings.
6. The last path component matches `WorkingFiles.isJobID`: `^job-[0-9]{8}-[0-9]{6}-[0-9A-Fa-f]{4}$`, the exact shape `JobController.makeJobID()` produces. Pin it with a round-trip test.
7. `removeItem`. An error becomes `.failed(localizedDescription)`.

**The single-file case uses the same checks.** The primary's partial `.mp4` before the fallback (§1) goes through a sibling, `removeFile(_:inJobDirectory:)`: `lstat` a regular file, parent `realpath` equal to the job directory, extension `mp4`, and the job directory itself passes checks 1–6.

**`MakeMKVRipper.removeJobDirectory(_:under:)` becomes a thin wrapper** returning `== .removed`. Its five existing tests pass unmodified:

- `job-20260101-000000-abcd` matches the pattern (hex is case-insensitive).
- `job-x`, `stale.mkv`, the root itself and an empty root are all still refused.

**No deletion on an ambiguous outcome:**

- The disposition comes only from the typed `JobOutcome`, never from log text or control flow reaching the end.
- `jobDirectoryCreated == false` → nothing is deleted.
- A succeeded job whose directory still holds anything besides the marker → keep, with a warning.
- A missing or unreadable marker → the sweep keeps it.
- An mtime that is unreadable or in the future → the sweep leaves it.
- Any guard it can't satisfy → refuse and log.

**A cleanup failure logs and never fails the job.** `finish(_:)` returns the outcome it was given unchanged, whatever `RemovalResult` comes back. The sweep never throws. A marker-write failure only logs.

**Concurrency.** Every `WorkingFiles` entry point that touches the filesystem is either plain `nonisolated` sync, when called only from `@concurrent` code, or `@concurrent nonisolated async`. The async ones are `sweep`, `dispose`, `writeMarker` and `createJobDirectory`. `finish(_:)` becomes `async`, so every `return finish(...)` in `run()` becomes `return await finish(...)`.

### 7. What changes in `DVDPipeline.run()`, in order
