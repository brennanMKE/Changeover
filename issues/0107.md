# 0107 — Login-item registration fails silently and is never surfaced to the user

| | |
|---|---|
| **Status** | open |
| **Module** | AppDelegate / Onboarding |
| **Platform** | macOS |
| **First seen** | 2026-09-11 |

## Description

`AppDelegate.registerLoginItem()` is `try? SMAppService.mainApp.register()` inside a dead `#available(macOS 13.0, *)` check (`Changeover/AppDelegate.swift:125-129`). The `try?` discards every error, the app never reads back the resulting status, and nothing in the UI says whether "launches at login" — advertised as a feature in `README.md:20` — is actually in effect. The install instructions compensate by telling the user to go check System Settings themselves (`README.md:81-83`, `Plan.md:307-308`).

## Long Description

Three separate defects in five lines:

1. **The error is thrown away.** `SMAppService.register()` throws for real,
   reachable reasons — the user previously disabled the item in System Settings
   (which makes registration fail until they re-enable it), the app is running
   from a location macOS will not register, or the operation is denied. `try?`
   turns all of them into silence.
2. **The status is never read.** `SMAppService.mainApp.status` returns
   `.enabled` / `.requiresApproval` / `.notRegistered` / `.notFound`.
   `.requiresApproval` is the common real-world case — macOS registers the item
   but shows a notification asking the user to approve it, and if they dismiss
   that notification the app does not start at login. Changeover cannot tell the
   difference between that and success.
3. **The `#available(macOS 13.0, *)` guard is dead code.**
   `MACOSX_DEPLOYMENT_TARGET = 26.2` (`Changeover.xcodeproj/project.pbxproj:328`,
   `:386`), so the branch is unconditionally true. Harmless, but it implies a
   back-compat story that does not exist and should go.

This lands in Phase 6 rather than staying a general cleanup because of where it
breaks. Registration behaves differently for a signed app in `/Applications`
than for a debug build launched from DerivedData — the path a DMG install
produces is exactly the path that has never been exercised. The current
mitigation is documentation: `README.md:81-83` says *"Launch once manually to
register the Login Item. Verify under System Settings → General → Login Items &
Extensions."* Telling a new user to go audit a system pane to find out whether
the app did its job is the Phase 6 anti-pattern in miniature.

There is also a question this ticket should settle, not just implement:
**should Changeover register itself at all, unprompted, on first launch?** It
does so today at `AppDelegate.swift:21`, before the user has configured
anything, and before they have decided they want it. For a headless mini that
rips discs, launch-at-login is the whole point; for someone trying the app once,
it is presumptuous.

## Steps to reproduce

1. Install Changeover to `/Applications` and launch it.
2. Open **System Settings → General → Login Items & Extensions** and turn
   Changeover *off*.
3. Quit Changeover and launch it again.
4. Look anywhere in the app for an indication of whether it will start at login.

## Expected behavior

Step 3's re-registration attempt either succeeds or reports why it did not. Step
4 finds an explicit row — in the setup checklist and/or Settings — showing the
current `SMAppService` status, with a control to enable it and a link to the
System Settings pane when the user's approval is required.

## Actual behavior

Step 3 silently fails (`try?` swallows it). Step 4 finds nothing; `README.md:20`
still lists "Launches at login via `SMAppService`" as a feature, and the only way
to learn the truth is to reboot or open System Settings.

## Plan

Depends on [#0104](0104.md) for the `SetupChecklist` model — this implements row
6, the one advisory (non-blocking) row.

**1. Rewrite `registerLoginItem()`** (`Changeover/AppDelegate.swift:125-129`):

- Drop the `#available(macOS 13.0, *)` wrapper — dead against a 26.2 deployment
  target.
- Replace `try?` with a real `do/catch` that records the error rather than
  discarding it.
- **Read `SMAppService.mainApp.status` afterwards** and store it on the
  checklist. The status, not the absence of a thrown error, is the truth.

**2. Decide the consent question and write the decision down.** Recommended:
**stop auto-registering at launch.** Move it to an explicit control in the setup
flow — "Start Changeover automatically when this Mac starts up", with a
one-sentence explanation that this is what makes disc insertion work without
anyone logging in and opening the app. Default it on for a first-time user if you
like, but make it a visible choice rather than something the app did before they
had configured a single setting. If the decision goes the other way, say why in
the resolution; either is defensible, silence is not.

**3. Map status to the checklist row.** `.enabled` → satisfied.
`.requiresApproval` → a distinct actionable state with a button that opens the
Login Items pane (`SMAppService.openSystemSettingsLoginItems()`) and text
explaining that macOS needs the user's approval. `.notRegistered` → offer to
register. `.notFound` → this generally means the bundle is somewhere macOS will
not accept (not in `/Applications`, or a stale copy); say so and suggest moving
it. This row must be **advisory, not blocking** — the app is fully usable at the
machine without it, so it must not gate `isConfigured` ([#0104](0104.md) step 3).

**4. Re-check the status when the app becomes active**, not only at launch. The
user will go flip the switch in System Settings and come back, and the row should
be correct when they do.

**5. Delete the manual instruction from the docs.** `README.md:81-83` and
`Plan.md:307-308` both tell the user to verify in System Settings; once the app
reports its own status those lines go. Coordinate with [#0108](0108.md) so the
README is edited once, not twice.

**Risks.** (a) `SMAppService` behavior depends on bundle identity and location;
testing this from a DerivedData build will not reproduce what a DMG-installed
copy does, and may produce misleading passes. (b) Repeatedly calling `register()`
when the user has deliberately disabled the item is user-hostile — check status
first and only register on an explicit action or a genuine `.notRegistered`
first run. (c) Two copies of the app (a build in DerivedData and one in
`/Applications`) sharing bundle id `co.sstools.Changeover`
(`project.pbxproj:412`, `:441`) will confuse both `SMAppService` and your
testing; delete one before drawing conclusions.

## Notes

**This is one of the few onboarding rows with a mechanical check**, but it must
be run against an installed, signed copy:

```bash
# What the system actually believes, independent of the app's own reporting:
sfltool dumpbtm | grep -i -A 5 changeover

# The bundle's identity, which is what SMAppService keys off:
codesign -dvvv /Applications/Changeover.app 2>&1 | grep -i identifier
```

Then the behavioral test, which cannot be shortcut: **enable the login item, log
out, log back in, and confirm the menu bar icon appears without anyone launching
the app.** A reboot is better still, since that is the scenario that matters for
a mini that rips discs unattended. A status string in the UI that says "enabled"
while the app does not actually start at login is worse than the current silence.

Per `issues/Issues.md`'s verification caveat, state plainly in the resolution
that these were manual checks and on which machine — and note whether the app was
run from `/Applications` or DerivedData, because the answer changes what the
result means. Do this on the clean machine from [#0103](0103.md) if the schedule
allows; a fresh user account on the build Mac is an acceptable substitute here,
since nothing about this row depends on Gatekeeper.
