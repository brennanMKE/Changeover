## Description

`README.md` is written for the author's own machine and two of its instructions are actively wrong. It tells the reader to put their TMDB API key in `Secrets.xcconfig` (`README.md:61-72`) — a build-time mechanism that stopped feeding anything when commit `1c1e3d9` moved the key to `UserDefaults` — and it tells them to run `xattr -cr /Applications/Changeover.app` (`README.md:74-79`), the exact step Phase 6 exists to eliminate.

## Long Description

The drift is not cosmetic. A new user who follows `README.md` in order:

1. Reads "Requirements" (`:23-37`) — correct, and useful.
2. Reads "First Launch" (`:39-58`) — mostly correct, but tells them to
   `mkdir -p` four folders by hand (`:53-58`) that the app should create itself
   ([#0104](0104.md) step 4).
3. Reads "Building → TMDB API Key" (`:61-72`) — copies
   `Secrets.xcconfig.example` to `Secrets.xcconfig`, pastes their key. **Nothing
   reads it.** `grep -n INFOPLIST Changeover.xcodeproj/project.pbxproj` shows no
   `INFOPLIST_KEY_TMDB_API_KEY`; `Changeover/Config.swift` is down to two
   constants (`:8`, `:11`) with no `tmdbAPIKey`; the live key path is
   `AppSettings.tmdbAPIKey` (`Changeover/AppSettings.swift:16`, `:42`, `:53`) fed
   by a `SecureField` in Settings (`Changeover/SettingsView.swift:51`).
4. Launches, finds an empty TMDB field, and has no idea why.

`Plan.md` carries the same stale story at `:109` and `:111` (including a note
about the author's own `~/.zshrc`) and the same `xattr -cr` block at `:301-306`.
`Plan.md` is a historical implementation record, so it is defensible to leave it
alone — but if it stays, the `## Deployment notes` section at the end should get
a one-line pointer saying it has been superseded, or the next reader will follow
it too.

The README also has no "Install" section at all — only "Building". After
[#0102](0102.md) there is a DMG, and downloading it becomes the primary path for
everyone who is not modifying the code.

## Steps to reproduce

1. Open `README.md` as someone who has never seen the project.
2. Follow "Building → TMDB API Key" (`:61-72`) exactly.
3. Build, run, and open Settings.

## Expected behavior

The documented steps produce a working app. The primary path is "download the
DMG, drag to Applications, launch" — no Terminal, no Xcode, no key file. Building
from source is a separate, clearly-labelled section for contributors.

## Actual behavior

Step 3 shows an empty TMDB API Key field. The key is in a file nothing reads, and
the only remaining mention of it in the build is a dead
`baseConfigurationReference` (`Changeover.xcodeproj/project.pbxproj:276`, `:340`)
pointing at a gitignored file (`.gitignore:4`).

## Plan

Do this **after** [#0102](0102.md) and [#0104](0104.md) land, so the instructions
describe what the app actually does rather than what it is planned to do. Writing
them earlier guarantees a second rewrite.

**1. Restructure `README.md` around two audiences**, users first:

- **Install** (new, primary): download the DMG, drag to Applications, launch.
  One screenshot of the first-run checklist. Explicitly note that no Terminal
  step is required — worth saying out loud, because anyone who has installed
  unsigned Mac software expects one.
- **Requirements** (keep `:23-37`, extend): MakeMKV and HandBrake with the
  `brew` commands, preserving the existing formula-not-cask warning at `:29`
  that is easy to get wrong, plus a TMDB account. Say that the app will detect
  and prompt for all of these ([#0105](0105.md)), so this section is orientation
  rather than a checklist to execute.
- **Setup** (rewrite of "First Launch", `:39-58`): the checklist in order, one
  line each. Keep the derived-paths table (`:45-51`) — it is genuinely useful for
  explaining what choosing one root does — but **delete the `mkdir -p` block**
  (`:53-58`) once [#0104](0104.md) creates the folders, and stop naming
  `/Volumes/MediaSSD` as though it were a requirement rather than one person's
  disk. `RemoteControl.md:86` — "Not a single-user app" — is the standard here.
- **Building from source** (rewrite of `:59-72`): clone, open in Xcode, build.
  **Delete the entire "TMDB API Key" subsection** (`:61-72`) — the key is a
  runtime setting now, entered in the app, and belongs in Setup, not Building.
  If [#0101](0101.md) retires `Secrets.xcconfig`, also delete
  `Changeover/Secrets.xcconfig.example` and say nothing about xcconfigs at all;
  if it is kept via `#include?`, document that instead. **This section cannot be
  written until [#0101](0101.md) decides**, so sequence accordingly.
- **Releasing** (new, or a separate `RELEASE.md` per [#0102](0102.md)): point at
  the `scripts/` pipeline. Do not duplicate the `mac-release` skill's procedure
  in the README — link to the checklist and let one file own it.
- **Delete "Deployment"** (`:74-83`) entirely. The `xattr -cr` line is the
  headline thing Phase 6 removes; the login-item verification instruction goes
  with [#0107](0107.md), which makes the app report its own status.

**2. Keep what is already good.** The name explanation at the top, the Plex
naming-convention section (`:85-99`) and the architecture table (`:101-117`) are
accurate and worth preserving — the architecture table just needs
`AppSettings.swift` amended (it currently says "settings backed by
`UserDefaults`", which is right) and new onboarding files added as they land.

**3. Decide `Plan.md`'s fate.** Recommended: leave it as the historical
implementation record it is, but strike or annotate the two misleading passages —
`:109`/`:111` (the `Secrets.xcconfig` + `~/.zshrc` note) and the `## Deployment
notes` section (`:301-308`) — with a pointer to the README and to
[#0102](0102.md). A stale document that knows it is stale is harmless; one that
reads as current is not.

**4. Sanity-check every command in the finished README by running it.** Not
reading it — running it. The `mkdir -p` paths, the `brew` lines, the `which`
invocations (`:33-36`). Stale docs are how this ticket happened in the first
place.

**Risks.** (a) Writing this before [#0104](0104.md)'s flow exists means
documenting an imagined UI; wait. (b) The screenshot will go stale the first time
the onboarding UI changes — keep it to one, of the checklist, and store it under
`issues/`-style conventions or a `docs/` folder rather than scattering images.

## Notes

**Verification is the test that matters for documentation: hand it to someone
who has not seen the project and watch.** Failing a real person, use the clean
machine or fresh user account from [#0103](0103.md) / [#0104](0104.md) and
follow the README literally, typing every command, resisting every urge to fill
in a step from memory. The steps you skip without noticing are exactly the ones a
new user cannot.

Concrete checks that do not need a person:

```bash
# No stale instructions survive anywhere in the docs:
grep -rn 'xattr -cr' README.md Plan.md MacApp.md
grep -rn 'Secrets.xcconfig' README.md Plan.md
grep -rn 'INFOPLIST_KEY_TMDB_API_KEY' .
grep -rn 'MediaSSD' README.md          # one person's disk, not a requirement

# Every link resolves:
grep -o 'https\?://[^)]*' README.md | sort -u | while read u; do
  printf '%s ' "$u"; curl -s -o /dev/null -w '%{http_code}\n' -I "$u"
done
```

The first grep should return nothing from `README.md` and `Plan.md` once this
ticket and [#0109](0109.md) are done. `MacApp.md` is [#0109](0109.md)'s problem.
