# 0005 — There is no eject, so every disc requires a trip to the machine to open the tray

| | |
|---|---|
| **Status** | open |
| **Phase** | 1 — Trustworthy single-disc rip |
| **Module** | DVDPipeline / DVDMonitor / DiscEjector |
| **Platform** | macOS |
| **First seen** | 2026-09-11 |

## Description

Nothing in the app ejects the disc — there is no `drutil`, no `unmountAndEjectDevice`, no eject path at all (`Plan.md` 11.4 is unchecked). Worse, `DVDMonitor` computes the mounted volume's URL and then discards it (`DVDMonitor.swift:18`, callback typed `(() -> Void)?` at line 4), so the app does not even retain which volume the current job came from.

## Long Description

This is the item that makes the Phase 1 demo mean something. "Insert a disc and walk away" is not true while the last step of every job is walking back to the mini to press the eject button. It is also the signal the whole multi-disc story in Phase 3 is built on: the tray opening is how the user knows it is time to swap.

`DVDMonitor.volumeMounted(_:)` (`DVDMonitor.swift:15-27`) extracts `url` from `NSWorkspace.volumeURLUserInfoKey`, uses it only to test for a `VIDEO_TS` directory, then calls a zero-argument closure. `AppDelegate.startDVDMonitor()` (`AppDelegate.swift:60-65`) forwards that to `showMetadataEntry()`. By the time a job finishes, nothing knows what was mounted.

There is also no unmount handling — the app never learns a disc was removed, so state cannot be reset when the user ejects manually.

## Steps to reproduce

1. Insert a DVD; the metadata window appears.
2. Search, select, Start Ripping, and let the job run to completion.
3. Observe the log's final line: `"── Done. Scan your Plex Movies library to pick up the new title."`
4. The disc is still mounted on the Desktop and still in the drive.
5. Walk to the machine and eject it by hand before the next disc can go in.

## Expected behavior

On a job that fully succeeded, the volume is unmounted and the drive opens, and the log says so. On a failed job the disc stays in, so it can be retried without re-inserting. A failed eject is reported but does not turn a successful job into a failed one.

## Actual behavior

The disc is never ejected under any outcome, and the app has not retained enough information to eject the right volume even if it wanted to.

## Notes

**This is the one Phase 1 ticket with essentially no automated verification.** It is hardware behavior: an external USB optical drive, a physical disc, and a tray that either opens or does not. `## Verification` must say plainly that it was verified manually, on which machine, with which disc, and that a failed-job run was also checked to confirm the disc stays in.

The one testable seam: that `DVDMonitor`'s callback carries the volume URL through to `JobController`. Invoke `volumeMounted(_:)` with a synthetic `Notification` whose `userInfo` carries a `volumeURLUserInfoKey` pointing at a temp directory containing a `VIDEO_TS` folder, and assert the URL arrives. That test is worth writing and running.

## Plan

### Carry the volume URL through

- `Changeover/DVDMonitor.swift`: change `var onDVDInserted: (() -> Void)?` (line 4) to `((URL) -> Void)?` and pass `url` in the MainActor hop (lines 24-26). `volumeMounted(_:)` stays `@objc nonisolated` — `NSWorkspace` calls it on an arbitrary thread and `Plan.md`'s convention table lists it explicitly as the one `nonisolated` member here. The existing `Task { @MainActor [weak self] in … }` hop is the right shape; keep it.
- Also observe `NSWorkspace.didUnmountNotification` so the app can clear `JobController.insertedDiscURL` when the user ejects by hand. Small, and it prevents a later job from trying to eject a volume that is already gone.
- `Changeover/AppDelegate.swift`, `startDVDMonitor()` (lines 60-65): store the URL on `jobs` ([#0002](0002.md)) before calling `showMetadataEntry()`.

### New file: `Changeover/DiscEjector.swift`

```swift
enum DiscEjector {
    static func eject(volumeURL: URL?) async -> Bool
}
```

Two strategies, in order:

1. **`NSWorkspace.shared.unmountAndEjectDevice(at:)`** (the throwing variant) when a volume URL is known. This is the correct API — it unmounts cleanly and ejects the media. `NSWorkspace` is MainActor-isolated, so this branch runs on MainActor; that is fine, it returns promptly.
2. **`/usr/bin/drutil eject`** as a fallback when no URL was recorded. Run it as a `Process`, structured the same way as `RipController` (`RipController.swift:17-24`) — a `Process` with `executableURL`, a `Pipe`, and a `terminationHandler`. That branch shells out and belongs in a `nonisolated static` function.

So the type is a mix: a MainActor entry point that tries the workspace API and falls back to a `nonisolated` process call. Do not make it an `actor`; `Plan.md` is explicit that types with no reason to leave MainActor stay plain.

`drutil eject` ejects the default drive regardless of which volume it corresponds to. On a single-drive machine that is acceptable as a fallback, but prefer the volume-URL path — and say so in a comment, because someone will otherwise "simplify" it to just `drutil`.

### Where it is called

`DVDPipeline.run()`, on the success path only, after cleanup ([#0004](0004.md)) and before the notification ([#0006](0006.md)). Guard on there actually being a running disc job.

### Risks

- **`unmountAndEjectDevice` fails while something holds the volume.** `makemkvcon` reads the disc directly; confirm the rip process has terminated before ejecting. It has — `RipController` only resumes from `terminationHandler` (`RipController.swift:44-54`) — but do not restructure that code without preserving the property. If the unmount still fails, report the real reason ("a file on the disc is still in use") rather than falling straight through to `drutil`, which will fail too.
- **Do not fail the job on a failed eject.** The movie is already in Plex. Log it, notify anyway, and say the disc could not be ejected.
- **Do not eject on failure.** A disc that failed to rip should stay in the drive for a retry; ejecting it is actively hostile.
- Sandbox is already off (`ENABLE_APP_SANDBOX = NO`), so neither strategy needs an entitlement — but note that the app is an `LSUIElement` accessory, so any error must reach the log or the notification rather than an alert nobody will see.
