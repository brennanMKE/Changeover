## Description

Nothing in the app ejects the disc — there is no `drutil`, no `unmountAndEjectDevice`, no eject path at all (`Plan.md` 11.4 is unchecked). Worse, `DVDMonitor` computes the mounted volume's URL and then discards it (`DVDMonitor.swift:18`, callback typed `(() -> Void)?` at line 4), so the app does not even retain which volume the current job came from.

## Root cause

Two things were true when this issue was filed and are no longer true. #0013 replaced `DVDMonitor`'s bare `NSWorkspace` callback with a `DiscInsertion` (mount URL, device node, disc identity) that #0002's `JobController.insertedDisc` retains, and #0014 made `DVDPipeline.disc` a non-optional `URL` that a job cannot start without. So the volume-URL half of this ticket — "carry the mount URL through so the eject step knows what to eject" — was already done by the time this was implemented; only the actual eject step was still missing. There was no `DiscEjector`, and no call to any eject API anywhere in the pipeline.

## Fix

Added `Changeover/DiscEjector.swift`. Two pure, unit-testable seams plus the real `DiskArbitration` call:

- `shouldEject(outcome: JobOutcome) -> Bool` — `true` only for `.succeeded`. Never eject on failure, so a disc that didn't rip stays in for a retry (the plan's own risk note). In practice this is also enforced structurally: the call site in `DVDPipeline.run()` only exists inside the success path.
- `classify(status: DAReturn, statusString: String?, action: String) -> Outcome` — turns a raw `DAReturn` plus the dissenter's status string into `.ejected` / `.busy(message:)` / `.failed(message:)`, with no `DiskArbitration` dependency of its own. `kDAReturnBusy` and `kDAReturnExclusiveAccess` both classify as `.busy` (something still has the disc open); everything else non-success is `.failed`.
- `eject(volumeURL: URL) async -> Outcome` — the real hardware step. Creates a private `DASession`, resolves the mounted volume with `DADiskCreateFromVolumePath`, then resolves the **whole-disk** object with `DADiskCopyWholeDisk` before calling `DADiskUnmount(_, kDADiskUnmountOptionWhole, ...)` and `DADiskEject`.

**Plan deviations:**

1. **No `drutil` fallback.** The Plan's second strategy ("`drutil eject` as a fallback when no URL is known") is dead code given #0013/#0014: `DVDPipeline.disc` is always a real, populated `URL` by the time a job runs, so the "volume URL unknown" branch the fallback exists for can never be reached in this pipeline. Implementing it anyway would add an untestable, unreachable path. `## Notes` at the top of the issue and the orchestrator's own steer for this pass both pointed the same direction: prefer the `DiskArbitration` seam, skip `drutil` unless the plan argues for a case that still applies — it doesn't.
2. **`DiskArbitration`, not `NSWorkspace.unmountAndEjectDevice(at:)`.** Keeps this file off MainActor entirely (an eject is background filesystem work with no reason to touch the main thread) and, more importantly, `DADissenterGetStatusString` is what turns a failed eject into an actionable message ("disc busy") — `NSWorkspace`'s throwing API only offers an `NSError`, not the finer-grained "why," and mirrors the exact framework `DVDMonitor` already uses to detect the disc in the first place.
3. **No `NSWorkspace.didUnmountNotification` observer added.** The plan called for one so `JobController.insertedDisc` clears on a manual eject. `DVDMonitor` already has this via `DARegisterDiskDisappearedCallback` → `onDVDRemoved` (#0013), wired to `AppDelegate.startDVDMonitor()` clearing `jobs.insertedDisc`. Ejecting through `DiscEjector` triggers the same disk-disappeared event, so this fires for free — nothing new was needed.
4. **`DADiskCopyWholeDisk` step not in the original plan.** Found during verification, not anticipated by the plan: issuing `kDADiskUnmountOptionWhole` against the per-volume `DADisk` `DADiskCreateFromVolumePath` returns comes back `kDAReturnUnsupported` against a real (GPT-partitioned) disk image. `DADiskCopyWholeDisk` resolves to the whole-disk object first, which is what the "whole" unmount option is actually meant to be issued against. See `## Gotchas`.

Wired into `DVDPipeline.run()` right after `PlexOrganizer.move` succeeds, before the final "Done" log line — #0004 (cleanup) and #0006 (notification) are both still `open`, so today this is the last pipeline step, not the middle of `move → cleanup → eject → notify` the Plan describes. Re-ordering will fall out naturally once #0004/#0006 land; nothing here assumes it's the last step.

- **The `DVDPipeline.swift` call site landed in someone else's commit.** This session ran concurrently with another implementer working #0012 in the same working copy (not a worktree). My in-progress edit to `DVDPipeline.swift` (the `DiscEjector.eject` call) was present, unstaged, in the shared working tree when that session committed its own `DVDPipeline.swift`/`PlexOrganizer.swift` change (`7af2503 #0012 Move the Plex move off the main actor`) — its broad staging swept my hunk in along with theirs. Nothing was lost or duplicated; the reviewer should look at both commits' diffs for the complete picture of what this issue changed. `cd895d0` itself contains only the two new files.
- **`kDAReturnUnsupported` on the per-volume `DADisk`.** Cost real debugging time: the first version called `DADiskUnmount(volumeDisk, kDADiskUnmountOptionWhole, ...)` directly, which is exactly what the Plan describes, and it fails against a real (partitioned) disk image with `kDAReturnUnsupported` (`-119930868`, i.e. `0xF8DA000C`). A DVD commonly has no partition scheme at all, so its whole disk and its one volume are frequently the same underlying device and this might never have surfaced against real hardware — but resolving the whole disk explicitly via `DADiskCopyWholeDisk` is correct either way and was cheap once found.


## Long Description

This is the item that makes the Phase 1 demo mean something. "Insert a disc and walk away" is not true while the last step of every job is walking back to the mini to press the eject button. It is also the signal the whole multi-disc story in Phase 3 is built on: the tray opening is how the user knows it is time to swap.

`DVDMonitor.volumeMounted(_:)` (`DVDMonitor.swift:15-27`) extracts `url` from `NSWorkspace.volumeURLUserInfoKey`, uses it only to test for a `VIDEO_TS` directory, then calls a zero-argument closure. `AppDelegate.startDVDMonitor()` (`AppDelegate.swift:60-65`) forwards that to `showMetadataEntry()`. By the time a job finishes, nothing knows what was mounted.

There is also no unmount handling — the app never learns a disc was removed, so state cannot be reset when the user ejects manually.

## Steps to reproduce

1. Insert a DVD; the metadata window appears.
2. Search, select, Start Ripping, and let the job run to completion.
3. Observe the log's final line: `"── Done. Scan your Plex Movies library to pick up the new title."`
4. The disc is still mounted on the Desktop and still in the drive.
5. Walk to the machine and eject it by hand before the next disc can go in.

## Expected behavior

On a job that fully succeeded, the volume is unmounted and the drive opens, and the log says so. On a failed job the disc stays in, so it can be retried without re-inserting. A failed eject is reported but does not turn a successful job into a failed one.

## Actual behavior

The disc is never ejected under any outcome, and the app has not retained enough information to eject the right volume even if it wanted to.

## Notes

**This is the one Phase 1 ticket with essentially no automated verification.** It is hardware behavior: an external USB optical drive, a physical disc, and a tray that either opens or does not. `## Verification` must say plainly that it was verified manually, on which machine, with which disc, and that a failed-job run was also checked to confirm the disc stays in.

The one testable seam: that `DVDMonitor`'s callback carries the volume URL through to `JobController`. Invoke `volumeMounted(_:)` with a synthetic `Notification` whose `userInfo` carries a `volumeURLUserInfoKey` pointing at a temp directory containing a `VIDEO_TS` folder, and assert the URL arrives. That test is worth writing and running.

## Plan

### Carry the volume URL through

- `Changeover/DVDMonitor.swift`: change `var onDVDInserted: (() -> Void)?` (line 4) to `((URL) -> Void)?` and pass `url` in the MainActor hop (lines 24-26). `volumeMounted(_:)` stays `@objc nonisolated` — `NSWorkspace` calls it on an arbitrary thread and `Plan.md`'s convention table lists it explicitly as the one `nonisolated` member here. The existing `Task { @MainActor [weak self] in … }` hop is the right shape; keep it.
- Also observe `NSWorkspace.didUnmountNotification` so the app can clear `JobController.insertedDiscURL` when the user ejects by hand. Small, and it prevents a later job from trying to eject a volume that is already gone.
- `Changeover/AppDelegate.swift`, `startDVDMonitor()` (lines 60-65): store the URL on `jobs` ([#0002](0002.md)) before calling `showMetadataEntry()`.

### New file: `Changeover/DiscEjector.swift`

```swift
enum DiscEjector {
    static func eject(volumeURL: URL?) async -> Bool
}
```

Two strategies, in order:

1. **`NSWorkspace.shared.unmountAndEjectDevice(at:)`** (the throwing variant) when a volume URL is known. This is the correct API — it unmounts cleanly and ejects the media. `NSWorkspace` is MainActor-isolated, so this branch runs on MainActor; that is fine, it returns promptly.
2. **`/usr/bin/drutil eject`** as a fallback when no URL was recorded. Run it as a `Process`, structured the same way as `RipController` (`RipController.swift:17-24`) — a `Process` with `executableURL`, a `Pipe`, and a `terminationHandler`. That branch shells out and belongs in a `nonisolated static` function.

So the type is a mix: a MainActor entry point that tries the workspace API and falls back to a `nonisolated` process call. Do not make it an `actor`; `Plan.md` is explicit that types with no reason to leave MainActor stay plain.

`drutil eject` ejects the default drive regardless of which volume it corresponds to. On a single-drive machine that is acceptable as a fallback, but prefer the volume-URL path — and say so in a comment, because someone will otherwise "simplify" it to just `drutil`.

### Where it is called

`DVDPipeline.run()`, on the success path only, after cleanup ([#0004](0004.md)) and before the notification ([#0006](0006.md)). Guard on there actually being a running disc job.

### Risks

- **`unmountAndEjectDevice` fails while something holds the volume.** `makemkvcon` reads the disc directly; confirm the rip process has terminated before ejecting. It has — `RipController` only resumes from `terminationHandler` (`RipController.swift:44-54`) — but do not restructure that code without preserving the property. If the unmount still fails, report the real reason ("a file on the disc is still in use") rather than falling straight through to `drutil`, which will fail too.
- **Do not fail the job on a failed eject.** The movie is already in Plex. Log it, notify anyway, and say the disc could not be ejected.
- **Do not eject on failure.** A disc that failed to rip should stay in the drive for a retry; ejecting it is actively hostile.
- Sandbox is already off (`ENABLE_APP_SANDBOX = NO`), so neither strategy needs an entitlement — but note that the app is an `LSUIElement` accessory, so any error must reach the log or the notification rather than an alert nobody will see.

## Carry-over from the #0013 review — 2026-09-12

The #0013 phase 3 reviewer approved the re-pass but recorded two follow-ups
without bouncing. Fold them into this ticket, since it is the next change to
touch `DVDMonitor` and its helpers:

1. **`OutputAccumulator` isolation.** `OutputAccumulator`
   (`LSDVDIdentity.swift:26`) is MainActor-isolated by the project default but is
   used from nonisolated code and from the `@Sendable` `readabilityHandler`,
   producing three compiler warnings (lines 91, 104, 127). Mark it `nonisolated`.
   It is safe today only because it is lock-protected and the target is in
   Swift 5 language mode.
2. **The retained `Box` is still explained wrongly.** The `deinit` comment
   (`DVDMonitor.swift:121-123`) still says there is "no separate invalidate entry
   point", and the Box justification says there is no non-blocking way to wait for
   an in-flight callback. Both are false: `DASessionSetDispatchQueue(session, nil)`
   followed by `queue.async { release }` on the serial queue orders the release
   after any executing handler, without blocking. The retained `Box` is correct
   and bounded; only the explanation needs fixing. Either correct the comment, or
   adopt the ordered release with a stress test.

Hardening the reviewer suggested, not required: after `waitUntilExit()` in
`LSDVDIdentity`, drain the pipe's final chunk (or wait on an EOF-signalled group)
so the tail can't be dropped under dispatch-pool starvation; and guard against
`waitUntilExit()` not returning under heavy concurrent spawning. Neither was seen
in production conditions (the DiskArbitration queue is serial).
