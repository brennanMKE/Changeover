## Description

Found by the Phase 3 review. When the disc leaves the drive mid-job — the drive's own eject button, a tray bump, a USB hiccup — `DVDMonitor.onDVDRemoved` fires and `AppDelegate` calls `jobs.removeDisc()` (`Changeover/AppDelegate.swift:113-115`). That method clears `insertedDisc`, `scanState` and every selection (`Changeover/JobController.swift:773-783`) and never looks at `current`. The running `DVDPipeline` learns nothing. What happens next depends on the drive:

- If `HandBrakeCLI`'s reads fail, the job ends `failed` with a disc-shaped reason (`.discUnreadable` or `.toolExited`), the notification says the disc could not be read, and `DiscReliabilityLog` writes a `failed` record against that disc's identity — a human act recorded as a bad disc.
- If the reads block, HandBrake goes silent and the job sits in "Encoding" until the 30-minute inactivity watchdog (#0009) fails it as `.unknown("…produced no output for 30 minutes…")`.

In neither case does any log line say the disc was removed. The only trace is that the metadata window went blank. The `FallbackPolicy.discStillPresent` closure (`Changeover/DVDPipeline.swift:506-510`) does the right thing — no MakeMKV attempt on a disc that is gone — but that is the only place the pipeline notices.

#0045's plan refresh specified this case ("When `onDVDRemoved` fires while `isRunning`, log a `⚠︎ Disc removed while a job was running` milestone and let HandBrake fail on its own"), and the #0040 orchestrator decided against a new `FailureReason.discRemoved` so older decoders keep working. The re-scope of #0045 to the manual Eject then dropped it, and nothing else picked it up. #0046's manual check 3 ("pull the disc mid-encode, then press Cancel, record how long HandBrakeCLI takes to exit") is about to exercise exactly this on joe with no code behind it.

  `DiscRemovedDuringJobPipelineTests

## Root cause

`JobController.removeDisc()` (`Changeover/JobController.swift`) cleared
`insertedDisc`, `scanState` and every selection whenever `DVDMonitor
.onDVDRemoved` fired, but never looked at `current` — the running job (and
its `DVDPipeline`) learned nothing. A disc pulled mid-job either failed
minutes later once `HandBrakeCLI`'s reads gave out, classified as a
disc-shaped reason and recorded by `DiscReliabilityLog` as a bad disc, or
went silent until #0009's 30-minute inactivity watchdog. No log line ever
said the disc had been removed. #0045's plan refresh had specified the
milestone; the ticket's later re-scope to the manual Eject dropped it, and
nothing else picked it back up.

## Fix

**Notice it, in one place.** `JobController.removeDisc()` now checks
`current` first: if a job is running, it calls the new `Job
.markDiscRemoved()` (logs `⚠︎ Disc removed while the job was running` into
*that job's own log*, never the controller's between-job log, and sets a
new host-only `Job.discRemovedDuringJob` flag), then calls `task?.cancel()`
unconditionally. Both the manual-eject path (`ejectDisc()` → `DiscEjector`
→ `DVDMonitor.onDVDRemoved`) and a physical pull (straight to
`DVDMonitor.onDVDRemoved`) funnel through this same `removeDisc()`, so
there is exactly one place that notices and reacts — no separate guard was
needed to "reuse" `isEjecting`/`scanGeneration` per the #0051 handoff; they
were already reset in the same call regardless of path.

**Stop it, through the existing cancel plumbing — chosen over "log only."**
The plan offered two options: (a) log and present only, bounded by the
30-minute watchdog on a blocked read; (b) also cancel, through #0046's real
SIGTERM→SIGKILL path. Took (b), per the plan's own recommendation — an
unattended run should not sit on a pulled disc for half an hour.
`removeDisc()` calls `task?.cancel()` with **no phase check** first (unlike
`cancel(id:)`'s `CancelPolicy`, which refuses during `.organizing`):
`DVDPipeline.run()` never checks `Task.isCancelled` inside
`PlexOrganizer.move` (the move is already reading the encoded file off
local disk, not the disc, and finishes unaffected — #0041's `organizing`
has no outgoing `cancelled` edge for exactly this reason), and the extras
loop's existing #0046 cancellation points already end the job `.succeeded`
with the remaining extras skipped and logged (the feature is already in
Plex). So one unconditional cancel does the right thing in every phase with
**no new `JobPhase` transitions needed** — it cuts a blocked or
still-reading encode short instead of waiting out the watchdog, and is a
harmless no-op everywhere a cancel wouldn't change the outcome anyway.

**No new `FailureReason` case — the #0040 decision stands.** `JobOutcome`
stays wire format. `Job.discRemovedDuringJob` is a new, host-only,
`private(set)` flag, deliberately **not** on `JobSnapshot`. The fact is
carried beside the outcome, exactly as the plan specified:

- `JobController.JobContext` and `DVDPipeline` gain a
  `discRemoved: @MainActor () -> Bool` closure — the same shape
  `FallbackPolicy`'s `discStillPresent` already uses — bound in `start()`
  to `job.discRemovedDuringJob`. `DVDPipeline.run()` reads it once, inside
  its `finish(_:)` helper, and when `true` overwrites `decisionRecord` to
  `"discRemoved"` — overriding whatever it already held, including
  `"cancelled"` (set at the existing boundary-2/boundary-3
  `Task.isCancelled` checks) — before the `DiscReliabilityLog.Record` is
  built. The override is unconditional in `finish(_:)`, so it applies
  whatever the outcome turned out to be (a plain failure, a cancelled
  encode, or even a success from an `.organizing`/`.extras` removal),
  matching the plan's "have `DVDPipeline` write `decision: "discRemoved"`
  … when it is true".
- `JobPresentation.make(for:isCancelling:discRemovedDuringJob:)` and
  `JobNotifier.message(for:outcome:discRemovedDuringJob:)` both gained an
  optional parameter (defaulted `false`, so every existing call site
  compiles and behaves unchanged). When the job's outcome settled
  `.cancelled` *and* the flag is set, the history row shows "Disc removed"
  / "The disc was removed while the job was running." (a new
  `JobPresentation.discRemovedDetail` constant shared with the notification
  body) and the notification reads "*Title* (*Year*) — disc removed" /
  "The disc was removed while the job was running. Nothing new was filed
  in Plex." — instead of the generic "Cancelled" / "*Title* (*Year*) was
  cancelled" a plain user cancel shows. A removal during
  `.organizing`/`.extras` still ends `.succeeded` and is presented exactly
  like any other success — the parameter only changes anything once the
  phase actually resolves to `.cancelled`.
- `JobHistoryView`'s two `JobPresentation.make` call sites (`JobHistoryRow`,
  `JobDetailView`) already hold the `Job`, not just its snapshot, so they
  pass `job.discRemovedDuringJob` directly — no new `JobController` lookup
  method was needed. `StatusMenuView`'s `menuSummary`/`menuTone` were left
  untouched: a cancelled-reason outcome (disc-removed or plain) is already
  excluded from "Last job failed — …" by `JobPresentation
  .reportableFailure`, the same rule a plain cancel already gets, and nothing
  in the plan asked for a persistent menu-bar distinction.

**Retry needed no code change.** #0048's `retryDecision(id:)` already
requires the job's own disc back in the drive (`SelectionReset.sameDisc`)
and a completed scan, and already treats `.cancelled` as retryable. Once
the physically-pulled disc is reinserted — a fresh insertion, scanned,
recognised as the same disc by identity — Retry is offered with nothing
new to build. Verified directly in
`DiscRemovedDuringJobTests.retryIsOfferedOnceTheSameDiscIsReinserted`.

**Decisions made (user AFK, delegated), recorded here:**

- **Option (b) — cancel — chosen over log-only**, per the plan's own
  recommendation.
- **No new `FailureReason` case.** The disc-removed fact travels as
  `Job.discRemovedDuringJob` plus the `DiscReliabilityLog.Record.decision`
  string, both additive.
- **`cancellingJobID` is left untouched by `removeDisc()`.** It's scoped to
  the user-initiated Cancel action (`cancel(id:)`), and setting it here
  would conflate "the user asked" with "the disc left" for a flag several
  views read. The brief transient window before the job reaches a terminal
  phase shows the ordinary phase label (e.g. "Encoding *Title*"), not
  "Cancelling…" — once the job actually settles, the
  `discRemovedDuringJob` override on `JobPresentation`/`JobNotifier` makes
  the final state read correctly regardless.
- **Eject's unbounded wait for a stuck scan (`await inFlightScan?.value` in
  `ejectDisc()`) was not bounded.** The handoff asked to bound it "if
  cheap, otherwise record it" — it's a #0051-scan concern orthogonal to
  #0052's job-cancellation scope, and touching it risked regressing
  #0051's own tested behaviour for no benefit to this ticket. Left as a
  follow-up, not implemented here.
- **`EjectPolicy`/manual `ejectDisc()` are unchanged.** A manual eject
  still refuses outright while a job runs (`EjectPolicy.jobRunningReason`,
  #0045's decision) — this ticket only changes what happens when the disc
  actually leaves the drive (`removeDisc()`), whether that departure was
  triggered by a successful eject elsewhere or a physical pull. There is
  still no path where "Eject Disc" ends a running job.

## Steps to reproduce

1. Start a job on a disc.
2. Press the drive's eject button, or otherwise remove the disc, a minute in.
3. Read the job's log and, when it ends, its failure headline, the notification and `~/Library/Logs/Changeover/disc-reliability.jsonl`.

## Expected behavior

The job's own log carries a `⚠︎ Disc removed while the job was running` milestone at the moment of removal. The failure headline and notification say the disc was removed, not that it was unreadable or that HandBrake timed out. The reliability record is marked so the disc is not counted as unreadable. The job ends promptly rather than after 30 minutes of silence.

## Actual behavior

Nothing is logged. The job ends as a disc read failure or a 30-minute timeout, the notification blames the disc or the tool, and the reliability log records a disc failure.

## Plan

No new `FailureReason` case (the #0040 decision stands; `JobOutcome` is wire format). The fact is carried beside the outcome instead.

- **Notice it.** In `JobController.removeDisc()`, when `current` exists (under option A the job's disc is the only disc), append `⚠︎ Disc removed while the job was running` to `current.log` — the job's log, not `controllerLog` — and set a new `Job.discRemovedDuringJob = true` (host-only; not on `JobSnapshot` unless #0060 wants it).
- **Present it.** `FailurePresenter.message(for:)` gains an optional "disc removed" context, or `JobController.finish` / `JobNotifier` prepend it: headline "The disc was removed during the job", body unchanged. `JobPresentation.make(for:)` shows the same in the history row's detail, so #0048's view and the notification agree.
- **Record it.** Give `JobContext` a `discRemoved: @MainActor () -> Bool` closure (the shape `discStillPresent` already uses) and have `DVDPipeline` write `decision: "discRemoved"` into the `DiscReliabilityLog.Record` when it is true. `decision` is a `String?`, so this is additive and no decoder breaks; reliability analysis filters it out the way it already must filter `"cancelled"` (#0046).
- **End it promptly — user's call, two options.** (a) Log and present only; let HandBrake fail on its own, bounded by the 30-minute watchdog in the blocked-read case. (b) On removal during `.encoding`/`.fallback`/`.extras`, also call `task?.cancel()`, so the process is stopped through #0046's SIGTERM→SIGKILL path and the job ends within seconds. The cost of (b) is that the wire outcome is then `.cancelled` and the history row reads "Cancelled" unless the presentation reads `discRemovedDuringJob` first. The review recommends (b) with the presentation override: an unattended run should not sit on a pulled disc for half an hour.
- **Tests** (`JobControllerTests`, gated runner, no disc): `removeDisc()` while a job runs appends the milestone to that job's log and to nothing else, and sets the flag; with no job running it logs nothing into any job; the notification text and history detail for a flagged failure; the reliability record carries `decision: "discRemoved"` when the closure returns true (pipeline test against the stub `HandBrakeCLI`, redirecting `DiscReliabilityLog` to a temp file as the fallback tests do). If option (b): the job ends within the test's grace and the next `start` is accepted.
- **Manual on joe:** #0046's check 3, now with an expected result: the milestone appears at once, the job ends with the "disc was removed" headline, and the reliability line says `discRemoved`.
